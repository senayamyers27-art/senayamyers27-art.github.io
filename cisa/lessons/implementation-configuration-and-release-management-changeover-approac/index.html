Implementation configuration and release management; changeover approaches

▶ Watch the overview video

Last reviewed September 29, 2026 · Leer en español

Going live is one of the riskiest moments in a system's life. Implementation planning, configuration management and release management reduce the chance that the wrong version, a bad setting or an untested change reaches production.

Configuration management records the approved configuration of each component, such as software versions, settings and dependencies, usually in a configuration management database. Version control tracks every change to code and configuration files. Release management packages tested changes into releases, schedules them, and moves them to production through a controlled process with approval, communication and rollback plans. Segregation of duties matters here: developers should not move their own code into production, and production libraries should be protected from direct changes.

Changeover, or cutover, approaches differ in risk and cost. Parallel changeover runs old and new systems together and compares results; it is the safest but most expensive. Phased changeover introduces the new system module by module or site by site, spreading risk. Pilot changeover runs the new system in one location or group first, then rolls out. Direct or abrupt changeover (big bang) switches everything at once; it is the cheapest and quickest but the riskiest, because there is no easy fallback.

Whatever the approach, the organization should have go/no-go criteria, a rollback plan, verified data conversion, trained users and support ready. The auditor checks that the release was authorized, the version deployed matches the tested version, and fallback arrangements existed.

Key terms

Release management
The process of planning, packaging, approving and deploying tested changes into production.
Parallel changeover
Running the old and new systems at the same time and comparing results before switching fully.
Direct cutover
Switching from the old system to the new one at a single point in time with no parallel running.
Rollback plan
A prepared procedure to return to the previous state if a release fails.
Real-world example

A utility company introduces new billing software region by region over six months. Each region goes live only after the previous one's first billing cycle reconciles, and a rollback plan lets any region return to the old system within a day.

Exam tip: Parallel is lowest risk and highest cost; direct cutover is highest risk and lowest cost. Phased and pilot sit in between.

Check yourself

Which changeover approach provides the best fallback?

Parallel changeover, because the old system keeps running and results can be compared.

Why confirm that the version deployed matches the version tested?

To make sure untested or unauthorized code did not reach production.
