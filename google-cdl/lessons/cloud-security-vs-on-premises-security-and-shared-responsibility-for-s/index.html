Cloud security vs on-premises security, and shared responsibility for security

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

In a traditional on-premises environment, the organization is responsible for every layer of security: guarding the building, securing the hardware and its supply chain, patching firmware and operating systems, protecting the network, managing identities and protecting the data. Doing all of this well requires large budgets and specialist staff that many organizations do not have.

In the cloud, security is shared. Google secures the infrastructure: physical data centers, custom hardware, the global network, the storage systems and the virtualization layer. This is backed by very large investments and teams of security specialists, and by operating at a scale where threats are detected across many customers. For many organizations, this makes the foundation more secure than what they could build themselves.

The customer is always responsible for its data, identities and access, and the configuration of the services it uses. How much more it manages depends on the service model. On Compute Engine (IaaS) the customer also secures the guest OS, applications and firewall rules. On serverless or PaaS, Google handles the OS and runtime. On SaaS, the customer mainly manages users, settings and data.

The cloud also changes how security work is done. Resources are created in minutes by many teams, so security must be automated rather than handled only by manual review. Identity becomes the main perimeter, because services are reached over the internet rather than only from inside an office network. Configuration errors, such as public buckets or overly broad permissions, become one of the most common risks. On the positive side, the cloud offers central logging, consistent policies across the organization, and security tools that would be hard to build on-premises.

Google Cloud's shared fate approach adds help on top of the split: secure-by-default settings, security blueprints and recommendations, and tools such as Security Command Center that point out risks in a customer's own configuration.

Key terms

Shared responsibility
The division of security duties between the cloud provider and the customer.
Shared fate
Google Cloud's approach of actively helping customers secure their workloads with defaults, tools and guidance.
Attack surface
All the points where an attacker could try to get into a system.
Identity perimeter
Treating identity and access checks, rather than the network edge, as the main security boundary.
Real-world example

A retailer moving from its own data center no longer manages locks, cameras and hardware firmware, because Google handles those. Its security team now focuses on IAM, secure configurations, monitoring with Security Command Center and training developers, which reduces its overall risk.

Exam tip: Moving to the cloud shifts infrastructure security to Google, but data, identities, access and configuration stay with the customer in every model.

Check yourself

Name two security tasks Google handles that an on-premises organization must do itself.

Physical data center security, hardware and supply chain security, and securing the network and virtualization layers (any two).

Why does identity become more important in the cloud?

Services are reached over the internet from anywhere, so verifying who is making each request becomes the main line of defense.
