Containers: what they are and why they make applications portable

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

A container is a lightweight, standalone package that includes an application's code together with everything it needs to run: the runtime, libraries, system tools and settings. Containers solve a long-standing problem in software, summed up as 'it works on my machine'. Because the container carries its dependencies, the application behaves the same on a developer's laptop, in a test environment, in a data center or in any cloud.

Containers are often compared with virtual machines. A VM virtualizes the hardware and includes a full guest operating system for each application, so it is relatively large and slow to start. Containers virtualize at the operating system level: many containers share the host machine's OS kernel while staying isolated from one another. That makes them much smaller, faster to start (often in seconds or less) and more efficient, since more of them fit on the same hardware.

A container image is the read-only template, built from a set of instructions (for example a Dockerfile), and a container is a running instance of it. Images are stored in a registry, such as Google Cloud's Artifact Registry, from where they can be pulled and run anywhere. Because images are versioned and immutable, teams can deploy exactly what they tested and roll back easily.

These properties make containers a foundation of application modernization. They fit microservices, where each service is packaged and deployed independently. They support consistent CI/CD pipelines. And they enable hybrid and multicloud strategies, because the same image can run in different environments.

Running a few containers is simple; running thousands across many machines needs orchestration: scheduling containers onto servers, restarting failed ones, scaling and networking them. Kubernetes is the open source standard for that, and Google Kubernetes Engine is Google Cloud's managed version. Cloud Run runs containers without any cluster to manage.

Key terms

Container
A lightweight package of an application and its dependencies that runs consistently in any environment.
Container image
A read-only, versioned template from which containers are started.
Artifact Registry
Google Cloud's service for storing and managing container images and other build artifacts.
Orchestration
Automated scheduling, scaling, networking and healing of many containers across machines.
Real-world example

A development team packages its booking service as a container image. The same image runs on developers' laptops, in the test environment and in production on GKE, so a bug found in testing reproduces exactly and a fix is deployed by pushing a new image version.

Exam tip: Portability and consistency across environments are the key container benefits. Containers share the host kernel, so they are lighter and faster to start than VMs, which each carry a full guest OS.

Check yourself

Why do containers start faster than VMs?

They share the host operating system kernel instead of booting a full guest OS.

What is the difference between a container image and a container?

The image is the read-only template; a container is a running instance of that image.
