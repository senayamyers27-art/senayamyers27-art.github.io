Google Cloud Observability: Cloud Monitoring, Cloud Logging, Cloud Trace and Error Reporting

▶ Watch the overview video

Last reviewed September 25, 2026

You cannot run a reliable service without knowing how it behaves. Observability is the ability to understand the internal state of a system from the data it produces, mainly metrics, logs and traces. Google Cloud Observability (formerly known as Stackdriver and then Cloud Operations suite) is a set of integrated services for this. Much of the data is collected automatically from Google Cloud services, and agents or libraries collect more from VMs and applications.

Cloud Monitoring collects metrics: numeric measurements over time, such as CPU utilization, request count, latency and error rate, from Google Cloud services, applications, other clouds and on-premises systems. You can build dashboards, create uptime checks that test whether an endpoint responds from locations around the world, and define alerting policies that notify people through email, SMS, chat tools or incident management systems when conditions are met. It also supports defining SLOs and tracking error budgets.

Cloud Logging collects, stores and lets you search log entries from Google Cloud services, VMs, containers and applications, including Cloud Audit Logs. The Logs Explorer lets you filter and query logs, log-based metrics turn log patterns into metrics for alerting, and log sinks route logs to Cloud Storage, BigQuery or Pub/Sub for long-term retention or analysis.

Cloud Trace is a distributed tracing system. It follows individual requests as they travel through different services, recording how long each step takes, which helps find the source of latency in microservices architectures. Error Reporting groups and counts application errors and crashes so developers see which problems are new or most frequent. Cloud Profiler analyzes the CPU and memory use of running code to find inefficient functions.

Together, these tools support SRE practices: measuring SLIs, alerting on symptoms users feel, investigating incidents and improving performance. The key distinction: metrics tell you something is wrong, logs tell you what happened, and traces show where time went in a request.

Key terms

Observability
The ability to understand a system's internal state from its metrics, logs and traces.
Cloud Monitoring
Collects metrics and provides dashboards, uptime checks and alerts.
Cloud Logging
Collects, stores, searches and routes log data.
Cloud Trace
Distributed tracing that shows how long each step of a request takes across services.
Real-world example

Customers report slow checkouts. A Cloud Monitoring alert confirms latency has risen, Cloud Trace shows most of the delay is in calls to the inventory service, and Cloud Logging reveals repeated timeout errors from that service's database connection. The team fixes the connection pool within an hour.

Exam tip: Metrics, dashboards and alerts: Cloud Monitoring. Searching and storing logs: Cloud Logging. Finding latency across microservices: Cloud Trace. Grouping application errors: Error Reporting.

Check yourself

Which tool would show which microservice is slowing down a request?

Cloud Trace.

How can you keep logs for years for compliance at low cost?

Route them with a log sink to Cloud Storage (for example in a colder storage class) or to BigQuery for analysis.
