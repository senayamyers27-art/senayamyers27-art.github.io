DevOps and Site Reliability Engineering (SRE) principles

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

Traditionally, developers wanted to release new features quickly, while operations teams wanted stability and resisted change. The result was slow releases, friction and blame. DevOps and Site Reliability Engineering are approaches that resolve this tension, and the exam expects you to know their main ideas.

DevOps is a culture and set of practices that bring development and operations together with shared goals and responsibilities. Key practices include small, frequent releases; automation of building, testing and deployment through continuous integration and continuous delivery (CI/CD); infrastructure as code; monitoring and fast feedback from production; and collaboration across teams. The aim is to deliver value to users faster and more reliably at the same time.

Site Reliability Engineering (SRE) is Google's way of running production systems, developed internally and shared publicly through books and practices. It is often described as a specific implementation of DevOps ideas. SRE treats operations as a software engineering problem: engineers write software and automation to run systems reliably at scale.

Core SRE principles include: defining reliability targets with service level objectives (SLOs) based on what users need, rather than aiming for 100%; using error budgets to balance feature releases and reliability; reducing toil, the repetitive manual work that scales with the service, by automating it; monitoring the signals that matter to users; practicing gradual rollouts and quick rollback so changes are safer; and running blameless postmortems after incidents to learn and fix underlying causes without punishing individuals.

For organizations moving to the cloud, these practices matter as much as the technology. Managed services reduce toil, CI/CD tools such as Cloud Build and Cloud Deploy automate delivery, and Google Cloud Observability provides the monitoring SRE depends on. Adopting SRE also usually means cultural change: accepting that failure will happen, learning from it openly and sharing responsibility for reliability.

Key terms

DevOps
A culture and practices uniting development and operations to deliver changes quickly and reliably.
Site Reliability Engineering (SRE)
Google's approach to running reliable systems by applying software engineering to operations.
Toil
Manual, repetitive operational work that scales with the service and can be automated.
Blameless postmortem
An incident review that focuses on causes and fixes, not on blaming individuals.
Real-world example

After a failed release causes an outage, an online bank holds a blameless postmortem. It finds that manual deployment steps were skipped, automates the deployment with a CI/CD pipeline, adds automatic rollback when error rates rise, and sets an SLO for its login service.

Exam tip: SRE is Google's implementation of DevOps principles. Key words to recognize: SLOs, error budgets, toil reduction, automation and blameless postmortems.

Check yourself

What is toil in SRE, and what should be done about it?

Repetitive manual operational work that scales with the service; SRE teams automate it to free time for engineering.

Why are postmortems blameless?

So people share what really happened, allowing the organization to fix the systemic causes rather than hide problems.
