Monoliths vs microservices and application modernization

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

A monolithic application is built and deployed as a single unit. All its features, such as user accounts, catalog, cart, payments and notifications, live in one codebase and run as one process or package. Monoliths are simple to start with, but as they grow they become hard to change: a small update requires testing and redeploying the whole application, one bug or overloaded feature can bring everything down, and scaling means copying the entire application even if only one part is busy. Large teams working in one codebase also slow one another down.

A microservices architecture splits an application into small, independent services, each responsible for one business capability and owned by a small team. Services communicate over well-defined APIs or through messaging such as Pub/Sub. Each service can be developed, deployed and scaled independently, and can even use a different language or database suited to its job. If the recommendation service fails, customers can still check out.

Microservices bring their own costs: more moving parts to monitor, network calls between services, distributed data and more complex testing. They pay off for large, fast-changing applications and multiple teams, not necessarily for small, simple ones. Containers, Kubernetes, Cloud Run, API management and observability tools make them practical.

Organizations rarely rewrite a monolith all at once. A common approach, sometimes called the strangler pattern, gradually carves features out into new services behind an API or load balancer, while the old application keeps running, until the monolith is small enough to retire.

Modernization also includes practices. Continuous integration and continuous delivery (CI/CD) automate building, testing and deploying each service. Infrastructure as code defines environments in version-controlled files. Together with DevOps culture, these let teams release small changes frequently and safely, which is the real business goal of modernization.

Key terms

Monolith
An application built and deployed as a single unit.
Microservices
An architecture of small, independently deployable services that communicate through APIs.
Strangler pattern
Gradually replacing parts of a legacy system with new services until the old system can be retired.
Infrastructure as code
Defining and managing infrastructure through version-controlled configuration files.
Real-world example

An online retailer's monolith needs a full weekend release for any change. The team first moves the product search feature into a separate service on Cloud Run behind the same URL, then the cart, then payments. Each team now releases its own service several times a week.

Exam tip: Independent deployment, independent scaling and fault isolation are the key microservices benefits. The trade-off is more operational complexity, so they suit large, fast-changing applications.
