Identidad federada con terceros: SAML, OAuth 2.0 y OIDC

La identidad federada permite que los usuarios se autentiquen una vez con su organización de origen y luego usen servicios de otras organizaciones sin crear cuentas separadas en ellas. Las organizaciones acuerdan de antemano confiar en las afirmaciones de identidad de las demás. Esto reduce la proliferación de contraseñas, centraliza la baja de cuentas (deshabilitas la cuenta de origen y el acceso federado se detiene) y traslada la autenticación a la parte mejor ubicada para hacerla bien. El costo es una dependencia de confianza: si el proveedor de identidad se compromete o se configura mal, todos los servicios que dependen de él quedan expuestos.

En toda federación aparecen dos roles. El proveedor de identidad (IdP) autentica al usuario y emite una declaración firmada sobre él. El proveedor de servicios (SP), llamado parte que confía (relying party, RP) en OpenID Connect, consume esa declaración y concede el acceso. La confianza se establece por adelantado mediante el intercambio de metadatos, incluidos los certificados que se usan para firmar las aserciones y los puntos de conexión a los que se redirige. El aprovisionamiento justo a tiempo puede crear una cuenta en el SP a partir de los atributos de la aserción en el primer inicio de sesión, mientras que estándares como el System for Cross-domain Identity Management (SCIM) automatizan por adelantado la creación y la eliminación de cuentas.

Security Assertion Markup Language (SAML) 2.0 es un estándar basado en XML muy usado para el inicio de sesión único web en las empresas. En un flujo típico iniciado por el SP, el usuario visita la aplicación de software como servicio, es redirigido al IdP corporativo, se autentica allí y es redirigido de vuelta con una aserción SAML firmada digitalmente que contiene su identidad y sus atributos. El SP valida la firma, la audiencia prevista y el período de validez antes de crear una sesión. Las aserciones también pueden cifrarse. SAML es maduro y común para el acceso del personal a las aplicaciones en la nube.

OAuth 2.0 se malinterpreta con frecuencia. Es un marco de autorización, no un protocolo de autenticación. Permite que el propietario de un recurso conceda a una aplicación cliente un acceso delegado y limitado a recursos en un servidor de recursos sin compartir una contraseña. Un servidor de autorización emite un token de acceso con alcances (scopes) específicos, como el permiso para leer un calendario, y el cliente presenta ese token a la API. El flujo de código de autorización con Proof Key for Code Exchange (PKCE) es el patrón recomendado para la mayoría de las aplicaciones, mientras que el antiguo flujo implícito se desaconseja. Los tokens deben ser de corta duración y de alcance limitado, y los tokens de actualización (refresh tokens) necesitan una protección robusta.

OpenID Connect (OIDC) agrega una capa de identidad sobre OAuth 2.0. Junto con el token de acceso, el proveedor OpenID emite un token de identidad (ID token), un JSON Web Token (JWT) firmado que indica quién es el usuario, quién emitió el token, para qué cliente se emitió y cuándo expira. OIDC usa JSON y REST ligeros, lo que resulta adecuado para las aplicaciones móviles y web modernas, y es la base de los conocidos botones de iniciar sesión con grandes proveedores. La parte que confía debe validar la firma, el emisor, la audiencia y la expiración del ID token. Al federarte con terceros, gestiona la relación como cualquier riesgo de proveedores: define en el acuerdo la entrega de atributos y la protección de datos, exige autenticación robusta en el IdP, monitorea las aserciones anómalas, protege las claves de firma y renueva los certificados antes de que expiren.

Considera un ejemplo práctico. Tu empresa adopta una aplicación de gastos en la nube. Los empleados inician sesión mediante SAML desde el IdP corporativo, que exige MFA resistente al phishing, y SCIM elimina las cuentas cuando recursos humanos registra una salida. Por otro lado, la aplicación de gastos quiere leer los recibos del almacenamiento en la nube de los empleados. Eso es acceso delegado, así que usa OAuth 2.0 con un alcance limitado a una carpeta de recibos y permiso de solo lectura. La propia aplicación móvil de la empresa usa OIDC para saber quién es el usuario. El equipo de seguridad documenta qué atributos recibe cada socio y configura una alerta para la expiración del certificado de firma.

Errores comunes: llamar a OAuth 2.0 protocolo de autenticación; aceptar aserciones o tokens sin comprobar la firma, la audiencia y la expiración; conceder alcances amplios, como el acceso completo al buzón, cuando basta el acceso de solo lectura al calendario; olvidar dar de baja la cuenta en el SP cuando la federación no es la única vía de entrada; y suponer que la federación elimina la necesidad de la debida diligencia sobre los proveedores. Otra trampa es pensar que el SP llega a ver la contraseña del usuario; en una federación bien hecha nunca la ve.

Las preguntas del examen dependen de unas pocas distinciones. 'Aserciones XML para el SSO empresarial' es SAML. 'Permitir que una aplicación acceda a mis fotos sin darle mi contraseña' es OAuth 2.0, que es autorización. 'Capa de autenticación sobre OAuth con un ID token en JSON' es OIDC. 'Parte que autentica al usuario' es el IdP; 'parte que consume la aserción' es el SP o la RP. Piensa como gerente: la federación concentra la confianza en el IdP, por lo que su seguridad y su disponibilidad se vuelven críticas para el negocio.

Términos clave

Proveedor de identidad (IdP)
El sistema que autentica a los usuarios y emite aserciones o tokens de identidad firmados.
Proveedor de servicios (SP)
La aplicación que se basa en la aserción del IdP para conceder el acceso; en OIDC se llama parte que confía (relying party).
Aserción SAML (SAML assertion)
Declaración XML firmada por un IdP sobre la identidad y los atributos de un usuario.
OAuth 2.0
Marco de autorización para conceder a las aplicaciones un acceso delegado y con alcance limitado sin compartir contraseñas.
Token de acceso (access token)
Credencial emitida en OAuth que el cliente presenta a una API para ejercer los alcances concedidos.
OpenID Connect (OIDC)
Capa de autenticación construida sobre OAuth 2.0 que emite un ID token firmado.
Token de identidad (ID token)
JWT firmado en OIDC que le indica a la parte que confía quién es el usuario y quién emitió el token.
Ejemplo real

Una universidad se une a una federación de investigación para que su personal pueda usar los portales de datos de las instituciones asociadas con sus credenciales de origen. Cuando una investigadora se va, deshabilitar su cuenta universitaria elimina de inmediato su acceso a todos los portales asociados. El acuerdo de la federación especifica que solo se entregan el nombre, el correo electrónico y la afiliación, lo que satisface a la oficina de privacidad.

Consejo para el examen: SAML se basa en XML y es común para el SSO empresarial; OAuth 2.0 es autorización (acceso delegado), no autenticación; OIDC es autenticación construida sobre OAuth 2.0 con tokens JSON.

Comprueba lo que sabes

Un sitio de impresión de fotos pide permiso para leer tu álbum de fotos en la nube. ¿Qué estándar se está usando y para qué?

OAuth 2.0, para la autorización delegada a recursos específicos sin compartir tu contraseña.

¿Qué agrega OIDC a OAuth 2.0?

Una capa de identidad: un ID token firmado que le indica a la parte que confía quién se autenticó.

¿Qué debe verificar un SP cuando recibe una aserción SAML?

La firma, la audiencia prevista y el período de validez, antes de confiar en la identidad y los atributos.

¿Cuál es el principal riesgo de la federación?

La dependencia del IdP: si se compromete o deja de estar disponible, todos los servicios que dependen de él se ven afectados.
