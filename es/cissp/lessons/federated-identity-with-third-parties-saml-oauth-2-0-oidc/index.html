Identidad federada con terceros: SAML, OAuth 2.0 y OIDC

La identidad federada permite que los usuarios se autentiquen una vez con su organización de origen y luego accedan a servicios operados por otras organizaciones sin crear cuentas separadas en ellas. Las organizaciones acuerdan confiar en las aserciones de identidad de las otras. Esto reduce la proliferación de contraseñas, centraliza la baja de accesos (se deshabilita la cuenta de origen y se detiene el acceso federado) y traslada la autenticación a la parte mejor posicionada para hacerla bien. El costo es una dependencia de confianza: si el proveedor de identidad se compromete o está mal configurado, todos los servicios que dependen de él quedan expuestos.

En toda federación aparecen dos roles. El proveedor de identidad (IdP) autentica al usuario y emite una declaración firmada sobre él. El proveedor de servicios (SP), llamado parte dependiente (RP, relying party) en OpenID Connect, consume esa declaración y otorga el acceso. La confianza se establece de antemano intercambiando metadatos, incluidos los certificados usados para firmar las aserciones.

SAML (Security Assertion Markup Language) 2.0 es un estándar basado en XML muy usado para el inicio de sesión único web empresarial. En un flujo típico iniciado por el SP, el usuario visita la aplicación SaaS, es redirigido al IdP corporativo, se autentica allí y es redirigido de vuelta con una aserción SAML firmada digitalmente que contiene la identidad y los atributos del usuario. El SP valida la firma, la audiencia prevista y el periodo de validez antes de crear una sesión. Las aserciones también pueden cifrarse. SAML es maduro y común para el acceso de la fuerza laboral a aplicaciones en la nube.

OAuth 2.0 suele malinterpretarse. Es un marco de autorización, no un protocolo de autenticación. Permite que un propietario de recursos otorgue a una aplicación cliente un acceso limitado y delegado a los recursos de un servidor de recursos, sin compartir su contraseña. Un servidor de autorización emite un token de acceso con alcances (scopes) específicos, como el permiso para leer un calendario. El cliente presenta ese token a la API. El flujo de código de autorización (authorization code flow), reforzado con PKCE (Proof Key for Code Exchange), es el patrón recomendado para la mayoría de las aplicaciones, mientras que el antiguo flujo implícito (implicit flow) se desaconseja. Los tokens deben tener una vida corta y un alcance limitado.

OpenID Connect (OIDC) añade una capa de identidad sobre OAuth 2.0. Junto con el token de acceso, el proveedor OpenID emite un token de ID (ID token), un JSON Web Token (JWT) firmado que indica quién es el usuario, quién emitió el token, para qué cliente se emitió y cuándo expira. OIDC usa JSON y REST ligeros, lo que conviene a las apps móviles y a las aplicaciones web modernas, y es la base de los conocidos botones de iniciar sesión con un gran proveedor. La parte dependiente debe validar la firma, el emisor, la audiencia y la expiración del token de ID.

Al federarte con terceros, gestiona la relación como cualquier riesgo de proveedor: define en el acuerdo la entrega de atributos y la protección de datos, exige autenticación fuerte en el IdP, monitorea aserciones anómalas, protege las claves de firma y rota los certificados antes de que expiren.

Términos clave

Identity provider (IdP) (proveedor de identidad)
La parte que autentica a los usuarios y emite aserciones o tokens firmados sobre ellos.
SAML assertion (aserción SAML)
Una declaración XML firmada de un IdP que transmite información de autenticación y atributos a un proveedor de servicios.
OAuth 2.0
Un marco de autorización para el acceso delegado que emite tokens de acceso con alcances definidos; por sí solo no autentica a los usuarios.
OpenID Connect (OIDC)
Una capa de autenticación construida sobre OAuth 2.0 que añade un token de ID firmado que describe al usuario.
JSON Web Token (JWT)
Un formato de token JSON compacto y firmado que se usa para los tokens de ID de OIDC y, a menudo, para los tokens de acceso.
Ejemplo real

Una universidad usa SAML para que el personal inicie sesión en un sistema de RR. HH. en la nube con su cuenta del campus. Por otro lado, un estudiante otorga a una app de planificación de estudios acceso OAuth para leer, pero no modificar, su calendario. La app de planificación también ofrece inicio de sesión mediante OIDC y recibe un token de ID que le dice la identidad del estudiante sin ver nunca su contraseña.

Consejo para el examen: La distinción clásica del examen: SAML está basado en XML y es común para el SSO empresarial; OAuth 2.0 es autorización (acceso delegado), no autenticación; OIDC es autenticación construida sobre OAuth 2.0 usando tokens JSON.

Comprueba lo que sabes

¿Qué protocolo usarías para permitir que una app de terceros lea las fotos de un usuario sin recibir su contraseña?

OAuth 2.0, que emite un token de acceso con alcance definido que otorga acceso delegado.

¿Qué añade OIDC a OAuth 2.0?

Un token de ID (un JWT firmado) y claims de identidad estándar para que el cliente pueda autenticar al usuario, no solo obtener acceso delegado.

¿Qué debe verificar un proveedor de servicios SAML antes de confiar en una aserción?

La firma digital contra el certificado de confianza del IdP, la audiencia prevista y la ventana de tiempo de validez, entre otras condiciones.
