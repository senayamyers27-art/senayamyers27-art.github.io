ISC2 CISSP 2024 outline

Debilidades comunes: inyección, XSS, CSRF, desbordamiento de búfer, condiciones de carrera y deserialización insegura

Un número reducido de tipos de debilidades explica una gran parte de las vulnerabilidades del software. El examen espera que reconozcas cada una a partir de un escenario, entiendas por qué ocurre y nombres las defensas principales. No necesitas saber cómo explotarlas; necesitas saber cómo surgen, cómo detectarlas en una descripción y qué control aborda cada causa raíz.

La inyección ocurre cuando una entrada no confiable se envía a un intérprete como parte de un comando o una consulta, y el intérprete trata parte de esa entrada como código. La inyección SQL es el caso clásico: una aplicación construye una consulta a la base de datos concatenando la entrada del usuario, y una entrada manipulada cambia la lógica de la consulta para leer o modificar datos. El mismo patrón afecta a los comandos del sistema operativo, a las consultas del Lightweight Directory Access Protocol (LDAP) y a otros. La defensa principal es mantener separados el código y los datos con consultas parametrizadas (sentencias preparadas) o API seguras, apoyadas por la validación de entradas del lado del servidor, cuentas de base de datos con mínimo privilegio y un manejo cuidadoso de los errores. En el ejemplo defensivo que sigue, el controlador de la base de datos envía el valor por separado del texto SQL, de modo que nunca puede cambiar la estructura de la consulta.

# Safe: the driver sends the value separately from the SQL text
cursor.execute("SELECT name FROM users WHERE id = %s", (user_id,))

El cross-site scripting (XSS) permite que un atacante haga que el navegador de una víctima ejecute un script en el contexto de un sitio confiable, lo que posibilita el robo de sesiones, la desfiguración de páginas o acciones en nombre del usuario. El XSS almacenado guarda el contenido malicioso en el servidor, por ejemplo en un comentario; el XSS reflejado lo hace rebotar desde un parámetro de la solicitud en un enlace manipulado; el XSS basado en DOM ocurre por completo en el script del lado del cliente. Las defensas incluyen la codificación de salida según el contexto, la validación de entradas, frameworks que escapan la salida automáticamente, un encabezado Content Security Policy (CSP) y el atributo HttpOnly en las cookies para que los scripts no puedan leer los tokens de sesión. La falsificación de solicitudes entre sitios (CSRF) es distinta: engaña al navegador de un usuario con sesión iniciada para que envíe una solicitud no deseada, como cambiar una dirección de correo, a un sitio que confía en ese navegador, porque el navegador adjunta las cookies automáticamente. Las defensas incluyen tokens anti-CSRF vinculados a la sesión, el atributo SameSite en las cookies y la reautenticación para las acciones sensibles. El XSS abusa de la confianza del usuario en un sitio; el CSRF abusa de la confianza del sitio en el navegador del usuario.

Un desbordamiento de búfer ocurre cuando un programa escribe en un búfer de memoria más datos de los que puede contener, sobrescribiendo la memoria adyacente. Esto puede hacer fallar el programa o, cuando un atacante controla los datos sobrescritos, redirigir la ejecución. Es más común en lenguajes sin verificación automática de límites, como C y C++. Las defensas incluyen la verificación de límites y las funciones seguras, los lenguajes con seguridad de memoria y protecciones de la plataforma como la aleatorización del diseño del espacio de direcciones (ASLR), la prevención de ejecución de datos (DEP) y los canarios de pila (stack canaries). Las condiciones de carrera ocurren cuando el resultado depende del momento en que suceden los eventos. La falla de tiempo de verificación a tiempo de uso (TOCTOU) es típica: un programa verifica una condición, como los permisos de un archivo o el saldo de una cuenta, y luego actúa en consecuencia, pero el estado cambia entre ambos momentos. Las defensas incluyen operaciones atómicas, bloqueos adecuados y volver a verificar dentro de una sola transacción. La deserialización insegura ocurre cuando una aplicación reconstruye objetos a partir de datos serializados no confiables, lo que puede permitir a un atacante manipular la lógica de la aplicación o incluso provocar la ejecución de código. Evita deserializar datos no confiables, prefiere formatos de datos simples como JSON con esquemas estrictos, aplica verificaciones de integridad como las firmas digitales y restringe qué clases pueden deserializarse.

Considera un ejemplo práctico. Una aplicación bancaria permite a los usuarios transferir dinero. Una revisión descubre que dos solicitudes de transferencia simultáneas pueden pasar ambas la verificación de saldo antes de que alguna descuente los fondos, una condición de carrera TOCTOU, así que la corrección realiza la verificación y el descuento en una sola transacción de base de datos con bloqueo. La misma revisión encuentra que el formulario de transferencia carece de un token anti-CSRF y que la aplicación guarda las preferencias del usuario como objetos serializados en una cookie, que se reemplaza por JSON firmado.

Errores comunes: confundir XSS con CSRF; depender solo del filtrado de entradas en lugar de consultas parametrizadas para la inyección; pensar que HTTPS previene el XSS o el CSRF (protege el transporte, no la lógica de la aplicación); creer que ASLR y DEP eliminan los desbordamientos de búfer en lugar de hacer más difícil su explotación; y tratar una condición de carrera como un problema de rendimiento en lugar de una falla de seguridad. Otro error es suponer que los datos serializados de tu propia cookie son confiables, cuando el usuario puede modificarlos.

Las preguntas del examen describen síntomas. "Una entrada cambia una consulta a la base de datos" apunta a la inyección y a las consultas parametrizadas. "Un script se ejecuta en los navegadores de otros usuarios" apunta al XSS y a la codificación de salida. "El navegador de un usuario con sesión iniciada realiza una acción que no pretendía" apunta al CSRF y a los tokens anti-CSRF. "Escribir más allá del final de la memoria" apunta al desbordamiento de búfer y a la verificación de límites. "La verificación y el uso ocurren en momentos distintos" apunta a TOCTOU y a las operaciones atómicas. "Reconstruir objetos a partir de datos no confiables" apunta a la deserialización insegura. Piensa como gerente: corrige las causas raíz mediante estándares de codificación segura, frameworks y capacitación, en lugar de parchear los síntomas uno por uno.

Términos clave

Inyección (injection)
Falla en la que una entrada no confiable se interpreta como parte de un comando o una consulta.
Cross-site scripting (XSS)
Falla que permite que un script proporcionado por el atacante se ejecute en el navegador de una víctima en el contexto de un sitio confiable.
Falsificación de solicitudes entre sitios (CSRF)
Ataque que hace que el navegador de un usuario autenticado envíe una solicitud no deseada a un sitio que confía en él.
Desbordamiento de búfer (buffer overflow)
Escribir en un búfer de memoria más datos de los que puede contener, sobrescribiendo la memoria adyacente.
Tiempo de verificación a tiempo de uso (TOCTOU)
Condición de carrera en la que una condición cambia entre el momento en que se verifica y el momento en que se usa.
Deserialización insegura (insecure deserialization)
Reconstruir objetos a partir de datos serializados no confiables de una forma que permite la manipulación o la ejecución de código.
Content Security Policy (CSP)
Encabezado de seguridad del navegador que restringe desde dónde pueden cargarse los scripts y otros contenidos, lo que limita el impacto del XSS.
Ejemplo real

Un foro comunitario permite a los usuarios publicar comentarios con formato. Un atacante publica un comentario que contiene un script, y cada visitante que ve el hilo lo ejecuta, enviando sus cookies de sesión a otro lugar. El foro corrige el XSS almacenado codificando la salida con un framework de plantillas que escapa por defecto, agrega una Content Security Policy y marca las cookies de sesión como HttpOnly para que los scripts no puedan leerlas.

Consejo para el examen: Distingue el XSS del CSRF: el XSS ejecuta el script del atacante en el navegador de la víctima (el usuario confía en el sitio); el CSRF envía solicitudes falsificadas usando la sesión de la víctima (el sitio confía en el navegador). Las consultas parametrizadas son la mejor respuesta única para la inyección SQL.

Comprueba lo que sabes

¿Cuál es la mejor defensa principal contra la inyección SQL?

Las consultas parametrizadas (sentencias preparadas), que mantienen los datos del usuario separados del código SQL.

¿En qué se diferencia el CSRF del XSS?

El CSRF falsifica solicitudes desde el navegador de un usuario autenticado hacia un sitio que confía en él, mientras que el XSS ejecuta el script del atacante en el navegador de la víctima.

¿Qué es una falla TOCTOU y cómo se previene?

Una condición de carrera en la que una condición cambia entre la verificación y el uso; se previene con operaciones atómicas, bloqueos o volviendo a verificar dentro de una sola transacción.

Menciona dos protecciones de la plataforma que dificultan la explotación de los desbordamientos de búfer.

La aleatorización del diseño del espacio de direcciones (ASLR) y la prevención de ejecución de datos (DEP), junto con los canarios de pila.
