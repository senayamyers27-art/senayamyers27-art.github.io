ISC2 CISSP 2024 outline

Debilidades comunes: inyección, XSS, CSRF, desbordamiento de búfer, condiciones de carrera y deserialización insegura

Un pequeño número de tipos de debilidades explica una gran parte de las vulnerabilidades del software. El CISSP espera que reconozcas cada una a partir de un escenario, entiendas por qué ocurre y nombres sus defensas principales.

La inyección ocurre cuando una entrada no confiable se envía a un intérprete como parte de un comando o de una consulta, y el intérprete trata parte de esa entrada como código. La inyección SQL es el caso clásico: una aplicación construye una consulta a la base de datos concatenando la entrada del usuario, y una entrada especialmente elaborada cambia la lógica de la consulta para leer o modificar datos. El mismo patrón afecta a los comandos del sistema operativo, las consultas LDAP y otros. La defensa principal es mantener separados el código y los datos mediante consultas parametrizadas (prepared statements) o API seguras, con el apoyo de la validación de entradas del lado del servidor, cuentas de base de datos con mínimo privilegio y un manejo cuidadoso de los errores. Un ejemplo defensivo en Python:

# Seguro: el driver envía el valor por separado del texto SQL
cursor.execute("SELECT name FROM users WHERE id = %s", (user_id,))

El cross-site scripting (XSS) permite a un atacante hacer que el navegador de una víctima ejecute un script en el contexto de un sitio de confianza, lo que permite robar la sesión, desfigurar la página o realizar acciones como el usuario. El XSS almacenado guarda el contenido malicioso en el servidor (en un comentario, por ejemplo); el XSS reflejado lo hace rebotar desde un parámetro de solicitud en un enlace manipulado; el XSS basado en DOM ocurre por completo en el script del lado del cliente. Las defensas incluyen la codificación de la salida según el contexto, la validación de entradas, los frameworks que escapan automáticamente, un encabezado Content Security Policy (CSP) y las cookies HttpOnly para mantener los tokens de sesión fuera del alcance de los scripts. La falsificación de solicitudes entre sitios (CSRF) es diferente: engaña al navegador de un usuario que inició sesión para que envíe una solicitud no deseada a un sitio que confía en ese navegador, como cambiar una dirección de correo, porque el navegador adjunta las cookies automáticamente. Las defensas incluyen los tokens anti-CSRF vinculados a la sesión, los atributos SameSite de las cookies y volver a autenticar para las acciones sensibles. Recuerda: XSS abusa de la confianza del usuario en un sitio; CSRF abusa de la confianza del sitio en el navegador del usuario.

Un desbordamiento de búfer ocurre cuando un programa escribe en un búfer de memoria más datos de los que este puede contener, sobrescribiendo la memoria adyacente. Esto puede hacer que el programa falle o, cuando un atacante controla los datos sobrescritos, redirigir la ejecución. Es más común en lenguajes sin verificación automática de límites, como C y C++. Las defensas incluyen la verificación de límites y las funciones seguras, los lenguajes con seguridad de memoria y protecciones de la plataforma como la aleatorización del diseño del espacio de direcciones (ASLR), la prevención de ejecución de datos (DEP) y los canarios de pila (stack canaries).

Las condiciones de carrera ocurren cuando el resultado depende del momento en que suceden los eventos. La falla de tiempo de verificación a tiempo de uso (TOCTOU) es típica: un programa verifica una condición, como los permisos de un archivo o el saldo de una cuenta, y luego actúa en consecuencia, pero el estado cambia entre ambos momentos. Las defensas incluyen las operaciones atómicas, el bloqueo adecuado y volver a verificar dentro de una sola transacción. La deserialización insegura ocurre cuando una aplicación reconstruye objetos a partir de datos serializados no confiables, lo que puede permitir a un atacante manipular la lógica de la aplicación o provocar la ejecución de código. Evita deserializar datos no confiables, usa formatos de datos simples como JSON con esquemas estrictos, aplica verificaciones de integridad como las firmas digitales y restringe qué clases pueden deserializarse.

Términos clave

Injection (inyección)
Entrada no confiable interpretada como comandos o consultas; se evita principalmente con consultas parametrizadas y validación de entradas.
Cross-site scripting (XSS)
Script inyectado que se ejecuta en el navegador de una víctima en el contexto de un sitio de confianza; se evita con la codificación de la salida y CSP.
Cross-site request forgery (CSRF) (falsificación de solicitudes entre sitios)
Forzar al navegador de un usuario autenticado a enviar solicitudes no deseadas; se evita con tokens anti-CSRF y cookies SameSite.
Buffer overflow (desbordamiento de búfer)
Escribir más allá de los límites de un búfer, corrompiendo la memoria; se mitiga con verificación de límites, lenguajes con seguridad de memoria, ASLR y DEP.
TOCTOU
Time-of-check to time-of-use (tiempo de verificación a tiempo de uso), una condición de carrera en la que el estado cambia entre la verificación y el uso de un recurso.
Insecure deserialization (deserialización insegura)
Reconstruir objetos a partir de datos no confiables de una manera que permite a los atacantes alterar la lógica o ejecutar código.
Ejemplo real

Una prueba de penetración de una tienda en línea encuentra tres problemas: las reseñas de productos muestran HTML proporcionado por los usuarios (XSS almacenado), el formulario para cambiar el correo acepta solicitudes sin un token (CSRF) y dos canjes simultáneos de tarjetas de regalo tienen éxito porque el saldo se verifica antes de una demora y se descuenta después (una condición de carrera). Las correcciones son la codificación de la salida con una CSP, los tokens anti-CSRF con cookies SameSite y una transacción atómica en la base de datos para los canjes.

Consejo para el examen: Distingue XSS de CSRF: XSS ejecuta el script del atacante en el navegador de la víctima (el usuario confía en el sitio); CSRF envía solicitudes falsificadas usando la sesión de la víctima (el sitio confía en el navegador). Las consultas parametrizadas son la mejor respuesta única para la inyección SQL.

Comprueba lo que sabes

¿Cuál es la defensa principal más eficaz contra la inyección SQL?

Las consultas parametrizadas (prepared statements), que mantienen los datos separados del código, con el apoyo de la validación de entradas y de cuentas de base de datos con mínimo privilegio.

¿Qué debilidad explota la confianza de un sitio en el navegador de un usuario autenticado?

La falsificación de solicitudes entre sitios (CSRF).

¿Qué tipo de falla es un problema de tiempo de verificación a tiempo de uso y cómo se evita?

Es una condición de carrera; se evita con operaciones atómicas, bloqueos o realizando la verificación y el uso dentro de una sola transacción.
