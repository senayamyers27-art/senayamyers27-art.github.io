ISC2 CISSP 2024 outline

Pruebas de seguridad de aplicaciones: SAST, DAST, SCA, IAST

Las herramientas de pruebas de seguridad de aplicaciones automatizan la búsqueda de vulnerabilidades en el software. El examen CISSP espera que conozcas las cuatro categorías principales, cómo funciona cada una, dónde encaja en el ciclo de vida del desarrollo y cuáles son sus fortalezas y puntos ciegos. Los programas maduros usan varias a la vez porque cada una ve problemas distintos.

Las pruebas estáticas de seguridad de aplicaciones (SAST) analizan el código fuente, el bytecode o los binarios sin ejecutar el programa. Rastrean cómo fluyen los datos desde las entradas (sources) hasta las operaciones sensibles (sinks) y señalan las rutas en las que una entrada no confiable llega a una consulta a la base de datos, a la ejecución de un comando o a una salida HTML sin validación ni codificación. SAST es una técnica de caja blanca que puede ejecutarse en cuanto se escribe el código, a menudo dentro del IDE o en cada commit, y señala a los desarrolladores el archivo y la línea exactos. Sus debilidades son los falsos positivos, el soporte específico por lenguaje y la falta de visibilidad sobre la configuración en tiempo de ejecución, la infraestructura desplegada o los problemas que solo aparecen cuando los componentes interactúan.

Las pruebas dinámicas de seguridad de aplicaciones (DAST) prueban una aplicación en ejecución desde el exterior, como lo haría un atacante, sin acceso al código fuente. Recorren la aplicación, envían solicitudes especialmente elaboradas y analizan las respuestas para detectar problemas como la inyección, el cross-site scripting, las debilidades de autenticación, los encabezados mal configurados y la fuga de información. DAST es una técnica de caja negra, independiente del lenguaje, y encuentra problemas de ejecución y de configuración que SAST no puede. Sin embargo, necesita una aplicación desplegada, normalmente en un entorno de pruebas o de preproducción (staging), se ejecuta más tarde en el ciclo de vida, puede pasar por alto rutas de código a las que no llega y no identifica la línea de código responsable.

El análisis de composición de software (SCA) identifica los componentes de terceros y de código abierto de una aplicación, incluidas las dependencias transitivas (las dependencias de las dependencias), y los compara con bases de datos de vulnerabilidades y licencias conocidas. Como la mayoría de las aplicaciones modernas están compuestas en gran parte por código abierto, SCA aborda una parte importante del riesgo. Puede generar una lista de materiales de software (SBOM), alertar cuando una vulnerabilidad recién divulgada afecta a un componente que ya está en producción y señalar obligaciones de licencia que podrían crear riesgo legal. SCA no encuentra fallas en el código propio de la organización.

Las pruebas interactivas de seguridad de aplicaciones (IAST) colocan un agente o sensores dentro de la aplicación en ejecución, normalmente en un entorno de pruebas, y observan la ejecución del código mientras las pruebas funcionales o los escaneos DAST la ejercitan. Como ve tanto la solicitud entrante como el flujo interno de datos, IAST puede confirmar vulnerabilidades reales con menos falsos positivos y señalar el código responsable. Depende de la cobertura de las pruebas, ya que solo se analiza el código que se ejercita, y es compatible con lenguajes y frameworks específicos. Una tecnología relacionada, la autoprotección de aplicaciones en tiempo de ejecución (RASP), usa una instrumentación similar en producción para bloquear los ataques en lugar de solo reportarlos.

En un pipeline de DevSecOps, SAST y SCA normalmente se ejecutan en cada commit o pull request, DAST e IAST se ejecutan contra las compilaciones de staging, y los hallazgos alimentan un proceso común de seguimiento de defectos con umbrales de severidad que pueden bloquear un lanzamiento. Los resultados de las herramientas siguen necesitando un triaje humano para confirmar y priorizar los hallazgos.

Términos clave

SAST
Static application security testing (pruebas estáticas de seguridad de aplicaciones): análisis de caja blanca del código sin ejecutarlo.
DAST
Dynamic application security testing (pruebas dinámicas de seguridad de aplicaciones): pruebas de caja negra de una aplicación en ejecución a través de sus interfaces.
SCA
Software composition analysis (análisis de composición de software): identificar los componentes de terceros y sus vulnerabilidades y licencias conocidas.
IAST
Interactive application security testing (pruebas interactivas de seguridad de aplicaciones): instrumentación dentro de una aplicación en ejecución que analiza su comportamiento durante las pruebas.
RASP
Runtime application self-protection (autoprotección de aplicaciones en tiempo de ejecución): instrumentación dentro de la aplicación que detecta y bloquea ataques en producción.
Ejemplo real

El pipeline de un sitio de reservas de viajes ejecuta SAST y SCA en cada pull request, lo que detecta una construcción insegura de consultas y una biblioteca XML desactualizada. En staging, un escaneo DAST nocturno encuentra que falta un encabezado de seguridad, mientras que el agente IAST, al observar las pruebas de regresión del equipo de QA, confirma que un parámetro de búsqueda llega a la base de datos sin sanitizar e identifica el método exacto responsable.

Consejo para el examen: Relaciona la herramienta con la situación: aún no hay aplicación en ejecución y necesitas las líneas exactas de código, SAST; aplicación en ejecución, vista del atacante, SAST no es posible, DAST; riesgo de dependencias de código abierto, SCA; aplicación en ejecución instrumentada con pocos falsos positivos, IAST.

Comprueba lo que sabes

¿Qué tipo de prueba es mejor para encontrar bibliotecas de código abierto vulnerables?

El análisis de composición de software (SCA).

¿Qué puede encontrar DAST que SAST normalmente no puede?

Problemas de ejecución y de configuración en la aplicación desplegada, como configuraciones incorrectas del servidor y encabezados de seguridad faltantes.

¿Por qué IAST suele producir menos falsos positivos que SAST?

Observa la ejecución real con solicitudes reales dentro de la aplicación en ejecución, lo que confirma que los datos contaminados llegan a una operación vulnerable.
