ISC2 CISSP 2024 outline

Guías y estándares de codificación segura: debilidades del código fuente, seguridad de API y prácticas de codificación segura

Los estándares de codificación segura dan a los desarrolladores reglas concretas para escribir software que resista los ataques. Convierten los principios generales en prácticas que pueden enseñarse, verificarse con herramientas y hacerse cumplir en la revisión de código. Entre las referencias más conocidas están el OWASP Top 10 (los riesgos de seguridad más críticos de las aplicaciones web), el OWASP Application Security Verification Standard (ASVS), la lista Common Weakness Enumeration (CWE) de tipos de debilidades del software y su Top 25 de las debilidades más peligrosas, los estándares de codificación SEI CERT para lenguajes específicos y el Secure Software Development Framework (SSDF) del NIST. Las organizaciones suelen adoptar uno o más y adaptarlos a sus lenguajes y plataformas.

Las debilidades del código fuente se agrupan en categorías recurrentes. Una validación de entradas deficiente permite que datos no confiables lleguen a los intérpretes. Un manejo inadecuado de errores revela a los usuarios trazas de pila, versiones o detalles de la base de datos. Las credenciales y claves codificadas de forma fija terminan en los repositorios. La criptografía débil o casera, los números aleatorios predecibles y los algoritmos obsoletos socavan la confidencialidad. El control de acceso roto no verifica la autorización en cada solicitud. Las condiciones de carrera y el manejo inseguro de la memoria crean fallas sutiles. Las puertas traseras o ganchos de mantenimiento (maintenance hooks), a veces dejados por los desarrolladores para hacer pruebas, eluden los controles normales y deben eliminarse antes del lanzamiento. El código muerto y las funciones de depuración que quedan en producción amplían la superficie de ataque.

Las prácticas fundamentales de codificación segura contrarrestan estas debilidades. Valida todas las entradas en el lado del servidor frente a una lista de permitidos del tipo, longitud, formato y rango esperados; las verificaciones del lado del cliente son solo para la usabilidad, ya que el atacante controla el cliente. Codifica la salida según el contexto en que se usa, como HTML, JavaScript o URL. Usa consultas parametrizadas o API seguras en lugar de construir comandos concatenando cadenas. Aplica la autenticación y la autorización de forma centralizada y verifica la autorización en cada solicitud y cada objeto. Falla de forma segura: ante un error, deniega el acceso y muestra mensajes genéricos mientras registras los detalles internamente. Usa bibliotecas criptográficas bien probadas y nunca inventes algoritmos. Mantén los secretos fuera del código. Aplica el mínimo privilegio a las propias cuentas de la aplicación, mantén las dependencias actualizadas y registra los eventos de seguridad sin datos sensibles.

Las interfaces de programación de aplicaciones (API) merecen especial atención porque exponen funcionalidades y datos directamente a otros programas, sin una interfaz de usuario que pueda ocultar las debilidades. El OWASP API Security Top 10 destaca riesgos como la autorización rota a nivel de objeto (BOLA), en la que una API devuelve cualquier registro cuyo identificador se proporcione sin verificar la propiedad; la autenticación rota; la exposición de más propiedades de un objeto de las que el solicitante debería ver; y el consumo de recursos sin restricciones, como la falta de límites de tasa. Protege las API exigiendo una autenticación fuerte, por ejemplo tokens de acceso OAuth 2.0 con alcances limitados; autorizando cada objeto y función; validando las entradas frente a un esquema; devolviendo solo los campos necesarios; aplicando límites de tasa y cuotas; usando Transport Layer Security (TLS); manteniendo un inventario de todas las versiones de la API, incluidas las antiguas; y monitoreando mediante una pasarela de API (API gateway). Las API REST suelen usar JSON y tokens, mientras que las API SOAP usan XML y pueden usar WS-Security.

Haz cumplir los estándares mediante capacitación, complementos para el IDE, reglas de análisis estático asociadas al estándar, listas de verificación para la revisión de código entre pares y puertas en el pipeline. Mide qué tipos de debilidades se repiten y enfoca la capacitación en ellos. Un estándar que existe solo como documento no cambia nada; uno integrado en las herramientas y las revisiones cambia el código.

Considera un ejemplo práctico. Una aplicación de ejercicio expone un endpoint que devuelve el historial de entrenamientos de un usuario cuando recibe un identificador de usuario. Una revisión de seguridad descubre que cualquier usuario con sesión iniciada puede cambiar el identificador en la solicitud y ver los datos de cualquier otra persona, una falla BOLA de manual. La corrección verifica, en el servidor, que el registro solicitado pertenezca a la identidad autenticada de quien lo pide. La revisión también encuentra que las respuestas de error incluyen trazas de pila completas y que la API no tiene límite de tasa. El equipo agrega mensajes de error genéricos con registro interno, limitación de tasa en la pasarela, y una regla de análisis estático y un elemento en la lista de verificación de revisión de código para la autorización a nivel de objeto.

Errores comunes: depender de la validación del lado del cliente para la seguridad; usar listas de denegados de caracteres maliciosos en lugar de listas de permitidos de la entrada esperada; suponer que un usuario con sesión iniciada está autorizado para todos los objetos; mostrar errores detallados a los usuarios; escribir cifrado propio; y dejar versiones antiguas de la API en funcionamiento sin monitoreo. Otra trampa es pensar que HTTPS por sí solo protege una API; TLS protege los datos en tránsito, pero no hace nada contra las fallas de autorización.

Las preguntas del examen suelen ir de un síntoma a una práctica. "Inyección" apunta a consultas parametrizadas y validación del lado del servidor. "Un script se ejecuta en los navegadores de los usuarios" apunta a la codificación de salida. "Un usuario puede ver los registros de otros usuarios cambiando un ID" apunta a la autorización a nivel de objeto. "Los errores detallados revelan la estructura de la base de datos" apunta al manejo seguro de errores. "Se encontraron credenciales en el código fuente" apunta a un gestor de secretos. "Un desarrollador dejó un punto de entrada oculto" apunta a un gancho de mantenimiento que la revisión de código debería detectar. Piensa como gerente: adopta un estándar reconocido, hazlo cumplir con herramientas y revisiones, y mide las debilidades recurrentes para enfocar la capacitación.

Términos clave

Common Weakness Enumeration (CWE)
Catálogo de tipos de debilidades de software y hardware, que incluye una lista de las más peligrosas.
Validación de entradas (input validation)
Comprobar que la entrada coincida con el tipo, la longitud, el formato y el rango esperados, idealmente frente a una lista de permitidos en el servidor.
Codificación de salida (output encoding)
Convertir los datos para que se traten como datos, y no como código, en el contexto donde se muestran o se usan.
Consulta parametrizada (parameterized query)
Consulta de base de datos en la que la entrada del usuario se pasa por separado del texto SQL, lo que evita la inyección.
Autorización rota a nivel de objeto (BOLA)
Falla de una API en la que el servidor devuelve objetos sin verificar que el solicitante pueda acceder a ellos.
Gancho de mantenimiento (maintenance hook)
Punto de entrada no documentado dejado en el código que elude los controles de seguridad normales.
Fallar de forma segura (fail securely)
Diseñar los errores para que denieguen el acceso por defecto y revelen la mínima información.
Ejemplo real

Durante una revisión de código, un revisor nota un comentario de un desarrollador que dice 'omisión temporal de administrador para pruebas' junto a una verificación que otorga derechos de administrador cuando está presente un encabezado especial. El código se elimina antes del lanzamiento, se agrega una regla de análisis estático para señalar patrones similares y la lista de verificación de lanzamiento del equipo incorpora un elemento que confirma que no quedan funciones de depuración ni de omisión.

Consejo para el examen: La validación de entradas del lado del servidor con listas de permitidos y la codificación de salida según el contexto son las respuestas clave para las preguntas sobre inyección y XSS. En las API, recuerda la autorización a nivel de objeto: verifica que el solicitante pueda acceder a cada registro específico, no solo que haya iniciado sesión.

Comprueba lo que sabes

¿Por qué la validación de entradas del lado del cliente es insuficiente para la seguridad?

El atacante controla el cliente y puede eludirla, así que la validación debe aplicarse en el servidor.

Un usuario cambia un número de cuenta en una solicitud a la API y ve los datos de otro cliente. ¿Qué debilidad es esta?

Autorización rota a nivel de objeto, porque la API no verificó que el solicitante fuera dueño del registro solicitado.

¿Qué significa fallar de forma segura en el manejo de errores?

Denegar el acceso ante un error y mostrar un mensaje genérico a los usuarios, mientras se registran los detalles internamente.

¿Qué es un gancho de mantenimiento y por qué es peligroso?

Un punto de entrada no documentado dejado por los desarrolladores que elude los controles normales y que puede ser descubierto y aprovechado.
