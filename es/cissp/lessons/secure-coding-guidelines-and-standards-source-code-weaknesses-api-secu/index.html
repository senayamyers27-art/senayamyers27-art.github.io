ISC2 CISSP 2024 outline

Guías y estándares de codificación segura: debilidades del código fuente, seguridad de API y prácticas de codificación segura

Los estándares de codificación segura dan a los desarrolladores reglas concretas para escribir software que resista los ataques. Convierten los principios generales en prácticas que se pueden enseñar, verificar con herramientas y exigir en la revisión de código. Entre las referencias conocidas están el OWASP Top 10 (los riesgos de seguridad más críticos de las aplicaciones web), el OWASP Application Security Verification Standard (ASVS), la lista CWE (Common Weakness Enumeration) de tipos de debilidades del software y su Top 25 de las debilidades más peligrosas, los estándares de codificación SEI CERT para lenguajes específicos y el NIST Secure Software Development Framework (SSDF). Las organizaciones suelen adoptar uno o más de ellos y adaptarlos a sus lenguajes y plataformas.

Las debilidades del código fuente suelen caer en categorías recurrentes. Una validación de entradas deficiente permite que datos no confiables lleguen a los intérpretes. Un manejo inadecuado de errores revela a los usuarios trazas de pila, versiones o detalles de la base de datos. Las credenciales y claves codificadas en el código terminan en los repositorios. La criptografía débil o hecha en casa, los números aleatorios predecibles y los algoritmos obsoletos socavan la confidencialidad. El control de acceso roto no verifica la autorización en cada solicitud. Las condiciones de carrera y el manejo inseguro de la memoria crean fallas sutiles. Las puertas traseras o ganchos de mantenimiento (maintenance hooks), que a veces dejan los desarrolladores para hacer pruebas, eluden los controles normales y deben eliminarse antes del lanzamiento. El código muerto y las funciones de depuración que quedan en producción amplían la superficie de ataque.

Las prácticas básicas de codificación segura contrarrestan estas debilidades. Valida todas las entradas del lado del servidor contra una lista de permitidos de tipo, longitud, formato y rango esperados; las verificaciones del lado del cliente sirven solo para la usabilidad. Codifica la salida según el contexto donde se usa, como HTML, JavaScript o URL. Usa consultas parametrizadas o API seguras en lugar de construir comandos concatenando cadenas. Aplica la autenticación y la autorización de forma centralizada y verifica la autorización en cada solicitud y para cada objeto. Falla de forma segura: ante un error, niega el acceso y muestra mensajes genéricos mientras registras los detalles internamente. Usa bibliotecas criptográficas bien verificadas y nunca inventes algoritmos. Gestiona los secretos fuera del código. Aplica el mínimo privilegio a las propias cuentas de la aplicación. Mantén las dependencias actualizadas. Registra los eventos de seguridad sin datos sensibles.

Las interfaces de programación de aplicaciones (API) merecen atención especial porque exponen funcionalidad y datos directamente a otros programas, a menudo sin una interfaz de usuario que pudiera ocultar las debilidades. El OWASP API Security Top 10 destaca riesgos como la autorización rota a nivel de objeto (broken object-level authorization), en la que una API devuelve cualquier registro cuyo ID se proporcione sin verificar la propiedad; la autenticación rota; la exposición de más propiedades de un objeto de las que el solicitante debería ver (listada como exposición excesiva de datos en la edición de 2019); y el consumo ilimitado de recursos, como la falta de límites de tasa. Protege las API exigiendo una autenticación fuerte (por ejemplo, tokens de OAuth 2.0 con alcances limitados), autorizando cada objeto y función, validando las entradas contra un esquema, devolviendo solo los campos necesarios, aplicando límites de tasa y cuotas, usando TLS, manteniendo un inventario de todas las versiones de las API, incluidas las antiguas, y monitoreando mediante un API gateway. Las API REST suelen usar JSON y tokens; las API SOAP usan XML y WS-Security.

Haz cumplir los estándares mediante capacitación, plug-ins del IDE, reglas de SAST alineadas con el estándar, listas de verificación para la revisión de código entre pares y compuertas en el pipeline. Mide los tipos de debilidades recurrentes para enfocar la capacitación adicional.

Términos clave

CWE
Common Weakness Enumeration, un catálogo de tipos de debilidades de software y hardware.
OWASP Top 10
Lista ampliamente referenciada de los riesgos de seguridad más críticos de las aplicaciones web.
Input validation (validación de entradas)
Verificar que las entradas coincidan con el tipo, la longitud, el formato y el rango esperados, preferiblemente con una lista de permitidos y del lado del servidor.
Maintenance hook (backdoor) (gancho de mantenimiento o puerta trasera)
Punto de entrada oculto que se deja en el código y que elude los controles de seguridad normales.
Broken object-level authorization (autorización rota a nivel de objeto)
Falla de una API en la que se otorga acceso a un objeto por su ID sin verificar que el solicitante esté autorizado para ese objeto.
Ejemplo real

Durante la revisión de código de una API de banca móvil, un revisor nota que el endpoint que devuelve los estados de cuenta recibe un parámetro de ID de cuenta, pero solo verifica que el solicitante haya iniciado sesión. Cualquier usuario autenticado podría solicitar los estados de cuenta de otro cliente. La corrección agrega una verificación de propiedad, el equipo escribe una regla de SAST para señalar endpoints similares y el problema se convierte en un ejemplo didáctico en la capacitación de los desarrolladores.

Consejo para el examen: La validación de entradas del lado del servidor con listas de permitidos y la codificación de la salida son las respuestas clave en las preguntas sobre inyección y XSS. Para las API, recuerda la autorización a nivel de objeto: verifica que el solicitante pueda acceder a cada registro específico, no solo que haya iniciado sesión.

Comprueba lo que sabes

¿Por qué la validación de entradas del lado del cliente es insuficiente para la seguridad?

Los atacantes pueden eludir el cliente y enviar solicitudes directamente, así que la validación debe aplicarse en el servidor.

¿Qué debe mostrar una aplicación a los usuarios cuando ocurre un error?

Un mensaje de error genérico, mientras registra la información detallada internamente, para evitar revelar detalles de la implementación.

¿Qué es la autorización rota a nivel de objeto en una API?

Cuando una API otorga acceso a un objeto con base en un identificador proporcionado sin verificar que el solicitante esté autorizado para ese objeto específico.
