ISC2 CISSP 2024 outline

Revisión y pruebas de código: estáticas, dinámicas, fuzzing, casos de mal uso, cobertura de pruebas y pruebas de interfaces

El software es donde nacen muchas vulnerabilidades, por lo que probar el código es una actividad de evaluación central en el dominio de Evaluación y Pruebas de Seguridad. El examen espera que conozcas las principales técnicas, qué tipo de falla encuentra cada una y en qué parte del ciclo de vida de desarrollo de software (SDLC) encaja cada una. Ninguna técnica lo detecta todo. Un programa maduro combina varias de ellas para que los puntos ciegos de una queden cubiertos por otra, y empieza a probar lo antes posible, porque una falla encontrada en el diseño o en el código cuesta mucho menos corregir que una encontrada en producción.

La revisión de código es el examen del código fuente por personas distintas de su autor. Va desde la revisión informal entre pares en una solicitud de extracción (pull request) hasta la inspección formal, como la inspección de Fagan, que usa roles definidos (moderador, autor, lector, revisor) y etapas (planificación, visión general, preparación, reunión de inspección, retrabajo y seguimiento). La revisión manual detecta fallas lógicas, debilidades de diseño, verificaciones de autorización ausentes y mal uso de funciones de seguridad que las herramientas rara vez comprenden. Sus costos son el tiempo y la dependencia de la habilidad del revisor, por lo que las organizaciones suelen reservar la revisión manual profunda para código de alto riesgo, como los módulos de autenticación, pagos y criptografía.

Las pruebas estáticas analizan el código sin ejecutarlo. Las herramientas de pruebas estáticas de seguridad de aplicaciones (SAST) analizan código fuente, bytecode o binarios y buscan patrones como entradas no confiables que llegan a una consulta de base de datos, credenciales codificadas de forma fija o llamadas a funciones inseguras. Las pruebas estáticas pueden ejecutarse temprano, incluso antes de que la aplicación pueda desplegarse, y señalan el archivo y la línea exactos, pero producen falsos positivos y no pueden ver la configuración en tiempo de ejecución. Las pruebas dinámicas evalúan el software mientras se ejecuta. Las pruebas dinámicas de seguridad de aplicaciones (DAST) sondean una aplicación en ejecución desde el exterior y observan las respuestas, encontrando fallas de inyección, configuraciones erróneas y manejo débil de sesiones tal como las vería un atacante, pero necesitan un entorno funcional y no pueden decirte qué línea de código es la responsable.

El fuzzing es una técnica dinámica que alimenta a un programa con grandes volúmenes de entradas inválidas, inesperadas o aleatorias y observa si hay fallos, bloqueos, errores de memoria o excepciones no controladas. El fuzzing por mutación (a veces llamado fuzzing tonto) modifica muestras válidas existentes, por ejemplo invirtiendo bits en un archivo que se sabe correcto. El fuzzing por generación (fuzzing inteligente) construye entradas a partir de un modelo del formato de archivo o protocolo esperado, por lo que alcanza rutas de código más profundas. El fuzzing es especialmente bueno para encontrar errores de manejo de entradas, como desbordamientos de búfer y errores del analizador sintáctico, y a menudo se automatiza para ejecutarse durante horas o días.

Las pruebas de casos de mal uso, también llamadas pruebas de casos de abuso, invierten el caso de uso ordinario. Un caso de uso describe cómo un usuario legítimo alcanza un objetivo; un caso de mal uso describe cómo alguien podría abusar del sistema, por ejemplo ingresando una cantidad negativa para provocar un reembolso u omitiendo un paso en un flujo de pago. Los casos de mal uso suelen derivarse del modelado de amenazas y obligan a los probadores a verificar el comportamiento hostil y no solo el camino feliz. El análisis de cobertura de pruebas mide cuánto del código ejercitaron realmente las pruebas, normalmente como un porcentaje: unidades probadas divididas entre el total de unidades. La cobertura puede contarse por sentencias, ramas, condiciones, funciones o rutas. Las pruebas de interfaces verifican los puntos donde se conectan los componentes, incluidas las interfaces de programación de aplicaciones (API), las interfaces de usuario y las interfaces físicas, comprobando que cada una valide las entradas, aplique la autorización y maneje los errores de forma segura, porque las interfaces son donde se cruzan los límites de confianza.

Considera un ejemplo práctico. Un banco está desarrollando una aplicación móvil de préstamos. Los desarrolladores ejecutan SAST en su pipeline y corrigen una consulta SQL señalada antes de que el código llegue a ejecutarse. Un ingeniero de seguridad escribe casos de mal uso a partir del modelo de amenazas, incluido un intento de cambiar el monto del préstamo después de la aprobación, y los probadores confirman que el servidor lo rechaza. El equipo aplica fuzzing al analizador de carga de documentos y encuentra un fallo con encabezados de imagen malformados. Antes del lanzamiento, DAST escanea la compilación de preproducción y señala un encabezado de seguridad faltante, las pruebas de interfaces confirman que la API de socios rechaza solicitudes sin tokens válidos, y los informes de cobertura muestran que el módulo de verificación de fraude solo se probó parcialmente, así que se agregan más pruebas.

Errores comunes: creer que una alta cobertura de pruebas significa que el código es seguro (la cobertura solo muestra qué se ejecutó, no si las pruebas verificaron lo correcto); pensar que el fuzzing es una técnica estática (requiere ejecución); esperar que DAST señale la línea vulnerable; y tratar los casos de mal uso como si fueran lo mismo que las pruebas funcionales normales. Otra trampa es suponer que las herramientas automatizadas reemplazan la revisión de código. Las herramientas encuentran patrones conocidos rápidamente, mientras que los revisores humanos encuentran fallas de lógica de negocio que ninguna firma describe.

Las preguntas del examen suelen describir una situación y preguntar qué técnica corresponde. Palabras clave como "sin ejecutar", "temprano en el desarrollo" o "código fuente disponible" apuntan a pruebas estáticas o SAST. "Aplicación en ejecución", "perspectiva del atacante" o "sin código fuente" apuntan a pruebas dinámicas o DAST. "Entradas aleatorias o malformadas" significa fuzzing, "cómo un atacante podría abusar de una función" significa pruebas de casos de mal uso, y "porcentaje de código ejercitado" significa análisis de cobertura de pruebas. Cuando se pregunte qué debería hacer primero un gerente, prefiere la respuesta que integra las pruebas en el ciclo de vida desde temprano y combina métodos en lugar de depender de una sola herramienta.

Términos clave

Pruebas estáticas de seguridad de aplicaciones (SAST)
Análisis de código fuente, bytecode o binarios en busca de vulnerabilidades sin ejecutar el programa.
Pruebas dinámicas de seguridad de aplicaciones (DAST)
Pruebas de una aplicación en ejecución desde el exterior, enviando solicitudes y analizando las respuestas.
Fuzzing
Suministro de grandes volúmenes de entradas malformadas o aleatorias a un programa en ejecución para provocar fallos y errores que revelen fallas.
Caso de mal uso (misuse case)
Escenario que describe cómo un atacante o un usuario descuidado podría abusar de una función, usado para diseñar pruebas negativas.
Análisis de cobertura de pruebas (test coverage analysis)
Medición de cuánto código, como sentencias o ramas, fue ejercitado por las pruebas.
Pruebas de interfaces (interface testing)
Pruebas de los puntos de conexión entre componentes, como API e interfaces de usuario, en cuanto a manejo de entradas, autorización y manejo de errores.
Inspección de Fagan (Fagan inspection)
Proceso formal y estructurado de revisión de código con roles y etapas definidos.
Ejemplo real

Un minorista en línea aplica fuzzing a su nuevo servicio de redimensionamiento de imágenes durante un fin de semana y descubre que ciertos encabezados de imagen malformados hacen fallar el proceso. Los desarrolladores corrigen las verificaciones de longitud del analizador. Por separado, un caso de mal uso escrito a partir del modelo de amenazas, ingresar un código de cupón dos veces en solicitudes paralelas, revela que el descuento se aplica dos veces, una falla de lógica de negocio que ni SAST ni DAST habían reportado.

Consejo para el examen: Estático significa que el código no se está ejecutando, puede hacerse temprano y señala la línea exacta; dinámico significa que la aplicación está en ejecución y muestra la visión del atacante. El fuzzing es dinámico y se enfoca en el manejo de entradas, y los casos de mal uso prueban lo que intentaría un atacante.

Comprueba lo que sabes

Un equipo tiene el código fuente pero aún no tiene una compilación desplegable. ¿Qué enfoque de pruebas puede usar ahora?

Pruebas estáticas como SAST o revisión manual de código, porque el análisis estático no requiere que el programa se ejecute.

¿Cuál es la diferencia entre el fuzzing por mutación y el fuzzing por generación?

El fuzzing por mutación altera entradas válidas existentes, mientras que el fuzzing por generación construye entradas nuevas a partir de un modelo del formato esperado, lo que le permite alcanzar rutas de código más profundas.

¿Por qué una cobertura de pruebas del 95 por ciento no demuestra que una aplicación sea segura?

La cobertura muestra cuánto código ejecutaron las pruebas, no si las pruebas verificaron fallas de seguridad o entradas hostiles.

Un probador documenta cómo un usuario podría enviar una cantidad negativa para obtener un reembolso. ¿Qué técnica es esta?

Pruebas de casos de mal uso (abuso), que modelan cómo podría abusarse de una función en lugar de usarse según lo previsto.
