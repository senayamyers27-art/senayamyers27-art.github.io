ISC2 CISSP 2024 outline

Revisión y pruebas de código: estáticas, dinámicas, fuzzing, casos de mal uso, cobertura de pruebas y pruebas de interfaces

El software es donde nacen muchas vulnerabilidades, así que probar el código es una actividad de evaluación central. El examen CISSP espera que conozcas las técnicas principales, qué encuentra cada una y en qué momento del ciclo de vida se aplica. Ninguna técnica por sí sola es suficiente; los programas maduros combinan varias.

La revisión de código es el examen del código fuente por personas distintas de su autor. Va desde la revisión informal entre pares durante un pull request hasta la inspección formal, como el proceso de inspección de Fagan, con roles definidos (moderador, autor, lector, revisor) y etapas (planificación, visión general, preparación, inspección, retrabajo, seguimiento). La revisión manual detecta fallas de lógica, debilidades de diseño y el mal uso de funciones de seguridad que las herramientas pasan por alto, pero es lenta y depende de la habilidad del revisor.

Las pruebas estáticas analizan el código sin ejecutarlo. Las herramientas de pruebas estáticas de seguridad de aplicaciones (SAST) analizan el código fuente o los binarios compilados para encontrar patrones como entradas sin sanitizar que llegan a una consulta de base de datos, credenciales incrustadas o funciones inseguras. Las pruebas estáticas pueden ejecutarse temprano, incluso antes de que la aplicación pueda desplegarse, y señalan la línea exacta de código, pero tienden a producir falsos positivos y no pueden ver la configuración en tiempo de ejecución. Las pruebas dinámicas evalúan el software mientras se ejecuta. Las pruebas dinámicas de seguridad de aplicaciones (DAST) sondean una aplicación en ejecución desde el exterior, enviando solicitudes elaboradas y observando las respuestas, lo que encuentra problemas como configuraciones incorrectas y fallas de inyección tal como los vería un atacante, pero necesitan un entorno funcional y no muestran en qué parte del código está el error.

El fuzzing es una técnica dinámica que alimenta a un programa con grandes volúmenes de entradas inválidas, inesperadas o aleatorias para provocar fallos, bloqueos o errores de memoria que sugieran vulnerabilidades. El fuzzing por mutación ('tonto') modifica entradas válidas existentes, como invertir bits en un archivo de muestra. El fuzzing por generación ('inteligente') construye las entradas a partir de un modelo del formato o protocolo esperado, lo que alcanza rutas de código más profundas. El fuzzing es especialmente bueno para encontrar errores en el manejo de entradas, como los desbordamientos de búfer.

Las pruebas de casos de mal uso (misuse case), también llamadas de casos de abuso (abuse case), invierten el caso de uso habitual. Donde un caso de uso describe cómo un usuario legítimo logra un objetivo, un caso de mal uso describe cómo un atacante podría abusar del sistema, como enviar una cantidad negativa para recibir un reembolso u omitir un paso en un flujo de pago. Escribir casos de mal uso a partir de los modelos de amenazas ayuda a los probadores a verificar que la aplicación maneja el comportamiento hostil, no solo el camino feliz.

El análisis de cobertura de pruebas mide cuánto del código han ejercitado las pruebas, comúnmente expresado como un porcentaje: unidades probadas divididas entre unidades totales. La cobertura puede medirse por sentencias, ramas, condiciones, funciones o rutas. Una cobertura alta no garantiza la seguridad, pero una cobertura baja muestra territorio sin probar. Las pruebas de interfaces verifican los puntos donde se conectan los componentes: interfaces de programación de aplicaciones (API), interfaces de usuario e interfaces físicas. Comprueban que cada interfaz valide las entradas, aplique la autorización y maneje los errores correctamente, ya que las interfaces son donde se cruzan los límites de confianza.

Términos clave

Static testing (SAST) (pruebas estáticas)
Analizar el código fuente o compilado sin ejecutarlo para encontrar vulnerabilidades temprano.
Dynamic testing (DAST) (pruebas dinámicas)
Probar una aplicación en ejecución desde el exterior para encontrar vulnerabilidades en su comportamiento.
Fuzzing
Suministrar grandes volúmenes de entradas malformadas o aleatorias para encontrar fallos y errores en el manejo de entradas; puede basarse en mutación o en generación.
Misuse case (caso de mal uso)
Un escenario que describe cómo un atacante podría abusar de un sistema, usado para diseñar pruebas de seguridad.
Test coverage (cobertura de pruebas)
La proporción del código (sentencias, ramas, rutas) que ejercitan las pruebas.
Ejemplo real

Un equipo que construye un servicio de carga de archivos ejecuta SAST en cada commit, lo que señala una ruta construida a partir de la entrada del usuario. Antes del lanzamiento, DAST contra una copia de staging encuentra un encabezado de seguridad faltante, y un fuzzer por generación construido a partir de la especificación del formato de imagen hace fallar el analizador de miniaturas. Los probadores también escriben un caso de mal uso en el que un usuario sube un archivo con un nombre diseñado para sobrescribir los archivos de otro cliente, y confirman que la corrección lo bloquea.

Consejo para el examen: Estático equivale a código que no se ejecuta, temprano, línea exacta, más falsos positivos. Dinámico equivale a aplicación en ejecución, vista del atacante, sin números de línea. El fuzzing es dinámico y apunta al manejo de entradas. Los casos de mal uso prueban lo que haría un atacante.

Comprueba lo que sabes

¿Qué técnica puede usarse antes de que una aplicación pueda desplegarse?

Las pruebas estáticas (SAST o revisión manual de código), porque no requieren que el código se ejecute.

¿Cuál es la diferencia entre el fuzzing por mutación y el fuzzing por generación?

El fuzzing por mutación modifica entradas válidas existentes; el fuzzing por generación crea entradas a partir de un modelo del formato o protocolo esperado.

¿Una cobertura de pruebas del 100 por ciento significa que el código es seguro?

No. Significa que las pruebas ejecutaron todo el código, pero las pruebas pueden no verificar fallas de seguridad ni entradas hostiles.
