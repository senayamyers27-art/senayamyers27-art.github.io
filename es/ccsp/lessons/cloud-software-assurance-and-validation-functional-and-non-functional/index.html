ISC2 Certified Cloud Security Professional 2026 outline (effective Aug 1, 2026)

Aseguramiento y validación del software en la nube: pruebas funcionales y no funcionales, SAST, DAST, IAST, SCA y casos de abuso

El aseguramiento del software es la confianza en que el software hace lo que debe y nada de lo que no debe. Esa confianza se obtiene con pruebas, y el CCSP espera que sepas qué tipo de prueba encuentra qué tipo de problema y dónde encaja cada una en un flujo de entrega en la nube.

Las pruebas funcionales verifican que las funciones se comporten como se especificó: un usuario puede restablecer su contraseña, el total de un pedido se calcula correctamente. La seguridad también tiene requisitos funcionales, como bloquear una cuenta después de fallos repetidos o negar el acceso a usuarios sin un rol. Las pruebas no funcionales verifican cualidades como el rendimiento, la escalabilidad, la disponibilidad, la resiliencia y la usabilidad. En la nube, las pruebas de carga y de resiliencia importan porque el autoescalado, la conmutación por falla y los límites de costo deben comportarse como se espera bajo estrés. Los casos de abuso, a veces llamados casos de mal uso, convierten el comportamiento de un atacante en escenarios de prueba: ¿qué pasa si un usuario envía el ID de otro cliente, sube un archivo enorme o llama a una API un millón de veces?

Las herramientas automatizadas de pruebas de seguridad miran el software desde ángulos distintos. Las pruebas estáticas de seguridad de aplicaciones (SAST) analizan el código fuente, el bytecode o los binarios sin ejecutarlos. Encuentran fallas temprano, señalan la línea exacta y encajan en el flujo de trabajo del desarrollador, pero pueden producir falsos positivos y no ven la configuración en ejecución. Las pruebas dinámicas de seguridad de aplicaciones (DAST) atacan una aplicación en ejecución desde fuera, como un evaluador de caja negra; encuentran problemas reales explotables y problemas de configuración, pero solo más tarde en el ciclo de vida y sin señalar el código. Las pruebas interactivas de seguridad de aplicaciones (IAST) colocan un agente dentro de la aplicación en ejecución durante las pruebas, combinando la observación en tiempo de ejecución con el detalle a nivel de código. El análisis de composición de software (SCA) hace un inventario de los componentes de terceros y de código abierto, señala vulnerabilidades conocidas y problemas de licencias y puede producir una lista de materiales de software (SBOM).

El aseguramiento de la calidad lo une todo. Integra estas pruebas en el flujo de CI/CD con umbrales que bloqueen los lanzamientos ante hallazgos graves, clasifica y corrige los resultados y agrega pruebas de penetración hechas por personas capacitadas para los sistemas críticos. Antes de hacer pruebas contra la infraestructura de un proveedor, revisa su política de pruebas de penetración; muchos proveedores permiten probar tus propios recursos sin aprobación previa, pero prohíben atacar la plataforma subyacente.

Términos clave

SAST
Pruebas estáticas de seguridad de aplicaciones: analizar el código sin ejecutarlo para encontrar fallas de seguridad.
DAST
Pruebas dinámicas de seguridad de aplicaciones: sondear una aplicación en ejecución desde fuera para encontrar debilidades explotables.
IAST
Pruebas interactivas de seguridad de aplicaciones: un agente dentro de la aplicación en ejecución observa el comportamiento durante las pruebas y reporta fallas con contexto del código.
SCA
Análisis de composición de software: identificar los componentes de terceros y sus vulnerabilidades y licencias conocidas.
Ejemplo real

El flujo de un equipo ejecuta SAST y SCA en cada pull request, bloquea las fusiones con hallazgos críticos y ejecuta DAST cada noche contra un entorno de staging. Cuando SCA señala una vulnerabilidad recién divulgada en una biblioteca de registro, el equipo sabe en menos de una hora cuáles de sus 40 servicios la incluyen, gracias a los SBOM que genera cada compilación.

Consejo para el examen: SAST = código en reposo, temprano, caja blanca. DAST = aplicación en ejecución, más tarde, caja negra. SCA = componentes de terceros. Si la pregunta trata de una biblioteca de código abierto con una vulnerabilidad conocida, la respuesta es SCA.

Comprueba lo que sabes

¿Qué tipo de prueba analiza el código fuente sin ejecutarlo?

SAST.

¿Qué aporta un SBOM?

Un inventario de los componentes y dependencias de un software, que se usa para encontrar los sistemas afectados cuando se divulga una vulnerabilidad.

¿Por qué debes leer primero la política de pruebas de penetración de un proveedor?

Los proveedores fijan reglas sobre lo que los clientes pueden probar; atacar la plataforma subyacente o a otros inquilinos suele estar prohibido.
