ISC2 Certified Cloud Security Professional 2026 outline (effective Aug 1, 2026)

Protección del plano de administración y los hipervisores: tipo 1 frente a tipo 2, escape de VM y aislamiento

El hipervisor y el plano de administración son los dos componentes que, si se comprometen, exponen todo lo que está por encima de ellos. El examen espera que conozcas los tipos de hipervisor, por qué importa el aislamiento y cómo protegen el acceso administrativo tanto el proveedor como el cliente.

Un hipervisor tipo 1, también llamado bare metal, se ejecuta directamente sobre el hardware físico sin un sistema operativo de uso general debajo. Tiene una superficie de ataque pequeña y alto rendimiento, por eso los proveedores de nube usan diseños tipo 1. Un hipervisor tipo 2, también llamado alojado (hosted), se ejecuta como una aplicación sobre un sistema operativo normal, como el software de virtualización de escritorio en una laptop. Es práctico para pruebas pero hereda todas las vulnerabilidades del sistema operativo anfitrión, así que no es adecuado para nubes multiinquilino.

El aislamiento es la promesa de seguridad del hipervisor: cada máquina virtual solo debe ver su propia memoria, almacenamiento y tráfico de red. El escape de VM rompe esa promesa, y es raro pero grave. Los proveedores reducen el riesgo manteniendo hipervisores mínimos, parchándolos rápido, usando funciones de virtualización por hardware y, a veces, delegando la red y el almacenamiento a hardware dedicado para que el host tenga menos código que atacar. Los clientes con requisitos estrictos pueden elegir hosts dedicados o aislados para que sus cargas de trabajo nunca compartan hardware con otros inquilinos, o cómputo confidencial para que la memoria esté cifrada incluso frente al host.

El plano de administración incluye la consola web, las API y las herramientas de línea de comandos que gestionan los recursos de nube. Protegerlo es principalmente trabajo del cliente para su propia cuenta. Ten pocos administradores, exige MFA resistente al phishing, evita usar la cuenta raíz o de propietario para el trabajo diario y guarda bajo llave sus credenciales, da a los administradores identidades privilegiadas separadas, otorga elevación justo a tiempo en lugar de privilegios permanentes, restringe el acceso a la consola y a la API por red o dispositivo cuando sea posible y registra cada acción de administración en un lugar protegido. Las cuentas de emergencia (break-glass) deben existir, estar muy controladas y generar alertas cada vez que se usen.

Términos clave

Hipervisor tipo 1
Un hipervisor bare metal que se ejecuta directamente sobre el hardware, usado por los proveedores de nube por su superficie de ataque pequeña.
Hipervisor tipo 2
Un hipervisor alojado que se ejecuta como aplicación sobre un sistema operativo de uso general.
Cuenta de emergencia (break-glass)
Una cuenta administrativa de emergencia guardada bajo llave que solo se usa cuando falla el acceso normal, con alertas y revisión en cada uso.
Acceso justo a tiempo
Otorgar privilegios elevados solo cuando se necesitan y por un tiempo limitado, en lugar de forma permanente.
Ejemplo real

Un minorista descubre que ocho ingenieros inician sesión a diario con las credenciales raíz de su cuenta de nube. Traslada todo el trabajo diario a roles de administrador federados con MFA y elevación por tiempo limitado, guarda las credenciales raíz con una llave de hardware en una caja fuerte y configura una alerta que avisa al equipo de seguridad cada vez que la cuenta raíz inicia sesión.

Consejo para el examen: El tipo 1 se ejecuta sobre el hardware y se usa en la nube; el tipo 2 se ejecuta sobre un sistema operativo anfitrión. Si una pregunta pide cuál es más seguro para la multitenencia, elige el tipo 1.

Comprueba lo que sabes

¿Por qué los proveedores de nube prefieren los hipervisores tipo 1?

Se ejecutan directamente sobre el hardware, con una superficie de ataque más pequeña y mejor rendimiento que los hipervisores alojados.

¿Qué puede hacer un cliente si una carga de trabajo no debe compartir hardware físico con otros inquilinos?

Usar hosts dedicados o aislados (o cómputo confidencial para proteger la memoria frente al host).

¿Cómo deben manejarse las credenciales raíz o de propietario de la cuenta de nube?

No usarlas para el trabajo diario; protegerlas con MFA fuerte, guardarlas de forma segura y monitorearlas con alertas en cada uso.
