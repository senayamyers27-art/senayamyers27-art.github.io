El antiguo comando de la CLI `terraform import`

Antes de que existieran los bloques import, la única forma de poner infraestructura existente bajo Terraform era el comando terraform import. Todavía está disponible y todavía aparece en el examen, así que necesitas saber cómo funciona y por qué normalmente se prefiere el enfoque más nuevo.

La sintaxis es terraform import ADDRESS ID. ADDRESS es la dirección del recurso en tu configuración, como aws_instance.web o module.app.aws_instance.web[0], e ID es el identificador del provider para el objeto real. El comando lee el objeto desde el provider y lo escribe de inmediato en el estado bajo esa dirección.

$ terraform import aws_instance.web i-0abc123def4567890
aws_instance.web: Importing from ID "i-0abc123def4567890"...
Import successful!

Hay un requisito previo importante: el bloque resource ya debe existir en tu configuración antes de ejecutar el comando. terraform import no escribe la configuración por ti. Si aws_instance.web no está declarado, el comando falla. Así que el flujo de trabajo antiguo era: escribir un bloque resource vacío o aproximado, ejecutar terraform import, luego ejecutar terraform plan y seguir ajustando el bloque hasta que el plan no mostrara cambios. Solo entonces la configuración es una descripción fiel del objeto real.

En comparación con los bloques import, el comando tiene limitaciones claras. Importa un recurso por invocación, así que traer docenas de objetos significa docenas de comandos o un script. Cambia el estado de inmediato, sin un plan que revisar primero y sin registro en el control de versiones de lo que se importó. No puede generar configuración. Y ocurre fuera del flujo de trabajo normal de pull requests, lo que dificulta auditarlo en entornos de equipo, especialmente con HCP Terraform, donde normalmente querrías que cada cambio de estado provenga de una ejecución revisada.

El comando también acepta indicadores útiles como -var y -var-file, porque Terraform debe evaluar la configuración (incluidos los ajustes del provider) para saber cómo llegar al objeto. Con un backend remoto, el objeto importado se escribe en el estado remoto y se aplica el bloqueo habitual.

¿Cuándo deberías seguir usándolo? Está bien para una importación rápida y puntual en un proyecto pequeño, o con herramientas que no han pasado a los bloques import. Para cualquier cosa más grande o compartida, prefiere los bloques import. En cualquier caso, importar no es lo mismo que crear: Terraform asume la gestión de un objeto existente, y un terraform destroy posterior eliminará ese objeto real, así que asegúrate de que quieres que Terraform sea su dueño.

Términos clave

terraform import
Un comando de la CLI que escribe de inmediato un objeto existente en el estado en una dirección de recurso dada.
ADDRESS
La dirección del recurso en la configuración a la que se vinculará el objeto importado.
Prerequisite resource block (bloque resource previo)
El bloque resource que ya debe existir en la configuración para que terraform import tenga éxito.
Post-import plan (plan posterior a la importación)
Ejecutar terraform plan después de importar y ajustar la configuración hasta que no se muestren cambios.
Ejemplo real

Un ingeniero necesita gestionar una zona DNS construida a mano. Escribe resource "aws_route53_zone" "main" {} con el nombre de la zona, ejecuta terraform import aws_route53_zone.main seguido del ID de la zona y luego ajusta el bloque hasta que terraform plan no informa cambios.

Consejo para el examen: terraform import necesita que el bloque resource exista primero, importa un objeto a la vez y no genera configuración; los bloques import eliminan esos límites.

Comprueba lo que sabes

¿Qué debe existir antes de ejecutar terraform import aws_instance.web i-123?

Un bloque resource para aws_instance.web en la configuración.

¿terraform import muestra un plan antes de cambiar el estado?

No. Escribe en el estado de inmediato; solo los bloques import pasan por plan y apply.
