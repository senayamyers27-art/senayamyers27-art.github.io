Cuándo usar los logs: errores de providers, fallos (crashes) y reportes de bugs

La mayoría de los errores de Terraform no necesitan logs. Los problemas de sintaxis, las variables faltantes, los errores de tipo y las validaciones fallidas producen mensajes claros que señalan un archivo y una línea. terraform validate y terraform fmt detectan muchos de ellos incluso antes de planificar. Recurre a los logs cuando la salida normal no basta para explicar lo que ocurrió.

Ayuda saber dónde está el problema. La resolución de problemas de Terraform suele agruparse en cuatro áreas: errores del lenguaje (sintaxis y semántica de HCL, que core detecta e informa con claridad), errores de estado (drift o corrupción del estado, que a menudo se corrigen con refresh-only o comandos de estado), errores de core (bugs en el propio Terraform) y errores de providers (problemas en un plugin de provider o en la API remota a la que llama). Los logs son más valiosos para los dos últimos.

Los errores de providers son la razón más común para habilitar el registro. Cuando la API de una nube rechaza una solicitud con un mensaje poco claro, un provider agota el tiempo de espera o un recurso sigue mostrando cambios después de cada apply, los logs del provider muestran las solicitudes y respuestas reales. Establecer TF_LOG_PROVIDER=DEBUG o TRACE te permite ver el endpoint, el código de estado y el cuerpo del error. A partir de ahí puedes saber si el problema es de permisos, de una cuota, de un límite de la API o un bug del provider.

Los fallos (crashes) son el otro caso importante. Si Terraform o un plugin entra en pánico (panic), ves un mensaje de que Terraform falló junto con un stack trace impreso en la salida. Ese trace, y un log de nivel TRACE de la misma ejecución, es lo que necesitan los mantenedores. Para un fallo de core, lo reportarías al proyecto de Terraform; para un fallo de un provider, a los mantenedores de ese provider, porque los providers son programas separados que se desarrollan por separado.

Al presentar un reporte de bug, incluye la versión de Terraform y las versiones de los providers (terraform version muestra ambas), una configuración mínima que reproduzca el problema, el comportamiento esperado y el real, y el log relevante, normalmente capturado con TF_LOG=TRACE y TF_LOG_PATH. Antes de compartirlo, elimina los secretos como tokens, contraseñas e identificadores de cuentas, porque los logs de trace pueden contenerlos.

Un enfoque práctico es empezar de forma acotada: reproduce el problema, activa el registro en DEBUG para el componente que sospechas y sube a TRACE solo si necesitas más. Busca en el log la palabra error o la dirección del recurso implicado. Luego vuelve a desactivar el registro, ya que los logs detallados hacen más lentas las ejecuciones y llenan los discos.

Términos clave

Provider error (error de provider)
Un fallo en un plugin de provider o en la API remota a la que llama, que a menudo se diagnostica con los logs del provider.
Crash (panic, fallo)
Una terminación inesperada de Terraform o de un plugin que imprime un stack trace y que debe reportarse con logs.
terraform version
Comando que muestra la versión de Terraform y las versiones de los providers instalados, necesarias para los reportes de bugs.
Minimal reproduction (reproducción mínima)
La configuración más pequeña que todavía muestra el problema, incluida en un reporte de bug.
Ejemplo real

Un apply falla por tiempo de espera agotado al crear un balanceador de carga. La salida normal solo dice que se excedió el plazo del contexto. Con TF_LOG_PROVIDER=DEBUG, la ingeniera ve que la API devuelve un error de limitación (throttling) en las comprobaciones de estado repetidas, y aumenta la cuota de solicitudes en lugar de editar la configuración.

Consejo para el examen: Usa los logs para errores de providers y fallos; incluye en los reportes de bugs la salida de terraform version, una configuración mínima y un log TRACE sin datos sensibles.

¿Qué comando da los detalles de versión que deberías incluir en un reporte de bug?

terraform version, que lista las versiones de Terraform y de los providers.

¿Por qué deben revisarse los logs de trace antes de publicarlos?

Pueden contener datos sensibles como tokens, contraseñas y atributos de recursos.
