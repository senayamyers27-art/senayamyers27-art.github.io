Migrar el estado entre backends con `terraform init -migrate-state`

Los equipos suelen empezar con estado local y luego pasar a un backend remoto, o moverse entre backends remotos cuando cambian de nube o adoptan HCP Terraform. Terraform puede copiar por ti el estado existente del backend anterior al nuevo como parte de la reinicialización, así que no tienes que mover archivos a mano.

El proceso es corto. Primero, edita la configuración: agrega, cambia o elimina el bloque backend (o agrega un bloque cloud). Luego, ejecuta terraform init. Terraform detecta que la configuración del backend difiere de la registrada en .terraform y pregunta qué hacer. Ejecutar terraform init -migrate-state le indica explícitamente que quieres copiar el estado existente al nuevo backend. Terraform entonces pide confirmación, copia el estado y, a partir de ese momento, usa la nueva ubicación.

$ terraform init -migrate-state
Initializing the backend...
Do you want to copy existing state to the new backend?
  Enter "yes" to copy and "no" to start with an empty state.

Compáralo con terraform init -reconfigure. Ese indicador también acepta una configuración de backend cambiada, pero ignora los ajustes del backend anterior guardados y no migra ningún estado. Es útil cuando intencionalmente quieres apuntar a otro estado que ya existe, o cuando el backend anterior no es accesible, pero usado por error te deja viendo un estado vacío o distinto mientras el estado anterior queda intacto. Recuerda: -migrate-state copia, -reconfigure no.

Volver de un backend remoto al estado local funciona de la misma forma: elimina el bloque backend y ejecuta terraform init -migrate-state, y Terraform copia el estado en un terraform.tfstate local. Si usas varios workspaces de la CLI, Terraform puede migrarlos todos, y te preguntará cómo asociarlos cuando el destino maneje los workspaces de otra forma. Agregar -force-copy responde que sí a los avisos, lo que es práctico en la automatización.

Antes de cualquier migración, toma precauciones. Asegúrate de que nadie más esté ejecutando Terraform, guarda una copia de respaldo del estado (por ejemplo con terraform state pull > backup.tfstate) y, después, ejecuta terraform plan para confirmar que el nuevo backend contiene los mismos recursos y que el plan no muestra cambios inesperados. Cuando tengas la confianza, elimina o restringe la ubicación del estado anterior para que nadie siga escribiendo en ella.

Términos clave

terraform init -migrate-state
Reinicializa con un backend cambiado y copia el estado existente del backend anterior al nuevo.
terraform init -reconfigure
Reinicializa con un backend cambiado ignorando los ajustes del backend anterior y sin migrar el estado.
-force-copy
Un indicador de init que responde automáticamente que sí a los avisos de migración del estado.
terraform state pull
Muestra el estado actual desde el backend configurado; útil para hacer un respaldo antes de una migración.
Ejemplo real

Una startup ha estado usando estado local. La líder técnica agrega un bloque backend gcs, ejecuta terraform state pull para guardar un respaldo, luego ejecuta terraform init -migrate-state y responde yes. Un terraform plan posterior no muestra cambios, lo que confirma que el bucket ahora contiene el mismo estado.

Consejo para el examen: Para que tus recursos sigan rastreados al cambiar de backend, usa -migrate-state; -reconfigure empieza de cero con el nuevo backend y no copia nada.

Comprueba lo que sabes

Cambias tu backend de local a s3 y quieres que tu estado existente se mueva. ¿Qué comando usas?

terraform init -migrate-state, y luego confirmas la copia.

¿Cuál es el riesgo de usar terraform init -reconfigure después de cambiar de backend?

No copia el estado, así que Terraform puede ver un estado vacío y planear recrear recursos existentes.
