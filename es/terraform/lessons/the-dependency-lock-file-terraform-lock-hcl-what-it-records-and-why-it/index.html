El archivo de bloqueo de dependencias `.terraform.lock.hcl`: qué registra y por qué se hace commit de él

Las restricciones de versión dicen qué versiones de un provider son aceptables. No garantizan que todos usen la misma versión. Si tu restricción es ~> 5.0 y mañana sale una nueva versión 5.x, un compañero que inicialice un clon nuevo podría obtener una versión distinta de la tuya. El archivo de bloqueo de dependencias, .terraform.lock.hcl, resuelve esto.

Cuando terraform init instala providers, escribe o actualiza .terraform.lock.hcl en el directorio del módulo raíz. Para cada provider registra la dirección source completa, la versión exacta seleccionada, las restricciones que estaban vigentes y un conjunto de checksums (hashes) de los paquetes del provider. En ejecuciones posteriores de init, Terraform reutiliza la versión registrada en lugar de elegir la más reciente permitida, y verifica que los paquetes descargados coincidan con los hashes registrados.

provider "registry.terraform.io/hashicorp/random" {
  version     = "3.6.2"
  constraints = "~> 3.5"
  hashes = [
    "h1:...",
    "zh:...",
  ]
}

Haz commit de este archivo en el control de versiones. Así, tu laptop, las laptops de tus compañeros, el pipeline de CI y HCP Terraform usan exactamente las mismas versiones de providers, y un cambio de versión de un provider aparece como un diff visible en un pull request. Los hashes también añaden una protección de la cadena de suministro: si un paquete descargado no coincide con un checksum registrado, init falla en lugar de ejecutar un binario inesperado.

Para pasar a una versión más reciente de un provider dentro de tus restricciones, ejecuta terraform init -upgrade. Terraform ignora las versiones bloqueadas, selecciona las versiones más recientes permitidas y reescribe el archivo de bloqueo, que luego revisas y confirmas con commit. Si cambiaste una restricción de forma que la versión bloqueada ya no la cumple, init informa un error y te indica que uses -upgrade.

Los hashes son específicos de cada plataforma. Si los desarrolladores usan macOS pero el pipeline se ejecuta en Linux, un archivo de bloqueo creado en una Mac podría contener solo hashes del paquete para Mac. El comando terraform providers lock puede rellenar de antemano hashes para varias plataformas, por ejemplo con -platform=linux_amd64 -platform=darwin_arm64.

Dos detalles se evalúan con frecuencia. El archivo de bloqueo solo rastrea providers; no bloquea las versiones de los módulos, que fijas con el argumento version del bloque module. Y es distinto del directorio .terraform, que contiene los plugins y módulos descargados y no debe incluirse en commits; agrega .terraform/ a .gitignore.

Términos clave

Dependency lock file (archivo de bloqueo de dependencias)
.terraform.lock.hcl, que registra las versiones exactas de los providers y los checksums de los paquetes seleccionados por terraform init.
terraform init -upgrade
Vuelve a seleccionar las versiones más recientes de providers (y módulos) permitidas por las restricciones y actualiza el archivo de bloqueo.
Checksum (hash)
Una huella digital de un paquete de provider que se usa para verificar que el archivo descargado es el esperado.
.terraform directory (directorio .terraform)
Directorio de trabajo local donde init guarda los providers y módulos descargados; no se incluye en commits.
Ejemplo real

Un pipeline falla de repente después de que una nueva versión minor de un provider cambió un valor predeterminado. El equipo no había hecho commit del archivo de bloqueo, así que CI eligió la versión más reciente. Después de hacer commit de .terraform.lock.hcl, CI usa la misma versión que los desarrolladores hasta que alguien ejecute deliberadamente terraform init -upgrade.

Consejo para el examen: Archivo de bloqueo: haz commit de él. Directorio .terraform/: no hagas commit de él. Y el archivo de bloqueo cubre providers, no módulos.

Comprueba lo que sabes

¿Qué comando actualiza las versiones de providers registradas en .terraform.lock.hcl?

terraform init -upgrade, que selecciona las versiones más recientes permitidas por las restricciones y reescribe el archivo.

¿El archivo de bloqueo de dependencias fija las versiones de los módulos?

No. Solo rastrea providers; las versiones de los módulos se restringen con el argumento version de los bloques module.
