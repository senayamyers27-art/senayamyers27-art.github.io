El bloque `cloud` para HCP Terraform

HCP Terraform (antes Terraform Cloud) es el servicio alojado de HashiCorp para ejecutar Terraform y guardar el estado. Para conectar una configuración a él, usas un bloque cloud dentro del bloque terraform de nivel superior. El bloque cloud reemplazó al antiguo backend remote como integración recomendada, y hace más que un backend: además de guardar el estado, permite que comandos de la CLI como plan y apply se ejecuten de forma remota en HCP Terraform.

El bloque necesita saber qué organización usar y a qué workspace o workspaces se asocia la configuración. El argumento organization nombra la organización de HCP Terraform. El bloque anidado workspaces selecciona los workspaces por name, que asocia la configuración a exactamente un workspace, o por tags, que la asocia a todos los workspaces que tengan esas etiquetas y te permite cambiar entre ellos con terraform workspace select. También puedes establecer project para colocar los nuevos workspaces en un proyecto concreto, y hostname cuando usas Terraform Enterprise en lugar de la dirección predeterminada de HCP Terraform.

terraform {
  cloud {
    organization = "example-org"
    workspaces {
      name = "networking-prod"
    }
  }
}

Una configuración puede tener un bloque cloud o un bloque backend, nunca ambos. Al igual que los bloques backend, el bloque cloud no puede usar variables de entrada ni locals. En su lugar, HCP Terraform admite variables de entorno que completan o anulan los ajustes: TF_CLOUD_ORGANIZATION, TF_CLOUD_HOSTNAME, TF_CLOUD_PROJECT y TF_WORKSPACE. Esto permite que un pipeline apunte el mismo código a distintas organizaciones o workspaces.

Antes de que terraform init pueda comunicarse con HCP Terraform, la CLI necesita un token de API. Normalmente obtienes uno con terraform login, que lo guarda en un archivo local de credenciales, o lo proporcionas en una variable de entorno. Luego terraform init se conecta a la organización, crea el workspace si es necesario y, si tenías un estado existente, puede migrarlo al workspace.

Una vez conectado, lo que ocurre con terraform plan depende del modo de ejecución del workspace. En el modo remoto (el predeterminado), el plan se ejecuta en la infraestructura de HCP Terraform y la salida se transmite a tu terminal, usando las variables guardadas en el workspace. En el modo local, las ejecuciones ocurren en tu máquina y HCP Terraform solo guarda el estado. En ambos casos, el estado se mantiene de forma segura en el workspace con historial y bloqueo.

Términos clave

cloud block (bloque cloud)
Un bloque dentro de terraform {} que conecta una configuración a HCP Terraform o Terraform Enterprise para el estado y las ejecuciones.
organization
El argumento del bloque cloud que nombra la organización de HCP Terraform dueña de los workspaces.
workspaces { name / tags }
El bloque anidado que asocia la configuración a un workspace por nombre o a varios por etiquetas.
Execution mode (modo de ejecución)
Un ajuste del workspace que decide si las ejecuciones se hacen de forma remota en HCP Terraform, localmente o en agentes.
Ejemplo real

Un equipo agrega un bloque cloud que nombra su organización y el workspace app-staging, ejecuta terraform login y luego terraform init. Su siguiente terraform plan se ejecuta en HCP Terraform, transmite la salida a la terminal y usa las credenciales de la nube guardadas como variables del workspace, así que nadie necesita claves en su laptop.

Consejo para el examen: El bloque cloud y un bloque backend son mutuamente excluyentes; el bloque cloud selecciona workspaces por nombre (uno) o por etiquetas (varios) y puede anularse con TF_CLOUD_ORGANIZATION y TF_WORKSPACE.

Comprueba lo que sabes

¿Puede una configuración contener tanto un bloque cloud como un bloque backend?

No. Son formas mutuamente excluyentes de configurar dónde se guarda el estado.

¿Cómo asocia un bloque cloud una configuración a varios workspaces?

Usando tags en el bloque workspaces en lugar de un único name.
