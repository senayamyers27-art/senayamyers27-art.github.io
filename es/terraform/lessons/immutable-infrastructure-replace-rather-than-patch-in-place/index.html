Infraestructura inmutable: reemplazar en lugar de parchear en el lugar

En un modelo mutable, mantienes los servidores funcionando durante mucho tiempo y los cambias en el lugar: inicias sesión, aplicas parches, editas archivos de configuración, actualizas software. Con los meses, cada servidor acumula su propio historial de cambios, y dos servidores que empezaron idénticos divergen poco a poco. A veces se les llama snowflake servers (servidores copo de nieve) porque no hay dos iguales, y reconstruir uno exactamente se vuelve difícil.

La infraestructura inmutable invierte esto. Una vez que un componente está desplegado, no lo modificas. Cuando algo necesita cambiar, construyes una versión nueva, la despliegas junto a la anterior o en su lugar, y destruyes la anterior. Cada instancia en ejecución se construye a partir de una definición conocida y versionada, así que lo que corre en producción es exactamente lo que se probó.

Terraform admite este patrón de forma natural. Muchos argumentos de recursos no se pueden cambiar en un objeto en vivo; cambiarlos fuerza el reemplazo, que el plan marca con -/+ y la nota de que el cambio fuerza el reemplazo. Para una máquina virtual, cambiar el ID de la imagen es un ejemplo típico. El flujo de trabajo habitual es construir (bake) una imagen de máquina nueva con Packer o una herramienta similar, actualizar la variable del ID de imagen en Terraform y aplicar. Terraform destruye la instancia anterior y crea una nueva.

El orden del reemplazo importa para la disponibilidad. De forma predeterminada, Terraform destruye el objeto anterior antes de crear el nuevo. Agregar lifecycle { create_before_destroy = true } invierte eso: el objeto nuevo se crea primero, y el anterior se destruye solo después de que el nuevo se haya creado con éxito. Combinado con un balanceador de carga, un grupo de auto scaling o un despliegue gradual (rolling deployment), esto da actualizaciones sin tiempo de inactividad o casi sin él.

resource "aws_instance" "web" {
  ami           = var.image_id
  instance_type = "t3.small"

  lifecycle {
    create_before_destroy = true
  }
}

Los beneficios incluyen consistencia, un rollback más fácil (volver a desplegar la imagen anterior), menos deriva de configuración y una superficie de ataque más pequeña, porque nadie necesita iniciar sesión en los servidores de producción para cambiarlos. Los parches de seguridad se aplican reconstruyendo las imágenes y reemplazando las instancias. Los costos son que los datos deben vivir fuera de las partes reemplazables, en bases de datos, almacenamiento de objetos o volúmenes conectados, y que tu pipeline debe poder construir y desplegar imágenes nuevas rápidamente. Terraform no obliga a la inmutabilidad; las actualizaciones en el lugar siguen disponibles para los argumentos que las admiten.

Términos clave

Immutable infrastructure (infraestructura inmutable)
Una práctica en la que los componentes desplegados nunca se modifican; los cambios se hacen reemplazándolos por versiones nuevas.
Mutable infrastructure (infraestructura mutable)
Servidores que se actualizan y parchean en el lugar durante su vida útil.
Snowflake server (servidor copo de nieve)
Un servidor cuya configuración ha derivado hasta volverse única y difícil de reproducir.
Golden image (imagen dorada)
Una imagen de máquina preconstruida y versionada que contiene el sistema operativo y el software, usada para lanzar instancias idénticas.
create_before_destroy
Un ajuste de lifecycle que hace que Terraform cree el reemplazo antes de destruir el original.
Ejemplo real

Se publica un parche crítico de OpenSSL. En lugar de iniciar sesión en 50 servidores, el equipo reconstruye su golden image con Packer, actualiza el ID de imagen en Terraform y aplica. Las instancias se reemplazan detrás del balanceador de carga con create_before_destroy, y ahora todos los servidores ejecutan la misma imagen parcheada.

Consejo para el examen: Debes saber que el orden de reemplazo predeterminado de Terraform es destruir y luego crear, y que create_before_destroy lo invierte. En la salida del plan, -/+ significa reemplazar (destruir y luego crear), mientras que +/- significa crear y luego destruir.

Comprueba lo que sabes

¿Cómo se aplica un parche en un modelo de infraestructura inmutable?

Construyendo una imagen o artefacto nuevo con el parche y reemplazando los componentes en ejecución, no modificándolos en el lugar.

¿Cuál es el orden predeterminado de Terraform cuando un recurso debe reemplazarse, y cómo lo cambias?

Destruir el objeto anterior y luego crear el nuevo; configura lifecycle { create_before_destroy = true } para crear primero el nuevo.
