El modelo de plugins de Terraform: un solo flujo de trabajo y un solo lenguaje (HCL) para muchos providers

Terraform por sí mismo no sabe nada de AWS, Azure, GitHub ni de ninguna plataforma en particular. El binario principal entiende el lenguaje, construye grafos de dependencias, gestiona el estado y ejecuta el flujo de trabajo de plan y apply. Todo lo específico de cada plataforma vive en los providers, que son programas plugin separados que Terraform descarga y ejecuta.

Terraform core y un provider se comunican mediante un protocolo de llamada a procedimiento remoto (RPC). Cuando escribes resource "azurerm_resource_group" "main", core mira el prefijo del tipo de recurso, azurerm, encuentra el provider correspondiente y le pide que valide los argumentos, planifique el cambio y luego lo realice. El provider traduce esas solicitudes en llamadas a la API de la plataforma. Esta separación es la razón por la que HashiCorp puede publicar Terraform core con un calendario y los autores de providers pueden publicar con el suyo propio.

El resultado es un solo flujo de trabajo y un solo lenguaje para muchas plataformas. Ya sea que gestiones un namespace de Kubernetes, un registro DNS de Cloudflare o una máquina virtual, escribes bloques HCL, ejecutas terraform init, terraform plan y terraform apply, y lees el mismo tipo de salida del plan. Las habilidades se transfieren: una vez que entiendes variables, outputs, módulos, estado y reglas de lifecycle, solo necesitas aprender los tipos de recursos y argumentos de cada provider, que se enumeran en la documentación del provider.

terraform {
  required_providers {
    aws    = { source = "hashicorp/aws" }
    github = { source = "integrations/github" }
  }
}

Los providers exponen tres cosas principales a tu configuración. Los resources (recursos) son objetos que Terraform crea y gestiona. Los data sources (fuentes de datos) son consultas de solo lectura de información que ya existe. Algunos providers también ofrecen funciones, que se llaman con la sintaxis provider::NAME::FUNCTION, aunque la mayor parte del trabajo diario usa las funciones integradas de Terraform. El provider también define su propio bloque de configuración, para ajustes como la región, el endpoint o el origen de las credenciales.

terraform init es el paso que lee required_providers, descarga las versiones correctas de los providers, normalmente desde el Terraform Registry público, y las instala en el directorio oculto .terraform de tu directorio de trabajo. Hasta que ejecutes init, plan y apply no pueden funcionar, porque core no tiene ningún plugin con el cual comunicarse. Cuando agregas un provider nuevo a una configuración, debes ejecutar init de nuevo.

Términos clave

Terraform core
El binario principal de Terraform que analiza la configuración, construye el grafo de dependencias, gestiona el estado y conduce el flujo de trabajo.
Provider (proveedor)
Un plugin que permite a Terraform gestionar una plataforma o servicio específico traduciendo las solicitudes en llamadas a su API.
Plugin
Un ejecutable separado que core lanza y con el que se comunica mediante RPC; los providers son plugins.
Data source (fuente de datos)
Una consulta de solo lectura, proporcionada por un provider, que obtiene información sobre objetos existentes.
Ejemplo real

Un equipo de plataforma gestiona la red de AWS, los monitores de Datadog y los turnos de guardia de PagerDuty. Cada uno usa un provider distinto, pero los ingenieros usan los mismos comandos init, plan y apply, los mismos patrones de variables y módulos, y el mismo proceso de revisión de pull requests para los tres.

Consejo para el examen: Si te preguntan qué componente contiene el código que habla con la API de una nube, la respuesta es el provider, no Terraform core. Core se encarga del lenguaje, el grafo, el estado y el flujo de trabajo.

Comprueba lo que sabes

¿Cómo sabe Terraform qué provider maneja un recurso de tipo google_storage_bucket?

Por el prefijo del tipo, google, que se asocia con el nombre local del provider declarado en required_providers (aquí hashicorp/google).

¿Qué debes ejecutar después de agregar un provider nuevo a una configuración, y por qué?

terraform init, porque descarga e instala el plugin del provider que core necesita antes de que plan o apply puedan funcionar.
