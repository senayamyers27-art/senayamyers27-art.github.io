Condiciones personalizadas: `validation` de variables, `precondition` y `postcondition`, y bloques `check`

Terraform te permite escribir tus propias reglas sobre qué cuenta como entrada válida e infraestructura válida. Estas condiciones personalizadas convierten suposiciones que antes vivían en la cabeza de alguien ("el tipo de instancia debe ser de tamaño t3", "la AMI debe ser para x86") en código que falla pronto con un mensaje claro. Toda condición personalizada tiene las mismas dos partes: una expresión condition que debe evaluarse como true y un error_message que explica en lenguaje sencillo qué salió mal.

El primer tipo es el bloque validation dentro de un bloque variable. Comprueba un valor en cuanto se proporciona, antes de planificar ningún recurso. Si la condición es falsa, Terraform se detiene con tu mensaje de error. Funciones como contains, can, regex y length son comunes aquí. En las versiones actuales de Terraform, una validación también puede referirse a otras variables, pero su tarea principal sigue siendo comprobar la entrada a la que pertenece.

variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "stage", "prod"], var.env)
    error_message = "env must be dev, stage or prod."
  }
}

El segundo tipo vive en el bloque lifecycle de un recurso o data source. Una precondition se comprueba antes de que Terraform cree o cambie el objeto, así que protege suposiciones sobre las entradas y otros objetos (por ejemplo, que una AMI consultada use la arquitectura correcta). Una postcondition se comprueba después de que el objeto se crea, actualiza o lee, y puede referirse al propio objeto con self (por ejemplo, que la nueva instancia realmente recibió un nombre DNS público). Los bloques output también pueden tener una precondition, que impide que un módulo exporte un valor que rompe una promesa. Una precondition o postcondition fallida es un error: bloquea la ejecución e impide que los recursos dependientes continúen.

El tercer tipo es el bloque check de nivel superior, agregado en Terraform 1.5. Un check contiene uno o más bloques assert, cada uno con una condición y un mensaje de error, y puede contener su propio bloque data con alcance limitado, como una solicitud HTTP para confirmar que un sitio web responde. La diferencia clave es la severidad: un check fallido produce una advertencia, no un error, así que el plan y el apply igual se completan. Los checks se ejecutan como último paso de cada plan y apply, lo que los hace buenos para la verificación continua del estado de salud más que como puertas estrictas.

¿Cómo eliges? Usa validation para rechazar pronto valores de entrada incorrectos. Usa precondition cuando un recurso no deba construirse a menos que algo sea cierto. Usa postcondition para confirmar que lo que se construyó o se leyó coincide con tus expectativas. Usa check cuando quieras enterarte de un problema sin detener el flujo de trabajo, por ejemplo para vigilar que un endpoint siga siendo accesible. En HCP Terraform, la validación continua (continuous validation) vuelve a ejecutar los checks y las condiciones de forma programada e informa los fallos.

Términos clave

validation block (bloque validation)
Una regla dentro de un bloque variable con condition y error_message que rechaza valores de entrada incorrectos antes de planificar.
precondition
Una condición de lifecycle (o de output) que se evalúa antes de crear o cambiar un objeto; su fallo es un error que detiene la ejecución.
postcondition
Una condición de lifecycle que se evalúa después de crear, actualizar o leer un objeto; puede usar self para inspeccionar el resultado.
check block (bloque check)
Un bloque de nivel superior con condiciones assert, opcionalmente con un data source de alcance limitado, cuyos fallos producen advertencias en lugar de errores.
Ejemplo real

Un equipo de plataforma expone un módulo con una variable instance_type. Un bloque validation la restringe a tamaños aprobados, una precondition confirma que la AMI elegida es x86_64, y un bloque check hace ping a la URL de salud del balanceador de carga después de cada apply, avisando al equipo si deja de responder sin bloquear cambios no relacionados.

Consejo para el examen: Recuerda la severidad: los fallos de validation, precondition y postcondition son errores que detienen la ejecución, mientras que una aserción fallida de un bloque check es solo una advertencia.

Comprueba lo que sabes

Quieres que te avisen cuando un sitio web deje de devolver HTTP 200, pero no quieres que los applies fallen. ¿Qué construcción encaja?

Un bloque check con un assert (y opcionalmente un data source de alcance limitado), porque los fallos de check se informan como advertencias y no bloquean plan ni apply.

¿Qué condición personalizada puede referirse a los atributos del propio recurso usando self?

Una postcondition, porque se ejecuta después de que el objeto se ha creado, actualizado o leído.

¿Dónde colocas una precondition para un recurso?

Dentro del bloque lifecycle del recurso; los bloques output también pueden contener una precondition.
