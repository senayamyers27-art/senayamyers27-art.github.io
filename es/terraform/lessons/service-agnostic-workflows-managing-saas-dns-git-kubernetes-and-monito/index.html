Flujos de trabajo independientes del servicio: gestionar SaaS, DNS, Git, Kubernetes y herramientas de monitoreo con providers

Terraform suele presentarse como una herramienta para la nube, pero un provider puede envolver cualquier servicio que tenga una API. Por eso se describe a Terraform como independiente del servicio (service-agnostic): el mismo flujo de trabajo gestiona cosas que no son máquinas virtuales en absoluto. El Terraform Registry lista miles de providers, que cubren servicios DNS, plataformas de control de código fuente, proveedores de identidad, herramientas de monitoreo y alertas, bases de datos, redes de distribución de contenido y más.

Piensa en lo que esto te permite codificar. Los registros DNS pueden gestionarse con providers para servicios como Cloudflare o las ofertas de DNS de las nubes, de modo que un nuevo nombre de host es un cambio revisado. Las plataformas Git pueden gestionarse con providers como integrations/github, lo que te permite definir repositorios, reglas de protección de ramas y acceso de equipos como código. Los objetos de Kubernetes, como namespaces y config maps, pueden gestionarse con el provider hashicorp/kubernetes, y los releases de Helm con hashicorp/helm. Las herramientas de monitoreo pueden tener dashboards, alertas y turnos de guardia definidos en código.

resource "github_repository" "service" {
  name       = "payments-api"
  visibility = "private"
}

resource "github_branch_protection" "main" {
  repository_id = github_repository.service.node_id
  pattern       = "main"
}

El beneficio es el mismo que para los recursos en la nube: repetibilidad, revisión e historial de auditoría. También es donde la recompensa en seguridad puede ser grande. La protección de ramas definida en código no puede desactivarse en silencio sin un cambio visible. Las alertas de monitoreo que forman parte de la misma configuración que el servicio que vigilan se crean al mismo tiempo, así que un servicio nuevo nunca se despliega sin ellas.

También hay algunos providers de utilidad pequeños que verás en los laboratorios. El provider hashicorp/random genera nombres, contraseñas e IDs aleatorios. El provider hashicorp/local gestiona archivos en la máquina que ejecuta Terraform. El provider hashicorp/tls puede crear claves y certificados, y hashicorp/http puede obtener datos de una URL como data source. Estos no llaman a ninguna nube, lo que los hace útiles para aprender y para unir configuraciones.

Un punto que debes tener en cuenta: algunas cosas que puedes gestionar con Terraform, como el contenido de un clúster de Kubernetes, también pueden gestionarse con otras herramientas, como un controlador GitOps. Decide qué herramienta es dueña de qué objetos, porque dos herramientas que gestionan el mismo objeto pelearán entre sí y producirán drift.

Términos clave

Service-agnostic (independiente del servicio)
Capaz de gestionar cualquier servicio que exponga una API, siempre que exista un provider para él.
Terraform Registry
El catálogo público donde se publican providers y módulos, y desde el cual terraform init los descarga de forma predeterminada.
Utility provider (provider de utilidad)
Un provider como random, local, tls o http que da soporte a las configuraciones sin gestionar una plataforma en la nube.
Branch protection (protección de ramas)
Reglas de una plataforma Git, como las revisiones obligatorias, que pueden codificarse con un provider de Git.
Ejemplo real

Cuando un equipo lanza un microservicio nuevo, un solo pull request agrega un repositorio Git con protección de ramas, un namespace de Kubernetes, un registro DNS y una política de alertas. Los cuatro se crean en un solo apply, y eliminar el servicio más adelante elimina los cuatro de forma limpia.

Consejo para el examen: Si una pregunta te pide si Terraform puede gestionar cosas como equipos de GitHub, registros DNS o dashboards de monitoreo, la respuesta es sí, siempre que exista un provider para la API del servicio.
