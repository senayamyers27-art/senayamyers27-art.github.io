Refactorización: bloques `moved` y `terraform state mv`

A medida que las configuraciones crecen, renombras recursos, los mueves a módulos y cambias de count a for_each. Cada uno de estos cambios modifica la dirección del recurso. Terraform rastrea los objetos por dirección, así que si simplemente renombras aws_instance.web a aws_instance.frontend, el plan muestra que la dirección anterior se destruye y se crea una nueva. Para una base de datos o un servidor de producción, eso es exactamente lo que no quieres. Las herramientas de refactorización le dicen a Terraform que el objeto solo se movió.

El enfoque moderno, agregado en Terraform 1.1, es el bloque moved. Lo escribes en la configuración con from (la dirección anterior) y to (la dirección nueva). Durante el siguiente plan, Terraform ve que el estado tiene un objeto en la dirección anterior, lo actualiza a la dirección nueva e informa el movimiento en lugar de una destrucción y una creación.

moved {
  from = aws_instance.web
  to   = aws_instance.frontend
}

moved {
  from = aws_s3_bucket.logs
  to   = module.logging.aws_s3_bucket.this
}

Los bloques moved funcionan para renombrar, para mover recursos hacia dentro o fuera de módulos, para renombrar llamadas a módulos (from = module.a, to = module.b) y para agregar count o for_each a un recurso existente (from = aws_instance.web, to = aws_instance.web[0]). Como el movimiento está en el código, se revisa en un pull request, se muestra en el plan y se aplica automáticamente en cada entorno y workspace que usa la configuración. Los autores de módulos pueden incluir bloques moved en una nueva versión del módulo para que quienes lo llaman actualicen sin perder recursos. Puedes conservar los bloques moved antiguos como historial de cambios; eliminarlos pronto puede romper a los usuarios que todavía tienen un estado antiguo.

El enfoque más antiguo es terraform state mv SOURCE DESTINATION. Edita el estado de inmediato: terraform state mv aws_instance.web aws_instance.frontend. También funciona para módulos (terraform state mv module.a module.b) y puede mover elementos entre archivos de estado separados. El comando cambia el estado directamente sin un plan, así que debe ejecutarse por separado en cada entorno, y no queda registro en el control de versiones. Actualiza siempre la configuración para que coincida, y considera usar -dry-run primero para ver qué se movería.

El examen espera que prefieras los bloques moved para refactorizar en entornos compartidos o con varios entornos, y que reconozcas terraform state mv como la alternativa imperativa. Ninguno cambia la infraestructura real; solo cambian qué dirección asocia Terraform con un objeto existente. Si un movimiento requiriera un cambio real en el objeto, como un tipo de recurso distinto, state mv no puede ayudar, y un bloque moved solo puede hacerlo cuando el provider admite explícitamente ese movimiento entre tipos (como de null_resource a terraform_data); de lo contrario, importas en el nuevo tipo de recurso y eliminas el anterior del estado.

Términos clave

moved block (bloque moved)
Un bloque de configuración con from y to que registra un cambio de dirección para que Terraform actualice el estado en lugar de reemplazar el objeto.
terraform state mv
Un comando de la CLI que cambia de inmediato la dirección de un objeto en el estado.
Refactoring (refactorización)
Reestructurar la configuración (renombrar, mover a módulos) sin cambiar la infraestructura real.
Resource address (dirección de recurso)
El identificador que usa Terraform para rastrear un objeto, como module.app.aws_instance.web[0].
Ejemplo real

Un equipo mueve diez recursos del módulo raíz a un nuevo módulo llamado network. Agrega diez bloques moved que asocian cada dirección anterior con module.network.<address>. El plan muestra diez movimientos y cero destrucciones, y el mismo pull request actualiza de forma segura dev, staging y prod.

Consejo para el examen: Renombrar un recurso sin moved ni state mv hace que Terraform planee una destrucción y una creación; moved es la opción declarativa y revisable.

Comprueba lo que sabes

Renombras el recurso aws_db_instance.main a aws_db_instance.primary. ¿Cómo evitas reemplazar la base de datos?

Agrega un bloque moved con from = aws_db_instance.main y to = aws_db_instance.primary (o ejecuta terraform state mv).

Nombra una ventaja de los bloques moved frente a terraform state mv.
