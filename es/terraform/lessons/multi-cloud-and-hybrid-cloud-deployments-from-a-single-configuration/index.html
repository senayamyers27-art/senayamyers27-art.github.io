Despliegues multicloud y de nube híbrida desde una sola configuración

Multicloud significa usar más de un proveedor de nube pública, por ejemplo AWS para cómputo y Google Cloud para analítica. Nube híbrida significa combinar la nube pública con infraestructura privada o local (on-premises), como un clúster de VMware vSphere en tu propio centro de datos. Ambos son comunes en organizaciones grandes, a menudo por resiliencia, razones regulatorias, costos o porque distintos equipos eligieron distintas plataformas.

Cada nube tiene su propia herramienta de IaC nativa, como AWS CloudFormation, las plantillas de Azure Resource Manager y Bicep, o Google Cloud Deployment Manager y sus sucesores. Esas herramientas funcionan bien dentro de una plataforma, pero no pueden gestionar recursos en otra. El modelo de providers de Terraform permite que una sola configuración, un solo lenguaje y un solo flujo de trabajo las cubran a todas. Un único terraform apply puede crear recursos en varias nubes y sistemas locales, respetando las dependencias entre ellos.

Las dependencias entre plataformas son donde esto brilla. Imagina que creas un balanceador de carga en una nube y un registro DNS en otro proveedor de DNS que apunta a él. Como el argumento del registro DNS hace referencia al atributo de dirección del balanceador de carga, Terraform sabe que debe crear primero el balanceador y pasar la dirección. Con herramientas nativas separadas tendrías que ejecutar una, copiar un output a mano o con scripts de unión, y luego ejecutar la otra.

resource "aws_lb" "app" { ... }

resource "cloudflare_record" "app" {
  zone_id = var.zone_id
  name    = "app"
  type    = "CNAME"
  content = aws_lb.app.dns_name
}

Ten cuidado de no exagerar lo que hace Terraform. No hace que las nubes sean intercambiables. Un aws_instance y un azurerm_linux_virtual_machine son tipos de recursos distintos con argumentos distintos, y no puedes cambiar de nube cambiando una palabra. Lo que ganas es un flujo de trabajo común, herramientas compartidas para revisión, políticas y estado, y la capacidad de conectar plataformas entre sí. Los equipos suelen envolver los detalles de cada plataforma en módulos con entradas similares para que el código que los llama se vea parecido.

Los entornos multicloud también plantean preocupaciones prácticas que debes reconocer: cada provider necesita sus propias credenciales, el estado de muchas plataformas debe guardarse en un backend compartido y protegido, y las configuraciones muy grandes a menudo se dividen en otras más pequeñas, cada una con su propio estado, para limitar el impacto de un error. Los bloques de código de esta lección están abreviados con ... para facilitar la lectura.

Términos clave

Multi-cloud (multicloud)
Usar dos o más proveedores de nube pública juntos.
Hybrid cloud (nube híbrida)
Combinar servicios de nube pública con infraestructura privada o local (on-premises).
Native IaC tool (herramienta de IaC nativa)
La herramienta de aprovisionamiento propia de un proveedor de nube, como CloudFormation o las plantillas ARM, que solo gestiona los recursos de ese proveedor.
Cross-provider reference (referencia entre providers)
Una expresión en el recurso de un provider que usa un atributo del recurso de otro provider, lo que crea una dependencia implícita.
Ejemplo real

Un minorista ejecuta su capa web en Azure, mantiene una copia de recuperación ante desastres en AWS y gestiona ambas, además de su clúster local de vSphere, desde un solo repositorio. Los ingenieros aprenden un solo flujo de trabajo, y un cambio de DNS para conmutar por error (failover) es un pull request revisado en lugar de una carrera manual.

Consejo para el examen: Las preguntas del examen contrastan Terraform con CloudFormation o las plantillas ARM: la ventaja de Terraform es gestionar muchos providers, incluidas varias nubes, con un solo flujo de trabajo. No es que el mismo bloque resource funcione en todas las nubes.

Comprueba lo que sabes

¿Qué característica de Terraform hace posible el despliegue multicloud desde una sola configuración?

Su modelo de plugins de providers: cada plataforma tiene un provider, y core los conduce a todos con el mismo lenguaje y flujo de trabajo.

¿Puedes mover una carga de trabajo de AWS a Azure cambiando solo el nombre del provider en tu configuración?

No. Los tipos de recursos y los argumentos son específicos de cada provider, así que debes reescribir esos recursos, aunque el flujo de trabajo y las herramientas siguen siendo los mismos.
