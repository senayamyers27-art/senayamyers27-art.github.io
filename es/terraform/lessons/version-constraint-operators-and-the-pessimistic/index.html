Operadores de restricción de versión: `=`, `!=`, `>=`, `<=` y el pesimista `~>`

Terraform usa la misma sintaxis de restricción de versión para required_version, los argumentos version de los providers y los argumentos version de los módulos. Una restricción es una cadena que contiene una o más condiciones separadas por comas, y una versión es aceptable solo si las cumple todas. Las versiones siguen el versionado semántico: MAJOR.MINOR.PATCH, donde un aumento de major puede romper la compatibilidad, uno de minor agrega funciones y uno de patch corrige bugs.

Los operadores son: = o ningún operador, que significa exactamente esta versión; !=, que excluye una versión; >, >=, < y <=, las comparaciones habituales; y ~>, el operador de restricción pesimista. Por ejemplo, ">= 1.2.0, < 2.0.0" permite cualquier versión desde 1.2.0 hasta 2.0.0 sin incluirla, y ">= 3.5, != 3.7.1" permite 3.5 y posteriores, omitiendo una versión que se sabe que tiene un bug.

El operador pesimista ~> solo permite que aumente el componente de versión más a la derecha que escribiste. Lee ~> 1.2.0 como al menos 1.2.0 pero menor que 1.3.0, así que acepta 1.2.0, 1.2.9 y así sucesivamente: solo parches nuevos. Lee ~> 1.2 como al menos 1.2 pero menor que 2.0, así que acepta 1.3, 1.10 y cualquier 1.x desde 1.2 en adelante: nuevas versiones minor y patch, pero ninguna versión major nueva. Por lo tanto, el número de componentes que escribes decide cuánta libertad permites.

version = "~> 5.0"      # >= 5.0.0, < 6.0.0
version = "~> 5.31.0"   # >= 5.31.0, < 5.32.0
version = "= 3.6.2"     # exactamente 3.6.2
version = ">= 2.0, < 3.0"

Las versiones preliminares (pre-release), como 1.5.0-beta1, solo coinciden con una restricción exacta = (o sin operador); los operadores de rango las ignoran, así que no tomarás una beta por accidente.

¿Qué estilo deberías elegir? La guía de HashiCorp es que los módulos reutilizables especifiquen solo una versión mínima, por ejemplo >= 5.0, para que se combinen fácilmente con otros módulos, mientras que los módulos raíz usen ~> o un rango explícito para evitar actualizaciones major inesperadas. Las fijaciones exactas rara vez son necesarias para los providers, porque el archivo de bloqueo ya registra la versión exacta seleccionada; la restricción describe lo que se permite cuando alguien actualiza deliberadamente con terraform init -upgrade.

Una trampa común del examen es leer ~> 1.2 como si fuera lo mismo que ~> 1.2.0. El primero permite 1.9; el segundo no. Resuélvelo eliminando el último componente que escribiste e incrementando el anterior para encontrar el límite superior exclusivo.

Términos clave

Semantic versioning (versionado semántico)
Esquema de versiones MAJOR.MINOR.PATCH en el que los cambios major pueden romper la compatibilidad, minor agrega funciones y patch corrige bugs.
Pessimistic constraint (~>) (restricción pesimista)
Permite que solo aumente el componente de versión especificado más a la derecha.
Exact constraint (=) (restricción exacta)
Permite solo una versión específica; también es la única forma de seleccionar una versión preliminar.
Exclusion (!=) (exclusión)
Rechaza una versión específica y permite otras que admitan las condiciones restantes.
Ejemplo real

La versión 4.12.0 de un provider tiene un bug que rompe la configuración de tu balanceador de carga. Configuras version = "~> 4.11, != 4.12.0" para que el equipo se mantenga en 4.x, omita la versión defectuosa y aun así tome la 4.12.1 cuando salga la corrección.

Consejo para el examen: Regla del límite superior para ~>: quita el último componente escrito y suma uno al nuevo último componente. ~> 2.1.3 significa < 2.2.0; ~> 2.1 significa < 3.0.

Comprueba lo que sabes

¿~> 1.4.0 permite la versión 1.5.0?

No. Permite >= 1.4.0 y < 1.5.0, así que solo versiones patch de 1.4.

¿Qué permite "~> 3.0"?

Cualquier versión desde 3.0.0 hasta 4.0.0, sin incluirla.

¿Qué estilo de restricción recomienda HashiCorp para los módulos reutilizables?

Una versión mínima como >= 5.0, dejando los límites superiores más estrictos al módulo raíz.
