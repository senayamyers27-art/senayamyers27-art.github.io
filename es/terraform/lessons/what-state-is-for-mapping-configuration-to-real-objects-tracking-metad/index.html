Para qué sirve el estado: asociar la configuración con objetos reales, rastrear metadatos y dependencias, y acelerar los planes

Terraform mantiene un archivo de estado, de forma predeterminada terraform.tfstate en el directorio de trabajo, que registra lo que gestiona. Quienes empiezan a veces preguntan por qué Terraform no puede simplemente mirar la nube. La respuesta es que el estado cumple varios propósitos que la API de la nube por sí sola no puede cumplir.

El primero y más importante es asociar la configuración con objetos reales. Tu configuración dice aws_instance.web; la nube conoce una instancia con el ID i-0abc.... El estado registra que esta dirección en particular corresponde a ese ID en particular. Sin él, Terraform no podría saber cuáles de los cientos de instancias de una cuenta creó, cuáles creó otra persona, ni si aws_instance.web ya existe. Cada dirección de recurso en el estado está vinculada a exactamente un objeto remoto.

El segundo es rastrear metadatos, especialmente las dependencias. Cuando eliminas un bloque resource de la configuración, la configuración ya no le dice a Terraform de qué dependía ese recurso. El estado recuerda las dependencias, así que Terraform puede destruir los objetos en el orden correcto aunque el código que los describía ya no exista. El estado también registra qué configuración de provider gestiona cada recurso, y otros datos de control.

El tercero es el rendimiento. Para cada objeto gestionado, el estado guarda los últimos atributos vistos. De forma predeterminada, Terraform los actualiza durante el plan consultando al provider, pero en infraestructuras grandes eso puede significar muchas llamadas a la API. El estado permite que Terraform trabaje con valores en caché cuando corresponde, y opciones como -refresh=false te permiten planificar rápidamente solo a partir del estado, a costa de no detectar drift.

El estado también permite la sincronización en equipos. Cuando el estado se guarda en un backend remoto compartido, como HCP Terraform o un bucket de almacenamiento de objetos, todos trabajan contra el mismo registro de la realidad, y el bloqueo del estado (state locking) impide que dos personas apliquen al mismo tiempo. El estado local en una laptop no se puede compartir de forma segura, por eso los equipos pasan pronto a backends remotos.

Trata el estado como datos privados de Terraform. No edites el JSON a mano. Cuando necesites cambiarlo, usa los comandos diseñados para ello, como terraform state list y terraform state show para leer, terraform state mv o un bloque moved para renombrar direcciones, terraform state rm o un bloque removed para dejar de gestionar un objeto, y bloques import o terraform import para adoptar objetos existentes. Terraform guarda un terraform.tfstate.backup del estado local anterior cuando escribe uno nuevo.

Términos clave

State (estado)
El registro de Terraform de los objetos reales que gestiona, sus atributos y metadatos, guardado en terraform.tfstate o en un backend remoto.
Resource address (dirección de recurso)
El identificador de un recurso en la configuración y el estado, como aws_instance.web o module.net.aws_vpc.main.
Backend
Dónde guarda Terraform el estado, como el disco local, HCP Terraform o un servicio de almacenamiento en la nube.
State locking (bloqueo del estado)
Un mecanismo que impide que operaciones concurrentes escriban el mismo estado al mismo tiempo.
Ejemplo real

Un ingeniero elimina el archivo terraform.tfstate pensando que es una caché. El siguiente plan propone crear de nuevo todos los recursos porque Terraform ya no sabe que existen, y apply fallaría por conflictos de nombres o crearía duplicados. Restaurar el backup o la copia remota corrige la asociación.

Consejo para el examen: Si te preguntan por el propósito principal del estado, elige asociar los recursos de la configuración con objetos del mundo real. Los metadatos como las dependencias y la caché para el rendimiento son los otros propósitos listados.

Comprueba lo que sabes

¿Por qué Terraform necesita el estado para destruir un recurso cuyo bloque eliminaste de la configuración?

El estado aún registra el ID, el provider y las dependencias del recurso, así que Terraform sabe qué eliminar y en qué orden.

¿Qué compromiso implica terraform plan -refresh=false?

Es más rápido porque omite consultar a los providers, pero no puede detectar el drift hecho fuera de Terraform.
