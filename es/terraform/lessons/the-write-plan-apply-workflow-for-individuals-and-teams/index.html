El flujo de trabajo Write → Plan → Apply para personas y equipos

El flujo de trabajo central de Terraform tiene tres pasos. Write (escribir): crear o cambiar la configuración como código. Plan (planificar): previsualizar los cambios que haría Terraform. Apply (aplicar): llevar a cabo esos cambios, después de que alguien los haya aprobado. Los pasos son los mismos tanto si trabajas solo como en una organización grande; lo que cambia es quién hace cada paso y dónde.

Para una persona que trabaja sola, el ciclo es corto y local. Editas archivos .tf en tu editor, normalmente en un repositorio Git. Ejecutas terraform init una vez (y de nuevo cuando cambian los providers, los módulos o el backend), y luego ejecutas terraform plan a menudo, como un programador ejecuta pruebas, para ver si tu edición produce los cambios que esperas y para detectar errores pronto. Cuando el plan se ve bien, ejecutas terraform apply, lees una vez más el plan que muestra y escribes yes. Después haces commit del código y lo subes con push.

Para un equipo, los mismos pasos se reparten entre personas y herramientas para que nadie cambie infraestructura compartida desde una laptop sin revisión. Un flujo típico de equipo se ve así:

1. Write:  crea una rama, cambia el código, haz push, abre un pull request
2. Plan:   CI o HCP Terraform ejecuta un plan especulativo y lo publica en el PR
3. Review: los compañeros revisan juntos el diff del código y la salida del plan
4. Apply:  tras la aprobación y el merge, el pipeline o HCP Terraform aplica

Varias prácticas hacen seguro el flujo de trabajo en equipo. El estado vive en un backend remoto compartido con bloqueo, así que dos applies no pueden chocar. Las credenciales para aplicar en producción viven en el pipeline o en HCP Terraform, no en máquinas individuales. El formato y la validación (terraform fmt -check, terraform validate) se ejecutan automáticamente, y las verificaciones de políticas pueden bloquear planes que rompen reglas, como un almacenamiento sin cifrar. El plan que aprobaron los revisores debe ser el plan que se aplica, por eso los pipelines a menudo lo guardan con plan -out y aplican ese archivo.

HCP Terraform integra este flujo de trabajo en equipo. Un workspace puede vincularse a un repositorio de control de versiones para que abrir un pull request dispare un plan especulativo, que muestra los cambios pero nunca puede aplicarse, y que hacer merge a la rama principal dispare una ejecución real que espera confirmación a menos que auto-apply esté habilitado. Las ejecuciones se hacen de forma remota con estado, variables y controles de acceso compartidos.

Sea cual sea tu forma de trabajar, mantén la disciplina de leer el plan antes de aprobar. El plan es el momento de notar una destrucción inesperada, el reemplazo de una base de datos o un cambio causado por un drift que nadie esperaba. Omitirlo con -auto-approve es apropiado en automatización solo cuando ya existe una puerta de aprobación antes en el proceso.

Términos clave

Core workflow (flujo de trabajo central)
El ciclo Write, Plan y Apply de Terraform para cambiar la infraestructura.
Speculative plan (plan especulativo)
Un plan que se ejecuta solo para revisión, como en un pull request, y que no puede aplicarse.
Remote backend (backend remoto)
Almacenamiento compartido del estado, como HCP Terraform, que permite a un equipo usar un solo estado de forma segura con bloqueo.
Pull request
Una solicitud para fusionar cambios de código que permite a los compañeros revisarlos, a menudo con la salida del plan adjunta.
Ejemplo real

Un desarrollador abre un pull request que agrega un clúster de caché. HCP Terraform publica un plan especulativo que muestra un recurso por agregar. Una revisora nota que el plan también reemplaza una subred por un error de tipeo no relacionado, el autor lo corrige y, después del merge, la ejecución aplica solo el cambio previsto.

Consejo para el examen: Conoce el orden y el propósito: Write (código), Plan (previsualización y revisión), Apply (aprovisionamiento). En los equipos, el plan se revisa junto con el código antes de aplicar nada.

Comprueba lo que sabes

En un flujo de trabajo en equipo, ¿cuándo se cambia realmente la infraestructura?

Solo en el paso Apply, después de que el código y su plan se hayan revisado y aprobado, normalmente mediante un pipeline o HCP Terraform y no desde una laptop.

¿Qué es un plan especulativo?

Un plan que se ejecuta para mostrar los cambios propuestos, por ejemplo en un pull request, y que por sí mismo no puede aplicarse.
