El argumento `version` (solo orígenes de registro) y `ref` para orígenes Git

Los módulos cambian con el tiempo, y un módulo sin versión fijada puede traer en silencio una nueva versión que renombra recursos o cambia valores predeterminados. Terraform te da dos mecanismos distintos para fijar versiones según de dónde venga el módulo, y el examen evalúa cuál se aplica a qué origen.

Para los módulos de un registro, ya sea el Terraform Registry público o un registro privado como el de HCP Terraform, usas el argumento version en el bloque module. Acepta la misma sintaxis de restricciones que las versiones de providers: una versión exacta ("1.4.0" o "= 1.4.0"), comparaciones (">= 1.2.0, < 2.0.0"), exclusiones ("!= 1.3.1") y el operador pesimista ~>. ~> 1.4 permite la 1.4 y cualquier versión 1.x posterior, pero no la 2.0; ~> 1.4.0 permite solo versiones patch 1.4.x. Durante terraform init, Terraform elige la versión disponible más reciente que cumpla la restricción.

El argumento version funciona solo con orígenes de registro. Si lo pones en una ruta local o un origen Git, Terraform informa un error, porque esos orígenes no tienen una lista de versiones de registro entre las cuales elegir. Los módulos locales se versionan junto con el código que los rodea, así que no necesitan fijarse.

Para los orígenes Git, fijas la versión con el parámetro de consulta ref en la cadena source. Puede nombrar una etiqueta, una rama o un SHA de commit completo: source = "git::ssh://git@example.com/infra/modules.git//vpc?ref=v2.1.0". Las etiquetas dan versiones legibles y estables. Un SHA de commit es lo más exacto y no se puede mover, lo que resulta atractivo para un control estricto de la cadena de suministro. Un nombre de rama es la opción más débil, porque la rama se mueve a medida que la gente hace push, así que dos ejecuciones de terraform init podrían obtener código distinto. Sin ningún ref, Terraform usa la rama predeterminada del repositorio.

module "vpc" {
  source  = "app.terraform.io/example-org/vpc/aws"
  version = "~> 3.2"
}

module "dns" {
  source = "git::ssh://git@example.com/infra/dns.git?ref=v1.0.4"
}

A diferencia de los providers, las versiones de los módulos no se registran en el archivo de bloqueo de dependencias (.terraform.lock.hcl). Ese archivo rastrea solo las versiones y los checksums de los providers. Así que, para los módulos, la restricción en tu código es tu única protección, por eso se recomiendan para producción versiones exactas o con límites estrictos, o etiquetas y SHAs inmutables. Para pasar a una versión más reciente permitida de un módulo, ejecuta terraform init -upgrade (o terraform get -update).

Términos clave

version argument (argumento version)
Un argumento del bloque module que establece una restricción de versión; válido solo para orígenes de módulos de registro.
ref parameter (parámetro ref)
Un parámetro de consulta en una dirección de origen Git que selecciona la etiqueta, rama o commit que se obtendrá.
Pessimistic constraint (~>) (restricción pesimista)
Un operador de versión que permite que solo aumente el componente especificado más a la derecha, como ~> 1.4, que permite 1.x a partir de 1.4.
Dependency lock file (archivo de bloqueo de dependencias)
.terraform.lock.hcl, que registra las versiones y los hashes de los providers, pero no las versiones de los módulos.
Ejemplo real

Un equipo fijó su módulo Git a ?ref=main. Una mañana, un colega fusionó en main un cambio incompatible, y la siguiente ejecución de CI lo trajo y planeó reemplazar un balanceador de carga. Cambiaron a etiquetas ?ref=v4.2.0 para que las actualizaciones de módulos ocurran solo cuando alguien edita el ref deliberadamente.

Consejo para el examen: version es solo para módulos de registro; los módulos Git se fijan con ?ref=. Recuerda también que el archivo de bloqueo no fija las versiones de los módulos.

Comprueba lo que sabes

Agregas version = "1.0.0" a un módulo cuyo source es ./modules/app. ¿Qué pasa?

Terraform informa un error, porque el argumento version solo se admite para orígenes de registro.

¿Qué ref de Git es la opción más inmutable?

Un SHA de commit completo, ya que las etiquetas técnicamente pueden moverse y las ramas se mueven constantemente.

¿.terraform.lock.hcl registra las versiones de los módulos?

No. Registra solo las versiones y los checksums de los providers.
