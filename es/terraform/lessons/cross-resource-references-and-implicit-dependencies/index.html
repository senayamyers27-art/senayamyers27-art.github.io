Referencias entre recursos y dependencias implícitas

Los recursos rara vez están solos. Una subred pertenece a una red, una instancia está en una subred, un registro DNS apunta a un balanceador de carga. En Terraform los conectas con referencias: expresiones que usan los atributos de otro objeto como valores de argumentos.

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "app" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}

resource "aws_instance" "web" {
  subnet_id     = aws_subnet.app.id
  ami           = var.ami_id
  instance_type = "t3.micro"
}

Las formas de referencia comunes son: TYPE.NAME.ATTRIBUTE para recursos; data.TYPE.NAME.ATTRIBUTE para data sources; var.NAME para variables de entrada; local.NAME para valores locales; module.NAME.OUTPUT para los outputs de un módulo hijo; y path.module, path.root y terraform.workspace para información del sistema de archivos y del workspace. Puedes referenciar los argumentos que estableces y los atributos que calcula el provider, como id, arn o public_ip; la documentación del provider lista ambos en las referencias de argumentos y atributos.

Cada referencia a otro recurso o data source crea una dependencia implícita. En el ejemplo, Terraform ve que la subred usa aws_vpc.main.id, así que la red debe existir antes de poder crear la subred. La instancia referencia la subred, así que espera a la subred. Nunca indicas el orden; Terraform lo deduce y construye el grafo de dependencias. Los recursos sin referencias entre sí pueden crearse en paralelo.

Las dependencias implícitas también explican (known after apply) en los planes. El ID de la red no existe hasta que el provider la crea, así que durante la planificación el vpc_id de la subred es desconocido. Terraform arrastra el valor desconocido y lo completa durante el apply una vez creada la red. Para destroy, se usan las mismas aristas en sentido inverso: primero la instancia, luego la subred y después la red.

Prefiere las dependencias implícitas siempre que sea posible. Son precisas, porque Terraform sabe exactamente qué atributo se necesita, y se documentan solas en el código. El depends_on explícito solo se necesita cuando existe una dependencia que ninguna referencia a un atributo expresa, como una aplicación dentro de una máquina virtual que necesita que primero exista una política de permisos. Eso se cubre en una lección posterior.

Una referencia también es un contrato. Si renombras un recurso, todas las expresiones que se refieren a él también deben cambiar, y de lo contrario Terraform verá el cambio de nombre como una destrucción y una creación; usa un bloque moved para decirle a Terraform que el objeto es el mismo.

Términos clave

Reference (referencia)
Una expresión que usa un valor de otro objeto, como aws_vpc.main.id o var.region.
Implicit dependency (dependencia implícita)
Una relación de orden que Terraform deduce automáticamente a partir de una referencia entre objetos.
Computed attribute (atributo calculado)
Un atributo que el provider establece después de la creación, como un ID, que a menudo se muestra como known after apply.
moved block (bloque moved)
Un bloque que le dice a Terraform que la dirección de un recurso cambió, para que actualice el estado en lugar de reemplazar el objeto.
Ejemplo real

Un ingeniero agrega un security group y configura vpc_security_group_ids = [aws_security_group.web.id] en una instancia existente. El plan crea primero el security group y luego actualiza la instancia, sin ningún orden explícito, porque la referencia creó una dependencia.

Consejo para el examen: Terraform ordena las operaciones usando referencias, no el orden de los archivos. Si una pregunta pide cómo sabe Terraform que debe crear la red antes que la subred, la respuesta es la dependencia implícita de aws_vpc.main.id.

Comprueba lo que sabes

¿Qué crea una dependencia implícita entre dos recursos?

Que el argumento de un recurso referencie los atributos del otro, como vpc_id = aws_vpc.main.id.

¿Por qué el vpc_id de una subred muestra (known after apply) cuando la red es nueva?

El provider asigna el ID de la red solo cuando la crea durante el apply, así que es desconocido en el momento del plan.
