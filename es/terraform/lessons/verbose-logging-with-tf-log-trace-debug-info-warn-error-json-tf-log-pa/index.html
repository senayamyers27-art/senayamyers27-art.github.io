Registro detallado con `TF_LOG` (TRACE, DEBUG, INFO, WARN, ERROR, JSON), `TF_LOG_PATH`, `TF_LOG_CORE` y `TF_LOG_PROVIDER`

La salida normal de Terraform te dice qué planea y qué salió mal a alto nivel. Cuando necesitas ver lo que ocurre por debajo (qué llamadas a la API hace un provider, cómo recorre Terraform el grafo de dependencias, por qué falló un plugin), activas el registro (logging) detallado con variables de entorno. Ningún indicador de la línea de comandos hace esto; se controla por completo mediante el entorno.

TF_LOG habilita el registro y establece el nivel. Los niveles, del más al menos detallado, son TRACE, DEBUG, INFO, WARN y ERROR. TRACE es el más detallado y el que HashiCorp pide en los reportes de bugs. También existe JSON, que produce logs de nivel TRACE en un formato JSON legible por máquina, útil para enviarlos a herramientas de logs. Dejar TF_LOG sin definir (o configurarlo como OFF) deshabilita el registro.

$ export TF_LOG=DEBUG
$ export TF_LOG_PATH=./terraform-debug.log
$ terraform plan

# PowerShell
PS> $env:TF_LOG = "TRACE"

De forma predeterminada, los logs van a la salida de error estándar, mezclados en tu terminal. TF_LOG_PATH los envía a un archivo, lo que es mucho más fácil de buscar o de adjuntar a un issue. El archivo se amplía (append) en lugar de sobrescribirse, y TF_LOG_PATH solo tiene efecto cuando el registro está habilitado con un nivel.

Los logs de Terraform provienen de dos fuentes: Terraform core (la propia CLI: carga de la configuración, construcción del grafo, manejo del estado) y los plugins de los providers (llamadas a la API de nubes y servicios). Puedes establecer niveles para cada una por separado. TF_LOG_CORE controla el registro de core y TF_LOG_PROVIDER controla el registro de los providers, y cada uno acepta los mismos niveles. Por ejemplo, TF_LOG_PROVIDER=TRACE con TF_LOG_CORE sin definir muestra la actividad detallada de los providers sin inundarte con mensajes del grafo de core, lo que es ideal cuando sospechas un problema de la API.

Los logs de nivel DEBUG y TRACE pueden contener información sensible, como cuerpos de solicitudes, atributos de recursos y a veces credenciales o tokens. Trata los archivos de log como los archivos de estado: no hagas commit de ellos, revísalos antes de compartirlos públicamente y elimínalos cuando termines. Recuerda quitar las variables después, ya que el registro detallado hace más lento a Terraform y produce archivos muy grandes.

Términos clave

TF_LOG
Variable de entorno que habilita el registro de Terraform en el nivel TRACE, DEBUG, INFO, WARN, ERROR o JSON.
TF_LOG_PATH
Variable de entorno que escribe (agregando al final) la salida de los logs en un archivo en lugar de en la salida de error estándar.
TF_LOG_CORE
Variable de entorno que establece el nivel de log solo para Terraform core.
TF_LOG_PROVIDER
Variable de entorno que establece el nivel de log solo para los plugins de los providers.
Ejemplo real

Un plan falla con un error de permisos poco claro de un proveedor de nube. Un ingeniero establece TF_LOG_PROVIDER=DEBUG y TF_LOG_PATH=provider.log, vuelve a ejecutar el plan y encuentra la llamada exacta a la API y el rol al que se le negó el acceso; luego quita ambas variables.

Consejo para el examen: TRACE es el nivel más detallado, JSON produce logs de nivel TRACE en formato JSON, y TF_LOG_PATH no hace nada a menos que se establezca un nivel de log.

Comprueba lo que sabes

¿Qué nivel de TF_LOG es el más detallado?

TRACE.

¿Cómo obtienes logs detallados de los providers pero no de Terraform core?

Establece TF_LOG_PROVIDER en un nivel como TRACE o DEBUG y deja TF_LOG_CORE sin definir.

¿A dónde van los logs si TF_LOG está definido pero TF_LOG_PATH no?

A la salida de error estándar, que se muestra en la terminal.
