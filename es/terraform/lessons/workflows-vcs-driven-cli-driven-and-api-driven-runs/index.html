Flujos de trabajo: ejecuciones basadas en VCS, en la CLI y en la API

Cada workspace de HCP Terraform usa uno de tres flujos de trabajo, que determinan cómo llega la configuración al workspace y qué inicia una ejecución. Las ejecuciones en sí (plan, verificaciones de políticas opcionales, apply) son las mismas; lo que cambia es el disparador.

En el flujo de trabajo basado en VCS, el workspace está conectado a un repositorio y una rama de un proveedor de control de versiones como GitHub, GitLab, Bitbucket o Azure DevOps. Cuando alguien hace push de un commit a esa rama, HCP Terraform obtiene la configuración e inicia una ejecución automáticamente. Cuando alguien abre un pull request, ejecuta un plan especulativo, una ejecución solo de plan que no puede aplicarse, y publica el resultado como una verificación de estado en el pull request para que los revisores vean exactamente qué cambiaría. Hacer merge del pull request dispara la ejecución real en la rama. Este es el flujo de trabajo más al estilo GitOps y el más común en los equipos.

En el flujo de trabajo basado en la CLI, trabajas desde tu terminal como siempre, con un bloque cloud en la configuración. Cuando ejecutas terraform plan, la CLI sube tu configuración local a HCP Terraform y el plan se ejecuta de forma remota, transmitiendo la salida a tu terminal; terraform apply hace lo mismo y pide confirmación. Se siente como Terraform local, pero mantiene el estado, las variables, las credenciales y el historial de ejecuciones en el workspace. Es adecuado para equipos que quieren ejecución remota pero ya tienen su propio proceso de revisión, y para desarrolladores que quieren probar cambios antes de hacer commit.

$ terraform plan
Running plan in HCP Terraform. Output will stream here.
Pressing Ctrl-C will stop streaming the logs, but will not stop the plan running remotely.

En el flujo de trabajo basado en la API, una herramienta externa controla todo mediante la API de HCP Terraform. Un script o un sistema de CI empaqueta la configuración en un tarball, crea una versión de configuración, la sube y luego crea una ejecución. Esto da el mayor control y se usa cuando las organizaciones tienen sus propios pipelines de CI/CD o construyen automatización personalizada. Requiere más esfuerzo de ingeniería que los otros dos.

Elegir depende sobre todo de dónde viven tu fuente de verdad y tus aprobaciones. Si los pull requests de un repositorio deben impulsar los cambios, elige el basado en VCS. Si las personas ejecutan Terraform de forma interactiva y quieren los beneficios remotos, elige el basado en la CLI. Si un pipeline existente o una herramienta personalizada debe orquestar las ejecuciones, elige el basado en la API. Ten en cuenta que un workspace conectado a VCS no acepta terraform apply desde la CLI, porque el repositorio es su fuente de verdad; igual puedes ejecutar planes especulativos contra él desde la CLI.

Términos clave

VCS-driven workflow (flujo de trabajo basado en VCS)
Un workspace conectado a una rama de un repositorio, donde los commits disparan ejecuciones y los pull requests disparan planes especulativos.
CLI-driven workflow (flujo de trabajo basado en la CLI)
Ejecuciones iniciadas desde la CLI local de terraform que suben la configuración y se ejecutan de forma remota en HCP Terraform.
API-driven workflow (flujo de trabajo basado en la API)
Ejecuciones iniciadas por herramientas externas que suben versiones de configuración y crean ejecuciones mediante la API de HCP Terraform.
Speculative plan (plan especulativo)
Una ejecución solo de plan que muestra los cambios propuestos pero nunca puede aplicarse, usada para las verificaciones de pull requests.
Ejemplo real

Un equipo de plataforma conecta su workspace de redes a la rama main de un repositorio de GitHub. Cada pull request muestra un plan especulativo como verificación de estado; después de la aprobación y el merge, HCP Terraform planifica y espera a que un usuario autorizado confirme el apply.

Consejo para el examen: En el flujo de trabajo VCS, los pull requests disparan ejecuciones especulativas (solo de plan); los merges a la rama rastreada disparan ejecuciones reales. Los workspaces conectados a VCS no aceptan applies desde la CLI.
