Usar varios providers distintos en una sola configuración

Una sola configuración de Terraform puede usar tantos providers como necesite. Declaras cada uno en required_providers, configuras cada uno con su propio bloque provider si necesita ajustes, y luego escribes recursos de cualquiera de sus tipos uno al lado del otro. terraform init los instala todos, y un solo plan muestra los cambios en todas las plataformas.

terraform {
  required_providers {
    docker = { source = "kreuzwerker/docker", version = "~> 3.0" }
    local  = { source = "hashicorp/local" }
    random = { source = "hashicorp/random" }
  }
}

provider "docker" {}

resource "random_pet" "name" {}

resource "docker_container" "web" {
  name  = random_pet.name.id
  image = "nginx:latest"
}

resource "local_file" "note" {
  filename = "container.txt"
  content  = docker_container.web.name
}

Observa cómo se conectan los recursos. El nombre del contenedor viene de random_pet, y el contenido del archivo viene del contenedor. Estas referencias crean dependencias implícitas, así que Terraform crea primero el nombre aleatorio, luego el contenedor y después el archivo, aunque participen tres providers distintos. Esta es la ventaja central frente a ejecutar herramientas separadas: Terraform ve un solo grafo de dependencias que abarca varios providers.

Terraform asocia cada recurso con su provider usando el prefijo del tipo de recurso: docker_container va al provider cuyo nombre local es docker, local_file a local, y así sucesivamente. Muchos providers, como random y local, no necesitan ninguna configuración, así que puedes omitir sus bloques provider y Terraform usa una configuración predeterminada vacía.

Las configuraciones con varios providers traen algunas consideraciones prácticas. Cada provider tiene su propia autenticación, así que el entorno que ejecuta Terraform necesita credenciales para todos ellos. Los planes tardan más a medida que se actualizan más APIs. Un fallo en la API de un provider puede detener un apply a mitad de camino, dejando creados los recursos anteriores; Terraform registra en el estado lo que tuvo éxito, y el siguiente apply continúa desde ahí. Y las configuraciones muy grandes que abarcan muchos providers pueden volverse difíciles de gestionar, así que los equipos a menudo las dividen en módulos raíz separados según líneas de equipo o de ciclo de vida, y pasan valores entre ellos mediante outputs y data sources.

Este patrón es lo que el laboratorio de la semana te pide probar: agregar el provider de terceros kreuzwerker/docker junto a local muestra un solo flujo de trabajo gestionando dos plataformas no relacionadas. Ejecuta terraform providers para listar todos los providers que requiere la configuración y qué módulo requiere cada uno.

Términos clave

Resource type prefix (prefijo del tipo de recurso)
La parte de un tipo de recurso antes del primer guion bajo, como docker en docker_container, que selecciona el provider.
terraform providers
Comando que muestra los providers que requieren la configuración y sus módulos.
Dependency graph (grafo de dependencias)
El mapa interno de Terraform de qué objetos dependen de cuáles, usado para ordenar las operaciones en todos los providers.
Partial apply (apply parcial)
Un apply que se detiene después de que algunos cambios tienen éxito; el estado registra el trabajo completado para que la siguiente ejecución pueda continuar.
Ejemplo real

La configuración de una startup crea una base de datos gestionada en su proveedor de nube, guarda en un gestor de secretos la contraseña generada por el provider random y crea una verificación de disponibilidad en un SaaS de monitoreo que apunta al nuevo endpoint, todo en un solo plan.

Consejo para el examen: No necesitas una configuración ni un comando separados por cada provider. Una configuración, un init y un apply pueden gestionarlos todos, y las referencias entre ellos crean dependencias automáticamente.

Comprueba lo que sabes

¿Cómo decide Terraform el orden de creación cuando recursos de distintos providers se referencian entre sí?

Construye un solo grafo de dependencias a partir de las referencias, así que un recurso se crea después de todo lo que referencia, sin importar el provider.

¿Necesitas un bloque provider para cada provider que usas?

No. Los providers que no necesitan ajustes, como random o local, pueden usarse solo con una entrada en required_providers.
