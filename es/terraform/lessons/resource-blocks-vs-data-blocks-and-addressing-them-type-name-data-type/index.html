Bloques resource frente a bloques data, y cómo direccionarlos (`TYPE.NAME`, `data.TYPE.NAME`)

Las configuraciones de Terraform se construyen principalmente con dos tipos de bloques que provienen de los providers. Un bloque resource declara un objeto de infraestructura que Terraform gestiona: lo crea, lo actualiza cuando cambian los argumentos y lo destruye cuando se elimina el bloque. Un bloque data declara un data source: una consulta de solo lectura de información sobre algo que ya existe, que Terraform lee pero nunca crea, cambia ni destruye.

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/*-amd64-server-*"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
}

Ambos bloques tienen dos etiquetas: el tipo, que viene del provider, y un nombre local que tú eliges. La combinación debe ser única dentro de un módulo para cada modo. El tipo determina qué argumentos se permiten; el nombre solo sirve para referirse al bloque en otras partes del código y aparece en la salida del plan y en el estado.

Las direcciones son la forma de referirse a estos bloques. Un recurso gestionado se direcciona como TYPE.NAME, por ejemplo aws_instance.web, y sus atributos como aws_instance.web.id o aws_instance.web.public_ip. Un data source siempre lleva el prefijo data.: data.TYPE.NAME, por ejemplo data.aws_ami.ubuntu, con atributos como data.aws_ami.ubuntu.id. Olvidar el prefijo data. es un error común que terraform validate informa como una referencia a un recurso no declarado.

Las direcciones crecen cuando usas módulos y varias instancias. Un recurso dentro de un módulo llamado network es module.network.aws_vpc.main. Un recurso con count tiene instancias como aws_instance.web[0], y uno con for_each tiene instancias como aws_instance.web["blue"]. Usas estas direcciones completas con comandos como terraform state show, -target y -replace.

¿Cuándo se leen los data sources? Normalmente durante la planificación, para que sus resultados estén disponibles al calcular el plan. Si los argumentos de un data source dependen de valores que no se conocen hasta el apply, como el ID de un recurso que está por crearse, Terraform aplaza su lectura hasta el momento del apply y lo muestra en el plan con <= y (known after apply). Los data sources se vuelven a leer en cada plan, así que siempre reflejan la realidad actual, y sus resultados también se registran en el estado.

Elegir entre ellos suele ser sencillo. Si Terraform debe ser dueño del ciclo de vida del objeto, usa un resource. Si otra cosa es su dueña, como la red de otro equipo, una imagen de máquina publicada por un proveedor o la identidad de la cuenta actual, usa un data source para consultarlo en lugar de escribir IDs de forma fija. Esto mantiene las configuraciones portables entre cuentas y regiones.

Términos clave

Resource block (bloque resource)
Declara un objeto de infraestructura que Terraform crea, actualiza y destruye.
Data block (data source, bloque data)
Declara una consulta de solo lectura de información existente que Terraform lee pero no gestiona.
Resource address (dirección de recurso)
La forma de referencia TYPE.NAME para los recursos y data.TYPE.NAME para los data sources, ampliada con rutas de módulos y claves de instancia.
Local name (nombre local)
La segunda etiqueta de un bloque resource o data, elegida por ti y única por tipo dentro de un módulo.
Ejemplo real

En lugar de escribir de forma fija un ID de imagen de máquina que es distinto en cada región, una configuración usa data "aws_ami" "ubuntu" para consultar la imagen aprobada más reciente, y la instancia referencia data.aws_ami.ubuntu.id. Desplegar en una región nueva no requiere cambiar el código.

Consejo para el examen: Los data sources se direccionan con el prefijo data. y Terraform nunca los destruye. Si una pregunta del examen pide cómo usar un objeto existente que Terraform no debe gestionar, la respuesta es un data source.

Comprueba lo que sabes

¿Cómo referencias el atributo id de un data source aws_vpc llamado shared?

data.aws_vpc.shared.id.

¿Qué le pasa a un data source cuando ejecutas terraform destroy?

Nada en el sistema real; Terraform solo lee los data sources, así que no hay nada que destruir.
