Integraciones: proveedores de VCS, run triggers, run tasks, notificaciones y credenciales dinámicas de providers

HCP Terraform se conecta con el resto de tu cadena de herramientas de varias formas. Cada integración resuelve un problema distinto, y el examen espera que asocies la función con el escenario.

Los proveedores de VCS conectan una organización con un sistema de control de versiones como GitHub, GitLab, Bitbucket o Azure DevOps. Una vez conectados, los workspaces pueden usar el flujo de trabajo basado en VCS: los commits a una rama rastreada inician ejecuciones, los pull requests reciben planes especulativos que se muestran como verificaciones de estado, y el registro privado puede publicar módulos directamente desde repositorios etiquetados. La conexión normalmente la configura una vez un administrador usando una aplicación OAuth o una GitHub App.

Los run triggers enlazan workspaces entre sí. Configuras un workspace posterior para que observe uno o más workspaces de origen; cuando un workspace de origen completa un apply exitoso, HCP Terraform pone automáticamente en cola una ejecución en el workspace posterior. Esto es adecuado para infraestructura por capas: cuando cambia el workspace de red, el workspace de la aplicación que lee sus outputs vuelve a planificar automáticamente.

Los run tasks envían datos de la ejecución a servicios externos y esperan su veredicto. Algunos ejemplos son escáneres de seguridad, herramientas de estimación de costos y verificadores de cumplimiento. Un run task puede adjuntarse en etapas como pre-plan, post-plan, pre-apply y post-apply, y su aplicación puede ser advisory (se muestran los resultados y la ejecución continúa) o mandatory (un fallo detiene la ejecución). Los run tasks son la forma en que las verificaciones de terceros se unen a la misma puerta que las políticas de Sentinel u OPA.

Las notificaciones informan a personas y sistemas sobre los eventos de las ejecuciones. Las configuraciones de notificaciones del workspace pueden enviar mensajes a correo electrónico, Slack, Microsoft Teams o un webhook genérico cuando las ejecuciones se crean, necesitan atención (por ejemplo, esperan aprobación), se completan o fallan, y para los resultados de las evaluaciones de estado, como un drift detectado.

Las credenciales dinámicas de providers eliminan los secretos de larga duración de los workspaces. En lugar de guardar claves estáticas de la nube, HCP Terraform emite un token firmado de identidad de carga de trabajo para cada ejecución usando OpenID Connect (OIDC). Configuras una relación de confianza en la nube (por ejemplo, un rol de AWS IAM, un registro de aplicación de Azure, un grupo de identidades de carga de trabajo de GCP o un rol de Vault) que acepta tokens de tu organización, proyecto o workspace. Las variables de entorno del workspace que empiezan por TFC_ activan la función y nombran el rol que se usará. Luego el provider intercambia el token por credenciales de corta duración válidas solo para esa ejecución, así que no hay nada de larga duración que se pueda filtrar o que haya que rotar.

TFC_AWS_PROVIDER_AUTH = true
TFC_AWS_RUN_ROLE_ARN  = arn:aws:iam::111122223333:role/tfc-app-prod

Términos clave

Run trigger
Un enlace que pone automáticamente en cola una ejecución en un workspace después de que un workspace de origen aplica con éxito.
Run task
Una integración que envía datos de la ejecución a un servicio externo en una etapa determinada y puede bloquear la ejecución si falla.
Notification configuration (configuración de notificaciones)
Un ajuste del workspace que envía eventos de ejecuciones y de salud a correo electrónico, herramientas de chat o webhooks.
Dynamic provider credentials (credenciales dinámicas de providers)
Credenciales de nube de corta duración obtenidas en cada ejecución intercambiando un token de identidad de carga de trabajo OIDC de HCP Terraform.
Ejemplo real

El workspace de aplicación de una empresa lee IDs de VPC de un workspace de red. Agregan un run trigger para que el workspace de aplicación vuelva a planificar cada vez que el workspace de red aplica, adjuntan un run task mandatory post-plan que ejecuta un escáner de seguridad, envían los fallos a un canal de chat y cambian ambos workspaces a credenciales dinámicas de AWS para que no se guarde ninguna clave de acceso.

Consejo para el examen: Asocia la función: los run triggers encadenan workspaces, los run tasks llaman a verificaciones externas, las notificaciones envían alertas y las credenciales dinámicas de providers reemplazan las claves estáticas de la nube por credenciales OIDC por ejecución.

Comprueba lo que sabes

¿Qué función inicia una ejecución en el workspace B después de que el workspace A aplica?

Un run trigger configurado en el workspace B con A como origen.

¿Qué problema resuelven las credenciales dinámicas de providers?

Eliminan las credenciales estáticas de la nube de larga duración emitiendo credenciales de corta duración por ejecución mediante la identidad de carga de trabajo OIDC.

¿En qué etapas pueden adjuntarse los run tasks?

Pre-plan, post-plan, pre-apply y post-apply.
