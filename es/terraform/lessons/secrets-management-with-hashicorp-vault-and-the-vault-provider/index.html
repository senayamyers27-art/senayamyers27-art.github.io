Gestión de secretos con HashiCorp Vault y el provider de Vault

HashiCorp Vault es un sistema de gestión de secretos. Guarda los secretos de forma centralizada, controla quién puede leerlos mediante políticas, registra cada acceso en logs de auditoría y, lo más importante, puede generar secretos dinámicos: credenciales creadas bajo demanda para un solo uso o un lease (arrendamiento) corto, que se revocan automáticamente después. Combinar Terraform con Vault significa que tu configuración nunca necesita una clave de nube de larga duración ni una contraseña de base de datos escrita en un archivo.

Terraform se comunica con Vault mediante el provider de Vault, que se configura como cualquier otro provider con la dirección del servidor de Vault y una forma de autenticarse. La dirección y el token normalmente se proporcionan mediante variables de entorno como VAULT_ADDR y VAULT_TOKEN en lugar de escribirse en el código, o mediante un método de autenticación como AppRole o una identidad de la nube. El provider puede hacer dos tareas: gestionar el propio Vault (mounts, políticas, métodos de autenticación, roles) como infraestructura, y leer secretos de Vault para usarlos en otras partes de tu configuración.

La lectura de un secreto estático de un motor clave/valor se hace con un data source, por ejemplo vault_kv_secret_v2 para la versión 2 del motor KV o el data source de secreto genérico más antiguo. Luego referencias un atributo de ese data source en otro bloque resource o provider. Para los secretos dinámicos, data sources como el de credenciales de acceso de AWS le piden al motor de secretos de AWS de Vault que genere claves de AWS de corta duración, que puedes pasar al bloque provider de AWS. Cuando el lease vence, Vault revoca las claves, así que una credencial filtrada tiene una vida útil corta.

data "vault_kv_secret_v2" "db" {
  mount = "secret"
  name  = "app/db"
}

# después: data.vault_kv_secret_v2.db.data["password"]

Hay una advertencia importante que le gusta al examen: los valores leídos mediante un data source se guardan en el archivo de estado de Terraform, igual que cualquier otro atributo. Vault protege el secreto en reposo dentro de Vault, pero una vez que Terraform lo lee en un data source normal, tu estado se convierte en otro lugar donde vive el secreto. Las mitigaciones incluyen proteger el estado con un backend cifrado y con control de acceso, preferir secretos dinámicos de corta duración para que una copia en el estado se vuelva inútil rápidamente y, cuando el provider lo admita, usar recursos efímeros para que el secreto se use durante la ejecución pero nunca se persista.

En HCP Terraform puedes ir más allá con las credenciales dinámicas de providers, en las que cada ejecución se autentica en Vault usando un token firmado de identidad de carga de trabajo en lugar de un token de Vault almacenado. Sea cual sea el patrón, el principio es el mismo: Vault es la única fuente de verdad para los secretos, Terraform los obtiene justo a tiempo, y nada secreto se escribe de forma fija en tu configuración ni se incluye en commits del control de versiones.

Términos clave

HashiCorp Vault
Una herramienta de gestión de secretos que guarda, controla el acceso, audita y genera dinámicamente secretos.
Dynamic secret (secreto dinámico)
Una credencial que Vault genera bajo demanda con un lease y revoca automáticamente cuando el lease vence.
Vault provider (provider de Vault)
El provider de Terraform que se usa para configurar Vault y leer secretos de él mediante data sources o recursos efímeros.
Lease (arrendamiento)
El período durante el cual un secreto de Vault es válido antes de que deba renovarse o se revoque.
Ejemplo real

En lugar de guardar una clave de acceso de AWS en las variables de HCP Terraform, un equipo configura el motor de secretos de AWS de Vault. Su configuración lee credenciales de AWS de corta duración de Vault al inicio de cada ejecución y las pasa al bloque provider de AWS; las claves vencen poco después de la ejecución, así que incluso la copia en el estado pierde su valor rápidamente.

Consejo para el examen: Los secretos leídos de Vault mediante un data source normal terminan en el estado de Terraform. Vault no cambia eso; protege el estado y prefiere secretos de corta duración o efímeros.

Comprueba lo que sabes

¿Por qué los secretos dinámicos son más seguros que los estáticos para las ejecuciones de Terraform?

Se crean bajo demanda con un lease corto y se revocan automáticamente, así que una copia filtrada (incluida la del estado) deja de funcionar poco después de la ejecución.

¿Cómo debería proporcionarse normalmente el token de Vault para el provider de Vault?

Mediante una variable de entorno como VAULT_TOKEN o un método de autenticación, no escrito de forma fija en la configuración.
