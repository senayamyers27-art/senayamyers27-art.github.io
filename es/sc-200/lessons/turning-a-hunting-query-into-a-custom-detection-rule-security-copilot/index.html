Microsoft Certified: Security Operations Analyst Associate SC-200

Convertir una consulta de hunting en una regla de detección personalizada; ayuda de Security Copilot para escribir KQL

El hunting es exploratorio: formulas una hipótesis, consultas y aprendes. Cuando una búsqueda encuentra algo que vale la pena vigilar de forma continua, la conviertes en una detección para que la próxima vez que ocurra se genere una alerta sin que una persona tenga que acordarse de revisar. En Defender XDR eso significa una regla de detección personalizada; en Sentinel, una regla de análisis programada o NRT.

Empieza por preparar la consulta para la detección. Las consultas de hunting a menudo devuelven agregados o listas amplias, mientras que una detección debe devolver eventos específicos sobre los que un analista pueda actuar. Asegúrate de que devuelva las columnas identificadoras obligatorias, como Timestamp, DeviceId y ReportId para las tablas de dispositivos, y las columnas de la entidad afectada (dispositivo, usuario o buzón). Si resumes, conserva esas columnas con una función como arg_max(Timestamp, *) para que cada fila siga apuntando a un evento real. Quita las instrucciones take o limit, que descartarían resultados sin avisar.

Después, ajusta para reducir el ruido. Ejecuta la consulta sobre todo el período de lookback que planeas usar y cuenta los resultados. Si devuelve cientos de coincidencias al día, agrega filtros para la actividad conocida como legítima, quizá usando una watchlist en Sentinel o una lista let de herramientas aprobadas. Una detección que se dispara constantemente enseña a los analistas a ignorarla. Luego elige una frecuencia acorde al riesgo: continua o por hora para técnicas de ataque activas, diaria para señales más lentas.

Luego, en advanced hunting, selecciona Create detection rule. Dale un nombre y una descripción claros, una severidad, una categoría y técnicas de MITRE ATT&CK, y acciones recomendadas para los analistas. Elige las entidades afectadas y, solo para lógica de alta confianza, acciones automatizadas como aislar un dispositivo. Después de guardarla, supervisa las ejecuciones y las alertas de la regla en la página Detection rules, y revísala cuando produzca falsos positivos.

Security Copilot puede ayudar en varios puntos. En advanced hunting, puedes describir lo que quieres en lenguaje sencillo, como 'muestra los dispositivos donde PowerShell se ejecutó con un comando codificado en los últimos 7 días', y Copilot genera una consulta KQL usando las tablas y columnas correctas. Puedes pedirle que explique una consulta existente, que corrija un error o que ajuste una consulta, por ejemplo para excluir ciertos hosts. Esto reduce la barrera para los analistas que todavía están aprendiendo KQL y acelera a los cazadores de amenazas con experiencia.

Siempre revisa el KQL generado antes de confiar en él. Verifica que consulte la tabla correcta, que los filtros coincidan con tu intención, que los rangos de tiempo sean razonables y que devuelva las columnas que necesita una detección. Ejecútalo e inspecciona los resultados. Las consultas generadas pueden usar la columna equivocada u omitir una condición, y un error sutil en una detección significa silencio durante un ataque o una avalancha de alertas falsas.

Términos clave

Hypothesis-driven hunting (hunting basado en hipótesis)
Hunting que parte de una idea específica sobre el comportamiento del atacante y la pone a prueba con consultas.
arg_max()
Una agregación que devuelve la fila con el valor máximo de una columna, conservando las demás columnas.
Detection-ready query (consulta lista para detección)
Una consulta que devuelve eventos específicos con las columnas identificadoras y de entidad obligatorias y un nivel de ruido aceptable.
Natural-language to KQL (de lenguaje natural a KQL)
La capacidad de Security Copilot de generar una consulta KQL a partir de una solicitud en lenguaje sencillo.
Ejemplo real

Una cazadora de amenazas le pide a Copilot 'procesos que crearon tareas programadas con comandos codificados en los últimos 7 días'. Revisa la consulta generada, corrige el nombre de una columna, agrega DeviceId y ReportId a la salida y excluye un servidor de implementación conocido. La consulta devuelve tres coincidencias por semana, así que la guarda como una regla de detección personalizada que se ejecuta cada 3 horas, etiquetada con la técnica de tareas programadas.

Consejo para el examen: Si un escenario dice que la regla no se puede guardar o que las alertas no tienen entidades, a la consulta le faltan columnas obligatorias o de entidad. El KQL generado es un punto de partida que el analista debe validar.

Comprueba lo que sabes

¿Por qué quitar take de una consulta antes de convertirla en una detección?

take limita los resultados de forma arbitraria, así que la regla podría perder eventos coincidentes.

¿Cómo puede una consulta resumida seguir funcionando como detección?

Conservando los identificadores de eventos y las columnas de entidad, por ejemplo con arg_max(Timestamp, *).

¿Qué debes revisar en el KQL que genera Copilot?

Las tablas, columnas, filtros, rango de tiempo y columnas de salida; luego ejecútalo e inspecciona los resultados.
