Grupos de seguridad de red y grupos de seguridad de aplicaciones: prioridad de reglas, reglas predeterminadas, asociación a subred vs. NIC y reglas de seguridad efectivas

Un grupo de seguridad de red (NSG) filtra el tráfico hacia y desde los recursos de Azure en una red virtual con una lista de reglas de permiso y denegación. Cada regla coincide según el origen, el puerto de origen, el destino, el puerto de destino y el protocolo (TCP, UDP, ICMP o cualquiera), y tiene una dirección (entrante o saliente), una acción y una prioridad. Los NSG tienen estado (stateful): si se permite una conexión entrante, el tráfico de retorno se permite automáticamente sin necesidad de una regla saliente. Los NSG son el firewall básico de capa 3 y capa 4 de toda red de Azure y aparecen en casi todas las preguntas de redes.

La prioridad es un número de 100 a 4096. Las reglas se procesan en orden, del número más bajo al más alto, y el procesamiento se detiene en la primera regla que coincide. Así, un Deny con prioridad 100 gana a un Allow con prioridad 200 para el mismo tráfico, y un Allow con 100 gana a un Deny con 200. Deja huecos entre las prioridades, como 100, 200, 300, para poder insertar reglas más adelante. Una regla se crea así: az network nsg rule create --resource-group rg-web --nsg-name nsg-web --name allow-https --priority 100 --direction Inbound --access Allow --protocol Tcp --source-address-prefixes Internet --destination-port-ranges 443.

Todo NSG incluye reglas predeterminadas con prioridades de 65000 en adelante, que no puedes eliminar pero sí invalidar con reglas de número más bajo. Entrantes: AllowVnetInBound (65000) permite el tráfico desde la VNet y las redes conectadas, AllowAzureLoadBalancerInBound (65001) permite los sondeos de estado del equilibrador de carga de Azure y DenyAllInBound (65500) bloquea todo lo demás, incluido internet. Salientes: AllowVnetOutBound (65000), AllowInternetOutBound (65001) y DenyAllOutBound (65500). El origen y el destino pueden usar etiquetas de servicio (service tags) como VirtualNetwork, Internet, AzureLoadBalancer o Storage en lugar de rangos IP, y Azure mantiene actualizadas sus listas de direcciones.

Puedes asociar un NSG con una subred, con una interfaz de red (NIC) o con ambas, y un mismo NSG puede reutilizarse en muchas. Cuando existen ambos, el tráfico debe estar permitido por los dos. Para el tráfico entrante se evalúa primero el NSG de la subred y luego el de la NIC. Para el tráfico saliente se evalúa primero el NSG de la NIC y luego el de la subred. Si cualquiera de los dos deniega, el tráfico se descarta. Muchos equipos aplican NSG solo a las subredes, por simplicidad, y usan NSG a nivel de NIC solo para excepciones. Cuando el tráfico se bloquea inesperadamente, revisa las reglas de seguridad efectivas (effective security rules): en la NIC de la VM, abre Effective security rules (o usa Network Watcher) para ver las reglas combinadas de los NSG de la subred y de la NIC, incluidas las reglas predeterminadas y las etiquetas de servicio expandidas. IP flow verify de Network Watcher te dice exactamente qué regla permite o deniega un paquete específico.

Los grupos de seguridad de aplicaciones (ASG) te permiten agrupar NIC por función y usar el nombre del grupo en las reglas en lugar de direcciones IP. Creas ASG como asg-web y asg-db, asignas la NIC de cada VM al ASG correcto y luego escribes una regla como 'permitir TCP 1433 desde asg-web hacia asg-db'. Cuando agregas un servidor web nuevo, solo agregas su NIC a asg-web; no hace falta cambiar ninguna regla. Todas las NIC de un ASG deben estar en la misma VNet, y los ASG de origen y destino de una regla también deben estar en la misma VNet.

Veamos un ejemplo práctico. Una aplicación de tres niveles tiene subredes web, de aplicación y de base de datos. El NSG de la subred web tiene una regla con prioridad 100 que permite TCP 443 desde Internet. El NSG de la subred de base de datos tiene una regla con prioridad 100 que permite TCP 1433 desde asg-app hacia asg-db, y otra con prioridad 4000 que deniega todo el tráfico desde VirtualNetwork, invalidando AllowVnetInBound para que los servidores web no puedan llegar directamente a la base de datos. Luego un desarrollador agrega un NSG a nivel de NIC en una VM de base de datos, sin reglas. Las conexiones desde el nivel de aplicación fallan, porque el tráfico entrante pasa el NSG de la subred pero choca con DenyAllInBound en el NSG de la NIC. Las reglas de seguridad efectivas muestran ambos NSG y revelan el problema.

Errores comunes: suponer que un número de prioridad más alto significa más importante; agregar un Allow con 300 debajo de un Deny con 200 y preguntarse por qué nada cambia; olvidar que DenyAllInBound bloquea el tráfico entrante desde internet; bloquear la etiqueta AzureLoadBalancer de modo que fallan los sondeos de estado; y olvidar que tanto el NSG de la subred como el de la NIC deben permitir el tráfico.

Palabras clave del examen: '¿qué regla se aplica?' significa encontrar el número de prioridad coincidente más bajo; 'orden de entrada' significa subred y luego NIC; 'agrupar servidores por función sin direcciones IP' significa ASG; 'ver todas las reglas aplicadas a una VM' significa reglas de seguridad efectivas; '¿qué regla bloquea este paquete?' significa IP flow verify.

Términos clave

Grupo de seguridad de red (network security group, NSG)
Conjunto de reglas de permiso y denegación con estado que filtra el tráfico de subredes e interfaces de red.
Prioridad (priority)
Número de 100 a 4096; los números más bajos se procesan primero y gana la primera coincidencia.
Reglas predeterminadas (default rules)
Reglas integradas del NSG desde 65000 en adelante, como AllowVnetInBound y DenyAllInBound, que no se pueden eliminar.
Etiqueta de servicio (service tag)
Grupo con nombre de prefijos IP para un servicio o ámbito de Azure, como Internet o AzureLoadBalancer, mantenido por Microsoft.
Grupo de seguridad de aplicaciones (application security group, ASG)
Agrupación lógica de NIC por función que se puede usar como origen o destino en reglas de NSG.
Reglas de seguridad efectivas (effective security rules)
La vista combinada de todas las reglas de NSG de la subred y de la NIC que realmente se aplican a una interfaz de red.
Filtrado con estado (stateful filtering)
Permitir automáticamente el tráfico de retorno de una conexión que una regla ya permitió.
Ejemplo real

Una empresa agrega servidores web nuevos cada mes y antes actualizaba las reglas de NSG con la dirección IP de cada servidor. El administrador crea un grupo de seguridad de aplicaciones llamado asg-web, reescribe la regla del NSG de la base de datos para permitir TCP 1433 solo desde asg-web y agrega la NIC de cada servidor web al grupo durante la implementación. Los servidores nuevos obtienen acceso a la base de datos automáticamente, y los que se retiran lo pierden en cuanto su NIC sale del grupo.

Consejo para el examen: Gana el número de prioridad más bajo y el procesamiento se detiene en la primera coincidencia. El tráfico entrante lo revisa el NSG de la subred y luego el de la NIC; el saliente, la NIC y luego la subred; ambos deben permitirlo. La regla predeterminada DenyAllInBound bloquea el tráfico de internet a menos que agregues un Allow.

Comprueba lo que sabes

Un NSG tiene Deny TCP 3389 con prioridad 200 y Allow TCP 3389 con prioridad 300. ¿Se permite RDP?

No. Las reglas se procesan desde el número más bajo, así que el Deny con 200 coincide primero y el procesamiento se detiene.

Una VM tiene NSG tanto en su subred como en su NIC. ¿Qué debe cumplirse para que el tráfico entrante llegue a ella?

Ambos NSG deben permitirlo; primero se evalúa el NSG de la subred y luego el de la NIC.

¿Qué regla predeterminada bloquea el tráfico entrante desde internet?

DenyAllInBound con prioridad 65500, precedida solo por AllowVnetInBound y AllowAzureLoadBalancerInBound.

¿Cómo puedes permitir el tráfico SQL desde todos los servidores web sin enumerar sus direcciones IP?

Coloca las NIC de los servidores web en un grupo de seguridad de aplicaciones y usa ese ASG como origen de la regla.
