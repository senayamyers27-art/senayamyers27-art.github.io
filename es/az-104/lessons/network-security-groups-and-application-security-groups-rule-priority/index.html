Grupos de seguridad de red y grupos de seguridad de aplicaciones: prioridad de reglas, reglas predeterminadas, asociación a subred vs. NIC y reglas de seguridad efectivas

Un grupo de seguridad de red (NSG) filtra el tráfico hacia y desde los recursos de Azure en una red virtual con una lista de reglas de permitir y denegar. Cada regla coincide según el origen, el puerto de origen, el destino, el puerto de destino y el protocolo (TCP, UDP, ICMP o cualquiera) y tiene una dirección (entrante o saliente), una acción y una prioridad. Los NSG tienen estado (stateful): si se permite una conexión entrante, el tráfico de respuesta se permite automáticamente sin necesidad de una regla saliente.

La prioridad es un número de 100 a 4096. Las reglas se procesan en orden del número más bajo al más alto, y el procesamiento se detiene en la primera regla que coincide. Así, un Deny con prioridad 100 gana sobre un Allow con 200 para el mismo tráfico, y un Allow con 100 gana sobre un Deny con 200. Deja huecos entre las prioridades, como 100, 200, 300, para poder insertar reglas más adelante.

Cada NSG incluye reglas predeterminadas con prioridades de 65000 en adelante, que no puedes eliminar pero sí anular con reglas de número más bajo. Entrantes: AllowVnetInBound (65000) permite el tráfico desde dentro de la VNet y las redes conectadas, AllowAzureLoadBalancerInBound (65001) permite los sondeos de estado del equilibrador de carga de Azure, y DenyAllInBound (65500) bloquea todo lo demás, incluido internet. Salientes: AllowVnetOutBound (65000), AllowInternetOutBound (65001) y DenyAllOutBound (65500). El origen y el destino pueden usar etiquetas de servicio (service tags) como VirtualNetwork, Internet, AzureLoadBalancer o Storage en lugar de intervalos de IP, y Azure mantiene actualizadas sus listas de direcciones.

Puedes asociar un NSG con una subred, con una interfaz de red (NIC) o con ambas, y un mismo NSG se puede reutilizar en muchas. Cuando existen ambos, el tráfico debe estar permitido por los dos. Para el tráfico entrante se evalúa primero el NSG de la subred y luego el de la NIC. Para el tráfico saliente se evalúa primero el NSG de la NIC y luego el de la subred. Si cualquiera de los dos lo deniega, el tráfico se descarta. Muchos equipos aplican los NSG solo a las subredes, por simplicidad.

Los grupos de seguridad de aplicaciones (ASG) te permiten agrupar NIC por función y usar el nombre del grupo en las reglas en lugar de direcciones IP. Creas ASG como asg-web y asg-db, asignas la NIC de cada VM al ASG correspondiente y luego escribes una regla como 'permitir TCP 1433 desde asg-web hacia asg-db'. Cuando agregas un servidor web nuevo, solo agregas su NIC a asg-web; no hace falta cambiar ninguna regla. Las NIC de un ASG deben estar en la misma VNet.

Cuando el tráfico se bloquea de forma inesperada, revisa las reglas de seguridad efectivas: en la NIC de la VM, abre Effective security rules (o usa Network Watcher) para ver las reglas combinadas de los NSG de la subred y de la NIC, incluidas las reglas predeterminadas y las etiquetas de servicio expandidas. IP flow verify de Network Watcher te indica exactamente qué regla permite o deniega un paquete específico.

Términos clave

Network security group (NSG) (grupo de seguridad de red)
Un conjunto con estado de reglas de permitir y denegar con prioridad que filtra el tráfico de subredes y NIC.
Priority (prioridad)
Un número de 100 a 4096; los números más bajos se evalúan primero y el procesamiento se detiene en la primera coincidencia.
Service tag (etiqueta de servicio)
Un grupo con nombre de prefijos IP para un servicio o ámbito de Azure, como Internet o Storage, mantenido por Microsoft.
Application security group (ASG) (grupo de seguridad de aplicaciones)
Un grupo con nombre de NIC que se puede usar como origen o destino en las reglas de NSG.
Effective security rules (reglas de seguridad efectivas)
Las reglas combinadas de todos los NSG aplicados a una NIC, tal como se aplican realmente.
Ejemplo real

Una aplicación de tres niveles tiene VM web, de aplicación y de base de datos en una subred. El administrador crea los ASG asg-web, asg-app y asg-db, y luego un NSG con reglas que permiten 443 desde Internet hacia asg-web (prioridad 100), 8080 desde asg-web hacia asg-app (110), 1433 desde asg-app hacia asg-db (120) y un Deny desde VirtualNetwork hacia asg-db (200). Los servidores web no pueden llegar directamente a la base de datos, y las VM nuevas solo necesitan el ASG correcto.

Consejo para el examen: Gana el número de prioridad más bajo y el procesamiento se detiene en la primera coincidencia. Entrante: NSG de subred y luego NSG de NIC; saliente: NIC y luego subred; ambos deben permitir. La regla predeterminada DenyAllInBound bloquea el tráfico de internet a menos que agregues un Allow.

Comprueba lo que sabes

La regla 100 deniega TCP 3389 desde Internet; la regla 200 permite TCP 3389 desde Internet. ¿Se permite RDP?

No. La regla 100 coincide primero y el procesamiento se detiene.

El NSG de la subred permite el puerto 80 entrante, pero el NSG de la NIC no tiene ninguna regla para él. ¿Se permite el puerto 80 desde internet?

No. La regla predeterminada DenyAllInBound del NSG de la NIC lo bloquea; ambos NSG deben permitir el tráfico.

¿Cómo permites el tráfico SQL solo desde los servidores web sin enumerar sus direcciones IP?

Coloca las NIC de los servidores web en un grupo de seguridad de aplicaciones y úsalo como origen en la regla del NSG.
