Puntos de conexión de servicio vs. puntos de conexión privados, y zonas DNS privadas para Private Link

Muchos servicios de plataforma de Azure, como Azure Storage, Azure SQL Database y Azure Key Vault, se alcanzan de forma predeterminada mediante puntos de conexión públicos en internet. Dos funciones permiten que los recursos de una red virtual (VNet) lleguen a ellos de forma más segura: los puntos de conexión de servicio (service endpoints) y los puntos de conexión privados (private endpoints). Sus nombres se parecen, pero funcionan de manera muy diferente, y elegir entre ellos es un escenario frecuente del examen, que suele decidirse según si se requiere acceso desde la red local, un ámbito por recurso o deshabilitar por completo el acceso público.

Un punto de conexión de servicio es una opción de una subred, como Microsoft.Storage o Microsoft.Sql. Una vez habilitado, el tráfico desde esa subred hacia el servicio viaja por la red troncal de Azure y lleva la identidad de la subred. El firewall del servicio puede entonces permitir esa subred específica (una regla de red virtual) y denegar todo lo demás. El servicio sigue usando su dirección IP pública y la VM sigue conectándose al nombre público. Los puntos de conexión de servicio son gratuitos, rápidos de configurar, solo funcionan para el tráfico que se origina en subredes de Azure (no desde la red local por VPN) y permiten el acceso a todas las instancias de ese tipo de servicio, a menos que agregues una directiva de punto de conexión de servicio (disponible para Storage) que limite a qué cuentas se puede llegar.

Un punto de conexión privado es una interfaz de red colocada en tu subred con una dirección IP privada, conectada mediante Azure Private Link a un recurso específico, como el servicio de blobs de una cuenta de almacenamiento o un servidor SQL. Los clientes se conectan a esa IP privada. Como es una dirección real en tu VNet, es accesible desde las VNet emparejadas y desde la red local por VPN o ExpressRoute, y luego puedes deshabilitar por completo el acceso de red público en el recurso. Como se asigna a una sola instancia de recurso, también ayuda a prevenir la filtración de datos hacia otras cuentas. Los puntos de conexión privados se facturan por hora y por gigabyte procesado.

Los puntos de conexión privados solo funcionan si los clientes resuelven el nombre normal del servicio a la IP privada. Cuando creas un punto de conexión privado, el nombre DNS (Domain Name System) público, como contoso.blob.core.windows.net, recibe un CNAME hacia un nombre privatelink, como contoso.privatelink.blob.core.windows.net. Creas una zona DNS privada de Azure con ese nombre privatelink, la vinculas a tus VNet y agregas un registro A para la IP privada. El portal lo hace por ti cuando eliges Integrate with private DNS zone, asociando un grupo de zonas DNS (DNS zone group) al punto de conexión para que los registros se mantengan automáticamente. Ejemplos: privatelink.blob.core.windows.net para blobs, privatelink.file.core.windows.net para archivos, privatelink.database.windows.net para Azure SQL y privatelink.vaultcore.azure.net para Key Vault.

En una red hub-and-spoke, mantén las zonas privatelink en un solo lugar y vincúlalas a cada VNet que necesite resolverlas. Los servidores DNS locales deben reenviar las consultas de esas zonas hacia Azure, normalmente a un punto de conexión de entrada de Azure DNS Private Resolver, porque las máquinas locales no pueden consultar directamente Azure DNS en 168.63.129.16. Puedes probar la resolución desde una VM con nslookup contoso.blob.core.windows.net; la respuesta debería ser una dirección privada como 10.20.1.5 y el alias debería incluir privatelink.

Veamos un ejemplo práctico. Un equipo de finanzas guarda estados de cuenta en una cuenta de almacenamiento y debe acceder a ella desde VM de Azure y desde la oficina central a través de una VPN de sitio a sitio, sin ningún acceso público. Los puntos de conexión de servicio no pueden ayudar a la oficina, así que el administrador crea un punto de conexión privado para el subrecurso blob en la VNet hub, lo integra con la zona privatelink.blob.core.windows.net vinculada al hub y a los spokes, configura los servidores DNS de la oficina para reenviar condicionalmente blob.core.windows.net al punto de conexión de entrada del Private Resolver y establece el acceso de red público en Disabled. Ahora tanto las VM como los equipos de la oficina resuelven la cuenta a 10.10.4.6.

Errores comunes: suponer que un punto de conexión de servicio da al servicio una IP privada; esperar que los puntos de conexión de servicio funcionen desde la red local; crear un punto de conexión privado sin integración DNS, de modo que nslookup sigue devolviendo una IP pública y la conexión se rechaza en cuanto se deshabilita el acceso público; crear una zona privada pero olvidar vincularla a la VNet del cliente; y apuntar los servidores locales a 168.63.129.16. Cuando falla una conexión con un punto de conexión privado, revisa primero el DNS.

La redacción del examen tiene pistas claras. 'Gratuito', 'lo más sencillo', 'restringir una cuenta de almacenamiento a una subred' significa un punto de conexión de servicio con una regla de red virtual. 'Dirección IP privada', 'accesible desde la red local', 'deshabilitar el acceso de red público' o 'solo esta cuenta de almacenamiento' significa un punto de conexión privado. 'El nombre se resuelve a una IP pública' significa que falta una zona DNS privada o el vínculo con la VNet. 'Los clientes locales no pueden resolver el punto de conexión privado' significa un reenviador DNS o Private Resolver.

Términos clave

Punto de conexión de servicio (service endpoint)
Opción de subred que enruta el tráfico hacia un servicio PaaS por la red troncal de Azure e identifica la subred ante el firewall del servicio.
Punto de conexión privado (private endpoint)
Interfaz de red con una IP privada en tu subred que se conecta a un recurso específico mediante Private Link.
Azure Private Link
La tecnología de plataforma que expone servicios de Azure en direcciones IP privadas dentro de tu VNet.
Zona DNS privada (private DNS zone)
Zona de Azure DNS que solo se puede resolver desde las VNet vinculadas, usada para los nombres privatelink.
Vínculo de red virtual (virtual network link)
La asociación que permite a una VNet resolver los registros de una zona DNS privada.
Directiva de punto de conexión de servicio (service endpoint policy)
Directiva que limita el tráfico de un punto de conexión de servicio a cuentas específicas de Azure Storage.
Azure DNS Private Resolver
Servicio administrado con puntos de conexión de entrada y de salida que permite al DNS local resolver zonas privadas de Azure y viceversa.
Ejemplo real

Después de deshabilitar el acceso público de una cuenta de almacenamiento, una VM de aplicación empieza a fallar con errores 403. Un ingeniero ejecuta nslookup en la VM y ve que la cuenta se resuelve a una dirección pública. El punto de conexión privado existe, pero su zona privatelink.blob.core.windows.net solo está vinculada a la VNet hub, no al spoke donde reside la VM. Agregar un vínculo de red virtual de la zona hacia el spoke hace que el nombre se resuelva a la IP privada, y la aplicación se recupera.

Consejo para el examen: El acceso desde la red local, deshabilitar el acceso público o limitar el ámbito a una sola instancia de recurso significa un punto de conexión privado. Si falla una conexión con un punto de conexión privado, revisa primero el DNS: el nombre debe resolverse a la IP privada mediante una zona privatelink vinculada.

Comprueba lo que sabes

¿Qué opción permite que los clientes locales lleguen a un servidor de Azure SQL a través de una VPN usando una dirección IP privada?

Un punto de conexión privado, porque los puntos de conexión de servicio solo funcionan para el tráfico desde subredes de Azure y conservan la IP pública.

Después de crear un punto de conexión privado, nslookup en una VM devuelve una IP pública. ¿Cuál es la causa probable?

Falta la zona DNS privada privatelink, le falta el registro A o no está vinculada a la VNet de la VM.

¿Qué cambia realmente al habilitar Microsoft.Storage como punto de conexión de servicio en una subred?

El tráfico desde la subred llega a Storage por la red troncal de Azure con la identidad de la subred, de modo que el firewall del almacenamiento puede permitir esa subred; el servicio conserva su IP pública.

¿Qué nombre de zona DNS privada se usa para un punto de conexión privado de Blob Storage?

privatelink.blob.core.windows.net.
