Rutas definidas por el usuario: tablas de rutas, tipos de próximo salto (aplicación virtual, puerta de enlace de red virtual, internet, ninguno) y tunelización forzada

Azure enruta el tráfico automáticamente con rutas del sistema (system routes), que no puedes eliminar. Cada subred recibe una ruta para el propio espacio de direcciones de la VNet (próximo salto Virtual network), una ruta predeterminada 0.0.0.0/0 hacia Internet, rutas para las VNet emparejadas y rutas aprendidas de las puertas de enlace. Ciertos rangos privados y reservados que no se usan en la VNet reciben el próximo salto None, de modo que el tráfico hacia ellos se descarta. Esto funciona bien hasta que quieres que el tráfico vaya a otro lugar, casi siempre a través de un firewall para inspeccionarlo, o de vuelta a la red local. Las rutas definidas por el usuario (UDR) te permiten invalidar las rutas del sistema. Creas un recurso de tabla de rutas, le agregas rutas y asocias la tabla de rutas con una o más subredes. Una tabla de rutas afecta al tráfico que sale de los recursos de las subredes a las que está asociada; nunca se asocia con una interfaz de red (NIC) ni con una VNet completa, y cada subred puede tener como máximo una tabla de rutas. La tabla de rutas debe estar en la misma región y suscripción que la VNet. Los pasos se ven así:

az network route-table create --resource-group rg-net --name rt-spoke
az network route-table route create --resource-group rg-net --route-table-name rt-spoke \
  --name default-to-fw --address-prefix 0.0.0.0/0 \
  --next-hop-type VirtualAppliance --next-hop-ip-address 10.0.1.4
az network vnet subnet update --resource-group rg-net --vnet-name vnet-spoke \
  --name app --route-table rt-spoke

Cada ruta tiene un prefijo de dirección (destino) y un tipo de próximo salto. Virtual appliance envía el tráfico a la IP privada de una aplicación virtual de red (NVA), como Azure Firewall o una VM de firewall de terceros; debes indicar esa dirección IP de próximo salto. Virtual network gateway envía el tráfico a la puerta de enlace VPN, normalmente hacia la red local. Virtual network enruta el tráfico dentro de la VNet, útil para invalidar una regla más amplia para un rango específico. Internet envía el tráfico directamente a internet. None descarta el tráfico, una forma sencilla de bloquear un destino.

Cuando varias rutas coinciden con un destino, Azure elige la coincidencia de prefijo más largo (longest prefix match): una ruta /24 gana a una /16, que gana a 0.0.0.0/0. Si rutas con el mismo prefijo provienen de orígenes diferentes, una UDR gana a una ruta BGP (Border Gateway Protocol) aprendida de una puerta de enlace, que gana a una ruta del sistema. La tabla de rutas también tiene la opción Propagate gateway routes; desactivarla impide que las rutas aprendidas por la puerta de enlace VPN o ExpressRoute se agreguen a la subred, algo común en spokes que deben enviar todo a través de un firewall. Una NVA reenvía tráfico que no está dirigido a ella, así que en su interfaz de red debes habilitar el reenvío IP (IP forwarding) en Azure, y el enrutamiento dentro de su sistema operativo. Azure Firewall se encarga de esto por ti.

La tunelización forzada (forced tunneling) consiste en enviar todo el tráfico destinado a internet de vuelta a la red local para inspeccionarlo, en lugar de dejar que salga de Azure directamente. Con una puerta de enlace VPN, creas una UDR para 0.0.0.0/0 con próximo salto Virtual network gateway y configuras un sitio predeterminado en la puerta de enlace basada en rutas; con ExpressRoute, la red local anuncia una ruta predeterminada por BGP. Usa las rutas efectivas o la herramienta de próximo salto de Network Watcher para confirmar qué ruta sigue realmente el tráfico de una VM.

Veamos un ejemplo práctico. El área de seguridad exige que todo el tráfico del spoke App, tanto hacia internet como hacia el spoke Data, pase por Azure Firewall en 10.0.1.4 en el hub. Creas la tabla de rutas rt-app con una ruta 0.0.0.0/0 hacia Virtual appliance 10.0.1.4 y la asocias con la subred App; luego, una tabla similar en la subred Data para que el tráfico de retorno sea simétrico. Como la puerta de enlace VPN del hub inyectaría de otro modo rutas locales que evitarían el firewall, deshabilitas la propagación de rutas de puerta de enlace en ambas tablas. El próximo salto desde una VM de App hacia 8.8.8.8 ahora muestra VirtualAppliance 10.0.1.4 y el ID de la tabla de rutas.

Errores comunes: intentar asociar una tabla de rutas con una NIC; olvidar el reenvío IP en la interfaz de red de una NVA de terceros; enrutar solo una dirección a través de un firewall, lo que crea un enrutamiento asimétrico que rompe las sesiones; poner una UDR 0.0.0.0/0 en GatewaySubnet o en AzureBastionSubnet, lo cual no se admite y rompe esos servicios; y olvidar que una ruta del sistema o BGP más específica gana a una UDR más amplia.

Redacción del examen: 'enviar todo el tráfico a través del firewall' significa 0.0.0.0/0 con próximo salto Virtual appliance; 'inspeccionar el tráfico de internet en la red local' significa tunelización forzada; 'bloquear el tráfico hacia un rango' significa próximo salto None; '¿qué ruta se usa?' significa primero el prefijo más largo y luego UDR sobre BGP sobre sistema.

Términos clave

Ruta del sistema (system route)
Ruta predeterminada que Azure crea automáticamente para cada subred, como el rango de la VNet y 0.0.0.0/0 hacia internet.
Ruta definida por el usuario (user-defined route, UDR)
Ruta personalizada en una tabla de rutas que invalida las rutas del sistema para las subredes asociadas.
Tabla de rutas (route table)
Recurso de Azure que contiene UDR, asociado con una o más subredes (como máximo una tabla por subred).
Tipo de próximo salto (next hop type)
A dónde se envía el tráfico que coincide: Virtual appliance, Virtual network gateway, Virtual network, Internet o None.
Coincidencia de prefijo más largo (longest prefix match)
La regla por la que se elige la ruta coincidente más específica, como una /24 sobre una /16.
Reenvío IP (IP forwarding)
Opción de la NIC que permite a una VM recibir y reenviar tráfico que no está dirigido a ella, necesaria para las NVA.
Tunelización forzada (forced tunneling)
Redirigir todo el tráfico destinado a internet desde Azure hacia la red local para inspeccionarlo.
Ejemplo real

Después de agregar una tabla de rutas que envía 0.0.0.0/0 a una VM de firewall de terceros, un equipo descubre que sus VM ya no pueden llegar a nada fuera de la subred. El próximo salto confirma que el tráfico va a la IP del firewall, pero el firewall nunca lo reenvía. La interfaz de red de la VM del firewall tiene el reenvío IP deshabilitado. Habilitarlo en la NIC, y en el sistema operativo del firewall, restablece la conectividad con la inspección en funcionamiento.

Consejo para el examen: Las tablas de rutas se asocian con subredes, no con NIC. Gana el prefijo más largo; en caso de empate, UDR gana a BGP, que gana a las rutas del sistema. Virtual appliance necesita una dirección IP de próximo salto y el reenvío IP en la NIC de la NVA, y None descarta el tráfico.

Comprueba lo que sabes

¿Qué tipo de próximo salto envía el tráfico a una VM de firewall y qué valor adicional se requiere?

Virtual appliance, con la dirección IP privada del firewall como dirección IP de próximo salto.

Una subred tiene una UDR para 10.0.0.0/8 y una ruta del sistema para 10.1.0.0/16. ¿Cuál se aplica a 10.1.2.3?

La ruta del sistema para 10.1.0.0/16, porque la coincidencia de prefijo más largo se elige antes de considerar el origen de la ruta.

¿Cómo obligas a que todo el tráfico destinado a internet desde Azure pase por los dispositivos de seguridad locales?

Con tunelización forzada: una ruta 0.0.0.0/0 hacia la puerta de enlace de red virtual con un sitio predeterminado, o una ruta predeterminada anunciada por BGP en el caso de ExpressRoute.

¿Qué hace el tipo de próximo salto None?

Descarta el tráfico hacia el prefijo de destino que coincide.
