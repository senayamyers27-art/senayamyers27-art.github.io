Azure Load Balancer: público vs. interno, SKU Standard, grupos de back-end, sondeos de estado, reglas de equilibrio de carga y reglas NAT de entrada

Azure Load Balancer distribuye el tráfico de red entrante entre un grupo de VM o instancias de conjuntos de escalado en buen estado. Funciona en la capa 4 del modelo OSI, la capa de transporte, así que equilibra flujos TCP y UDP según direcciones IP y puertos, sin examinar el contenido HTTP. Para el enrutamiento basado en URL o un firewall de aplicaciones web, usarías en su lugar Application Gateway, un servicio de capa 7.

Un equilibrador de carga es público o interno según su configuración de IP de front-end. Un equilibrador de carga público tiene una dirección IP pública como front-end y equilibra el tráfico de internet hacia las VM, y también puede proporcionarles conectividad saliente a internet. Un equilibrador de carga interno tiene como front-end una dirección IP privada de una subred y equilibra el tráfico dentro de una VNet o desde redes conectadas, por ejemplo entre un nivel web y un nivel de aplicación.

Usa la SKU Standard. Microsoft retiró la SKU Basic, y Standard tiene las características en las que se centra el examen: admite zonas de disponibilidad (front-ends con redundancia de zona o zonales), tiene SLA, admite grupos de back-end más grandes, sondeos de estado HTTPS y HA ports, y es segura de forma predeterminada, lo que significa que el tráfico entrante se bloquea a menos que un grupo de seguridad de red en las subredes o NIC de las VM de back-end lo permita. Un equilibrador de carga Standard debe usar IP públicas Standard, y los miembros de su grupo de back-end deben estar en una sola VNet.

Los componentes principales son estos. El grupo de back-end (backend pool) es el conjunto de NIC de VM o direcciones IP que reciben el tráfico. Un sondeo de estado (health probe) comprueba cada back-end con un protocolo y un puerto, TCP, HTTP o HTTPS, a un intervalo; una instancia que falla se saca de la rotación hasta que vuelve a pasar. Los sondeos HTTP esperan una respuesta 200 desde una ruta como /health. Los sondeos provienen de la dirección de la plataforma Azure 168.63.129.16, que la regla predeterminada de NSG AllowAzureLoadBalancerInBound permite, así que no la bloquees.

Una regla de equilibrio de carga (load-balancing rule) lo une todo: IP y puerto de front-end, grupo y puerto de back-end, protocolo, sondeo de estado y persistencia de sesión. De forma predeterminada, el equilibrador de carga usa un hash de cinco tuplas (IP de origen, puerto de origen, IP de destino, puerto de destino, protocolo), así que distintas conexiones de un mismo cliente pueden llegar a VM diferentes. La persistencia de sesión establecida en Client IP o Client IP and protocol mantiene a un cliente en la misma VM. En un equilibrador de carga Standard interno, una regla HA ports equilibra todos los puertos y protocolos a la vez, lo que resulta útil para las aplicaciones virtuales de red.

Una regla NAT de entrada (inbound NAT rule) reenvía el tráfico que llega a un puerto de front-end específico hacia una VM y un puerto específicos, en lugar de equilibrarlo. Por ejemplo, el puerto de front-end 50001 hacia el puerto 3389 de VM1 y el 50002 hacia el puerto 3389 de VM2 te permiten llegar a cada VM individualmente a través de la única IP pública del equilibrador de carga. Las reglas de salida (outbound rules) controlan cómo las VM de back-end comparten las IP de front-end para el acceso saliente a internet, aunque ahora una NAT gateway es la forma recomendada de proporcionar conectividad saliente.

Términos clave

Public load balancer (equilibrador de carga público)
Un equilibrador de carga con una IP de front-end pública que distribuye el tráfico de internet hacia las VM de back-end.
Internal load balancer (equilibrador de carga interno)
Un equilibrador de carga con una IP de front-end privada que distribuye el tráfico dentro de una VNet o de redes conectadas.
Health probe (sondeo de estado)
Una comprobación periódica TCP, HTTP o HTTPS que saca de la rotación las instancias de back-end en mal estado.
Load-balancing rule (regla de equilibrio de carga)
Una asignación de una IP y un puerto de front-end a un grupo y un puerto de back-end, con un sondeo y una configuración de persistencia de sesión.
Inbound NAT rule (regla NAT de entrada)
Una regla que reenvía un puerto de front-end específico hacia una VM y un puerto de back-end específicos.
Ejemplo real

Tres VM web están detrás de un equilibrador de carga Standard público. Una regla asigna el puerto 443 del front-end al puerto 443 del grupo de back-end con un sondeo HTTPS en /health. Cuando el servicio web de VM2 falla, el sondeo falla y el tráfico va solo a VM1 y VM3. Como Standard es seguro de forma predeterminada, el administrador también agregó una regla de NSG que permite 443 desde Internet hacia la subred web.

Consejo para el examen: Los equilibradores de carga Standard bloquean el tráfico entrante hasta que un NSG lo permite. Las reglas de equilibrio de carga reparten el tráfico; las reglas NAT de entrada asignan un puerto a una VM. Las necesidades de capa 7 (rutas URL, WAF) apuntan a Application Gateway, no a Load Balancer.

Comprueba lo que sabes

Un equilibrador de carga Standard nuevo está configurado correctamente, pero los clientes no pueden conectarse a las VM de back-end. ¿Qué deberías revisar primero?

Que un NSG permita el tráfico entrante, porque los equilibradores de carga y las IP públicas Standard son seguros de forma predeterminada.

¿Cómo te conectas por RDP a una VM específica del grupo de back-end a través de la IP pública del equilibrador de carga?

Crea una regla NAT de entrada que asigne un puerto de front-end (como 50001) al puerto 3389 de esa VM (o usa Bastion en su lugar).

Los usuarios pierden su carrito de compras porque cada solicitud va a una VM diferente. ¿Qué configuración ayuda?

La persistencia de sesión establecida en Client IP (o Client IP and protocol) en la regla de equilibrio de carga.
