Azure Load Balancer: público vs. interno, SKU Standard, grupos de back-end, sondeos de estado, reglas de equilibrio de carga y reglas NAT de entrada

Azure Load Balancer distribuye el tráfico de red entrante entre un grupo de máquinas virtuales (VM) o instancias de conjuntos de escalado en buen estado. Funciona en la capa 4 del modelo OSI (Open Systems Interconnection), la capa de transporte, así que equilibra flujos TCP y UDP según direcciones IP y puertos, sin mirar el contenido HTTP. Para el enrutamiento basado en URL, la terminación TLS o un firewall de aplicaciones web usarías en su lugar Application Gateway, un servicio de capa 7. Load Balancer es rápido, de baja latencia y adecuado para cualquier protocolo TCP o UDP. Un equilibrador de carga es público o interno según su configuración de IP de front-end. Un equilibrador de carga público tiene una dirección IP pública como front-end y equilibra el tráfico de internet hacia las VM, y también puede proporcionarles conectividad saliente a internet. Un equilibrador de carga interno tiene como front-end una dirección IP privada de una subred y equilibra el tráfico dentro de una red virtual (VNet) o desde redes conectadas, por ejemplo entre un nivel web y un nivel de aplicación.

Usa el SKU Standard. Microsoft retiró el SKU Basic, y Standard tiene las funciones en las que se centra el examen: admite zonas de disponibilidad (front-ends con redundancia de zona o zonales), tiene un SLA (acuerdo de nivel de servicio), admite grupos de back-end más grandes, sondeos de estado HTTPS y puertos HA, y es seguro de forma predeterminada, lo que significa que el tráfico entrante se bloquea a menos que un grupo de seguridad de red (NSG) en las subredes o NIC de las VM de back-end lo permita. Un equilibrador de carga Standard debe usar IP públicas Standard, y los miembros de su grupo de back-end deben estar en una sola VNet.

Los componentes principales son estos. El grupo de back-end (backend pool) es el conjunto de interfaces de red de VM o direcciones IP que reciben el tráfico. Un sondeo de estado (health probe) comprueba cada back-end en un protocolo y puerto (TCP, HTTP o HTTPS) a intervalos; una instancia que falla se saca de la rotación hasta que vuelve a pasar el sondeo. Los sondeos HTTP esperan una respuesta 200 desde una ruta como /health. Los sondeos provienen de la dirección de la plataforma Azure 168.63.129.16, que la regla de NSG predeterminada AllowAzureLoadBalancerInBound permite, así que no la bloquees. Una regla de equilibrio de carga (load-balancing rule) une todo: IP y puerto de front-end, grupo y puerto de back-end, protocolo, sondeo de estado y persistencia de sesión. De forma predeterminada, el equilibrador de carga usa un hash de cinco tuplas (IP de origen, puerto de origen, IP de destino, puerto de destino y protocolo), así que distintas conexiones de un mismo cliente pueden llegar a VM diferentes. La persistencia de sesión configurada como Client IP, o Client IP and protocol, mantiene a un cliente en la misma VM. En un equilibrador de carga interno Standard, una regla de puertos HA equilibra todos los puertos y protocolos a la vez, lo que resulta útil para las aplicaciones virtuales de red.

az network lb probe create --resource-group rg-web --lb-name lb-web \
  --name http-probe --protocol Http --port 80 --path /health
az network lb rule create --resource-group rg-web --lb-name lb-web --name http \
  --protocol Tcp --frontend-port 80 --backend-port 80 \
  --frontend-ip-name fe-web --backend-pool-name bp-web --probe-name http-probe

Una regla NAT de entrada (inbound NAT rule; NAT es traducción de direcciones de red) reenvía el tráfico que llega a un puerto de front-end específico hacia una VM y un puerto específicos, en lugar de equilibrarlo. Por ejemplo, el puerto de front-end 50001 hacia el puerto 3389 de VM1 y el 50002 hacia el puerto 3389 de VM2 te permiten llegar a cada VM individualmente a través de la única IP pública del equilibrador de carga. Las reglas de salida (outbound rules) controlan cómo las VM de back-end comparten las IP de front-end para el acceso saliente a internet, aunque ahora una puerta de enlace NAT es la forma recomendada de proporcionar conectividad saliente.

Veamos un ejemplo práctico. Un nivel web de tres VM en las zonas 1, 2 y 3 está detrás de un equilibrador de carga público Standard con una IP de front-end con redundancia de zona, un sondeo de estado en HTTP /health y una regla de equilibrio de carga para TCP 443. Un nivel de aplicación está detrás de un equilibrador de carga interno Standard en 10.1.2.10 en el puerto 8080. Después de la implementación, el sitio web no responde. El NSG de la subred web no tiene ninguna regla que permita 443 desde internet, y Standard está cerrado de forma predeterminada. Agregar la regla lo soluciona. Más adelante, una VM cuyo servicio web falla se saca de la rotación automáticamente porque su sondeo falla.

Errores comunes: esperar que un equilibrador de carga Standard deje pasar tráfico sin una regla de permiso en el NSG; bloquear la etiqueta de servicio AzureLoadBalancer, de modo que todos los sondeos fallan y el grupo parece vacío; sondear un puerto o una ruta que la aplicación no atiende; mezclar SKU de IP pública y de equilibrador de carga; elegir Load Balancer cuando el escenario necesita enrutamiento por ruta URL o un firewall de aplicaciones web; y usar una regla de equilibrio de carga cuando necesitas llegar a una VM específica.

La redacción del examen es predecible. 'Distribuir tráfico TCP o UDP' significa Azure Load Balancer. 'Front-end privado entre niveles' significa equilibrador de carga interno. 'Enrutar por ruta URL' o 'WAF' significa Application Gateway. 'Quitar automáticamente las VM con problemas' significa un sondeo de estado. 'Los usuarios deben permanecer en la misma VM' significa persistencia de sesión (Client IP). 'Conectarse a cada VM en un puerto diferente a través de una IP pública' significa reglas NAT de entrada. 'Todos los puertos para una NVA' significa puertos HA en un equilibrador de carga interno Standard.

Términos clave

Azure Load Balancer
Servicio de capa 4 que distribuye flujos TCP y UDP entre instancias de back-end en buen estado.
Equilibrador de carga interno (internal load balancer)
Equilibrador de carga con una IP de front-end privada que equilibra el tráfico dentro de una VNet o de redes conectadas.
Grupo de back-end (backend pool)
El conjunto de NIC de VM o direcciones IP que reciben el tráfico de un equilibrador de carga.
Sondeo de estado (health probe)
Comprobación periódica TCP, HTTP o HTTPS que saca de la rotación a las instancias de back-end que fallan.
Regla de equilibrio de carga (load-balancing rule)
Asignación de una IP y un puerto de front-end a un grupo y un puerto de back-end, usando un sondeo de estado.
Regla NAT de entrada (inbound NAT rule)
Regla que reenvía un puerto de front-end a una VM y un puerto de back-end específicos.
Persistencia de sesión (session persistence)
Configuración que mantiene las conexiones de un cliente en la misma instancia de back-end, según la IP del cliente.
Ejemplo real

Un estudio de videojuegos ejecuta servidores de juego UDP en seis VM. Un equilibrador de carga público Standard con un front-end con redundancia de zona distribuye a los jugadores entre los servidores, y un sondeo de estado TCP en el puerto del juego saca cualquier servidor cuyo proceso se bloquee. Para el mantenimiento, el estudio agrega reglas NAT de entrada que asignan los puertos 50001 a 50006 a SSH en cada VM, accesibles solo desde la IP de la oficina mediante una regla de NSG, en lugar de dar a cada VM su propia IP pública.

Consejo para el examen: Los equilibradores de carga Standard bloquean el tráfico entrante hasta que un NSG lo permite. Las reglas de equilibrio de carga reparten el tráfico; las reglas NAT de entrada asignan un puerto a una VM. Las necesidades de capa 7, como rutas URL o un WAF, apuntan a Application Gateway, no a Load Balancer.

Comprueba lo que sabes

Los servidores web detrás de un equilibrador de carga público Standard nuevo no reciben tráfico, pero los sondeos de estado se completan correctamente. ¿Qué debes revisar?

El NSG de la subred o de las NIC de back-end, porque Standard es seguro de forma predeterminada y necesita una regla explícita que permita el puerto de entrada.

¿Cuál es la diferencia entre una regla de equilibrio de carga y una regla NAT de entrada?

Una regla de equilibrio de carga reparte el tráfico entre el grupo de back-end; una regla NAT de entrada reenvía un puerto de front-end a una VM específica.

Un carrito de compras pierde el estado porque los usuarios llegan a VM diferentes. ¿Qué configuración del equilibrador de carga ayuda?

La persistencia de sesión configurada como Client IP (o Client IP and protocol) para que un cliente permanezca en la misma VM.

¿Qué servicio deberías usar si las solicitudes deben enrutarse por ruta URL?

Application Gateway, porque Azure Load Balancer funciona en la capa 4 y no inspecciona las rutas HTTP.
