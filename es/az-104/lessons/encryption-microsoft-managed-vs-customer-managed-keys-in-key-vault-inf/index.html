Cifrado: claves administradas por Microsoft vs. claves administradas por el cliente en Key Vault, cifrado de infraestructura y ámbitos de cifrado

Todos los datos que se escriben en Azure Storage se cifran en reposo automáticamente con cifrado AES (Advanced Encryption Standard) de 256 bits, un proceso llamado Storage Service Encryption. No puedes desactivarlo y no tiene costo adicional. El cifrado y el descifrado son transparentes: las aplicaciones leen y escriben datos con normalidad. Lo que eliges es quién administra las claves y si agregar más capas.

De forma predeterminada se usan claves administradas por Microsoft. Microsoft genera, almacena y rota las claves, y tú no tienes nada que configurar. Esto cumple la mayoría de los requisitos. Algunas organizaciones tienen reglas de cumplimiento que exigen control sobre la clave de cifrado, la capacidad de rotarla según su propio calendario o la capacidad de volver ilegibles los datos revocando la clave. Para ellas existen las claves administradas por el cliente.

Con claves administradas por el cliente (CMK), creas una clave RSA en Azure Key Vault o en Azure Key Vault Managed HSM, y la cuenta de almacenamiento la usa para encapsular (cifrar) las claves de cifrado de datos de la cuenta. La cuenta de almacenamiento necesita una identidad administrada, asignada por el sistema o por el usuario, con permiso sobre la clave, por ejemplo el rol Key Vault Crypto Service Encryption User, o directivas de acceso get, wrap key y unwrap key. El almacén de claves debe tener habilitados soft delete y purge protection para que la clave no pueda perderse de forma permanente por accidente. Si especificas la clave sin versión, Azure Storage toma automáticamente las nuevas versiones de la clave cuando la rotas. Si deshabilitas o eliminas la clave o quitas el acceso de la identidad, los datos quedan inaccesibles hasta que se restaure el acceso, lo cual es a la vez el propósito y el riesgo.

El cifrado de infraestructura (infrastructure encryption) agrega una segunda capa de cifrado a nivel de infraestructura, con un modo de algoritmo diferente y claves diferentes, así que los datos se cifran dos veces. Existe para escenarios de cumplimiento estrictos que exigen doble cifrado. Debe habilitarse al crear la cuenta de almacenamiento y no se puede habilitar ni deshabilitar después.

Los ámbitos de cifrado (encryption scopes) te permiten usar claves diferentes dentro de una misma cuenta para Blob Storage. Creas un ámbito en la cuenta de almacenamiento, respaldado por una clave administrada por Microsoft o por una clave administrada por el cliente, y luego lo estableces como predeterminado para un contenedor o lo especificas al escribir blobs individuales. Puedes exigir que todos los blobs de un contenedor usen el ámbito predeterminado del contenedor. Esto es útil para aplicaciones multiinquilino en las que los datos de cada cliente deben protegerse con una clave distinta en la misma cuenta.

No confundas el cifrado de almacenamiento con las características de cifrado de discos para VM, como encryption at host o Azure Disk Encryption, que se tratan con las máquinas virtuales. El cifrado en tránsito también es una configuración aparte: habilita 'Secure transfer required' y una versión mínima de TLS para que los clientes tengan que usar HTTPS o SMB cifrado.

Términos clave

Storage Service Encryption
Cifrado AES-256 automático y siempre activo de los datos en reposo en Azure Storage.
Customer-managed key (CMK) (clave administrada por el cliente)
Una clave que controlas en Key Vault o Managed HSM y que protege las claves de cifrado de datos de una cuenta de almacenamiento.
Infrastructure encryption (cifrado de infraestructura)
Una segunda capa opcional de cifrado a nivel de infraestructura que debe habilitarse al crear la cuenta.
Encryption scope (ámbito de cifrado)
Una configuración de clave con nombre dentro de una cuenta de almacenamiento que se puede aplicar a contenedores o a blobs individuales.
Ejemplo real

Una empresa de salud debe poder cortar al instante el acceso a los documentos de pacientes si termina un contrato. El administrador crea una clave en un Key Vault con purge protection, da a la identidad administrada asignada por el sistema de la cuenta de almacenamiento el rol Key Vault Crypto Service Encryption User y cambia la cuenta a claves administradas por el cliente. Deshabilitar la clave volvería ilegibles los datos, y rotarla solo requiere agregar una nueva versión de la clave.

Consejo para el examen: El cifrado de infraestructura solo se puede establecer al crear la cuenta. CMK necesita una identidad administrada y un almacén de claves con soft delete y purge protection. El cifrado en reposo no se puede deshabilitar.

Comprueba lo que sabes

¿Puedes habilitar el cifrado de infraestructura en una cuenta de almacenamiento existente?

No. Debe habilitarse al crear la cuenta.

¿Qué necesita la cuenta de almacenamiento para usar una clave administrada por el cliente en Key Vault?

Una identidad administrada con permiso para obtener, encapsular y desencapsular la clave (get, wrap, unwrap), y un almacén de claves con soft delete y purge protection habilitados.

Los blobs de dos clientes comparten una cuenta de almacenamiento, y cada uno debe cifrarse con una clave distinta. ¿Qué característica ayuda?

Los ámbitos de cifrado, cada uno respaldado por una clave diferente y establecido como predeterminado en el contenedor de cada cliente.
