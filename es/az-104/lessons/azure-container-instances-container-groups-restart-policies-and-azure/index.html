Azure Container Instances (grupos de contenedores, directivas de reinicio) y Azure Container Apps (revisiones, entrada y reglas de escalado)

Azure ofrece varias formas de ejecutar contenedores sin administrar máquinas virtuales. Dos entran en el alcance de este examen: Azure Container Instances (ACI), para ejecutar contenedores de forma rápida y sencilla, y Azure Container Apps, para ejecutar microservicios y aplicaciones web con escalado automático, revisiones y entrada (ingress) administrada. Ninguno requiere que operes tú mismo un clúster de Kubernetes. La habilidad evaluada es elegir el servicio correcto y configurar sus opciones clave: grupos de contenedores y directivas de reinicio para ACI, y revisiones, entrada y reglas de escalado para Container Apps. ACI inicia un contenedor en segundos y factura por segundo la vCPU y la memoria que usa. La unidad de implementación es un grupo de contenedores (container group): uno o más contenedores programados en el mismo host que comparten un ciclo de vida, una red local (se comunican entre sí por localhost), una dirección IP pública opcional con una etiqueta de nombre DNS y volúmenes montados, como un recurso compartido de Azure Files. Es similar a un pod de Kubernetes. Los grupos de varios contenedores se admiten para contenedores Linux y suelen implementarse desde un archivo YAML o una plantilla de Azure Resource Manager (ARM), por ejemplo un contenedor de aplicación más un sidecar de registro. Un grupo de contenedores también se puede implementar en una subred de red virtual para acceso privado. Un contenedor único y rápido se ve así:

az container create --resource-group rg-jobs --name nightly-report \
  --image contosoacr.azurecr.io/tools/report:3.2 --cpu 1 --memory 2 \
  --restart-policy OnFailure --assign-identity
az container logs --resource-group rg-jobs --name nightly-report

Las directivas de reinicio (restart policies) de ACI controlan qué ocurre cuando un contenedor termina. Always (la predeterminada) reinicia los contenedores cada vez que se detienen, lo que conviene para servicios de larga duración. OnFailure reinicia solo si el proceso termina con un código distinto de cero, lo que conviene para trabajos que deben reintentarse después de un error. Never ejecuta los contenedores una sola vez, lo que conviene para tareas puntuales como una compilación, un informe o una transformación de datos. Si ejecutas un trabajo por lotes con Always, se reinicia sin fin al terminar y sigue facturando. Como ACI no tiene escalado automático integrado ni división de tráfico, es ideal para tareas sencillas, trabajos de ráfaga y pruebas rápidas.

Azure Container Apps es una plataforma sin servidor construida sobre Kubernetes y componentes de código abierto como KEDA (Kubernetes Event-driven Autoscaling), Dapr (Distributed Application Runtime) y Envoy, con la complejidad oculta. Las aplicaciones se ejecutan en un entorno de Container Apps (Container Apps environment), un límite compartido de red y registro para un conjunto de aplicaciones. Una revisión es una instantánea inmutable de una versión de la aplicación. Cambiar opciones con ámbito de revisión, como la imagen, la CPU, la memoria o las reglas de escalado, crea una revisión nueva; cambiar opciones con ámbito de aplicación, como los secretos o la entrada, no lo hace. En el modo de revisión única (single revision mode), la revisión nueva reemplaza a la anterior. En el modo de varias revisiones (multiple revision mode), varias revisiones se ejecutan a la vez y divides el tráfico por porcentaje, para implementaciones azul-verde o canary, y reviertes moviendo el tráfico.

La entrada (ingress) controla cómo llega el tráfico a la aplicación. Puede estar deshabilitada (para trabajadores en segundo plano), ser interna (accesible solo dentro del entorno o de su red virtual) o externa (accesible desde internet), para HTTP o TCP, en un puerto de destino que especificas. Las reglas de escalado definen cuántas réplicas se ejecutan entre un mínimo y un máximo: las reglas HTTP escalan según las solicitudes simultáneas, las reglas TCP según las conexiones y las reglas personalizadas usan escaladores de KEDA, como la longitud de una cola de Azure Service Bus o de Storage. Con un mínimo de cero réplicas, una aplicación escala a cero cuando está inactiva y no pagas nada por cómputo hasta que llega tráfico.

Veamos un ejemplo práctico. Un equipo tiene dos necesidades. Primero, un script nocturno convierte archivos CSV y debe reintentarse si falla; lo implementan en ACI con la directiva de reinicio OnFailure y montan un recurso compartido de Azure Files. Segundo, una API orientada a clientes debe escalar con el tráfico y publicarse de forma segura. La colocan en Container Apps con entrada externa en el puerto 8080, una regla de escalado HTTP de 50 solicitudes simultáneas por réplica, mínimo 1 y máximo 10, y el modo de varias revisiones. La versión 2 recibe el 10 por ciento del tráfico; cuando los errores se mantienen bajos, la mueven al 100 por ciento.

Errores comunes: dejar un trabajo por lotes con la directiva predeterminada Always; esperar que ACI escale automáticamente o divida el tráfico; intentar dividir el tráfico en el modo de revisión única; esperar que un cambio de secreto cree una revisión nueva; y configurar la entrada como interna y luego preguntarse por qué la aplicación no es accesible desde internet.

Palabras clave del examen: 'ejecutar una vez y detenerse' significa Never; 'reintentar ante un error' significa OnFailure; 'sidecar que comparte localhost' significa un grupo de contenedores; 'canary', 'azul-verde' o 'dividir el tráfico' significa el modo de varias revisiones; 'escalar según los mensajes de una cola' significa una regla de escalado personalizada de KEDA; y 'no pagar nada cuando está inactiva' significa un mínimo de cero réplicas.

Términos clave

Grupo de contenedores (container group)
La unidad de implementación de ACI: contenedores en un mismo host que comparten ciclo de vida, red, dirección IP y volúmenes.
Directiva de reinicio (restart policy)
La configuración de ACI (Always, OnFailure o Never) que decide si los contenedores se reinician cuando terminan.
Entorno de Container Apps (Container Apps environment)
Límite compartido que proporciona red y registro para un conjunto de aplicaciones de contenedor.
Revisión (revision)
Instantánea inmutable de una versión de una aplicación de contenedor, que se crea cuando cambian opciones con ámbito de revisión.
Modo de varias revisiones (multiple revision mode)
Configuración de Container Apps que ejecuta varias revisiones a la vez para poder dividir el tráfico entre ellas.
Entrada (ingress)
La configuración de Container Apps que expone una aplicación de forma interna o externa por HTTP o TCP en un puerto de destino.
KEDA
Kubernetes Event-driven Autoscaling, el componente que usa Container Apps para reglas de escalado basadas en eventos, como la longitud de una cola.
Ejemplo real

Una aseguradora recibe documentos de reclamaciones en una cola de Service Bus. Ejecuta el servicio de procesamiento en Azure Container Apps con la entrada deshabilitada, una regla de escalado de KEDA de una réplica por cada 20 mensajes en cola, mínimo 0 y máximo 30. Por la noche la aplicación escala a cero y no cuesta nada de cómputo. Un script de migración puntual e independiente se ejecuta en Azure Container Instances con la directiva de reinicio Never, así que se ejecuta una vez, escribe su registro y deja de facturar.

Consejo para el examen: Los trabajos por lotes en ACI necesitan Never u OnFailure, no la directiva predeterminada Always. En Container Apps, dividir el tráfico requiere el modo de varias revisiones, y un mínimo de cero réplicas permite escalar a cero; ACI no tiene escalado automático.

Comprueba lo que sabes

Un contenedor en ACI ejecuta una carga de datos puntual, pero sigue ejecutándose y facturando después de terminar. ¿Qué debes cambiar?

Configura la directiva de reinicio en Never (u OnFailure si debe reintentarse ante errores), porque la predeterminada Always lo reinicia después de cada salida.

¿Qué comparten los contenedores de un mismo grupo de contenedores de ACI?

El host, el ciclo de vida, la red local (localhost), la dirección IP pública y la etiqueta DNS, y los volúmenes montados.

Quieres enviar el 20 por ciento del tráfico a una versión nueva de Container Apps. ¿Qué se requiere?

El modo de varias revisiones, con pesos de tráfico del 80 por ciento en la revisión anterior y del 20 por ciento en la nueva.

¿Actualizar un secreto en una aplicación de contenedor crea una revisión nueva?

No. Los secretos tienen ámbito de aplicación; solo los cambios con ámbito de revisión, como la imagen o las reglas de escalado, crean una revisión nueva.
