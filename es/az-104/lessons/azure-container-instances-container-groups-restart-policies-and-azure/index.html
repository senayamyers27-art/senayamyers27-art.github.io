Azure Container Instances (grupos de contenedores, directivas de reinicio) y Azure Container Apps (revisiones, entrada y reglas de escalado)

Azure ofrece varias formas de ejecutar contenedores sin administrar VM. Dos entran en el alcance de este examen: Azure Container Instances (ACI), para ejecutar contenedores de forma rápida y sencilla, y Azure Container Apps, para ejecutar microservicios y aplicaciones web con escalado, revisiones y entrada (ingress). Ninguna requiere que operes un clúster de Kubernetes.

ACI inicia un contenedor en segundos y factura por segundo según las vCPU y la memoria que usa. La unidad de implementación es un grupo de contenedores (container group): uno o más contenedores que se programan en el mismo host y comparten un ciclo de vida, una red local (se comunican entre sí en localhost), una dirección IP pública opcional con una etiqueta de nombre DNS y volúmenes montados, como un recurso compartido de Azure Files. Es similar a un pod de Kubernetes. Los grupos de varios contenedores se admiten para contenedores Linux y normalmente se implementan desde un archivo YAML o una plantilla ARM, por ejemplo un contenedor de la aplicación más un sidecar de registro. Un grupo de contenedores también se puede implementar en una subred de una red virtual para acceso privado.

Las directivas de reinicio de ACI controlan qué pasa cuando un contenedor termina. Always (la predeterminada) reinicia los contenedores cada vez que se detienen, lo que es adecuado para servicios de larga duración. OnFailure reinicia solo si el proceso termina con un error, lo que es adecuado para trabajos que deben reintentarse. Never ejecuta los contenedores una sola vez, lo que es adecuado para tareas puntuales como una compilación o una transformación de datos. Si ejecutas un trabajo por lotes con Always, se reinicia sin fin y sigue facturando.

Azure Container Apps es una plataforma sin servidor construida sobre Kubernetes y componentes de código abierto como KEDA (Kubernetes Event-driven Autoscaling), Dapr y Envoy, con la complejidad oculta. Las aplicaciones se ejecutan en un entorno de Container Apps, que proporciona un límite de red compartido y un destino de registros para un conjunto de aplicaciones. Configuras la imagen, la CPU y la memoria, los secretos, las variables de entorno y cómo escala la aplicación y recibe tráfico.

Una revisión (revision) es una instantánea inmutable de una versión de una container app. Cambiar configuraciones con ámbito de revisión, como la imagen o las reglas de escalado, crea una revisión nueva; cambiar configuraciones con ámbito de aplicación, como los secretos o la entrada, no la crea. En el modo de revisión única (single revision mode), la nueva revisión reemplaza a la anterior. En el modo de varias revisiones (multiple revision mode), varias revisiones se ejecutan a la vez y divides el tráfico por porcentaje entre ellas, para lanzamientos blue-green o canary, y reviertes moviendo el tráfico.

La entrada (ingress) controla cómo llega el tráfico a la aplicación. Puede estar deshabilitada, ser interna (accesible solo dentro del entorno o de su red virtual) o externa (accesible desde internet), para HTTP o TCP, en un puerto de destino que especificas. Las reglas de escalado definen cuántas réplicas se ejecutan entre un mínimo y un máximo: las reglas HTTP escalan según las solicitudes simultáneas, las reglas TCP según las conexiones, y las reglas personalizadas usan escaladores de KEDA, como la longitud de una cola en Azure Service Bus o en colas de Storage. Con un mínimo de cero réplicas, una aplicación escala a cero cuando está inactiva y no pagas nada por el proceso hasta que llega tráfico.

Términos clave

Container group (grupo de contenedores)
Una implementación de ACI de uno o más contenedores que comparten host, ciclo de vida, red y volúmenes.
Restart policy (directiva de reinicio)
La configuración de ACI Always, OnFailure o Never que decide si los contenedores se reinician después de terminar.
Revision (revisión)
Una instantánea inmutable de una versión de Container Apps, creada cuando cambian configuraciones con ámbito de revisión.
Ingress (entrada)
La configuración de Container Apps que expone una aplicación de forma interna o externa mediante HTTP o TCP.
Scale rule (regla de escalado)
Una regla de Container Apps basada en orígenes de eventos HTTP, TCP o KEDA que define el número de réplicas.
Ejemplo real

Un trabajo nocturno convierte facturas a PDF y debe ejecutarse una vez y detenerse. El administrador lo implementa en ACI con la directiva de reinicio Never. El portal de clientes, en cambio, se ejecuta en Container Apps con entrada HTTPS externa, una regla de escalado HTTP de 0 a 10 réplicas y el modo de varias revisiones, para que una versión nueva pueda recibir el 10 por ciento del tráfico antes del despliegue completo.

Consejo para el examen: Los trabajos por lotes en ACI deben usar Never u OnFailure, no el valor predeterminado Always. En Container Apps, dividir el tráfico requiere el modo de varias revisiones, y un número mínimo de réplicas de cero permite escalar a cero.

Comprueba lo que sabes

Dos contenedores deben compartir la red localhost y un volumen en ACI. ¿Qué implementas?

Un grupo de varios contenedores (Linux), normalmente desde un archivo YAML o una plantilla ARM.

Quieres enviar el 20 por ciento del tráfico a una versión nueva de una container app. ¿Qué se requiere?

El modo de varias revisiones, con pesos de tráfico definidos entre la revisión anterior y la nueva.

Una container app solo debe ser accesible por otras aplicaciones de su entorno. ¿Cómo configuras la entrada?

Habilita la entrada con visibilidad interna (no externa).
