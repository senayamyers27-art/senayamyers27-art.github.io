Plantillas ARM y archivos Bicep: interpretar y modificar, implementar, exportar una implementación como plantilla y convertir ARM JSON a Bicep

La infraestructura como código (IaC) consiste en describir los recursos de Azure en archivos y dejar que Azure Resource Manager (ARM) los cree, en lugar de hacer clic en el portal. Los archivos son repetibles, revisables y están bajo control de versiones, así que el mismo entorno se puede construir para desarrollo, pruebas y producción sin desviaciones. Los formatos nativos de Azure son las plantillas ARM, escritas en JSON (JavaScript Object Notation), y Bicep, un lenguaje más sencillo que se compila a ARM JSON. El examen espera que sepas leer ambos, cambiar un valor e implementar.

Una plantilla ARM tiene una estructura fija: $schema y contentVersion, luego parameters (valores que se proporcionan al implementar, como el nombre de una VM), variables (valores que se calculan dentro de la plantilla), resources (lo que se implementa, cada uno con type, apiVersion, name, location y properties) y outputs (valores que se devuelven después de la implementación). Las expresiones entre corchetes llaman a funciones de plantilla, por ejemplo [resourceGroup().location], [parameters('storageName')] o [concat(variables('prefix'), 'web')]. dependsOn indica el orden entre recursos, como implementar una red virtual antes que la interfaz de red que la usa. Los parámetros pueden tener allowedValues, un defaultValue y tipos como string, int y securestring para contraseñas. Bicep expresa lo mismo con menos sintaxis. Esta es una cuenta de almacenamiento con un parámetro y una salida:

param storageName string
param location string = resourceGroup().location

resource sa 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: storageName
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}

output blobEndpoint string = sa.properties.primaryEndpoints.blob

Léelo de arriba abajo: param declara entradas (con un valor predeterminado opcional), resource declara un recurso con un nombre simbólico (sa), un tipo y una versión de API, y output devuelve un valor. Bicep resuelve las dependencias automáticamente cuando un recurso hace referencia al nombre simbólico de otro, así que rara vez escribes dependsOn. Para cambiar la redundancia, editarías Standard_LRS a Standard_GRS; para dejar que elija quien implementa, agrega @allowed(['Standard_LRS','Standard_GRS']) param skuName string y usa skuName en el recurso. Las piezas reutilizables van en módulos (module net './network.bicep' = { ... }). Los valores de los parámetros pueden venir de un archivo de parámetros (.json o .bicepparam), de modo que una sola plantilla implemente desarrollo y producción con valores distintos. También puedes obtener una plantilla a partir de recursos existentes: en el portal, un grupo de recursos o un recurso tiene Exportar plantilla en Automatización, y una implementación anterior en la lista Implementaciones del grupo de recursos muestra su plantilla original. Las plantillas exportadas son un punto de partida; a menudo tienen nombres e identificadores fijos, incluyen propiedades de solo lectura y pueden no cubrir todos los tipos de recurso, así que parametrízalas y límpialas antes de reutilizarlas.

La conversión entre formatos se hace con la CLI de Bicep, incluida en la CLI de Azure. az bicep decompile --file main.json convierte una plantilla ARM JSON en un archivo Bicep en la medida de lo posible, que luego revisas corrigiendo las advertencias. az bicep build --file main.bicep compila Bicep a ARM JSON. Rara vez necesitas compilar manualmente, porque az deployment group create --resource-group rg-app --template-file main.bicep y New-AzResourceGroupDeployment -ResourceGroupName rg-app -TemplateFile main.bicep aceptan archivos .bicep directamente. La página Implementar una plantilla personalizada del portal acepta ARM JSON, ofrece plantillas de inicio rápido y te permite editar la plantilla y completar los parámetros antes de implementar.

Veamos un ejemplo práctico. Construiste a mano en el portal un entorno de aplicación web que funciona y ahora necesitas una copia idéntica para un equipo de pruebas. Abres el grupo de recursos, eliges Exportar plantilla, descargas el JSON y ejecutas az bicep decompile sobre él. El archivo Bicep tiene fijos el nombre de la aplicación web y la SKU del plan de App Service, así que los reemplazas por param appName string y param planSku string = 'B1', eliminas las propiedades de solo lectura que señaló el descompilador y creas un archivo test.bicepparam. Implementas en un grupo de recursos nuevo, compruebas la URL de salida y confirmas el archivo Bicep en el control de código fuente para que los cambios futuros se revisen.

Errores comunes: confundir parámetros (proporcionados al implementar) con variables (calculadas dentro de la plantilla); esperar que una plantilla exportada se implemente sin problemas sin editarla; ejecutar decompile cuando querías build; olvidar actualizar apiVersion o el nombre de la SKU exactamente como lo espera el proveedor de recursos; y escribir secretos directamente en lugar de usar parámetros securestring o referencias a Key Vault.

La redacción del examen sigue estas distinciones: 'valor elegido al implementar' apunta a un parámetro; 'valor devuelto después de la implementación' apunta a una salida; 'reutilizar recursos creados manualmente' apunta a Exportar plantilla; 'convertir JSON a Bicep' apunta a az bicep decompile; y '¿qué línea cambias para usar almacenamiento georredundante?' apunta al nombre de la sku.

Términos clave

Infraestructura como código (IaC)
Describir la infraestructura en archivos bajo control de versiones que un motor de implementación convierte en recursos reales.
Plantilla ARM (ARM template)
Un archivo JSON que declara recursos, parámetros, variables y salidas de Azure para que Azure Resource Manager los implemente.
Bicep
Un lenguaje específico de dominio para Azure que se compila a ARM JSON con una sintaxis más sencilla y dependencias automáticas.
Parámetro (parameter)
Un valor que se proporciona al implementar para que una misma plantilla se reutilice con entradas distintas.
Salida (output)
Un valor que devuelve una plantilla después de la implementación, como la URL de un punto de conexión.
Exportar plantilla (export template)
Una función del portal que genera una plantilla a partir de recursos existentes o muestra la plantilla de una implementación anterior.
Descompilar (decompile)
Convertir una plantilla ARM JSON a Bicep con az bicep decompile.
Ejemplo real

Un administrador construyó a mano en el portal un entorno de aplicación web que funciona y quiere recrearlo para un equipo de pruebas. Usa Exportar plantilla en el grupo de recursos, descompila el JSON a Bicep, reemplaza los nombres fijos por parámetros y lo implementa en un grupo de recursos nuevo con un archivo de parámetros de prueba; luego confirma el archivo Bicep en el control de código fuente.

Consejo para el examen: Ten claro de dónde vienen los valores: los parámetros se proporcionan al implementar, las variables se calculan en la plantilla y las salidas se devuelven después. az bicep decompile convierte JSON a Bicep; az bicep build hace lo contrario.

Comprueba lo que sabes

¿Qué sección de la plantilla editarías para que el tamaño de la VM se pueda elegir al implementar?

Agrega un parámetro para el tamaño en la sección parameters (param en Bicep) y haz referencia a él en el recurso de la VM.

¿Cómo conviertes una plantilla ARM JSON existente a Bicep?

Ejecuta az bicep decompile --file template.json y revisa el resultado.

¿Dónde puedes obtener una plantilla de recursos que se crearon manualmente en el portal?

En Exportar plantilla del grupo de recursos o del recurso (en Automatización); luego límpiala y parametrízala.

¿Necesitas compilar un archivo Bicep a JSON antes de implementarlo con la CLI de Azure?

No. az deployment group create y New-AzResourceGroupDeployment aceptan archivos .bicep y los compilan automáticamente.
