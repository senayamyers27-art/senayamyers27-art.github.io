Azure DNS: zonas públicas, delegación, conjuntos de registros, registros de alias; zonas DNS privadas con registro automático

Azure DNS hospeda zonas DNS (Domain Name System) en la red global de servidores de nombres de Microsoft, de modo que administras tus registros con las mismas herramientas, control de acceso basado en roles (RBAC), bloqueos y plantillas que el resto de Azure. No registra nombres de dominio por ti; compras un dominio a un registrador y luego hospedas su zona en Azure DNS. Hay dos tipos de zonas: las zonas públicas responden consultas desde internet y las zonas privadas responden solo para las redes virtuales (VNet) que vinculas a ellas.

Crear una zona pública como contoso.com le da un registro SOA (start of authority) y un conjunto de registros NS (name server) que enumera cuatro servidores de nombres de Azure asignados a esa zona, con nombres bajo azure-dns.com, azure-dns.net, azure-dns.org y azure-dns.info. La zona no hace nada hasta que delegas el dominio: en tu registrador, reemplaza las entradas de servidores de nombres del dominio por esos cuatro servidores de nombres de Azure. Cuando el cambio se propaga, los resolutores de internet preguntan a Azure DNS por tus registros. Puedes comprobarlo con nslookup -type=NS contoso.com. Delegar un subdominio funciona igual dentro del DNS: para hospedar dev.contoso.com como zona propia, quizá administrada por otro equipo, crea la zona secundaria y luego, en la zona principal contoso.com, agrega un conjunto de registros NS llamado dev que contenga los servidores de nombres de la zona secundaria.

Los registros se organizan en conjuntos de registros (record sets): todos los registros con el mismo nombre y tipo forman un conjunto, con un único TTL (time to live) que indica cuánto tiempo pueden los resolutores almacenar la respuesta en caché. Por ejemplo, el conjunto de registros A www puede contener varias direcciones IP. Los tipos admitidos incluyen A, AAAA, CNAME, MX, NS, PTR, SOA, SRV, TXT y CAA. Un conjunto de registros CNAME solo puede contener un registro, y no puedes crear un CNAME en el ápice de la zona (el propio contoso.com), que es una regla del estándar DNS. Los registros de alias (alias records) resuelven dos problemas. Un conjunto de registros de alias de tipo A, AAAA o CNAME apunta a un recurso de Azure en lugar de a un valor fijo: una dirección IP pública, un perfil de Traffic Manager, un punto de conexión de Azure Front Door o de CDN, u otro conjunto de registros de la misma zona. Cuando la IP del recurso cambia, el alias se actualiza automáticamente, así que nunca tienes registros huérfanos (dangling) que apunten a una dirección antigua. Y como un alias A puede estar en el ápice, puedes apuntar contoso.com a un perfil de Traffic Manager o a Front Door, algo que un CNAME no puede hacer.

az network dns zone create --resource-group rg-dns --name contoso.com
az network dns record-set a add-record --resource-group rg-dns \
  --zone-name contoso.com --record-set-name www --ipv4-address 20.50.10.4
az network dns zone show --resource-group rg-dns --name contoso.com --query nameServers

Una zona DNS privada, como corp.contoso.com, funciona solo dentro de Azure. La vinculas a las VNet con vínculos de red virtual; las VM de las VNet vinculadas pueden resolver sus registros mediante el DNS proporcionado por Azure. Al crear un vínculo puedes habilitar el registro automático (auto-registration), y entonces Azure crea y quita automáticamente registros A para las VM de esa VNet a medida que se crean, cambian de IP o se eliminan. Una VNet puede vincularse a muchas zonas privadas para resolución, pero solo una de ellas puede tener el registro automático habilitado para esa VNet. Las zonas privadas también son lo que hace que los puntos de conexión privados se resuelvan a sus IP privadas.

Veamos un ejemplo práctico. Contoso compra contoso.com a un registrador y quiere que Azure lo hospede. La administradora crea la zona pública, lee los cuatro servidores de nombres asignados y actualiza el registrador. Agrega un registro de alias A en el ápice que apunta a la IP pública del equilibrador de carga web, para que el registro siga a la IP automáticamente, y un CNAME www que apunta a contoso.com. Internamente, crea la zona privada corp.contoso.com, vincula la VNet hub con el registro automático habilitado y vincula los spokes solo para resolución. Las VM nuevas del hub aparecen como vm-name.corp.contoso.com sin que nadie edite registros.

Errores comunes: crear una zona pero nunca actualizar el registrador, de modo que nada se resuelve; intentar agregar un CNAME en el ápice; agregar un segundo valor a un conjunto CNAME; configurar un TTL muy largo justo antes de un cambio planificado, de modo que las respuestas antiguas permanecen en caché; esperar el registro automático en más de una zona privada por VNet; y olvidar vincular una zona privada a la VNet que la necesita.

En las preguntas del examen, 'los registros no se resuelven desde internet después de crear la zona' significa actualizar los registros NS en el registrador; 'apuntar el dominio raíz a Front Door o Traffic Manager' significa un registro de alias; 'evitar DNS huérfano cuando cambia una IP' significa alias; 'las VM obtienen nombres DNS automáticamente' significa una zona privada con registro automático; 'otro equipo administra un subdominio' significa una zona secundaria más delegación NS.

Términos clave

Zona DNS (DNS zone)
Contenedor de los registros DNS de un dominio, hospedado en Azure DNS como público o privado.
Delegación (delegation)
Apuntar un dominio o subdominio a servidores de nombres específicos con registros NS en el registrador o en la zona principal.
Conjunto de registros (record set)
Todos los registros DNS con el mismo nombre y tipo en una zona, que comparten un TTL.
TTL
Time to live, el número de segundos que los resolutores pueden almacenar en caché una respuesta DNS.
Registro de alias (alias record)
Conjunto de registros A, AAAA o CNAME que hace referencia a un recurso de Azure y se actualiza automáticamente cuando cambia su dirección.
Zona DNS privada (private DNS zone)
Zona que se resuelve solo para las VNet vinculadas a ella mediante vínculos de red virtual.
Registro automático (auto-registration)
Opción del vínculo de red virtual que mantiene automáticamente los registros A de las VM de esa VNet; una zona por VNet.
Ejemplo real

El sitio de marketing de una empresa pasa a estar detrás de Azure Front Door, y el equipo necesita que el dominio desnudo fabrikam.com, no solo www, llegue a él. Un CNAME no se puede colocar en el ápice de la zona, así que el administrador crea un registro de alias A en el ápice de la zona pública de Azure DNS que apunta al punto de conexión de Front Door. Cuando cambian las direcciones de Front Door, el registro las sigue automáticamente y no queda ninguna entrada huérfana que limpiar.

Consejo para el examen: Una zona no hace nada hasta que los registros NS del registrador apuntan a los servidores de nombres de Azure. Usa un registro de alias para el ápice de la zona y para seguir recursos de Azure, y recuerda que solo una zona privada por VNet puede tener el registro automático.

Comprueba lo que sabes

Creaste una zona pública en Azure DNS, pero sus registros no se resuelven en internet. ¿Qué falta?

La delegación: los registros de servidores de nombres del registrador deben cambiarse a los cuatro servidores de nombres de Azure DNS asignados a la zona.

¿Cómo puedes apuntar el ápice de la zona contoso.com a un perfil de Traffic Manager?

Crea un registro de alias A en el ápice que apunte al perfil de Traffic Manager, porque no se permite un CNAME en el ápice.

Una VNet está vinculada a tres zonas DNS privadas. ¿Cuántas pueden tener el registro automático habilitado para ella?

Solo una.

¿Cómo delegas dev.contoso.com a una zona independiente?

Crea la zona dev.contoso.com y luego agrega en la zona contoso.com un conjunto de registros NS llamado dev con los servidores de nombres de la zona secundaria.
