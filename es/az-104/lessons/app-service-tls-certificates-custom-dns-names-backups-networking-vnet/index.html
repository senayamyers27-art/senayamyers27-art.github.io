App Service: certificados TLS, nombres DNS personalizados, copias de seguridad, redes (integración con VNet, puntos de conexión privados) y ranuras de implementación

Cada aplicación de App Service recibe un nombre de host predeterminado, <app-name>.azurewebsites.net, con HTTPS ya funcionando mediante un certificado de Microsoft. Las aplicaciones de producción normalmente necesitan un dominio personalizado, su propio certificado TLS (Transport Layer Security), copias de seguridad, redes privadas y una forma segura de publicar actualizaciones. Todas estas configuraciones están en las hojas de la aplicación en el portal.

Para agregar un dominio personalizado, ve a Custom domains > Add custom domain. App Service te pide demostrar que eres dueño del dominio con un registro TXT llamado asuid.<subdomain> que contiene el ID de verificación de dominio de la aplicación, y asignar el nombre: un registro CNAME que apunte www a <app-name>.azurewebsites.net o, para un dominio raíz (apex) como contoso.com, un registro A que apunte a la dirección IP de la aplicación. Después de la validación, el nombre se agrega a la aplicación. Los dominios personalizados no están disponibles en el nivel Free.

Para usar HTTPS con el nombre personalizado, enlaza un certificado. Las opciones incluyen un certificado administrado de App Service gratuito (para dominios personalizados sin comodín, renovado automáticamente), un certificado de App Service que compras a través de Azure, un certificado importado desde Azure Key Vault o un archivo de certificado privado cargado (.pfx). Los enlaces suelen ser SNI (Server Name Indication) SSL, que permite que muchos certificados compartan una dirección IP; IP-based SSL da una dirección dedicada. Activa 'HTTPS Only' para que las solicitudes HTTP se redirijan a HTTPS, y establece la versión mínima de TLS.

Las copias de seguridad copian el contenido y la configuración de la aplicación y, opcionalmente, una base de datos conectada. En los niveles compatibles, la plataforma realiza copias de seguridad automáticas; las copias de seguridad personalizadas te permiten definir tu propia programación, retención y una cuenta de almacenamiento de destino, y puedes restaurar en la misma aplicación, en otra aplicación o en una ranura de implementación. Las copias de seguridad no sustituyen el control de código fuente, pero ayudan a recuperarse de un cambio erróneo.

Las redes tienen dos direcciones, y el examen comprueba que no las confundas. Entrante: un punto de conexión privado da a la aplicación una dirección IP privada en tu red virtual, para que los clientes lleguen a ella de forma privada, y luego puedes deshabilitar el acceso público; las restricciones de acceso (access restrictions) proporcionan reglas de permitir y denegar basadas en IP o en puntos de conexión de servicio. Saliente: la integración con VNet (VNet integration) permite que la aplicación llame a recursos dentro de una red virtual, como una base de datos con IP privada, a través de una subred dedicada y delegada. La integración con VNet no hace que la aplicación sea accesible de forma privada; un punto de conexión privado no permite que la aplicación llegue al interior de la red.

Las ranuras de implementación (nivel Standard y superiores) son aplicaciones activas con sus propios nombres de host, como <app-name>-staging.azurewebsites.net. Implementas en la ranura de staging, la pruebas y la precalientas, y luego la intercambias (swap) con producción; el intercambio cambia el enrutamiento sin tiempo de inactividad, y volver a intercambiar es una reversión instantánea. La configuración de la aplicación y las cadenas de conexión se mueven con el código durante un intercambio, a menos que las marques como 'deployment slot setting' (fijas o sticky), lo que las mantiene con la ranura, por ejemplo una cadena de conexión a la base de datos de staging. También puedes enrutar un porcentaje del tráfico de producción a una ranura para pruebas, y habilitar el intercambio automático (auto swap) después de la implementación.

Términos clave

Custom domain verification (verificación de dominio personalizado)
Demostrar a App Service la propiedad del dominio con un registro TXT asuid antes de asignar un registro CNAME o A.
App Service managed certificate (certificado administrado de App Service)
Un certificado TLS gratuito y renovado automáticamente para un dominio personalizado sin comodín en una aplicación.
VNet integration (integración con VNet)
Una característica saliente que permite que una aplicación llegue a recursos dentro de una red virtual a través de una subred delegada.
Private endpoint (App Service) (punto de conexión privado)
Una característica entrante que da a la aplicación una IP privada en una red virtual para que los clientes lleguen a ella de forma privada.
Deployment slot setting (configuración de ranura de implementación)
Una configuración de aplicación o cadena de conexión fija (sticky) que permanece con su ranura durante un intercambio.
Ejemplo real

Un equipo implementa la versión 2 de una API en la ranura de staging, que tiene una cadena de conexión fija que apunta a una base de datos de prueba. Después de que pasan las pruebas de humo, intercambian staging con producción; el código nuevo ahora usa la cadena de conexión fija de producción. Cuando aparece un error una hora después, vuelven a intercambiar para revertir al instante.

Consejo para el examen: La integración con VNet es solo saliente; un punto de conexión privado es solo entrante. Los intercambios de ranuras mueven la configuración a menos que esté marcada como deployment slot setting. Los dominios raíz usan un registro A; los subdominios normalmente un CNAME, ambos con un registro TXT asuid para la verificación.

Comprueba lo que sabes

Una aplicación debe llamar a una VM con SQL Server que solo tiene una IP privada en una red virtual. ¿Qué característica usas?

La integración con VNet, que proporciona acceso saliente desde la aplicación hacia la red virtual.

Después de un intercambio de ranuras, producción está usando la base de datos de staging. ¿Qué salió mal?

La cadena de conexión no estaba marcada como deployment slot setting, así que se intercambió junto con el código.

¿Qué registros DNS necesitas para asignar www.contoso.com a una aplicación?

Un CNAME de www al nombre azurewebsites.net de la aplicación y un registro TXT asuid.www con el ID de verificación.
