Azure Bastion: AzureBastionSubnet, SKU y acceso por explorador y cliente nativo

Abrir RDP (Remote Desktop Protocol, puerto 3389) o SSH (Secure Shell, puerto 22) a internet expone las máquinas virtuales (VM) a escaneos constantes y a ataques de adivinación de contraseñas. Azure Bastion es un servicio administrado que te permite conectarte a tus VM por RDP y SSH sin darles direcciones IP públicas. Te conectas a Bastion por TLS (Transport Layer Security) en el puerto 443, desde Azure Portal o desde un cliente nativo, y Bastion abre la sesión RDP o SSH hacia la IP privada de la VM dentro de la red virtual (VNet). Las VM no necesitan IP pública ni agente, lo que reduce drásticamente la superficie de ataque.

Una implementación dedicada de Bastion vive en su propia subred, que debe llamarse exactamente AzureBastionSubnet y ser como mínimo /26. El host de Bastion recibe una dirección IP pública Standard. Lo implementas en una VNet, a menudo un hub, y a partir del SKU Basic puede llegar a las VM de esa VNet y de las VNet emparejadas, así que un solo Bastion puede atender toda una red hub-and-spoke. Los grupos de seguridad de red (NSG) de las subredes de las VM deben permitir RDP o SSH desde el rango de direcciones de la subred de Bastion y, si colocas un NSG en la propia AzureBastionSubnet, debe permitir el tráfico entrante y saliente específico que Bastion necesita, como HTTPS 443 entrante desde internet y la etiqueta de servicio GatewayManager.

Bastion se ofrece en varios SKU, y las funciones crecen con cada uno. Developer es una opción gratuita y ligera para desarrollo y pruebas que usa infraestructura compartida, admite una conexión a la vez a VM de la misma VNet y no necesita AzureBastionSubnet; solo está disponible en algunas regiones. Basic es una implementación dedicada con RDP y SSH desde el portal y una capacidad fija. Standard agrega escalado del host (eliges el número de instancias para tener más sesiones simultáneas), compatibilidad con cliente nativo, conexión basada en IP (conectarte a una IP privada, incluidas máquinas locales accesibles desde la VNet), vínculos que se pueden compartir (shareable links), puertos personalizados y transferencia de archivos mediante el cliente nativo. Premium agrega funciones como la grabación de sesiones y la implementación solo privada sin IP pública. Puedes actualizar un SKU, por ejemplo de Basic a Standard, pero no bajarlo.

El acceso por explorador es el más sencillo: abre la VM en el portal, elige Connect > Bastion, escribe las credenciales (un nombre de usuario y contraseña, una clave privada SSH o una clave almacenada en Azure Key Vault) y la sesión se abre en una pestaña del explorador. Copiar y pegar texto funciona mediante el portapapeles de Bastion. El acceso con cliente nativo (Standard y Premium) te permite usar tu cliente local de Escritorio remoto o tu cliente SSH, que admite funciones como la transferencia de archivos y varios monitores. Primero debes habilitar la compatibilidad con cliente nativo en la configuración de Bastion; luego inicias sesión con la interfaz de línea de comandos (CLI) de Azure:

az network bastion rdp --name bas-hub --resource-group rg-hub \
  --target-resource-id /subscriptions/<sub>/resourceGroups/rg-app/providers/Microsoft.Compute/virtualMachines/vm-app1
az network bastion ssh --name bas-hub --resource-group rg-hub \
  --target-resource-id <vm-id> --auth-type AAD

Veamos un ejemplo práctico. Una empresa tiene una VNet hub y tres spokes emparejados con unas cuarenta VM, varias de las cuales tienen actualmente IP públicas con RDP abierto a internet. La administradora crea AzureBastionSubnet como 10.0.3.0/26 en el hub e implementa Bastion Standard con dos instancias. Habilita la compatibilidad con cliente nativo para que los ingenieros puedan copiar archivos con su propio cliente RDP, actualiza los NSG de los spokes para permitir TCP 3389 y 22 solo desde 10.0.3.0/26 y luego quita todas las IP públicas de las VM. Ahora los ingenieros se conectan desde el portal o con az network bastion rdp, y los escaneos de seguridad ya no muestran puertos de administración expuestos.

Errores comunes: llamar a la subred BastionSubnet o hacerla más pequeña que /26; suponer que las VM todavía necesitan una IP pública; bloquear RDP o SSH desde el rango de la subred de Bastion en el NSG de destino; esperar cliente nativo, transferencia de archivos o vínculos compartibles en el SKU Basic; elegir el SKU Developer para producción o para VNet emparejadas; y suponer que Bastion es una VM de salto (jump box) a la que tienes que aplicar parches, cuando es un servicio de plataforma totalmente administrado.

Las preguntas del examen suelen evaluar nombres, tamaños y funciones de los SKU. 'Conectarse a VM sin direcciones IP públicas a través de internet usando solo el puerto 443' significa Azure Bastion. '¿Qué nombre de subred y qué tamaño mínimo?' significa AzureBastionSubnet, /26 o mayor. 'Usar el cliente RDP local', 'cargar archivos', 'vínculo compartible', 'más sesiones simultáneas' o 'conectarse por dirección IP a un servidor local' significan Standard o superior. 'Grabar las sesiones' significa Premium. 'La opción más barata para una sola VM de desarrollo' apunta al SKU Developer.

Términos clave

Azure Bastion
Servicio PaaS administrado que proporciona RDP y SSH a las VM por TLS sin exponer IP públicas en las VM.
AzureBastionSubnet
El nombre exacto de subred, de al menos /26, requerido para una implementación dedicada de Bastion.
Compatibilidad con cliente nativo (native client support)
Función de Standard y Premium que te permite conectarte con tu cliente RDP o SSH local mediante la CLI de Azure.
Escalado del host (host scaling)
Agregar instancias de Bastion (Standard y superiores) para admitir más sesiones simultáneas.
Conexión basada en IP (IP-based connection)
Función de Standard para conectarse a una dirección IP privada, incluidas máquinas locales accesibles desde la VNet.
Vínculo compartible (shareable link)
Función de Standard que permite a un usuario conectarse a una VM específica mediante una URL sin acceso al portal.
SKU Developer
Opción de Bastion gratuita y de infraestructura compartida para desarrollo y pruebas, con una conexión a la vez y sin subred dedicada.
Ejemplo real

Un auditor señala que doce VM de producción aceptan RDP desde internet. El equipo de operaciones implementa Azure Bastion Standard en la VNet hub, confirma que los ingenieros pueden conectarse a cada spoke emparejado desde el portal y luego elimina las direcciones IP públicas de las VM. Los contratistas que no deben ver el portal reciben vínculos compartibles para las dos VM que mantienen, y los NSG ahora permiten los puertos de administración solo desde la subred de Bastion.

Consejo para el examen: La subred debe llamarse AzureBastionSubnet y ser /26 o mayor. El cliente nativo, la transferencia de archivos, el escalado del host, los vínculos compartibles y la conexión basada en IP requieren Standard o superior, y las VM de destino no necesitan IP pública.

Comprueba lo que sabes

¿Cuáles son el nombre y el tamaño mínimo de la subred para un host de Bastion dedicado?

AzureBastionSubnet, con un prefijo de /26 o mayor.

Los ingenieros quieren conectarse a través de Bastion con su propio cliente de Escritorio remoto. ¿Qué SKU y qué opción se necesitan?

Standard o Premium con la compatibilidad con cliente nativo habilitada; luego se conectan con az network bastion rdp.

¿Puede un solo Bastion en una VNet hub llegar a VM en VNet spoke emparejadas?

Sí, los SKU Basic y superiores pueden llegar a VM en VNet emparejadas; el SKU Developer no puede.

¿Qué puerto necesitan abierto de salida los usuarios para usar Bastion desde un explorador?

TCP 443, porque la sesión se ejecuta por TLS hacia el host de Bastion en lugar de directamente por 3389 o 22.
