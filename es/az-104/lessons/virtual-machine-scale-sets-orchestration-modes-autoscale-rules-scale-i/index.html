Virtual Machine Scale Sets: modos de orquestación, reglas de escalado automático y reducción horizontal

Un Virtual Machine Scale Set (VMSS, conjunto de escalado de máquinas virtuales) administra un grupo de máquinas virtuales (VM) con equilibrio de carga como un solo recurso. En lugar de crear cada VM a mano, describes el modelo una vez (imagen, tamaño, red, extensiones) e indicas al conjunto de escalado cuántas instancias debe ejecutar. Puede agregar y quitar instancias automáticamente según la demanda, repartirlas entre zonas de disponibilidad y dominios de error, e implementar actualizaciones. Los conjuntos de escalado son la respuesta estándar para niveles sin estado, como front-ends web, servidores de API y trabajadores por lotes, donde cualquier instancia puede atender cualquier solicitud y perder una no implica perder datos.

Los conjuntos de escalado tienen dos modos de orquestación, que se eligen al crearlos y no se pueden cambiar después. La orquestación Uniform usa instancias idénticas creadas a partir de un solo modelo; las administras principalmente mediante las API del propio conjunto de escalado, lo que resulta adecuado para cargas de trabajo grandes, homogéneas y sin estado. La orquestación Flexible, el modo predeterminado y recomendado para implementaciones nuevas, administra VM estándar de Azure que también puedes administrar individualmente con los comandos normales de VM, como az vm restart. Te permite mezclar tamaños de VM y capacidad Spot y normal, reparte las instancias entre dominios de error y zonas para lograr alta disponibilidad, y puede incorporar VM que agregues manualmente. Si una pregunta exige mezclar tamaños o tratar las instancias como VM comunes, la respuesta es Flexible.

El escalado automático (autoscale) se configura en la hoja Scaling del conjunto de escalado y usa el motor de escalado automático de Azure Monitor. Paso a paso: cambia de escalado manual a escalado automático personalizado; define un número mínimo, máximo y predeterminado de instancias; agrega una regla de escalado horizontal (scale-out), por ejemplo 'Percentage CPU promedio entre instancias mayor que 70 durante 10 minutos, aumentar el recuento en 2'; agrega la regla simétrica de reducción horizontal (scale-in), 'CPU promedio por debajo de 30 durante 10 minutos, disminuir el recuento en 1'. Cada regla tiene un período de enfriamiento (cool down; cinco minutos es lo habitual) durante el cual no ocurre ningún otro escalado para que la métrica se estabilice. Los perfiles basados en programación cambian los límites en horarios definidos, como un mínimo más alto durante el horario laboral, y el escalado automático predictivo puede escalar por adelantado ante patrones de carga diarios o semanales recurrentes.

az monitor autoscale create --resource-group rg-web --resource vmss-web \
  --resource-type Microsoft.Compute/virtualMachineScaleSets \
  --name as-web --min-count 2 --max-count 10 --count 2
az monitor autoscale rule create --resource-group rg-web --autoscale-name as-web \
  --condition "Percentage CPU > 70 avg 10m" --scale out 2
az monitor autoscale rule create --resource-group rg-web --autoscale-name as-web \
  --condition "Percentage CPU < 30 avg 10m" --scale in 1

El escalado automático nunca baja del mínimo ni supera el máximo, digan lo que digan las reglas, y usa el recuento predeterminado cuando las métricas no están disponibles. Las reglas pueden usar métricas del host como CPU, red y disco, métricas del sistema operativo invitado, métricas de Application Insights o incluso la longitud de una cola de almacenamiento o de Service Bus. Al reducir, la directiva de reducción horizontal (scale-in policy) decide qué instancias se eliminan. La directiva Default primero equilibra las instancias entre zonas de disponibilidad y dominios de error y luego elimina la instancia con el ID de instancia más alto. NewestVM elimina primero las instancias creadas más recientemente y OldestVM elimina las más antiguas, y ambas siguen equilibrando entre zonas. La protección de instancias marca una VM como 'protect from scale-in' para que el escalado automático nunca la elimine, o como 'protect from scale set actions' para que también quede excluida de actualizaciones y otras operaciones del conjunto de escalado. La directiva de actualización (upgrade policy) controla cómo llegan los cambios del modelo a las instancias existentes: Manual, Automatic (todas a la vez, con posible tiempo de inactividad) o Rolling (por lotes, con comprobaciones de estado entre ellos).

Veamos un ejemplo práctico. Un minorista ejecuta su tienda en línea en un conjunto de escalado Flexible de seis VM repartidas en tres zonas, detrás de un equilibrador de carga Standard con un sondeo de estado HTTP en /health. Las noches son de mucha actividad, así que el equipo define mínimo 3, máximo 15 y predeterminado 3, una regla de escalado horizontal al 70 por ciento de CPU y una regla de reducción al 30 por ciento, además de un perfil de programación que sube el mínimo a 6 de 17:00 a 22:00. Una VM aloja un trabajo de informes de larga duración, así que habilitan 'protect from scale-in' en ella. Eligen la directiva de reducción NewestVM porque las instancias nuevas tienen la caché menos precalentada. Cuando termina una promoción, el conjunto vuelve a tres instancias bien repartidas y la VM de informes sobrevive.

Errores comunes: crear solo una regla de escalado horizontal, de modo que el conjunto crece y nunca se reduce y la factura sigue subiendo; definir umbrales de escalado y de reducción demasiado cercanos (por ejemplo 60 y 55 por ciento), lo que provoca oscilaciones (flapping) porque cada acción desencadena la otra; esperar que el escalado automático baje del mínimo durante la noche; olvidar un sondeo de estado o la extensión Application Health, de modo que el tráfico llega a instancias que todavía están arrancando; y suponer que puedes cambiar de Uniform a Flexible más adelante, lo cual no es posible sin volver a implementar.

Las preguntas del examen suelen esconder la respuesta en una palabra clave. 'Mezclar tamaños de VM' o 'administrar las instancias como VM individuales' apunta a la orquestación Flexible. 'Los costos siguen subiendo después del pico' apunta a que falta una regla de reducción. '¿Qué VM se elimina primero?' apunta a la directiva de reducción, donde Default significa equilibrar zonas y luego el ID de instancia más alto. 'Garantizar que una VM específica nunca se elimine' apunta a la protección de instancias. 'Agregar capacidad antes del pico de las 9:00 todos los días' apunta a un perfil basado en programación o al escalado automático predictivo, no a una regla de métricas.

Términos clave

Virtual Machine Scale Set (VMSS)
Recurso de Azure que implementa y administra un grupo de VM idénticas o mixtas como una sola unidad con escalado integrado.
Orquestación Flexible (Flexible orchestration)
El modo recomendado del conjunto de escalado que administra VM estándar, permite tamaños mixtos y te deja administrar cada VM individualmente.
Orquestación Uniform (Uniform orchestration)
Modo del conjunto de escalado que crea instancias idénticas a partir de un modelo, administradas mediante las API del conjunto de escalado.
Regla de escalado automático (autoscale rule)
Condición sobre una métrica, como la CPU promedio en una ventana de tiempo, que agrega o quita instancias cuando se cumple.
Enfriamiento (cool down)
El período de espera después de una acción de escalado durante el cual el escalado automático no realiza otra acción para que las métricas se estabilicen.
Directiva de reducción horizontal (scale-in policy)
La configuración (Default, NewestVM u OldestVM) que decide qué instancias se eliminan cuando el conjunto se reduce.
Protección de instancias (instance protection)
Marca por instancia que impide que una VM sea eliminada por la reducción horizontal o afectada por acciones del conjunto de escalado.
Ejemplo real

Una empresa de medios procesa los videos subidos con un grupo de VM trabajadoras. Usa un conjunto de escalado con una regla de escalado automático basada en la longitud de su cola de almacenamiento: cuando esperan más de 500 mensajes, agrega 3 instancias; cuando esperan menos de 50, quita 1. El mínimo es 1 y el máximo es 20. Durante la noche la cola se vacía y el conjunto se reduce a una sola VM, mientras que un aumento de subidas por la mañana lo hace crecer de nuevo en minutos sin que nadie inicie sesión.

Consejo para el examen: Siempre combina una regla de escalado horizontal con una regla de reducción. La directiva de reducción Default equilibra entre zonas y dominios de error y luego elimina el ID de instancia más alto; usa la protección de instancias para conservar una VM específica y elige la orquestación Flexible cuando debas mezclar tamaños.

Comprueba lo que sabes

Un conjunto de escalado creció durante un pico de tráfico pero nunca se redujo después. ¿Cuál es la causa más probable?

No hay una regla de reducción horizontal; el escalado automático solo quita instancias cuando una regla se lo indica, así que cada regla de escalado horizontal necesita una regla de reducción correspondiente.

¿Qué modo de orquestación te permite mezclar tamaños de VM y administrar las instancias con comandos normales de VM?

La orquestación Flexible, que administra VM estándar de Azure y es el modo recomendado para implementaciones nuevas.

Con la directiva de reducción Default, ¿qué instancia se elimina?

Después de equilibrar entre zonas de disponibilidad y dominios de error, se elimina la instancia con el ID de instancia más alto.

¿Cómo evitas que el escalado automático elimine alguna vez una instancia en particular?

Habilita la protección de instancias en ella con 'protect from scale-in', o con 'protect from scale set actions' para excluirla también de las actualizaciones.
