Acceso basado en identidad para Azure Files (AD DS, Entra Domain Services, Entra Kerberos) con RBAC a nivel de recurso compartido y permisos NTFS

Azure Files ofrece recursos compartidos de archivos mediante SMB (Server Message Block), el mismo protocolo que usan los servidores de archivos de Windows. Puedes montar un recurso compartido con la clave de la cuenta de almacenamiento, pero eso da acceso total a todos los que conozcan la clave, como ser administrador del servidor de archivos. Para reemplazar de verdad un servidor de archivos, quieres que los usuarios inicien sesión con sus propias identidades y reciban solo el acceso que les corresponde. Eso es la autenticación basada en identidad.

Azure Files admite tres orígenes de identidad para SMB, y una cuenta de almacenamiento solo puede usar uno a la vez. Active Directory Domain Services (AD DS) local: unes la cuenta de almacenamiento a tu dominio como una cuenta de equipo o de inicio de sesión de servicio, normalmente con el módulo de PowerShell AzFilesHybrid, y los usuarios deben estar sincronizados con Microsoft Entra ID mediante Entra Connect. Los clientes necesitan línea de visión a un controlador de dominio. Microsoft Entra Domain Services: un dominio administrado en Azure; lo habilitas en la cuenta de almacenamiento, y los clientes unidos a ese dominio administrado usan Kerberos contra él. Microsoft Entra Kerberos: el propio Entra ID emite los tickets de Kerberos, así que los clientes unidos a Microsoft Entra o con unión híbrida pueden acceder a los recursos compartidos sin línea de visión a los controladores de dominio, lo que es ideal para trabajadores remotos. Está orientado a identidades de usuario híbridas sincronizadas desde AD.

Luego el acceso se comprueba en dos niveles, y ambos deben permitir la acción. Los permisos a nivel de recurso compartido (share-level) son roles de Azure RBAC asignados a usuarios o grupos de Entra en el recurso compartido o la cuenta de almacenamiento. Storage File Data SMB Share Reader da acceso de lectura, Storage File Data SMB Share Contributor da lectura, escritura y eliminación, y Storage File Data SMB Share Elevated Contributor además permite al usuario cambiar los permisos NTFS. También puedes establecer un permiso predeterminado a nivel de recurso compartido que se aplica a todas las identidades autenticadas, lo que te ahorra asignar roles si quieres que NTFS haga todo el trabajo detallado.

Los permisos a nivel de directorio y archivo son listas de control de acceso NTFS normales de Windows. Para establecerlos, un administrador monta el recurso compartido, comúnmente con la clave de la cuenta de almacenamiento para tener control total, y usa el Explorador de archivos o icacls para conceder, por ejemplo, Modify en la carpeta Finance al grupo Finance. Estas ACL viajan con los archivos y funcionan igual que en el servidor de archivos anterior.

El acceso efectivo es el más restrictivo de las dos capas. Un usuario con Share Contributor pero solo Read en la ACL NTFS de una carpeta solo puede leer esa carpeta. Un usuario con Full Control en NTFS pero sin rol a nivel de recurso compartido, y sin permiso predeterminado de recurso compartido, no puede abrir el recurso compartido en absoluto.

Recuerda que SMB usa el puerto TCP 445. La configuración de identidad no sirve de nada si la red del cliente bloquea el puerto 445 saliente, cosa que hacen muchos proveedores de servicios de internet y firewalls corporativos.

Términos clave

AD DS authentication (autenticación con AD DS)
Autenticación de Azure Files en la que la cuenta de almacenamiento está unida al Active Directory local y los usuarios presentan tickets Kerberos de AD.
Microsoft Entra Kerberos
Una opción de Azure Files en la que Entra ID emite tickets Kerberos para identidades híbridas, de modo que los clientes no necesitan línea de visión a un controlador de dominio.
Share-level permission (permiso a nivel de recurso compartido)
Un rol de Azure RBAC, como Storage File Data SMB Share Contributor, que controla el acceso a todo un recurso compartido de archivos.
NTFS permissions (permisos NTFS)
Listas de control de acceso de Windows en directorios y archivos del recurso compartido que proporcionan acceso detallado.
Ejemplo real

Una empresa retira su servidor de archivos local y traslada los datos a un recurso compartido de Azure Files. La cuenta de almacenamiento se une al dominio AD DS existente, el permiso predeterminado a nivel de recurso compartido se establece en Storage File Data SMB Share Contributor, y las ACL NTFS copiadas del servidor anterior siguen controlando quién puede abrir la carpeta de cada departamento. Los usuarios asignan la unidad con sus credenciales de dominio habituales.

Consejo para el examen: Dos capas: primero RBAC a nivel de recurso compartido, luego NTFS, y gana la más estricta. Solo se puede habilitar un origen de identidad por cuenta de almacenamiento. Elevated Contributor es el rol de recurso compartido que permite cambiar las ACL NTFS.

Comprueba lo que sabes

Un usuario tiene Storage File Data SMB Share Reader en un recurso compartido y permiso NTFS Full Control en una carpeta. ¿Puede crear archivos en la carpeta?

No. Reader a nivel de recurso compartido lo limita a solo lectura, y se aplica la capa más restrictiva.

¿Qué opción de identidad permite que laptops unidas a Entra fuera de la oficina lleguen a Azure Files con Kerberos sin contactar a un controlador de dominio?

La autenticación con Microsoft Entra Kerberos.

¿Cómo sueles establecer los permisos NTFS iniciales en un recurso compartido nuevo?

Montando el recurso compartido con acceso administrativo (por ejemplo, la clave de la cuenta de almacenamiento) y usando el Explorador de archivos o icacls para establecer las ACL.
