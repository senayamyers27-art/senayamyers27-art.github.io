Roles de Entra vs. roles de Azure RBAC, y roles del plano de datos como Storage Blob Data Reader

Azure tiene dos sistemas de roles separados, y las preguntas del examen suelen comprobar si sabes cuál se aplica. Los roles de Microsoft Entra controlan lo que alguien puede hacer en el propio directorio: crear usuarios, restablecer contraseñas, administrar grupos, registrar aplicaciones y configurar opciones del inquilino. Algunos ejemplos son Global Administrator, User Administrator, Groups Administrator, Helpdesk Administrator, License Administrator y Application Administrator. Su ámbito es todo el inquilino o una unidad administrativa (un contenedor que limita un rol a un subconjunto de usuarios o grupos), y se asignan en Microsoft Entra ID > Roles y administradores. Los roles de control de acceso basado en roles (RBAC) de Azure controlan lo que alguien puede hacer con los recursos de Azure: máquinas virtuales, cuentas de almacenamiento, redes. Sus ámbitos son grupos de administración, suscripciones, grupos de recursos y recursos, y se asignan en la hoja Control de acceso (IAM) de un recurso. Los dos sistemas son independientes. Un Global Administrator no tiene automáticamente acceso a las suscripciones, y el Owner de una suscripción no puede crear usuarios en Entra ID a menos que también tenga un rol de Entra adecuado. Al leer una pregunta, decide primero si la tarea afecta a objetos del directorio (usuarios, grupos, aplicaciones, licencias, contraseñas) o a recursos de Azure; eso determina de qué sistema de roles sale la respuesta.

Existe un puente. Un Global Administrator puede activar 'Administración de acceso para recursos de Azure' en Microsoft Entra ID > Propiedades. Eso le otorga el rol User Access Administrator en el ámbito raíz (/), por encima de todos los grupos de administración y suscripciones, de modo que puede concederse a sí mismo o a otros acceso a cualquier suscripción. Está pensado para recuperación, por ejemplo cuando el único Owner de la suscripción dejó la empresa, y se debe volver a desactivar después, porque la asignación elevada es muy poderosa y queda registrada para auditoría.

Azure RBAC a su vez se divide en dos planos. El plano de control (plano de administración) es la API de Azure Resource Manager (ARM) en management.azure.com: crear una cuenta de almacenamiento, cambiar su firewall, leer sus propiedades. El plano de datos son los datos dentro del recurso: blobs, mensajes de cola, entidades de tabla, secretos de Key Vault, a los que se accede mediante el punto de conexión propio del servicio, como <account>.blob.core.windows.net. Owner, Contributor y Reader son roles del plano de control. Sus definiciones contienen Actions pero no DataActions, así que por sí solos no conceden la lectura de un blob mediante autorización de Microsoft Entra.

Los roles del plano de datos cubren ese hueco. Storage Blob Data Reader permite a una entidad leer y listar contenedores y blobs; Storage Blob Data Contributor agrega escritura y eliminación; Storage Blob Data Owner además permite establecer listas de control de acceso (ACL) POSIX en Azure Data Lake Storage. Hay roles equivalentes para colas (Storage Queue Data Reader y Contributor), tablas (Storage Table Data Reader y Contributor), Azure Files sobre REST y Key Vault en su modelo de permisos RBAC (Key Vault Secrets User, Key Vault Administrator). Asígnalos en la cuenta de almacenamiento o, para aplicar privilegio mínimo, en el ámbito del contenedor, por ejemplo az role assignment create --role "Storage Blob Data Reader" --assignee <principal-id> --scope <storage-account-id>/blobServices/default/containers/reports.

Una sorpresa habitual es que un Contributor todavía puede leer blobs en el portal. Esto ocurre porque Contributor tiene la acción del plano de control Microsoft.Storage/storageAccounts/listKeys/action, de modo que el portal puede obtener la clave de la cuenta de almacenamiento y usar la autorización con clave compartida (Shared Key). Si deshabilitas el acceso con clave compartida en la cuenta, o cambias el método de autenticación del portal a 'Cuenta de usuario de Microsoft Entra', solo funcionan los roles del plano de datos. Un Reader, que no puede listar las claves, ve la cuenta pero recibe un error de autorización al abrir un contenedor, a menos que también tenga un rol de datos.

Veamos un ejemplo práctico. Una aplicación de análisis se ejecuta con una identidad administrada y solo necesita leer archivos del contenedor reports. Reader en la cuenta de almacenamiento no funcionaría, porque Reader no tiene acciones de datos y no puede listar las claves, y Contributor permitiría a la aplicación eliminar la cuenta. Asignas Storage Blob Data Reader en el contenedor reports a la identidad administrada. Por otro lado, una colega que es Owner de la suscripción pregunta por qué no puede restablecer la contraseña de un usuario; le explicas que Owner es un rol de RBAC y le asignas Helpdesk Administrator en Entra ID, con ámbito en una unidad administrativa de su departamento.

Errores comunes: esperar que Global Administrator pueda administrar VM de forma predeterminada; esperar que el Owner de la suscripción pueda administrar usuarios; elegir Reader o Contributor cuando la pregunta trata de leer el contenido de blobs con Entra ID; y olvidar desactivar el acceso elevado después de una recuperación.

La redacción del examen ayuda: 'restablecer contraseñas', 'crear usuarios', 'registrar aplicaciones' apuntan a roles de Entra. 'Crear VM', 'administrar redes' apuntan a Azure RBAC. 'Leer datos de blobs con Microsoft Entra ID' o 'una identidad administrada lee un contenedor' apunta a un rol Storage Blob Data. 'Solo quedaba un Owner, recuperar el acceso' apunta a elevar a un Global Administrator a User Access Administrator en el ámbito raíz.

Términos clave

Rol de Microsoft Entra
Un rol de directorio, como User Administrator, que controla la administración de objetos de Entra y de la configuración del inquilino.
Unidad administrativa (administrative unit)
Un contenedor de Entra que limita el ámbito de un rol de directorio a un subconjunto de usuarios, grupos o dispositivos.
Plano de control (control plane)
Operaciones de administración sobre recursos de Azure mediante Azure Resource Manager, reguladas por las Actions de los roles de RBAC.
Plano de datos (data plane)
Operaciones sobre los datos dentro de un recurso, como leer blobs, reguladas por las DataActions de los roles de RBAC.
Storage Blob Data Reader
Un rol integrado del plano de datos que permite leer y listar contenedores de blobs y blobs con autorización de Entra.
Acceso elevado (elevated access)
La opción de Global Administrator que otorga User Access Administrator en el ámbito raíz para recuperar el acceso a todas las suscripciones.
Ejemplo real

Una aplicación de análisis se ejecuta con una identidad administrada y necesita leer archivos de un contenedor. El administrador asigna Storage Blob Data Reader solo en ese contenedor. Darle Reader en la cuenta de almacenamiento no funcionaría, porque Reader no tiene acciones de datos y no puede listar las claves, y Contributor le daría mucho más poder del que necesita, incluida la capacidad de eliminar la cuenta.

Consejo para el examen: Las tareas de directorio (usuarios, grupos, contraseñas, registros de aplicaciones) apuntan a roles de Entra; las tareas sobre recursos apuntan a Azure RBAC. Si la pregunta trata de leer el contenido de blobs con Entra ID, busca un rol Storage Blob Data, no Reader ni Contributor.

Comprueba lo que sabes

Un usuario es Owner de una suscripción. ¿Puede restablecer la contraseña de otro usuario en Entra ID?

No por ese rol. Owner es un rol de Azure RBAC; restablecer contraseñas necesita un rol de Entra como Helpdesk Administrator o User Administrator.

Un usuario con Reader en una cuenta de almacenamiento recibe un error de autorización al abrir un contenedor en el portal. ¿Qué rol lo soluciona con privilegio mínimo?

Storage Blob Data Reader en el ámbito del contenedor o de la cuenta, que concede acceso de lectura en el plano de datos.

¿Cómo puede un Global Administrator recuperar el acceso a una suscripción cuyo único Owner se fue?

Activando 'Administración de acceso para recursos de Azure' para recibir User Access Administrator en el ámbito raíz, concediendo el rol necesario y luego desactivándolo.

¿Por qué un Contributor puede examinar blobs en el portal incluso sin un rol de datos?

Contributor puede listar las claves de la cuenta de almacenamiento, así que el portal usa la autorización con clave compartida; deshabilitar el acceso con clave compartida elimina esa vía.
