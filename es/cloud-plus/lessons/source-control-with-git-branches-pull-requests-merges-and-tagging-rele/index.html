Control de versiones con Git: ramas, solicitudes de incorporación de cambios, fusiones y etiquetado de lanzamientos

El control de versiones anota cada cambio en el código y la configuración: quién cambió qué, cuándo y por qué, con la capacidad de volver atrás. Git es la herramienta estándar, y en las operaciones de nube contiene no solo el código de aplicación sino también la infraestructura como código, las definiciones de canalizaciones, los scripts y las políticas.

Un repositorio de Git contiene el historial completo como una serie de confirmaciones (commits). Cada confirmación es una instantánea con un autor, un mensaje y un hash único. El ciclo básico es editar archivos, prepararlos (stage) con git add, anotarlos con git commit -m "mensaje", y compartirlos con git push a un repositorio remoto alojado en una plataforma como GitHub, GitLab, Bitbucket o el servicio de repositorios de un proveedor de nube. git pull obtiene y fusiona los cambios de los demás, y git clone copia un repositorio a tu máquina.

Las ramas (branches) te permiten trabajar en un cambio sin afectar a la línea principal de código. Creas una rama de funcionalidad (git switch -c feature/add-cache), confirmas en ella, y cuando está lista, la fusionas de vuelta en la rama principal. Las estrategias comunes incluyen el desarrollo basado en tronco (trunk-based), con ramas de corta vida fusionadas a main con frecuencia, y modelos con ramas develop y release de larga vida. Las ramas de corta vida causan menos conflictos dolorosos.

Una solicitud de incorporación de cambios (pull request, llamada merge request en algunas plataformas) pide fusionar una rama en otra. Muestra la diferencia (diff), ejecuta comprobaciones automatizadas de la canalización de CI y permite a los compañeros de equipo revisar y comentar. Las reglas de protección de rama en main pueden exigir aprobaciones, comprobaciones exitosas y ningún empuje directo, lo que te da revisión por pares y separación de funciones también para los cambios de infraestructura. Al fusionar, Git crea una confirmación de fusión que une los historiales o, con la fusión por rebase o squash, coloca los cambios encima como un historial lineal más limpio. Un conflicto de fusión ocurre cuando ambas ramas cambiaron las mismas líneas; una persona debe decidir el resultado correcto.

Las etiquetas (tags) marcan confirmaciones específicas, normalmente lanzamientos, con nombres como v2.3.0 siguiendo el versionado semántico (mayor.menor.parche). Las etiquetas anotadas (git tag -a v2.3.0 -m "Release 2.3.0") anotan quién etiquetó y cuándo. Las canalizaciones a menudo compilan e implementan desde etiquetas, así que siempre sabes exactamente qué código se está ejecutando. Nunca confirmes secretos: una vez empujados, permanecen en el historial, y deben rotarse incluso tras eliminarlos.

Términos clave

Commit (confirmación)
Una instantánea anotada de los cambios en Git, con un autor, un mensaje y un hash único.
Branch (rama)
Una línea de desarrollo independiente dentro de un repositorio.
Pull request (solicitud de incorporación de cambios)
Una solicitud para fusionar una rama en otra, usada para la revisión y las comprobaciones automatizadas.
Merge conflict (conflicto de fusión)
Una situación en la que dos ramas cambian las mismas líneas y Git no puede combinarlas automáticamente.
Tag (etiqueta)
Un puntero con nombre a una confirmación específica, normalmente usado para marcar una versión de lanzamiento.
Ejemplo real

Un ingeniero cambia un módulo de Terraform en una rama, abre una solicitud de incorporación de cambios, y la canalización ejecuta comprobaciones de formato, un escaneo de seguridad y un plan. Un compañero de equipo revisa la salida del plan y aprueba. Tras fusionar, el gestor de lanzamientos etiqueta la confirmación v1.8.0 y la canalización implementa exactamente esa versión etiquetada.

Consejo para el examen: Las solicitudes de incorporación de cambios con protección de rama proporcionan revisión, comprobaciones automatizadas y un rastro de auditoría. Las etiquetas identifican los lanzamientos. Si se confirma un secreto, eliminarlo en una nueva confirmación no basta; rota el secreto, porque permanece en el historial.

Comprueba lo que sabes

¿Cuál es el propósito de la protección de rama en la rama main?

Detener los empujes directos y exigir solicitudes de incorporación de cambios con aprobaciones y comprobaciones exitosas antes de que los cambios se fusionen.

¿Por qué etiquetar los lanzamientos?

Las etiquetas marcan la confirmación exacta que se lanzó, para que puedas reconstruir, implementar o revertir a una versión conocida.
