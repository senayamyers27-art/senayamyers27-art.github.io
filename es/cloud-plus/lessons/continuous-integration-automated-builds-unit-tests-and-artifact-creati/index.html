Integración continua: compilaciones automatizadas, pruebas unitarias y creación de artefactos

La integración continua (CI) es la práctica de fusionar los cambios de los desarrolladores en una rama compartida con frecuencia, a menudo varias veces al día, y compilar y probar automáticamente cada cambio. El objetivo es encontrar los problemas de integración en minutos, mientras el cambio es pequeño y está fresco en la mente del desarrollador, en lugar de semanas después durante una fase de integración dolorosa.

Un servidor o servicio de CI vigila el repositorio. Cuando se empuja código o se abre una solicitud de incorporación de cambios, un webhook dispara una canalización definida en un archivo almacenado con el código, comúnmente YAML. La canalización se ejecuta en agentes de compilación o ejecutores (runners), que pueden estar alojados por el servicio o ser autoalojados. Los pasos típicos son: obtener el código, instalar dependencias, compilar o empaquetar, ejecutar linters y análisis estático, ejecutar pruebas unitarias, ejecutar escaneos de seguridad sobre el código y las dependencias, y producir un artefacto de compilación. Si algún paso falla, la canalización se detiene e informa del fallo en la solicitud de incorporación de cambios, y el equipo trata una compilación rota como la máxima prioridad.

Las pruebas unitarias (unit tests) comprueban piezas pequeñas de código, como una sola función, de forma aislada, usando dependencias falsas o simuladas (mocked). Se ejecutan en segundos y dan retroalimentación precisa. Las pruebas de integración comprueban que los componentes funcionan juntos, como la aplicación con una base de datos real, y tardan más, así que pueden ejecutarse más tarde en la canalización. Los informes de cobertura de código muestran cuánto código ejercitan las pruebas, aunque una cobertura alta no garantiza buenas pruebas.

La salida de una compilación exitosa es un artefacto: un paquete implementable como una imagen de contenedor, un archivo zip para una función, un binario compilado o un paquete de biblioteca. Almacena los artefactos en un repositorio de artefactos o un registro de contenedores con una versión única, por ejemplo el número de compilación o el hash de la confirmación de Git, para que cada artefacto pueda rastrearse hasta el código fuente exacto que lo produjo. Compila una vez, implementa muchas: el mismo artefacto se mueve por prueba, preproducción y producción, en lugar de reconstruirse en cada entorno, lo que podría introducir diferencias.

Mantén las compilaciones rápidas y reproducibles: fija (pin) las versiones de las dependencias, almacena en caché las dependencias y ejecuta las pruebas en paralelo.

Términos clave

Continuous integration (integración continua)
Fusionar con frecuencia los cambios de código en una rama compartida con compilación y prueba automáticas de cada cambio.
Build agent / runner (agente de compilación / ejecutor)
La máquina o el contenedor que ejecuta los trabajos de la canalización.
Unit test (prueba unitaria)
Una prueba automatizada que comprueba una pequeña unidad de código de forma aislada.
Build artifact (artefacto de compilación)
La salida versionada e implementable de una compilación, como una imagen de contenedor o un paquete.
Artifact repository (repositorio de artefactos)
Un servicio de almacenamiento para salidas de compilación versionadas, como un repositorio de paquetes o un registro de contenedores.
Ejemplo real

Un desarrollador abre una solicitud de incorporación de cambios que modifica la función de precios. En cuatro minutos la canalización de CI compila el código, ejecuta 600 pruebas unitarias y falla porque una prueba de redondeo de descuentos se rompe. El desarrollador la corrige antes de la revisión, y la compilación fusionada produce una imagen de contenedor etiquetada con el hash de la confirmación en el registro.

Consejo para el examen: La CI trata de compilar y probar cada cambio automáticamente y producir un artefacto versionado. Compila una vez y promociona el mismo artefacto; no reconstruyas para cada entorno.

Comprueba lo que sabes

¿Por qué etiquetar los artefactos de compilación con el hash de la confirmación o el número de compilación?

Para que cada artefacto sea identificable de forma única y rastreable hasta el código fuente exacto que lo produjo.

¿En qué se diferencian las pruebas unitarias de las pruebas de integración?

Las pruebas unitarias comprueban piezas pequeñas de código de forma aislada y se ejecutan rápido; las pruebas de integración comprueban que los componentes funcionan juntos con dependencias reales y tardan más.
