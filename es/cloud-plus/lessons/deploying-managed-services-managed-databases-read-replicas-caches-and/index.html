Implementación de servicios gestionados: bases de datos gestionadas, réplicas de lectura, cachés y Kubernetes gestionado

Los servicios gestionados dejan que el proveedor haga el trabajo indiferenciado, como instalar software, parchear, hacer copias de seguridad y conmutación por error, para que tu equipo pueda centrarse en la aplicación. Cloud+ espera que sepas qué ofrece cada servicio gestionado común y qué configuras tú todavía.

Un servicio de base de datos relacional gestionado ejecuta motores como MySQL, PostgreSQL o SQL Server por ti. Eliges la versión del motor, el tamaño de la instancia, el almacenamiento, la ubicación de red (normalmente subredes privadas), la retención de copias de seguridad y la ventana de mantenimiento. El proveedor se encarga del parcheo durante esa ventana, de las copias de seguridad automatizadas con restauración a un punto en el tiempo, y de la alta disponibilidad mediante una opción multi-AZ que mantiene un standby síncrono en otra zona y conmuta automáticamente. Tú todavía administras los usuarios de la base de datos, el esquema, el rendimiento de las consultas y quién puede alcanzar el punto de conexión.

Las réplicas de lectura (read replicas) son copias de la base de datos que reciben los cambios de forma asíncrona y atienden consultas de solo lectura. Escalan las cargas de trabajo intensivas en lectura, como los informes o las búsquedas de catálogo de productos, y pueden colocarse en otra región para atender a usuarios lejanos o para DR. Como la replicación es asíncrona, las réplicas pueden ir ligeramente por detrás, así que las escrituras y las lecturas que deben estar al día van al primario. No confundas los dos roles: un standby multi-AZ existe para la disponibilidad, mientras que una réplica de lectura existe para el escalado de lectura, aunque algunas réplicas pueden promocionarse durante un desastre.

Una caché gestionada, que normalmente ejecuta Redis o Memcached, mantiene los datos leídos con frecuencia en memoria para respuestas de microsegundos a milisegundos. La aplicación revisa primero la caché y consulta la base de datos solo en caso de fallo (miss), un patrón llamado caché-a-un-lado (cache-aside). Las cachés reducen la carga y la latencia de la base de datos, y también almacenan datos de sesión. Configura tiempos de expiración sensatos para que los datos en caché no queden obsoletos.

Kubernetes gestionado ejecuta el plano de control de Kubernetes por ti: el servidor de API, el planificador y el almacén de estado del clúster son parcheados, escalados y hechos de alta disponibilidad por el proveedor. Tú administras los nodos de trabajo o grupos de nodos (a menos que elijas una opción de nodos sin servidor), las cargas de trabajo que implementas, la red y el control de acceso, y las actualizaciones de versión del clúster que disparas dentro de la ventana de soporte del proveedor.

Términos clave

Managed database (base de datos gestionada)
Un servicio de base de datos en el que el proveedor se encarga de la instalación, el parcheo, las copias de seguridad y la conmutación por error.
Read replica (réplica de lectura)
Una copia de solo lectura de una base de datos actualizada de forma asíncrona, usada para escalar las lecturas.
Multi-AZ standby
Una copia de base de datos replicada de forma síncrona en otra zona, usada para la conmutación por error automática, no para lecturas.
Cache-aside (caché a un lado)
Un patrón en el que la aplicación lee primero de la caché y carga desde la base de datos en caso de fallo.
Managed Kubernetes (Kubernetes gestionado)
Un servicio en el que el proveedor opera el plano de control de Kubernetes mientras tú administras las cargas de trabajo y normalmente los nodos de trabajo.
Ejemplo real

Las páginas de producto de un minorista sobrecargan su base de datos durante las promociones. El equipo añade dos réplicas de lectura para las consultas de catálogo y una caché Redis gestionada para los productos más vistos, dejando el primario libre para los pedidos. La CPU de la base de datos cae fuertemente y los tiempos de página bajan.

Consejo para el examen: El escalado de lectura apunta a réplicas de lectura o una caché; la conmutación por error automática dentro de una región apunta a un despliegue multi-AZ. Con los servicios gestionados el proveedor parchea el motor, pero tú todavía eres dueño de los usuarios, los datos, el acceso de red y los ajustes de las copias de seguridad.

Comprueba lo que sabes

¿Por qué un usuario podría ver datos ligeramente desactualizados al leer de una réplica de lectura?

La replicación a las réplicas de lectura es asíncrona, así que puede haber retraso de replicación (lag) respecto al primario.

En Kubernetes gestionado, ¿qué opera el proveedor?

El plano de control (servidor de API, planificador, almacén de datos del clúster); el cliente administra las cargas de trabajo y normalmente los nodos de trabajo.
