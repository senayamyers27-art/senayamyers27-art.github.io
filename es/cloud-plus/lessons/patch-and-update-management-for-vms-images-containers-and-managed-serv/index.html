CompTIA Cloud+ CV0-004

Gestión de parches y actualizaciones para VMs, imágenes, contenedores y servicios gestionados

El software sin parchear es una de las formas más comunes en que los atacantes entran, así que la gestión de parches es un deber operativo central. En la nube, qué parcheas y cómo depende del modelo de servicio y de si tu infraestructura es mutable o inmutable.

Para las VMs que administras (IaaS), eres responsable del sistema operativo y el software instalado. Un proceso de parcheo tiene etapas claras: inventariar lo que se ejecuta, obtener información de parches de los proveedores y de los escaneos de vulnerabilidades, priorizar por gravedad y exposición, probar en un entorno no de producción, implementar en una ventana de mantenimiento, verificar el éxito e informar de la conformidad. Los servicios de gestión de parches de la nube y las herramientas de gestión de configuración pueden escanear las instancias contra una línea base de parches, agruparlas en grupos de parches e instalar las actualizaciones según un horario. Parchea en oleadas, manteniendo parte de cada capa en funcionamiento para que el servicio permanezca disponible, y ten un plan de reversión como una instantánea tomada antes de parchear.

Con infraestructura inmutable parcheas imágenes en lugar de servidores. Una canalización de imágenes construye una nueva imagen dorada con las últimas actualizaciones, la prueba y publica una nueva versión; los grupos de autoescalado reemplazan entonces las instancias antiguas por nuevas. Esto evita la desviación y da una reversión limpia. Los contenedores funcionan igual: no parcheas dentro de un contenedor en ejecución. Reconstruye la imagen a partir de una imagen base actualizada, vuelve a escanearla, empújala al registro con una etiqueta nueva y vuelve a implementar. Escanear las imágenes en el registro revela qué cargas de trabajo en ejecución usan una imagen base con una vulnerabilidad recién anunciada.

Para los servicios gestionados, el proveedor parchea la plataforma subyacente, pero tú todavía tienes opciones. Las bases de datos y los clústeres de Kubernetes gestionados aplican los parches menores en una ventana de mantenimiento que tú defines, y las actualizaciones de versión mayor normalmente las disparas tú y necesitan pruebas porque pueden cambiar el comportamiento. Lee las notificaciones del proveedor, elige ventanas en horas de bajo tráfico y mantén los motores dentro de las versiones admitidas.

Los parches de emergencia para vulnerabilidades activamente explotadas pueden saltarse partes del proceso normal bajo un procedimiento de cambio expedito, pero aun así deberían probarse rápido, documentarse y revisarse después.

Términos clave

Patch baseline (línea base de parches)
El conjunto definido de parches, por clasificación y gravedad, que las instancias deben tener instalados para ser conformes.
Maintenance window (ventana de mantenimiento)
Un periodo programado en el que las actualizaciones y los cambios pueden aplicarse con impacto mínimo.
Image pipeline (canalización de imágenes)
Un proceso automatizado que construye, prueba y publica imágenes de máquina o de contenedor actualizadas.
Base image (imagen base)
La imagen de partida, como una imagen de SO o de entorno de ejecución de un lenguaje, sobre la que se construyen las imágenes de aplicación.
Emergency change (cambio de emergencia)
Un proceso de cambio expedito para correcciones urgentes, revisado tras la implementación.
Ejemplo real

Se anuncia una vulnerabilidad crítica en una biblioteca común. El escáner del registro de contenedores señala 14 imágenes construidas sobre la imagen base afectada. El equipo actualiza la etiqueta de la imagen base en sus Dockerfiles, reconstruye mediante CI, vuelve a implementar con una actualización progresiva y confirma que el escáner ya no informa del hallazgo.

Consejo para el examen: Los contenedores y las instancias inmutables se parchean reconstruyendo y volviendo a implementar, nunca parcheando en el lugar. Para los servicios gestionados, el proveedor parchea la plataforma, pero tú eliges la ventana de mantenimiento y planificas las actualizaciones de versión mayor.

Comprueba lo que sabes

¿Cómo parcheas una biblioteca vulnerable dentro de un contenedor en ejecución?

Reconstruyes la imagen del contenedor con la versión corregida o una imagen base actualizada, luego vuelves a implementar los contenedores desde la nueva imagen.

¿Por qué tomar una instantánea antes de parchear una VM?

Para tener un punto de reversión rápido si el parche rompe el sistema.
