Identidades de carga de trabajo: roles de instancia, identidades gestionadas y cuentas de servicio en lugar de claves almacenadas

Las aplicaciones también necesitan llamar a las API de la nube: un servidor web lee de un almacenamiento de objetos, una función escribe en una cola, una canalización despliega infraestructura. La forma antigua era crear un usuario, generar una clave de acceso de larga duración y ponerla en un archivo de configuración o una variable de entorno. Esas claves se filtran constantemente, a través de código subido a repositorios públicos, imágenes de contenedor, registros y copias de seguridad, y a menudo siguen siendo válidas durante años.

Las identidades de carga de trabajo eliminan los secretos almacenados. En lugar de una clave, la propia carga de trabajo obtiene una identidad, y la plataforma le proporciona credenciales de corta vida que rotan automáticamente. En AWS adjuntas un rol de IAM a una instancia EC2 mediante un perfil de instancia, o a una función o tarea de contenedor; el código que usa el SDK encuentra credenciales temporales desde el servicio de metadatos de la instancia sin ninguna configuración. En Azure, una identidad gestionada (asignada por el sistema, atada al ciclo de vida de un recurso, o asignada por el usuario, una identidad independiente que puede compartirse) permite que una VM, un servicio de aplicaciones o una función obtenga tokens de Microsoft Entra ID. En Google Cloud, una cuenta de servicio adjunta a una VM o servicio hace el mismo papel.

Luego concedes a esa identidad permisos de privilegio mínimo, exactamente como harías con una persona: esta función solo puede escribir en esta cola. Como las credenciales son temporales y se obtienen de la plataforma, no hay nada que rotar a mano y nada útil que robar de un repositorio de código.

Importan dos puntos más. Primero, el punto de conexión de metadatos que entrega las credenciales debe protegerse. Los ataques de falsificación de solicitud del lado del servidor (SSRF) intentan engañar a una aplicación para que solicite el servicio de metadatos y devuelva credenciales; las versiones de metadatos más nuevas y orientadas a sesión, como IMDSv2 de AWS, requieren un token y bloquean ese ataque simple, así que hazlas obligatorias. Segundo, para las cargas de trabajo fuera de la nube, como un sistema de CI u otra nube, usa la federación de identidades de carga de trabajo con OIDC: el sistema externo presenta un token firmado y lo intercambia por credenciales de nube temporales. Las claves de cuenta de servicio deberían ser un último recurso, estrictamente restringidas y rotadas.

Términos clave

Workload identity (identidad de carga de trabajo)
Una identidad asignada a una aplicación o recurso en lugar de a una persona, usada para acceder a otros servicios.
Instance profile / instance role (perfil de instancia / rol de instancia)
Una forma de adjuntar un rol de IAM a una VM para que el software en ella reciba credenciales temporales.
Managed identity (identidad gestionada)
Una identidad de Azure para un recurso, gestionada por la plataforma, que obtiene tokens sin secretos almacenados.
Service account (cuenta de servicio)
Una cuenta no humana usada por aplicaciones y servicios, notablemente en Google Cloud y Kubernetes.
Instance metadata service (servicio de metadatos de la instancia)
Un punto de conexión local en una VM que proporciona configuración y credenciales temporales al software que se ejecuta en ella.
Ejemplo real

Un escaneo de seguridad encuentra una clave de acceso en un archivo de configuración en una imagen de servidor web. El equipo borra la clave, adjunta a la instancia un rol que permite leer solo el bucket de la aplicación y elimina la línea de configuración. El SDK usa automáticamente las credenciales temporales del rol, y las imágenes futuras no contienen ningún secreto.

Consejo para el examen: Siempre que una pregunta describa claves de acceso almacenadas en código, archivos de configuración o variables de entorno para una aplicación que se ejecuta en la nube, la respuesta es un rol de instancia, una identidad gestionada o una cuenta de servicio con privilegio mínimo.

Comprueba lo que sabes

¿Por qué los roles de instancia son más seguros que las claves de acceso en un archivo de configuración?

Proporcionan credenciales de corta vida que rotan automáticamente y nunca se almacenan en archivos ni en código donde puedan filtrarse.

¿Cuál es la diferencia entre una identidad gestionada asignada por el sistema y una asignada por el usuario?

Una identidad asignada por el sistema está atada a un recurso y se borra con él; una identidad asignada por el usuario es un recurso separado que puede adjuntarse a varios recursos.
