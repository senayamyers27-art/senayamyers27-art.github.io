Validación posterior al despliegue: pruebas de humo, comprobaciones de estado, líneas base de rendimiento y documentación

Un despliegue no está terminado cuando la canalización se pone en verde. La validación posterior al despliegue confirma que la nueva versión funciona para los usuarios y que tienes la información para darle soporte.

Las pruebas de humo (smoke tests) son comprobaciones rápidas y superficiales de que las funciones más importantes funcionan justo tras el despliegue: la página de inicio carga, un usuario puede iniciar sesión, una búsqueda devuelve resultados, se puede realizar un pedido con una cuenta de prueba. El nombre viene de las pruebas de hardware: enciéndelo y mira si echa humo. No son una suite de regresión completa; se ejecutan en minutos y responden si es seguro enviar usuarios al lanzamiento. Automatízalas en la canalización para que un fallo pueda disparar una reversión automática.

Las comprobaciones de estado (health checks) se ejecutan de forma continua. Los balanceadores de carga y los orquestadores sondean un punto de conexión como /health y retiran o reinician las instancias que fallan. Las comprobaciones de estado superficiales solo confirman que el proceso responde; las comprobaciones de estado profundas también prueban dependencias como la base de datos. Las comprobaciones profundas detectan más problemas pero pueden hacer que cada instancia se marque como no sana a la vez cuando una dependencia compartida tiene un fallo momentáneo, así que elige con cuidado. En Kubernetes, las sondas de disponibilidad (readiness probes) deciden si un pod recibe tráfico y las sondas de vitalidad (liveness probes) deciden si debe reiniciarse.

Una línea base de rendimiento (performance baseline) es un registro del comportamiento normal: tiempos de respuesta, tasas de error, uso de CPU y memoria, rendimiento y carga de la base de datos bajo tráfico típico. Tras un lanzamiento, compara las nuevas métricas con la línea base. Una versión que funciona pero es un 40 por ciento más lenta, o que usa el doble de memoria, es un problema que quieres encontrar ahora en lugar de durante el próximo pico. Registra una nueva línea base tras cambios significativos para que las comparaciones futuras sigan siendo significativas.

Por último, actualiza la documentación: el diagrama de arquitectura, el inventario de configuración y versiones, los runbooks para incidentes comunes, el registro de cambios con qué se implementó y cuándo, y cualquier nueva monitorización o alerta. Una buena documentación convierte el próximo incidente de una investigación en una consulta.

Términos clave

Smoke test (prueba de humo)
Una comprobación rápida de las funciones críticas justo tras el despliegue para confirmar que el sistema básicamente funciona.
Health check (comprobación de estado)
Un sondeo recurrente usado por los balanceadores de carga u orquestadores para decidir si una instancia está sana.
Performance baseline (línea base de rendimiento)
Una medida registrada del rendimiento normal usada para detectar regresiones.
Readiness probe (sonda de disponibilidad)
Una comprobación de Kubernetes que decide si un pod debe recibir tráfico.
Runbook
Procedimientos documentados paso a paso para operar o resolver problemas de un sistema.
Ejemplo real

Tras un lanzamiento, la canalización ejecuta pruebas de humo que inician sesión con una cuenta de prueba y realizan un pedido de prueba. Pasan, pero el panel muestra que el tiempo de respuesta del percentil 95 de la página de pago es el doble de la línea base. El equipo revierte, encuentra un índice de base de datos que faltaba y vuelve a implementar al día siguiente.

Consejo para el examen: Las pruebas de humo son comprobaciones rápidas de las rutas críticas justo tras el despliegue; las líneas base te dicen si el rendimiento cambió. No puedes decir que algo es más lento sin una línea base con la que comparar.

Comprueba lo que sabes

¿Cuál es la diferencia entre una prueba de humo y una prueba de regresión completa?

Una prueba de humo comprueba rápidamente unas pocas funciones críticas tras el despliegue; las pruebas de regresión comprueban a fondo que las funcionalidades existentes siguen funcionando y tardan mucho más.

¿Por qué deberías registrar una línea base de rendimiento antes y después de los cambios?

Para detectar regresiones comparando las nuevas métricas con el comportamiento normal conocido, y para fijar umbrales de alerta significativos.
