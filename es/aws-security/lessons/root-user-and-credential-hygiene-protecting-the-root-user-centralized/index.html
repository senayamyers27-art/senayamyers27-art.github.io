AWS Certified Security – Specialty SCS-C03

Usuario root e higiene de credenciales: proteger el usuario root, acceso root centralizado, eliminar claves de largo plazo y credential reports

Cada cuenta de AWS tiene un usuario root con control total, incluidas tareas que ninguna política IAM puede otorgar, como cambiar ajustes de la cuenta, cerrarla o restaurar una bucket policy de S3 bloqueada. Protegerlo, y limpiar las credenciales de largo plazo en general, es higiene básica que el examen espera.

Para una cuenta independiente: usa una contraseña fuerte y única, activa MFA (idealmente una llave de hardware o una passkey, y puedes registrar varios dispositivos), nunca crees access keys de root y elimina las que existan, mantén el correo de root en una lista de distribución monitoreada y alerta sobre los inicios de sesión de root con una regla de EventBridge o una alarma de CloudWatch. Usa root solo para las pocas tareas que lo requieren.

En AWS Organizations, la administración centralizada del acceso root va más allá. Desde la cuenta de administración o un administrador delegado, puedes eliminar las credenciales root (contraseña, access keys, dispositivos MFA y certificados de firma) de las cuentas miembro, y las cuentas nuevas se pueden crear sin ellas. Cuando se necesita una tarea privilegiada de root, como desbloquear una bucket policy de S3 que niega a todos o eliminar una política de SQS mal configurada, la cuenta central usa sts:AssumeRoot para obtener una sesión root de corta duración limitada a esa tarea. Las SCPs también pueden negar acciones del usuario root en las cuentas miembro.

Para los usuarios IAM, el credential report es un CSV que lista cada usuario con el estado, la antigüedad y el último uso de su contraseña y sus access keys, y su estado de MFA. Úsalo para encontrar claves más antiguas que tu política de rotación, claves sin uso y usuarios sin MFA. Los datos de último acceso de IAM muestran qué servicios usa realmente un usuario o rol. La mejor corrección es reemplazar los usuarios IAM por Identity Center para personas y roles para cargas de trabajo, y luego eliminar las access keys restantes. Donde las claves deban quedarse, rótalas creando una segunda clave, actualizando la aplicación y luego desactivando y eliminando la anterior.

Términos clave

Usuario root
Identidad creada junto con una cuenta de AWS, con acceso total que las políticas IAM no pueden limitar en una cuenta independiente.
Acceso root centralizado
Función de Organizations para eliminar las credenciales root de las cuentas miembro y realizar tareas de root mediante sesiones de corta duración.
sts:AssumeRoot
Acción de STS que se usa para obtener una sesión root limitada a una tarea en una cuenta miembro.
Credential report
Informe CSV de IAM con las contraseñas, access keys, su antigüedad y el estado de MFA de todos los usuarios.
Ejemplo real

Una empresa con 150 cuentas habilita el acceso root centralizado y elimina las contraseñas de root de todas las cuentas miembro. Meses después, un ingeniero deja a todos sin acceso a un bucket con una política mal hecha; el equipo de seguridad usa una sesión root desde la cuenta de administrador delegado para eliminar la bucket policy, y CloudTrail registra la acción.

Consejo para el examen: Las access keys de root nunca deberían existir. Para muchas cuentas miembro, la respuesta moderna es la administración centralizada del acceso root, no un cajón lleno de dispositivos MFA.
