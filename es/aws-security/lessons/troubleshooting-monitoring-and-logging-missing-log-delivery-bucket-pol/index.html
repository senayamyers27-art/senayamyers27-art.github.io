AWS Certified Security – Specialty SCS-C03

Solución de problemas de monitoreo y registro: entrega de logs faltante, bucket policies para la entrega de logs y key policies de KMS para logs cifrados

El registro de seguridad falla en silencio. Un trail que deja de entregar, un flow log sin datos o una alarma que nunca se dispara pueden pasar semanas sin que nadie lo note, por eso el examen incluye preguntas de diagnóstico. La buena noticia es que la mayoría de las fallas vienen de unas pocas causas.

Empieza por los permisos del servicio que entrega. CloudTrail, VPC Flow Logs, Config, ELB y otros escriben en S3 como un service principal (por ejemplo cloudtrail.amazonaws.com o delivery.logs.amazonaws.com) o mediante un rol IAM que tú proporcionas. La bucket policy de destino debe permitir que ese principal escriba (s3:PutObject) y a menudo que lea la ACL del bucket, idealmente con condiciones aws:SourceArn y aws:SourceAccount. Cuando alguien endurece la política de un bucket central, o una RCP o SCP agrega un deny, la entrega puede romperse. Los flow logs hacia CloudWatch Logs necesitan un rol IAM que el servicio pueda asumir con permiso para crear log streams y escribir eventos.

Luego revisa el cifrado. Si los archivos de log se cifran con una customer managed key de KMS, la key policy debe permitir que el servicio la use, en el caso de CloudTrail kms:GenerateDataKey* con un encryption context del trail, y los lectores necesitan kms:Decrypt. Una clave deshabilitada o pendiente de eliminación también detiene la entrega. Los log groups de CloudWatch Logs cifrados con KMS necesitan que la key policy permita al service principal de logs de esa región.

Después revisa lo obvio: ¿el trail sigue registrando (aws cloudtrail get-trail-status muestra IsLogging y el último error de entrega)?, ¿el bucket todavía existe?, ¿el recurso está en la región que estás mirando?, ¿los data events realmente están seleccionados?, ¿un event pattern o un metric filter usó un nombre de campo ligeramente incorrecto? Los servicios también informan errores: CloudTrail muestra LatestDeliveryError y los flow logs muestran un estado de entrega. Recorre destino, permisos, cifrado y configuración, en ese orden.

Términos clave

Service principal
Identificador como cloudtrail.amazonaws.com que representa a un servicio de AWS en las políticas.
get-trail-status
Llamada a la API de CloudTrail que muestra si un trail está registrando y los errores de entrega recientes.
aws:SourceArn
Condition key que vincula el permiso de un service principal a un recurso específico, como un trail.
Encryption context
Datos adicionales de clave-valor vinculados a una operación de KMS, usados en políticas y registrados en CloudTrail.
Ejemplo real

Después de asignar una nueva clave de KMS al organization trail, get-trail-status muestra LatestDeliveryError: InsufficientEncryptionPolicyException. El ingeniero agrega una sentencia a la key policy que permite a cloudtrail.amazonaws.com llamar a kms:GenerateDataKey* con el ARN del trail en la condición del encryption context, y la entrega se reanuda.

Consejo para el examen: Cuando los logs se detienen justo después de un cambio, el cambio casi siempre es la causa: una edición de la bucket policy, una clave de KMS nueva o una SCP o RCP nueva. Busca la respuesta que restaura el acceso del service principal de la forma más acotada.

Comprueba lo que sabes

Un flow log hacia CloudWatch Logs no muestra datos. ¿Qué elemento de IAM debes revisar?

El rol IAM asignado al flow log: su trust policy debe permitir al servicio de flow logs y sus permisos deben permitir crear log streams y escribir eventos.

¿Qué comando de CloudTrail muestra el último error de entrega?

aws cloudtrail get-trail-status.
