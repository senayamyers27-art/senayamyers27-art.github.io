AWS Certified Security – Specialty SCS-C03

Responder a credenciales IAM comprometidas: desactivar access keys, revocar sesiones de roles y revisar la actividad en CloudTrail

Las credenciales filtradas están entre los incidentes más comunes en AWS: claves subidas a un repositorio público, guardadas en un script o robadas de una instancia a través del servicio de metadatos. Hallazgos de GuardDuty como UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration o avisos de AWS Health sobre claves expuestas suelen iniciar la respuesta.

Para la access key de largo plazo de un usuario IAM, primero desactiva la clave (ponla en Inactive) en lugar de eliminarla. Eso detiene al atacante de inmediato y conserva el ID de la clave, que necesitas para buscar en los logs y que puedes reactivar si el hallazgo era incorrecto. Si la contraseña también podría estar comprometida, restablécela y revisa los dispositivos MFA. Puedes adjuntar al usuario una política de deny explícito como protección adicional.

Las credenciales de rol son temporales, así que no hay clave que desactivar. Para un rol, usa Revoke active sessions en la consola de IAM. Agrega una política en línea que niega todas las acciones cuando aws:TokenIssueTime es anterior al momento en que revocaste, así que cada token robado deja de funcionar, mientras que quienes llaman legítimamente, como las instancias EC2, simplemente obtienen credenciales nuevas. Para una instancia cuyas credenciales de rol fueron exfiltradas, corrige también la causa, por ejemplo exigiendo IMDSv2.

Luego dimensiona el daño con CloudTrail. Busca por el ID de la access key o por el nombre de sesión del rol cada llamada hecha desde la filtración, y busca persistencia: nuevos usuarios IAM, access keys, roles, cambios en trust policies, funciones Lambda, instancias EC2 en regiones inusuales o cambios en el registro. Elimina lo que creó el atacante, rota los secretos que pudo leer y revisa la facturación por minado de criptomonedas. Por último, elimina la clave vieja y corrige la causa raíz, por ejemplo moviendo la carga de trabajo a un rol y agregando escaneo de secretos al repositorio.

Términos clave

Desactivar access key
Poner una access key de IAM en Inactive para que deje de funcionar pero siga existiendo para la investigación.
Revoke active sessions
Acción de un rol IAM que niega todas las solicitudes de sesiones emitidas antes de un momento elegido.
aws:TokenIssueTime
Condition key que contiene el momento en que se emitieron las credenciales temporales.
Persistencia
Cambios que hace un atacante para mantener el acceso, como crear usuarios, claves o roles nuevos.
Ejemplo real

La access key de un desarrollador aparece en un repositorio público. Quien responde la desactiva, descubre en CloudTrail que el atacante creó un usuario IAM nuevo y lanzó instancias con GPU en tres regiones, elimina el usuario y las instancias, borra la clave después de la revisión y pasa al desarrollador a IAM Identity Center con credenciales de corta duración.

Consejo para el examen: Primero desactiva, después elimina. Para roles, la respuesta es revocar sesiones, no eliminar el rol, lo que rompería cargas de trabajo sanas.

Comprueba lo que sabes

¿Por qué desactivar primero una access key filtrada en lugar de eliminarla?

Desactivarla detiene su uso de inmediato pero conserva el ID de la clave para búsquedas en CloudTrail y permite reactivarla si la alerta era falsa.

Después de revocar las sesiones de un rol, ¿qué pasa con una instancia EC2 que lo usa?

Sigue funcionando, porque obtiene credenciales nuevas emitidas después del momento de la revocación.
