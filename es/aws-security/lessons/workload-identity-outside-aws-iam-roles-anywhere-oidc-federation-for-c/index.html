AWS Certified Security – Specialty SCS-C03

Identidad de cargas de trabajo fuera de AWS: IAM Roles Anywhere, federación OIDC para pipelines de CI/CD y EKS Pod Identity

Las access keys de largo plazo en servidores y pipelines están entre las causas más comunes de brechas. AWS ofrece formas para que las cargas de trabajo fuera de AWS, y las cargas en Kubernetes, obtengan credenciales de corta duración.

IAM Roles Anywhere es para servidores, contenedores y aplicaciones que corren fuera de AWS, por ejemplo en un centro de datos, y que pueden tener un certificado X.509. Creas un trust anchor que apunta a tu autoridad certificadora, ya sea AWS Private CA o el certificado de tu propia CA, y un profile que lista qué roles se pueden usar y cualquier session policy. La trust policy del rol permite a rolesanywhere.amazonaws.com y puede revisar atributos del certificado, como el common name del sujeto. En el servidor, el credential helper firma una solicitud con la clave privada del certificado y recibe credenciales temporales. Revocas el acceso revocando certificados (con una CRL importada) o deshabilitando el trust anchor.

Los sistemas de CI/CD como GitHub Actions, GitLab y otros emiten tokens OIDC para cada job. Registras el proveedor como un proveedor de identidad OIDC de IAM y creas un rol cuya trust policy permite sts:AssumeRoleWithWebIdentity desde ese proveedor, con condiciones sobre los claims de audiencia (aud) y sujeto (sub) del token, por ejemplo solo la rama main de un repositorio. El pipeline asume el rol en cada ejecución y nunca guarda claves. Omitir la condición sub o usar comodines es un error grave, porque cualquier repositorio de esa plataforma podría asumir tu rol.

Dentro de Amazon EKS, los pods no deberían usar el rol de instancia del nodo. EKS Pod Identity asocia un rol IAM con una service account de Kubernetes mediante la API de EKS, y el Pod Identity Agent entrega las credenciales a los pods. El método anterior, IAM Roles for Service Accounts (IRSA), usa el proveedor OIDC del clúster y AssumeRoleWithWebIdentity. Ambos dan a cada carga de trabajo su propio rol de mínimo privilegio.

Términos clave

IAM Roles Anywhere
Servicio que permite a cargas de trabajo fuera de AWS cambiar certificados X.509 por credenciales temporales de un rol.
Trust anchor
Certificado de CA que Roles Anywhere usa para verificar los certificados de las cargas de trabajo.
Federación OIDC
Confiar en tokens de un proveedor OpenID Connect para asumir un rol IAM con AssumeRoleWithWebIdentity.
EKS Pod Identity
Función de EKS que asocia un rol IAM a una service account de Kubernetes para dar credenciales a los pods.
Ejemplo real

Una empresa elimina todas las access keys de su sistema de builds. Los workflows de GitHub Actions asumen un rol de despliegue solo cuando el sub del token es repo:acme/web:ref:refs/heads/main, y los servidores batch on-premises usan Roles Anywhere con certificados de AWS Private CA.

Consejo para el examen: Fuera de AWS con certificados: Roles Anywhere. Pipelines con tokens OIDC: proveedor de identidad OIDC más un rol con condiciones sub estrictas. Pods en EKS: Pod Identity o IRSA, nunca el rol del nodo.

Comprueba lo que sabes

¿De qué protege la condición sub en una trust policy OIDC de GitHub?

De que otros repositorios o ramas de la misma plataforma asuman tu rol.

¿Cómo revocas el acceso de un servidor que usa Roles Anywhere?

Revocando su certificado mediante una CRL importada o deshabilitando el trust anchor o el profile.
