AWS Certified Security – Specialty SCS-C03

Credenciales temporales: roles IAM, STS AssumeRole, trust policies, external IDs y el problema del confused deputy

Los roles IAM son la forma preferida de otorgar acceso en AWS porque usan credenciales temporales que expiran solas. AWS Security Token Service (STS) emite estas credenciales cuando un principal de confianza asume el rol.

Un rol tiene dos políticas. La trust policy es una política basada en recursos que dice quién puede asumir el rol, con un Principal como una cuenta de AWS, un rol específico, un servicio como ec2.amazonaws.com o lambda.amazonaws.com, o un proveedor de identidad federado. Las políticas de permisos dicen qué puede hacer el rol una vez asumido. sts:AssumeRole devuelve un access key ID, una secret access key y un session token, válidos durante un tiempo que puede llegar a la duración máxima de sesión del rol. Las variantes incluyen AssumeRoleWithSAML y AssumeRoleWithWebIdentity para federación. Servicios como EC2 (mediante instance profiles), Lambda y ECS asumen roles por ti y rotan las credenciales automáticamente.

Para el acceso entre cuentas, el rol en la cuenta B confía en la cuenta A o en un principal específico de ella, y la política de identidad de la cuenta A debe permitir sts:AssumeRole sobre el ARN de ese rol. CloudTrail en ambas cuentas registra la llamada AssumeRole, y el nombre de sesión ayuda a rastrear quién la usó. El role chaining, asumir un segundo rol desde una sesión de rol, limita la sesión a una hora.

El problema del confused deputy ocurre cuando una parte de confianza con acceso a muchos clientes es engañada para usar ese acceso en el cliente equivocado. Para terceros, exige una condición sts:ExternalId única en la trust policy, acordada con el proveedor para cada cliente. Para servicios de AWS que actúan en tu nombre, por ejemplo SNS recibiendo eventos de S3 o un servicio escribiendo logs en tu bucket, agrega condiciones aws:SourceArn y aws:SourceAccount en las políticas de recursos para que solo tus recursos puedan activar el acceso del servicio.

Términos clave

Trust policy
Política basada en recursos de un rol que especifica quién puede asumirlo.
AWS STS
Security Token Service, que emite credenciales temporales para roles y usuarios federados.
External ID
Valor único exigido en la trust policy de un rol para evitar ataques de confused deputy por parte de terceros.
Confused deputy
Situación en la que se engaña a una entidad de confianza para que use sus permisos en nombre de una parte no autorizada.
Ejemplo real

Un proveedor de análisis de costos necesita acceso de lectura a los datos de facturación de un cliente. El cliente crea un rol que confía en la cuenta de AWS del proveedor con la condición sts:ExternalId igual a un valor que el proveedor generó para este cliente. Otro cliente del proveedor que conozca el ARN del rol no puede hacer que el proveedor lo asuma, porque no tiene el external ID correcto.

Consejo para el examen: Un proveedor externo que asume un rol: external ID. Un service principal de AWS que escribe o publica en tu recurso: aws:SourceArn y aws:SourceAccount. Ambos evitan problemas de confused deputy.

Comprueba lo que sabes

¿Qué dos cosas se necesitan para que un principal de la cuenta A asuma un rol en la cuenta B?

La trust policy del rol en B debe permitir al principal o a la cuenta A, y una política de identidad en A debe permitir sts:AssumeRole sobre el rol.

¿Cuál es la duración máxima de sesión en el role chaining?

Una hora.
