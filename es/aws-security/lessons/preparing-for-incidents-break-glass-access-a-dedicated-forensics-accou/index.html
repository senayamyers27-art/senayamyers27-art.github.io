AWS Certified Security – Specialty SCS-C03

Prepararse para incidentes: acceso break-glass, una cuenta forense dedicada y game days para probar el plan

La mayor parte de la respuesta a incidentes ocurre antes del incidente. Si quienes responden no pueden iniciar sesión, no tienen permisos o no tienen un lugar seguro para analizar la evidencia, cada minuto del evento se gasta en arreglar el acceso en lugar del problema.

Prepara el acceso de antemano. Crea roles de respuesta a incidentes en cada cuenta, desplegados con StackSets o Control Tower, que quienes responden puedan asumir solo cuando haga falta, con permisos para leer logs, tomar snapshots de volúmenes, cambiar security groups y revocar sesiones. Mantén una ruta break-glass para cuando falle el inicio de sesión normal, por ejemplo si el proveedor de identidad está caído: unos pocos usuarios IAM o credenciales root con MFA de hardware, credenciales guardadas en un lugar sellado y auditado, y alarmas en cada uso para que cualquier inicio de sesión se investigue.

Configura una cuenta forense en su propia OU con SCPs estrictas. La evidencia, como snapshots de EBS, imágenes de memoria y exportaciones de logs, se copia allí, a buckets de S3 con versionado y Object Lock, para que no se pueda cambiar. Las estaciones o instancias de análisis forense corren allí, aisladas de las redes de producción, a menudo desde una AMI preparada con herramientas de análisis. Asegúrate de que las key policies de KMS permitan a la cuenta forense usar las claves que protegen los snapshots, o no podrás copiar la evidencia cifrada cuando importe.

Por último, prueba. Los tabletop exercises recorren un escenario en discusión. Los game days ejecutan una simulación realista en un entorno que no es de producción: genera sample findings de GuardDuty, siembra una access key señuelo o haz público un bucket de prueba, y observa si la detección se dispara, la automatización corre, se avisa a las personas y los runbooks funcionan. Registra los tiempos, corrige las brechas y actualiza el plan. El examen favorece las respuestas que preparan de antemano el acceso, el aislamiento y el almacenamiento de evidencia, y que prueban el plan con regularidad.

Términos clave

Acceso break-glass
Credenciales de emergencia, muy protegidas y monitoreadas, que se usan solo cuando fallan las rutas de acceso normales.
Cuenta forense
Cuenta de AWS aislada que se usa para guardar evidencia y ejecutar análisis lejos de producción.
Game day
Evento de práctica que simula un incidente para probar personas, procesos y herramientas.
Tabletop exercise
Recorrido en discusión de un escenario de incidente para probar roles y decisiones.
Ejemplo real

En un game day, el equipo genera un sample finding de GuardDuty de exfiltración de credenciales. La regla de EventBridge se dispara, pero la Lambda de respuesta falla porque falta el rol de respuesta en una cuenta nueva. Corrigen el StackSet para que cada cuenta nueva reciba el rol y repiten la prueba con éxito.

Consejo para el examen: Busca pistas de 'antes de un incidente': las respuestas correctas crean de antemano roles, claves, cuentas y runbooks. Una respuesta que otorga acceso amplio solo después de que empieza el incidente, o que comparte credenciales de manera informal, es una trampa.

Comprueba lo que sabes

¿Por qué hay que considerar las key policies de KMS al preparar una cuenta forense?

Los snapshots cifrados solo se pueden copiar y usar allí si la key policy permite a la cuenta forense usar la clave.

¿Qué debe ocurrir cada vez que se usan credenciales break-glass?

Se dispara una alarma para revisar el uso, y luego las credenciales se rotan y se vuelven a sellar.
