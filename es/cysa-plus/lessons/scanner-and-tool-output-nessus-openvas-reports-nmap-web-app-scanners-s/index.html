CompTIA CySA+ CS0-004

Salida de escáneres y herramientas: reportes de Nessus/OpenVAS, nmap, escáneres de aplicaciones web, SAST, DAST, SCA, fuzzing, herramientas de postura en la nube

Gran parte del dominio de vulnerabilidades de CySA+ trata de leer resultados: dado un reporte de escaneo o el resultado de un comando, ¿qué te dice y qué deberías hacer después? Las preguntas basadas en desempeño (performance-based) a menudo te muestran directamente la salida de las herramientas.

Nessus (un escáner comercial) y OpenVAS (el escáner de código abierto de la suite Greenbone) producen reportes similares. Cada hallazgo normalmente indica el ID del plugin o de la prueba, un título, la severidad (critical, high, medium, low, informational), una puntuación CVSS, el host y el puerto afectados, una descripción, la evidencia que vio el escáner (como un banner de versión), referencias a identificadores CVE y una solución recomendada. Lee con atención la sección de evidencia: te dice si el hallazgo se basa en un número de versión, en una prueba real o en un parche faltante, lo que te ayuda a juzgar su exactitud.

nmap es la herramienta estándar de descubrimiento de red y escaneo de puertos. Las opciones comunes incluyen -sS (escaneo TCP SYN), -sT (conexión TCP completa), -sU (UDP), -sV (detección de servicios y versiones), -O (detección del sistema operativo), -p (selección de puertos), -Pn (omitir el descubrimiento de hosts) y -A (agresivo: sistema operativo, versión, scripts y traceroute). Los estados de puerto son open (un servicio está escuchando), closed (alcanzable pero sin servicio) y filtered (sin respuesta o bloqueado, normalmente por un firewall). El Nmap Scripting Engine, invocado con --script o -sC, puede ejecutar verificaciones adicionales, incluidos scripts de vulnerabilidades.

Los escáneres de aplicaciones web (como OWASP ZAP, el escáner de Burp Suite o Nikto) rastrean un sitio y prueban problemas como inyección, cross-site scripting, encabezados de seguridad faltantes y componentes desactualizados. Producen muchos hallazgos que requieren validación manual.

El examen distingue los métodos de prueba según cuándo y cómo analizan el código. Las pruebas estáticas de seguridad de aplicaciones (SAST) analizan el código fuente o los binarios sin ejecutarlos, encontrando problemas como funciones inseguras o entradas no validadas en etapas tempranas del desarrollo, pero pueden producir falsos positivos y no ven la configuración en tiempo de ejecución. Las pruebas dinámicas de seguridad de aplicaciones (DAST) prueban la aplicación en ejecución desde afuera, como un atacante, encontrando comportamientos realmente explotables pero solo en las rutas de código alcanzables. El análisis de composición de software (SCA) hace un inventario de las bibliotecas de terceros y de código abierto, a menudo generando un software bill of materials (SBOM), y señala los componentes con vulnerabilidades conocidas o problemas de licencia. El fuzzing envía grandes volúmenes de entradas malformadas, aleatorias o inesperadas a un programa para provocar fallos o errores, y es especialmente bueno para encontrar corrupción de memoria y errores en el manejo de entradas.

Las herramientas de postura en la nube, incluidos los productos CSPM y los servicios de seguridad nativos del proveedor, reportan errores de configuración como almacenamiento abierto al público, registro deshabilitado, volúmenes sin cifrar, cuentas root sin MFA y políticas de identidad demasiado permisivas. La salida normalmente relaciona cada hallazgo con un benchmark como los CIS Benchmarks e identifica el recurso afectado, para que puedas dirigirlo al dueño correcto.

Términos clave

SAST
Static application security testing (pruebas estáticas): analizar el código fuente o los binarios en busca de fallas sin ejecutarlos.
DAST
Dynamic application security testing (pruebas dinámicas): probar una aplicación en ejecución desde afuera en busca de debilidades explotables.
SCA
Software composition analysis (análisis de composición de software): identificar los componentes de terceros y sus vulnerabilidades y licencias conocidas.
Fuzzing
Suministrar grandes volúmenes de entradas inesperadas o malformadas a un software para descubrir fallos y errores.
Filtered port (puerto filtrado)
Un estado de puerto de nmap que significa que las sondas no recibieron respuesta o fueron bloqueadas, normalmente por un firewall.
Ejemplo real

El pipeline de un desarrollador ejecuta SAST en cada commit, SCA sobre las dependencias y DAST cada noche contra un sitio de staging. SCA señala una biblioteca de logging con una vulnerabilidad conocida crítica, SAST señala una consulta SQL construida con concatenación de cadenas y DAST confirma que la inyección es alcanzable. Cada herramienta encontró algo que las otras podrían pasar por alto.

Consejo para el examen: SAST es de caja blanca y temprano (código en reposo); DAST es de caja negra y posterior (aplicación en ejecución); SCA trata de los componentes de terceros; el fuzzing trata de las entradas malformadas. En nmap, filtered normalmente significa que hay un firewall de por medio.

Comprueba lo que sabes

Un resultado de nmap muestra el puerto 443 como filtered. ¿Qué significa muy probablemente?

Un firewall o filtro está descartando las sondas, así que nmap no puede determinar si hay un servicio escuchando.

¿Qué método de prueba detectaría una biblioteca de código abierto vulnerable en tu aplicación?

El análisis de composición de software (SCA).

¿Cuál es una limitación de SAST en comparación con DAST?

SAST no ejecuta la aplicación, así que puede reportar falsos positivos y pasar por alto problemas de tiempo de ejecución y de configuración que DAST sí observaría.
