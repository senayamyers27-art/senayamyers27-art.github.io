CompTIA CySA+ CS0-004

Vulnerabilidades de software comunes: inyección, XSS, SSRF, IDOR, control de acceso roto, desbordamiento de búfer, cookies inseguras

El examen CySA+ espera que reconozcas las clases comunes de vulnerabilidades a partir de una descripción, una entrada de log o un fragmento de la salida de un escáner, y que sepas qué control corrige cada una. El OWASP Top 10 del Open Worldwide Application Security Project es una lista de referencia útil para los riesgos de las aplicaciones web. Para cada clase de las siguientes, hazte dos preguntas: ¿el código de quién termina ejecutándose o qué verificación falta, y cómo se vería la evidencia?

La inyección ocurre cuando se envía una entrada no confiable a un intérprete como parte de un comando o una consulta, de modo que la entrada cambia el significado del comando. La inyección de Structured Query Language (SQL) ataca las consultas a la base de datos y puede exponer, modificar o eliminar datos. La inyección de comandos pasa la entrada a una shell del sistema operativo. Otras formas incluyen la inyección de Lightweight Directory Access Protocol (LDAP) y la inyección de XML. La causa raíz es mezclar código y datos sin separación. El cross-site scripting (XSS) es una inyección en una página web que luego ejecuta el navegador de otro usuario. El XSS reflejado hace rebotar una carga útil en el servidor en una sola solicitud, normalmente mediante un enlace manipulado. El XSS almacenado (persistente) guarda la carga útil en la aplicación, como en un comentario, así que cada visitante la ejecuta. El XSS basado en DOM ocurre por completo en el script del lado del cliente que escribe datos no confiables en la página. El XSS se usa para robar cookies de sesión, actuar como la víctima o mostrar contenido falso. No lo confundas con la falsificación de solicitudes entre sitios (CSRF), que engaña al navegador de un usuario con sesión iniciada para que envíe una solicitud no deseada a un sitio que confía en él.

La falsificación de solicitudes del lado del servidor (SSRF) hace que el propio servidor envíe solicitudes a un destino que elige el atacante, por ejemplo al proporcionar una URL interna a una función que obtiene imágenes desde una dirección web. Como el servidor está dentro de la red, el SSRF puede llegar a servicios internos o a los endpoints de metadatos de las instancias en la nube, que pueden exponer credenciales temporales. La referencia directa insegura a objetos (IDOR) ocurre cuando una aplicación usa un identificador proporcionado por el usuario, como un número de factura, para obtener un registro sin verificar si el usuario puede verlo. Cambiar el número revela los datos de otra persona. El IDOR es una forma de control de acceso roto, que abarca cualquier falla en aplicar lo que los usuarios autenticados pueden hacer: llegar a las páginas de administración navegando directamente a ellas, escalar privilegios cambiando un parámetro de rol o endpoints de API sin verificaciones.

Un desbordamiento de búfer (buffer overflow) ocurre cuando un programa escribe más datos en un búfer de memoria de los que puede contener y sobrescribe la memoria adyacente. En lenguajes como C y C++, sin verificación automática de límites, esto puede hacer que el programa falle o permitir que un atacante redirija la ejecución, lo que a veces lleva a la ejecución remota de código. Las señales incluyen fallos con entradas largas y hallazgos del fuzzing. Las cookies inseguras exponen los tokens de sesión. Las cookies de sesión deben llevar el atributo Secure (se envían solo por HTTPS), HttpOnly (JavaScript no puede leerlas, lo que limita el robo mediante XSS) y un valor SameSite adecuado (limita el envío entre sitios, lo que ayuda contra el CSRF). Los ID de sesión deben ser largos y aleatorios, regenerarse después del inicio de sesión y expirar correctamente al cerrar sesión y por tiempo de inactividad.

Considera un ejemplo práctico. Durante una prueba autorizada, un probador con sesión iniciada como el cliente A consulta su pedido en /api/orders/5521, luego cambia el número a 5522 y recibe el pedido del cliente B, incluidos su dirección y su número de teléfono. El servidor verificó que hubiera un usuario con sesión iniciada, pero nunca verificó que el pedido perteneciera a ese usuario. Esto es IDOR, una forma de control de acceso roto. La misma prueba nota que la cookie de sesión no tiene el atributo HttpOnly, lo que haría mucho más dañina cualquier falla de XSS. Las correcciones recomendadas son una verificación de propiedad del lado del servidor en cada solicitud de objeto y los atributos correctos en las cookies.

Errores comunes: confundir XSS (se ejecuta en el navegador de la víctima) con CSRF (falsifica una solicitud desde el navegador de la víctima) o con inyección SQL (se ejecuta en la base de datos); pensar que el IDOR es un problema de autenticación, cuando el usuario está autenticado pero no autorizado; suponer que HTTPS por sí solo protege las cookies sin los atributos Secure y HttpOnly; confundir el SSRF, en el que el servidor hace la solicitud, con el CSRF, en el que la hace el navegador del usuario; y tratar los desbordamientos de búfer como un problema exclusivo de la web.

Las preguntas del examen con frecuencia dependen de quién ejecuta la carga útil o de qué verificación falta. 'La base de datos devuelve filas adicionales' o 'comilla y palabra clave SQL en el parámetro' es inyección SQL. 'El script se ejecuta en los navegadores de otros usuarios' es XSS, almacenado si persiste para cada visitante. 'El servidor obtiene una dirección interna o un endpoint de metadatos' es SSRF. 'Cambiar un ID muestra el registro de otro usuario' es IDOR. 'Un usuario normal llega a funciones de administración' es control de acceso roto. 'Fallo con una entrada muy larga' es un desbordamiento de búfer. 'Cookie legible por script o enviada por HTTP' es una cookie insegura.

Términos clave

Inyección (injection)
Una falla en la que una entrada no confiable se interpreta como parte de un comando o una consulta, lo que cambia su significado.
Cross-site scripting (XSS)
La inyección de script en una página web que luego se ejecuta en los navegadores de otros usuarios.
SSRF
Falsificación de solicitudes del lado del servidor (server-side request forgery), que hace que un servidor envíe solicitudes a destinos elegidos por el atacante, a menudo internos.
IDOR
Referencia directa insegura a objetos (insecure direct object reference), en la que cambiar un identificador da acceso a los datos de otro usuario porque no se verifica la autorización.
Control de acceso roto (broken access control)
Cualquier falla en aplicar lo que un usuario autenticado tiene permitido ver o hacer.
Desbordamiento de búfer (buffer overflow)
Escribir más datos en un búfer de memoria de los que puede contener, sobrescribiendo la memoria adyacente.
Atributo HttpOnly (HttpOnly flag)
Un atributo de cookie que impide que JavaScript lea la cookie, lo que limita el robo de sesiones mediante XSS.
Ejemplo real

Un probador con sesión iniciada como el cliente A consulta /api/orders/5521, luego cambia el número a 5522 y ve el pedido del cliente B con su dirección y número de teléfono. El servidor verifica que el usuario tenga sesión iniciada, pero no que el pedido le pertenezca, lo cual es IDOR, una forma de control de acceso roto. La corrección es una verificación de propiedad del lado del servidor en cada solicitud.

Consejo para el examen: Pregúntate quién ejecuta la carga útil: la base de datos o la shell (inyección), el navegador de otro usuario (XSS) o el servidor al obtener una URL (SSRF). Cambiar un ID para ver los datos de otra persona es IDOR. En el SSRF, el servidor hace la solicitud; en el CSRF, el navegador de la víctima.

Comprueba lo que sabes

¿Qué distingue al XSS almacenado del XSS reflejado?

El XSS almacenado se guarda en la aplicación y se ejecuta para cada visitante; el XSS reflejado se devuelve en una sola respuesta, normalmente mediante un enlace manipulado.

¿Por qué el SSRF es especialmente peligroso en los entornos de nube?

Se puede hacer que el servidor consulte servicios internos o endpoints de metadatos de las instancias que pueden exponer credenciales.

¿El IDOR es una falla de autenticación o de autorización?

De autorización: el usuario tiene sesión iniciada, pero la aplicación no verifica si puede acceder a ese objeto.

¿Qué atributos de cookie protegen los tokens de sesión y qué hace cada uno?

Secure envía la cookie solo por HTTPS, HttpOnly bloquea el acceso desde JavaScript y SameSite limita el envío entre sitios.
