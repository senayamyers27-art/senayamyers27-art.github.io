CompTIA CySA+ CS0-004

Vulnerabilidades de software comunes: inyección, XSS, SSRF, IDOR, control de acceso roto, desbordamiento de búfer, cookies inseguras

El examen CySA+ espera que reconozcas las clases de vulnerabilidades comunes a partir de una descripción, una entrada de log o un fragmento de la salida de un escáner, y que sepas qué control corrige cada una. El OWASP Top 10 es una lista de referencia útil para los riesgos de las aplicaciones web.

La inyección ocurre cuando una entrada no confiable se envía a un intérprete como parte de un comando o consulta, de modo que la entrada cambia el significado del comando. La SQL injection ataca las consultas a bases de datos y puede exponer, modificar o eliminar datos. La inyección de comandos pasa la entrada a una shell del sistema operativo. Otras formas incluyen la LDAP injection y la XML injection. La causa raíz es mezclar código y datos sin separarlos.

El cross-site scripting (XSS) es una inyección en una página web que luego ejecuta el navegador de otro usuario. El XSS reflejado hace rebotar un payload en el servidor en una sola solicitud, normalmente mediante un enlace manipulado. El XSS almacenado (persistente) guarda el payload en la aplicación, por ejemplo en un comentario, de modo que cada visitante lo ejecuta. El XSS basado en DOM ocurre completamente en scripts del lado del cliente que escriben datos no confiables en la página. El XSS se usa para robar cookies de sesión, realizar acciones como la víctima o mostrar contenido falso. No lo confundas con cross-site request forgery (CSRF), que engaña al navegador de un usuario con sesión iniciada para que envíe una solicitud no deseada a un sitio que confía en él.

La server-side request forgery (SSRF) hace que el propio servidor envíe solicitudes a un destino que elige el atacante, por ejemplo proporcionando una URL interna a una función que descarga imágenes. Como el servidor está dentro de la red, la SSRF puede alcanzar servicios internos o endpoints de metadatos de instancias en la nube que exponen credenciales.

La insecure direct object reference (IDOR) ocurre cuando una aplicación usa un identificador proporcionado por el usuario, como invoice?id=1001, para obtener un registro sin verificar si el usuario tiene permiso para verlo. Cambiar el número revela los datos de otra persona. La IDOR es una forma de control de acceso roto (broken access control), que abarca cualquier falla al hacer cumplir lo que pueden hacer los usuarios autenticados: acceder a páginas de administración navegando directamente a ellas, escalar privilegios cambiando un parámetro de rol o la falta de verificaciones en los endpoints de la API.

Un desbordamiento de búfer (buffer overflow) ocurre cuando un programa escribe en un búfer de memoria más datos de los que puede contener, sobrescribiendo la memoria adyacente. En lenguajes como C y C++ sin verificación automática de límites, esto puede hacer fallar el programa o permitir que un atacante redirija la ejecución. Las señales incluyen fallos ante entradas largas y los resultados del fuzzing.

Las cookies inseguras exponen los tokens de sesión. Las cookies deben llevar el atributo Secure (enviadas solo por HTTPS), HttpOnly (no legibles por JavaScript, lo que limita el robo mediante XSS) y un valor SameSite adecuado (limita el envío entre sitios, lo que ayuda contra CSRF). Los IDs de sesión deben ser largos y aleatorios, regenerarse después del inicio de sesión y expirar correctamente.

Términos clave

XSS
Cross-site scripting: inyectar scripts en páginas web que ven otros usuarios, los cuales se ejecutan en sus navegadores.
SSRF
Server-side request forgery: engañar a un servidor para que haga solicitudes a destinos elegidos por el atacante, a menudo internos.
IDOR
Insecure direct object reference: acceso a objetos cambiando un identificador sin verificaciones de autorización.
Buffer overflow (desbordamiento de búfer)
Escribir más allá del límite de un búfer de memoria, lo que puede hacer fallar un programa o permitir la ejecución de código.
HttpOnly flag (atributo HttpOnly)
Un atributo de cookie que impide que los scripts del lado del cliente lean la cookie.
Ejemplo real

Un tester con sesión iniciada como el cliente A consulta /api/orders/5521, luego cambia el número a 5522 y ve el pedido del cliente B con su dirección y número de teléfono. El servidor verifica que el usuario haya iniciado sesión, pero no que el pedido le pertenezca, lo cual es IDOR, una forma de control de acceso roto.

Consejo para el examen: Fíjate en quién ejecuta el payload: la base de datos o la shell (inyección), el navegador de otro usuario (XSS), el servidor que obtiene una URL (SSRF). Cambiar un ID para ver los datos de otra persona es IDOR.

Comprueba lo que sabes

¿Cuál es la diferencia entre XSS almacenado y XSS reflejado?

El XSS almacenado lo guarda la aplicación y se entrega a cada visitante; el XSS reflejado se devuelve de inmediato a partir de una sola solicitud manipulada, normalmente mediante un enlace.

¿Por qué la SSRF es especialmente peligrosa en entornos de nube?

Se puede hacer que el servidor consulte servicios internos o endpoints de metadatos de instancias que pueden revelar credenciales.

¿Qué atributo de cookie impide que una cookie de sesión se envíe por HTTP sin cifrar?

El atributo Secure.
