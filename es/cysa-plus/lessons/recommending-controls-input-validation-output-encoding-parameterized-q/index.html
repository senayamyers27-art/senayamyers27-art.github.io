CompTIA CySA+ CS0-004

Recomendación de controles: validación de entradas, codificación de salidas, consultas parametrizadas, protecciones de memoria, codificación segura

Encontrar una vulnerabilidad es solo la mitad del trabajo de un analista. También necesitas recomendar una corrección que ataque la causa raíz y no solo el síntoma, y el examen te pedirá relacionar cada falla con su mejor control. Piensa en capas: la corrección principal elimina la falla en el código, y los controles secundarios, como los firewalls de aplicaciones web (WAF), el mínimo privilegio y el monitoreo, reducen el daño si algo se escapa.

La validación de entradas verifica que los datos que entran a una aplicación coincidan con lo esperado antes de usarlos: tipo, longitud, formato y rango. Las listas de permitidos (allow listing), que aceptan solo patrones conocidos como buenos, como dígitos para un código postal, son más fuertes que las listas de bloqueo (deny listing), que bloquean cadenas conocidas como malas, porque los atacantes encuentran infinitas formas de codificar una entrada maliciosa. La validación debe hacerse en el servidor; las verificaciones del lado del cliente en el navegador mejoran la usabilidad, pero pueden evadirse fácilmente. La validación reduce muchos ataques, pero no basta por sí sola contra la inyección o el cross-site scripting (XSS), porque algunas entradas legítimas contienen caracteres que son peligrosos en ciertos contextos, como un apóstrofo en un apellido.

La codificación de salidas (output encoding), también llamada escape, convierte los caracteres especiales en una representación segura para el contexto en el que se muestran los datos. En HTML, caracteres como < y > se convierten en &lt; y &gt;, de modo que el navegador los muestra como texto en lugar de ejecutarlos como marcado. La codificación debe coincidir con el contexto: el cuerpo HTML, los atributos HTML, JavaScript, las URL y CSS necesitan reglas diferentes. La codificación de salidas es la defensa principal contra el XSS, a menudo combinada con un encabezado Content Security Policy (CSP) que limita qué scripts pueden ejecutarse. Las consultas parametrizadas, también llamadas sentencias preparadas (prepared statements), son la defensa principal contra la inyección SQL. La estructura de la consulta se define con marcadores de posición, y la entrada del usuario se proporciona por separado como parámetros, así que la base de datos siempre la trata como datos, nunca como código. Los procedimientos almacenados y los mapeadores objeto-relacionales ayudan cuando usan parámetros internamente.

# Unsafe: input becomes part of the SQL text
cur.execute("SELECT * FROM users WHERE name = '" + name + "'")
# Safe: parameterized query, input passed separately
cur.execute("SELECT * FROM users WHERE name = %s", (name,))

Las protecciones de memoria reducen el daño de los desbordamientos de búfer. La aleatorización del diseño del espacio de direcciones (ASLR) coloca el código y los datos en direcciones impredecibles. La prevención de ejecución de datos (DEP), también llamada no ejecución (NX), marca las regiones de memoria como la pila como no ejecutables. Los canarios de pila (stack canaries) son valores colocados antes de las direcciones de retorno que se verifican antes de que una función regrese, lo que detecta las sobrescrituras. Sin embargo, la mejor corrección es el código seguro: funciones con verificación de límites, un manejo cuidadoso de las longitudes o lenguajes con seguridad de memoria. La codificación segura lo une todo: un ciclo de vida de desarrollo seguro con modelado de amenazas, revisión de código y pruebas de seguridad; mínimo privilegio para las cuentas de la aplicación y de la base de datos; manejo de errores que no filtre trazas de pila; gestión segura de sesiones; dependencias actualizadas; ningún secreto codificado de forma fija; y funciones probadas del framework para la autenticación, el cifrado y la codificación en lugar de versiones caseras. Las verificaciones de control de acceso deben aplicarse en el servidor en cada solicitud, que es la corrección para las referencias directas inseguras a objetos (IDOR) y el control de acceso roto. Para la falsificación de solicitudes del lado del servidor (SSRF), usa listas de permitidos para las URL de destino y bloquea las solicitudes a rangos de direcciones internas y a los endpoints de metadatos.

Considera un ejemplo práctico. Un escaneo encuentra XSS almacenado en un formulario de reseñas de productos e inyección SQL en la función de búsqueda de una tienda en línea. Recomiendas consultas parametrizadas para el código de búsqueda, codificación de salidas según el contexto cuando se muestra el texto de las reseñas, una Content Security Policy para limitar los orígenes de los scripts y validación de entradas del lado del servidor con límites de longitud en ambos campos. También recomiendas restringir la cuenta de base de datos que usa la aplicación web a las tablas que necesita. Se agrega una regla en el WAF como medida temporal mientras los desarrolladores publican las correcciones del código, pero dejas claro que no las reemplaza.

Errores comunes: elegir la validación de entradas como la mejor corrección única para la inyección SQL o el XSS, cuando las consultas parametrizadas y la codificación de salidas son los controles principales; depender de la validación del lado del cliente; tratar un WAF como una corrección en lugar de una capa compensatoria; creer que ASLR y DEP eliminan los desbordamientos de búfer, cuando solo dificultan la explotación; y suponer que ocultar una URL o un botón es control de acceso.

Las preguntas del examen normalmente emparejan una falla con su mejor control. La inyección SQL se empareja con las consultas parametrizadas. El XSS se empareja con la codificación de salidas, apoyada por CSP. El desbordamiento de búfer se empareja con la verificación de límites o los lenguajes con seguridad de memoria, con ASLR, DEP y los canarios como mitigaciones. El IDOR y el control de acceso roto se emparejan con las verificaciones de autorización del lado del servidor. El SSRF se empareja con las listas de destinos permitidos. 'Trazas de pila mostradas a los usuarios' se empareja con un manejo de errores adecuado. Si una respuesta dice 'validar la entrada' y otra nombra el control principal específico, la específica suele ser la correcta.

Términos clave

Validación de entradas (input validation)
Verificar que los datos entrantes coincidan con el tipo, la longitud, el formato y el rango esperados antes de usarlos.
Lista de permitidos (allow listing)
Aceptar solo las entradas que coinciden con patrones conocidos como buenos, en lugar de intentar bloquear las entradas conocidas como malas.
Codificación de salidas (output encoding)
Convertir los caracteres especiales a una forma segura para el contexto en el que se muestran los datos, lo que previene el XSS.
Consulta parametrizada (parameterized query)
Una consulta a la base de datos con marcadores de posición en la que la entrada del usuario se pasa por separado, de modo que se trata solo como datos.
ASLR
Aleatorización del diseño del espacio de direcciones (address space layout randomization), que coloca el código y los datos en direcciones de memoria impredecibles.
DEP / NX
Prevención de ejecución de datos (data execution prevention), que marca las regiones de memoria como la pila como no ejecutables.
Content Security Policy
Un encabezado de respuesta HTTP que restringe de qué orígenes cargará el navegador scripts y otro contenido.
Ejemplo real

Un escaneo encuentra XSS almacenado en un formulario de reseñas de productos e inyección SQL en la función de búsqueda. El analista recomienda consultas parametrizadas para el código de búsqueda, codificación de salidas según el contexto para el texto de las reseñas junto con una Content Security Policy, validación de entradas del lado del servidor para ambos y una cuenta de base de datos con mínimo privilegio, con una regla en el WAF solo como medida provisional hasta que se publiquen las correcciones del código.

Consejo para el examen: Emparejamientos de mejor corrección: inyección SQL con consultas parametrizadas, XSS con codificación de salidas, desbordamiento de búfer con verificación de límites y protecciones de memoria, IDOR con verificaciones de autorización del lado del servidor. La validación de entradas ayuda en todas partes, pero rara vez es la mejor respuesta única para la inyección.

Comprueba lo que sabes

¿Cuál es la defensa principal contra la inyección SQL?

Las consultas parametrizadas (sentencias preparadas), que mantienen la entrada del usuario separada del código SQL.

¿Por qué la validación de entradas debe hacerse en el servidor?

Las verificaciones del lado del cliente pueden evadirse enviando solicitudes directamente, así que solo se puede confiar en la validación del lado del servidor.

¿Qué hace la codificación de salidas para prevenir el XSS?

Convierte caracteres como < y > en representaciones seguras para que el navegador los muestre como texto en lugar de ejecutarlos como código.

¿ASLR y DEP corrigen los desbordamientos de búfer?

No; dificultan la explotación, pero la verdadera corrección es el código con verificación de límites o un lenguaje con seguridad de memoria.
