CompTIA CySA+ CS0-004

Recomendación de controles: validación de entradas, codificación de salidas, consultas parametrizadas, protecciones de memoria, codificación segura

Encontrar una vulnerabilidad es solo la mitad del trabajo de un analista. También necesitas recomendar una corrección que ataque la causa raíz, y el examen te pedirá que relaciones cada falla con su mejor control.

La validación de entradas verifica que los datos que entran a una aplicación coincidan con lo esperado antes de usarlos: tipo, longitud, formato y rango. El allow listing (aceptar solo patrones conocidos como buenos, como dígitos para un código postal) es más fuerte que el deny listing (bloquear cadenas conocidas como malas), porque los atacantes encuentran infinitas formas de codificar entradas maliciosas. La validación debe ocurrir en el servidor; las verificaciones del lado del cliente en el navegador mejoran la usabilidad pero pueden evadirse. La validación reduce muchos ataques, pero por sí sola no es suficiente contra la inyección o el XSS.

La codificación de salidas (output encoding, también llamada escaping) convierte los caracteres especiales en una representación segura para el contexto donde se muestran los datos. Para HTML, caracteres como < y > se convierten en &lt; y &gt;, de modo que el navegador los muestra como texto en lugar de ejecutarlos como marcado. La codificación debe coincidir con el contexto: el cuerpo HTML, un atributo HTML, JavaScript, una URL o CSS necesitan reglas distintas. La codificación de salidas es la defensa principal contra el XSS, a menudo combinada con un encabezado Content Security Policy (CSP) que limita qué scripts pueden ejecutarse.

Las consultas parametrizadas, también llamadas prepared statements, son la defensa principal contra la SQL injection. La estructura de la consulta se define con marcadores de posición, y la entrada del usuario se proporciona por separado como parámetros, de modo que la base de datos siempre la trata como datos, nunca como código SQL. Los procedimientos almacenados y los mapeadores objeto-relacionales (ORMs) ayudan cuando usan parámetros internamente. Escapar las entradas y usar cuentas de base de datos con mínimo privilegio son capas secundarias.

# Inseguro: la entrada se vuelve parte del texto SQL
cur.execute("SELECT * FROM users WHERE name = '" + name + "'")
# Seguro: consulta parametrizada, la entrada se pasa por separado
cur.execute("SELECT * FROM users WHERE name = %s", (name,))

Las protecciones de memoria reducen el daño de los desbordamientos de búfer. La aleatorización del diseño del espacio de direcciones (ASLR) ubica el código y los datos en direcciones impredecibles. La prevención de ejecución de datos (DEP), también llamada no-execute (NX), marca regiones de memoria como la pila (stack) como no ejecutables. Los stack canaries son valores colocados antes de las direcciones de retorno que se verifican antes de que una función retorne, detectando sobrescrituras. Sin embargo, la mejor corrección es el código seguro: funciones con verificación de límites, un manejo cuidadoso de las longitudes o lenguajes seguros en memoria.

La codificación segura lo une todo: sigue un ciclo de vida de desarrollo seguro con modelado de amenazas, revisión de código y pruebas de seguridad; aplica mínimo privilegio a las cuentas de la aplicación y de la base de datos; maneja los errores sin filtrar stack traces; gestiona las sesiones de forma segura; mantén actualizadas las dependencias; nunca escribas secretos directamente en el código; y usa funciones probadas del framework para la autenticación, el cifrado y la codificación en lugar de escribir las tuyas. Las verificaciones de control de acceso deben aplicarse en el servidor en cada solicitud, que es la corrección para IDOR y el control de acceso roto. Para SSRF, valida y usa allow listing de las URLs de destino y bloquea las solicitudes a rangos de direcciones internas.

Términos clave

Parameterized query (consulta parametrizada)
Una consulta a la base de datos que separa el código SQL de los valores proporcionados por el usuario, lo que previene la SQL injection.
Output encoding (codificación de salidas)
Convertir caracteres especiales para que los datos se muestren como texto en un contexto dado en lugar de ejecutarse.
ASLR
Address space layout randomization: aleatorizar las ubicaciones de memoria para dificultar la explotación de errores de memoria.
DEP
Data execution prevention: marcar regiones de memoria como no ejecutables para que los datos inyectados no puedan ejecutarse como código.
Allow listing (lista de permitidos)
Aceptar solo entradas que coincidan con un conjunto definido de valores o patrones conocidos como buenos.
Ejemplo real

Un escaneo encuentra XSS almacenado en un formulario de reseñas de productos y SQL injection en la función de búsqueda. El analista recomienda consultas parametrizadas para el código de búsqueda, codificación de salidas según el contexto para el texto de las reseñas más una Content Security Policy, y validación de entradas del lado del servidor para ambos, en lugar de depender solo de una regla del WAF.

Consejo para el examen: Mejores correcciones por pareja: SQL injection con consultas parametrizadas, XSS con codificación de salidas, desbordamiento de búfer con verificación de límites y protecciones de memoria, IDOR con verificaciones de autorización del lado del servidor. La validación de entradas ayuda en todos los casos, pero rara vez es la mejor respuesta única para la inyección.

Comprueba lo que sabes

¿Cuál es el control más eficaz contra la SQL injection?

Las consultas parametrizadas (prepared statements), que mantienen la entrada del usuario separada del código SQL.

¿Por qué la validación de entradas del lado del cliente no es suficiente?

Los atacantes pueden evadir el navegador y enviar solicitudes directamente, así que la validación debe aplicarse en el servidor.

¿Cómo hace DEP más difícil la explotación de un desbordamiento de búfer?

Marca las áreas de datos como la pila como no ejecutables, de modo que el código inyectado allí no pueda ejecutarse.
