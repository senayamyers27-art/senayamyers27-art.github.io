Authentication policy y Authentication Portal

User-ID normalmente averigua en silencio quién está detrás de una dirección IP, a partir de los controladores de dominio, GlobalProtect o syslog. A veces eso no basta: la laptop de un contratista no está en el dominio, o un servidor sensible debería exigir una prueba de identidad reciente, posiblemente con MFA. La Authentication policy y el Authentication Portal (antes llamado Captive Portal) cubren estos casos.

La Authentication policy (Policies > Authentication) es una rulebase que se evalúa para el tráfico antes de que la política de seguridad use el usuario. Cada regla coincide por zona de origen, dirección de origen, usuario de origen (a menudo 'unknown' para usuarios sin mapeo, o 'known-user' para MFA escalonada o step-up), zona y dirección de destino, servicio y categoría de URL. Su acción es un authentication enforcement object que elige el método y el perfil de autenticación, además de un tiempo de espera (timeout) que decide cuánto tiempo el usuario permanece autenticado antes de que se le vuelva a pedir autenticación.

Los métodos de aplicación son browser-challenge, web-form y no-captive-portal. Browser-challenge usa el inicio de sesión único Kerberos (SPNEGO), así que los navegadores del dominio se autentican de forma transparente sin ningún aviso. Web-form muestra una página de inicio de sesión y actúa como respaldo de browser-challenge cuando falla el SSO. No-captive-portal deja pasar el tráfico coincidente sin autenticar, útil como regla de excepción por encima de reglas más amplias. Existen objetos predefinidos como default-browser-challenge, default-web-form y default-no-captive-portal, y puedes crear los tuyos para adjuntar un perfil de autenticación con MFA.

El Authentication Portal en sí se configura en Device > User Identification > Authentication Portal Settings. Sus dos modos son importantes. En el modo Transparent, el firewall suplanta al sitio web de destino original y responde con un desafío de autenticación; funciona con cualquier tipo de interfaz, incluidos virtual wire y Layer 2, pero provoca advertencias de certificado a menos que haya descifrado con un certificado de confianza. El modo Redirect envía el navegador a una interfaz Layer 3 del firewall (el redirect host) con un HTTP 302, lo que permite cookies de sesión para que no se vuelva a pedir autenticación a los usuarios, y es necesario para el SSO Kerberos y los diseños multisitio. El modo Redirect necesita un perfil de administración de interfaz con Response Pages habilitado en la interfaz de redirección y un nombre DNS que resuelva hacia ella.

Solo el tráfico web puede activar el portal, porque el firewall necesita un navegador para mostrar la página. Para sitios HTTPS, el firewall debe descifrar la sesión para inyectar el desafío, así que combina las reglas de autenticación con una política de descifrado. Para aplicaciones que no son web, como SSH hacia un servidor, el usuario primero se autentica en un navegador, lo que crea un mapeo de usuario con marca de tiempo, y luego la regla de autenticación permite el tráfico no web hasta que expire el timeout. Así es como agregas MFA delante de protocolos heredados.

Los resultados aparecen en el Authentication log y en Monitor > Logs con el usuario. Recuerda que las reglas de seguridad aún deben permitir el tráfico; la autenticación identifica a los usuarios, pero no otorga acceso por sí misma.

Términos clave

Authentication policy (política de autenticación)
Una rulebase que decide qué tráfico debe autenticarse, cómo y por cuánto tiempo antes de que se le aplique la política de seguridad.
Authentication enforcement object (objeto de aplicación de autenticación)
La acción de la regla que elige browser-challenge, web-form o no-captive-portal y un perfil de autenticación.
Redirect mode (modo de redirección)
Modo del Authentication Portal que redirige a los usuarios a una interfaz Layer 3 del firewall, compatible con cookies de sesión y SSO Kerberos.
Transparent mode (modo transparente)
Modo del Authentication Portal en el que el firewall suplanta al sitio de destino para presentar el desafío.
Ejemplo real

Los usuarios de la Wi-Fi de invitados no están en el dominio, así que sus IP se asocian a unknown. Una regla de autenticación para el usuario de origen unknown desde la zona Guest usa un enforcement object web-form vinculado a una base de datos local de invitados. Después de iniciar sesión, la IP de un invitado queda asociada a su cuenta, y las reglas de seguridad le permiten solo navegación web.

Consejo para el examen: El modo Redirect necesita una interfaz Layer 3 con Response Pages en su perfil de administración; el modo Transparent se adapta a vwire y Layer 2. Los disparadores HTTPS requieren descifrado. La Authentication policy identifica; la política de seguridad sigue decidiendo si se permite o se deniega.

Comprueba lo que sabes

¿Qué método de aplicación brinda SSO transparente para los navegadores del dominio?

browser-challenge, usando Kerberos.

¿Por qué una sesión SSH no puede activar el portal directamente?

El portal necesita un navegador web para mostrar el desafío; los usuarios se autentican primero mediante un navegador y luego se permite SSH hasta el timeout.

¿Qué debe tener la interfaz del redirect host para el modo Redirect?

Un perfil de administración de interfaz con Response Pages habilitado, en una interfaz Layer 3.
