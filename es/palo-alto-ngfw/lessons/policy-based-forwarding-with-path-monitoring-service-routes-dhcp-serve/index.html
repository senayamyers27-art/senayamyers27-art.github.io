Policy-based forwarding con path monitoring; service routes; servidor/relay DHCP y DNS proxy

Normalmente el firewall reenvía según el destino usando la tabla de enrutamiento. Policy-based forwarding (PBF, reenvío basado en políticas) anula eso para el tráfico que cumple criterios específicos, por ejemplo enviar el tráfico de invitados por un enlace de banda ancha económico mientras el tráfico corporativo usa MPLS. Las reglas PBF se encuentran en Policies > Policy Based Forwarding y se evalúan antes de la búsqueda de ruta para una sesión nueva.

Una regla PBF coincide por zona o interfaz de origen, dirección de origen, usuario de origen, dirección de destino, aplicación y servicio. Su acción es Forward (con una interfaz de salida y un siguiente salto opcional), Forward to vsys (en firewalls multi-vsys), Discard o No PBF (usar el enrutamiento normal). El PBF basado en aplicaciones tiene una trampa: la decisión de PBF se toma con el primer paquete, antes de que App-ID haya identificado la aplicación. El firewall lo resuelve con una caché de aplicaciones (application cache), de modo que la primera sesión de una aplicación sigue la tabla de enrutamiento y las sesiones posteriores coinciden con la regla PBF una vez que la aplicación está en la caché. Usa criterios de servicio o de dirección cuando puedas.

Path monitoring hace que PBF sea seguro. Agregas un perfil de monitoreo y una IP monitoreada (a menudo el siguiente salto o algo más allá). Si los pings fallan, la acción Fail Over deshabilita la regla para que el tráfico vuelva a la tabla de enrutamiento, mientras que Wait Recover sigue usando la regla hasta que el camino se recupere. Symmetric Return, disponible en la acción Forward, hace que las respuestas a las sesiones que llegaron por una interfaz concreta salgan por esa misma interfaz y siguiente salto, lo cual es importante con dos ISP para que el tráfico de retorno no salga por el proveedor equivocado.

Los service routes responden a otra pregunta: ¿qué interfaz usa el propio plano de administración del firewall para llegar a servicios como DNS, NTP, actualizaciones de software, syslog, LDAP, RADIUS o Panorama? De forma predeterminada todo sale por el puerto MGT dedicado. En Device > Setup > Services > Service Route Configuration puedes elegir una interfaz de datos y una dirección de origen por servicio, algo común cuando la red de MGT no tiene acceso a Internet.

En las interfaces Layer 3 el firewall puede actuar como servidor DHCP, entregando direcciones de un pool junto con gateway, DNS y otras opciones, y puede heredar la configuración DNS de una interfaz cliente DHCP ascendente. O puede actuar como DHCP relay, reenviando los broadcasts de los clientes a un servidor DHCP central. Una interfaz no puede ser servidor y relay a la vez. Esto se configura en Network > DHCP.

Un DNS proxy (Network > DNS Proxy) hace que una interfaz del firewall responda las consultas DNS de los clientes. Reenvía las consultas a servidores primario y secundario, puede enviar dominios específicos a servidores específicos mediante reglas de dominio (split DNS), puede contener entradas estáticas de FQDN a IP y almacena las respuestas en caché. Es práctico para sucursales y algunas funciones, como el web proxy, lo requieren.

Términos clave

Policy-based forwarding (PBF, reenvío basado en políticas)
Reglas que reenvían el tráfico coincidente según criterios como origen, usuario o aplicación en lugar de la tabla de enrutamiento.
Symmetric return (retorno simétrico)
Una opción de PBF que envía las respuestas de vuelta por la misma interfaz y siguiente salto por donde llegó el tráfico original.
Service route (ruta de servicio)
Una configuración que hace que un servicio del plano de administración, como DNS, actualizaciones o syslog, origine su tráfico desde una interfaz de datos en lugar de MGT.
DNS proxy
Una función del firewall que responde las consultas DNS de los clientes, las reenvía a servidores elegidos por dominio y almacena los resultados en caché.
Ejemplo real

Una sucursal minorista tiene MPLS y un enlace de banda ancha. Una regla PBF envía la zona Guest a la interfaz de banda ancha con path monitoring sobre el gateway del ISP configurado en Fail Over. Cuando el enlace de banda ancha se cae, la regla se deshabilita y el tráfico de invitados sigue la ruta predeterminada por MPLS hasta que el enlace se recupera.

Consejo para el examen: PBF se evalúa antes del enrutamiento, pero el PBF basado en aplicaciones solo aplica cuando la aplicación ya está en la caché de aplicaciones, así que la primera sesión usa la tabla de enrutamiento. Los service routes son para el tráfico originado por el firewall, no para el tráfico de los usuarios.

Comprueba lo que sabes

¿Por qué la primera sesión de una aplicación podría ignorar una regla PBF basada en aplicaciones?

La decisión de PBF se toma con el primer paquete, antes de que App-ID identifique la aplicación; solo las sesiones posteriores coinciden gracias a la caché de aplicaciones.

Tu puerto MGT no tiene acceso a Internet y las actualizaciones dinámicas fallan. ¿Qué configuras?

Un service route para que el servicio de actualizaciones (Palo Alto Networks services) use una interfaz de datos con acceso a Internet.

¿Qué hace Fail Over en el path monitoring de PBF?

Deshabilita la regla PBF cuando falla el monitoreo, para que el tráfico vuelva a la tabla de enrutamiento normal.
