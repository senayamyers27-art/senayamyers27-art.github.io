VPN IKEv2 resistentes a la computación cuántica (post-quantum preshared keys) y túneles GRE

Las VPN actuales usan el intercambio de claves Diffie-Hellman, que una computadora cuántica lo suficientemente grande podría romper. La preocupación es 'harvest now, decrypt later' (recolectar ahora, descifrar después): un atacante graba hoy el tráfico VPN cifrado y lo descifra dentro de algunos años. Las funciones de VPN resistentes a la computación cuántica de las versiones recientes de PAN-OS abordan esto para los túneles sitio a sitio IKEv2.

El enfoque que nombra este tema son las post-quantum preshared keys (PPK), estandarizadas en RFC 8784 para IKEv2. Ambos peers se configuran con la misma clave secreta de alta entropía y un key ID coincidente, además de la autenticación normal. La PPK se mezcla en la derivación de las claves IPsec. Aunque un atacante rompa más adelante el intercambio Diffie-Hellman, aún no puede derivar las claves de sesión sin la PPK, que nunca se envió por la red. Las PPK solo funcionan con IKEv2, no con IKEv1, y ambos peers deben admitir la extensión. Las configuras en las opciones avanzadas de IKEv2 del IKE gateway, con un parámetro de negociación que decide si el túnel exige la PPK o si puede recurrir a un intercambio normal con peers que no la admiten. Exigirla es más seguro, pero fallará con un peer que no la admita.

Las versiones más recientes también agregan el intercambio de claves híbrido (hybrid key exchange), donde un mecanismo de encapsulamiento de claves post-cuántico se combina con el Diffie-Hellman clásico usando las extensiones de IKEv2 para múltiples intercambios de claves. El principio a recordar es 'híbrido': el resultado es al menos tan fuerte como el más fuerte de los dos métodos. Revisa las notas de la versión para saber qué algoritmos admite tu versión de PAN-OS en lugar de suponerlo.

Recomendaciones prácticas: usa algoritmos simétricos fuertes como AES-256 con SHA-256 o superior, porque se considera que la criptografía simétrica con claves grandes está mucho menos expuesta a ataques cuánticos. Administra las PPK como cualquier secreto, rótalas y nunca las reutilices entre peers no relacionados.

Generic Routing Encapsulation (GRE) es un protocolo de tunelización simple y sin cifrado (protocolo IP 47) que envuelve los paquetes dentro de un nuevo encabezado IP. Se usa para llegar a socios o servicios en la nube que requieren GRE y para transportar tráfico como los intercambios de protocolos de enrutamiento hacia un peer. En PAN-OS lo configuras en Network > GRE Tunnels: una interfaz tunnel (con zona y router), la interfaz y dirección locales, la dirección del peer, el TTL, una opción Copy ToS opcional y keepalives que marcan el túnel como caído si el peer deja de responder. Luego enrutas el tráfico hacia la interfaz tunnel igual que con IPsec.

Como GRE no ofrece confidencialidad ni integridad, no lo uses sobre redes no confiables para datos sensibles a menos que algo más los proteja. La política de seguridad sigue aplicándose al tráfico que entra y sale de la zona de la interfaz del túnel GRE, y necesitas una regla que permita GRE entre los extremos del túnel.

Términos clave

Post-quantum preshared key (PPK, clave precompartida post-cuántica)
Un secreto compartido adicional que se mezcla en la derivación de claves de IKEv2 (RFC 8784) para que las claves de sesión resistan futuros ataques cuánticos contra Diffie-Hellman.
Harvest now, decrypt later (recolectar ahora, descifrar después)
La amenaza de grabar hoy tráfico cifrado para descifrarlo cuando las computadoras cuánticas puedan romper el intercambio de claves.
GRE
Generic Routing Encapsulation, un protocolo de tunelización sin cifrado (protocolo IP 47) que encapsula paquetes en un nuevo encabezado IP.
Hybrid key exchange (intercambio de claves híbrido)
Combinar un intercambio de claves clásico y uno post-cuántico para que el resultado sea al menos tan fuerte como el más fuerte de ambos.
Ejemplo real

El túnel entre el centro de datos de un banco y su sitio de recuperación ante desastres (DR) transporta datos de replicación que deben mantenerse confidenciales durante décadas. Ambos lados ejecutan IKEv2 en versiones de PAN-OS que admiten PPK, así que los ingenieros agregan la misma PPK generada aleatoriamente y el mismo key ID en cada IKE gateway y configuran la negociación para exigirla. Ahora el tráfico grabado queda protegido aunque Diffie-Hellman se rompa más adelante.

Consejo para el examen: PPK significa solo IKEv2 y deben coincidir en ambos peers. GRE no es cifrado; si una pregunta requiere confidencialidad a través de Internet, GRE por sí solo es la respuesta incorrecta.

Comprueba lo que sabes

¿Por qué una PPK protege contra futuros ataques cuánticos?

Se mezcla en la derivación de las claves IPsec pero nunca se transmite, así que romper solo Diffie-Hellman no revela las claves.

¿Puedes usar una PPK con un IKE gateway IKEv1?

No, las PPK son una extensión de IKEv2.

¿Qué hace un keepalive de GRE?

Verifica que el peer responda y marca el túnel como caído si no lo hace, para que el enrutamiento pueda reaccionar.
