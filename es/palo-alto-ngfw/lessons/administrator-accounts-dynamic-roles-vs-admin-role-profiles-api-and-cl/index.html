Cuentas de administrador: dynamic roles vs admin role profiles, permisos de API y CLI

Cada persona o sistema que administra el firewall debe tener su propia cuenta de administrador con el mínimo privilegio necesario. Las cuentas se crean en Device > Administrators, y cada cuenta tiene un método de autenticación y un rol administrativo. El rol decide qué puede ver y cambiar la cuenta.

Los dynamic roles (roles dinámicos) vienen integrados y cubren las necesidades comunes: Superuser (acceso total, incluida la creación de otros administradores), Superuser (read-only), Device Administrator (acceso total a un firewall excepto la administración de administradores y algunos ajustes), Device Administrator (read-only) y, en firewalls multi-vsys, Virtual System Administrator y su versión de solo lectura, que restringen al administrador a los vsys elegidos. Se llaman dinámicos porque Palo Alto los actualiza automáticamente cuando llegan funciones nuevas en una versión de PAN-OS, así que un administrador con un rol dinámico obtiene acceso a los menús nuevos sin que tengas que editar nada.

Los admin role profiles son roles personalizados que creas en Device > Admin Roles. Tienen alcance de dispositivo (device) o de vsys. Para cada área de la interfaz web defines Enable, Read Only o Disable, por ejemplo otorgando acceso total a Monitor y Policies pero ningún acceso a Device. El perfil también tiene pestañas separadas para la XML API, la REST API y la línea de comandos. La contrapartida es el mantenimiento: cuando una actualización agrega funciones nuevas, los perfiles personalizados no se actualizan, así que debes revisarlos y ajustarlos.

El permiso de CLI en un role profile es una sola opción: none, superuser, superreader, deviceadmin, devicereader (y sus equivalentes de vsys en sistemas multi-vsys). Configurarlo en none bloquea la administración por SSH y consola para ese rol aunque la interfaz web esté permitida. Los permisos de la XML API se definen por tipo de solicitud, como report, log, configuration, operational requests, commit, User-ID agent, export e import. Los permisos de la REST API se definen por recurso. Esta granularidad es la forma de crear cuentas solo para API: deshabilita todo acceso a la interfaz web y a la CLI y habilita solo los tipos de API que necesita un script.

La autenticación de los administradores puede ser local (contraseña almacenada en el firewall, con complejidad de contraseña y password profiles para el vencimiento) o externa mediante un perfil de autenticación, como RADIUS o SAML. Con RADIUS, TACACS+ y SAML incluso puedes asignar el rol y el access domain desde el servidor usando atributos específicos del fabricante (vendor-specific attributes), de modo que las cuentas no necesitan existir localmente.

Da seguimiento a lo que hacen los administradores en el Config log, que registra quién cambió qué, y en el System log para los inicios de sesión. Habilita la configuración de bloqueo (lockout) en los perfiles de autenticación para que los fallos repetidos bloqueen la cuenta.

Términos clave

Dynamic role (rol dinámico)
Un rol de administrador integrado, como Superuser o Device Administrator, que se actualiza automáticamente con las funciones nuevas.
Admin role profile (perfil de rol de administrador)
Un rol personalizado que define permisos por área para la interfaz web, XML API, REST API y CLI; debe mantenerse manualmente después de las actualizaciones.
superreader
Un nivel de rol de CLI que permite acceso de solo lectura a toda la CLI.
Vsys administrator (administrador de vsys)
Un rol restringido a administrar sistemas virtuales específicos en un firewall multi-vsys.
Ejemplo real

Un script de monitoreo solo necesita extraer los logs de amenazas. Creas un admin role profile con todas las áreas de la interfaz web deshabilitadas, la CLI configurada en none y solo el tipo Log de la XML API habilitado; luego creas una cuenta con ese perfil y generas una API key para ella. Si la clave se filtra, no puede cambiar la configuración.

Consejo para el examen: Los dynamic roles se actualizan automáticamente; los admin role profiles personalizados no. Si una pregunta menciona control granular, acceso solo por API o deshabilitar la CLI, la respuesta es un admin role profile.

Comprueba lo que sabes

¿Por qué un administrador con un rol personalizado podría no ver una función nueva después de una actualización?

Los admin role profiles personalizados no se actualizan automáticamente; hay que habilitar el área nueva en el perfil.

¿Cómo impides que un rol use SSH pero permites la interfaz web?

Configura la opción Command Line del role profile en none.

¿Qué dynamic role no puede crear ni administrar otras cuentas de administrador?

Device Administrator; solo Superuser puede administrar administradores.
