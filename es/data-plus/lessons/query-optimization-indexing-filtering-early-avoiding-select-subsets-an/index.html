CompTIA Data+ DA0-002

Optimización de consultas: índices, filtrar pronto, evitar SELECT *, subconjuntos y tablas temporales

Una consulta que devuelve la respuesta correcta pero demasiado lento sigue siendo un problema. Las consultas lentas retrasan los reportes, compiten con otros usuarios y, en los warehouses en la nube que cobran por datos escaneados o por tiempo de cómputo, cuestan dinero. Data+ espera que conozcas las formas comunes de hacer que las consultas sean más rápidas.

Un índice (index) es una estructura de datos separada, muy parecida al índice de un libro, que permite a la base de datos encontrar las filas que coinciden con un valor sin recorrer toda la tabla. Los índices ayudan más en las columnas usadas en filtros WHERE, condiciones de JOIN y ORDER BY, especialmente cuando la consulta selecciona una pequeña fracción de las filas. No son gratuitos: ocupan almacenamiento y ralentizan las inserciones y actualizaciones, porque el índice también debe mantenerse. Envolver una columna indexada en una función, como WHERE YEAR(order_date) = 2025, puede impedir que la base de datos use el índice; WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01' sí puede usarlo.

Filtra pronto y filtra en la base de datos. Aplica las condiciones WHERE lo antes posible, incluso dentro de subconsultas y antes de los joins, para que lleguen menos filas a los pasos costosos. Traer millones de filas a una herramienta de BI o a una hoja de cálculo para filtrarlas allí mueve muchos más datos de los necesarios.

Evita SELECT *. Seleccionar todas las columnas lee y transfiere datos que no necesitas. En los warehouses columnares, donde el costo y la velocidad dependen de qué columnas se escanean, esto importa muchísimo. Enumerar las columnas también evita que los reportes se rompan cuando alguien agrega o reordena columnas en la tabla.

Trabaja con subconjuntos mientras desarrollas. Prueba la lógica con una muestra o un rango de fechas estrecho, usando LIMIT o una extracción filtrada, y luego ejecuta la consulta completa cuando sea correcta. Las tablas particionadas, por ejemplo por fecha, permiten que el motor omita particiones completas cuando filtras por la columna de partición.

Las tablas temporales y las expresiones de tabla comunes (CTE, escritas con WITH) dividen una consulta compleja en pasos legibles. Una tabla temporal guarda un resultado intermedio, como los pedidos filtrados de este trimestre, para que los pasos posteriores puedan reutilizarlo en lugar de recalcularlo, y algunas bases de datos permiten indexarla. Las CTE mejoran principalmente la legibilidad. La mayoría de las bases de datos también pueden mostrar un plan de ejecución, mediante EXPLAIN o un comando similar, que revela recorridos completos de tablas, índices faltantes y joins costosos.

Términos clave

Index (índice)
Una estructura de datos que acelera la búsqueda de filas por los valores de una columna, a costa de almacenamiento y escrituras más lentas.
Execution plan (plan de ejecución)
La descripción que hace la base de datos de cómo ejecutará una consulta, incluidos los recorridos, los joins y el uso de índices.
Temporary table (tabla temporal)
Una tabla que guarda un resultado intermedio durante la sesión actual para que los pasos posteriores puedan reutilizarlo.
Common table expression, CTE (expresión de tabla común)
Una subconsulta con nombre definida con WITH que hace que las consultas complejas sean más fáciles de leer.
Ejemplo real

La consulta de un reporte diario tardaba ocho minutos. Su plan de ejecución mostraba un recorrido completo de una tabla de pedidos de 300 millones de filas porque el filtro usaba YEAR(order_date). Reescribir el filtro como un rango de fechas que pudiera usar el índice sobre order_date, enumerar solo las seis columnas necesarias y guardar las filas filtradas en una tabla temporal redujo el tiempo de ejecución a menos de treinta segundos.

Consejo para el examen: Indexa las columnas por las que filtras y haces joins, filtra lo antes posible y nombra solo las columnas que necesitas. Filtrar después de que los datos llegan a la herramienta de BI es la respuesta lenta.

Comprueba lo que sabes

¿Por qué demasiados índices pueden perjudicar una base de datos transaccional?

Cada inserción, actualización y eliminación también debe actualizar cada índice, lo que ralentiza las escrituras y consume almacenamiento.

¿Cómo reduce el costo evitar SELECT * en un warehouse columnar en la nube?

Los motores columnares escanean solo las columnas referenciadas, así que nombrar menos columnas reduce los datos leídos, lo que determina tanto la velocidad como el costo basado en el escaneo.
