CompTIA Data+ DA0-002

Data warehouses, data marts, data lakes y lakehouses; OLTP vs. OLAP

Las organizaciones guardan los datos en distintos tipos de almacenes según para qué sirven. Data+ espera que sepas distinguirlos y elegir el correcto para cada escenario.

Los sistemas OLTP (procesamiento de transacciones en línea) gestionan las operaciones diarias: recibir pedidos, actualizar inventario, registrar pagos. Manejan muchas lecturas y escrituras pequeñas y simultáneas, y cada una debe ser rápida y confiable. Suelen ser bases de datos relacionales normalizadas. Los sistemas OLAP (procesamiento analítico en línea) existen para analizar el negocio: menos usuarios que ejecutan consultas grandes, principalmente de lectura, que agregan el historial, como los ingresos por región y por trimestre. Ejecutar análisis pesados sobre un sistema OLTP puede ralentizar el negocio, y esa es una de las razones por las que los datos analíticos se copian a otro lugar.

Un data warehouse (almacén de datos) es un repositorio central de datos integrados, limpios y estructurados provenientes de muchos sistemas de origen, organizado para reportes y análisis. Los datos se transforman a un esquema definido antes de cargarlos o durante la carga (schema on write), se conserva el historial y el diseño suele ser un esquema en estrella. Un data mart es un subconjunto más pequeño y centrado en un tema, como un mart de ventas o de finanzas, construido para las necesidades de un departamento. Puede extraerse del warehouse o construirse por separado.

Un data lake (lago de datos) guarda grandes volúmenes de datos sin procesar en su formato nativo, ya sean estructurados, semiestructurados o no estructurados, normalmente en almacenamiento de objetos económico. La estructura se aplica solo cuando se leen los datos (schema on read). Los lagos son adecuados para ciencia de datos y exploración, para conservar datos cuyo uso aún no has decidido, y para almacenar logs, imágenes y JSON. Sin gobernanza pueden convertirse en un data swamp (pantano de datos) en el que nadie confía ni sabe navegar.

Un data lakehouse combina ambas ideas. Los datos viven en formatos de archivo abiertos como Parquet sobre almacenamiento de lago, pero una capa de tablas añade funciones de warehouse: esquemas, transacciones, control de versiones y SQL rápido. El objetivo es que una sola copia de los datos sirva tanto para los reportes de BI como para la ciencia de datos.

Cuando leas un escenario, busca las pistas. Archivos sin procesar de muchos tipos guardados de forma económica para más adelante apuntan a un lago. Historial limpio e integrado para reportes empresariales apunta a un warehouse. Los reportes de un solo departamento apuntan a un data mart. Registrar transacciones a medida que ocurren apunta a OLTP.

Términos clave

OLTP
Online transaction processing (procesamiento de transacciones en línea): sistemas optimizados para muchas lecturas y escrituras pequeñas y rápidas que hacen funcionar el negocio.
OLAP
Online analytical processing (procesamiento analítico en línea): sistemas optimizados para consultas analíticas complejas, principalmente de lectura, sobre datos históricos.
Data warehouse (almacén de datos)
Un repositorio central de datos históricos integrados, limpios y estructurados, modelados para reportes (schema on write).
Data lake (lago de datos)
Un repositorio de datos sin procesar en formatos nativos donde la estructura se aplica al leerlos (schema on read).
Data mart
Un subconjunto temático de datos al estilo warehouse para un equipo o función.
Ejemplo real

Un grupo hospitalario gestiona admisiones y facturación en bases de datos OLTP. Cada noche, los datos limpios fluyen a un warehouse que se usa para los reportes empresariales, con un data mart de finanzas para el equipo del director financiero. La telemetría sin procesar de los dispositivos y los documentos escaneados llegan a un data lake, donde el equipo de ciencia de datos los explora antes de decidir qué vale la pena modelar.

Consejo para el examen: Schema on write significa warehouse; schema on read significa lake. Transacciones significa OLTP; análisis significa OLAP.

Comprueba lo que sabes

¿Por qué las organizaciones evitan ejecutar reportes pesados directamente sobre los sistemas OLTP?

Las consultas analíticas grandes compiten por recursos con las transacciones en vivo y pueden ralentizar o bloquear el sistema operativo; además, los esquemas OLTP normalizados hacen que las consultas de análisis sean complejas.

¿Qué problema intenta resolver un lakehouse?

Le da al almacenamiento de lago funciones de warehouse, como esquemas, transacciones y SQL rápido, para que una sola copia de los datos sirva tanto para BI como para ciencia de datos.
