Fundamentos de aplicaciones seguras: validación de entradas y OWASP Top 10

Las aplicaciones, especialmente las aplicaciones web, están expuestas a cualquier persona en internet y manejan datos valiosos. La mayoría de los ataques a aplicaciones explotan la misma causa raíz: la aplicación confía en entradas que controla un atacante. Como SSCP quizá no escribas código, pero necesitas reconocer las clases de vulnerabilidades comunes, entender las defensas y trabajar con los desarrolladores y las herramientas que encuentran estas fallas.

La validación de entradas significa comprobar todas las entradas en cuanto a tipo, longitud, formato y rango antes de usarlas. Trata todo lo que viene de fuera del límite de confianza como no confiable: campos de formularios, URL, cookies, encabezados, archivos subidos y llamadas a la API. La validación debe hacerse del lado del servidor; la validación del lado del cliente en el navegador mejora la usabilidad, pero se puede evadir fácilmente. La validación por lista de permitidos, que acepta solo patrones buenos conocidos (por ejemplo, un código postal de una longitud y unos caracteres específicos), es más fuerte que intentar bloquear los caracteres malos conocidos. La validación se complementa con la codificación de salida (output encoding), que convierte los caracteres especiales para que los datos se muestren como texto en lugar de ejecutarse en el navegador, y con las consultas parametrizadas, que mantienen los datos separados de los comandos de la base de datos.

El OWASP Top 10, publicado por el Open Worldwide Application Security Project, es una lista de concientización muy utilizada sobre las categorías de riesgo de seguridad más críticas de las aplicaciones web. Se actualiza cada pocos años y las categorías se renombran y reordenan, así que aprende los conceptos en lugar de la clasificación. Entre las categorías que han aparecido en ediciones recientes están: broken access control (usuarios que actúan fuera de sus permisos, como cambiar un ID en una URL para ver el registro de otro usuario); cryptographic failures (datos sensibles sin cifrar o algoritmos débiles); injection (datos no confiables interpretados como comandos, como la inyección SQL o la inyección de comandos del sistema operativo); insecure design (diseño inseguro); security misconfiguration (cuentas predeterminadas, errores demasiado detallados, funciones innecesarias); vulnerable and outdated components (componentes vulnerables y desactualizados); identification and authentication failures (se permiten contraseñas débiles, mal manejo de sesiones); software and data integrity failures (actualizaciones no confiables o deserialización insegura); security logging and monitoring failures (fallas de registro y monitoreo); y server-side request forgery (SSRF), en la que se engaña al servidor para que haga solicitudes a recursos internos. La edición 2025, por ejemplo, integra SSRF dentro de broken access control, amplía los componentes desactualizados a software supply chain failures (fallas de la cadena de suministro de software) y añade el mal manejo de condiciones excepcionales (mishandling of exceptional conditions).

Vale la pena entender dos ataques clásicos. La inyección SQL ocurre cuando una aplicación construye una consulta a la base de datos concatenando la entrada del usuario, lo que permite a un atacante cambiar la lógica de la consulta para leer o modificar datos. La solución central son las consultas parametrizadas (prepared statements), más el mínimo privilegio para la cuenta de la base de datos. El cross-site scripting (XSS) ocurre cuando una aplicación incluye entradas no confiables en una página sin codificarlas, de modo que el navegador de la víctima ejecuta un script proporcionado por el atacante, que puede robar cookies de sesión o actuar como el usuario. Las defensas son la codificación de salida, la validación de entradas, una content security policy y marcar las cookies como HttpOnly. El cross-site request forgery (CSRF) engaña al navegador de un usuario con sesión iniciada para que envíe solicitudes no deseadas; los tokens anti-CSRF y las cookies SameSite lo defienden.

El desarrollo seguro une todo esto: modelado de amenazas durante el diseño, estándares de codificación segura, revisión de código, pruebas estáticas de seguridad de aplicaciones (SAST) sobre el código fuente, pruebas dinámicas (DAST) de las aplicaciones en ejecución, análisis de composición de software para detectar bibliotecas vulnerables, y un firewall de aplicaciones web (WAF) como control compensatorio. Los mensajes de error deben ser genéricos para los usuarios, mientras que la información detallada va a los logs.

Términos clave

Input validation (validación de entradas)
Comprobación del lado del servidor de que la entrada coincide con el tipo, la longitud, el formato y el rango esperados antes de usarla.
Parameterized query (consulta parametrizada)
Una consulta a la base de datos en la que la entrada del usuario se pasa como parámetros de datos y nunca se interpreta como parte del comando SQL.
Cross-site scripting (XSS)
Una falla que permite que un script proporcionado por el atacante se ejecute en los navegadores de otros usuarios porque la salida no se codificó correctamente.
OWASP Top 10
Una lista de concientización, actualizada periódicamente, de las categorías de riesgo de seguridad más críticas de las aplicaciones web.
Ejemplo real

Una prueba de penetración descubre que cambiar el número de pedido en la URL de una tienda muestra los pedidos de otros clientes (broken access control) y que el cuadro de búsqueda refleja la entrada en la página sin codificarla (XSS). Los desarrolladores añaden verificaciones de autorización del lado del servidor en cada consulta de pedidos, codifican la salida y añaden una content security policy; el WAF recibe una regla temporal mientras se despliegan las correcciones.

Consejo para el examen: La mejor solución para la inyección SQL son las consultas parametrizadas, no solo el filtrado de entradas o un WAF. La validación del lado del cliente nunca es suficiente por sí sola, porque los atacantes evaden el navegador por completo.

Comprueba lo que sabes

¿Por qué la validación de entradas debe hacerse en el servidor?

Las comprobaciones del lado del cliente se pueden evadir enviando las solicitudes directamente o alterándolas, así que solo la validación del lado del servidor es confiable.

¿Cuál es la defensa principal contra la inyección SQL?

Las consultas parametrizadas (prepared statements), apoyadas por la validación de entradas y por cuentas de base de datos con mínimo privilegio.

Un usuario cambia un ID de cuenta en una URL y ve los datos de otro usuario. ¿Qué categoría es esta?

Broken access control (control de acceso roto).
