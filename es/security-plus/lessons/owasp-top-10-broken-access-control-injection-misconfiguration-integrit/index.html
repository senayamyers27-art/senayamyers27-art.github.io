CompTIA Security+ SY0-701

OWASP Top 10: control de acceso roto, inyección, configuración incorrecta, fallas de integridad y SSRF

El Open Worldwide Application Security Project (OWASP) es una comunidad sin fines de lucro que publica guías gratuitas sobre la seguridad de las aplicaciones web. Su documento más conocido, el OWASP Top 10, clasifica las categorías de riesgo de seguridad más críticas de las aplicaciones web con base en datos del mundo real. Se actualiza cada pocos años, así que el orden y los nombres exactos cambian, pero las categorías centrales son duraderas y Security+ espera que las reconozcas junto con sus defensas. Los desarrolladores usan la lista para priorizar la programación segura, y los equipos de seguridad la usan para definir el alcance de las pruebas y de la revisión de código.

El control de acceso roto (broken access control) ha estado en el primer lugar en las ediciones recientes. Significa que los usuarios pueden actuar fuera de los permisos previstos: ver la cuenta de otro cliente cambiando un ID en la URL (una referencia directa insegura a objetos), llegar a páginas de administración sin ser administrador o modificar datos que solo deberían leer. Ocurre cuando la autorización se verifica en la interfaz de usuario, pero no en el servidor, o no se verifica en cada solicitud. Defensas: denegar por defecto, aplicar la autorización en el servidor en cada solicitud, comprobar que el usuario que inició sesión es el dueño del registro que pide, y registrar y alertar sobre las fallas de control de acceso.

La inyección ocurre cuando una entrada no confiable se envía a un intérprete como parte de un comando o una consulta, de modo que el intérprete trata los datos como código. La inyección SQL contra bases de datos es el caso clásico; otras son la inyección de comandos del sistema operativo y la inyección LDAP. El cross-site scripting (XSS) se agrupa dentro de la inyección en las ediciones recientes. Las defensas principales son las consultas parametrizadas (prepared statements), que mantienen separados los datos y el código, además de la validación de entradas en el servidor, la codificación de salidas y las cuentas de base de datos con privilegio mínimo. La configuración de seguridad incorrecta (security misconfiguration) abarca valores predeterminados inseguros, funciones innecesarias que quedan habilitadas, cuentas predeterminadas, mensajes de error detallados que revelan trazas de la pila, encabezados de seguridad faltantes y almacenamiento en la nube de lectura pública. Las defensas son las líneas base endurecidas, las verificaciones automatizadas de configuración y eliminar todo lo que no se necesite.

Las fallas de integridad del software y de los datos ocurren cuando se confía en código o datos sin verificarlos. Algunos ejemplos son las aplicaciones que instalan actualizaciones sin comprobar las firmas, los pipelines de compilación que descargan dependencias de fuentes no confiables y la deserialización insegura, en la que una aplicación reconstruye objetos a partir de datos controlados por el atacante. Los ataques a la cadena de suministro de la época de 2020, que insertaron código malicioso en actualizaciones legítimas de fabricantes, son el ejemplo de manual. Defensas: firmas digitales en las actualizaciones y los paquetes, repositorios de confianza, fijación y revisión de dependencias, y protección del pipeline de CI/CD.

La falsificación de solicitudes del lado del servidor (SSRF) engaña a un servidor para que haga solicitudes en nombre del atacante. Si una aplicación obtiene una URL proporcionada por el usuario, como una función de vista previa de enlaces o de importación de imágenes, un atacante puede dirigirla a direcciones internas que no puede alcanzar directamente, como paneles de administración internos o el servicio de metadatos de instancias de un proveedor de nube, que puede exponer credenciales. Defensas: validar las direcciones de destino y usar una lista de permitidas, bloquear las solicitudes a rangos internos y de metadatos, desactivar los esquemas de URL innecesarios y segmentar el acceso de red del servidor. Otras categorías del Top 10 incluyen las fallas criptográficas, el diseño inseguro, los componentes vulnerables y desactualizados, las fallas de identificación y autenticación, y las fallas de registro y monitoreo de seguridad.

Recorre un ejemplo de revisión de código. El endpoint de un desarrollador devuelve una factura usando /invoice?id=1043. El revisor nota que el servidor obtiene la factura por su ID, pero nunca comprueba que la factura 1043 pertenezca al cliente que inició sesión, lo cual es control de acceso roto. El mismo endpoint construye su SQL concatenando la cadena del ID, lo cual es un riesgo de inyección. La solución es una consulta parametrizada más una verificación de propiedad en cada solicitud:

-- vulnerable pattern: query built by string concatenation
-- safer pattern: parameterized query plus ownership check
SELECT * FROM invoices WHERE id = ? AND customer_id = ?

Errores comunes: depender de verificaciones del lado del cliente o de campos ocultos de formularios para la autorización; creer que la validación de entradas por sí sola detiene la inyección (la parametrización es el control principal); confundir SSRF (el servidor hace la solicitud maliciosa) con CSRF (la hace el navegador de la víctima); y pensar que un WAF corrige el código inseguro (ayuda como capa compensatoria, pero el código debe corregirse). Palabras clave del examen: 'cambiar el ID en la URL para ver los datos de otro usuario' es control de acceso roto; 'entrada que se pasa a una consulta o un comando' es inyección; 'configuración predeterminada, errores detallados, almacenamiento abierto' es configuración incorrecta; 'actualizaciones sin firmar, deserialización, pipeline comprometido' es falla de integridad; 'el servidor obtiene una URL interna o de metadatos' es SSRF.

Términos clave

OWASP Top 10
Una lista actualizada periódicamente de las categorías de riesgo de seguridad más críticas de las aplicaciones web.
Control de acceso roto (broken access control)
Fallas que permiten a los usuarios actuar fuera de los permisos previstos, como ver los registros de otros.
Referencia directa insegura a objetos (IDOR)
Acceder a un objeto cambiando un identificador porque el servidor no verifica la autorización.
Inyección (injection)
Enviar una entrada no confiable a un intérprete para que se ejecute como parte de un comando o una consulta.
Configuración de seguridad incorrecta (security misconfiguration)
Valores predeterminados inseguros, funciones innecesarias, errores detallados o almacenamiento abierto que debilitan una aplicación.
Falla de integridad del software y los datos
Confiar en código, actualizaciones o datos sin verificar su integridad, como las actualizaciones sin firmar o la deserialización insegura.
Falsificación de solicitudes del lado del servidor (SSRF)
Engañar a un servidor para que haga solicitudes a destinos que elige el atacante, a menudo sistemas internos.
Ejemplo real

Un sitio para compartir fotos permite a los usuarios importar una imagen pegando una URL. Un evaluador proporciona una dirección interna y descubre que el servidor devuelve datos del servicio de metadatos de instancias del proveedor de nube, incluidas credenciales temporales. El equipo corrige la SSRF con una lista de permitidos de hosts externos de imágenes, bloqueando los rangos de direcciones privadas y de metadatos, y trasladando la función de importación a un servicio aislado sin acceso a redes internas ni a credenciales.

Consejo para el examen: SSRF significa que se engaña al servidor para que haga la solicitud; CSRF significa que se engaña al navegador del usuario. Para la inyección, la mejor respuesta casi siempre son las consultas parametrizadas, no solo la validación de entradas.

Comprueba lo que sabes

Un usuario cambia 'account=500' por 'account=501' en una URL y ve el estado de cuenta de otro cliente. ¿Qué categoría es y cuál es la solución?

Control de acceso roto (una referencia directa insegura a objetos); el servidor debe verificar en cada solicitud que el usuario está autorizado para ese registro.

¿Por qué las consultas parametrizadas son más eficaces contra la inyección SQL que filtrar caracteres peligrosos?

Mantienen separados el código y los datos para que la entrada nunca se ejecute como SQL, mientras que los filtros pueden eludirse con trucos de codificación.

Una aplicación instala actualizaciones descargadas por HTTP sin comprobar las firmas. ¿Qué categoría aplica?

Fallas de integridad del software y de los datos, porque se confía en el código sin verificarlo.

¿Qué recurso interno suelen atacar los ataques SSRF contra servidores en la nube y por qué?

El servicio de metadatos de instancias, porque puede exponer credenciales temporales y la configuración del entorno de nube.
