CompTIA Security+ SY0-701

Riesgos de la virtualización: VM escape y VM sprawl

La virtualización permite que un solo servidor físico ejecute muchas máquinas virtuales (VM), cada una con su propio sistema operativo, administradas por un hipervisor. Es la base de los centros de datos modernos y de la nube pública. Ahorra dinero y facilita crear, copiar y mover sistemas, pero introduce sus propios riesgos. Security+ se centra en dos riesgos con nombre propio, el escape de VM (VM escape) y la proliferación de VM (VM sprawl), además de la reutilización de recursos y la seguridad del propio hipervisor. Entenderlos te ayuda a ver por qué los hipervisores deben parchearse con rapidez y por qué cada VM necesita un responsable.

Hay dos tipos de hipervisor. Un hipervisor de tipo 1 (bare-metal) se ejecuta directamente sobre el hardware, como en las plataformas empresariales y de nube; tiene una superficie de ataque pequeña y un alto rendimiento. Un hipervisor de tipo 2 (alojado o hosted) se ejecuta como una aplicación sobre un sistema operativo normal, como el software de virtualización de escritorio que se usa para laboratorios y pruebas; hereda las vulnerabilidades del sistema operativo anfitrión. En ambos casos, el hipervisor es el componente que mantiene separadas las VM, así que su seguridad es crítica: si falla, falla el aislamiento entre las VM.

El escape de VM es un ataque en el que el código que se ejecuta dentro de una VM sale de la máquina virtual e interactúa directamente con el hipervisor o el host. Desde allí, un atacante podría acceder a otras VM del mismo host o controlarlas. El escape de VM normalmente requiere explotar una vulnerabilidad en el hipervisor o en los dispositivos virtuales que emula, como una tarjeta de red virtual o un adaptador gráfico. Es poco común, pero grave, sobre todo en entornos multitenencia donde las VM de distintos clientes comparten hardware. Las defensas incluyen parchear los hipervisores con rapidez, quitar el hardware virtual innecesario de las VM, limitar funciones como las carpetas compartidas y el portapapeles compartido, aislar las VM de alto riesgo en hosts separados y monitorear el host.

La proliferación de VM (VM sprawl) es el crecimiento descontrolado de máquinas virtuales. Como las VM son tan fáciles de crear, se acumulan servidores de prueba, proyectos olvidados y copias antiguas. Nadie les aplica parches, puede que no aparezcan en el inventario ni en el monitoreo, y todavía pueden contener datos sensibles o credenciales antiguas. Cada una es una parte no administrada de la superficie de ataque y además desperdicia recursos y licencias. Las defensas se basan en procesos: exigir aprobación y un responsable para las VM nuevas, etiquetar las VM con su responsable y su propósito, fijar fechas de vencimiento para las VM temporales, realizar descubrimiento y conciliación del inventario con regularidad, y dar de baja de forma segura las máquinas sin uso.

La reutilización de recursos es un riesgo relacionado. Cuando una VM libera memoria, almacenamiento u otros recursos y estos se reasignan a otra, cualquier dato que haya quedado en ellos podría exponerse si no se borró correctamente. Los hipervisores y los proveedores de nube son responsables de borrar los recursos antes de reutilizarlos, lo que es una de las razones por las que importan las garantías de aislamiento de los proveedores. Las instantáneas (snapshots) son otra consideración: son prácticas para revertir cambios, pero pueden contener datos sensibles y estados antiguos sin parches, así que deben protegerse, cifrarse y eliminarse con el tiempo.

Veamos una auditoría que detecta proliferación. La consola de administración del hipervisor de una empresa muestra 410 VM, pero el inventario de activos registra 290. La investigación encuentra 120 VM sin responsable, incluidas 30 que todavía ejecutan un sistema operativo que llegó al fin de su vida útil, varias copias de una base de datos de producción hechas para pruebas y un servidor web de una campaña de marketing ya terminada que sigue accesible desde internet. El equipo contacta a los responsables cuando es posible, apaga y archiva las VM huérfanas durante treinta días, después las elimina de forma segura e introduce etiquetas obligatorias y una conciliación mensual.

Errores comunes: confundir el escape de VM con que simplemente se comprometa una VM (el escape significa específicamente salir hacia el hipervisor o el host); pensar que la proliferación de VM es solo un problema de costos; suponer que, como las VM están aisladas, una VM vulnerable no puede afectar a otras (sí puede si el hipervisor tiene fallas o si las VM comparten redes sin controles); y olvidar incluir las VM y las instantáneas en los procesos de respaldo, parches y monitoreo. Los contenedores tienen un riesgo análogo, el escape de contenedor, que a menudo es más fácil porque los contenedores comparten el kernel del host.

Palabras clave del examen: 'el código dentro de un invitado afecta al host o a otros invitados' y 'sale de la máquina virtual' apuntan al escape de VM, que se corrige principalmente con parches del hipervisor. 'Muchas VM no administradas u olvidadas', 'VM que no están en el inventario' y 'máquinas de prueba sin parches' apuntan a la proliferación de VM, que se corrige con gobernanza e inventario. 'Datos de un inquilino anterior encontrados en el almacenamiento asignado' apunta a la reutilización de recursos. El tipo 1 es bare-metal y más seguro; el tipo 2 se ejecuta sobre un sistema operativo anfitrión.

Términos clave

Hipervisor (hypervisor)
Software que crea y administra máquinas virtuales y las mantiene aisladas entre sí.
Hipervisor de tipo 1 (Type 1 hypervisor)
Un hipervisor bare-metal que se ejecuta directamente sobre el hardware.
Hipervisor de tipo 2 (Type 2 hypervisor)
Un hipervisor alojado que se ejecuta como una aplicación sobre un sistema operativo normal.
Escape de VM (VM escape)
Un ataque en el que el código sale de una máquina virtual para llegar al hipervisor, al host o a otras VM.
Proliferación de VM (VM sprawl)
El crecimiento descontrolado de máquinas virtuales no administradas, sin parches u olvidadas.
Reutilización de recursos (resource reuse)
El riesgo de que queden datos en la memoria o el almacenamiento reasignados de una VM o un inquilino a otro.
Instantánea (snapshot)
Un estado guardado de una VM en un momento dado, que puede contener datos sensibles y vulnerabilidades antiguas.
Ejemplo real

Un proveedor de hipervisores publica una corrección urgente para una falla en un adaptador de red emulado que podría permitir que el código de una VM invitada se ejecute en el host. Una empresa de hosting que ejecuta VM para muchos clientes programa un mantenimiento de emergencia, migra en caliente las cargas de trabajo fuera de cada host, le aplica el parche y devuelve las cargas de trabajo. Hasta que termina de aplicar los parches, cambia las VM de los clientes a otro tipo de adaptador virtual que no está afectado.

Consejo para el examen: El escape de VM se corrige principalmente aplicando parches al hipervisor y reduciendo al mínimo el hardware virtual. La proliferación de VM es un problema de gobernanza que se corrige con inventario, responsables y reglas de ciclo de vida.

Comprueba lo que sabes

¿Por qué el escape de VM es especialmente peligroso en una nube pública?

Las VM de otros clientes pueden compartir el mismo host, así que escapar hacia el hipervisor podría exponer a muchos inquilinos.

¿Qué hace que la proliferación de VM sea un problema de seguridad y no solo de costos?

Las VM olvidadas quedan sin parches ni monitoreo, pueden contener datos sensibles y amplían la superficie de ataque.

¿Qué tipo de hipervisor tiene la superficie de ataque más pequeña y por qué?

El tipo 1, porque se ejecuta directamente sobre el hardware sin un sistema operativo anfitrión completo debajo.

Nombra dos controles que reducen la proliferación de VM.

Exigir aprobación y etiquetas de responsable para las VM nuevas, fijar fechas de vencimiento y conciliar regularmente las VM con el inventario.
