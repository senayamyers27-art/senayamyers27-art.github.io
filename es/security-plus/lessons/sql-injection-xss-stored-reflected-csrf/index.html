CompTIA Security+ SY0-701

Inyección SQL, XSS (almacenado/reflejado) y CSRF

Estos tres ataques a aplicaciones web aparecen en casi todos los exámenes de Security+. Cada uno abusa de un tipo distinto de confianza, y las defensas son diferentes, así que aprende a distinguirlos.

La inyección SQL (SQL injection, SQLi) ataca la base de datos que está detrás de una aplicación. Ocurre cuando una aplicación construye una consulta a la base de datos concatenando la entrada del usuario directamente en el texto de la consulta. Si la entrada contiene sintaxis SQL, como comillas y condiciones adicionales, la base de datos trata parte de la entrada como instrucciones. Un atacante podría saltarse un inicio de sesión, leer tablas que no debería ver o modificar y borrar datos. Las señales en los logs incluyen palabras clave de SQL, comillas y marcadores de comentario en campos de formularios o parámetros de URL, y mensajes de error de la base de datos devueltos a los usuarios. La defensa principal son las consultas parametrizadas (prepared statements), en las que la estructura de la consulta es fija y la entrada del usuario se pasa por separado como datos que nunca pueden cambiar el comando. La validación de entradas, las cuentas de base de datos con privilegio mínimo y un firewall de aplicaciones web agregan capas.

# Seguro: la entrada se pasa como parámetro, nunca se concatena en el texto SQL
cursor.execute("SELECT * FROM users WHERE email = %s", (email,))

El cross-site scripting (XSS) ataca a los usuarios de un sitio web. El atacante logra que el sitio entregue su script a los navegadores de otras personas, donde se ejecuta con la confianza del sitio. El script puede robar cookies de sesión, capturar pulsaciones de teclas, cambiar el contenido de la página o realizar acciones como si fuera el usuario. En el XSS almacenado (stored o persistente), el script malicioso se guarda en el servidor, por ejemplo en un comentario o un campo del perfil, y se ejecuta para todos los que ven esa página, lo que lo hace más peligroso. En el XSS reflejado (reflected), el script se incluye en un enlace manipulado; el servidor lo devuelve en la respuesta, así que solo se ejecuta para la persona que hace clic en ese enlace, que normalmente llega por phishing. Un tercer tipo, el XSS basado en DOM, ocurre por completo en el código del lado del cliente. Las defensas son la codificación de la salida (escapar los datos del usuario cuando se muestran), la validación de entradas, un encabezado Content Security Policy que limita desde dónde se pueden cargar scripts y marcar las cookies de sesión como HttpOnly para que los scripts no puedan leerlas.

El cross-site request forgery (CSRF, a veces pronunciado 'sea-surf' en inglés) engaña al navegador de un usuario que inició sesión para que envíe una solicitud no deseada a un sitio que confía en ese usuario. Como los navegadores adjuntan automáticamente las cookies del sitio, un formulario oculto en una página maliciosa puede hacer que el navegador de la víctima envíe, por ejemplo, un cambio de contraseña o una transferencia de fondos en un sitio bancario donde todavía tiene la sesión iniciada. El atacante nunca ve la respuesta; simplemente provoca la acción. Las defensas incluyen los tokens anti-CSRF (valores únicos e impredecibles en cada formulario que el atacante no puede conocer), los atributos de cookie SameSite y exigir una nueva autenticación para las acciones sensibles.

La forma fácil de recordar la diferencia: el XSS abusa de la confianza del usuario en un sitio web (el sitio le envía al usuario un script malicioso). El CSRF abusa de la confianza del sitio web en el navegador del usuario (el navegador le envía al sitio una solicitud falsificada). La inyección SQL abusa de la confianza de la aplicación en su entrada cuando se comunica con la base de datos.

Términos clave

SQL injection (inyección SQL)
Insertar sintaxis SQL en la entrada de una aplicación para que altere la consulta que se ejecuta en la base de datos.
Stored XSS (XSS almacenado)
Cross-site scripting en el que el script malicioso se guarda en el servidor y se ejecuta para cada persona que ve la página afectada.
Reflected XSS (XSS reflejado)
Cross-site scripting en el que el script viaja en una solicitud, como un enlace manipulado, y se le devuelve solo a ese usuario.
CSRF
Cross-site request forgery, que hace que el navegador de un usuario autenticado envíe una solicitud no deseada a un sitio de confianza.
Parameterized query (consulta parametrizada)
Una consulta a la base de datos cuya estructura es fija y en la que la entrada del usuario se proporciona por separado como datos.
Ejemplo real

Un foro permite a los usuarios publicar comentarios sin codificarlos. Un atacante publica un comentario que contiene un script, y a cada visitante que lee el hilo se le ejecuta el script en su navegador. Los desarrolladores corrigen este XSS almacenado codificando toda la salida y agregando una Content Security Policy.

Consejo para el examen: El XSS almacenado afecta a todos los que ven la página; el XSS reflejado afecta a quien hace clic en el enlace manipulado. El CSRF se detiene con tokens anti-CSRF; la inyección SQL se detiene con consultas parametrizadas.

Comprueba lo que sabes

¿Qué hace que el XSS almacenado sea más peligroso que el XSS reflejado?

El script se guarda en el servidor y se ejecuta para cada usuario que ve la página, sin que cada víctima tenga que hacer clic en un enlace manipulado.

¿Cómo evita un token anti-CSRF las solicitudes falsificadas?

El servidor exige un valor secreto por sesión o por formulario que la página del atacante no puede conocer ni leer, así que las solicitudes falsificadas no lo incluyen y se rechazan.

¿Qué pista en los logs sugiere intentos de inyección SQL?

Campos de formulario o parámetros de URL que contienen palabras clave de SQL, comillas o marcadores de comentario, a menudo con errores de base de datos en las respuestas.
