CompTIA Security+ SY0-701

Inyección SQL, XSS (almacenado/reflejado) y CSRF

Tres ataques a aplicaciones web aparecen en casi todos los exámenes de Security+: la inyección SQL, el cross-site scripting (XSS) y la falsificación de solicitudes entre sitios (CSRF, cross-site request forgery). Los tres abusan de la forma en que una aplicación web confía en los datos que recibe o en el navegador que los envía. Son importantes porque las aplicaciones web están expuestas a todo internet, y un solo formulario vulnerable puede filtrar una base de datos completa de clientes o permitir que un atacante actúe como un usuario con sesión iniciada. El examen se centra en distinguirlos y en elegir la defensa correcta para cada uno, no en escribir los ataques.

La inyección SQL (SQLi) ocurre cuando una aplicación construye una consulta a la base de datos pegando la entrada del usuario directamente en el texto SQL. Si la entrada contiene sintaxis SQL, la base de datos la ejecuta como parte de la consulta. Un atacante puede usar esto para evadir un inicio de sesión, leer tablas que no debería ver, modificar o eliminar datos y, a veces, ejecutar comandos en el servidor de base de datos. Las señales en los logs incluyen palabras clave de SQL, comillas y secuencias de comentario dentro de campos de formularios o parámetros de URL, además de mensajes de error de la base de datos devueltos a los usuarios. La defensa principal son las consultas parametrizadas (sentencias preparadas o prepared statements), en las que la estructura de la consulta es fija y la entrada del usuario se pasa por separado como datos, de modo que nunca puede cambiar el comando. Los controles de apoyo son la validación de entrada del lado del servidor, los procedimientos almacenados usados de forma segura, las cuentas de base de datos con privilegio mínimo, los mensajes de error genéricos y un firewall de aplicaciones web (WAF) como capa adicional.

El cross-site scripting (XSS) ocurre cuando una aplicación incluye entrada no confiable en una página web sin codificarla, de modo que el navegador de la víctima ejecuta un script proporcionado por el atacante como si viniera del sitio confiable. Ese script puede robar cookies de sesión, capturar pulsaciones de teclas, cambiar el contenido de la página o hacer solicitudes en nombre del usuario. En el XSS reflejado, la entrada maliciosa forma parte de una solicitud, a menudo un enlace manipulado, y el servidor la refleja de inmediato en la respuesta a esa única víctima; el atacante debe engañar a cada víctima para que haga clic. En el XSS almacenado (persistente), la aplicación guarda la entrada, por ejemplo en un comentario, un campo de perfil o un ticket de soporte, y la entrega a todos los usuarios que ven ese contenido, lo que lo hace más peligroso. El XSS basado en DOM ocurre completamente en el navegador, cuando un script del lado del cliente escribe datos no confiables en la página.

Las defensas contra XSS se centran en la codificación de salida (output encoding): convertir los caracteres especiales en equivalentes seguros según el contexto (HTML, atributo, JavaScript o URL) para que el navegador los muestre como texto en lugar de ejecutarlos. La validación de entrada, un encabezado de Content Security Policy (CSP) que restringe qué scripts puede ejecutar una página, y marcar las cookies de sesión como HttpOnly (para que los scripts no puedan leerlas) agregan capas. Los frameworks web modernos codifican la salida de forma predeterminada, y muchos errores de XSS aparecen cuando los desarrolladores eluden ese comportamiento.

La falsificación de solicitudes entre sitios (CSRF, a veces pronunciada 'sea-surf' en inglés) engaña al navegador de la víctima para que envíe una solicitud no deseada a un sitio en el que la víctima ya inició sesión. Como los navegadores adjuntan las cookies automáticamente a las solicitudes, el sitio objetivo ve una sesión válida y realiza la acción, como cambiar una dirección de correo o transferir dinero. El atacante nunca ve la respuesta; solo provoca la acción. Defensas: tokens anti-CSRF (un valor aleatorio e impredecible vinculado a la sesión que debe incluirse en cada solicitud que cambie el estado), atributos de cookie SameSite que impiden enviar cookies en solicitudes entre sitios, volver a autenticar para acciones sensibles y verificar el encabezado Origin o Referer.

Esta es la corrección central de SQLi tal como la vería un desarrollador en una revisión de código. El patrón vulnerable construye una cadena; el patrón seguro usa un marcador de posición y pasa el valor por separado:

# vulnerable: user input becomes part of the SQL text
query = "SELECT * FROM users WHERE name = '" + name + "'"
# safe: parameterized query, input is always treated as data
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))

Errores comunes: confundir XSS con CSRF (XSS ejecuta el script del atacante en el navegador de la víctima y abusa de la confianza del usuario en un sitio; CSRF hace que el navegador envíe una solicitud y abusa de la confianza del sitio en el navegador); creer que HTTPS detiene estos ataques (no lo hace; viajan dentro de sesiones cifradas legítimas); y depender de la validación del lado del cliente, que los atacantes simplemente evaden. Palabras clave del examen: 'base de datos', 'consulta', 'evasión del inicio de sesión' y 'comilla simple en la entrada' apuntan a inyección SQL. 'Script en un comentario que se muestra a todos los visitantes' es XSS almacenado. 'Enlace malicioso que refleja la entrada' es XSS reflejado. 'Acción no deseada realizada usando la sesión existente de la víctima' es CSRF. Asocia las defensas: consultas parametrizadas para SQLi, codificación de salida y CSP para XSS, tokens anti-CSRF y cookies SameSite para CSRF.

Términos clave

Inyección SQL (SQL injection)
Insertar sintaxis SQL en una entrada que la aplicación coloca en una consulta a la base de datos, cambiando el significado de la consulta.
Consulta parametrizada (parameterized query)
Una consulta con estructura fija en la que la entrada del usuario se pasa por separado como datos; también se llama sentencia preparada.
XSS reflejado (reflected XSS)
Script incluido en una solicitud que el servidor incorpora de inmediato en su respuesta a esa víctima.
XSS almacenado (stored XSS)
Script guardado por la aplicación y entregado a todos los usuarios que ven el contenido afectado.
Codificación de salida (output encoding)
Convertir caracteres especiales para que los navegadores muestren los datos no confiables como texto en lugar de ejecutarlos.
CSRF
Falsificación de solicitudes entre sitios (cross-site request forgery), que hace que el navegador de un usuario con sesión iniciada envíe una solicitud no deseada a un sitio confiable.
Token anti-CSRF
Un valor aleatorio vinculado a la sesión que debe acompañar a las solicitudes que cambian el estado y que los atacantes no pueden adivinar.
Ejemplo real

Un portal de soporte permite que los clientes agreguen notas a los tickets. Un evaluador agrega una nota que contiene un script de prueba inofensivo y descubre que se ejecuta en el navegador de cada agente de soporte que abre el ticket, una falla de XSS almacenado que podría robar las sesiones de los agentes. Los desarrolladores cambian la vista de notas para usar la codificación de salida automática del framework, agregan una Content Security Policy y configuran la cookie de sesión como HttpOnly y SameSite. También encuentran un formulario de cambio de contraseña sin token anti-CSRF y lo corrigen.

Consejo para el examen: El XSS almacenado se guarda en el servidor y afecta a cada visitante; el XSS reflejado rebota en el servidor en una sola solicitud manipulada. CSRF abusa de la confianza del sitio en el navegador del usuario, mientras que XSS abusa de la confianza del usuario en el sitio.

Comprueba lo que sabes

¿Por qué las consultas parametrizadas detienen la inyección SQL?

Fijan de antemano la estructura de la consulta y pasan la entrada solo como datos, así que la entrada nunca puede interpretarse como comandos SQL.

Un script malicioso colocado en una publicación de un foro se ejecuta para cada visitante. ¿Es XSS almacenado o reflejado?

XSS almacenado (persistente), porque la aplicación guarda el script y lo entrega a todos los que lo ven.

¿Por qué un ataque CSRF puede tener éxito aunque el atacante nunca conozca la contraseña de la víctima?

El navegador de la víctima envía automáticamente su cookie de sesión válida con la solicitud falsificada, así que el sitio la trata como legítima.

¿Migrar un sitio a HTTPS evita XSS o CSRF?

No; HTTPS protege los datos en tránsito, pero estos ataques ocurren mediante solicitudes legítimas y contenido de la página dentro de la sesión cifrada.
