CompTIA Security+ SY0-701

Listas de aplicaciones permitidas (allow listing)

Las listas de aplicaciones permitidas (application allow listing, antes llamadas whitelisting) autorizan que se ejecute solo el software aprobado en un sistema y bloquean todo lo demás por defecto. Invierten el modelo tradicional del antivirus. El antivirus usa una lista de denegación: intenta reconocer los programas maliciosos conocidos y los bloquea, lo que significa que el malware completamente nuevo, las herramientas personalizadas y muchas técnicas sin archivos pueden colarse. Una lista de permitidos, en cambio, pregunta '¿este programa es conocido y está aprobado?' y rechaza todo lo que no lo esté, se haya visto antes o no. Eso la convierte en uno de los controles más eficaces contra el ransomware y el software no autorizado. Las guías de seguridad del gobierno y de la industria la incluyen de forma constante entre las medidas defensivas de mayor valor, precisamente porque no depende de reconocer las herramientas del atacante.

Las listas de permitidos pueden identificar las aplicaciones aprobadas de varias formas, con distintas fortalezas. Una regla de hash aprueba un archivo exacto; es muy precisa, pero cada actualización cambia el hash, así que las reglas deben actualizarse con cada parche. Una regla de editor o de certificado aprueba cualquier software firmado por un proveedor de confianza, lo que resiste las actualizaciones y es más fácil de mantener, pero confía en todo lo que ese proveedor firme. Una regla de ruta aprueba todo lo que esté en una ubicación como C:\Program Files; es simple, pero débil si los usuarios pueden escribir en esa carpeta. Muchas implementaciones combinan reglas de editor para el software comercial con reglas de hash para herramientas específicas y reglas de ruta cuidadosamente elegidas para ubicaciones protegidas.

Las herramientas que implementan listas de permitidos incluyen Windows Defender Application Control y AppLocker en Windows, controles similares en las plataformas de gestión de endpoints y de EDR, y mecanismos en macOS y Linux. Las plataformas móviles ya funcionan en gran medida con este modelo y solo permiten aplicaciones firmadas de tiendas aprobadas, a menos que el dispositivo tenga jailbreak o esté habilitada la instalación lateral (sideloading). En los servidores y los sistemas industriales, que ejecutan un conjunto pequeño y estable de software, las listas de permitidos son especialmente prácticas y eficaces.

La implementación requiere cuidado, porque una lista de permitidos estricta puede bloquear trabajo legítimo. El enfoque habitual es: inventariar el software que realmente se usa, construir reglas a partir de ese inventario, ejecutar en modo de auditoría (registrando lo que se bloquearía sin bloquearlo), revisar y corregir las brechas y luego pasar a la aplicación. Después, un proceso de cambios gestiona las solicitudes de software nuevo y las actualizaciones. Empezar por sistemas estables y de alto valor, como servidores, quioscos y terminales de punto de venta, da resultados rápidos antes de abordar los escritorios variados de los usuarios. Los desarrolladores y el personal de TI, que legítimamente ejecutan muchas herramientas, suelen necesitar una política más flexible o estaciones de trabajo administradas separadas, y el proceso de excepciones debe ser lo bastante rápido para que la gente no busque formas de evadirlo.

Veamos un escenario práctico. Las estaciones de trabajo de finanzas de una empresa son blanco de ransomware que llega como adjunto de correo y de usuarios que instalan herramientas de acceso remoto no aprobadas. El equipo implementa una lista de permitidos en modo de auditoría durante dos semanas, descubre que finanzas usa unas treinta aplicaciones, crea reglas de editor para los principales proveedores y reglas de hash para dos herramientas internas, y bloquea la ejecución desde carpetas en las que el usuario puede escribir, como Descargas y Temp. En modo de aplicación, una muestra de ransomware de prueba colocada en Descargas no puede ejecutarse, y el intento de un usuario de instalar una herramienta remota no aprobada se bloquea y se registra para la mesa de ayuda.

Las listas de permitidos deben cubrir más que los ejecutables. Los scripts (PowerShell, JavaScript, VBScript), los instaladores, las bibliotecas y las macros pueden ejecutar código, y los atacantes los usan precisamente porque las listas de permitidos antiguas los ignoraban. Los atacantes también abusan de programas legítimos y permitidos, lo que a veces se llama living off the land (vivir de la tierra), usando herramientas de confianza del sistema para descargar o ejecutar contenido malicioso. Por eso, las buenas políticas de listas de permitidos restringen o monitorean las herramientas integradas que los usuarios comunes no necesitan y combinan la lista de permitidos con un EDR para vigilar el comportamiento.

Errores comunes: confundir las listas de permitidos con las listas de denegación (la lista de permitidos bloquea todo lo que no esté aprobado; la lista de denegación bloquea solo lo que se sabe que es malicioso); usar reglas de ruta en carpetas en las que los usuarios pueden escribir; olvidar que las reglas de hash dejan de funcionar cuando el software se actualiza; implementar directamente en modo de aplicación sin modo de auditoría y provocar interrupciones; y suponer que la lista de permitidos reemplaza a los parches (las aplicaciones aprobadas todavía pueden tener vulnerabilidades).

Palabras clave del examen: 'solo pueden ejecutarse aplicaciones aprobadas', 'bloquear malware desconocido o de día cero' e 'impedir que los usuarios instalen software no autorizado' apuntan a listas de aplicaciones permitidas. 'Bloquear archivos maliciosos conocidos' apunta a una lista de denegación o a un antivirus. 'Sistemas de función fija como quioscos, puntos de venta y controladores industriales' son candidatos clásicos para las listas de permitidos. Cuando una pregunta pida el control más eficaz contra ejecutables desconocidos, la lista de permitidos gana al antivirus.

Términos clave

Lista de aplicaciones permitidas (application allow listing)
Permitir que se ejecute solo el software aprobado y bloquear todo lo demás por defecto.
Lista de denegación (deny listing)
Bloquear software malicioso conocido específico y permitir todo lo demás.
Regla de hash (hash rule)
Una regla de la lista de permitidos que aprueba un archivo por su hash criptográfico exacto.
Regla de editor (publisher rule)
Una regla de la lista de permitidos que aprueba el software firmado con el certificado de un proveedor de confianza.
Regla de ruta (path rule)
Una regla de la lista de permitidos que aprueba los programas ubicados en una carpeta específica.
Modo de auditoría (audit mode)
Ejecutar una política de lista de permitidos que registra los bloqueos que ocurrirían sin aplicarlos.
Living off the land
Atacantes que usan herramientas legítimas integradas para evitar la detección y evadir los controles.
Ejemplo real

Las terminales de punto de venta de un minorista ejecutan las mismas cinco aplicaciones en todas partes. Después de que un competidor sufre malware de clonación de tarjetas, el minorista implementa una lista de permitidos estricta en cada terminal con reglas de editor y de hash. Meses después, un atacante que obtiene las credenciales de un gerente de tienda copia una herramienta de extracción de memoria (memory scraping) en una terminal, pero su ejecución se bloquea y una alerta llega al SOC en cuestión de minutos.

Consejo para el examen: La lista de permitidos es denegación por defecto para el software, así que detiene los ejecutables desconocidos y de día cero que el antivirus basado en firmas no detecta. Las reglas de hash son precisas, pero dejan de funcionar con las actualizaciones; las reglas de editor resisten las actualizaciones.

Comprueba lo que sabes

¿Por qué la lista de aplicaciones permitidas es más eficaz que el antivirus contra el malware completamente nuevo?

Bloquea todo lo que no esté aprobado explícitamente, así que no necesita reconocer el malware como malicioso.

¿Cuál es la principal desventaja de mantenimiento de las reglas de lista de permitidos basadas en hash?

Cada actualización de software cambia el hash del archivo, así que las reglas deben actualizarse cada vez.

¿Por qué las listas de permitidos deben implementarse primero en modo de auditoría?

Para descubrir qué software legítimo se bloquearía y corregir las reglas antes de que la aplicación provoque interrupciones.

¿Por qué es peligrosa una regla de ruta para una carpeta en la que el usuario puede escribir?

Los usuarios o el malware podrían colocar cualquier programa en esa carpeta y se le permitiría ejecutarse.
