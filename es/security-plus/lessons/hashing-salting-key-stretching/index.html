CompTIA Security+ SY0-701

Hashing, salting y key stretching

Una función hash toma una entrada de cualquier tamaño y produce una salida de longitud fija llamada hash, resumen (digest) o huella. La misma entrada siempre da el mismo hash, pero incluso el cambio de un solo carácter produce un resultado completamente distinto. Un buen hash criptográfico es unidireccional, lo que significa que no puedes regresar del hash a la entrada, y resistente a colisiones, lo que significa que es inviable encontrar dos entradas distintas con el mismo hash. El hashing protege la integridad, no la confidencialidad: no oculta los datos, te permite detectar si los datos cambiaron. También es la base de cómo los sistemas deberían almacenar las contraseñas.

Algoritmos comunes que debes reconocer: SHA-256 y el resto de la familia SHA-2, así como SHA-3, son actuales y confiables. MD5 y SHA-1 están rotos en cuanto a resistencia a colisiones y no deben usarse con fines de seguridad, aunque todavía puedes ver MD5 como una suma de verificación rápida. Un código de autenticación de mensajes basado en hash (HMAC) combina un hash con una clave secreta, así que demuestra tanto la integridad como que el emisor conocía la clave, que es como muchos protocolos protegen los mensajes en tránsito. Los hashes también aparecen en las firmas digitales (quien firma, firma un hash del documento en lugar del documento completo), en los registros de blockchain, en el manejo de evidencia forense (un investigador calcula el hash de una imagen de disco para demostrar que no ha cambiado desde su adquisición) y en las herramientas de monitoreo de integridad de archivos que alertan cuando cambian archivos del sistema.

La integridad de archivos es el uso más sencillo. Un fabricante publica el hash SHA-256 de un instalador; después de descargarlo, calculas el hash tú mismo y comparas. Si coinciden, el archivo no se corrompió ni fue manipulado. Hay un detalle importante: si un atacante puede reemplazar tanto el instalador como el hash en la misma página web, la verificación no demuestra nada, por eso los fabricantes también firman sus versiones. En Linux o Windows podrías calcular el hash así:

sha256sum installer.iso
# Windows PowerShell
Get-FileHash .\installer.iso -Algorithm SHA256

Las contraseñas nunca deben almacenarse en texto plano ni con cifrado reversible. En su lugar, el sistema almacena un hash; al iniciar sesión, calcula el hash de lo que escribiste y compara. Sin embargo, los hashes simples tienen debilidades. Las contraseñas idénticas producen hashes idénticos, así que un atacante que roba la base de datos puede ver qué usuarios comparten una contraseña, y puede usar tablas arcoíris (rainbow tables) precalculadas, enormes tablas de búsqueda de pares hash-contraseña, para revertir al instante las contraseñas comunes. Una sal (salt) resuelve esto. Una sal es un valor aleatorio, único para cada usuario, que se agrega a la contraseña antes de calcular el hash y se almacena junto con el hash. No necesita ser secreta; su función es hacer que cada hash sea único para que las tablas precalculadas no sirvan y cada contraseña tenga que atacarse por separado.

El estiramiento de claves (key stretching) hace que cada intento sea lento. En lugar de calcular el hash una vez, una función de key stretching ejecuta el hash muchos miles de veces, o usa un diseño que exige mucha memoria de forma deliberada, de modo que verificar un intento tome, por ejemplo, una fracción de segundo. Eso es imperceptible para un usuario que inicia sesión, pero devastador para un atacante que intenta miles de millones de combinaciones sin conexión. Los algoritmos creados para esto incluyen PBKDF2, bcrypt, scrypt y Argon2. Por lo tanto, un almacén moderno de contraseñas usa una sal por usuario más un algoritmo de key stretching. Algunos sistemas también agregan una pimienta (pepper), un valor secreto que se guarda separado de la base de datos, como capa adicional.

Errores comunes: llamar cifrado al hashing (el cifrado es reversible con una clave; el hashing no está pensado para revertirse); pensar que la sal debe mantenerse en secreto (se almacena en claro junto al hash); creer que una sal hace más lenta la fuerza bruta (frustra el precálculo y oculta duplicados; lo que hace más lento cada intento es el key stretching); y usar un hash rápido, como SHA-256 simple, para contraseñas, lo cual está bien para la integridad de archivos, pero es demasiado rápido para almacenar contraseñas. También se suele suponer que una salida de hash más larga significa que el hash puede guardar más datos; un hash siempre tiene la misma longitud sin importar el tamaño de la entrada, y justamente por eso las colisiones deben existir en teoría y solo se debe confiar en algoritmos resistentes a colisiones.

Las preguntas del examen suelen pedir el mejor control. 'Verificar que una descarga no se modificó' apunta al hashing. 'Frustrar las tablas arcoíris' o 'que contraseñas idénticas tengan hashes distintos' apunta al salting. 'Hacer más lentos los ataques de fuerza bruta' o 'aumentar el factor de trabajo' apunta al key stretching (bcrypt, PBKDF2, Argon2). 'Integridad y autenticación de un mensaje con una clave compartida' apunta a HMAC. Si una opción dice 'descifrar el hash de la contraseña', descártala.

Términos clave

Hash
Una salida unidireccional de longitud fija de una función hash que se usa para verificar la integridad.
Colisión
Dos entradas distintas que producen el mismo hash, lo que rompe la seguridad de una función hash.
Sal (salt)
Un valor aleatorio por usuario que se agrega a una contraseña antes de calcular el hash para que cada hash sea único.
Tabla arcoíris (rainbow table)
Una tabla precalculada de hashes y sus contraseñas correspondientes que se usa para revertir rápidamente hashes sin sal.
Estiramiento de claves (key stretching)
Repetir o reforzar un hash para que cada intento sea lento, con algoritmos como PBKDF2, bcrypt o Argon2.
HMAC
Un código de autenticación de mensajes basado en hash que combina un hash con una clave secreta para dar integridad y autenticidad.
Pimienta (pepper)
Un valor secreto que se agrega a las contraseñas antes de calcular el hash y que se almacena separado de la base de datos de contraseñas.
Ejemplo real

Un atacante roba la tabla de usuarios de una aplicación web. Como los desarrolladores usaron bcrypt con una sal única para cada cuenta, dos usuarios con la contraseña 'Summer2024' tienen hashes distintos, las tablas arcoíris no sirven y cada intento le toma al atacante cientos de milisegundos por cuenta. La empresa de todos modos obliga a restablecer las contraseñas, pero la mayoría de las contraseñas fuertes siguen sin descifrarse mientras se contiene el incidente.

Consejo para el examen: La sal frustra las tablas arcoíris y oculta las contraseñas duplicadas; el key stretching hace más lenta la fuerza bruta. El hashing es para la integridad y nunca se 'descifra'.

Comprueba lo que sabes

Dos usuarios eligen la misma contraseña. Sin salting, ¿qué puede saber un atacante que roba la base de datos?

Que ambas cuentas comparten contraseña, porque sus hashes son idénticos, y descifrar una equivale a descifrar ambas.

¿Por qué SHA-256 es una buena opción para verificar un archivo descargado, pero una mala opción por sí solo para almacenar contraseñas?

Es rápido, lo cual es bueno para verificar la integridad, pero permite a los atacantes probar miles de millones de contraseñas rápidamente.

¿La sal debe mantenerse en secreto? ¿Por qué?

No; se almacena junto al hash, y su propósito es hacer único cada hash, no ser un secreto.

¿Qué control aumenta el tiempo necesario para cada intento de contraseña?

El key stretching, como bcrypt, PBKDF2 o Argon2.
