CompTIA Security+ SY0-701

IaC, serverless, microservicios y contenedores

Las aplicaciones modernas rara vez son un solo programa grande en un solo servidor. Se construyen a partir de partes pequeñas, se despliegan automáticamente y a menudo se ejecutan en infraestructura que el equipo nunca toca directamente. Cada una de estas decisiones de arquitectura cambia dónde está el riesgo, y Security+ te pide reconocer los beneficios y la nueva superficie de ataque de cada una.

La infraestructura como código (infrastructure as code, IaC) significa describir servidores, redes y permisos en archivos de texto (plantillas o scripts) que una herramienta lee para construir el entorno. El beneficio de seguridad es la consistencia: el mismo archivo revisado produce siempre la misma configuración segura, lo que reduce la desviación de configuración y hace que los cambios sean auditables mediante el control de versiones. El riesgo es que un error en una plantilla se copia en todas partes a la vez, y que los secretos, como contraseñas o claves, a veces terminan escritos directamente en los archivos. Escanear las plantillas antes del despliegue y guardar los secretos en un gestor de secretos dedicado atiende ambos problemas.

La computación serverless (a menudo function as a service) te permite subir una función pequeña que el proveedor ejecuta solo cuando un evento la dispara. No gestionas ningún sistema operativo, así que parchear el servidor ya no es tu trabajo. Lo que te sigue preocupando es el código de la función, sus dependencias, los permisos que se le otorgan y los eventos que pueden dispararla. Un error común es darle a una función un acceso mucho más amplio del que necesita, lo que rompe el privilegio mínimo.

Los microservicios dividen una aplicación en muchos servicios pequeños que se comunican entre sí por la red, normalmente mediante interfaces de programación de aplicaciones (APIs). Esto mejora la escalabilidad y permite a los equipos actualizar una parte sin volver a desplegar todo. La contrapartida es que hay muchas más conexiones de red que proteger: cada servicio necesita autenticación, autorización y comunicación cifrada, y las propias APIs se convierten en objetivos. Un API gateway a menudo centraliza la autenticación y la limitación de tasa.

Los contenedores empaquetan una aplicación con sus bibliotecas y configuraciones en una imagen que se ejecuta en un espacio aislado sobre un kernel de host compartido. Los contenedores son más ligeros que las máquinas virtuales porque no llevan cada uno un sistema operativo completo, pero ese kernel compartido significa que el aislamiento es más débil que el que proporciona un hipervisor. Los controles clave son usar imágenes base confiables y mínimas, escanear las imágenes en busca de vulnerabilidades conocidas, no ejecutar los contenedores como root y mantener parcheados el host y la plataforma de orquestación. Las herramientas de orquestación como Kubernetes programan y gestionan muchos contenedores y tienen sus propios controles de acceso, que deben restringirse.

El hilo común es que estos enfoques adelantan la seguridad, llevándola al código y a la configuración. Revisar plantillas, imágenes y permisos antes del despliegue es mucho más barato que encontrar un problema en producción.

Términos clave

Infrastructure as code, IaC (infraestructura como código)
Definir y construir la infraestructura a partir de archivos de configuración con control de versiones en lugar de configurarla manualmente.
Serverless
Un modelo en el que el proveedor ejecuta código disparado por eventos sin que el cliente gestione servidores ni sistemas operativos.
Microservices (microservicios)
Una arquitectura que divide una aplicación en servicios pequeños e independientes que se comunican mediante APIs.
Container (contenedor)
Un paquete ligero de una aplicación y sus dependencias que se ejecuta aislado sobre un kernel de host compartido.
Configuration drift (desviación de configuración)
La divergencia gradual de los sistemas respecto de su configuración prevista y documentada.
Ejemplo real

Un equipo de desarrollo construye su red en la nube a partir de una plantilla IaC. Un revisor nota que la plantilla abre la administración remota a todo internet y contiene una contraseña de base de datos incrustada. Corregir la plantilla una sola vez y mover la contraseña a un gestor de secretos corrige todos los despliegues futuros, en lugar de corregir decenas de servidores uno por uno.

Consejo para el examen: Los contenedores comparten el kernel del host; las máquinas virtuales tienen cada una su propio sistema operativo sobre un hipervisor. Si una pregunta enfatiza un aislamiento más fuerte, ganan las VM; si enfatiza lo ligero y portátil, ganan los contenedores.

Comprueba lo que sabes

¿Cuál es el principal beneficio de seguridad de la infraestructura como código?

Configuraciones consistentes, repetibles y revisables que reducen la desviación y el error humano, con los cambios registrados en el control de versiones.

En un modelo serverless, ¿qué tarea de seguridad ya no le corresponde al cliente?

Parchear y gestionar los servidores y sistemas operativos subyacentes. El cliente sigue siendo dueño del código, las dependencias y los permisos.

¿Por qué se considera que el aislamiento de los contenedores es más débil que el de las VM?

Los contenedores comparten el kernel del sistema operativo del host, así que una falla del kernel puede afectar a todos los contenedores, mientras que cada VM ejecuta su propio sistema operativo sobre un hipervisor.
