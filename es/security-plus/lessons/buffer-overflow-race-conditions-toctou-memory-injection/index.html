CompTIA Security+ SY0-701

Desbordamiento de búfer, condiciones de carrera (TOCTOU) e inyección en memoria

Algunas de las vulnerabilidades más graves provienen de la forma en que los programas gestionan la memoria y los tiempos. No necesitas escribir exploits para Security+, pero sí debes entender cómo surgen estas fallas, cómo se ven sus resultados y cómo se previenen.

Un búfer es un área de memoria de tamaño fijo reservada para guardar datos, como un campo de 64 caracteres para un nombre de usuario. Un desbordamiento de búfer (buffer overflow) ocurre cuando un programa escribe en el búfer más datos de los que puede contener y no verifica la longitud. Los datos sobrantes se derraman en la memoria adyacente y sobrescriben otras variables o información de control, como la dirección a la que el programa regresará cuando termine una función. Los resultados van desde un fallo (una denegación de servicio) hasta que un atacante redirija el programa para ejecutar el código que él elija, a menudo con los privilegios del programa. Los lenguajes que gestionan la memoria de forma manual, como C y C++, son los más propensos a esto. Las defensas incluyen la verificación de límites y la validación de entradas en el código, los lenguajes con seguridad de memoria y las protecciones del sistema operativo: la prevención de ejecución de datos (data execution prevention, DEP), que marca áreas de memoria como no ejecutables, y la aleatorización del diseño del espacio de direcciones (address space layout randomization, ASLR), que coloca el código en direcciones impredecibles para que un atacante no pueda saltar a él de forma confiable. Aplicar parches elimina las fallas de desbordamiento conocidas.

Una condición de carrera (race condition) ocurre cuando el resultado de un programa depende del momento o del orden de eventos que no controla, como dos procesos o hilos que tocan el mismo recurso al mismo tiempo. Una forma específica y frecuente en el examen es time-of-check to time-of-use (TOCTOU). El programa verifica algo, por ejemplo que un usuario puede escribir en un archivo o que una cuenta tiene saldo suficiente, y luego lo usa más tarde. Si el recurso puede cambiar entre la verificación y el uso, un atacante puede cambiarlo en ese intervalo. Una ilustración clásica: un programa con privilegios verifica que un archivo es seguro, y luego un atacante lo reemplaza rápidamente con un enlace a un archivo sensible del sistema antes de que el programa lo abra. Las defensas incluyen bloquear los recursos, hacer que la verificación y el uso sean una sola operación atómica y diseñar el código para evitar el estado compartido.

La inyección en memoria (memory injection) consiste en insertar código malicioso en el espacio de memoria de un proceso legítimo en ejecución y ejecutarlo ahí. La inyección de DLL, en la que se hace que un proceso cargue una biblioteca maliciosa, y el process hollowing, en el que se reemplaza en memoria el código de un proceso legítimo, son ejemplos. Como el código malicioso se ejecuta dentro de un proceso de confianza y a menudo nunca toca el disco como archivo, puede evadir el antivirus tradicional que escanea archivos. Esto está estrechamente relacionado con el malware sin archivos (fileless). Las herramientas de detección y respuesta en endpoints (EDR) que monitorean el comportamiento de los procesos, las listas de aplicaciones permitidas, el privilegio mínimo y mantener los sistemas parcheados ayudan a detectarla y prevenirla.

Las tres categorías comparten un tema: el programa confía en que los datos o el estado son lo que espera. La programación segura, la validación de entradas y las protecciones de la plataforma cierran juntas estas brechas.

Términos clave

Buffer overflow (desbordamiento de búfer)
Escribir en un búfer de memoria más datos de los que puede contener, lo que sobrescribe la memoria adyacente y puede permitir la ejecución de código.
Race condition (condición de carrera)
Una falla en la que el resultado de un programa depende del momento o el orden no controlado de los eventos.
TOCTOU
Time-of-check to time-of-use, una condición de carrera en la que un recurso cambia entre el momento en que se verifica y el momento en que se usa.
Memory injection (inyección en memoria)
Colocar código malicioso en la memoria de un proceso legítimo y ejecutarlo ahí.
ASLR
Address space layout randomization, que aleatoriza las ubicaciones en memoria para dificultar la explotación.
Ejemplo real

Una aplicación bancaria verifica que una cuenta tenga fondos suficientes y, un momento después, descuenta el retiro. Un atacante envía dos solicitudes de retiro en el mismo instante; ambas pasan la verificación antes de que ocurra cualquiera de los descuentos, y la cuenta queda en sobregiro. La solución es bloquear el registro de la cuenta para que la verificación y el descuento ocurran de forma atómica.

Consejo para el examen: TOCTOU se trata del intervalo entre verificar y usar. El desbordamiento de búfer se trata de escribir más allá de un límite de memoria. DEP y ASLR son las defensas del sistema operativo más asociadas con los desbordamientos de búfer.

Comprueba lo que sabes

¿Qué hace DEP para reducir el riesgo de desbordamiento de búfer?

Marca las áreas de datos de la memoria como no ejecutables, para que los datos inyectados no se puedan ejecutar como código.

¿Cuál es el problema central en una vulnerabilidad TOCTOU?

El recurso puede cambiar entre el momento en que se verifica y el momento en que se usa.

¿Por qué la inyección en memoria puede evadir el antivirus basado en archivos?

El código malicioso se ejecuta en memoria dentro de un proceso legítimo y puede que nunca se escriba en el disco como archivo.
