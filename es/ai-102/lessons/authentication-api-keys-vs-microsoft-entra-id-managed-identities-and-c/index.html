Autenticación: claves de API frente a Microsoft Entra ID, identidades administradas y roles RBAC de Cognitive Services

Los servicios de Azure AI aceptan dos tipos de credenciales. Las claves son sencillas: cada recurso tiene dos, y cualquiera que tenga una puede llamar al recurso. Esa sencillez también es el riesgo, porque una clave copiada en el código, en un archivo de configuración o en un mensaje de chat funciona para quien la encuentre, y los registros no pueden decirte qué persona o aplicación la usó. La autenticación con Microsoft Entra ID (antes Azure Active Directory) reemplaza el secreto compartido por un token emitido para una identidad específica, y el acceso se controla con el control de acceso basado en roles de Azure (RBAC).

Para usar Entra ID, el recurso necesita un endpoint con subdominio personalizado (los recursos creados en el portal lo obtienen automáticamente; algunos más antiguos usan un endpoint regional y hay que asignarles un subdominio). Quien llama obtiene un token para el ámbito de Cognitive Services y lo envía como token bearer, y el recurso comprueba que la identidad tenga un rol adecuado. Una vez que las aplicaciones usan tokens, puedes establecer disableLocalAuth en true para que las claves dejen de funcionar por completo.

La mejor identidad para una aplicación alojada en Azure es una identidad administrada. Una identidad asignada por el sistema se crea junto con un recurso, como un App Service o una function app, queda ligada a él y se elimina con él. Una identidad asignada por el usuario es un recurso independiente que puedes asociar a varias aplicaciones. En ambos casos Azure administra la credencial, así que no hay ningún secreto que guardar ni rotar. En el código, DefaultAzureCredential detecta la identidad administrada automáticamente.

Los roles del plano de datos son los que permiten que una identidad llame a las API. Cognitive Services User permite que una identidad llame a las API de la mayoría de los servicios de Azure AI con un token. Cognitive Services OpenAI User permite llamadas de inferencia a las implementaciones de Azure OpenAI, mientras que Cognitive Services OpenAI Contributor además permite crear implementaciones y hacer fine-tuning. Algunos servicios también tienen sus propios roles, como Search Index Data Reader para consultar Azure AI Search. Los roles del plano de administración, como Reader o Contributor, te permiten ver o cambiar el recurso en sí; Reader no puede llamar a las API, y los roles de nivel Contributor que pueden listar claves en la práctica otorgan acceso a los datos a través de las claves, así que asígnalos con cuidado.

Otorga los roles en el ámbito razonable más pequeño, normalmente el recurso individual, y a grupos o identidades administradas en lugar de a personas individuales cuando sea posible.

Términos clave

Managed identity (identidad administrada)
Una identidad de Entra ID para un recurso de Azure cuyas credenciales Azure crea y rota automáticamente.
Cognitive Services User
Un rol RBAC que permite a una identidad llamar a las API del plano de datos de los servicios de Azure AI.
Cognitive Services OpenAI User
Un rol RBAC que permite llamadas de inferencia a implementaciones de Azure OpenAI sin derechos de administración.
Custom subdomain (subdominio personalizado)
Un nombre de endpoint único y específico del recurso, necesario para la autenticación con tokens de Entra ID.
Ejemplo real

Una function app resume tickets de soporte con Azure OpenAI. El ingeniero habilita su identidad administrada asignada por el sistema, le asigna Cognitive Services OpenAI User en el recurso de Azure OpenAI, cambia el código para usar DefaultAzureCredential y luego deshabilita la autenticación con claves en el recurso.

Consejo para el examen: Reader es un rol del plano de administración y no puede llamar a las API de IA. Para llamadas sin claves, elige una identidad administrada más Cognitive Services User (u OpenAI User para Azure OpenAI). La autenticación con tokens necesita un subdominio personalizado.

Comprueba lo que sabes

Una aplicación en App Service debe llamar a Azure AI Vision sin guardar ningún secreto. ¿Qué configuras?

Habilita una identidad administrada en la aplicación, asígnale Cognitive Services User en el recurso de Vision y autentícate con DefaultAzureCredential.

¿Por qué podría fallar la autenticación con Entra ID en un recurso antiguo mientras las claves sí funcionan?

El recurso usa un endpoint regional compartido y no tiene subdominio personalizado, que la autenticación con tokens requiere.
