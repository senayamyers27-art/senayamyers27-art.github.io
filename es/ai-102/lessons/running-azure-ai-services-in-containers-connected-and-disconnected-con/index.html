Ejecución de servicios de Azure AI en contenedores: contenedores conectados y desconectados y configuración de facturación

Algunas capacidades de Azure AI están disponibles como contenedores Docker que ejecutas en tu propio hardware, en Azure Kubernetes Service, en Azure Container Instances o en el perímetro (edge). Los contenedores acercan el modelo a los datos, lo que ayuda cuando los datos deben quedarse en las instalaciones por cumplimiento normativo, cuando la latencia hacia la nube es demasiado alta o cuando necesitas controlar tú mismo el rendimiento. Hay contenedores para funciones seleccionadas, incluidas partes de Language (como sentimiento y detección de idioma), voz a texto y texto a voz de Speech, Translator, Vision Read y Document Intelligence. Comprueba qué funciones se ofrecen antes de planificar.

La mayoría de los contenedores son contenedores conectados. Procesan tus datos localmente, pero deben comunicarse con Azure con regularidad para informar el uso para la facturación. Tus imágenes y textos no se envían a Azure; solo la información de medición. Si el contenedor no puede llegar al endpoint de facturación durante demasiado tiempo, deja de atender solicitudes. Las imágenes de contenedor se descargan de Microsoft Container Registry.

Todo contenedor conectado necesita tres valores al iniciar: ApiKey, la clave de un recurso de Azure correspondiente; Billing, el URI del endpoint de ese recurso; y Eula=accept, que confirma que aceptas la licencia. Si falta cualquiera de ellos, el contenedor no inicia.

docker run --rm -it -p 5000:5000 --memory 8g --cpus 1 \
  mcr.microsoft.com/azure-cognitive-services/textanalytics/sentiment:latest \
  Eula=accept \
  Billing=<your-language-endpoint> \
  ApiKey=<your-language-key>

Una vez en ejecución, el contenedor expone la misma API REST en el puerto local, así que tu aplicación simplemente apunta su endpoint al host del contenedor en lugar de a la nube. Puedes escalar ejecutando varios contenedores detrás de un balanceador de carga y comprobar su estado en los endpoints de estado del contenedor.

Los contenedores desconectados son para entornos sin ninguna conexión a internet, como instalaciones seguras o barcos. No informan el uso en línea. Para usarlos debes presentar una solicitud a Microsoft y ser aprobado, y compras un plan de nivel de compromiso para un volumen determinado. El contenedor se inicia una vez con conexión para descargar un archivo de licencia y después funciona sin conexión.

Recuerda lo que los contenedores no cambian: sigues necesitando un recurso de Azure del tipo correcto para la facturación, y la seguridad del host, de la red y de las imágenes de contenedor pasa a ser tu responsabilidad.

Términos clave

Connected container (contenedor conectado)
Un contenedor que procesa los datos localmente pero informa el uso a Azure para la facturación.
Disconnected container (contenedor desconectado)
Un contenedor aprobado para uso totalmente sin conexión bajo un plan de compromiso, sin informe de uso en línea.
Billing setting (valor Billing)
El valor de inicio del contenedor que contiene el endpoint del recurso de Azure al que se le cobra el uso.
Eula=accept
El argumento de inicio obligatorio que confirma la aceptación de los términos de licencia del contenedor.
Ejemplo real

Un hospital debe mantener las notas de los pacientes dentro de su centro de datos. Ejecuta el contenedor de detección de PII de Language en su clúster de Kubernetes con los valores ApiKey, Billing y Eula apuntando a un recurso de Language. Las notas se analizan localmente y solo los conteos de uso llegan a Azure.

Consejo para el examen: Conoce los tres parámetros obligatorios del contenedor: ApiKey, Billing y Eula. Sin nada de internet significa contenedores desconectados, que requieren aprobación de Microsoft y un plan de compromiso.

Comprueba lo que sabes

¿Qué datos salen del sitio al usar un contenedor conectado?

Solo la medición de uso para la facturación; el texto, las imágenes o el audio procesados se quedan en local.

Un contenedor no inicia. El comando incluye ApiKey y Eula=accept. ¿Qué falta probablemente?

El parámetro Billing con el endpoint del recurso de Azure.
