Monolitos vs. microservicios y modernización de aplicaciones

Una aplicación monolítica se construye e implementa como una sola unidad. Todas sus funciones, como cuentas de usuario, catálogo, carrito, pagos y notificaciones, viven en una sola base de código y se ejecutan como un solo proceso o paquete. Los monolitos son sencillos al principio, pero a medida que crecen se vuelven difíciles de cambiar: una actualización pequeña requiere probar y volver a implementar toda la aplicación, un error o una función sobrecargada puede tumbarlo todo, y escalar significa copiar la aplicación completa aunque solo una parte esté ocupada. Los equipos grandes que trabajan en una sola base de código también se estorban entre sí.

Una arquitectura de microservicios divide una aplicación en servicios pequeños e independientes, cada uno responsable de una capacidad de negocio y a cargo de un equipo pequeño. Los servicios se comunican mediante APIs bien definidas o mediante mensajería como Pub/Sub. Cada servicio se puede desarrollar, implementar y escalar de forma independiente, e incluso puede usar un lenguaje o una base de datos distintos, adecuados a su tarea. Si el servicio de recomendaciones falla, los clientes aún pueden pagar.

Los microservicios traen sus propios costos: más piezas que monitorear, llamadas de red entre servicios, datos distribuidos y pruebas más complejas. Valen la pena para aplicaciones grandes que cambian rápido y con varios equipos, no necesariamente para aplicaciones pequeñas y sencillas. Los contenedores, Kubernetes, Cloud Run, la administración de APIs y las herramientas de observabilidad los hacen prácticos.

Las organizaciones rara vez reescriben un monolito de una sola vez. Un enfoque común, a veces llamado patrón estrangulador (strangler pattern), va separando gradualmente funciones en servicios nuevos detrás de una API o un balanceador de carga, mientras la aplicación antigua sigue funcionando, hasta que el monolito es lo bastante pequeño para retirarlo.

La modernización también incluye prácticas. La integración continua y la entrega continua (CI/CD) automatizan la compilación, las pruebas y la implementación de cada servicio. La infraestructura como código (infrastructure as code) define los entornos en archivos con control de versiones. Junto con la cultura DevOps, esto permite a los equipos lanzar cambios pequeños con frecuencia y de forma segura, que es el verdadero objetivo de negocio de la modernización.

Términos clave

Monolith (monolito)
Una aplicación construida e implementada como una sola unidad.
Microservices (microservicios)
Una arquitectura de servicios pequeños que se implementan de forma independiente y se comunican mediante APIs.
Strangler pattern (patrón estrangulador)
Reemplazar gradualmente partes de un sistema heredado con servicios nuevos hasta que el sistema antiguo pueda retirarse.
Infrastructure as code (infraestructura como código)
Definir y administrar la infraestructura mediante archivos de configuración con control de versiones.
Ejemplo real

El monolito de un minorista en línea necesita un fin de semana completo de lanzamiento para cualquier cambio. El equipo primero mueve la función de búsqueda de productos a un servicio separado en Cloud Run detrás de la misma URL, luego el carrito y luego los pagos. Ahora cada equipo lanza su propio servicio varias veces por semana.

Consejo para el examen: La implementación independiente, el escalado independiente y el aislamiento de fallas son los beneficios clave de los microservicios. La contrapartida es más complejidad operativa, así que convienen a aplicaciones grandes que cambian rápido.
