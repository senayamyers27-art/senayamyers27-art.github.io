Ansible: inventario, comandos ad hoc, playbooks, idempotencia, roles, ansible-vault

Ansible es una herramienta de gestión de configuración y automatización sin agentes (agentless). Un nodo de control se conecta a los hosts administrados por SSH (o WinRM para Windows), envía módulos pequeños, los ejecuta y los elimina. No hace falta instalar nada en los hosts Linux administrados salvo SSH y Python, lo que hace que Ansible sea fácil de adoptar. Linux+ lo usa como el ejemplo principal de configuración automatizada.

El inventario lista los hosts que administra Ansible y los agrupa. Puede estar en formato INI o YAML, por ejemplo /etc/ansible/hosts o un archivo inventory del proyecto:

[web]
web01.example.com
web02.example.com

[db]
db01.example.com ansible_user=admin

Los grupos te permiten apuntar a muchos hosts a la vez, y el grupo especial all incluye a todos los hosts. Las variables se pueden establecer por host, por grupo o en los directorios group_vars/ y host_vars/. Los inventarios dinámicos consultan nubes o CMDB (bases de datos de gestión de configuración) para obtener los hosts actuales. ansible-inventory --graph muestra la estructura, y ansible.cfg establece valores predeterminados como la ruta del inventario y el usuario remoto.

Los comandos ad hoc ejecutan un solo módulo para tareas rápidas: ansible all -m ping prueba la conectividad (una verificación con un módulo de Ansible, no ICMP), ansible web -m ansible.builtin.dnf -a 'name=nginx state=present' -b instala un paquete con escalada de privilegios (-b significa become, normalmente sudo), y ansible db -a 'uptime' usa el módulo command de forma predeterminada.

Los playbooks son archivos YAML que describen el estado deseado como plays y tareas. Cada play apunta a hosts, y cada tarea llama a un módulo con parámetros. Los handlers son tareas que se ejecutan solo cuando un cambio las notifica, como reiniciar un servicio después de que cambia su archivo de configuración. Ejecuta un playbook con ansible-playbook site.yml; --check hace una prueba en seco, --diff muestra los cambios en archivos, --syntax-check valida y --limit web01 restringe los destinos. La salida informa cada tarea como ok (ya correcta), changed o failed. La idempotencia es la idea clave: volver a ejecutar el mismo playbook no debería cambiar nada si el sistema ya está en el estado deseado. Módulos como dnf, apt, copy, template, user, service y lineinfile revisan primero el estado actual y actúan solo si es necesario. Los módulos command y shell no son idempotentes por sí mismos, así que prefiere módulos específicos o agrega protecciones como creates:.

Los roles empaquetan la automatización reutilizable en una estructura de directorios estándar: tasks/, handlers/, templates/ (plantillas Jinja2), files/, vars/, defaults/ y meta/. ansible-galaxy init myrole crea el esqueleto, y las colecciones de Ansible Galaxy agrupan roles y módulos para reutilizarlos. Un playbook aplica roles con una lista roles:.

Los secretos como contraseñas y claves de API nunca deben estar en texto plano en un repositorio. ansible-vault create secrets.yml, edit, encrypt, decrypt y view administran archivos cifrados con AES, y ansible-playbook site.yml --ask-vault-pass o --vault-password-file proporcionan la clave en tiempo de ejecución. ansible-vault encrypt_string cifra un solo valor dentro de un archivo que por lo demás está en texto plano.

Términos clave

Inventory (inventario)
La lista de hosts y grupos administrados, con variables opcionales, a los que apunta Ansible.
Ad hoc command (comando ad hoc)
Un comando ansible puntual que ejecuta un solo módulo contra hosts, como ansible all -m ping.
Playbook
Un archivo YAML de plays y tareas que describe el estado deseado de los hosts.
Idempotence (idempotencia)
La propiedad de que ejecuciones repetidas producen el mismo resultado y no hacen cambios una vez que el estado es correcto.
ansible-vault
Una herramienta que cifra archivos o cadenas que contienen secretos usados por Ansible.
Ejemplo real

Para desplegar un sshd_config endurecido en 60 servidores, escribes un rol con una tarea template que notifica a un handler 'reload sshd'. La primera ejecución de ansible-playbook informa changed en cada host; una segunda ejecución informa solo ok, lo que demuestra la idempotencia. La contraseña de administrador compartida que usa una tarea se guarda en un archivo group_vars cifrado con vault.

Consejo para el examen: Ansible no usa agentes y funciona por push a través de SSH; cuando una pregunta lo compara con Puppet o Chef, esa diferencia suele ser la clave.

Comprueba lo que sabes

¿Qué prueba realmente ansible web -m ping?

Que Ansible puede conectarse por SSH a los hosts del grupo web y ejecutar un módulo con Python; no es un ping ICMP.

¿Por qué los módulos command y shell se consideran no idempotentes?

Se ejecutan siempre, sin importar el estado actual, a menos que se protejan con opciones como creates o removes.

¿Cómo debería guardarse una contraseña de base de datos que se usa en un playbook?

Cifrada con ansible-vault y descifrada en tiempo de ejecución con una contraseña de vault.
