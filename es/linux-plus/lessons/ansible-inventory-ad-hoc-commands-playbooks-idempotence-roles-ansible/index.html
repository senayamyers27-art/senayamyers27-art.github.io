Ansible: inventario, comandos ad hoc, playbooks, idempotencia, roles, ansible-vault

Ansible es una herramienta de gestión de configuración y automatización sin agentes (agentless). Un nodo de control se conecta a los hosts administrados por SSH (o WinRM para Windows), envía pequeños programas llamados módulos, los ejecuta y los elimina. No hace falta instalar nada en los hosts Linux administrados, salvo SSH y Python, lo que facilita adoptar Ansible. Linux+ lo usa como el ejemplo principal de configuración automatizada, así que aprende su vocabulario: inventario, módulo, tarea, play, playbook, handler, rol y vault.

El inventario lista los hosts que Ansible administra y los agrupa. Puede estar en formato INI o YAML, por ejemplo /etc/ansible/hosts o un archivo inventory del proyecto. Los grupos te permiten apuntar a muchos hosts a la vez, y el grupo especial all incluye todos los hosts. Los patrones de host seleccionan los destinos con precisión: web:db significa cualquiera de los dos grupos, web:&prod significa los hosts que están en ambos y all:!db significa todo excepto db. Las variables pueden definirse por host, por grupo o en los directorios group_vars/ y host_vars/. Los inventarios dinámicos consultan nubes o CMDB (bases de datos de gestión de configuración) para obtener los hosts actuales. ansible-inventory --graph muestra la estructura, y ansible.cfg define valores predeterminados como la ruta del inventario y el usuario remoto.

[web]
web01.example.com
web02.example.com

[db]
db01.example.com ansible_user=admin

Los comandos ad hoc ejecutan un solo módulo para tareas rápidas: ansible all -m ping prueba la conectividad (una verificación de módulo de Ansible sobre SSH, no ICMP), ansible web -m ansible.builtin.dnf -a 'name=nginx state=present' -b instala un paquete con escalada de privilegios (-b significa become, normalmente sudo) y ansible db -a 'uptime' usa el módulo command por defecto. ansible-doc dnf muestra las opciones y ejemplos de cualquier módulo. Los playbooks son archivos YAML que describen el estado deseado como plays y tareas. Cada play apunta a unos hosts, y cada tarea invoca un módulo con parámetros. Los handlers son tareas que solo se ejecutan cuando un cambio las notifica, como recargar un servicio después de que cambia su archivo de configuración. Ejecuta un playbook con ansible-playbook site.yml; --check hace una ejecución de prueba (dry run), --diff muestra los cambios en archivos, --syntax-check valida y --limit web01 restringe los destinos. La salida informa cada tarea como ok (ya correcta), changed o failed, con un resumen (recap) por host.

La idempotencia es la idea clave: volver a ejecutar el mismo playbook no debería cambiar nada si el sistema ya está en el estado deseado. Módulos como dnf, apt, copy, template, user, service y lineinfile revisan primero el estado actual y actúan solo si hace falta. Los módulos command y shell no son idempotentes por sí mismos, así que prefiere módulos creados para cada propósito o agrega protecciones como creates:. Los roles empaquetan automatización reutilizable en una estructura de directorios estándar: tasks/, handlers/, templates/ (plantillas Jinja2), files/, vars/, defaults/ y meta/. ansible-galaxy init myrole crea el esqueleto, y las colecciones agrupan roles y módulos para reutilizarlos. Un playbook aplica roles con una lista roles:. Los secretos, como contraseñas y claves de API, nunca deben quedar en texto plano en un repositorio. ansible-vault create, edit, encrypt, decrypt y view administran archivos cifrados con AES, --ask-vault-pass o --vault-password-file proporcionan la clave en tiempo de ejecución, y ansible-vault encrypt_string cifra un solo valor.

Considera un ejemplo práctico. Para desplegar un sshd_config endurecido en 60 servidores, creas un rol con ansible-galaxy init sshd_hardening. Su tarea usa el módulo template para generar sshd_config.j2 con validate: sshd -t -f %s, de modo que nunca se instala un archivo incorrecto, y notifica a un handler llamado reload sshd. Primero ejecutas ansible-playbook site.yml --check --diff --limit web01, revisas el diff y luego lo ejecutas para todos los hosts. La primera ejecución informa changed en todos los hosts y el handler se dispara; una segunda ejecución informa solo ok, lo que demuestra la idempotencia. La contraseña de administrador compartida que usa otra tarea vive en un group_vars/all/vault.yml cifrado con vault.

Errores comunes: usar shell para todo, lo que hace que los playbooks no sean idempotentes; errores de indentación en YAML, que detectan --syntax-check o ansible-lint; reiniciar servicios en cada ejecución en lugar de usar handlers; olvidar -b cuando una tarea necesita root; hacer commit de secretos sin cifrar o del archivo de contraseña del vault; esperar que ansible -m ping pruebe ICMP cuando un firewall bloquea el ping pero SSH funciona; y apuntar a all cuando querías un solo grupo, algo que --limit o un patrón de host cuidadoso previenen.

Las preguntas del examen usan señales claras. 'Sin agentes, usa SSH' es Ansible. 'Lista de hosts administrados y grupos' es el inventario. 'Tarea puntual en muchos servidores' es un comando ad hoc. 'Ejecutarlo dos veces no hace más cambios' es idempotencia. 'Ejecutar solo cuando cambia un archivo de configuración' es un handler. 'Estructura reutilizable de tareas, plantillas y valores predeterminados' es un rol. 'Cifrar una contraseña usada por un playbook' es ansible-vault. 'Previsualizar los cambios sin aplicarlos' es --check.

Términos clave

Inventario (inventory)
La lista de hosts administrados y grupos, en INI o YAML, opcionalmente con variables de host y de grupo.
Módulo (module)
Una pequeña unidad de trabajo, como dnf o copy, que Ansible envía a un host y ejecuta.
Comando ad hoc
Un solo módulo ejecutado desde la línea de comandos contra un patrón de host, como ansible all -m ping.
Playbook
Un archivo YAML de plays y tareas que describe el estado deseado de los hosts de destino.
Handler
Una tarea que se ejecuta solo cuando un cambio la notifica, normalmente para reiniciar o recargar un servicio.
Idempotencia (idempotence)
La propiedad de que repetir una operación deja sin cambios un sistema que ya está correcto.
ansible-vault
La herramienta que cifra archivos o cadenas que contienen secretos para usarlos en playbooks.
Ejemplo real

Para desplegar un sshd_config endurecido en 60 servidores, escribes un rol con una tarea template que notifica a un handler 'reload sshd'. La primera ejecución de ansible-playbook informa changed en todos los hosts; una segunda ejecución informa solo ok, lo que demuestra la idempotencia. La contraseña de administrador compartida que usa una tarea se guarda en un archivo group_vars cifrado con vault y se proporciona con --ask-vault-pass.

Consejo para el examen: Ansible no usa agentes y funciona por push sobre SSH; cuando una pregunta lo contrasta con Puppet o Chef, esa diferencia suele ser el punto clave. command y shell no son idempotentes a menos que se protejan.

Comprueba lo que sabes

¿Qué prueba realmente ansible web -m ping?

Que Ansible puede conectarse por SSH a los hosts del grupo web y ejecutar un módulo con Python; no es un ping ICMP.

¿Por qué los módulos command y shell se consideran no idempotentes?

Se ejecutan siempre sin importar el estado actual, a menos que se protejan con opciones como creates o removes.

¿Cómo debe almacenarse la contraseña de una base de datos usada en un playbook?

Cifrada con ansible-vault y descifrada en tiempo de ejecución con una contraseña de vault.

¿Cómo previsualizas lo que cambiaría un playbook sin cambiar nada?

Ejecuta ansible-playbook con --check, y agrega --diff para ver los cambios en el contenido de los archivos.
