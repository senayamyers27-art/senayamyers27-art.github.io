Git: clone, branch/switch, add, commit, merge, rebase, revert, pull requests

Git es un sistema de control de versiones distribuido: cada copia de un repositorio contiene el historial completo, y registras los cambios como commits. Los administradores usan Git para scripts, código de gestión de configuración, definiciones de infraestructura y documentación, y es la base de GitOps y de CI/CD (integración continua y entrega continua). Linux+ espera soltura con Git en el día a día: obtener un repositorio, registrar cambios, trabajar en ramas, combinar trabajo y deshacer errores de forma segura.

Git tiene tres áreas: el árbol de trabajo (tus archivos), el área de preparación o índice (los cambios preparados para el siguiente commit) y el historial del repositorio. git clone <url> copia un repositorio remoto, incluido su historial, y configura un remoto llamado origin. git init inicia un repositorio nuevo en el directorio actual. git status muestra qué cambió y qué está preparado, y git diff muestra los cambios no preparados (git diff --staged para los preparados). Define tu identidad una sola vez con git config --global user.name 'Your Name' y git config --global user.email.

git add file prepara los cambios, git add -p te permite preparar partes de archivos y git commit -m 'message' registra la instantánea preparada. Escribe mensajes que expliquen por qué se hizo el cambio. git log --oneline --graph muestra el historial. git push envía los commits al remoto y git pull descarga e integra los cambios remotos; git fetch solo descarga sin cambiar tu rama. Un archivo .gitignore lista los archivos que Git no debe rastrear, como la salida de compilación o secretos locales. Las ramas son punteros ligeros que te permiten trabajar de forma aislada: git branch las lista, git branch feature-x crea una y git switch feature-x te mueve a ella (git switch -c feature-x hace ambas cosas). El antiguo git checkout hace lo mismo y más, así que git checkout -b feature-x es equivalente. Mantén estable la rama principal y trabaja en ramas de funcionalidad de corta duración.

Hay dos formas de combinar ramas. git merge feature-x, ejecutado desde main, une los historiales; si main no ha avanzado, es un fast-forward; de lo contrario, Git crea un commit de merge con dos padres. git rebase main, ejecutado desde la rama de funcionalidad, vuelve a aplicar tus commits encima del main más reciente, lo que produce un historial lineal pero con nuevos ID de commit. Como el rebase reescribe el historial, nunca hagas rebase de commits que otros ya descargaron. Cualquiera de los dos puede producir conflictos cuando ambos lados cambiaron las mismas líneas; Git los marca con <<<<<<<, ======= y >>>>>>> en el archivo, lo editas hasta el resultado correcto, ejecutas git add y continúas con git commit o git rebase --continue. git merge --abort o git rebase --abort te devuelven al punto de partida.

Deshacer cambios también tiene dos estilos. git revert <commit> crea un nuevo commit que revierte uno anterior, lo cual es seguro en ramas compartidas porque el historial se conserva. git reset mueve el puntero de la rama hacia atrás (--soft mantiene los cambios preparados, --mixed los mantiene sin preparar, --hard los descarta), lo que reescribe el historial y corresponde a trabajo local no publicado. git restore file descarta las ediciones sin commit de un archivo, git restore --staged file lo quita del área de preparación y git stash guarda temporalmente el trabajo en curso. Un pull request (llamado merge request en algunas plataformas) no es un comando de Git sino un flujo de trabajo de la plataforma de hospedaje: publicas una rama y pides que se fusione. Tus compañeros revisan el diff, se ejecutan verificaciones automáticas y, una vez aprobada, la rama se fusiona. Las reglas de protección de ramas pueden exigir revisiones y verificaciones exitosas, lo que lleva el control de cambios al código de infraestructura.

Considera un ejemplo práctico. Clonas el repositorio de Ansible del equipo, ejecutas git switch -c fix-ntp, editas la plantilla de chrony y ejecutas git add -p para preparar solo las líneas relevantes. git commit -m 'Use internal NTP pool for chrony' lo registra, y git push -u origin fix-ntp publica la rama. Abres un pull request; el pipeline analiza el playbook con un linter y un colega lo aprueba, así que la rama se fusiona. Al día siguiente, otro commit en main resulta romper la configuración de DNS en todos los servidores. En lugar de reescribir el historial compartido con reset, ejecutas git revert <commit-id> y publicas, y el pipeline vuelve a aplicar la configuración corregida. Tanto el error como su reversión siguen visibles en git log para la revisión.

Errores comunes: hacer commit de secretos, que permanecen en el historial incluso después de que un commit posterior los elimine; olvidar preparar un archivo, de modo que falta en el commit; ejecutar git reset --hard o hacer rebase en una rama compartida y forzar el push, lo que rompe la copia de todos los demás; confundir fetch (solo descargar) con pull (descargar e integrar); dejar marcadores de conflicto en un archivo; y trabajar directamente en main en lugar de en una rama.

La redacción del examen suele ser directa. 'Copiar un repositorio remoto' es git clone. 'Preparar cambios para el siguiente commit' es git add y el área de preparación. 'Crear una rama y moverse a ella' es git switch -c o git checkout -b. 'Historial lineal' apunta a rebase, y 'conservar ambos historiales con un commit de merge' a merge. 'Deshacer de forma segura un commit ya publicado' es git revert, mientras que 'descartar commits locales' es git reset. 'Descargar sin cambiar la rama de trabajo' es git fetch. 'Revisión por pares antes de fusionar' es un pull request.

Términos clave

Commit
Una instantánea registrada de los cambios preparados, con autor, mensaje e ID único.
Área de preparación (staging area)
El índice donde se preparan los cambios con git add antes de hacer commit.
Rama (branch)
Un puntero móvil a una línea de commits, usado para trabajar en cambios de forma aislada.
merge frente a rebase
merge une historiales, posiblemente con un commit de merge; rebase vuelve a aplicar commits sobre una nueva base para obtener un historial lineal con nuevos ID.
git revert
Crea un nuevo commit que deshace uno anterior sin reescribir el historial.
git reset
Mueve el puntero de la rama a un commit anterior, reescribiendo el historial local; --hard además descarta los cambios.
Pull request
Una solicitud en la plataforma de hospedaje para revisar y fusionar una rama publicada, a menudo condicionada a verificaciones y aprobaciones.
Ejemplo real

El commit de un colega en el repositorio compartido de Ansible rompió la configuración de DNS en todos los servidores. En lugar de reescribir el historial compartido con reset, ejecutas git revert <commit-id>, publicas la corrección y el pipeline vuelve a aplicar la configuración corregida. Tanto el error como su reversión siguen visibles en git log para la revisión posterior al incidente.

Consejo para el examen: En ramas compartidas, elige revert en lugar de reset y merge en lugar de rebase; los comandos que reescriben el historial corresponden solo a trabajo local no publicado.

Comprueba lo que sabes

¿Qué comando crea una nueva rama llamada fix-dns y cambia a ella?

git switch -c fix-dns (o git checkout -b fix-dns).

¿Cuál es la diferencia entre git fetch y git pull?

fetch descarga los cambios remotos sin alterar tu rama; pull los descarga y luego los fusiona o les hace rebase en tu rama actual.

¿Cómo registras solo los cambios preparados con un mensaje?

git commit -m 'message'.

¿Por qué se prefiere git revert a git reset para un commit ya publicado en main?

revert agrega un nuevo commit y mantiene intacto el historial compartido, mientras que reset reescribe un historial que otros ya descargaron.
