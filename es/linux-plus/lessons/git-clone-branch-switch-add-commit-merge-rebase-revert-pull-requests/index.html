Git: clone, branch/switch, add, commit, merge, rebase, revert, pull requests

Git es un sistema de control de versiones distribuido: cada copia de un repositorio contiene el historial completo, y registras los cambios como commits. Los administradores usan Git para scripts, código de gestión de configuración, definiciones de infraestructura y documentación, y es la base de GitOps y de CI/CD. Linux+ espera soltura con Git en el día a día.

Git tiene tres áreas: el árbol de trabajo (tus archivos), el área de preparación o índice (staging area, los cambios preparados para el siguiente commit) y el historial del repositorio. git clone <url> copia un repositorio remoto, incluido el historial, y configura un remoto llamado origin. git init inicia un repositorio nuevo. git status muestra qué cambió y qué está preparado, y git diff muestra los cambios no preparados (git diff --staged para los preparados). Configura tu identidad una sola vez con git config --global user.name y user.email.

git add file prepara los cambios, git add -p te permite preparar partes de archivos y git commit -m 'message' registra la instantánea preparada con un mensaje. Escribe mensajes que expliquen por qué se hizo el cambio. git log --oneline --graph muestra el historial. git push envía los commits al remoto y git pull obtiene e integra los cambios remotos; git fetch solo descarga sin cambiar tu rama. Un archivo .gitignore lista los archivos que Git no debe rastrear, como la salida de compilación o secretos locales.

Las ramas son punteros ligeros que te permiten trabajar en cambios de forma aislada. git branch lista las ramas, git branch feature-x crea una y git switch feature-x se mueve a ella (git switch -c feature-x hace ambas cosas). El más antiguo git checkout hace lo mismo y más. Mantén estable la rama principal y trabaja en ramas de funcionalidad (feature branches) de corta duración.

Hay dos formas de combinar ramas. git merge feature-x, ejecutado desde main, une los historiales; si main no ha avanzado, es un fast-forward, y si no, Git crea un commit de fusión (merge commit) con dos padres. git rebase main, ejecutado desde la rama de funcionalidad, vuelve a aplicar tus commits encima del main más reciente, produciendo un historial lineal pero con nuevos ID de commit. Como el rebase reescribe el historial, nunca hagas rebase de commits que otros ya descargaron. Cualquiera de los dos puede producir conflictos cuando ambos lados cambiaron las mismas líneas; Git los marca con <<<<<<<, ======= y >>>>>>> en el archivo, editas hasta obtener el resultado correcto, haces git add y continúas con git commit o git rebase --continue.

Deshacer cambios también tiene dos estilos. git revert <commit> crea un commit nuevo que revierte uno anterior, seguro para ramas compartidas porque el historial se conserva. git reset mueve el puntero de la rama hacia atrás (--soft mantiene los cambios preparados, --hard los descarta), lo que reescribe el historial y es para trabajo local que no se ha enviado. git restore file descarta las ediciones sin commit de un archivo y git stash guarda temporalmente el trabajo en curso.

Un pull request (llamado merge request en algunas plataformas) no es un comando de Git, sino un flujo de trabajo de la plataforma de alojamiento: envías (push) una rama y pides que se fusione. Los compañeros revisan las diferencias, se ejecutan las verificaciones automáticas de CI y, una vez aprobada, la rama se fusiona. Las reglas de protección de ramas pueden exigir revisiones y verificaciones aprobadas, llevando el control de cambios al código de infraestructura.

Términos clave

Commit
Una instantánea registrada de los cambios preparados, con autor, marca de tiempo, mensaje y referencia al padre.
Staging area (área de preparación)
El índice donde se preparan los cambios con git add antes de hacer commit.
merge vs rebase
merge une historiales, posiblemente con un commit de fusión; rebase vuelve a aplicar los commits sobre una nueva base para un historial lineal.
git revert
Crea un commit nuevo que deshace uno anterior sin reescribir el historial.
Pull request
Un flujo de trabajo de la plataforma que solicita la revisión y fusión de una rama, normalmente condicionado por verificaciones de CI.
Ejemplo real

Un commit de un colega en el repositorio compartido de Ansible rompió la configuración de DNS en todos los servidores. En lugar de reescribir el historial compartido con reset, ejecutas git revert <commit-id>, envías la corrección y el pipeline vuelve a aplicar la configuración corregida. El error y su reversión quedan visibles en git log para la revisión posterior al incidente.

Consejo para el examen: En ramas compartidas, elige revert en lugar de reset y merge en lugar de rebase; los comandos que reescriben el historial son solo para trabajo local no publicado.

Comprueba lo que sabes

¿Qué comando crea una rama nueva llamada fix-dns y se cambia a ella?

git switch -c fix-dns (o git checkout -b fix-dns).

¿Cuál es la diferencia entre git fetch y git pull?

fetch descarga los cambios remotos sin alterar tu rama; pull los descarga y luego los fusiona o hace rebase en tu rama actual.

¿Cómo registras solo los cambios preparados con un mensaje?

git commit -m 'message'.
