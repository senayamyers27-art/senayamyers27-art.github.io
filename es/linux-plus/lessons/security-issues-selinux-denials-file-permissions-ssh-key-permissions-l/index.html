CompTIA Linux+ XK0-006

Problemas de seguridad: denegaciones de SELinux, permisos de archivos, permisos de claves SSH, cuentas bloqueadas

Muchos tickets de 'simplemente dejó de funcionar' son en realidad controles de seguridad haciendo su trabajo: SELinux bloqueando un acceso inesperado, permisos demasiado restrictivos o demasiado abiertos, SSH rechazando una clave o una cuenta bloqueada tras inicios de sesión fallidos. La habilidad consiste en identificar qué control es el responsable y corregir la configuración sin debilitar la seguridad.

Las denegaciones de SELinux a menudo aparecen como errores 'Permission denied' o HTTP 403 aunque los permisos normales parezcan correctos. Primero confirma que SELinux está involucrado: getenforce muestra el modo, y ausearch -m avc -ts recent (o journalctl -t setroubleshoot, o sealert -a /var/log/audit/audit.log) muestra las denegaciones AVC indicando el tipo del proceso de origen, el tipo del archivo de destino y la operación. Las causas y soluciones habituales son: etiquetas de archivo incorrectas después de mv o de restaurar archivos (se corrige con restorecon -Rv ruta), contenido en una ubicación no estándar (agrega una regla con semanage fcontext -a -t type 'path(/.*)?' y luego restorecon), un servicio en un puerto no estándar (semanage port -a -t http_port_t -p tcp 8081) o un comportamiento opcional que necesita un booleano (setsebool -P httpd_can_network_connect on). Poner brevemente el modo permissive con setenforce 0 puede confirmar que SELinux es la causa, pero vuelve a enforcing y corrige el problema de la política en lugar de dejarlo desactivado.

Los problemas de permisos de archivos siguen las reglas de lecciones anteriores. El usuario del proceso necesita lectura sobre los archivos y ejecución sobre cada directorio de la ruta; compruébalo con namei -l /ruta/completa y ls -l, y averigua con qué usuario se ejecuta un servicio con ps -o user= -p PID o con la configuración User= de la unidad. Revisa la pertenencia a grupos con id user, las ACL con getfacl y las opciones de montaje como noexec con findmnt. La solución es el cambio mínimo necesario, como ajustar la propiedad del grupo o agregar una ACL, nunca chmod 777, que crea un nuevo problema de seguridad. Presta atención también a lo contrario: archivos demasiado permisivos, como scripts escribibles por todos que ejecuta root, claves privadas legibles por otros o archivos de configuración que contienen contraseñas.

La autenticación con claves SSH falla en silencio cuando los permisos son laxos, porque la comprobación StrictModes de sshd rechaza las claves que otros usuarios podrían haber manipulado. En el servidor, el directorio personal del usuario no debe ser escribible por el grupo ni por todos, ~/.ssh debería ser 700 y ~/.ssh/authorized_keys 600, todo propiedad del usuario. En el cliente, la clave privada debe ser 600, o ssh se niega a usarla con 'UNPROTECTED PRIVATE KEY FILE'. En sistemas con SELinux, un archivo authorized_keys creado de forma inusual puede necesitar restorecon -Rv ~/.ssh. Para el diagnóstico, ejecuta ssh -v user@host en el cliente y lee journalctl -u sshd (o /var/log/secure o auth.log) en el servidor, donde mensajes como 'Authentication refused: bad ownership or modes' apuntan directamente a la causa. Confirma también que la clave está en el archivo de la cuenta correcta y que AllowUsers o AllowGroups permiten al usuario.

Las cuentas bloqueadas o expiradas producen fallos de inicio de sesión que parecen contraseñas incorrectas. Revisa cada causa posible: faillock --user nombre muestra los bloqueos por intentos fallidos (restablece con --reset después de confirmar que los intentos no fueron un ataque); passwd -S nombre muestra si la contraseña está bloqueada (LK o L); chage -l nombre muestra las fechas de expiración de la contraseña y de la cuenta; el shell en /etc/passwd podría ser nologin; y para las cuentas de directorio, revisa SSSD e id nombre. Investiga por qué se bloqueó una cuenta antes de desbloquearla, porque una ráfaga de fallos desde una dirección IP desconocida puede ser un intento de fuerza bruta que requiere un bloqueo en el firewall o un informe de incidente.

Términos clave

AVC denial (denegación AVC)
Un mensaje del access vector cache de SELinux que registra una operación bloqueada por la política, guardado en el log de auditoría.
StrictModes
Una configuración de sshd (activada de forma predeterminada) que rechaza las claves cuando los permisos del directorio personal, de .ssh o de authorized_keys son demasiado abiertos.
namei -l
Muestra la propiedad y los permisos de cada componente de una ruta, revelando dónde se bloquea el acceso.
faillock
Comando que muestra y restablece los bloqueos por inicios de sesión fallidos registrados por pam_faillock.
passwd -S
Muestra el estado de la contraseña de un usuario, incluido si está bloqueada.
Ejemplo real

Después de restaurar un directorio personal, el inicio de sesión con clave SSH de un desarrollador falla y pasa a pedir contraseña. journalctl -u sshd muestra 'Authentication refused: bad ownership or modes for directory /home/dev'. La restauración dejó el directorio personal escribible por el grupo. chmod 755 /home/dev, chmod 700 ~/.ssh, chmod 600 ~/.ssh/authorized_keys y restorecon -Rv /home/dev/.ssh restablecen el inicio de sesión con clave.

Consejo para el examen: Cuando el acceso falla pero los permisos parecen correctos en un sistema con SELinux, revisa ausearch -m avc antes de tocar chmod; la solución normalmente es restorecon, semanage o un booleano, nunca deshabilitar SELinux.

Comprueba lo que sabes

¿Qué permisos deberían tener ~/.ssh y ~/.ssh/authorized_keys para que el inicio de sesión con clave funcione de forma confiable?

~/.ssh 700 y authorized_keys 600, propiedad del usuario, con un directorio personal que no sea escribible por el grupo ni por otros.

Un usuario dice que su contraseña dejó de funcionar de repente. Menciona tres comandos para revisar el estado de la cuenta.

faillock --user <name>, passwd -S <name> y chage -l <name> (revisa también el shell en /etc/passwd).

¿Por qué chmod 777 es una mala solución para un error de permiso denegado?

Da acceso completo a todos, creando un agujero de seguridad en lugar de otorgar solo el acceso mínimo que necesita el proceso.
