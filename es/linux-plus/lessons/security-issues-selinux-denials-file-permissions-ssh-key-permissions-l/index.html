CompTIA Linux+ XK0-006

Problemas de seguridad: denegaciones de SELinux, permisos de archivos, permisos de claves SSH, cuentas bloqueadas

Muchos tickets de 'simplemente dejó de funcionar' son en realidad controles de seguridad haciendo su trabajo: SELinux (Security-Enhanced Linux) bloqueando un acceso inesperado, permisos demasiado estrictos o demasiado laxos, SSH rechazando una clave o una cuenta bloqueada tras inicios de sesión fallidos. La habilidad consiste en identificar qué control es el responsable y corregir la configuración sin debilitar la seguridad. Las respuestas del examen que desactivan un control casi siempre son incorrectas; las que hacen el cambio correcto más pequeño son las acertadas.

Las denegaciones de SELinux suelen aparecer como errores 'Permission denied' o HTTP 403 aunque los permisos normales parezcan correctos. Primero confirma que SELinux está involucrado: getenforce muestra el modo, y ausearch -m avc -ts recent (o journalctl -t setroubleshoot, o sealert -a /var/log/audit/audit.log) muestra las denegaciones AVC (access vector cache) con el tipo del proceso de origen, el tipo del archivo de destino y la operación. ls -Z muestra las etiquetas de los archivos y ps -eZ las de los procesos.

Las causas y soluciones habituales de SELinux son: etiquetas de archivo incorrectas después de mv o de restaurar archivos (se corrige con restorecon -Rv path); contenido en una ubicación no estándar (agrega una regla con semanage fcontext -a -t httpd_sys_content_t '/srv/web(/.*)?' y luego restorecon); un servicio en un puerto no estándar (semanage port -a -t http_port_t -p tcp 8081); o un comportamiento opcional que necesita un booleano (setsebool -P httpd_can_network_connect on). Poner brevemente el modo permisivo con setenforce 0 puede confirmar que SELinux es la causa, pero vuelve con setenforce 1 y corrige el problema de política en lugar de dejarlo desactivado. chcon cambia una etiqueta de forma temporal, pero un reetiquetado la deshace, así que semanage más restorecon es la solución duradera.

Los problemas de permisos de archivos siguen las reglas de lecciones anteriores. El usuario del proceso necesita lectura sobre los archivos y ejecución sobre cada directorio de la ruta; verifícalo con namei -l /full/path y ls -l, y averigua con qué usuario se ejecuta un servicio con ps -o user= -p PID o con la opción User= de la unidad. Revisa la pertenencia a grupos con id user, las ACL (listas de control de acceso) con getfacl y las opciones de montaje como noexec con findmnt. La solución es el cambio mínimo necesario, como ajustar el grupo propietario o agregar una ACL, nunca chmod 777. Presta atención también al caso inverso: scripts escribibles por todos que ejecuta root, claves privadas legibles por otros o archivos de configuración que contienen contraseñas.

La autenticación SSH con clave falla en silencio cuando los permisos son laxos, porque la verificación StrictModes de sshd rechaza las claves que otros usuarios podrían haber manipulado. En el servidor, el directorio home no debe ser escribible por el grupo ni por otros, ~/.ssh debe tener 700 y ~/.ssh/authorized_keys 600, todo propiedad del usuario. En el cliente, la clave privada debe tener 600, o ssh la rechaza con 'UNPROTECTED PRIVATE KEY FILE'. Un archivo authorized_keys creado de una forma inusual puede necesitar restorecon -Rv ~/.ssh. Diagnostica con ssh -v user@host en el cliente y con journalctl -u sshd (o /var/log/secure o auth.log) en el servidor, donde 'Authentication refused: bad ownership or modes' apunta directamente a la causa. Las cuentas bloqueadas o vencidas producen fallas que parecen contraseñas incorrectas: faillock --user name muestra los bloqueos (se restablecen con --reset), passwd -S name muestra una contraseña bloqueada (LK o L), chage -l name muestra las fechas de vencimiento, el shell en /etc/passwd podría ser nologin, y para las cuentas de directorio revisa SSSD e id name.

Considera un ejemplo práctico. Después de restaurar un directorio home, el inicio de sesión SSH con clave de un desarrollador falla y vuelve a pedir contraseña. ssh -v muestra que la clave se ofrece y se rechaza. En el servidor, journalctl -u sshd muestra 'Authentication refused: bad ownership or modes for directory /home/dev'. La restauración dejó el directorio home escribible por el grupo, y ls -Z muestra que ~/.ssh tiene una etiqueta genérica. Ejecutas chmod 755 /home/dev, chmod 700 /home/dev/.ssh, chmod 600 /home/dev/.ssh/authorized_keys y restorecon -Rv /home/dev/.ssh, y el inicio de sesión con clave funciona. Esa misma semana, un servidor web devuelve 403 para contenido movido desde un directorio home a /srv/web; ausearch -m avc muestra etiquetas user_home_t, y una regla de semanage fcontext más restorecon lo corrige sin tocar el modo enforcing.

Errores comunes: deshabilitar SELinux o dejarlo en modo permisivo; usar chcon como solución permanente; ejecutar chmod 777 para que desaparezca un error; corregir los permisos del archivo pero olvidar el permiso de ejecución de un directorio padre; aflojar los permisos de ~/.ssh con la intención de ayudar; desbloquear una cuenta sin revisar si los fallos fueron un ataque; y revisar solo la contraseña cuando la cuenta está vencida o tiene un shell nologin.

Las preguntas del examen premian identificar el control. 'Permission denied pero los permisos se ven bien en RHEL' significa SELinux, así que revisa ausearch -m avc y corrige con restorecon, semanage o un booleano. 'Los archivos movidos a la raíz web ahora devuelven 403' es un problema de etiquetas que se corrige con restorecon. 'Clave rechazada, bad ownership or modes' es StrictModes. 'UNPROTECTED PRIVATE KEY FILE' es la clave del cliente que necesita 600. 'Cuenta bloqueada tras intentos fallidos' es faillock, y 'contraseña vencida' es chage.

Términos clave

Denegación AVC (AVC denial)
Un mensaje de la access vector cache de SELinux que registra un acceso bloqueado; se encuentra con ausearch -m avc.
restorecon
Restablece las etiquetas de SELinux de los archivos a los valores definidos por la política.
semanage fcontext
Agrega una regla persistente de etiquetado de SELinux para una ruta, que se aplica con restorecon.
Booleano de SELinux (SELinux boolean)
Un interruptor de política de encendido/apagado como httpd_can_network_connect, que se define de forma persistente con setsebool -P.
StrictModes
La verificación de sshd que rechaza las claves cuando los permisos del home, de ~/.ssh o de authorized_keys son demasiado abiertos.
namei -l
Muestra los permisos de cada componente de una ruta, lo que revela un bit de ejecución faltante en un directorio padre.
passwd -S
Muestra el estado de la contraseña de una cuenta, incluido si está bloqueada.
Ejemplo real

Después de restaurar un directorio home, el inicio de sesión SSH con clave de un desarrollador falla y vuelve a pedir contraseña. journalctl -u sshd muestra 'Authentication refused: bad ownership or modes for directory /home/dev'. La restauración dejó el directorio home escribible por el grupo. chmod 755 /home/dev, chmod 700 ~/.ssh, chmod 600 ~/.ssh/authorized_keys y restorecon -Rv /home/dev/.ssh restablecen el inicio de sesión con clave.

Consejo para el examen: Cuando el acceso falla pero los permisos se ven bien en un sistema con SELinux, revisa ausearch -m avc antes de tocar chmod; la solución suele ser restorecon, semanage o un booleano, nunca deshabilitar SELinux.

Comprueba lo que sabes

¿Qué permisos deben tener ~/.ssh y ~/.ssh/authorized_keys para que el inicio de sesión con clave funcione de forma confiable?

~/.ssh 700 y authorized_keys 600, propiedad del usuario, con un directorio home que no sea escribible por el grupo ni por otros.

Un usuario dice que su contraseña dejó de funcionar de repente. Nombra tres comandos para revisar el estado de la cuenta.

faillock --user <name>, passwd -S <name> y chage -l <name> (revisa también el shell en /etc/passwd).

¿Por qué chmod 777 es una mala solución para un error de permiso denegado?

Otorga acceso total a todos, lo que crea un hueco de seguridad en lugar de otorgar solo el acceso mínimo que el proceso necesita.

Contenido web movido con mv devuelve 403, y ausearch muestra una denegación AVC. ¿Cuál es la solución probable?

restorecon -Rv sobre el contenido (agregando primero una regla de semanage fcontext si es una ubicación no estándar), porque mv conservó la etiqueta de SELinux anterior.
