Unidades de systemd: systemctl start/stop/enable/mask, salida de status, anulaciones drop-in con systemctl edit

systemd administra casi todo lo que se ejecuta en un sistema Linux moderno mediante unidades. Una unidad es un objeto de configuración de cierto tipo, identificado por su sufijo: .service para demonios, .socket para la activación por socket, .timer para tareas programadas, .mount para montajes, .target para grupos de unidades, y otros. systemctl es la herramienta que usas para controlarlas, y aprender a separar 'ahora' de 'en el arranque' es la clave de la mayoría de las preguntas del examen.

Los comandos básicos del ciclo de vida actúan sobre el sistema en ejecución: systemctl start httpd, stop, restart (detener y luego iniciar) y reload (pedirle al servicio que vuelva a leer su configuración sin detenerse, si lo admite). El comportamiento en el arranque es independiente: systemctl enable httpd crea enlaces simbólicos, según la línea WantedBy= de la sección [Install] de la unidad, para que la unidad se inicie en el arranque, y disable los elimina. Ambos son independientes, por eso existe systemctl enable --now httpd para hacer las dos cosas a la vez. systemctl is-active e is-enabled responden cada pregunta en los scripts. mask va más allá que disable: systemctl mask httpd enlaza el archivo de unidad con /dev/null, de modo que no se puede iniciar en absoluto, ni manualmente ni como dependencia de otra unidad, hasta que ejecutes unmask. Úsalo cuando un servicio nunca deba ejecutarse, por ejemplo para evitar que se active un servicio en conflicto.

systemctl status httpd es tu primer diagnóstico. Muestra la línea Loaded (ruta del archivo de unidad y si está enabled, disabled o masked), la línea Active (active (running), inactive (dead) o failed, con una marca de tiempo), el PID principal, el cgroup (grupo de control) de procesos y las últimas líneas del journal. Una unidad fallida también muestra el código de salida o la señal, como status=203/EXEC, que significa que no se pudo ejecutar el ejecutable. systemctl --failed lista todas las unidades fallidas, systemctl list-units --type=service lista los servicios activos y journalctl -u httpd muestra el log completo de la unidad. Los archivos de unidad están en tres lugares, en orden de precedencia: /etc/systemd/system/ (administrador), /run/systemd/system/ (tiempo de ejecución) y /usr/lib/systemd/system/ o /lib/systemd/system/ (instalados por paquetes). Nunca edites directamente los archivos que aportan los paquetes, porque las actualizaciones los sobrescriben. En su lugar, crea una anulación drop-in con systemctl edit httpd, que abre un editor y guarda tus cambios en /etc/systemd/system/httpd.service.d/override.conf. Solo se anulan los ajustes que indiques.

[Service]
Restart=on-failure
RestartSec=5
LimitNOFILE=65536

systemctl edit --full httpd copia la unidad completa a /etc para reemplazarla por entero, y systemctl cat httpd muestra la unidad más todos los drop-ins. Un detalle sutil: los ajustes de tipo lista como ExecStart= deben vaciarse primero con una línea ExecStart= vacía antes de establecer un nuevo valor en un drop-in, o systemd se quejará de valores múltiples. Después de editar archivos de unidad a mano, ejecuta systemctl daemon-reload para que systemd los vuelva a leer; systemctl edit lo hace por ti. Una sección de servicio típica contiene ExecStart=, User= y Restart=, y la sección [Install] con WantedBy=multi-user.target es la que usa enable.

Veamos un ejemplo práctico. Un servicio de API interno falla de vez en cuando y queda caído. systemctl status api muestra 'failed' con status=1/FAILURE, y journalctl -u api muestra la caída. En lugar de editar la unidad del proveedor en /usr/lib/systemd/system, ejecutas systemctl edit api.service, añades las líneas Restart=on-failure y RestartSec=5 mostradas arriba, guardas y ejecutas systemctl restart api. Ahora systemctl cat api.service muestra la anulación, y la siguiente caída provoca un reinicio automático. Como la anulación vive en /etc, la siguiente actualización del paquete de la API deja tu corrección en su lugar.

Errores comunes: ejecutar start y suponer que el servicio volverá después de reiniciar (también necesitas enable); usar disable cuando una dependencia sigue activando la unidad (usa mask); editar archivos bajo /usr/lib/systemd/system, que las actualizaciones sobrescriben; olvidar daemon-reload después de ediciones manuales; y anular ExecStart= sin vaciarlo primero. Una trampa más discreta es reload frente a restart: reload mantiene el proceso en ejecución y solo vuelve a leer la configuración, así que no cargará un binario nuevo después de una actualización, y no todos los servicios lo admiten. Si tienes dudas, systemctl reload-or-restart intenta primero una recarga y, si no puede, reinicia.

Las preguntas del examen suelen formularse como resultados. 'Funciona ahora pero no después de reiniciar' significa enable. 'Iniciar ahora y en el arranque' significa enable --now. 'Nunca debe iniciarse, ni siquiera como dependencia' significa mask. 'Cambiar un ajuste sin tocar el archivo del proveedor' significa systemctl edit y un drop-in en /etc/systemd/system/<unit>.d/. 'Edité un archivo de unidad pero nada cambió' significa daemon-reload. 'status=203/EXEC' apunta a una ruta incorrecta o a que falta el permiso de ejecución en el programa.

Términos clave

Unidad (unit)
Un objeto de configuración de systemd, como un .service, .socket, .timer, .mount o .target.
enable vs start
enable configura una unidad para que se inicie en el arranque; start la ejecuta ahora. Ninguno implica al otro.
mask
Enlaza una unidad con /dev/null para que no se pueda iniciar manualmente ni como dependencia.
Anulación drop-in (drop-in override)
Un archivo .conf en /etc/systemd/system/<unit>.d/ que anula ajustes seleccionados de una unidad.
daemon-reload
Le indica a systemd que vuelva a leer los archivos de unidad después de que cambian en el disco.
WantedBy=
Un ajuste de [Install] que indica el target que debe activar la unidad cuando está habilitada.
Ejemplo real

Un servicio de API interno falla de vez en cuando y queda caído. En lugar de editar la unidad del proveedor en /usr/lib/systemd/system, ejecutas systemctl edit api.service, añades Restart=on-failure y RestartSec=5 bajo [Service], guardas y reinicias el servicio. Ahora systemctl cat api.service muestra la anulación, y la siguiente caída provoca un reinicio automático.

Consejo para el examen: Conoce la diferencia de fuerza: stop afecta al momento actual, disable afecta al arranque y mask bloquea la unidad por completo hasta que se desenmascare.

Comprueba lo que sabes

Un servicio funciona ahora, pero no está en ejecución después de reiniciar. ¿Qué comando lo corrige?

systemctl enable <service> (o enable --now para iniciarlo también), porque start por sí solo no afecta al arranque.

¿Dónde guarda sus cambios systemctl edit nginx?

En /etc/systemd/system/nginx.service.d/override.conf, un drop-in que anula solo los ajustes que indiques.

¿Qué debes ejecutar después de editar manualmente un archivo de unidad en /etc/systemd/system?

systemctl daemon-reload y luego reiniciar la unidad si hace falta, para que systemd vuelva a leer el archivo modificado.

¿Qué es más fuerte, disable o mask, y por qué?

mask, porque enlaza la unidad con /dev/null para que no pueda iniciarse en absoluto, ni manualmente ni como dependencia; disable solo elimina los enlaces del arranque.
