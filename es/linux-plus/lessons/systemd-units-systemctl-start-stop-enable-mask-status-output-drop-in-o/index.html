CompTIA Linux+ XK0-006

Unidades de systemd: systemctl start/stop/enable/mask, salida de status, anulaciones drop-in con systemctl edit

systemd administra casi todo lo que se ejecuta en un sistema Linux moderno mediante unidades. Una unidad es un objeto de configuración de cierto tipo, identificado por su sufijo: .service para demonios, .socket para activación por socket, .timer para tareas programadas, .mount para montajes, .target para grupos de unidades, y más. systemctl es la herramienta que usas para controlarlas.

Los comandos básicos del ciclo de vida actúan sobre el sistema en ejecución: systemctl start httpd, stop, restart (detener y luego iniciar) y reload (pedir al servicio que vuelva a leer su configuración sin detenerse, si lo admite). El comportamiento en el arranque es aparte: systemctl enable httpd crea enlaces simbólicos para que la unidad arranque en el boot dentro de su target, y disable los elimina. Ambos son independientes, por eso existe systemctl enable --now httpd para hacer las dos cosas a la vez. systemctl is-active e is-enabled responden cada pregunta en scripts.

mask va más allá que disable. systemctl mask httpd enlaza el archivo de unidad a /dev/null, de modo que no se puede iniciar en absoluto, ni manualmente ni como dependencia de otra unidad, hasta que lo desenmascares con unmask. Úsalo cuando un servicio nunca deba ejecutarse, por ejemplo para evitar que se active un servicio en conflicto.

systemctl status httpd es tu primer diagnóstico. Muestra la línea Loaded (ruta del archivo de unidad y si está habilitada o deshabilitada), la línea Active (active (running), inactive (dead), failed, con una marca de tiempo), el PID principal, el cgroup (control group) de procesos y las últimas líneas del journal. Una unidad fallida también muestra el código de salida o la señal, como status=203/EXEC, que significa que no se pudo ejecutar el ejecutable. systemctl --failed lista todas las unidades fallidas y systemctl list-units --type=service lista los servicios activos.

Los archivos de unidad viven en tres lugares, en orden de precedencia: /etc/systemd/system/ (administrador), /run/systemd/system/ (tiempo de ejecución) y /usr/lib/systemd/system/ o /lib/systemd/system/ (instalados por paquetes). Nunca edites directamente los archivos que proporcionan los paquetes, porque las actualizaciones los sobrescriben. En su lugar, crea una anulación drop-in con systemctl edit httpd, que abre un editor y guarda tus cambios en /etc/systemd/system/httpd.service.d/override.conf. Solo se anulan las configuraciones que incluyas. Por ejemplo:

[Service]
Restart=on-failure
RestartSec=5
LimitNOFILE=65536

systemctl edit --full httpd copia la unidad completa a /etc para reemplazarla por completo, y systemctl cat httpd muestra la unidad más todos los drop-ins. Un detalle sutil: las configuraciones de tipo lista como ExecStart= deben limpiarse primero con una línea ExecStart= vacía antes de establecer un nuevo valor en un drop-in. Después de editar archivos de unidad a mano, ejecuta systemctl daemon-reload para que systemd los vuelva a leer; systemctl edit lo hace por ti. Una sección de servicio típica contiene ExecStart=, User=, Restart= y una sección [Install] con WantedBy=multi-user.target, que es lo que usa enable.

Términos clave

Unit (unidad)
Un objeto de configuración de systemd como .service, .socket, .timer, .mount o .target.
enable vs start
enable configura una unidad para que arranque en el boot; start la ejecuta ahora. Ninguno implica al otro.
mask
Enlaza una unidad a /dev/null para que no pueda iniciarse manualmente ni como dependencia.
Drop-in override (anulación drop-in)
Un archivo .conf en /etc/systemd/system/<unit>.d/ que anula configuraciones seleccionadas de una unidad.
daemon-reload
Le indica a systemd que vuelva a leer los archivos de unidad después de que cambien en disco.
Ejemplo real

Un servicio de API interno falla de vez en cuando y se queda caído. En lugar de editar la unidad del proveedor en /usr/lib/systemd/system, ejecutas systemctl edit api.service, agregas Restart=on-failure y RestartSec=5 bajo [Service], guardas y reinicias el servicio. systemctl cat api.service ahora muestra la anulación, y la siguiente falla provoca un reinicio automático.

Consejo para el examen: Conoce la diferencia de alcance: stop afecta el ahora, disable afecta el arranque y mask bloquea la unidad por completo hasta que se desenmascare.

Comprueba lo que sabes

Un servicio se ejecuta ahora, pero no está en ejecución después de reiniciar. ¿Qué comando lo soluciona?

systemctl enable <service> (o enable --now para iniciarlo también).

¿Dónde guarda sus cambios systemctl edit nginx?

En /etc/systemd/system/nginx.service.d/override.conf.

¿Qué debes ejecutar después de editar manualmente un archivo de unidad en /etc/systemd/system?

systemctl daemon-reload y luego reiniciar la unidad si es necesario.
