CompTIA Linux+ XK0-006

Scripts en Bash: shebang, variables, expansión de parámetros, comillas, códigos de salida y $?

Un script de Bash es un archivo de texto con comandos de shell que se ejecutan en secuencia, lo que te permite automatizar cualquier cosa que puedas escribir. Las preguntas basadas en desempeño de Linux+ suelen mostrar un script corto y preguntar qué imprime o por qué falla, así que la sintaxis básica debe estar bien firme. La mayoría de los errores en scripts vienen de un puñado de detalles: cómo se inicia el script, cómo se asignan y expanden las variables, cómo funcionan las comillas y cómo se informan el éxito y la falla.

La primera línea es el shebang, que le indica al kernel qué intérprete debe ejecutar el archivo: #!/bin/bash, o #!/usr/bin/env bash para buscar bash en el PATH. Haz ejecutable el script con chmod +x script.sh y ejecútalo como ./script.sh; como alternativa, bash script.sh lo ejecuta sin permiso de ejecución. Ejecutarlo con source script.sh (o . script.sh) lo corre en el shell actual, así que las variables y los cambios de directorio que haga se mantienen después. Un script iniciado de forma normal se ejecuta en un proceso hijo y no puede cambiar el entorno de su proceso padre. Las líneas que empiezan con # son comentarios.

Las variables se asignan sin espacios alrededor del signo igual: name=web01. name = web01 en cambio ejecuta un comando llamado name. Lee un valor con $name o ${name}; las llaves son necesarias cuando sigue texto, como en ${name}_backup. La sustitución de comandos captura la salida: today=$(date +%F). La aritmética usa $(( )): count=$((count + 1)). Los parámetros especiales incluyen $0 (nombre del script), $1, $2 y así sucesivamente (argumentos posicionales), $# (número de argumentos), $@ (todos los argumentos como palabras separadas), $$ (el PID del script) y $? (estado de salida del último comando). read -p 'Name: ' user lee una entrada, y export VAR hace que una variable sea visible para los procesos hijos. La expansión de parámetros transforma variables sin herramientas externas: ${var:-default} sustituye un valor predeterminado si var no está definida o está vacía, ${var:=default} además la asigna, ${var:?message} termina con un error si no está definida, ${#var} da la longitud, ${file%.txt} elimina el sufijo coincidente más corto, ${path##*/} elimina el prefijo más largo hasta la última barra (como basename) y ${var/old/new} reemplaza la primera coincidencia.

Las comillas controlan cómo trata el shell los caracteres especiales. Las comillas dobles permiten la expansión de variables y comandos, pero impiden la división en palabras y el globbing: "$file" sigue siendo un solo argumento aunque contenga espacios. Las comillas simples hacen todo literal: '$HOME' imprime los cinco caracteres. Una barra invertida escapa un solo carácter. La regla práctica es poner comillas dobles en cada expansión, "$var" y "$@", a menos que quieras específicamente la división. Todo comando devuelve un estado de salida de 0 a 255: 0 significa éxito y cualquier otro valor, falla, con significados definidos por el programa. $? contiene el estado del comando más reciente, así que revísalo de inmediato, porque el siguiente comando lo sobrescribe. Un script define su propio estado con exit 0 o exit 1. && y || usan los códigos de salida: mkdir /backup && cp file /backup copia solo si mkdir tuvo éxito, y ping -c1 host || echo down imprime solo en caso de falla.

#!/bin/bash
target="${1:-/var/log}"
size=$(du -sh "$target" 2>/dev/null)
status=$?
if [ "$status" -ne 0 ]; then
  echo "cannot read $target (exit $status)" >&2
  exit 1
fi
echo "$target uses ${size%%[[:space:]]*}"

Considera un ejemplo práctico. El script anterior recibe un directorio como primer argumento y recurre a /var/log mediante ${1:-/var/log}. Captura la salida de du con sustitución de comandos, guarda $? de inmediato en status para que el valor no se pierda, y termina con 1 y un mensaje en la salida de error estándar si du falló. Por último, ${size%%[[:space:]]*} elimina todo desde el primer espacio en blanco en adelante, dejando solo la cifra del tamaño. Ejecutado como ./dusize.sh /srv/My Files, fallaría, porque el argumento sin comillas se divide en dos; ./dusize.sh "/srv/My Files" funciona, y dentro del script el "$target" entre comillas mantiene el nombre intacto.

Errores comunes: espacios alrededor de = en las asignaciones; variables sin comillas que se dividen en los espacios o expanden comodines; revisar $? después de un echo en lugar de después del comando que te interesa; usar source cuando querías ejecutar un proceso separado, o al revés; confundir % (sufijo) con # (prefijo) en la expansión de parámetros; poner entre comillas simples una cadena que necesita expandir una variable; y olvidar hacer ejecutable el script o darle un final de línea de Windows que rompe el shebang.

Las preguntas del examen suelen mostrar código y pedir la salida o el error. 'La variable conserva su valor después de que termina el script' apunta a source. 'Command not found' en una línea de asignación significa espacios alrededor de =. 'Los nombres de archivo con espacios rompen el script' significa que faltan comillas dobles. 'Valor predeterminado si no se da ningún argumento' es ${1:-default}. 'Quitar una extensión' es %, y 'quitar una ruta inicial' es ##*/. 'Estado del comando anterior' es $?, y 'número de argumentos' es $#.

Términos clave

Shebang
La primera línea #! que nombra el intérprete que el kernel debe usar para ejecutar un script.
Parámetros posicionales (positional parameters)
Los argumentos del script, disponibles como $1, $2 y así sucesivamente, con $# como la cantidad y $@ como la lista completa.
Expansión de parámetros (parameter expansion)
Sintaxis del shell como ${var:-default} o ${file%.txt} que sustituye o transforma los valores de las variables.
Sustitución de comandos (command substitution)
$(command), que se reemplaza a sí misma por la salida del comando.
Estado de salida ($?)
El código de 0 a 255 que devuelve un comando, donde 0 significa éxito; $? contiene el más reciente.
source
Ejecuta un script en el shell actual para que sus variables y cambios de directorio persistan.
Ejemplo real

Un script de respaldo falla con un archivo llamado 'Q3 report.xlsx'. La línea cp $file /backup dividió el nombre en dos argumentos. Cambiarla a cp "$file" /backup lo corrige, y agregar if [ $? -ne 0 ]; then echo 'copy failed' >&2; exit 1; fi justo después de la copia hace que la falla sea visible en los logs del trabajo de cron en lugar de continuar en silencio.

Consejo para el examen: Busca espacios alrededor de = en las asignaciones y variables sin comillas; ambos son errores deliberados comunes en las preguntas de scripts del examen. % recorta desde el final, # recorta desde el inicio.

Comprueba lo que sabes

¿Qué produce ${filename%.log} si filename es app.log?

app, porque % elimina el patrón de sufijo coincidente más corto, .log.

¿Cuál es la diferencia entre echo '$HOME' y echo "$HOME"?

Las comillas simples imprimen el texto literal $HOME; las comillas dobles lo expanden a la ruta del directorio home.

¿Por qué debes revisar $? inmediatamente después del comando que te interesa?

Porque cada comando, incluidos echo o test, sobrescribe $? con su propio estado de salida.

Un script define una variable, pero está vacía en tu shell después de que ./script.sh termina. ¿Por qué?

El script se ejecutó en un proceso hijo; ejecútalo con source script.sh (o . script.sh) para conservar sus variables en el shell actual.
