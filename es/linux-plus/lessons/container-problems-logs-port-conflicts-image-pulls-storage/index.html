Problemas de contenedores: logs, conflictos de puertos, descarga de imágenes, almacenamiento

Los contenedores fallan de maneras características: la aplicación que contienen se cae, el puerto no puede publicarse, la imagen no puede descargarse o el almacenamiento falta, está lleno o es inaccesible. Los comandos de la lección de contenedores se convierten en tu kit de diagnóstico, y el proceso refleja el diagnóstico de servicios comunes: revisar el estado, leer los logs, inspeccionar la configuración y luego mirar la red y el almacenamiento alrededor del contenedor. Los ejemplos usan Podman, pero los mismos subcomandos funcionan con Docker.

Empieza por averiguar el estado del contenedor. podman ps -a (o docker ps -a) incluye los contenedores detenidos y muestra su estado, como Exited (1) 2 minutes ago o un bucle de reinicios. podman logs name muestra lo que la aplicación imprimió antes de detenerse, que suele ser la respuesta: una variable de entorno faltante, un error de configuración o una conexión fallida a la base de datos. podman inspect name muestra el código de salida, el indicador OOMKilled, el comando, el entorno, los montajes y la política de reinicio. Un código de salida 137 significa que el proceso fue terminado con SIGKILL (128 + 9), a menudo por el OOM killer o por un límite de memoria, mientras que 139 indica una falla de segmentación. podman events muestra los eventos del ciclo de vida, y podman exec -it name sh te permite mirar dentro de un contenedor en ejecución. Si un contenedor termina de inmediato, verifica que su comando principal no simplemente finalice, o ejecuta la imagen de forma interactiva con un shell para inspeccionarla.

Los conflictos de puertos aparecen como errores del tipo 'address already in use' cuando publicas con -p. Solo un proceso puede enlazar un puerto del host, así que revisa con ss -tlpn | grep :8080 los servicios del host y con podman ps otros contenedores que ya lo estén publicando, y luego elige otro puerto del host o detén el servicio en conflicto. Si el contenedor se ejecuta pero no es alcanzable, revisa podman port name para confirmar la asignación, confirma que la aplicación dentro del contenedor escucha en 0.0.0.0 y no en 127.0.0.1, y revisa el firewall del host. Podman sin root (rootless) no puede enlazar puertos del host por debajo de 1024 por defecto, lo que produce un error de permisos y no un conflicto.

Las fallas al descargar imágenes tienen varias causas. 'manifest unknown' o 'not found' significa un nombre o una etiqueta de imagen incorrectos; 'unauthorized' o 'denied' significa que necesitas iniciar sesión con podman login registry o que no tienes acceso a un repositorio privado; 'toomanyrequests' indica un límite de tasa del registro; y los tiempos de espera agotados, las fallas de DNS o los errores de certificado TLS apuntan a problemas de red, de proxy o de reloj. Los nombres cortos sin registro pueden resolverse contra una lista en /etc/containers/registries.conf, así que usa nombres completamente calificados como registry.example.com/team/app:1.4 para ser explícito y evitar descargar una imagen impostora. Fijar una etiqueta o un digest específicos en lugar de latest también evita sorpresas.

Los problemas de almacenamiento se presentan de dos formas. Espacio: las imágenes, los contenedores detenidos, los volúmenes y la caché de compilación consumen disco en /var/lib/containers (Podman como root), ~/.local/share/containers (Podman sin root) o /var/lib/docker. podman system df resume el uso, y podman image prune, podman container prune, podman volume prune y podman system prune lo recuperan; ten cuidado, porque podar volúmenes elimina datos. Acceso: un bind mount que da 'Permission denied' dentro del contenedor suele deberse a etiquetas de SELinux (agrega :Z para una etiqueta privada o :z para una compartida a la opción -v) o a UID que no coinciden, especialmente en modo rootless, donde los UID del contenedor se asignan a UID subordinados en el host; podman unshare ayuda a ajustar la propiedad. Los datos escritos dentro de un contenedor sin un volumen desaparecen cuando se elimina el contenedor, una causa común de pérdida de datos después de actualizar una imagen.

Considera un ejemplo práctico. Una API en contenedor se reinicia una y otra vez. podman ps -a muestra Exited (137), y podman inspect api --format '{{.State.OOMKilled}}' imprime true. podman logs api muestra mensajes de arranque normales que simplemente se interrumpen, lo cual es coherente con una terminación forzada y no con un error de la aplicación. El contenedor se inició con --memory 256m, pero la nueva versión necesita más. Lo vuelves a crear con --memory 512m, y se mantiene en ejecución. Al día siguiente, el nuevo contenedor de un compañero falla con 'address already in use' en el puerto 8080; podman ps muestra que la versión anterior de la API sigue publicando el 8080, así que la detiene y el nuevo contenedor arranca.

Errores comunes: reiniciar una y otra vez un contenedor que se cae sin leer podman logs; tratar el código de salida 137 como un error de la aplicación en lugar de una terminación forzada; enlazar la aplicación a 127.0.0.1 dentro del contenedor; usar nombres de imagen no calificados; ejecutar system prune --volumes y perder datos; deshabilitar SELinux en lugar de usar :Z; y guardar datos en la capa escribible del contenedor en lugar de en un volumen.

Las preguntas del examen siguen patrones. 'El contenedor termina de inmediato' significa revisar podman logs. 'Código de salida 137' u 'OOMKilled true' significa memoria. 'address already in use' significa un conflicto de puertos en el host, que se encuentra con ss o podman ps. 'manifest unknown' significa un nombre o una etiqueta incorrectos, y 'unauthorized' significa podman login. 'El disco se llena de imágenes' es podman system df y prune. 'Permission denied en un bind mount en RHEL' es :Z. 'Rootless no puede usar el puerto 80' es el límite de puertos privilegiados.

Términos clave

Código de salida 137 (exit code 137)
La terminación de un contenedor causada por SIGKILL (128 + 9), a menudo por el OOM killer o por un límite de memoria.
podman ps -a
Lista todos los contenedores, incluidos los detenidos, con su estado.
podman inspect
Muestra la configuración y el estado detallados del contenedor, incluidos el código de salida, OOMKilled, los montajes y los puertos.
registries.conf
El archivo que define los registros y cómo se resuelven los nombres cortos de imágenes.
podman system df
Resume el espacio en disco que usan las imágenes, los contenedores y los volúmenes.
Opción de volumen Z (Z volume option)
El sufijo :Z o :z en -v que reetiqueta un bind mount para que el contenedor pueda acceder a él bajo SELinux.
Contenedor sin root (rootless container)
Un contenedor ejecutado por un usuario sin privilegios, con los UID asignados a ID subordinados en el host.
Ejemplo real

Una API en contenedor se reinicia una y otra vez. podman ps -a muestra Exited (137), y podman inspect muestra OOMKilled true. El contenedor tenía --memory 256m, pero la nueva versión necesita más. Subir el límite a 512m y volver a desplegar detiene los reinicios, y podman logs ahora muestra que el servicio arranca con normalidad.

Consejo para el examen: Revisa primero los logs y luego inspecciona: podman logs explica la mayoría de las caídas de aplicaciones, y podman inspect revela los códigos de salida, las terminaciones por OOM, los montajes y las asignaciones de puertos.

Comprueba lo que sabes

Un contenedor termina con el código 137. ¿Cuál es la causa más probable?

Fue terminado con SIGKILL, a menudo porque superó su límite de memoria o porque lo eligió el OOM killer.

podman run -p 80:8080 falla con un error de permisos al ejecutarlo como usuario normal. ¿Por qué?

Los contenedores sin root no pueden enlazar puertos del host por debajo de 1024 por defecto; usa un puerto del host más alto o ajusta la configuración del sistema.

Un directorio montado con bind mount da Permission denied dentro de un contenedor en un host RHEL. ¿Cuál es una solución común?

Agregar :Z (o :z) a la opción de volumen para que el directorio se reetiquete y el contenedor pueda acceder a él bajo SELinux.

Una descarga falla con 'manifest unknown'. ¿Qué debes revisar?

El nombre y la etiqueta de la imagen, ya que el registro no tiene ninguna imagen que coincida con esa referencia; un nombre completamente calificado evita la ambigüedad.
