Problemas de contenedores: logs, conflictos de puertos, descarga de imágenes, almacenamiento

Los contenedores fallan de maneras características: la aplicación de adentro se cae, no se puede publicar el puerto, no se puede descargar la imagen, o el almacenamiento falta, está lleno o es inaccesible. Los comandos de la lección de contenedores se convierten en tu kit de solución de problemas, y el proceso refleja la solución de problemas de servicios comunes.

Empieza por averiguar el estado del contenedor. podman ps -a (o docker ps -a) incluye los contenedores detenidos y muestra su estado, como Exited (1) 2 minutes ago o un bucle de reinicios. podman logs nombre muestra lo que imprimió la aplicación antes de detenerse, que normalmente es la respuesta: una variable de entorno faltante, un error de configuración, una conexión fallida a la base de datos. podman inspect nombre muestra el código de salida, el indicador OOMKilled, el comando, el entorno, los montajes y la política de reinicio; un código de salida 137 significa que el proceso fue terminado con SIGKILL (128 + 9), a menudo por el OOM killer o por un límite de memoria, mientras que 139 indica una falla de segmentación. podman events muestra los eventos del ciclo de vida, y podman exec -it nombre sh te permite mirar dentro de un contenedor en ejecución. Si el contenedor sale de inmediato, intenta ejecutar la imagen de forma interactiva con un shell para inspeccionarla, o verifica que el comando principal no simplemente termine y salga.

Los conflictos de puertos aparecen como errores del tipo 'address already in use' cuando publicas con -p. Solo un proceso puede usar un puerto del host, así que revisa con ss -tlpn | grep :8080 los servicios del host y con podman ps otros contenedores que ya lo estén publicando, y luego elige otro puerto del host o detén el servicio en conflicto. Si el contenedor se ejecuta pero no es accesible, revisa podman port nombre para confirmar el mapeo, confirma que la aplicación dentro escucha en 0.0.0.0 y no en 127.0.0.1 dentro del contenedor, y revisa el firewall del host. Podman rootless no puede usar puertos del host menores a 1024 de forma predeterminada, lo que produce un error de permisos en lugar de un conflicto.

Las fallas al descargar imágenes tienen varias causas. 'manifest unknown' o 'not found' significa un nombre de imagen o una etiqueta incorrectos; 'unauthorized' o 'denied' significa que necesitas iniciar sesión con podman login registry o que no tienes acceso a un repositorio privado; 'toomanyrequests' indica un límite de tasa del registro; y los tiempos de espera agotados, las fallas de DNS o los errores de certificado TLS apuntan a problemas de red, de proxy o del reloj. Los nombres cortos sin registro pueden resolverse contra una lista en /etc/containers/registries.conf, así que usa nombres completamente calificados como registry.example.com/team/app:1.4 para ser explícito y evitar descargar una imagen impostora. Fijar una etiqueta o un digest específicos en lugar de latest también evita sorpresas.

Los problemas de almacenamiento vienen en dos formas. Espacio: las imágenes, los contenedores detenidos, los volúmenes y la caché de construcción consumen disco en /var/lib/containers (Podman como root), ~/.local/share/containers (Podman rootless) o /var/lib/docker. podman system df resume el uso, y podman image prune, podman container prune, podman volume prune y podman system prune lo recuperan; ten cuidado, porque depurar volúmenes elimina datos. Acceso: un bind mount que da 'Permission denied' dentro del contenedor normalmente significa etiquetas de SELinux (agrega :Z o :z a la opción -v) o desajustes de UID, especialmente en modo rootless, donde los UID del contenedor se asignan a UID subordinados en el host; podman unshare ayuda a ajustar la propiedad. Recuerda también que los datos escritos dentro de un contenedor sin volumen desaparecen cuando se elimina el contenedor, una causa común de pérdida de datos después de actualizar una imagen.

Términos clave

Exit code 137 (código de salida 137)
Un proceso de contenedor terminado por SIGKILL (128 + 9), con frecuencia por límites de memoria o por el OOM killer.
podman ps -a
Lista todos los contenedores, incluidos los detenidos, con su estado e información de salida.
registries.conf
Configuración que controla los registros, incluida la forma en que se resuelven los nombres cortos de imagen.
podman system df
Resume el uso de disco de imágenes, contenedores y volúmenes.
:Z volume option (opción de volumen :Z)
Vuelve a etiquetar un directorio del host montado con una etiqueta SELinux privada para que el contenedor pueda acceder a él.
Ejemplo real

Una API en contenedor se reinicia una y otra vez. podman ps -a muestra Exited (137), y podman inspect muestra OOMKilled true. El contenedor tenía --memory 256m, pero la nueva versión necesita más. Subir el límite a 512m y volver a desplegar detiene los reinicios, y podman logs ahora muestra que el servicio arranca con normalidad.

Consejo para el examen: Revisa primero los logs y luego inspecciona: podman logs explica la mayoría de las caídas de aplicaciones, y podman inspect revela los códigos de salida, las terminaciones por OOM, los montajes y los mapeos de puertos.

Comprueba lo que sabes

Un contenedor sale con el código 137. ¿Cuál es la causa más probable?

Fue terminado con SIGKILL, a menudo porque superó su límite de memoria o porque el OOM killer lo eligió.

podman run -p 80:8080 falla como usuario normal con un error de permisos. ¿Por qué?

Los contenedores rootless no pueden usar puertos del host menores a 1024 de forma predeterminada; usa un puerto del host más alto o ajusta la configuración del sistema.

Un directorio montado da Permission denied dentro de un contenedor en un host RHEL. ¿Cuál es una solución común?

Agregar :Z (o :z) a la opción del volumen para que el directorio se vuelva a etiquetar y el contenedor pueda acceder a él bajo SELinux.
