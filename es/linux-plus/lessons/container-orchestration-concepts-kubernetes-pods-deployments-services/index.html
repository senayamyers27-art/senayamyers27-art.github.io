Conceptos de orquestación de contenedores: pods, deployments y services de Kubernetes

Ejecutar unos cuantos contenedores a mano funciona en un solo host, pero las aplicaciones en producción necesitan muchos contenedores repartidos en muchas máquinas, que se reinicien cuando fallan, que escalen según la demanda y que se actualicen sin tiempo de inactividad. La orquestación de contenedores automatiza esto, y Kubernetes (a menudo escrito K8s) es el orquestador dominante. Linux+ evalúa los conceptos centrales más que la administración profunda de clústeres: qué hace cada objeto, cómo se relacionan y cuál cambias para obtener un resultado.

Un clúster de Kubernetes tiene un plano de control (control plane) y nodos de trabajo. El plano de control incluye el servidor de API (todo se comunica con él), etcd (un almacén clave-valor que guarda el estado del clúster), el planificador o scheduler (elige qué nodo ejecuta cada carga de trabajo) y los administradores de controladores (mantienen la realidad alineada con el estado deseado). Cada nodo de trabajo ejecuta un agente kubelet, un runtime de contenedores como containerd o CRI-O, y kube-proxy para la red de los servicios. Interactúas con el clúster mediante kubectl. Kubernetes es declarativo: describes el estado deseado en manifiestos YAML y los aplicas con kubectl apply -f file.yaml, y los controladores trabajan continuamente para que el clúster coincida. Esto se diferencia de ejecutar comandos de forma imperativa uno por uno, y es la razón por la que Kubernetes combina bien con flujos de trabajo basados en Git donde los manifiestos se revisan y se versionan.

El pod es la unidad desplegable más pequeña: uno o más contenedores que comparten un namespace de red (una sola dirección IP, así que se comunican por localhost) y pueden compartir volúmenes. La mayoría de los pods contienen un solo contenedor de aplicación, a veces con un auxiliar 'sidecar' como un enviador de logs. Los pods son desechables; cuando uno muere, se reemplaza por un pod nuevo con una IP nueva, no se repara. Rara vez creas pods directamente. Un deployment declara qué imagen ejecutar y cuántas réplicas quieres. Administra un ReplicaSet que mantiene ese número de pods en ejecución, reemplazando automáticamente los que fallan. Cambiar la imagen desencadena una actualización progresiva (rolling update) que reemplaza los pods de forma gradual; kubectl rollout status la supervisa y kubectl rollout undo la revierte. kubectl scale deployment web --replicas=5 cambia el número.

Como las IP de los pods cambian, los clientes necesitan una dirección estable. Un service la proporciona: una IP virtual fija y un nombre DNS que reparte la carga entre todos los pods que coinciden con un selector de etiquetas, como app: web. Los tipos de service incluyen ClusterIP (accesible solo dentro del clúster, el predeterminado), NodePort (abre un puerto en cada nodo) y LoadBalancer (le pide al proveedor de nube un balanceador de carga externo). Un Ingress puede enrutar tráfico HTTP por nombre de host o ruta hacia los services. Otros objetos que debes reconocer: los namespaces dividen un clúster en áreas lógicas, los ConfigMaps guardan configuración y los Secrets guardan valores sensibles (codificados en base64 de forma predeterminada, lo cual no es cifrado), y los PersistentVolumeClaims solicitan almacenamiento que sobrevive a los pods. Los comandos cotidianos incluyen kubectl get pods, kubectl describe pod name, kubectl logs name y kubectl exec -it name -- sh, que reflejan los comandos de contenedores que ya conoces.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
        - name: web
          image: registry.example.com/shop/web:2.1
          ports: [{containerPort: 8080}]

Veamos un ejemplo práctico. Una tienda en línea ejecuta su capa web como el deployment anterior, con tres réplicas detrás de un service ClusterIP llamado web cuyo selector es app: web, y con un Ingress al frente para el nombre de host de la tienda. Cuando falla un nodo, el ReplicaSet programa pods de reemplazo en nodos sanos y, como los clientes usan el nombre del service en lugar de las IP de los pods, los clientes no notan nada. Para una promoción, escalas a seis réplicas; cuando una imagen nueva se comporta mal, kubectl rollout undo deployment/web restaura la versión anterior.

Errores comunes: crear pods sueltos para una aplicación y preguntarte por qué no se reemplazan después de una falla; apuntar a los clientes hacia las IP de los pods; un service cuyo selector no coincide con las etiquetas de los pods, de modo que no tiene endpoints; exponer un service interno como NodePort o LoadBalancer cuando basta con ClusterIP; tratar los Secrets codificados en base64 como si estuvieran cifrados; y editar a mano los objetos en vivo, de modo que el clúster se desvía de los manifiestos del control de versiones.

Las preguntas del examen suelen preguntar qué objeto proporciona un comportamiento. 'La unidad más pequeña, los contenedores comparten una IP' es un pod. 'Mantener N copias en ejecución', 'actualización progresiva' o 'reversión' es un deployment. 'IP o nombre DNS estable, balanceo de carga entre pods' es un service; 'accesible solo dentro del clúster' es ClusterIP. 'Enrutar por nombre de host o ruta' es un Ingress. 'Ajustes no secretos' es un ConfigMap; 'contraseñas o tokens' es un Secret. 'Cliente de línea de comandos' es kubectl, y 'estado deseado en YAML' describe la configuración declarativa.

Términos clave

Pod
La unidad más pequeña de Kubernetes: uno o más contenedores que comparten una dirección IP y volúmenes.
Deployment
Un objeto que declara una imagen y un número de réplicas, mantiene esa cantidad de pods y realiza actualizaciones progresivas.
Service
Una IP virtual y un nombre DNS estables que reparten el tráfico entre los pods seleccionados por etiquetas.
kubectl
El cliente de línea de comandos que se comunica con el servidor de API de Kubernetes.
Configuración declarativa (declarative configuration)
Describir el estado deseado en manifiestos y dejar que los controladores reconcilien el clúster para que coincida.
Secret
Un objeto de Kubernetes para valores sensibles, codificado en base64 de forma predeterminada en lugar de cifrado.
Ejemplo real

Una tienda en línea ejecuta su capa web como un deployment con tres réplicas detrás de un service ClusterIP llamado web, con un Ingress al frente. Cuando falla un nodo, el ReplicaSet del deployment programa pods de reemplazo en nodos sanos y, como los clientes usan el nombre del service en lugar de las IP de los pods, los clientes no notan nada.

Consejo para el examen: Ten claros los tres roles: un pod ejecuta contenedores, un deployment mantiene el número correcto de pods en ejecución y los actualiza, y un service les da una dirección de red estable.

Comprueba lo que sabes

¿Por qué los clientes deben conectarse a un service en lugar de directamente a la IP de un pod?

Los pods se reemplazan con frecuencia y obtienen IP nuevas; un service proporciona una IP y un nombre DNS estables que siguen a los pods actuales.

¿Qué objeto cambiarías para ejecutar más copias de una aplicación?

El número de réplicas del deployment, por ejemplo con kubectl scale deployment <name> --replicas=N.

¿Los Secrets de Kubernetes están cifrados de forma predeterminada?

No; de forma predeterminada sus valores solo están codificados en base64, así que el control de acceso y el cifrado en reposo deben configurarse por separado.

Una nueva versión de imagen provoca errores después de una actualización progresiva. ¿Cómo vuelves a la versión anterior?

kubectl rollout undo deployment/<name>, que revierte el deployment a su ReplicaSet anterior.
