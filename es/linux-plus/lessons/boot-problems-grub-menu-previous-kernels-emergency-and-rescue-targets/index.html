CompTIA Linux+ XK0-006

Problemas de arranque: menú de GRUB, kernels anteriores, targets de emergencia y rescate, errores de fstab

Un sistema que no arranca genera estrés, pero la mayoría de las fallas caen en unas pocas categorías. Relaciona lo que ves en la consola con la etapa del arranque y luego usa la ruta de recuperación adecuada. Los escenarios de Linux+ normalmente describen el mensaje y preguntan cuál es el siguiente paso.

Si no aparece ningún cargador de arranque, o aparece un mensaje como 'no bootable device', el problema está antes de que arranque Linux: un orden de arranque del firmware incorrecto, una EFI System Partition o un código de arranque del MBR faltante o dañado, o un disco que falló. Arranca desde un medio de instalación o de rescate, monta el sistema instalado, entra en él con chroot y reinstala el cargador de arranque con grub2-install o grub-install en sistemas BIOS (en sistemas UEFI es común reinstalar los paquetes de shim y GRUB o corregir las entradas con efibootmgr), y luego regenera la configuración. Si GRUB carga pero cae en un prompt grub> o grub rescue>, no puede encontrar su configuración o sus módulos, a menudo después de un cambio de particiones.

El menú de GRUB es tu principal herramienta de recuperación. Si está oculto, mantén presionado Shift (BIOS) o presiona Esc (UEFI) durante el arranque para mostrarlo. Una actualización del kernel que provoca un pánico o un controlador faltante normalmente se puede evitar eligiendo una entrada de kernel anterior, ya que las distribuciones mantienen varios kernels instalados precisamente por esta razón. Una vez arrancado, puedes hacer que el kernel que funciona sea el predeterminado (por ejemplo con grubby --set-default en sistemas de la familia RHEL), eliminar el kernel defectuoso o reconstruir su initramfs con dracut -f --kver <version> si la imagen estaba incompleta. Un mensaje 'kernel panic - not syncing: VFS: unable to mount root fs' apunta a un argumento root= incorrecto o a un initramfs al que le faltan controladores de almacenamiento.

Para cambiar el comportamiento del arranque una sola vez, presiona e sobre una entrada del menú, edita la línea que empieza con linux y presiona Ctrl+X. Agregar systemd.unit=rescue.target da un shell de root monousuario con los sistemas de archivos locales montados y servicios mínimos; pide la contraseña de root. systemd.unit=emergency.target es más mínimo: el sistema de archivos raíz se monta en solo lectura y casi nada más arranca, lo cual es útil cuando el propio modo de rescate falla. Para recuperar el acceso cuando se pierde la contraseña de root, puedes agregar rd.break (familia RHEL, que se detiene en el initramfs) o init=/bin/bash, volver a montar el sistema de archivos raíz en lectura-escritura, restablecer la contraseña y, en sistemas con SELinux, crear /.autorelabel para que las etiquetas se corrijan en el siguiente arranque. Protege GRUB con una contraseña para que otros no puedan hacer lo mismo.

Los errores en /etc/fstab son una de las fallas de arranque más comunes. Un error de tipeo en un UUID, un dispositivo que ya no existe o un tipo de sistema de archivos incorrecto hacen que systemd espere el dispositivo, agote el tiempo y te deje en modo de emergencia con un mensaje como 'Give root password for maintenance'. Inicia sesión, ejecuta journalctl -xb para ver qué montaje falló, luego mount -o remount,rw / para poder editar, corrige o comenta la línea incorrecta, y confirma con mount -a y findmnt --verify antes de reiniciar. Agregar nofail a los montajes no esenciales evita que un disco faltante detenga el arranque.

Después de la recuperación, revisa journalctl -b -1 del arranque fallido para confirmar la causa, y usa systemd-analyze blame para ver qué unidades hacen lento el arranque.

Términos clave

GRUB rescue prompt (prompt de rescate de GRUB)
Un shell mínimo de GRUB que se muestra cuando GRUB no encuentra su configuración o sus módulos.
Previous kernel (kernel anterior)
Un kernel instalado más antiguo que se puede seleccionar en GRUB para recuperarse de una actualización del kernel defectuosa.
rescue.target
Un target de systemd monousuario con los sistemas de archivos locales montados y servicios mínimos.
emergency.target
El target de systemd más mínimo, con el sistema de archivos raíz en solo lectura y casi ningún servicio.
chroot
Cambia el directorio raíz aparente para que puedas reparar un sistema instalado desde un medio de rescate.
Ejemplo real

Después de una migración de almacenamiento, un servidor arranca con 'You are in emergency mode'. journalctl -xb muestra que se agotó el tiempo esperando un dispositivo con un UUID que ya no existe. Ejecutas mount -o remount,rw /, reemplazas el UUID antiguo en /etc/fstab por el nuevo obtenido con blkid, pruebas con mount -a y reinicias con éxito.

Consejo para el examen: El modo de emergencia justo después de un cambio de almacenamiento casi siempre significa /etc/fstab; un kernel panic justo después de una actualización normalmente significa arrancar el kernel anterior desde GRUB.

Comprueba lo que sabes

¿Cómo arrancas una sola vez en modo de rescate sin cambiar ningún archivo?

Presiona e en el menú de GRUB, agrega systemd.unit=rescue.target a la línea linux y arranca con Ctrl+X.

En modo de emergencia, el sistema de archivos raíz está en solo lectura. ¿Cómo lo haces escribible para corregir /etc/fstab?

mount -o remount,rw /.

Un kernel nuevo provoca un pánico al arrancar, pero el anterior funcionaba. ¿Cuál es la recuperación más rápida?

Selecciona el kernel anterior en el menú de GRUB y luego establécelo como predeterminado o corrige el initramfs del kernel nuevo.
