CompTIA Linux+ XK0-006

SELinux: modos, contextos, restorecon, semanage, booleanos, ausearch; perfiles y modos de AppArmor

Los permisos estándar son DAC (control de acceso discrecional): el propietario decide quién obtiene acceso. SELinux (Security-Enhanced Linux) y AppArmor añaden MAC (control de acceso obligatorio): una política de todo el sistema limita lo que puede hacer cada programa sin importar la propiedad de los archivos, de modo que un servidor web comprometido no puede leer archivos fuera de lo que permite su política. Ambas comprobaciones deben superarse, así que un archivo puede tener permisos perfectos y aun así denegarse el acceso. Los sistemas de la familia RHEL usan SELinux; Ubuntu y Debian usan AppArmor, que SUSE también usó durante años, aunque las versiones más nuevas de SUSE usan SELinux de forma predeterminada.

SELinux tiene tres modos. Enforcing aplica la política y bloquea las infracciones. Permissive permite todo, pero registra lo que se habría denegado, lo cual es útil para solucionar problemas. Disabled desactiva SELinux por completo. getenforce muestra el modo, sestatus da el detalle y setenforce 0 o setenforce 1 cambian entre permissive y enforcing hasta el reinicio. El ajuste persistente es SELINUX= en /etc/selinux/config. Volver de disabled a habilitado requiere un reetiquetado completo del sistema de archivos (por ejemplo, creando /.autorelabel y reiniciando), y deshabilitar SELinux para que un problema desaparezca es la respuesta equivocada tanto en el examen como en la práctica.

Cada proceso y archivo tiene un contexto, con la forma user:role:type:level, por ejemplo system_u:object_r:httpd_sys_content_t:s0. En la política targeted predeterminada, lo que importa es el tipo: el proceso de Apache se ejecuta como httpd_t y puede leer archivos etiquetados como httpd_sys_content_t. Consulta los contextos con ls -Z para archivos y ps -eZ para procesos. Las etiquetas son el problema más común. Un archivo creado en un directorio personal y luego movido con mv conserva su etiqueta anterior, así que al servidor web se le deniega el acceso, mientras que cp crea un archivo nuevo que toma la etiqueta del destino. restorecon -Rv /var/www/html restablece los archivos a las etiquetas predeterminadas definidas por la política. chcon -t type file cambia una etiqueta de forma temporal, pero un reetiquetado o restorecon lo deshará.

Para definir un nuevo valor predeterminado para una ruta personalizada, usa semanage fcontext -a -t httpd_sys_content_t '/srv/web(/.*)?' y luego ejecuta restorecon -Rv /srv/web. semanage port -a -t http_port_t -p tcp 8081 permite que un servicio use un puerto no estándar, y semanage port -l lista las etiquetas de puertos. Los booleanos son interruptores de encendido y apagado para comportamientos opcionales de la política. getsebool -a los lista, y setsebool -P httpd_can_network_connect on permite que Apache establezca conexiones de red salientes; -P lo hace persistente. Las denegaciones se registran como mensajes AVC (access vector cache) en /var/log/audit/audit.log. ausearch -m avc -ts recent encuentra las denegaciones recientes, sealert (de setroubleshoot) las explica en lenguaje sencillo y audit2why las interpreta. audit2allow puede generar un módulo de política personalizado, pero es preferible corregir primero las etiquetas, los puertos o los booleanos.

AppArmor, en cambio, confina los programas con perfiles basados en rutas guardados en /etc/apparmor.d/. Cada perfil se ejecuta en modo enforce (las infracciones se bloquean y se registran) o en modo complain (las infracciones solo se registran). aa-status lista los perfiles cargados y sus modos, aa-enforce y aa-complain cambian el modo de un perfil, aa-disable desactiva uno y apparmor_parser -r recarga un perfil después de editarlo. Las denegaciones aparecen en el log del kernel o en el log de auditoría con apparmor="DENIED". La diferencia clave de diseño es que SELinux etiqueta los objetos y decide por tipo, mientras que AppArmor decide por la ruta del archivo, así que mover un archivo cambia cómo lo ve AppArmor, pero no su etiqueta de SELinux.

Veamos un ejemplo práctico. Después de mover un sitio nuevo a /var/www/html con mv, los visitantes reciben 403 Forbidden. Los permisos se ven bien, así que sospechas del MAC. ls -Z muestra los archivos etiquetados como user_home_t, y ausearch -m avc -ts recent muestra que a httpd_t se le denegó el acceso de lectura a ellos. Ejecutar restorecon -Rv /var/www/html los vuelve a etiquetar como httpd_sys_content_t y el sitio carga, con SELinux todavía en enforcing. La semana siguiente, la aplicación debe llamar a una API externa; el log de AVC muestra una conexión de red denegada, y setsebool -P httpd_can_network_connect on lo corrige sin escribir ninguna política personalizada.

Errores comunes: deshabilitar SELinux o dejarlo en permissive de forma permanente en lugar de corregir la causa; usar chcon como solución permanente, que un reetiquetado posterior deshace; olvidar -P en setsebool, de modo que el booleano se restablece al reiniciar; ejecutar semanage fcontext pero no restorecon, de modo que los archivos existentes conservan sus etiquetas anteriores; editar /etc/selinux/config y esperar que el modo cambie sin reiniciar; y editar un perfil de AppArmor sin recargarlo.

Las preguntas del examen suelen describir una denegación con permisos Unix correctos. 'Archivos movidos a la raíz web, errores 403' apunta a restorecon. 'Ruta de contenido personalizada, hacer la etiqueta permanente' es semanage fcontext más restorecon. 'Servicio en un puerto no estándar' es semanage port -a. 'Permitir un comportamiento opcional de forma persistente' es setsebool -P. 'Encontrar denegaciones' es ausearch -m avc. 'Registrar sin bloquear' es permissive (SELinux) o complain (AppArmor). 'Listar los perfiles de AppArmor y sus modos' es aa-status.

Términos clave

MAC
Control de acceso obligatorio (mandatory access control): una política aplicada por el sistema que restringe los programas sin importar la propiedad de los archivos.
Contexto de SELinux (SELinux context)
La etiqueta user:role:type:level de archivos y procesos; el tipo determina la mayoría de las decisiones de la política targeted.
restorecon
Restablece las etiquetas de SELinux de los archivos a los valores predeterminados definidos en la política.
semanage fcontext
Define una etiqueta de SELinux predeterminada y persistente para un patrón de rutas, que aplica restorecon.
Booleano de SELinux (SELinux boolean)
Un interruptor de la política que se activa con setsebool (-P para que sea persistente) para permitir comportamientos opcionales.
Denegación AVC (AVC denial)
Un mensaje de access vector cache en el log de auditoría que registra una acción que SELinux bloqueó o bloquearía.
Perfil de AppArmor (AppArmor profile)
Una política basada en rutas para un programa, que funciona en modo enforce o complain.
Ejemplo real

Después de mover un sitio nuevo a /var/www/html con mv, los visitantes reciben 403 Forbidden. ls -Z muestra los archivos etiquetados como user_home_t, y ausearch -m avc -ts recent muestra que a httpd_t se le denegó el acceso de lectura. Ejecutar restorecon -Rv /var/www/html los vuelve a etiquetar como httpd_sys_content_t y el sitio carga, con SELinux todavía en enforcing.

Consejo para el examen: La respuesta de buenas prácticas casi nunca es 'deshabilitar SELinux'; busca en su lugar restorecon, semanage fcontext, semanage port o setsebool -P, y usa el modo permissive solo temporalmente para confirmar que SELinux es la causa.

Comprueba lo que sabes

¿Qué modo de SELinux registra las denegaciones sin bloquearlas?

Permissive, que registra los mensajes AVC pero permite las acciones, lo que lo hace útil para solucionar problemas.

Sirves contenido web desde /srv/web. ¿Cómo haces permanente su etiqueta correcta?

semanage fcontext -a -t httpd_sys_content_t '/srv/web(/.*)?' seguido de restorecon -Rv /srv/web.

¿Cuál es el equivalente en AppArmor del modo permissive de SELinux para un solo perfil?

El modo complain, que se establece con aa-complain y registra las infracciones sin bloquearlas.

¿Por qué un archivo movido con mv provoca denegaciones de SELinux y un archivo copiado no?

mv conserva la etiqueta original del archivo, mientras que cp crea un archivo nuevo que hereda la etiqueta predeterminada del directorio de destino.
