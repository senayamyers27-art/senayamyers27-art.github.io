CompTIA Linux+ XK0-006

Endurecimiento del sistema operativo: deshabilitar servicios sin uso, Secure Boot, parches, integridad de archivos (AIDE)

Endurecer (hardening) significa reducir la superficie de ataque de un sistema: eliminar lo que no se necesita, restringir lo que queda, mantener el software al día y vigilar los cambios no autorizados. Ningún control por sí solo detiene todos los ataques, así que el endurecimiento superpone varias defensas, un enfoque llamado defensa en profundidad. Las cuatro áreas de esta lección, servicios, integridad del arranque, parches y monitoreo de integridad de archivos, son el núcleo de la mayoría de las listas de verificación de endurecimiento.

Empieza por los servicios. Cada servicio de red que escucha es un posible punto de entrada, así que ejecuta solo lo que el rol del servidor requiere. ss -tulpn lista los puertos TCP y UDP en escucha con el proceso dueño, y systemctl list-unit-files --state=enabled muestra lo que se inicia al arrancar. Para todo lo innecesario, systemctl disable --now name lo detiene e impide que se inicie, y systemctl mask name impide que se inicie incluso manualmente o como dependencia. Mejor aún, elimina los paquetes innecesarios con dnf o apt para que no haya nada que parchar. Reemplaza los protocolos heredados en texto claro, como Telnet, rsh y FTP simple, por SSH y SFTP. Las imágenes de instalación mínima facilitan esto desde el inicio.

Secure Boot es una función de UEFI (Unified Extensible Firmware Interface) que verifica las firmas digitales de los componentes de arranque para que solo se ejecute código confiable antes del sistema operativo. La mayoría de las distribuciones usan un pequeño cargador firmado llamado shim que luego verifica GRUB y el kernel, y el kernel puede exigir módulos firmados. Esto defiende contra bootkits y rootkits que manipulan las primeras etapas del arranque. mokutil --sb-state muestra si Secure Boot está habilitado. Los módulos de kernel de terceros, como algunos drivers, deben firmarse con una clave inscrita como MOK (Machine Owner Key) o no se cargarán. Protege la configuración del firmware y GRUB con contraseñas para que alguien en la consola no pueda cambiar fácilmente los parámetros de arranque.

Los parches corrigen vulnerabilidades conocidas, y el software sin parchar es una de las formas más comunes en que se comprometen los sistemas. Aplica actualizaciones con regularidad con dnf upgrade o apt update && apt upgrade, dando prioridad a las actualizaciones de seguridad (dnf updateinfo list --security, dnf upgrade --security). Automatiza cuando corresponda con dnf-automatic o unattended-upgrades. Las actualizaciones del kernel necesitan un reinicio para surtir efecto, a menos que uses un servicio de parcheo en vivo (live patching), y needs-restarting -r (familia RHEL) o el archivo /var/run/reboot-required (familia Debian) te indican cuándo hace falta uno. Prueba las actualizaciones primero en sistemas que no sean de producción, programa ventanas de mantenimiento y ten un plan de reversión, como snapshots o dnf history undo.

El monitoreo de integridad de archivos detecta cambios no autorizados en archivos importantes, una señal común de intrusión. AIDE (Advanced Intrusion Detection Environment) construye una base de datos de atributos y hashes de archivos y luego compara los escaneos posteriores contra ella. La configuración está en /etc/aide.conf o /etc/aide/aide.conf. Uso típico: aide --init crea una base de datos nueva, la colocas en su lugar como referencia (por ejemplo, renombrando aide.db.new.gz a aide.db.gz), y luego aide --check informa los archivos agregados, eliminados y modificados, normalmente desde un timer diario o un trabajo de cron. Después de cambios legítimos, como aplicar parches, ejecuta aide --update y reemplaza la base de datos. Guarda una copia fuera de línea o de solo lectura, ya que de lo contrario un atacante con root podría alterarla. Otros pasos comunes incluyen una configuración estricta de SSH, un firewall de host, SELinux o AppArmor en modo enforcing, noexec, nosuid y nodev en /tmp, parámetros de red de sysctl seguros y registro centralizado de logs.

Considera un ejemplo práctico. Al endurecer un nuevo relay de correo, ejecutas ss -tulpn y encuentras cups y un antiguo listener de rpcbind. Deshabilitas y eliminas ambos paquetes, aplicas las actualizaciones de seguridad con dnf upgrade --security y reinicias con el nuevo kernel después de que needs-restarting -r indica que se requiere un reinicio. mokutil --sb-state informa que Secure Boot está habilitado. Luego inicializas AIDE, instalas la base de datos, la copias a un almacenamiento de solo lectura y programas un aide --check nocturno. Una semana después, el informe señala un binario modificado en /usr/bin sin ninguna actualización de paquete que lo explique, y abres un incidente.

Errores comunes: detener un servicio con systemctl stop pero dejarlo habilitado, de modo que vuelve en el siguiente arranque; deshabilitar Secure Boot de forma permanente para cargar un solo driver sin firmar en lugar de inscribir una MOK; instalar parches sin reiniciar cuando se trata de una corrección del kernel; no actualizar nunca la línea base de AIDE después de aplicar parches, de modo que los cambios reales se esconden entre cientos de cambios esperados; y guardar la base de datos de AIDE solo en el mismo host que protege.

Las preguntas del examen usan pistas reconocibles. 'Reducir la superficie de ataque' apunta a eliminar o deshabilitar servicios y paquetes sin uso. 'Impedir que un servicio se inicie, incluso como dependencia' es mask. 'Solo cargadores de arranque y kernels firmados' es Secure Boot, y 'un driver de terceros no se carga con Secure Boot activado' apunta a la firma con MOK. 'Detectar cambios no autorizados en archivos del sistema' es AIDE o el monitoreo de integridad de archivos. 'Aplicar solo correcciones de seguridad' es dnf upgrade --security.

Términos clave

Superficie de ataque (attack surface)
El conjunto total de servicios, software e interfaces que un atacante podría intentar explotar.
systemctl mask
Enlaza una unidad a /dev/null para que no pueda iniciarse manualmente ni como dependencia hasta que se desenmascare.
Secure Boot
Una función de UEFI que solo permite ejecutar cargadores de arranque, kernels y módulos firmados.
MOK
Machine Owner Key, una clave inscrita localmente que se usa para firmar kernels o módulos para que se carguen con Secure Boot.
AIDE
Advanced Intrusion Detection Environment, una herramienta de integridad de archivos que compara los archivos con una línea base almacenada de hashes y atributos.
Gestión de parches (patch management)
El proceso de encontrar, probar, aplicar y verificar actualizaciones de software, dando prioridad a las correcciones de seguridad.
Defensa en profundidad (defense in depth)
Superponer varios controles independientes para que la falla de uno no deje expuesto el sistema.
Ejemplo real

Al endurecer un nuevo relay de correo, ejecutas ss -tulpn y encuentras cups y un antiguo listener de rpcbind. Deshabilitas y eliminas ambos paquetes, aplicas todas las actualizaciones de seguridad con dnf upgrade --security y reinicias con el nuevo kernel, confirmas que mokutil --sb-state informa Secure Boot habilitado e inicializas AIDE para que una verificación nocturna señale los cambios inesperados en /etc y /usr/bin.

Consejo para el examen: Después de actualizaciones legítimas, la línea base de AIDE debe actualizarse; si no, cada binario parchado aparece como un cambio y las intrusiones reales se esconden en el ruido. disable impide el inicio al arrancar; mask bloquea la unidad por completo.

Comprueba lo que sabes

¿Qué comando lista los puertos en escucha y los procesos que los poseen?

ss -tulpn.

¿Contra qué amenaza defiende principalmente Secure Boot?

Contra cargadores de arranque, kernels y código de arranque temprano manipulados o maliciosos, como bootkits y rootkits.

¿Qué compara aide --check?

El estado actual de los archivos monitoreados (hashes, permisos, propietario, tamaños) contra la base de datos de línea base almacenada.

¿Cuál es la diferencia entre systemctl disable y systemctl mask?

disable impide que una unidad se inicie al arrancar, pero todavía puede iniciarse manualmente o por una dependencia; mask impide que se inicie en absoluto.
