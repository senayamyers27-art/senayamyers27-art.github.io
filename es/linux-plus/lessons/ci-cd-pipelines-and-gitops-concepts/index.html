Pipelines de CI/CD y conceptos de GitOps

Una vez que los scripts, la configuración y la infraestructura viven en Git, puedes automatizar cómo se prueban y entregan los cambios. Los pipelines de CI/CD (integración continua y entrega o despliegue continuos) hacen esto, y GitOps extiende la idea para que Git se convierta en la única fuente de verdad sobre lo que debe estar en ejecución. Linux+ cubre los conceptos y el vocabulario más que un producto en particular, así que aprende para qué sirve cada etapa y cómo encajan las piezas.

Integración continua significa que las personas fusionan cambios pequeños en una rama compartida con frecuencia, y cada cambio desencadena una compilación y una ejecución de pruebas automatizadas. Para el código de administración, eso puede incluir analizar scripts de shell con ShellCheck, ejecutar ansible-lint o yamllint, tofu validate y plan, construir imágenes de contenedores, ejecutar pruebas unitarias y escanear en busca de vulnerabilidades o de secretos incluidos por accidente en un commit. Los problemas se detectan minutos después de introducirse, cuando son más baratos de corregir, y una verificación fallida bloquea la fusión.

Entrega continua significa que cada cambio que pasa el pipeline se empaqueta y queda listo para publicarse, con una puerta de aprobación humana antes de producción. El despliegue continuo va un paso más allá y publica automáticamente cuando pasan todas las verificaciones. Los despliegues suelen avanzar por entornos como desarrollo, staging y producción, y usan estrategias que limitan el riesgo: las actualizaciones progresivas (rolling updates) reemplazan las instancias de forma gradual, los despliegues blue-green cambian el tráfico entre dos entornos idénticos y las publicaciones canary envían primero una pequeña parte del tráfico a la nueva versión. Todo pipeline también debe facilitar la reversión (rollback).

Un pipeline se define como código, normalmente un archivo YAML en el repositorio, como un archivo de GitLab CI, un workflow de GitHub Actions o un Jenkinsfile. Está formado por etapas (build, test, deploy) que contienen trabajos (jobs) que se ejecutan en runners o agentes, a menudo dentro de contenedores. Los trabajos se desencadenan por eventos como un push, un pull request o una programación, y producen artefactos, como un paquete o una imagen de contenedor, que pasan a las etapas posteriores. Los secretos, como las claves de despliegue, se guardan en las variables protegidas del sistema de CI o en un gestor de secretos, nunca en el repositorio, y los runners deben tener solo los permisos que necesitan.

GitOps aplica estas ideas a las operaciones. El estado deseado, por ejemplo los manifiestos de Kubernetes o las definiciones de infraestructura, se declara en un repositorio Git. Los cambios se hacen solo mediante pull requests, lo que aporta revisión, aprobación y un registro de auditoría completo. Un agente automatizado, como Argo CD o Flux en Kubernetes, compara continuamente el sistema en vivo con el repositorio y reconcilia cualquier diferencia. En este modelo basado en pull, el clúster obtiene su configuración en lugar de que un pipeline le inyecte credenciales. Los beneficios son la consistencia, la trazabilidad y la recuperación rápida: revertir es tan simple como revertir un commit, y la deriva causada por cambios manuales se detecta y se deshace. La disciplina es que nadie edita producción a mano; si no está en Git, no existe.

Considera un ejemplo práctico. Un equipo administra sus aplicaciones de Kubernetes con GitOps. Un ingeniero abre un pull request que aumenta el número de réplicas de un deployment de tres a cinco. El pipeline de CI valida el YAML, ejecuta verificaciones de políticas y publica los resultados en el pull request; un colega lo aprueba y se fusiona. Argo CD detecta el nuevo commit y escala el deployment. Más tarde, durante una tarde ajetreada, alguien edita a mano el número de réplicas en el clúster; Argo CD marca la aplicación como fuera de sincronía (out of sync) y restaura la versión de Git. Cuando una publicación posterior se comporta mal, el equipo revierte su commit, y el clúster vuelve al estado anterior en cuestión de minutos.

Errores comunes: confundir la entrega continua (puerta manual) con el despliegue continuo (automático); guardar credenciales en el YAML del pipeline; dar a los runners amplios derechos administrativos; hacer correcciones de emergencia directamente en los servidores en un entorno GitOps, que el reconciliador deshará; omitir pruebas para que un pipeline sea más rápido; y tratar la CI solo como un servidor de compilación, en lugar de una puerta de calidad que se ejecuta con cada cambio.

La redacción del examen se corresponde con claridad. 'Probar automáticamente cada commit' es integración continua. 'Listo para publicar, pero una persona aprueba producción' es entrega continua, y 'publicado automáticamente después de pasar las pruebas' es despliegue continuo. 'Git es la fuente de verdad y un agente reconcilia el clúster' es GitOps. 'Revertir' en GitOps significa revertir el commit. 'Un pequeño porcentaje de usuarios recibe primero la nueva versión' es canary, y 'cambiar entre dos entornos idénticos' es blue-green.

Términos clave

Integración continua (continuous integration)
Fusionar cambios pequeños con frecuencia, con cada cambio compilado y probado automáticamente.
Entrega continua frente a despliegue continuo
La entrega mantiene cada cambio que pasa las pruebas listo para publicarse tras una aprobación manual; el despliegue publica automáticamente.
Pipeline
Una definición bajo control de versiones de etapas y trabajos que compilan, prueban y despliegan los cambios.
Artefacto (artifact)
Un resultado de un trabajo del pipeline, como un paquete o una imagen de contenedor, que pasa a las etapas posteriores.
GitOps
Operar sistemas declarando el estado deseado en Git y haciendo que un agente reconcilie el entorno en vivo con él.
Publicación canary (canary release)
Enviar una pequeña parte del tráfico a una nueva versión antes de desplegarla por completo.
Deriva (drift)
Una diferencia entre el sistema en vivo y el estado declarado, normalmente por cambios manuales.
Ejemplo real

Un equipo administra sus aplicaciones de Kubernetes con GitOps. Un ingeniero abre un pull request que aumenta el número de réplicas de un deployment; el pipeline de CI valida el YAML y ejecuta verificaciones de políticas, un colega lo aprueba y, tras la fusión, Argo CD detecta el nuevo commit y escala el deployment. Cuando más tarde alguien edita a mano el número de réplicas en el clúster, Argo CD marca la deriva y restaura la versión de Git.

Consejo para el examen: En GitOps, la respuesta para revertir casi siempre es 'revertir el commit en Git', no 'corregirlo directamente en el servidor o el clúster'. La entrega tiene una puerta humana; el despliegue no.

Comprueba lo que sabes

¿Cuál es la diferencia entre la entrega continua y el despliegue continuo?

La entrega continua requiere una aprobación manual antes de publicar en producción; el despliegue continuo publica automáticamente una vez que pasan las verificaciones.

En GitOps, ¿cuál es la fuente de verdad del estado deseado?

El repositorio Git; los cambios se hacen mediante pull requests y un agente automatizado los reconcilia.

¿Dónde deben guardarse las credenciales de despliegue de un pipeline?

En las variables secretas protegidas del sistema de CI o en un gestor de secretos, nunca en un commit del repositorio.

¿Qué estrategia de despliegue envía primero una pequeña parte del tráfico a una nueva versión?

Una publicación canary, que limita el impacto si la nueva versión se comporta mal.
