Pipelines de CI/CD y conceptos de GitOps

Una vez que los scripts, la configuración y la infraestructura viven en Git, puedes automatizar cómo se prueban y entregan los cambios. Los pipelines de CI/CD (integración continua y entrega o despliegue continuos) hacen esto, y GitOps extiende la idea para que Git se convierta en la única fuente de verdad de lo que debería estar en ejecución. Linux+ cubre los conceptos y el vocabulario.

La integración continua significa que los desarrolladores fusionan cambios pequeños en una rama compartida con frecuencia, y cada cambio desencadena una compilación y una ejecución de pruebas automatizadas. Para el código de administración, eso podría incluir revisar scripts de shell con ShellCheck, ejecutar ansible-lint o yamllint, tofu validate y plan, construir imágenes de contenedor, ejecutar pruebas unitarias y escanear en busca de vulnerabilidades o de secretos subidos por accidente. Los problemas se detectan a los pocos minutos de introducirse, cuando son más baratos de corregir.

La entrega continua significa que cada cambio que pasa el pipeline se empaqueta y queda listo para publicarse, con una puerta de aprobación humana antes de producción. El despliegue continuo va un paso más allá y publica automáticamente cuando pasan todas las verificaciones. Los despliegues normalmente avanzan por entornos, como desarrollo, staging y producción, y usan estrategias que limitan el riesgo: las actualizaciones progresivas (rolling updates) reemplazan instancias gradualmente, los despliegues blue-green cambian el tráfico entre dos entornos idénticos y los lanzamientos canary envían primero una pequeña parte del tráfico a la nueva versión. Todo pipeline también debería facilitar la reversión (rollback).

Un pipeline se define como código, normalmente un archivo YAML guardado en el repositorio, como un archivo de GitLab CI, un workflow de GitHub Actions o un Jenkinsfile. Está formado por etapas (build, test, deploy) que contienen trabajos (jobs) que se ejecutan en runners o agentes, a menudo dentro de contenedores. Los trabajos se disparan por eventos como un push, un pull request o una programación horaria, y producen artefactos, como un paquete compilado o una imagen de contenedor, que pasan a las etapas siguientes. Los secretos como las claves de despliegue se guardan en las variables protegidas del sistema de CI o en un gestor de secretos, nunca en el repositorio, y los runners deberían tener solo los permisos que necesitan.

GitOps aplica estas ideas a las operaciones. El estado deseado del sistema, por ejemplo manifiestos de Kubernetes o definiciones de infraestructura, se declara en un repositorio Git. Los cambios se hacen solo mediante pull requests, lo que aporta revisión, aprobación y un registro de auditoría completo. Un agente automatizado, como Argo CD o Flux en Kubernetes, compara continuamente el sistema en vivo con el repositorio y concilia cualquier diferencia. En este modelo basado en pull, el clúster obtiene su configuración en lugar de que un pipeline le inyecte credenciales.

Los beneficios son la consistencia, la trazabilidad y la recuperación rápida. Revertir es tan sencillo como revertir un commit, y los cambios manuales hechos directamente en el sistema (drift, desviación) se detectan y se deshacen automáticamente. La disciplina es que nadie edita producción a mano: si no está en Git, no existe.

Términos clave

Continuous integration (integración continua)
Compilar y probar automáticamente cada cambio fusionado en un repositorio compartido.
Continuous delivery vs deployment (entrega vs despliegue continuo)
La entrega mantiene cada cambio aprobado listo para publicarse con una puerta manual; el despliegue lo publica automáticamente.
Pipeline
Una definición con control de versiones de etapas y trabajos que compilan, prueban y despliegan código.
GitOps
Un modelo operativo en el que Git contiene el estado deseado declarado y agentes automatizados concilian los sistemas para que coincidan.
Drift (desviación)
Diferencias entre el sistema en vivo y la configuración declarada, normalmente por cambios manuales.
Ejemplo real

Un equipo administra sus aplicaciones de Kubernetes con GitOps. Un ingeniero abre un pull request que aumenta la cantidad de réplicas de un deployment; el pipeline de CI valida el YAML y ejecuta verificaciones de políticas, un colega lo aprueba y, tras la fusión, Argo CD detecta el nuevo commit y escala el deployment. Cuando alguien más tarde edita a mano la cantidad de réplicas en el clúster, Argo CD señala la desviación y restaura la versión de Git.

Consejo para el examen: En GitOps, la respuesta para revertir casi siempre es 'revertir el commit en Git', no 'corregirlo directamente en el servidor o el clúster'.

Comprueba lo que sabes

¿Cuál es la diferencia entre la entrega continua y el despliegue continuo?

La entrega continua requiere una aprobación manual antes de publicar en producción; el despliegue continuo publica automáticamente una vez que pasan las verificaciones.

En GitOps, ¿cuál es la fuente de verdad del estado deseado?

El repositorio Git; los cambios se hacen mediante pull requests y un agente automatizado los concilia.

¿Dónde deberían guardarse las credenciales de despliegue de un pipeline?

En las variables secretas protegidas del sistema de CI o en un gestor de secretos, nunca en el repositorio.
