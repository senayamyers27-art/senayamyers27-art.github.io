CompTIA Linux+ XK0-006

Problemas de almacenamiento: discos llenos, agotamiento de inodos (df -i), archivos eliminados pero abiertos (lsof +L1), fsck/xfs_repair

Los problemas de almacenamiento están entre los incidentes más comunes de Linux: los servicios no arrancan, los logs dejan de escribirse, las bases de datos se caen y los usuarios no pueden guardar su trabajo. Los síntomas suelen parecerse, normalmente 'No space left on device', así que necesitas una forma sistemática de encontrar la causa real.

Empieza con df -h para ver qué sistema de archivos está lleno. Luego profundiza con du: du -xh --max-depth=1 /var | sort -h lista los directorios más grandes solo en ese sistema de archivos (-x se queda en un solo sistema de archivos). find /var -xdev -type f -size +500M encuentra archivos grandes. Los culpables comunes son logs desbocados, volcados de memoria (core dumps), kernels antiguos en /boot, cachés de paquetes (dnf clean all, apt clean), imágenes y volúmenes de contenedores y respaldos olvidados. Recuerda que ext4 reserva de forma predeterminada un porcentaje de bloques para root (ajustable con tune2fs -m), así que un sistema de archivos puede estar lleno para los usuarios mientras root todavía puede escribir.

El agotamiento de inodos es la clásica pregunta trampa. Cada archivo usa un inodo, y en ext4 la cantidad de inodos se fija al crear el sistema de archivos. Si millones de archivos diminutos, como archivos de sesión o entradas de la cola de correo, consumen todos los inodos, obtienes 'No space left on device' aunque df -h muestre mucho espacio libre. df -i muestra el uso de inodos; con IUse% al 100 por ciento has encontrado la causa. Encuentra los directorios con más archivos, por ejemplo con find /var -xdev -type f | cut -d/ -f2-4 | sort | uniq -c | sort -rn | head, luego elimina o archiva los archivos innecesarios y corrige lo que los crea. XFS asigna inodos de forma dinámica, así que es menos propenso a esto.

Los archivos eliminados pero abiertos explican por qué df y du no coinciden. Cuando eliminas un archivo que un proceso todavía tiene abierto, el nombre desaparece, así que du ya no lo cuenta, pero el kernel conserva los bloques de datos hasta que el último proceso cierre el archivo, por lo que df sigue mostrando el espacio como usado. Esto suele pasar cuando alguien borra un log enorme en lugar de rotarlo. lsof +L1 lista los archivos abiertos cuyo número de enlaces es menor que uno, es decir, eliminados; lsof | grep deleted también funciona. La solución es reiniciar o recargar el proceso que lo retiene (o hacer que vuelva a abrir sus logs). En una emergencia, truncar el archivo a través de /proc/<PID>/fd/<N> libera espacio, pero reiniciar el servicio es la solución limpia. Usa logrotate o trunca con > file en lugar de rm para los logs activos.

La corrupción del sistema de archivos, tras una caída, un corte de energía o un disco que falla, se repara con herramientas de verificación, y deben ejecutarse sobre sistemas de archivos desmontados (o sobre el sistema de archivos raíz en el arranque o desde un medio de rescate) para no causar más daño. Para ext2/3/4, fsck /dev/sdb1 llama a e2fsck; -y responde que sí a las correcciones y -f fuerza una verificación. Configurar el sexto campo de fstab hace que las verificaciones en el arranque ocurran automáticamente. Para XFS, fsck no hace nada útil; usa xfs_repair /dev/sdb1 sobre el dispositivo desmontado. Si se queja de un log sucio, montar y desmontar limpiamente el sistema de archivos reproduce el log; xfs_repair -L pone a cero el log, pero puede perder cambios recientes, así que es el último recurso. Btrfs usa btrfs scrub y btrfs check. Revisa siempre también la salud del disco (datos SMART, mensajes del kernel), porque la corrupción puede ser un síntoma de hardware que está fallando.

Términos clave

Inode exhaustion (agotamiento de inodos)
Un sistema de archivos que se queda sin inodos, lo que bloquea los archivos nuevos aunque quede espacio libre; se ve con df -i.
Deleted-but-open file (archivo eliminado pero abierto)
Un archivo cuyo nombre se eliminó mientras un proceso todavía lo mantiene abierto, por lo que su espacio no se libera.
lsof +L1
Lista los archivos abiertos con un número de enlaces menor que uno, revelando archivos eliminados que todavía consumen espacio.
fsck / e2fsck
Herramientas de verificación y reparación para sistemas de archivos de la familia ext, que se ejecutan sobre dispositivos desmontados.
xfs_repair
La herramienta de reparación para sistemas de archivos XFS; fsck no se usa con XFS.
Ejemplo real

Un servidor de correo informa 'No space left on device', pero df -h muestra un 40 por ciento de uso. df -i muestra /var al 100 por ciento de uso de inodos, y al contar archivos se descubren millones de entradas obsoletas en un directorio de cola dejadas por una tarea atascada. Después de corregir la tarea y limpiar las entradas antiguas, el uso de inodos baja y el correo vuelve a fluir.

Consejo para el examen: Si df -h muestra espacio libre pero las escrituras fallan, piensa en inodos (df -i). Si df muestra lleno pero du no encuentra los datos, piensa en archivos eliminados pero abiertos (lsof +L1).

Comprueba lo que sabes

¿Qué comando confirma el agotamiento de inodos?

df -i, que muestra el uso de inodos (IUse%) de cada sistema de archivos.

Eliminaste un log de 20 GB, pero df todavía muestra el espacio usado. ¿Por qué, y qué lo soluciona?

El proceso que escribe el log todavía mantiene abierto el archivo eliminado; reinicia o envía una señal a ese proceso para que cierre el archivo, lo que libera el espacio.

¿Qué herramienta repara un sistema de archivos XFS corrupto, y en qué estado debe estar?

xfs_repair, ejecutado sobre el dispositivo desmontado.
