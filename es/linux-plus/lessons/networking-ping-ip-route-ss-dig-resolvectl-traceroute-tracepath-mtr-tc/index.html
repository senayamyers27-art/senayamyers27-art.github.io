CompTIA Linux+ XK0-006

Redes: ping, ip route, ss, dig/resolvectl, traceroute/tracepath/mtr, tcpdump, nmap

La resolución de problemas de red avanza más rápido cuando recorres las capas en orden: ¿la interfaz está activa con la dirección correcta?, ¿puedes llegar al gateway?, ¿funciona el enrutamiento?, ¿funciona la resolución de nombres? y ¿el servicio realmente está escuchando y se le permite el paso? Cada herramienta de esta lección responde una de esas preguntas, y saber qué herramienta responde cada pregunta es lo que evalúa el examen.

Empieza localmente con ip a (direcciones y estado del enlace) e ip route (tabla de enrutamiento). La línea que empieza con default via es el gateway predeterminado; sin ella, solo se puede llegar a las redes conectadas directamente. ip route get 8.8.8.8 muestra exactamente qué ruta e interfaz usaría un paquete hacia esa dirección. Luego ping prueba la alcanzabilidad con eco ICMP (Internet Control Message Protocol): ping -c 4 192.168.1.1 para el gateway, luego una IP remota y luego un nombre de host. Si una IP funciona pero un nombre falla, el problema es el DNS (Domain Name System). Muchos firewalls bloquean ICMP, así que un ping fallido no demuestra que un host esté caído.

La resolución de nombres se prueba con dig: dig example.com muestra la respuesta, el TTL y qué servidor respondió, dig @8.8.8.8 example.com consulta a un servidor específico, dig -x 203.0.113.10 realiza una búsqueda inversa, dig MX example.com pide los registros de correo y +short recorta la salida. nslookup y host son alternativas más simples. En sistemas que usan systemd-resolved, resolvectl status muestra los servidores DNS por interfaz, resolvectl query name resuelve a través del resolvedor del sistema y resolvectl flush-caches vacía su caché. getent hosts name sigue /etc/nsswitch.conf, así que incluye /etc/hosts, que dig ignora.

Las herramientas de ruta muestran dónde se detienen los paquetes. traceroute host lista cada salto de router usando valores crecientes de TTL (time to live); traceroute -T -p 443 usa TCP para atravesar firewalls que bloquean los valores predeterminados. tracepath hace un trabajo similar sin privilegios de root e informa el MTU de la ruta (unidad máxima de transmisión). mtr host combina ping y traceroute en una vista que se actualiza continuamente, con pérdida y latencia por salto, lo que es excelente para problemas intermitentes. Los asteriscos en un salto pueden significar simplemente que ese router no responde, así que fíjate si la pérdida continúa hasta el final.

ss muestra los sockets y reemplazó al antiguo netstat. ss -tulpn lista los puertos TCP y UDP en escucha con direcciones numéricas y el proceso dueño; ss -tan muestra todas las conexiones TCP con sus estados, como ESTABLISHED o TIME-WAIT. Un servicio que escucha en 127.0.0.1:8080 solo acepta conexiones locales, mientras que 0.0.0.0:8080 o *:8080 escucha en todas las interfaces, una razón muy común por la que un servicio no es alcanzable desde otros hosts. tcpdump captura paquetes: tcpdump -i eth0 -nn port 53 muestra el tráfico DNS sin resolver nombres, host 10.0.0.5 filtra por dirección y -w capture.pcap guarda en un archivo para Wireshark. Las solicitudes que salen sin respuestas, o los reinicios TCP (resets), separan rápidamente los problemas locales de los remotos. nmap escanea en busca de puertos abiertos, cerrados o filtrados: nmap -p 22,80,443 server verifica puertos específicos y nmap -sV identifica las versiones de los servicios. Escanear desde otro host muestra lo que la red realmente deja pasar. Escanea solo los sistemas que te pertenecen o que tienes autorización para probar.

Considera un ejemplo práctico. Los usuarios no pueden llegar a una nueva API en el puerto 8080. Desde un cliente, ping api01 y dig api01.example.com funcionan, así que el direccionamiento, el enrutamiento y el DNS están bien. nmap -p 8080 api01 informa el puerto como cerrado en lugar de filtrado, lo que sugiere que nada está escuchando del lado de la red, más que un descarte por parte de un firewall. En el servidor, ss -tlpn muestra el proceso escuchando solo en 127.0.0.1:8080. Cambiar la dirección de enlace (bind) de la aplicación a 0.0.0.0 y agregar una regla de firewalld con firewall-cmd --add-port=8080/tcp --permanent y firewall-cmd --reload lo resuelve, y tcpdump -nn port 8080 confirma que los handshakes se completan.

Errores comunes: concluir que un host está caído porque falla el ping; probar el DNS con dig y olvidar que la aplicación puede usar /etc/hosts a través de nsswitch; interpretar un salto con asterisco en traceroute como la falla; pasar por alto una dirección de enlace de loopback; usar los hábitos de netstat en sistemas donde solo está instalado ss; y ejecutar nmap contra redes que no tienes autorización para escanear.

La redacción del examen se relaciona con las herramientas. 'Mostrar el gateway predeterminado' es ip route. 'La IP funciona pero el nombre falla' significa DNS, así que dig, resolvectl o /etc/resolv.conf. 'Qué proceso está escuchando en un puerto' es ss -tulpn. 'En qué punto de la ruta se detienen los paquetes' es traceroute, tracepath o mtr, con mtr para pérdidas intermitentes. 'Capturar paquetes para analizarlos' es tcpdump. 'Qué puertos están abiertos desde afuera' es nmap. 'Closed' (cerrado) significa alcanzable pero sin nada escuchando; 'filtered' (filtrado) suele significar un firewall.

Términos clave

Ruta predeterminada (default route)
La ruta usada para los destinos sin una entrada más específica, que aparece como default via en ip route.
ss
La herramienta de estadísticas de sockets que lista los puertos en escucha, las conexiones y los procesos dueños.
dig
Una herramienta de consultas DNS que muestra las respuestas, los TTL y el servidor que respondió.
resolvectl
El cliente de systemd-resolved, que muestra los servidores DNS por enlace y resuelve nombres a través del resolvedor del sistema.
mtr
Una herramienta que combina ping y traceroute para mostrar continuamente la pérdida y la latencia por salto.
tcpdump
Una herramienta de captura de paquetes de línea de comandos con filtros, capaz de guardar archivos pcap.
nmap
Un escáner de puertos que informa los puertos abiertos, cerrados y filtrados y puede identificar servicios.
Ejemplo real

Los usuarios no pueden llegar a una nueva API en el puerto 8080. ping y dig funcionan, y nmap -p 8080 desde un cliente muestra el puerto cerrado. En el servidor, ss -tlpn muestra el proceso escuchando solo en 127.0.0.1:8080. Cambiar la dirección de enlace de la aplicación a 0.0.0.0 y agregar una regla de firewalld para 8080/tcp lo resuelve.

Consejo para el examen: Trabaja de abajo hacia arriba: enlace e IP, gateway, IP remota, nombre DNS y luego el puerto del servicio. Si las IP funcionan pero los nombres fallan, concéntrate en el DNS y en nsswitch en lugar del enrutamiento.

Comprueba lo que sabes

ping 8.8.8.8 funciona pero ping example.com falla. ¿Dónde es probable que esté el problema?

En la resolución de nombres: la configuración del servidor DNS, /etc/resolv.conf, systemd-resolved o nsswitch.conf.

¿Qué comando lista los puertos TCP y UDP en escucha con los nombres de los procesos?

ss -tulpn.

¿Qué significa para los clientes remotos un servicio enlazado a 127.0.0.1?

Solo acepta conexiones del host local, así que los clientes remotos no pueden conectarse.

¿Qué herramienta muestra mejor una pérdida de paquetes intermitente en un salto determinado?

mtr, que sondea repetidamente cada salto y muestra la pérdida y la latencia por salto a lo largo del tiempo.
