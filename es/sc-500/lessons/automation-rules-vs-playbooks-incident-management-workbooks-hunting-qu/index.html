Microsoft Certified: Cloud and AI Security Engineer Associate (replaces Azure Security Engineer Associate / AZ-500) SC-500

Reglas de automatización vs playbooks, administración de incidentes, workbooks, consultas de hunting, watchlists e inteligencia de amenazas

Una vez que Sentinel crea incidentes, los analistas necesitan administrarlos de forma eficiente. Varias funciones apoyan ese trabajo, y al examen le gusta evaluar cuál encaja en cada escenario.

Las reglas de automatización (automation rules) son reglas ligeras y administradas de forma central que se ejecutan cuando se crea o actualiza un incidente, o cuando se crea una alerta. Sus condiciones pueden comprobar el nombre de la regla de análisis, la gravedad, las entidades, las etiquetas y otras propiedades, y sus acciones pueden asignar un propietario, cambiar el estado o la gravedad, agregar etiquetas, agregar una lista de tareas para los analistas, ejecutar un playbook o cerrar el incidente (por ejemplo, cerrar automáticamente falsos positivos conocidos). Se ejecutan por orden de prioridad y pueden tener una fecha de caducidad, lo que es útil para una supresión temporal durante pruebas planificadas. No se necesita código.

Los playbooks son flujos de trabajo de Azure Logic Apps que se desencadenan desde Sentinel mediante el desencadenador de incidente, de alerta o de entidad. Manejan respuestas más complejas y de varios pasos que involucran otros sistemas: enriquecer una IP con inteligencia de amenazas, publicar una tarjeta adaptable en Teams pidiendo a un analista que apruebe, deshabilitar un usuario en Entra ID, aislar un dispositivo mediante Defender for Endpoint o abrir un ticket en ServiceNow. Los playbooks se ejecutan con su propia identidad (preferiblemente una identidad administrada) con permisos en los sistemas de destino, y Sentinel necesita permiso (el rol Microsoft Sentinel Automation Contributor en el grupo de recursos del playbook) para ejecutarlos. El patrón típico es una regla de automatización que llama a un playbook, combinando condiciones centrales con acciones completas.

La administración de incidentes se realiza en la página Incidents: cada incidente tiene una gravedad, un estado (New, Active, Closed), un propietario, una clasificación al cerrarse (verdadero positivo, positivo benigno, falso positivo, indeterminado), comentarios, tareas, las alertas y entidades involucradas, una línea de tiempo y un gráfico de investigación. Las páginas de entidades muestran todo lo que se sabe sobre un usuario o un host.

Los workbooks son paneles interactivos creados con Azure Monitor Workbooks, con gráficos, cuadrículas y parámetros basados en KQL. Las soluciones del Content hub incluyen muchas plantillas, como el análisis de inicios de sesión o las vistas generales de firewalls, que guardas y personalizas. Úsalos para visualización e informes, no para detección.

El hunting es la búsqueda proactiva de amenazas que las reglas no detectaron. Las consultas de hunting son consultas KQL, muchas integradas y asignadas a MITRE ATT&CK, que ejecutas a petición. Los resultados interesantes pueden guardarse como marcadores (bookmarks), que conservan las filas y las entidades asignadas; los marcadores pueden promoverse a incidentes, y la función Hunts organiza campañas basadas en hipótesis. Livestream ejecuta una consulta de forma continua para la supervisión en vivo, y los notebooks permiten análisis avanzados.

Las watchlists son tablas de búsqueda basadas en CSV que cargas en Sentinel, como usuarios VIP, IP de administración aprobadas, empleados dados de baja o activos críticos. Las consultas las referencian con _GetWatchlist('VIPUsers') para enriquecer o filtrar las detecciones. La inteligencia de amenazas incorpora indicadores de compromiso (direcciones IP, dominios, URL, hashes de archivos) mediante conectores como Microsoft Defender Threat Intelligence, servidores TAXII o la API de carga, y los guarda en tablas de inteligencia de amenazas, donde las reglas integradas los comparan con tus registros.

Términos clave

Automation rule (regla de automatización)
Una regla de Sentinel sin código que se ejecuta ante eventos de incidentes o alertas para asignar, etiquetar, cambiar el estado, agregar tareas o ejecutar playbooks.
Playbook
Un flujo de trabajo de Logic Apps desencadenado por Sentinel para realizar acciones de respuesta y enriquecimiento de varios pasos.
Workbook
Un panel interactivo basado en KQL para visualizar los datos de Sentinel.
Hunting query (consulta de hunting)
Una consulta KQL que se ejecuta de forma proactiva para buscar amenazas no detectadas por las reglas de análisis.
Watchlist
Una tabla de búsqueda basada en CSV en Sentinel que se referencia en las consultas con _GetWatchlist.
Ejemplo real

Las alertas sobre los VIP de finanzas deben atenderse primero. Cargas una watchlist VIPUsers, actualizas las reglas de análisis correspondientes para combinarla y elevar la gravedad, y creas una regla de automatización que asigna los incidentes etiquetados como VIP al analista sénior y ejecuta un playbook que publica en Teams y restablece las sesiones del usuario después de que un analista lo aprueba.

Consejo para el examen: Acciones simples de triaje (asignar, etiquetar, cerrar, fijar la gravedad) sin código: reglas de automatización. Acciones que involucran sistemas externos o aprobaciones: playbooks, normalmente lanzados por una regla de automatización. Paneles: workbooks. Búsquedas proactivas: hunting. Listas de búsqueda: watchlists. IoC: inteligencia de amenazas.

Comprueba lo que sabes

Quieres que cada incidente de una regla específica se asigne automáticamente a un analista. ¿Qué usas?

Una regla de automatización con una condición sobre el nombre de la regla de análisis y una acción de asignar propietario.

¿Qué permiso le permite a Sentinel ejecutar un playbook?

Microsoft Sentinel Automation Contributor concedido a Sentinel en el grupo de recursos del playbook.

¿Cómo haces referencia a una watchlist en KQL?

Con la función _GetWatchlist('alias').
