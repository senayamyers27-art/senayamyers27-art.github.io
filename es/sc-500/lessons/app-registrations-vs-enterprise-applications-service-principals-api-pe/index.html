Registros de aplicaciones vs aplicaciones empresariales (service principals), permisos de API, consentimiento de administrador y configuración de consentimiento de usuario

Cuando registras una aplicación en Microsoft Entra ID intervienen dos objetos. El objeto de aplicación (application object), que ves en App registrations, es la definición global de la aplicación: su nombre, el ID de aplicación (cliente), los URI de redirección, las credenciales (secretos de cliente o certificados), los permisos que solicita y los roles de aplicación o ámbitos (scopes) que expone. Vive en el tenant de origen de la aplicación. El service principal, que ves en Enterprise applications, es la instancia local de esa aplicación en un tenant específico. Es lo que realmente inicia sesión, recibe usuarios asignados, obtiene consentimiento y es objetivo de Conditional Access. Un objeto de aplicación puede tener service principals en muchos tenants (una aplicación multitenant), cada uno con su propio consentimiento y sus propias asignaciones.

Una regla práctica: App registrations es donde los desarrolladores definen cómo funciona la aplicación; Enterprise applications es donde los administradores controlan quién puede usarla y qué se le ha permitido hacer en su tenant. Las identidades administradas también aparecen como service principals en Enterprise applications, pero no tienen un registro de aplicación que tú administres.

Los permisos de API son de dos tipos. Los permisos delegados (delegated) permiten que la aplicación actúe en nombre de un usuario que inició sesión; el acceso efectivo es la intersección entre lo que se concedió a la aplicación y lo que el usuario puede hacer. Los permisos de aplicación (application, solo de aplicación) permiten que la aplicación actúe por sí misma sin usuario, para servicios en segundo plano, y se aplican a todo el tenant; por ejemplo, Mail.Read como permiso de aplicación lee todos los buzones. Los permisos de aplicación siempre requieren consentimiento de administrador.

El consentimiento es el acto de conceder esos permisos. El consentimiento de usuario significa que un usuario individual acepta que una aplicación acceda a sus propios datos con permisos delegados de bajo riesgo. El consentimiento de administrador lo otorga un administrador (como Global Administrator, Privileged Role Administrator, Cloud Application Administrator o Application Administrator, según el permiso) en nombre de toda la organización, y es obligatorio para los permisos de aplicación y los permisos delegados de alto privilegio.

Los ataques de concesión de consentimiento ilícito (illicit consent grant) engañan a los usuarios para que den consentimiento a una aplicación multitenant maliciosa que luego lee su correo o sus archivos sin necesitar su contraseña. Las defensas están en Enterprise applications > Consent and permissions: restringe el consentimiento de usuario a aplicaciones de publicadores verificados para permisos seleccionados de bajo impacto, o deshabilita por completo el consentimiento de usuario, y habilita el flujo de consentimiento de administrador (admin consent workflow) para que los usuarios puedan pedir aprobación a revisores designados en lugar de quedar bloqueados. Revisa periódicamente las aplicaciones empresariales y los permisos concedidos, y elimina las que no se usan o tienen permisos excesivos.

En cuanto a credenciales, prefiere certificados o credenciales de identidad federada (workload identity federation, por ejemplo desde GitHub Actions) en lugar de secretos de cliente, y prefiere identidades administradas cuando el código se ejecuta en Azure.

Términos clave

Application object (objeto de aplicación)
La definición global de la aplicación en su tenant de origen, administrada en App registrations.
Service principal (entidad de servicio)
La instancia local de una aplicación en un tenant, administrada en Enterprise applications, que recibe consentimiento y asignaciones.
Delegated permission (permiso delegado)
Un permiso que usa una aplicación en nombre de un usuario que inició sesión, limitado por el propio acceso de ese usuario.
Application permission (permiso de aplicación)
Un permiso solo de aplicación que se usa sin usuario que haya iniciado sesión; siempre necesita consentimiento de administrador.
Admin consent workflow (flujo de consentimiento de administrador)
Un proceso que permite a los usuarios solicitar aprobación de un administrador para aplicaciones a las que no pueden dar consentimiento.
Ejemplo real

Los usuarios siguen dando consentimiento a herramientas de calendario de terceros que solicitan Mail.ReadWrite. Configuras el consentimiento de usuario en 'Allow user consent for apps from verified publishers, for selected permissions', clasificas como permitidos solo permisos de bajo riesgo como User.Read y activas el flujo de consentimiento de administrador con el equipo de seguridad como revisores.

Consejo para el examen: Los permisos de aplicación necesitan consentimiento de administrador, sin excepción. Cuando la pregunta es 'dónde restrinjo quién puede iniciar sesión en esta aplicación o asignarla a usuarios', la respuesta es Enterprise applications (el service principal), no App registrations.

Comprueba lo que sabes

Un servicio en segundo plano sin usuario debe leer los perfiles de todos los usuarios. ¿Qué tipo de permiso y consentimiento necesita?

Un permiso de aplicación como User.Read.All, con consentimiento de administrador.

Una aplicación multitenant está registrada en el tenant A y se usa en el tenant B. ¿Dónde está el objeto de aplicación y dónde el service principal?

El objeto de aplicación está en el tenant A; el tenant B tiene su propio service principal (y normalmente el tenant A también tiene uno).

¿Cómo evitas que los usuarios den consentimiento a aplicaciones riesgosas sin bloquear las solicitudes legítimas?

Restringe o deshabilita el consentimiento de usuario y habilita el flujo de consentimiento de administrador para que las solicitudes vayan a los revisores.
