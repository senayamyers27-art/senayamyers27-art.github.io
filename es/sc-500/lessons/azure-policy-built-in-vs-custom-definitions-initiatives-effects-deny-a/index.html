Microsoft Certified: Cloud and AI Security Engineer Associate (replaces Azure Security Engineer Associate / AZ-500) SC-500

Azure Policy: definiciones integradas vs personalizadas, iniciativas, efectos (Deny, Audit, Modify, DeployIfNotExists), tareas de corrección, exenciones

Azure RBAC controla quién puede actuar; Azure Policy controla cómo pueden ser los recursos. Una definición de directiva (policy definition) es una regla escrita en JSON con una condición if (por ejemplo, una cuenta de almacenamiento donde supportsHttpsTrafficOnly es false) y un efecto then. Asignas la definición a un ámbito (grupo de administración, suscripción o grupo de recursos), excluyendo opcionalmente ámbitos secundarios, y Azure evalúa los recursos coincidentes al crearlos y actualizarlos, y periódicamente para verificar el cumplimiento.

Las definiciones integradas (built-in) las escribe y mantiene Microsoft y cubren cientos de requisitos comunes, como ubicaciones permitidas, etiquetas obligatorias, 'Storage accounts should restrict network access' o 'Key vaults should have purge protection enabled'. Las definiciones personalizadas (custom) son las que escribes cuando ninguna integrada encaja, usando alias (rutas de propiedades como Microsoft.Storage/storageAccounts/minimumTlsVersion). Las definiciones pueden tener parámetros, de modo que una misma definición puede reutilizarse con distintos valores permitidos.

Una iniciativa (initiative, o policy set definition) agrupa muchas definiciones para que se asignen y se supervisen juntas. El Microsoft cloud security benchmark de Defender for Cloud es en sí una gran iniciativa. Asignar una iniciativa te da un único porcentaje de cumplimiento y un solo lugar para administrar los parámetros.

Los efectos que debes conocer: Deny bloquea una solicitud de creación o actualización que infringe la regla. Audit permite la solicitud pero marca el recurso como no conforme y registra una advertencia. AuditIfNotExists señala recursos cuando falta un recurso relacionado (como una configuración de diagnóstico o una extensión). Modify agrega, cambia o quita propiedades o etiquetas del recurso durante la creación o actualización. DeployIfNotExists (DINE) despliega un recurso relacionado mediante una plantilla ARM cuando falta, como habilitar configuraciones de diagnóstico o instalar un agente. Append agrega campos, y Disabled desactiva la regla. Deny previene; Audit informa; Modify y DeployIfNotExists corrigen.

Modify y DeployIfNotExists actúan automáticamente solo sobre recursos nuevos o actualizados. Los recursos no conformes que ya existen necesitan una tarea de corrección (remediation task), que creas desde la página de cumplimiento de la asignación. Como estos efectos modifican recursos, la asignación necesita una identidad administrada (asignada por el sistema o por el usuario) con los roles indicados en la definición, como Contributor o Monitoring Contributor, en el ámbito de la asignación. Olvidar esa identidad es un error clásico.

Las exenciones (exemptions) excluyen un recurso o ámbito específico de una asignación sin editar la asignación. Cada exención tiene una categoría, Waiver (riesgo aceptado) o Mitigated (el objetivo se cumple de otra forma), una fecha de caducidad opcional y una descripción, lo que deja un registro para los auditores. Las exclusiones (notScopes) en la asignación son una herramienta más burda, sin categoría ni caducidad.

En un laboratorio, asigna la directiva integrada 'Allowed locations' con Deny a un grupo de recursos, intenta crear un recurso en otra región y lee el error RequestDisallowedByPolicy; luego asigna una definición DeployIfNotExists y ejecuta una tarea de corrección.

Términos clave

Policy definition (definición de directiva)
Una regla JSON con una condición y un efecto que describe las configuraciones de recursos permitidas.
Initiative (iniciativa)
Un grupo de definiciones de directiva que se asignan y se reportan juntas, también llamado policy set.
DeployIfNotExists
Un efecto que despliega un recurso o configuración relacionados que faltan usando una plantilla.
Remediation task (tarea de corrección)
Un trabajo que aplica Modify o DeployIfNotExists a recursos que ya existían antes de la asignación.
Exemption (exención)
Un registro que excluye un recurso o ámbito de una asignación, categorizado como Waiver o Mitigated, opcionalmente con límite de tiempo.
Ejemplo real

Asignas una directiva DeployIfNotExists que configura los ajustes de diagnóstico de todos los key vaults para enviar registros a un área de trabajo central. Los vaults nuevos reciben la configuración automáticamente, pero treinta vaults existentes aparecen como no conformes, así que creas una tarea de corrección que usa la identidad administrada de la asignación para corregirlos.

Consejo para el examen: Deny lo detiene, Audit lo informa, Modify y DeployIfNotExists lo corrigen, y los recursos existentes necesitan una tarea de corrección más una identidad administrada. Para una excepción temporal y documentada, elige una exención con fecha de caducidad.

Comprueba lo que sabes

¿Qué efecto agregaría una etiqueta CostCenter faltante a los recursos al crearlos?

Modify (Append también puede agregar campos, pero Modify es el efecto recomendado para etiquetas).

Asignas una directiva DeployIfNotExists pero los recursos existentes siguen sin cumplir. ¿Qué haces?

Crear una tarea de corrección, asegurándote de que la identidad administrada de la asignación tenga los roles necesarios.

¿Cuál es la diferencia entre una iniciativa y una definición individual?

Una iniciativa agrupa muchas definiciones en una sola asignación y una vista de cumplimiento con parámetros compartidos.
