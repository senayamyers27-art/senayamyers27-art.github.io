Cifrado de Storage: claves administradas por Microsoft vs administradas por el cliente, cifrado de infraestructura, almacenamiento de blobs inmutable

Todos los datos escritos en Azure Storage se cifran automáticamente en reposo con AES de 256 bits mediante Azure Storage encryption (también llamado storage service encryption). No puedes desactivarlo y es transparente para las aplicaciones. La cuestión es quién controla las claves.

Con las claves administradas por Microsoft (Microsoft-managed keys), la opción predeterminada, Microsoft genera, almacena y rota las claves. No se requiere configuración. Con las claves administradas por el cliente (customer-managed keys, CMK), tú proporcionas una clave de cifrado de claves guardada en Azure Key Vault o en Key Vault Managed HSM. Azure Storage usa cifrado de sobre (envelope encryption): los datos se cifran con una clave de cifrado de datos, y esa clave de datos se envuelve (se cifra) con tu clave. Tú controlas el ciclo de vida de la clave: puedes rotarla, auditar su uso y, sobre todo, revocar el acceso a ella, lo que vuelve ilegibles los datos. Las organizaciones eligen CMK por requisitos normativos o por la capacidad de cortar el acceso criptográficamente.

Configurar CMK requiere: un key vault con soft delete y purge protection habilitados; una clave RSA o RSA-HSM; una identidad administrada para la cuenta de almacenamiento (asignada por el sistema, o asignada por el usuario, que es obligatoria al configurar CMK durante la creación de la cuenta); y permiso para que esa identidad envuelva y desenvuelva con la clave, por ejemplo el rol Key Vault Crypto Service Encryption User. Puedes apuntar a una versión específica de la clave u omitir la versión para que Storage use automáticamente la más reciente después de rotarla. Las claves proporcionadas por el cliente (customer-provided keys) son una función distinta, en la que el cliente entrega una clave con cada solicitud de Blob; y los ámbitos de cifrado (encryption scopes) permiten usar claves distintas para distintos contenedores o blobs dentro de una misma cuenta.

El cifrado de infraestructura (infrastructure encryption) agrega una segunda capa de cifrado a nivel de infraestructura, con un algoritmo de cifrado distinto y una clave distinta, de modo que los datos se cifran dos veces. Debe habilitarse al crear la cuenta de almacenamiento y no puede agregarse después. Es para clientes cuyas normas de cumplimiento exigen doble cifrado.

El almacenamiento de blobs inmutable guarda los datos en un estado WORM (write once, read many: se escribe una vez y se lee muchas) para que no puedan modificarse ni eliminarse durante un período, ni siquiera por los administradores de la cuenta. Hay dos tipos de directivas. Las directivas de retención basadas en tiempo (time-based retention) mantienen los blobs inmutables durante un intervalo definido; mientras están desbloqueadas pueden cambiarse, pero una vez bloqueadas el intervalo solo puede ampliarse, no acortarse ni eliminarse, lo que cumple normativas como SEC 17a-4(f). Las retenciones legales (legal holds) mantienen los datos inmutables hasta que se quita la retención (identificada con una etiqueta), sin duración fija, para litigios o investigaciones. Las directivas pueden aplicarse en el ámbito del contenedor o, con inmutabilidad a nivel de versión, en versiones individuales de blobs. La inmutabilidad también es una defensa sólida contra el ransomware que intenta cifrar o eliminar las copias de seguridad.

No confundas cifrado con inmutabilidad: CMK protege la confidencialidad y te da control sobre las claves; el almacenamiento inmutable protege la integridad y la disponibilidad frente a la eliminación o la manipulación.

Términos clave

Customer-managed key (clave administrada por el cliente)
Una clave en Key Vault o Managed HSM que envuelve las claves de cifrado de datos de la cuenta de almacenamiento bajo tu control.
Infrastructure encryption (cifrado de infraestructura)
Una segunda capa de cifrado independiente que solo se habilita al crear la cuenta de almacenamiento.
Time-based retention policy (directiva de retención basada en tiempo)
Una directiva de inmutabilidad que impide eliminar y modificar blobs durante un intervalo definido; una vez bloqueada, solo puede ampliarse.
Legal hold (retención legal)
Una configuración de inmutabilidad que conserva los datos indefinidamente hasta que se quita la etiqueta de retención.
Ejemplo real

Una firma financiera debe conservar sin alteraciones los registros de operaciones durante siete años y controlar sus propias claves. Crea una cuenta de almacenamiento con cifrado de infraestructura, configura CMK desde un vault con purge protection usando una identidad asignada por el usuario, y aplica una directiva de retención basada en tiempo bloqueada de siete años al contenedor de registros.

Consejo para el examen: El cifrado de infraestructura solo puede habilitarse al crear la cuenta. Una directiva de retención basada en tiempo bloqueada no puede acortarse ni eliminarse, solo ampliarse. CMK necesita soft delete más purge protection en el vault y una identidad administrada con derechos de wrap/unwrap.

Comprueba lo que sabes

¿Qué les pasa a los datos de una cuenta de almacenamiento cifrada con CMK si se deshabilita la clave?

Los datos quedan inaccesibles porque Storage ya no puede desenvolver las claves de cifrado de datos.

¿Qué opción de inmutabilidad encaja con evidencia conservada para una demanda sin fecha de fin?

Una retención legal, ya que no tiene un final fijo y dura hasta que se quita.

¿Puedes habilitar el cifrado de infraestructura en una cuenta existente?

No, debe elegirse al crear la cuenta.
