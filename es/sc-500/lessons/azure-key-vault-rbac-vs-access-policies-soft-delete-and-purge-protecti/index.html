Azure Key Vault: RBAC vs directivas de acceso, eliminación temporal y protección contra purga, rotación de claves, restricciones de red, Defender for Key Vault

Azure Key Vault es un servicio administrado para almacenar secretos (contraseñas, cadenas de conexión), claves criptográficas (claves RSA y EC usadas para cifrado y firma) y certificados. Las aplicaciones obtienen lo que necesitan en tiempo de ejecución usando su identidad de Entra, de modo que los secretos quedan fuera del código. El nivel Premium añade claves protegidas por módulos de seguridad de hardware (HSM); Azure Key Vault Managed HSM es una oferta aparte, de un solo tenant, para requisitos más estrictos.

Key Vault tiene dos planos. El plano de administración (crear el vault, cambiar su configuración de red) siempre se controla con Azure RBAC, mediante roles como Key Vault Contributor. El plano de datos (leer un secreto, usar una clave) puede autorizarse de una de dos formas, elegida por vault. El modelo heredado de directivas de acceso del vault (vault access policy) concede a una entidad conjuntos de permisos (Get, List, Set, Delete, etc.) para claves, secretos y certificados en todo el vault. El modelo Azure RBAC usa roles de datos como Key Vault Administrator, Key Vault Secrets User, Key Vault Secrets Officer, Key Vault Crypto User y Key Vault Certificates Officer, y puede limitarse hasta un secreto individual. Microsoft recomienda el modelo RBAC: es coherente con el resto de Azure, funciona con PIM y corrige una debilidad conocida de las directivas de acceso, en la que cualquiera con Contributor en el vault podía concederse acceso a los datos editando la directiva.

La eliminación temporal (soft delete) mantiene los vaults y objetos eliminados en un estado recuperable durante un período de retención (de 7 a 90 días, 90 por defecto) y ahora siempre está activada en los vaults nuevos. Durante ese tiempo puedes recuperarlos o purgarlos. La protección contra purga (purge protection), que habilitas por separado y no se puede desactivar una vez habilitada, bloquea la purga hasta que termina el período de retención, incluso para los administradores. Esto protege contra un insider malicioso o un actor de ransomware que elimina y purga claves para que los datos cifrados sean irrecuperables. Los servicios que usan claves administradas por el cliente, como Storage o Azure SQL TDE, requieren tanto soft delete como purge protection en el vault.

Las claves deben rotarse con regularidad. Key Vault admite una directiva de rotación de claves (key rotation policy) que crea automáticamente una nueva versión de la clave según un calendario (por ejemplo, cada año) y puede enviar un evento de próxima caducidad a través de Event Grid. Los servicios configurados para usar la versión más reciente de la clave toman la nueva automáticamente. Los secretos pueden tener fechas de caducidad, y los eventos de Event Grid de 'próxima caducidad' pueden disparar una Function o una Logic App para rotarlos. Los certificados pueden renovarse automáticamente mediante autoridades de certificación integradas.

Las restricciones de red reducen la exposición. En Networking puedes deshabilitar por completo el acceso público y usar un private endpoint, o permitir redes virtuales seleccionadas (mediante service endpoints) e intervalos de IP. La opción 'Allow trusted Microsoft services to bypass this firewall' permite que servicios como Azure Backup o Storage (para CMK) lleguen al vault. Las reglas de firewall se aplican al plano de datos.

Microsoft Defender for Key Vault, un plan de Defender for Cloud, analiza el acceso al vault y genera alertas ante comportamientos inusuales, como el acceso desde una dirección IP sospechosa o un nodo de salida de Tor, una aplicación o usuario inusual que accede a muchos secretos, o volúmenes anómalos de operaciones. Combínalo con configuraciones de diagnóstico que envíen los registros AuditEvent a un área de trabajo de Log Analytics para investigar.

Términos clave

Access policy model (modelo de directivas de acceso)
La autorización heredada del plano de datos de Key Vault que concede conjuntos de permisos a nivel de todo el vault para cada entidad.
Key Vault RBAC
Autorización del plano de datos mediante roles de Azure como Key Vault Secrets User, que puede limitarse a un solo secreto.
Soft delete (eliminación temporal)
Mantiene recuperables los vaults y objetos eliminados durante un período de retención de 7 a 90 días.
Purge protection (protección contra purga)
Impide la eliminación permanente hasta que pasa el período de retención; no se puede deshabilitar una vez habilitada.
Key rotation policy (directiva de rotación de claves)
Un calendario que crea automáticamente nuevas versiones de la clave y puede notificar antes de la caducidad.
Ejemplo real

Antes de habilitar claves administradas por el cliente para una cuenta de almacenamiento, habilitas purge protection en el vault, cambias el vault al modelo de permisos Azure RBAC, concedes a la identidad administrada de la cuenta de almacenamiento el rol Key Vault Crypto Service Encryption User sobre la clave, estableces una directiva de rotación anual y restringes el acceso de red a un private endpoint con los servicios de confianza permitidos.

Consejo para el examen: Contributor en un vault no concede acceso a los secretos en el modelo RBAC, pero en el modelo de directivas de acceso un Contributor puede agregarse una directiva a sí mismo. Si los datos deben estar a salvo de una eliminación irrecuperable, la respuesta es purge protection, no solo soft delete.

Comprueba lo que sabes

¿Por qué Microsoft recomienda el modelo de permisos RBAC en lugar de las directivas de acceso?

Es coherente con Azure RBAC, admite ámbito por objeto y PIM, e impide que los Contributors se concedan acceso a los datos editando las directivas.

¿Qué añade purge protection además de soft delete?

Impide que cualquiera purgue de forma permanente los elementos eliminados hasta que termine el período de retención, y no se puede desactivar.

¿Qué configuración de Key Vault permite que Azure Backup llegue a un vault que deniega el acceso público?

La excepción del firewall que permite que los servicios de confianza de Microsoft omitan el firewall.
