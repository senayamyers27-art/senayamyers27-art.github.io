Identidades administradas: asignadas por el sistema vs asignadas por el usuario, y reemplazo de secretos almacenados por acceso basado en tokens

Las aplicaciones a menudo necesitan llamar a otros servicios: un App Service que lee de Key Vault, una VM que escribe en Storage, una Function que consulta Azure SQL. La forma antigua era guardar una cadena de conexión, una clave o un secreto de cliente en la configuración, lo cual puede filtrarse, caducar u olvidarse en un repositorio de código. Una identidad administrada (managed identity) resuelve esto dándole al recurso de Azure su propia identidad en Microsoft Entra ID, cuyas credenciales Azure crea, almacena y rota por ti. Tu código nunca ve un secreto.

Una identidad administrada asignada por el sistema (system-assigned) se habilita en un solo recurso (por ejemplo, en la hoja Identity de una VM o de una aplicación web) y está ligada al ciclo de vida de ese recurso. Se crea junto con el recurso, solo ese recurso puede usarla y se elimina cuando se elimina el recurso. Una identidad administrada asignada por el usuario (user-assigned) es un recurso de Azure independiente (Microsoft.ManagedIdentity/userAssignedIdentities) que creas primero y luego asocias a uno o varios recursos. Sobrevive cuando esos recursos se eliminan.

Elige la asignada por el sistema cuando un solo recurso necesita su propia identidad y quieres que la limpieza sea automática. Elige la asignada por el usuario cuando varios recursos necesitan los mismos permisos (por ejemplo, un grupo de VMs en un scale set o muchas function apps), cuando quieres crear identidades por adelantado y conceder acceso antes de desplegar los recursos, o cuando los recursos se recrean con frecuencia y no quieres rehacer las asignaciones de roles cada vez. Un recurso puede tener al mismo tiempo una identidad asignada por el sistema y varias asignadas por el usuario.

Por dentro, una identidad administrada es un service principal especial. El código que se ejecuta en el recurso solicita un token de acceso a un endpoint local: el Azure Instance Metadata Service (IMDS) en la dirección link-local 169.254.169.254 en las VMs, o un endpoint de identidad proporcionado mediante variables de entorno en App Service y Functions. Luego el token se presenta al servicio de destino, que debe aceptar la autenticación de Entra. En el código, DefaultAzureCredential o ManagedIdentityCredential de la biblioteca Azure Identity se encargan de todo esto.

Obtener un token es solo la mitad del trabajo; la identidad también necesita permiso. Le concedes un rol de Azure RBAC en el destino, como Key Vault Secrets User en un vault o Storage Blob Data Contributor en un contenedor, o creas para ella un usuario de base de datos contenido (contained database user) en Azure SQL. Aplica el mínimo privilegio y el ámbito más reducido posible.

Reemplazar secretos normalmente sigue estos pasos: habilitar la identidad, concederle el rol de plano de datos adecuado, cambiar la aplicación para que use credenciales basadas en tokens, eliminar la clave o cadena de conexión almacenada y, por último, rotar o deshabilitar la clave antigua (por ejemplo, deshabilitando el acceso con Shared Key en la cuenta de almacenamiento) para que el riesgo de un secreto filtrado desaparezca de verdad.

Términos clave

Managed identity (identidad administrada)
Una identidad de Entra para un recurso de Azure cuyas credenciales Azure administra y rota automáticamente.
System-assigned identity (identidad asignada por el sistema)
Una identidad administrada creada en un recurso y ligada a su ciclo de vida.
User-assigned identity (identidad asignada por el usuario)
Un recurso de identidad administrada independiente que puede asociarse a muchos recursos y persiste por separado.
IMDS
El Azure Instance Metadata Service en 169.254.169.254 que las VMs usan para solicitar tokens de identidad administrada.
Ejemplo real

Una aplicación web guardaba una clave de cuenta de almacenamiento en su configuración (app settings). Habilitas la identidad asignada por el sistema de la aplicación web, le das Storage Blob Data Reader en el contenedor, actualizas el código para usar DefaultAzureCredential, eliminas el app setting y luego rotas ambas claves de almacenamiento para que la antigua deje de funcionar.

Consejo para el examen: Si varios recursos deben compartir una identidad, o la identidad debe sobrevivir a la eliminación del recurso, elige la asignada por el usuario. Si el escenario dice 'ninguna credencial almacenada en el código o la configuración', la respuesta es una identidad administrada más un rol de RBAC en el destino.

Comprueba lo que sabes

¿Qué le pasa a una identidad asignada por el sistema cuando se elimina su VM?

Se elimina junto con la VM, y sus asignaciones de roles dejan de poder usarse.

Una VM tiene una identidad administrada pero recibe errores 403 al leer secretos de Key Vault. ¿Qué falta?

Autorización en el vault, como el rol Key Vault Secrets User (modelo RBAC) o una directiva de acceso que conceda Get sobre los secretos.

¿Por qué podrías crear por adelantado una identidad asignada por el usuario?

Para poder concederle roles antes de que existan los recursos y reutilizarla en muchos recursos o nuevos despliegues.
