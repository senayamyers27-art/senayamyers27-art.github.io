Seguridad de AKS: integración con Entra ID, Azure RBAC para Kubernetes, clústeres privados, directivas de red, Defender for Containers, Azure Policy para AKS

Azure Kubernetes Service (AKS) ejecuta un plano de control de Kubernetes administrado mientras tú administras los grupos de nodos y las cargas de trabajo. La seguridad abarca quién puede usar la API de Kubernetes, cómo se expone la API, cómo se comunican los pods entre sí y cómo detectas amenazas y aplicas estándares.

De forma predeterminada, Kubernetes tiene sus propias cuentas y certificados locales, que son difíciles de auditar y revocar. La integración de Microsoft Entra administrada por AKS permite a los usuarios autenticarse en el clúster con sus identidades de Entra: az aks get-credentials genera un kubeconfig que desencadena un inicio de sesión de Entra mediante kubelogin, de modo que se aplican MFA y Conditional Access. También debes deshabilitar las cuentas locales (--disable-local-accounts) para que la credencial de administrador estática no pueda usarse como puerta trasera.

La autorización tiene entonces dos opciones. Con Kubernetes RBAC, creas Roles y ClusterRoles dentro del clúster y los vinculas a usuarios o grupos de Entra con RoleBindings. Con Azure RBAC para la autorización de Kubernetes, asignas roles de Azure como Azure Kubernetes Service RBAC Reader, Writer, Admin y Cluster Admin en el ámbito del clúster o del espacio de nombres (namespace), administrados en el portal como cualquier otro rol de Azure. Por separado, roles de Azure como Azure Kubernetes Service Cluster User Role controlan quién puede descargar el kubeconfig en primer lugar. Las cargas de trabajo deben usar Microsoft Entra Workload ID (federando una cuenta de servicio de Kubernetes con una identidad administrada) para llegar a los servicios de Azure sin secretos.

Un clúster privado (private cluster) da al servidor de API un endpoint privado en tu red virtual, de modo que la API de Kubernetes no es accesible desde internet; lo administras desde dentro de la red, por VPN o ExpressRoute, o mediante funciones como az aks command invoke. Si se requiere un servidor de API público, restríngelo con intervalos de IP autorizados. Controla también la salida de los nodos, por ejemplo enrutándola a través de Azure Firewall con las reglas FQDN requeridas por AKS.

De forma predeterminada, todos los pods de un clúster pueden comunicarse entre sí. Las directivas de red (network policies) son recursos de Kubernetes que restringen el tráfico entre pods por etiquetas, espacios de nombres y puertos, implementando la microsegmentación. Requieren un motor de directivas de red, que normalmente se elige al crear el clúster (algunos motores también pueden habilitarse en un clúster existente): Azure Network Policy Manager, Calico o Cilium (Azure CNI powered by Cilium).

Microsoft Defender for Containers protege clústeres en AKS y, con conectores o Arc, en EKS, GKE y otros Kubernetes. Proporciona detección de amenazas en tiempo de ejecución mediante el sensor de Defender en los nodos y análisis de los registros de auditoría del plano de control (alertas por cosas como la creación de contenedores privilegiados, paneles expuestos o minería de criptomonedas), evaluación de vulnerabilidades de imágenes en registros y de contenedores en ejecución usando Microsoft Defender Vulnerability Management, descubrimiento sin agente y hallazgos de postura, y recomendaciones de postura de seguridad de Kubernetes.

Azure Policy para AKS usa el complemento de Azure Policy (Azure Policy add-on), que ejecuta OPA Gatekeeper en el clúster para auditar o denegar los recursos de Kubernetes que infringen las directivas. Las iniciativas integradas incluyen los estándares de seguridad de pods baseline y restricted, el bloqueo de contenedores privilegiados, la exigencia de imágenes de registros permitidos y la aplicación de límites de recursos.

Términos clave

AKS-managed Entra integration (integración de Entra administrada por AKS)
Configuración en la que los usuarios inician sesión en la API de Kubernetes con identidades de Entra en lugar de certificados locales.
Azure RBAC for Kubernetes (Azure RBAC para Kubernetes)
Uso de asignaciones de roles de Azure, en el ámbito del clúster o del espacio de nombres, para autorizar acciones de la API de Kubernetes.
Private cluster (clúster privado)
Un clúster de AKS cuyo servidor de API solo es accesible mediante una IP privada en la red virtual.
Network policy (directiva de red)
Un recurso de Kubernetes que restringe el tráfico entre pods según etiquetas, espacios de nombres y puertos.
Azure Policy add-on (complemento de Azure Policy)
Un complemento de AKS que usa OPA Gatekeeper para auditar o denegar recursos de Kubernetes no conformes.
Ejemplo real

Un equipo de pagos refuerza su clúster de AKS: habilita la integración con Entra con Azure RBAC y deshabilita las cuentas locales, lo reconstruye como clúster privado con Azure CNI y Calico, agrega directivas de red para que solo el espacio de nombres api pueda llegar al espacio de nombres db, habilita Defender for Containers y asigna la iniciativa de seguridad de pods restricted con el complemento de Azure Policy.

Consejo para el examen: Las directivas de red necesitan un motor de directivas de red habilitado en el clúster, que normalmente se elige al crearlo. Deshabilitar las cuentas locales es lo que obliga a que todo el acceso pase por Entra. La aplicación con Gatekeeper dentro del clúster es Azure Policy para AKS; la detección de amenazas y el análisis de imágenes es Defender for Containers.

Comprueba lo que sabes

¿Cómo impides que el certificado de administrador del clúster eluda la autenticación de Entra?

Deshabilitando las cuentas locales en el clúster de AKS.

¿Qué función impide que se creen pods privilegiados?

Azure Policy para AKS (el complemento basado en Gatekeeper) con la iniciativa de seguridad de pods baseline o restricted en modo Deny.

¿Qué hace que el servidor de API de Kubernetes sea inaccesible desde internet?

Desplegar AKS como clúster privado.
