Autorización de Storage: Entra ID con RBAC del plano de datos, claves de cuenta, deshabilitar Shared Key, rotación de claves

Toda solicitud para leer o escribir datos en Azure Storage (blobs, archivos, colas, tablas) debe estar autorizada. Hay varias formas, y el examen quiere que sepas ordenarlas. La más sólida es la autorización con Microsoft Entra ID: quien llama presenta un token OAuth 2.0 de un usuario, grupo, service principal o identidad administrada, y Azure comprueba sus roles de RBAC del plano de datos. No existe un secreto compartido que pueda filtrarse, el acceso está ligado a la identidad y puede revocarse, y cada solicitud es atribuible en los registros.

Los roles del plano de datos son distintos de los roles de administración. Owner o Contributor en una cuenta de almacenamiento te permiten administrarla, pero por sí solos no conceden acceso a los datos basado en Entra. Para blobs usas Storage Blob Data Reader, Storage Blob Data Contributor o Storage Blob Data Owner (que además puede definir ACL POSIX en Data Lake Storage Gen2); para colas, Storage Queue Data Reader y Contributor; para tablas, Storage Table Data Reader y Contributor; y para Azure Files por REST o SMB con autenticación basada en identidad, los roles Storage File Data. Asígnalos en el ámbito más reducido que funcione, hasta un contenedor individual.

La autorización Shared Key usa una de las dos claves de acceso de la cuenta de 512 bits. Una clave concede acceso total a todos los datos de la cuenta, nunca caduca por sí sola y no está ligada a ninguna identidad, así que los registros no pueden decirte quién la usó. Tener el rol que incluye listKeys (como Contributor o Storage Account Key Operator Service Role) significa en la práctica acceso total a los datos, y por eso Contributor es más poderoso de lo que parece a primera vista. Las firmas de acceso compartido (que se tratan a continuación) también se derivan de las claves, salvo la user delegation SAS.

Puedes establecer Allow storage account key access en Disabled en la cuenta (la propiedad allowSharedKeyAccess). A partir de ahí, se rechazan las solicitudes firmadas con claves de cuenta y los tokens SAS de servicio o de cuenta firmados con ellas; solo funcionan Entra ID y la user delegation SAS. Antes de deshabilitarla, revisa las métricas o registros de almacenamiento en busca de solicitudes que usen Shared Key para no romper aplicaciones heredadas, y usa Azure Policy para auditar o denegar las cuentas donde siga habilitada. Además, establece en el portal la autorización de Entra como predeterminada para que los usuarios exploren los datos con su identidad.

Si las claves deben mantenerse, rótalas. Hay dos claves para que puedas rotar sin tiempo de inactividad: pasa las aplicaciones a key2, regenera key1, vuelve a pasarlas o déjalas, y luego regenera key2 más adelante. Guardar las claves en Key Vault y configurar una directiva de caducidad de claves (key expiration policy) en la cuenta, que avisa y marca las claves más antiguas que el intervalo definido, ayuda a mantener la rotación al día. Regenerar una clave invalida de inmediato toda SAS que se haya firmado con ella.

El acceso de lectura anónimo (público) a los contenedores es una configuración aparte, Allow Blob anonymous access, que debe deshabilitarse a menos que realmente hospedes contenido público.

Términos clave

Data-plane RBAC (RBAC del plano de datos)
Roles de Azure como Storage Blob Data Reader que autorizan el acceso a los datos dentro de una cuenta de almacenamiento.
Account access key (clave de acceso de la cuenta)
Una de las dos claves que conceden acceso total a todos los datos de una cuenta de almacenamiento mediante autorización Shared Key.
allowSharedKeyAccess
La propiedad de la cuenta de almacenamiento que, cuando es false, rechaza las solicitudes autorizadas con claves de cuenta o con SAS firmadas con claves.
Key expiration policy (directiva de caducidad de claves)
Una configuración de la cuenta de almacenamiento que marca las claves de cuenta que no se han rotado dentro de un número de días definido.
Ejemplo real

Una auditoría muestra que los desarrolladores usan la clave de la cuenta de almacenamiento incrustada en un script. Concedes al grupo de desarrolladores Storage Blob Data Contributor en su contenedor, cambias el script para usar az storage blob upload --auth-mode login, confirmas en las métricas que las solicitudes con Shared Key se detienen, y luego deshabilitas el acceso con clave de la cuenta de almacenamiento y regeneras ambas claves.

Consejo para el examen: Owner o Contributor por sí solos no dan acceso a los datos con Entra, pero sí permiten listar las claves, lo que da acceso total a los datos. La respuesta más segura para Storage casi siempre es Entra ID con un rol de datos y Shared Key deshabilitado.

Comprueba lo que sabes

Un usuario con Reader en una cuenta de almacenamiento no puede leer blobs con autenticación de Entra. ¿Qué rol lo corrige con el mínimo privilegio?

Storage Blob Data Reader en el ámbito del contenedor o de la cuenta.

¿Qué le pasa a una SAS de servicio después de deshabilitar el acceso con Shared Key?

Deja de funcionar, porque las SAS de servicio y de cuenta se firman con claves de cuenta; solo la user delegation SAS sigue siendo válida.

¿Por qué hay dos claves de cuenta?

Para que puedas pasar los clientes a una clave mientras regeneras la otra, rotando sin tiempo de inactividad.
