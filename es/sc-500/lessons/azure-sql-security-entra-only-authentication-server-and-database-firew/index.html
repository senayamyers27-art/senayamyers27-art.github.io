Microsoft Certified: Cloud and AI Security Engineer Associate (replaces Azure Security Engineer Associate / AZ-500) SC-500

Seguridad de Azure SQL: autenticación solo con Entra, reglas de firewall de servidor y de base de datos, TDE con CMK, Always Encrypted, enmascaramiento dinámico de datos, auditoría, Defender for SQL

Azure SQL Database y Azure SQL Managed Instance ofrecen protección en capas: quién puede llegar al servidor, quién puede autenticarse, qué puede ver y cómo se supervisa la actividad. Saber qué función aborda cada amenaza es el núcleo de este tema.

Para la autenticación, puedes usar autenticación SQL (usuario y contraseña almacenados en la base de datos), autenticación de Microsoft Entra o ambas. Definir un administrador de Microsoft Entra para el servidor y luego habilitar la autenticación solo con Microsoft Entra (Microsoft Entra-only authentication) deshabilita por completo los inicios de sesión SQL, incluido el inicio de sesión del administrador del servidor, de modo que todo el acceso usa identidades de Entra con MFA, Conditional Access e identidades administradas. Los usuarios de base de datos para entidades de Entra se crean con CREATE USER [name] FROM EXTERNAL PROVIDER. Azure Policy puede auditar o exigir la autenticación solo con Entra.

El acceso de red se controla con reglas de firewall. Las reglas de firewall de IP a nivel de servidor se aplican a todas las bases de datos del servidor lógico y se administran en el portal o con sp_set_firewall_rule en master. Las reglas de firewall de IP a nivel de base de datos, definidas con sp_set_database_firewall_rule, se aplican solo a una base de datos y viajan con ella, lo cual es útil para la replicación geográfica. La configuración 'Allow Azure services and resources to access this server' permite cualquier IP hospedada en Azure, incluidas las de otros clientes, así que deshabilítala cuando sea posible. Mejores opciones son las reglas de red virtual mediante service endpoints, los private endpoints con el acceso de red público denegado, y una versión mínima de TLS.

El cifrado de datos transparente (transparent data encryption, TDE) cifra en reposo los archivos de base de datos, las copias de seguridad y los registros, y está activado de forma predeterminada con una clave administrada por el servicio. Con TDE con claves administradas por el cliente (bring your own key), el protector de TDE es una clave asimétrica en Key Vault o Managed HSM, a la que accede la identidad administrada del servidor; revocarla deja inaccesibles las bases de datos. TDE protege el medio de almacenamiento, no los datos frente a un usuario que puede consultar la base de datos.

Always Encrypted protege columnas confidenciales, como números de identificación nacional, frente a todos los que no tienen la clave maestra de columna, incluidos los administradores de bases de datos y los operadores de la nube. El cifrado y el descifrado ocurren en el controlador del cliente; el motor de base de datos solo ve texto cifrado. Una clave de cifrado de columna cifra los datos y, a su vez, está protegida por una clave maestra de columna almacenada fuera de la base de datos, a menudo en Key Vault. El cifrado determinista permite búsquedas por igualdad; el cifrado aleatorio es más fuerte pero no permite búsquedas. Always Encrypted con enclaves seguros agrega consultas más completas.

El enmascaramiento dinámico de datos (dynamic data masking) oculta partes de los valores en los resultados de las consultas para usuarios sin privilegios, por ejemplo mostrando XXXX-XXXX-XXXX-1234 para un número de tarjeta, con funciones de enmascaramiento como default, email, random y partial. Es una comodidad para limitar la exposición, no cifrado; los datos no cambian, y los usuarios con el permiso UNMASK los ven sin ocultar.

La auditoría escribe los eventos de la base de datos en una cuenta de almacenamiento, un área de trabajo de Log Analytics o Event Hubs, a nivel de servidor o de base de datos. Microsoft Defender for SQL agrega la evaluación de vulnerabilidades (analiza configuraciones incorrectas con una línea base) y Advanced Threat Protection, que alerta sobre inyección SQL, inicios de sesión sospechosos, intentos de fuerza bruta y exportación anómala de datos.

Términos clave

Microsoft Entra-only authentication (autenticación solo con Microsoft Entra)
Una configuración del servidor que deshabilita la autenticación SQL para que solo las identidades de Entra puedan iniciar sesión.
TDE
Transparent data encryption (cifrado de datos transparente), que cifra en reposo los archivos de base de datos, los registros y las copias de seguridad.
Always Encrypted
Cifrado de columnas del lado del cliente que mantiene el texto sin cifrar oculto al motor de base de datos y a sus administradores.
Dynamic data masking (enmascaramiento dinámico de datos)
Una directiva que ofusca los valores de columna en los resultados de las consultas para usuarios sin el permiso UNMASK.
Database-level firewall rule (regla de firewall a nivel de base de datos)
Una regla de IP almacenada en una base de datos que se aplica solo a esa base de datos.
Ejemplo real

Una aplicación de salud debe mantener los ID de pacientes ilegibles para los DBA, impedir los inicios de sesión con contraseña y alertar sobre intentos de inyección. Habilitas la autenticación solo con Entra, cifras la columna PatientID con Always Encrypted usando una clave maestra de columna en Key Vault, enmascaras los números de teléfono para el personal de soporte con dynamic data masking y habilitas Defender for SQL.

Consejo para el examen: Ocultar datos a los DBA: Always Encrypted. Ocultar datos en los resultados a usuarios con pocos privilegios: dynamic data masking. Proteger discos y copias de seguridad: TDE. Controlar tú mismo la clave: TDE con CMK. Detener los inicios de sesión con contraseña: autenticación solo con Entra.

Comprueba lo que sabes

¿Qué función impide que un administrador de base de datos vea números de tarjetas de crédito en texto sin cifrar?

Always Encrypted, porque solo los clientes con la clave maestra de columna pueden descifrar.

¿Cuál es la diferencia de ámbito entre las reglas de firewall a nivel de servidor y a nivel de base de datos?

Las reglas a nivel de servidor se aplican a todas las bases de datos del servidor lógico; las de nivel de base de datos se aplican a una base de datos y se mueven con ella.

¿Protege dynamic data masking frente a un usuario con acceso directo a los archivos de datos?

No, solo enmascara los resultados de las consultas; los datos almacenados no cambian y no quedan cifrados por esta función.
