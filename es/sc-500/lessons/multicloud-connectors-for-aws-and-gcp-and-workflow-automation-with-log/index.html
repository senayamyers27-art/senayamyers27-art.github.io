Conectores multinube para AWS y GCP, y automatización de flujos de trabajo con Logic Apps

Muchas organizaciones ejecutan cargas de trabajo en Amazon Web Services (AWS) y Google Cloud Platform (GCP) además de Azure. Defender for Cloud puede proteger las tres desde un solo lugar usando conectores nativos, sin que tengas que instalar nada en la otra nube más allá de lo que despliega el conector.

Para conectar AWS, vas a Environment settings > Add environment > Amazon Web Services y proporcionas el ID de la cuenta (o la cuenta de administración de una organización de AWS, que puede incorporar automáticamente las cuentas miembro). Seleccionas los planes de Defender que vas a usar (Defender CSPM, Servers, Containers, Databases) y luego Defender for Cloud genera una plantilla de AWS CloudFormation. Ejecutar esa plantilla en AWS crea los roles de IAM y la confianza de OpenID Connect que permiten a Defender for Cloud leer la configuración y los datos, siguiendo el mínimo privilegio, sin claves de acceso de larga duración. El conector en sí es un recurso de Azure en la suscripción y el grupo de recursos que elijas, y los hallazgos de los recursos de AWS aparecen junto a los de Azure, evaluados frente al Microsoft cloud security benchmark y, opcionalmente, frente a estándares de AWS como AWS Foundational Security Best Practices o CIS.

GCP es similar. Conectas un solo proyecto o una organización, eliges los planes y Defender for Cloud proporciona un script (que se ejecuta en Google Cloud Shell o se despliega con Terraform) que crea las cuentas de servicio y la configuración de federación de identidades de cargas de trabajo requeridas. Después de la incorporación, los recursos de GCP reciben recomendaciones, y los planes de pago extienden la protección a las VMs de Compute Engine y a los clústeres de GKE.

Para los servidores en AWS y GCP, Defender for Servers usa Azure Arc para una cobertura completa: el conector puede aprovisionar automáticamente el agente de Arc en instancias EC2 y de Compute Engine (lo que requiere que las instancias lleguen a los endpoints de Azure y, en AWS, usa Systems Manager), tras lo cual Defender for Endpoint y la administración de vulnerabilidades funcionan como en Azure. El análisis sin agente también cubre estas máquinas. Defender for Containers puede proteger clústeres EKS y GKE mediante componentes aprovisionados por el conector.

La automatización de flujos de trabajo (workflow automation) conecta Defender for Cloud con Azure Logic Apps para que los eventos de seguridad desencadenen acciones automáticamente. Creas una automatización en Environment settings > Workflow automation, eliges un tipo de desencadenador (alertas de seguridad, recomendaciones o cambios de cumplimiento normativo), filtras condiciones como la gravedad de la alerta o nombres de recomendaciones específicas, y eliges una Logic App que use el desencadenador de Microsoft Defender for Cloud. Luego la Logic App puede publicar en Teams, abrir un ticket en ServiceNow o Jira, enviar un correo al propietario del recurso, deshabilitar un usuario comprometido o aplicar una corrección. La Logic App necesita los permisos adecuados, a menudo mediante su identidad administrada, y el usuario que configura la automatización necesita Logic App Contributor o derechos similares para desencadenarla. Azure Policy puede desplegar la automatización de flujos de trabajo a escala en varias suscripciones.

Para la respuesta a escala de SOC, el equivalente en Sentinel son los playbooks, que también son Logic Apps; la automatización de flujos de trabajo de Defender for Cloud es adecuada para automatizar la postura y las alertas a nivel de Defender for Cloud.

Términos clave

Multicloud connector (conector multinube)
Un recurso de Defender for Cloud que incorpora una cuenta de AWS o un proyecto de GCP para la evaluación de la postura y la protección.
CloudFormation template (plantilla de CloudFormation)
La plantilla de despliegue de AWS generada por Defender for Cloud para crear los roles de IAM que necesita el conector.
Workflow automation (automatización de flujos de trabajo)
Una función de Defender for Cloud que desencadena Logic Apps a partir de alertas, recomendaciones o cambios de cumplimiento.
Auto-provisioning of Arc (aprovisionamiento automático de Arc)
Instalación, impulsada por el conector, del agente de Azure Arc en VMs de AWS o GCP para Defender for Servers.
Ejemplo real

Una empresa conecta la cuenta de administración de su organización de AWS a Defender for Cloud, despliega la pila de CloudFormation generada y habilita Defender CSPM y Defender for Servers. Luego crea una automatización de flujos de trabajo que ejecuta una Logic App que publica cada alerta de gravedad High, de Azure o de AWS, en el canal de Teams del equipo de seguridad y abre un ticket.

Consejo para el examen: La incorporación de AWS usa una plantilla de CloudFormation; GCP usa un script de Cloud Shell o Terraform; ambos evitan las claves de larga duración mediante federación. La protección completa de servidores en otras nubes depende de Azure Arc. Las reacciones automáticas a las alertas o recomendaciones de Defender for Cloud son workflow automation con Logic Apps.

Comprueba lo que sabes

¿Qué genera Defender for Cloud para concederse acceso a una cuenta de AWS?

Una plantilla de CloudFormation que crea roles de IAM con una confianza OIDC para el conector.

¿Qué tres tipos de desencadenadores puede usar la automatización de flujos de trabajo?

Alertas de seguridad, recomendaciones y evaluaciones de cumplimiento normativo.

¿Qué debe instalarse en las instancias EC2 para una cobertura completa de Defender for Servers?

El agente de Azure Arc (aprovisionado automáticamente por el conector), además de Defender for Endpoint mediante el plan.
