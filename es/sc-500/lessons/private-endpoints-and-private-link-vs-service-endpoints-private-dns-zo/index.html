Private endpoints y Private Link vs service endpoints, zonas DNS privadas

Los servicios de plataforma como Storage, SQL Database y Key Vault tienen endpoints públicos de forma predeterminada. Dos funciones te permiten llegar a ellos desde una red virtual sin atravesar la internet pública, y el examen pregunta con frecuencia cuál elegir.

Un service endpoint de red virtual (punto de conexión de servicio) se habilita en una subred para un servicio (por ejemplo Microsoft.Storage). A partir de ahí, el tráfico de esa subred hacia el servicio viaja por la red troncal de Azure con la identidad de la subred adjunta, y el firewall del servicio puede permitir esa subred por su nombre. El servicio sigue usando su dirección IP pública; tus VMs simplemente lo alcanzan por una ruta optimizada. Los service endpoints son gratuitos y sencillos, pero solo funcionan desde VNets de Azure (en general, no desde el entorno local por VPN o ExpressRoute), se aplican a todo el servicio en una región a menos que agregues service endpoint policies (compatibles con Storage) para restringir a qué cuentas se puede llegar, y por sí solos no impiden la exfiltración de datos hacia la cuenta de otro cliente del mismo servicio.

Un private endpoint (punto de conexión privado) es una interfaz de red en tu subred con una dirección IP privada de tu espacio de direcciones, asignada a un recurso específico (el subrecurso blob de una cuenta de almacenamiento concreta, un servidor SQL, un vault) mediante Azure Private Link. Los clientes se conectan a esa IP privada. Como es una IP normal de tu red, se puede alcanzar desde VNets emparejadas y desde el entorno local por VPN o ExpressRoute. Como se asigna a un solo recurso, impide de forma inherente llegar a través de él a recursos de otros clientes. Después puedes establecer el acceso de red público del recurso en Disabled. Los private endpoints tienen un costo por hora y por procesamiento de datos.

Azure Private Link es la tecnología subyacente. Además de los servicios de Microsoft, puedes exponer tu propio servicio detrás de un Standard Load Balancer como Private Link service, para que clientes u otros equipos lo consuman mediante private endpoints en sus redes.

El DNS es la parte que confunde a la gente. Los clientes siguen usando el nombre público, como mystorage.blob.core.windows.net. Cuando se crea un private endpoint, el registro DNS público se cambia por un CNAME que apunta a mystorage.privatelink.blob.core.windows.net. Creas una zona DNS privada de Azure llamada privatelink.blob.core.windows.net, la vinculas a tus VNets y guardas en ella un registro A para mystorage que apunta a la IP privada. El portal puede hacerlo automáticamente. Dentro de las VNets vinculadas, el nombre se resuelve a la IP privada; fuera, se resuelve a la IP pública (que ahora está bloqueada). Para los clientes locales, reenvía las consultas de la zona del servicio a Azure DNS mediante Azure DNS Private Resolver o una VM reenviadora de DNS en Azure.

Pruébalo con nslookup mystorage.blob.core.windows.net desde una VM: una dirección 10.x u otra privada significa que funcionó; una dirección pública significa que el DNS no está configurado.

Términos clave

Service endpoint (punto de conexión de servicio)
Una configuración de subred que enruta el tráfico hacia un servicio de Azure por la red troncal y permite que el firewall del servicio admita esa subred; el servicio conserva su IP pública.
Private endpoint (punto de conexión privado)
Una NIC con una IP privada en tu subred asignada a un recurso específico mediante Private Link.
Private Link service
Tu propio servicio detrás de un Standard Load Balancer, expuesto a los consumidores mediante private endpoints.
Private DNS zone (zona DNS privada)
Una zona de Azure DNS, como privatelink.blob.core.windows.net, que resuelve los nombres de servicio a las IP de los private endpoints para las VNets vinculadas.
Ejemplo real

Los analistas del entorno local deben consultar una base de datos de Azure SQL por ExpressRoute sin exposición pública. Creas un private endpoint para el servidor SQL en una subred del hub, vinculas la zona DNS privada privatelink.database.windows.net a la VNet del hub, configuras DNS Private Resolver con un reenviador condicional desde el DNS local y estableces el acceso de red público en Disabled.

Consejo para el examen: Acceso desde el entorno local, una IP privada, alcance por recurso y protección contra exfiltración apuntan a private endpoints. Acceso gratuito, sencillo y a nivel de subred conservando la IP pública apunta a service endpoints. Si un private endpoint 'no funciona', sospecha primero del DNS.

Comprueba lo que sabes

¿Qué opción permite que los clientes locales lleguen a una cuenta de almacenamiento por VPN usando una IP privada?

Un private endpoint, con el DNS resolviendo el nombre a su IP privada.

Después de crear un private endpoint, una VM sigue resolviendo la cuenta de almacenamiento a una IP pública. ¿Qué falta?

La zona DNS privada privatelink con un registro A, vinculada a la VNet de la VM (o un DNS personalizado equivalente).

¿Cambia un service endpoint la dirección IP de destino del servicio?

No, al servicio se le sigue llegando por su IP pública; solo cambian la ruta y la identidad de origen.
