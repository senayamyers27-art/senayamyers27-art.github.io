Niveles de registros y retención (Analytics vs data lake/auxiliar), tablas personalizadas, fundamentos de KQL

Los registros de seguridad son valiosos, pero caros cuando se ingieren a precio completo. Las fuentes de gran volumen, como los flujos del firewall, los registros de proxy o las consultas DNS, pueden necesitarse para investigaciones y cumplimiento, pero rara vez se usan para la detección en tiempo real. Por eso Sentinel y Log Analytics ofrecen niveles, llamados planes de tabla (table plans), que intercambian funciones por costo. Microsoft ha ido cambiando estas opciones, así que céntrate en los conceptos y revisa los nombres actuales en el portal.

El nivel Analytics (plan de registros Analytics) es el nivel completo: los datos admiten cualquier consulta KQL, reglas de análisis, workbooks, hunting y un rendimiento interactivo rápido. Tiene el costo de ingesta más alto. Incluye retención interactiva durante un período, y puedes ampliar la retención por tabla. Úsalo para datos de alto valor relevantes para la detección: inicios de sesión de identidad, eventos de EDR, alertas de seguridad, eventos de seguridad de Windows de servidores críticos.

Los niveles de menor costo están diseñados para datos de gran volumen y menor valor. Los planes de registros Basic y Auxiliary de Log Analytics permiten una ingesta mucho más barata con capacidades de consulta limitadas, cargos por consulta y menor compatibilidad con reglas de alerta. El Microsoft Sentinel data lake, una capacidad más reciente, proporciona un nivel de lago para el almacenamiento de datos de seguridad a largo plazo y bajo costo en formatos abiertos, que puedes consultar con KQL (normalmente de forma asíncrona con trabajos KQL o mediante notebooks) y desde el cual puedes promover resultados resumidos de vuelta al nivel Analytics para la detección. Reflejar (mirroring) las tablas de Analytics en el lago también te permite conservarlas durante años a bajo costo. El diseño general es: datos aptos para detección en Analytics, datos masivos en el nivel de lago o auxiliar, y reglas de resumen (summary rules) o trabajos KQL para llevar la información destilada a Analytics.

La retención tiene dos partes. La retención interactiva (de análisis) es el tiempo durante el cual los datos se pueden consultar con rendimiento completo. La retención a largo plazo (antes llamada archivo) conserva los datos a bajo costo hasta por 12 años; para consultarlos ejecutas un trabajo de búsqueda (search job) o una restauración. Configura la retención por tabla para cumplir los requisitos de cumplimiento mientras controlas el costo.

Las tablas personalizadas (custom tables) contienen datos que ninguna tabla integrada cubre. Sus nombres terminan en _CL. Las creas mediante la Logs Ingestion API con un data collection endpoint y una DCR que define el esquema y la transformación, o mediante la recopilación de registros de texto o JSON personalizados con AMA. Las tablas personalizadas basadas en DCR pueden usar cualquier plan de tabla.

KQL (Kusto Query Language) es un lenguaje de solo lectura basado en canalizaciones: empiezas con una tabla y pasas las filas por operadores separados por |. Los operadores clave son where (filtrar), project (elegir columnas), extend (agregar columnas calculadas), summarize (agregar con count, dcount, sum, by columnas), sort by, top, join, union, parse y render (gráficos). Los filtros de tiempo usan ago(), como ago(1h).

SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType != "0"
| summarize Failures = count() by UserPrincipalName, IPAddress
| where Failures > 20
| sort by Failures desc

Términos clave

Analytics tier (nivel Analytics)
El nivel de registros completo que admite todo KQL, las reglas de análisis y las consultas rápidas, con el costo de ingesta más alto.
Sentinel data lake
Un nivel de lago de bajo costo para datos de seguridad a largo plazo, consultado de forma asíncrona y usado para alimentar Analytics con resultados resumidos.
Long-term retention (retención a largo plazo)
Retención de bajo costo de hasta 12 años, a la que se accede mediante trabajos de búsqueda o restauración.
Custom table (tabla personalizada)
Una tabla para datos no estándar, con el sufijo _CL, creada mediante la Logs Ingestion API o los registros personalizados de AMA.
summarize
Un operador de KQL que agrega filas, como contar eventos por usuario.
Ejemplo real

Los registros de flujo del firewall cuestan más que todos los demás datos juntos. Mantienes los eventos de amenazas y de denegación del firewall en el nivel Analytics para la detección, envías los registros de flujo completos al nivel de data lake para las investigaciones, ejecutas un trabajo KQL diario que resume las conexiones a destinos poco comunes en una tabla de Analytics y configuras una retención a largo plazo de dos años para el cumplimiento.

Consejo para el examen: La detección y las reglas en tiempo real necesitan datos del nivel Analytics. Los datos de gran volumen y consultados rara vez pertenecen a un nivel de menor costo, como el data lake o los registros auxiliares/básicos. Los datos archivados necesitan un trabajo de búsqueda o una restauración. Las tablas personalizadas terminan en _CL.

Comprueba lo que sabes

¿Por qué no poner todos los registros de flujo del firewall en el nivel Analytics?

El volumen hace que la ingesta sea costosa, y la mayor parte de los datos no se necesita para la detección en tiempo real; un nivel de menor costo es más adecuado.

¿Qué operador de KQL cuenta los eventos por usuario?

summarize, por ejemplo summarize count() by UserPrincipalName.

¿Cómo consultas los datos que están en retención a largo plazo?

Ejecutando un trabajo de búsqueda o restaurando los datos para que se puedan consultar.
