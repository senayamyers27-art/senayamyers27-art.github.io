Microsoft Certified: Cloud and AI Security Engineer Associate (replaces Azure Security Engineer Associate / AZ-500) SC-500

Diseño del área de trabajo de Microsoft Sentinel, conectores de datos, Azure Monitor Agent con reglas de recopilación de datos, Syslog y CEF, eventos de seguridad de Windows

Microsoft Sentinel es la solución nativa de la nube de Microsoft para la administración de información y eventos de seguridad (SIEM) y la orquestación, automatización y respuesta de seguridad (SOAR). Se habilita sobre un área de trabajo de Log Analytics, donde se almacenan todos los datos recopilados y se consultan con KQL. Sentinel se administra cada vez más desde el portal de Microsoft Defender junto con Defender XDR, aunque los conceptos son los mismos que en el portal de Azure.

El diseño del área de trabajo es la primera decisión. Microsoft recomienda la menor cantidad posible de áreas de trabajo, idealmente una por tenant, porque la correlación y la búsqueda de amenazas (hunting) son más fáciles cuando los datos están juntos. Las razones para agregar áreas de trabajo incluyen requisitos de residencia o soberanía de datos (los datos deben quedarse en una región), tenants separados (los proveedores de servicios administrados usan Azure Lighthouse sobre las áreas de trabajo de sus clientes) y la separación de la facturación. El acceso dentro de una sola área de trabajo puede limitarse con RBAC de contexto de recurso o RBAC a nivel de tabla en lugar de dividirla. Los roles de Sentinel incluyen Microsoft Sentinel Reader, Responder, Contributor y Automation Contributor, además de los roles de Log Analytics para el área de trabajo.

Los conectores de datos (data connectors) traen los datos. Se distribuyen mediante el Content hub como soluciones que empaquetan conectores, reglas de análisis, workbooks y playbooks. Los conectores de servicio a servicio ingieren fácilmente las fuentes de Microsoft: registros de inicio de sesión y de auditoría de Microsoft Entra ID, Azure Activity, Microsoft Defender XDR (incidentes y eventos sin procesar), alertas de Defender for Cloud, y actividad de Microsoft 365 y Office. Las fuentes de terceros usan recopilación basada en agentes, conectores sin código basados en API o Azure Functions.

El Azure Monitor Agent (AMA) es el agente actual para recopilar registros de máquinas Windows y Linux en Azure y, con Azure Arc, en otros lugares; reemplaza al agente heredado de Log Analytics (MMA/OMS), que ya está retirado. AMA se configura mediante reglas de recopilación de datos (data collection rules, DCR), que definen qué recopilar (ID de eventos, facilities y niveles de Syslog, contadores de rendimiento), transformaciones opcionales escritas en KQL que filtran o modifican los datos antes de la ingesta, y el área de trabajo y la tabla de destino. Una DCR puede asociarse con muchas máquinas, y una máquina puede tener varias DCR, así que puedes administrar la recopilación de forma central y económica.

Los eventos de seguridad de Windows se recopilan con el conector Windows Security Events via AMA, eligiendo un conjunto: All events, Common (un conjunto de auditoría recomendado), Minimal, o Custom con consultas XPath para ID de eventos específicos, como 4624 (inicio de sesión correcto) o 4625 (inicio de sesión fallido). Llegan a la tabla SecurityEvent. Windows Forwarded Events via AMA admite los recopiladores de Windows Event Forwarding.

Linux y los dispositivos de red envían Syslog. Con AMA, el conector Syslog via AMA recopila las facilities y gravedades en la tabla Syslog. Muchos firewalls y appliances envían Common Event Format (CEF), un formato de mensaje Syslog estandarizado, que el conector Common Event Format via AMA analiza y guarda en la tabla CommonSecurityLog. Como los appliances no pueden ejecutar un agente, despliegas una VM Linux como reenviador de registros (log forwarder) con rsyslog o syslog-ng y AMA, apuntas los dispositivos hacia ella en UDP o TCP 514 y asocias las DCR con el reenviador. Ten cuidado de no recopilar los mismos mensajes tanto en la tabla Syslog como en CommonSecurityLog, lo que duplica el costo.

Planifica los costos desde el principio: el volumen de ingesta determina el precio, y las transformaciones de las DCR son la herramienta principal para descartar el ruido antes de que se facture.

Términos clave

Log Analytics workspace (área de trabajo de Log Analytics)
El almacén de datos subyacente de Microsoft Sentinel, que se consulta con KQL.
Azure Monitor Agent
El agente actual para recopilar registros de máquinas Windows y Linux, configurado mediante reglas de recopilación de datos.
Data collection rule (regla de recopilación de datos)
Una configuración que define qué datos recopila AMA, las transformaciones KQL opcionales y el destino.
CEF
Common Event Format, un formato de mensaje Syslog estandarizado que usan muchos appliances de seguridad, almacenado en CommonSecurityLog.
Log forwarder (reenviador de registros)
Una VM Linux con AMA que recibe Syslog o CEF de los dispositivos y lo envía al área de trabajo.
Ejemplo real

Una empresa despliega Sentinel en una sola área de trabajo en su región principal. Instala las soluciones de Microsoft Entra ID, Defender XDR y Azure Activity, usa Windows Security Events via AMA con el conjunto Common en los controladores de dominio, y crea un reenviador Linux con AMA para recibir CEF de sus firewalls, con una transformación de DCR que descarta los registros ruidosos de tráfico permitido de una red de pruebas.

Consejo para el examen: Usa por defecto una sola área de trabajo, a menos que la residencia, los límites de tenant o la facturación obliguen a tener más. AMA más DCR es el método de recopilación; el agente heredado está retirado. CEF va a CommonSecurityLog mediante un reenviador Linux; los eventos de Windows van a SecurityEvent; las transformaciones de DCR filtran los datos antes de la ingesta.

Comprueba lo que sabes

¿Qué tabla almacena los mensajes CEF analizados?

CommonSecurityLog.

¿Cómo recopilas los registros de un appliance de firewall que no puede ejecutar un agente?

Enviando su Syslog/CEF a un reenviador de registros Linux que ejecute AMA, con el conector CEF via AMA y una DCR.

¿Cuál es una razón válida para crear una segunda área de trabajo de Sentinel?

Un requisito de residencia de datos que obliga a que algunos datos permanezcan en otra región (o un límite de tenant o de facturación distinto).
