Red Hat Certified System Administrator EX200 (RHEL 10)

Configurar la autenticación SSH basada en claves (ssh-keygen, ssh-copy-id, permisos de ~/.ssh, sshd_config)

La autenticación con claves de SSH (Secure Shell) reemplaza una contraseña escrita con un par de claves. La clave privada se queda en tu cliente; la clave pública se copia al servidor. Cuando te conectas, el servidor desafía al cliente a demostrar que tiene la clave privada correspondiente, y la clave privada en sí nunca viaja por la red. Las claves resisten la adivinación de contraseñas, permiten la automatización y se esperan en el RHCSA cada vez que una tarea dice inicio de sesión sin contraseña.

Genera un par con ssh-keygen. El tipo predeterminado en el RHEL actual es Ed25519 o RSA según la versión, y puedes elegirlo con -t ed25519. Acepta la ubicación predeterminada en ~/.ssh/ y elige si proteger la clave privada con una frase de contraseña (passphrase); una frase vacía permite el uso desatendido, mientras que una frase añade protección si roban el archivo, y ssh-agent puede guardarla en caché.

ssh-keygen -t ed25519            # crea ~/.ssh/id_ed25519 y .pub
ssh-copy-id student@serverb      # pide la contraseña una vez
ssh student@serverb              # ahora inicia sesión con la clave

ssh-copy-id añade tu clave pública a ~/.ssh/authorized_keys en el servidor para el usuario de destino y establece permisos razonables. Si la copias a mano, los permisos importan, porque sshd rechaza las claves cuando los archivos están demasiado abiertos: el directorio personal no debe poder escribirlo el grupo ni los otros, ~/.ssh debe ser 700, authorized_keys 600 y la clave privada 600. Todo debe pertenecer al usuario. Las etiquetas de SELinux también importan; si creas los archivos moviéndolos, ejecuta restorecon -Rv ~/.ssh.

El comportamiento del servidor se establece en /etc/ssh/sshd_config y, preferiblemente, en archivos drop-in dentro de /etc/ssh/sshd_config.d/ que terminan en .conf, que se leen primero; para la mayoría de las opciones gana el primer valor encontrado. Ajustes comunes: PubkeyAuthentication yes (el predeterminado), PasswordAuthentication no para exigir claves y PermitRootLogin con los valores yes, no o prohibit-password (root solo puede iniciar sesión con clave).

# /etc/ssh/sshd_config.d/50-local.conf
PasswordAuthentication no
PermitRootLogin no

sshd -t                  # probar la sintaxis
systemctl reload sshd

Antes de deshabilitar las contraseñas, confirma en una segunda sesión que el inicio con clave funciona para no quedarte sin acceso. Si se rechaza una clave, ejecuta el cliente con ssh -v y lee el lado del servidor en journalctl -u sshd, que normalmente nombra el permiso incorrecto. Protege las claves privadas como si fueran contraseñas: nunca las copies a los servidores y quita las claves públicas de authorized_keys cuando deba terminar el acceso.

Términos clave

Key pair (par de claves)
Una clave privada guardada en el cliente y una clave pública correspondiente colocada en los servidores para la autenticación.
authorized_keys
El archivo ~/.ssh/authorized_keys de un servidor que lista las claves públicas autorizadas para iniciar sesión como ese usuario.
ssh-copy-id
Copia una clave pública al archivo authorized_keys de un usuario remoto con los permisos correctos.
PermitRootLogin
Un ajuste de sshd que controla los inicios de sesión de root: yes, no o prohibit-password (solo con clave).
Ejemplo real

El usuario student de servera debe iniciar sesión en serverb sin contraseña. Como student ejecutas ssh-keygen aceptando los valores predeterminados, luego ssh-copy-id student@serverb e introduces la contraseña una vez. Ahora ssh student@serverb hostname imprime serverb sin pedir nada, y journalctl -u sshd en serverb muestra Accepted publickey.

Consejo para el examen: La mayoría de los fallos con claves son de permisos: ~/.ssh debe ser 700, authorized_keys 600 y el directorio personal no debe poder escribirlo el grupo ni el resto del mundo. Revisa journalctl -u sshd en el servidor para ver la razón.

Comprueba lo que sabes

¿Qué archivo del servidor debe contener tu clave pública?

~/.ssh/authorized_keys en el directorio personal de la cuenta con la que inicias sesión.

¿Qué ejecutas después de cambiar los ajustes de sshd?

sshd -t para revisar la sintaxis y luego systemctl reload sshd (o restart).

¿Qué permite PermitRootLogin prohibit-password?

Que root inicie sesión con una clave, pero no con una contraseña.
