AWS Certified Cloud Practitioner CLF-C02

Modelos de implementación (nube, híbrido y local) y aprovisionamiento único frente a repetible

Un modelo de implementación describe dónde se ejecutan tus aplicaciones y su infraestructura. AWS describe tres: nube, híbrido y local (on-premises). El examen te presenta un escenario y te pregunta de qué modelo se trata, o por qué una organización podría elegirlo, así que concéntrate en las pistas. Este tema también cubre cómo creas los recursos, ya sea una sola vez a mano o de forma repetible mediante código, porque esa elección afecta la confiabilidad, la seguridad y tu capacidad de recuperación.

En una implementación en la nube, a veces llamada nativa de la nube o all-in, cada parte de la aplicación se ejecuta en la nube. Puede haberse construido allí desde el principio o haberse migrado por completo. Puede usar infraestructura de bajo nivel, como instancias de Amazon Elastic Compute Cloud (Amazon EC2), o servicios administrados y serverless de más alto nivel, como AWS Lambda y Amazon DynamoDB. Una empresa sin centro de datos propio que ejecuta todo en AWS usa el modelo de nube, aunque reparta sus cargas de trabajo entre varias Regiones o cuentas.

Una implementación híbrida conecta recursos en la nube con infraestructura que permanece en las instalaciones propias. Las organizaciones eligen el modelo híbrido cuando algunos sistemas todavía no pueden moverse por regulaciones, necesidades de latencia muy baja, dependencia de hardware local como equipos de fábrica o un plan de migración gradual, pero aun así quieren los beneficios de la nube en otras partes. Una empresa podría mantener su sistema heredado de planificación de recursos empresariales (ERP) en su propio centro de datos y ejecutar sus nuevas aplicaciones web para clientes en AWS, conectadas mediante AWS Site-to-Site VPN o AWS Direct Connect. Servicios como AWS Outposts, AWS Storage Gateway y AWS Systems Manager, que puede administrar servidores locales, respaldan las configuraciones híbridas. La idea clave es que los dos entornos funcionan juntos como un solo sistema: usuarios, datos y herramientas de administración abarcan ambos, en lugar de simplemente existir uno al lado del otro.

Una implementación local (on-premises), a veces llamada nube privada, ejecuta los recursos en el propio centro de datos de la organización usando virtualización y herramientas de gestión de recursos para obtener cierta agilidad parecida a la de la nube. Ofrece el máximo control físico, pero no la escala, el alcance global ni la economía de pago por uso de la nube pública. La organización compra el hardware por adelantado, un gasto de capital (CapEx), y debe planificar la capacidad con anticipación, mientras que la nube lo convierte en un gasto operativo variable (OpEx).

El aprovisionamiento es la forma en que creas los recursos, y puede ser único o repetible. El aprovisionamiento único, como lanzar una instancia de prueba en la consola, está bien para experimentos y aprendizaje. El aprovisionamiento repetible usa código o plantillas, como AWS CloudFormation, el AWS Cloud Development Kit o scripts de la CLI en control de versiones, para que la misma configuración pueda recrearse en otro entorno, cuenta o Región. La producción debe aprovisionarse de forma repetible porque los pasos manuales se olvidan fácilmente, son difíciles de auditar y es casi imposible reproducirlos con exactitud después de un desastre. Las plantillas también hacen posibles las revisiones: un colega puede verificar una regla de grupo de seguridad en un pull request antes de que llegue a producción.

Veamos un ejemplo práctico. Un fabricante ejecuta software de control de máquinas que debe responder en milisegundos en la planta, mientras que su tienda en línea y su analítica pueden ejecutarse en cualquier lugar. Mantiene los sistemas de control en la planta, implementa la tienda en AWS y conecta ambos con Direct Connect: un modelo híbrido. El entorno de la tienda está definido en una plantilla de CloudFormation, así que el equipo puede levantar una copia de staging para pruebas y reconstruir producción en otra Región durante un simulacro de recuperación ante desastres. El primer prototipo, construido a mano en la consola, fue un aprovisionamiento único y se eliminó después.

Errores comunes: llamar «híbrido» a un diseño de AWS con varias Regiones o varias cuentas (sigue siendo nube, porque nada se ejecuta en las instalaciones propias); suponer que el modelo híbrido siempre es un estado temporal (para algunas cargas reguladas o sensibles a la latencia es una elección de largo plazo); pensar que nube privada significa una cuenta de AWS dedicada; y tratar el aprovisionamiento repetible como opcional para producción. Otra trampa es suponer que Outposts hace que una carga de trabajo sea «solo nube»; el hardware de Outposts está en tus instalaciones, así que respalda diseños híbridos.

En el examen, busca pistas de ubicación. «Todo se ejecuta en AWS» o «sin centro de datos» significa nube. «Mantiene algunos sistemas en su propio centro de datos y los conecta a AWS» significa híbrido. «Virtualización en el propio centro de datos de la empresa» significa local o nube privada. Para el aprovisionamiento, «consistente», «repetible», «varios entornos» o «recuperarse rápidamente recreando la infraestructura» apuntan al aprovisionamiento repetible con infraestructura como código, mientras que «experimento rápido» o «prueba puntual» es donde el aprovisionamiento único en la consola es aceptable.

Términos clave

Implementación en la nube
Modelo en el que todas las partes de una aplicación se ejecutan en la nube.
Implementación híbrida
Modelo que conecta recursos en la nube con infraestructura que permanece en las instalaciones propias.
Local (nube privada)
Modelo en el que los recursos se ejecutan en el propio centro de datos de la organización usando virtualización y herramientas de gestión.
Aprovisionamiento único
Crear recursos manualmente para un solo uso, normalmente a través de la consola.
Aprovisionamiento repetible
Crear recursos a partir de código o plantillas para que la misma configuración pueda recrearse de forma consistente.
AWS Outposts
Hardware administrado por AWS instalado en las instalaciones del cliente para ejecutar servicios de AWS de forma local.
Ejemplo real

Un banco debe mantener su libro contable principal en hardware de sus propios centros de datos por razones regulatorias, pero quiere usar AWS para una nueva interfaz de banca móvil y analítica de fraude. Conecta el centro de datos a una VPC con AWS Direct Connect y una Site-to-Site VPN de respaldo, creando una implementación híbrida. Todas las piezas en AWS están definidas en CloudFormation para que los auditores puedan revisar los cambios y el banco pueda reconstruirlas en una segunda Región.

Consejo para el examen: El modelo híbrido requiere infraestructura local y recursos en la nube conectados entre sí. Los diseños con varias Regiones o varias cuentas que se ejecutan por completo en AWS siguen siendo el modelo de nube.

Comprueba lo que sabes

Una startup sin servidores propios ejecuta todas sus cargas de trabajo en AWS en dos Regiones. ¿Qué modelo de implementación es?

Nube (all-in), porque nada se ejecuta en instalaciones propias; tener varias Regiones no lo convierte en híbrido.

Menciona dos razones por las que una organización podría elegir un modelo híbrido.

Regulaciones o datos que deben permanecer en las instalaciones propias, latencia muy baja hacia equipos locales o una migración gradual de sistemas heredados.

¿Por qué la infraestructura de producción debe aprovisionarse de forma repetible?

Las plantillas o el código recrean la misma configuración de forma consistente, pueden revisarse y auditarse, y permiten reconstruir rápidamente después de un desastre.

¿Qué oferta de AWS coloca hardware y servicios de AWS dentro del propio centro de datos del cliente?

AWS Outposts.
