AWS Certified Cloud Practitioner CLF-C02

Principios de diseño en la nube: bajo acoplamiento, diseñar para fallas, automatización y operaciones como código

Más allá de los seis pilares, AWS enseña un puñado de principios generales de diseño para arquitecturas en la nube. El examen Cloud Practitioner verifica que los reconozcas y que puedas elegir la arquitectura que los sigue.

El bajo acoplamiento (loose coupling) significa que los componentes interactúan mediante interfaces bien definidas y no dependen directamente de la disponibilidad ni de los tiempos de los demás. Si una capa web llama directamente a una capa de procesamiento de pedidos y la capa de procesamiento se vuelve lenta, la capa web también falla; eso es alto acoplamiento. Si en cambio la capa web coloca los pedidos en una cola de Amazon Simple Queue Service (SQS) y la capa de procesamiento los lee de ella, cualquiera de los dos lados puede escalar, fallar o ser reemplazado sin afectar al otro. Los balanceadores de carga, las colas, las notificaciones mediante Amazon SNS y los eventos mediante Amazon EventBridge son las herramientas típicas para desacoplar.

Diseñar para fallas (designing for failure) parte de la suposición de que todo falla tarde o temprano: discos, instancias e incluso centros de datos completos. En lugar de esperar que nada se rompa, incorporas redundancia y recuperación automática. Ejecuta en varias Availability Zones, evita los puntos únicos de falla, mantén respaldos y prueba que puedes restaurarlos, y usa comprobaciones de estado (health checks) para que los recursos fallidos se reemplacen automáticamente. Una idea relacionada es tratar los servidores como recursos desechables: si una instancia se comporta mal, termínala y deja que la automatización lance una nueva en lugar de repararla a mano.

La automatización elimina pasos manuales lentos y propensos a errores. Auto Scaling agrega y quita capacidad, las comprobaciones de estado reemplazan instancias fallidas y las alarmas disparan acciones. Las operaciones como código, a veces llamadas infraestructura como código (IaC), significan definir tu infraestructura y tus procedimientos operativos en archivos que se pueden versionar, revisar y ejecutar repetidamente. Las plantillas de AWS CloudFormation son el principal ejemplo de AWS: describes los recursos que quieres y CloudFormation los crea de la misma manera cada vez.

Otros principios que puedes ver incluyen usar servicios administrados en lugar de ejecutar tu propio software en servidores, pensar en paralelo (repartir el trabajo entre muchos recursos pequeños) y hacer cambios frecuentes, pequeños y reversibles. Cuando el examen pregunta qué arquitectura es la más resiliente o la más fácil de escalar, la respuesta suele ser la que está desacoplada, distribuida entre AZ y automatizada.

Términos clave

Loose coupling (bajo acoplamiento)
Diseñar los componentes para que interactúen mediante interfaces como colas o balanceadores de carga, de modo que la falla de uno no se propague a los demás.
Single point of failure (punto único de falla)
Un componente cuya falla derriba todo el sistema porque nada más puede asumir su trabajo.
Infrastructure as code (IaC, infraestructura como código)
Definir la infraestructura en archivos de plantilla legibles por máquina para poder versionarla, revisarla y desplegarla de forma repetible.
Disposable resources (recursos desechables)
Tratar los servidores como unidades reemplazables que se terminan y se recrean automáticamente en lugar de repararse a mano.
Ejemplo real

Un sitio para compartir fotos solía redimensionar las imágenes dentro de la propia solicitud de carga, y las cargas fallaban cada vez que el redimensionamiento era lento. El equipo cambió el diseño para que la capa web guarde la carga en S3 y envíe un mensaje a una cola SQS, y una flota separada de trabajadores redimensiona las imágenes desde la cola. Ahora las cargas funcionan incluso cuando los trabajadores están ocupados o se están reemplazando.

Consejo para el examen: Cuando una pregunta pide cómo desacoplar componentes o absorber picos entre capas, piensa en Amazon SQS. Cuando pregunta cómo aprovisionar entornos idénticos repetidamente, piensa en AWS CloudFormation (operaciones como código).

Comprueba lo que sabes

¿Qué servicio de AWS se usa con más frecuencia para desacoplar una capa productora de una capa consumidora para que escalen de forma independiente?

Amazon SQS, una cola de mensajes administrada: el productor escribe mensajes y el consumidor los procesa a su propio ritmo.

¿Cómo se ve en la práctica 'diseñar para fallas'?

Suponer que los componentes fallarán e incorporar redundancia y recuperación automática, por ejemplo ejecutando en varias AZ con comprobaciones de estado y respaldos probados.
