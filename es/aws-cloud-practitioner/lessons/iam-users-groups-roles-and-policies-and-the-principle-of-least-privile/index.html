AWS Certified Cloud Practitioner CLF-C02

Usuarios, grupos, roles y políticas de IAM, y el principio de mínimo privilegio

AWS Identity and Access Management (IAM) controla quién puede iniciar sesión en tu cuenta de AWS (autenticación) y qué tiene permitido hacer (autorización). IAM es un servicio global, no ligado a una Región, y está disponible sin cargo adicional. Es el núcleo de la responsabilidad de seguridad del cliente, porque casi todas las fallas de seguridad en AWS se reducen a que alguien tenga un acceso que no debería tener. IAM tiene cuatro bloques básicos. Un usuario de IAM (IAM user) es una identidad para una persona o aplicación, con credenciales de largo plazo: una contraseña para la consola y, de forma opcional, claves de acceso para la interfaz de línea de comandos (CLI) y los kits de desarrollo de software (SDK). Un grupo de IAM (IAM group) es un conjunto de usuarios; adjuntas los permisos al grupo y cada miembro los hereda. Los grupos no pueden contener otros grupos, y un grupo no es una identidad que pueda iniciar sesión. Un rol de IAM (IAM role) es una identidad con permisos pero sin credenciales de largo plazo. En su lugar, una entidad de confianza asume el rol y recibe credenciales temporales de AWS Security Token Service (AWS STS). Las políticas definen los permisos en sí.

Los roles los usan los servicios de AWS (por ejemplo, una instancia EC2 que necesita leer de S3 usa un perfil de instancia con un rol), los usuarios de otra cuenta de AWS y las personas que inician sesión mediante un proveedor de identidad central como IAM Identity Center. AWS ahora recomienda los roles y las credenciales temporales en lugar de los usuarios de IAM siempre que sea posible, porque las credenciales temporales vencen por sí solas y no hay claves de largo plazo que puedan filtrarse. Ejecutar aws sts get-caller-identity muestra a qué usuario o rol pertenecen tus credenciales actuales, lo que resulta útil cuando los permisos se comportan de forma inesperada.

Los permisos se definen en políticas, que son documentos JavaScript Object Notation (JSON). Cada declaración (statement) tiene un Effect (Allow o Deny), una o más Actions (como s3:GetObject), Resources identificados mediante Amazon Resource Names (ARN) y Conditions opcionales. De forma predeterminada todo está denegado; un Allow explícito concede el acceso, y un Deny explícito siempre prevalece sobre cualquier Allow. Las políticas basadas en identidad se adjuntan a usuarios, grupos y roles; las políticas basadas en recursos, como las políticas de bucket de S3, se adjuntan a los recursos. Las políticas administradas por AWS (AWS managed policies) las crea AWS de antemano, y las políticas administradas por el cliente (customer managed policies) son las que tú escribes y mantienes.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-reports/*"
  }]
}

El principio de mínimo privilegio (least privilege) significa conceder solo los permisos necesarios para realizar una tarea y nada más. En la práctica: empieza con permisos mínimos y agrega según sea necesario, adjunta los permisos a grupos y roles en lugar de a usuarios individuales, usa condiciones para acotar el acceso (por ejemplo, a un rango de IP específico o exigiendo MFA) y revisa el acceso con regularidad. IAM Access Analyzer ayuda encontrando recursos compartidos fuera de tu cuenta, señalando accesos que no se usan y generando políticas basadas en la actividad real registrada en CloudTrail. Exigir MFA a los usuarios humanos y evitar o rotar las claves de acceso de largo plazo completan las buenas prácticas de IAM.

Veamos un ejemplo práctico. Cinco analistas necesitan acceso de lectura a un bucket de informes. En lugar de adjuntar la política anterior a cinco usuarios, creas un grupo Analysts, le adjuntas la política y agregas a los usuarios, de modo que un analista nuevo obtiene acceso al unirse al grupo. Un trabajo nocturno en una instancia EC2 también necesita leer el bucket; en lugar de guardar claves de acceso en el servidor, adjuntas un rol a la instancia, y el SDK obtiene automáticamente credenciales temporales.

Errores comunes: guardar claves de acceso en instancias EC2 o en el código en lugar de usar roles; adjuntar AdministratorAccess porque es más rápido; pensar que los grupos pueden anidarse o iniciar sesión; y olvidar que un Deny explícito en cualquier lugar prevalece sobre cualquier Allow. También se suele confundir la autenticación (demostrar quién eres, con una contraseña, MFA o un rol) con la autorización (lo que una política te permite hacer una vez que se sabe quién eres), y suponer que un nuevo usuario de IAM puede hacer algo simplemente porque puede iniciar sesión. Un usuario nuevo sin políticas puede iniciar sesión en la consola pero no puede actuar sobre ningún recurso.

Las preguntas del examen suelen evaluar qué bloque básico corresponde. 'Un servicio de AWS como EC2 o Lambda necesita acceder a otro servicio de AWS' es un rol de IAM. 'Varias personas necesitan los mismos permisos' es un grupo de IAM. 'Definir qué acciones se permiten sobre qué recursos' es una política. 'Credenciales temporales' o 'acceso entre cuentas' apunta a los roles. 'Conceder solo los permisos necesarios' es mínimo privilegio, y 'encontrar recursos compartidos con cuentas externas' es IAM Access Analyzer.

Términos clave

Usuario de IAM (IAM user)
Identidad con credenciales de largo plazo que representa a una persona o aplicación.
Grupo de IAM (IAM group)
Conjunto de usuarios de IAM que comparten los permisos adjuntos al grupo.
Rol de IAM (IAM role)
Identidad con permisos que asumen las entidades de confianza para recibir credenciales temporales.
Política de IAM (IAM policy)
Documento JSON que permite o deniega acciones sobre recursos, de forma opcional bajo ciertas condiciones.
Amazon Resource Name (ARN)
Identificador único de un recurso de AWS que se usa en las políticas.
Mínimo privilegio (least privilege)
Conceder solo los permisos mínimos necesarios para realizar una tarea.
IAM Access Analyzer
Herramienta que identifica accesos externos o sin usar y ayuda a generar políticas de mínimo privilegio.
Ejemplo real

Un equipo de desarrollo les dio AdministratorAccess a todos los desarrolladores para avanzar rápido. Después de que un desarrollador eliminó por accidente una base de datos de producción, la empresa creó grupos para desarrolladores y operadores con políticas acotadas, puso los cambios de producción detrás de un rol que exige MFA para asumirlo, y usó la generación de políticas de IAM Access Analyzer para construir una política de mínimo privilegio a partir de lo que cada equipo realmente usó durante 90 días.

Consejo para el examen: Un servicio de AWS que necesita llamar a otro servicio de AWS debe usar un rol de IAM, nunca claves de acceso guardadas. Varias personas que necesitan los mismos permisos significa un grupo de IAM. Un Deny explícito siempre prevalece sobre un Allow.

Comprueba lo que sabes

Una aplicación en EC2 necesita leer de S3. ¿Cuál es la forma recomendada de darle permisos?

Adjuntar un rol de IAM a la instancia para que reciba credenciales temporales; no guardar claves de acceso en el servidor.

¿Un grupo de IAM puede iniciar sesión o contener otros grupos?

No. Un grupo es solo una forma de adjuntar permisos a muchos usuarios; no puede iniciar sesión ni anidarse.

Si una política permite s3:DeleteObject y otra lo deniega explícitamente, ¿qué ocurre?

La acción se deniega, porque un Deny explícito siempre prevalece sobre un Allow.

¿Qué es el principio de mínimo privilegio?

Conceder solo los permisos necesarios para realizar una tarea y nada más.
