AWS Certified Cloud Practitioner CLF-C02

Usuarios, grupos, roles y políticas de IAM, y el principio de mínimo privilegio

AWS Identity and Access Management (IAM) controla quién puede iniciar sesión en tu cuenta de AWS (autenticación) y qué puede hacer (autorización). IAM es un servicio global, disponible sin costo adicional, y es el núcleo de la responsabilidad de seguridad del cliente.

Un usuario de IAM (IAM user) es una identidad para una persona o aplicación, con credenciales de largo plazo: una contraseña para la consola y, opcionalmente, claves de acceso para la CLI y los SDK. Un grupo de IAM (IAM group) es una colección de usuarios; adjuntas permisos al grupo y cada miembro los hereda. Los grupos no pueden contener otros grupos, y un grupo no es una identidad que pueda iniciar sesión. Un rol de IAM (IAM role) es una identidad con permisos pero sin credenciales de largo plazo. En cambio, una entidad de confianza asume el rol y recibe credenciales temporales. Los roles los usan los servicios de AWS (por ejemplo, una instancia EC2 que necesita leer de S3), los usuarios de otra cuenta y las personas que inician sesión mediante un proveedor de identidad central. AWS ahora recomienda roles y credenciales temporales en lugar de usuarios de IAM siempre que sea posible.

Los permisos se definen en políticas (policies), que son documentos JSON. Cada declaración (statement) tiene un Effect (Allow o Deny), una o más Actions (como s3:GetObject) y Resources (identificados por Amazon Resource Names, o ARN). De forma predeterminada todo está denegado; un Allow explícito concede el acceso, y un Deny explícito siempre prevalece sobre cualquier Allow. Las políticas basadas en identidad se adjuntan a usuarios, grupos y roles; las políticas basadas en recursos, como las políticas de bucket de S3, se adjuntan a los recursos. Las políticas administradas por AWS (AWS managed policies) vienen predefinidas; las políticas administradas por el cliente (customer managed policies) son las que escribes tú.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-reports/*"
  }]
}

El principio de mínimo privilegio (principle of least privilege) significa otorgar solo los permisos necesarios para realizar una tarea y nada más. Empieza con permisos mínimos y agrega según haga falta, prefiere grupos y roles en lugar de permisos adjuntos a usuarios individuales, y revisa el acceso con regularidad. IAM Access Analyzer puede ayudarte a encontrar recursos compartidos fuera de tu cuenta y a generar políticas basadas en la actividad real. Usar MFA para los usuarios humanos y rotar o evitar las claves de largo plazo completan las buenas prácticas de IAM.

Términos clave

IAM user (usuario de IAM)
Una identidad con credenciales de largo plazo que representa a una persona o aplicación en una cuenta de AWS.
IAM group (grupo de IAM)
Una colección de usuarios de IAM que comparten los permisos adjuntos al grupo.
IAM role (rol de IAM)
Una identidad con permisos que asumen entidades de confianza y que proporciona credenciales temporales.
IAM policy (política de IAM)
Un documento JSON que permite o deniega acciones sobre recursos; un deny explícito siempre gana.
Principle of least privilege (principio de mínimo privilegio)
Otorgar solo los permisos mínimos necesarios para realizar una tarea.
Ejemplo real

Una aplicación que se ejecuta en una instancia EC2 necesita subir archivos a un bucket de S3. En lugar de guardar en el servidor las claves de acceso de un usuario de IAM, el equipo crea un rol de IAM con una política que permite s3:PutObject solo en ese bucket y adjunta el rol a la instancia. La aplicación obtiene credenciales temporales automáticamente y no hay claves que se puedan filtrar.

Consejo para el examen: Cuando un servicio de AWS (como EC2 o Lambda) necesita acceder a otro servicio de AWS, la respuesta es un rol de IAM, no claves de acceso guardadas en el servidor. Cuando varias personas necesitan los mismos permisos, la respuesta es un grupo de IAM.

Comprueba lo que sabes

Si una política permite s3:DeleteObject y otra política adjunta lo deniega explícitamente, ¿qué ocurre?

La acción se deniega. Un Deny explícito siempre prevalece sobre un Allow.

¿Cuál es la principal diferencia entre un usuario de IAM y un rol de IAM?

Un usuario tiene credenciales de largo plazo ligadas a una identidad; un rol no tiene credenciales de largo plazo y se asume para obtener credenciales temporales.
