El modelo de responsabilidad compartida de AWS: seguridad de la nube frente a seguridad en la nube

La seguridad en AWS es un trabajo compartido. El modelo de responsabilidad compartida (shared responsibility model) detalla qué partes cuida AWS y cuáles siguen siendo tuyas. Es una de las ideas más evaluadas en el examen Cloud Practitioner, y casi todas las preguntas de seguridad se vuelven más fáciles cuando la tienes clara.

AWS es responsable de la seguridad de la nube (security of the cloud). Eso significa proteger la infraestructura que ejecuta todos los servicios de AWS: los centros de datos físicos y sus guardias, el hardware, la red global y la capa de virtualización (el hipervisor) que separa las instancias de los clientes. AWS también opera y parchea el software de sus servicios administrados. No puedes visitar un centro de datos de AWS, y no necesitas preocuparte de que alguien robe un disco de un rack; ese es trabajo de AWS.

Tú, el cliente, eres responsable de la seguridad en la nube (security in the cloud). Eso abarca lo que pones en AWS y cómo lo configuras: tus datos y si están cifrados, la gestión de identidades y accesos (quién puede hacer qué), los sistemas operativos y aplicaciones de tus instancias EC2, incluidos sus parches, la configuración de red, como los security groups y las network ACLs, y las decisiones de cifrado del lado del cliente y del lado del servidor. Si dejas un bucket de Amazon S3 abierto al público, es un problema de configuración del cliente, no una falla de AWS.

Algunos controles son compartidos. La gestión de parches es compartida: AWS parchea la infraestructura y los servicios administrados, y tú parcheas tus sistemas operativos invitados y tus aplicaciones. La gestión de la configuración es compartida: AWS configura su infraestructura y tú configuras tus bases de datos, sistemas operativos y aplicaciones. La concientización y la capacitación también son compartidas: AWS capacita a sus empleados y tú capacitas a los tuyos.

Una forma sencilla de recordarlo: si puedes tocarlo en la consola o en la API y elegir su configuración, probablemente eres responsable de ello. Si es físico o está por debajo del hipervisor, le pertenece a AWS. La división cambia según el tipo de servicio, como verás en la siguiente lección, pero los datos del cliente y la gestión de accesos son siempre responsabilidad del cliente.

Términos clave

Security of the cloud (seguridad de la nube)
La responsabilidad de AWS sobre las instalaciones físicas, el hardware, la red y la capa de virtualización que ejecutan sus servicios.
Security in the cloud (seguridad en la nube)
La responsabilidad del cliente sobre los datos, las identidades, las configuraciones, los sistemas operativos y las aplicaciones que ejecuta en AWS.
Shared control (control compartido)
Un control en el que AWS y el cliente se encargan cada uno de una capa, como los parches, la gestión de la configuración y la capacitación.
Hypervisor (hipervisor)
El software de virtualización que ejecuta máquinas virtuales en hosts físicos y aísla a los clientes; AWS lo protege.
Ejemplo real

Los datos de una empresa se filtran porque un bucket de S3 estaba configurado para permitir lecturas públicas. En la revisión posterior al incidente, el equipo confirma que la infraestructura de AWS funcionó según lo diseñado; la política del bucket era una configuración del cliente, así que corregirla y evitar que se repita con S3 Block Public Access es responsabilidad del cliente.

Consejo para el examen: Los datos del cliente, los usuarios y permisos de IAM y las reglas de los security groups son siempre trabajo del cliente, sea cual sea el servicio. La seguridad física, la eliminación del hardware y el hipervisor son siempre trabajo de AWS.

Comprueba lo que sabes

¿Quién es responsable de parchear el sistema operativo invitado de una instancia de Amazon EC2?

El cliente. AWS parchea el host subyacente y el hipervisor; el cliente parchea el sistema operativo y las aplicaciones dentro de la instancia.

Nombra dos controles compartidos entre AWS y el cliente.

La gestión de parches, la gestión de la configuración y la concientización y capacitación son los ejemplos estándar.
