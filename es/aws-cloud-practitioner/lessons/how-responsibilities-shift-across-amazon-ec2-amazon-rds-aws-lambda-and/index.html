AWS Certified Cloud Practitioner CLF-C02

Cómo cambian las responsabilidades entre Amazon EC2, Amazon RDS, AWS Lambda y Amazon S3

El modelo de responsabilidad compartida no es una línea fija. Cuanto más administra AWS por ti, más responsabilidad pasa a AWS y menos queda de tu lado. Comparar cuatro servicios comunes deja claro ese cambio, y el examen a menudo pregunta 'quién hace qué' justamente para estos: Amazon Elastic Compute Cloud (Amazon EC2), Amazon Relational Database Service (Amazon RDS), AWS Lambda y Amazon Simple Storage Service (Amazon S3).

Amazon EC2 es infraestructura como servicio (IaaS). AWS protege el host físico, la red y el hipervisor. Tú eres responsable de casi todo lo que está por encima: elegir el sistema operativo invitado y aplicarle parches, instalar y actualizar las aplicaciones, configurar cualquier firewall basado en el host y tus security groups, administrar los permisos de AWS Identity and Access Management (IAM) y los pares de claves, y proteger, cifrar y respaldar tus datos. EC2 te da el mayor control y, por lo tanto, la mayor responsabilidad. AWS Systems Manager Patch Manager puede automatizar la aplicación de parches del sistema operativo, pero decidir usarlo y configurarlo sigue siendo tu trabajo.

Amazon RDS es un servicio de base de datos administrado. AWS asume el sistema operativo del host de la base de datos, la instalación del motor de base de datos, la aplicación de parches del motor y del sistema operativo durante una ventana de mantenimiento que tú eliges, la ejecución de copias de seguridad automatizadas y la conmutación por error Multi-AZ cuando la habilitas. Tú sigues administrando quién puede conectarse (security groups, usuarios de la base de datos y autenticación de base de datos con IAM donde se admite), si el almacenamiento está cifrado, qué configuración de parámetros y qué período de retención de copias de seguridad eliges, si la instancia es accesible públicamente, y los datos y las consultas en sí. No puedes iniciar sesión en el sistema operativo de una instancia estándar de RDS, lo cual es una pista de que el sistema operativo es trabajo de AWS.

AWS Lambda es cómputo sin servidor (serverless). Subes el código de tu función y AWS la ejecuta cuando llega un evento, así que AWS se encarga de los servidores, el sistema operativo, los parches del entorno de ejecución en los runtimes administrados, el escalado y la disponibilidad entre Zonas de Disponibilidad. Tu responsabilidad se reduce al código de tu función y sus dependencias de terceros, el rol de ejecución de IAM y sus permisos, la configuración como las variables de entorno y el acceso de red, el manejo de secretos y los datos que procesa tu código. Si tu código incluye una biblioteca vulnerable, aplicar parches a esa biblioteca es tu responsabilidad, no la de AWS.

Amazon S3 es un servicio de almacenamiento abstracto. AWS administra la infraestructura de almacenamiento, la durabilidad y la disponibilidad. Tú eres responsable de tus objetos y su clasificación, las políticas de bucket y el control de acceso, la configuración de S3 Block Public Access, las decisiones de cifrado más allá de la predeterminada, el control de versiones, Object Lock y las reglas de ciclo de vida, y el registro de los accesos. Una forma rápida de revisar una de tus configuraciones desde la línea de comandos es aws s3api get-public-access-block --bucket my-bucket, que muestra si el acceso público está bloqueado para ese bucket. El patrón en los cuatro servicios es una línea que se desliza. De EC2 a RDS y luego a Lambda y S3, AWS asume más capas: primero el hardware, después el sistema operativo y el motor de base de datos, y luego el entorno de ejecución y el escalado. Lo que nunca se mueve está en la parte superior de la pila: tus datos, tus identidades y permisos, y tus decisiones de configuración. Un hábito útil es dibujar la pila de cualquier servicio, desde las instalaciones abajo hasta los datos arriba, y marcar dónde termina AWS.

Veamos un ejemplo práctico. Un equipo ejecuta su sitio web en EC2 con una base de datos MySQL en la misma instancia. Una revisión de seguridad descubre que el sistema operativo lleva meses sin parches y que las copias de seguridad no se han probado. El equipo traslada la base de datos a RDS para que AWS aplique parches al motor y ejecute copias de seguridad automatizadas, y traslada el procesamiento de imágenes a Lambda para que no haya ningún servidor al que aplicar parches. Sus obligaciones restantes son los roles de IAM, las reglas de los security groups, la configuración de cifrado, su código y sus datos.

Errores comunes: suponer que AWS aplica parches al sistema operativo invitado en EC2 porque AWS 'es dueño del servidor'; suponer que RDS significa que ya no controlas el acceso de red ni el cifrado; suponer que Lambda elimina todo el trabajo de seguridad, cuando el código de la función, las dependencias y el rol de ejecución siguen siendo tuyos; y suponer que AWS protege automáticamente los buckets de S3. S3 bloquea el acceso público de forma predeterminada en los buckets nuevos y cifra los objetos nuevos de forma predeterminada, pero cualquiera con permiso puede cambiar esa configuración, y administrarla es tu responsabilidad.

Las preguntas del examen suelen nombrar un servicio y una tarea. '¿Quién aplica parches al sistema operativo de una instancia EC2?' es el cliente. '¿Quién aplica parches al motor de base de datos en RDS?' es AWS, dentro de la ventana de mantenimiento que tú defines. '¿Quién administra los servidores subyacentes de Lambda?' es AWS. '¿Quién configura las políticas de bucket o el cifrado de S3?' es el cliente. Cuando las opciones incluyen una tarea sobre datos o acceso en cualquier servicio, la respuesta es el cliente; cuando incluyen hardware, instalaciones o el hipervisor, la respuesta es AWS.

Términos clave

Infraestructura como servicio (IaaS)
Modelo en el que el proveedor suministra cómputo, almacenamiento y red virtuales, y el cliente administra el sistema operativo y todo lo que está por encima.
Servicio administrado (managed service)
Servicio en el que AWS opera la infraestructura y el software subyacentes, como el sistema operativo y el motor de base de datos en Amazon RDS.
Sin servidor (serverless)
Modelo, como AWS Lambda, en el que AWS administra los servidores, el entorno de ejecución y el escalado, y tú aportas el código y la configuración.
Ventana de mantenimiento (maintenance window)
Período semanal que eliges durante el cual AWS aplica parches a recursos administrados como las instancias de RDS.
Rol de ejecución (execution role)
Rol de IAM que asume una función Lambda para obtener permisos sobre otros servicios de AWS.
S3 Block Public Access
Configuración a nivel de cuenta y de bucket que impide que los datos de S3 se hagan públicos, y que controla el cliente.
Ejemplo real

Un inversionista le pregunta a una empresa emergente quién es responsable de aplicar parches. En sus servidores de aplicaciones EC2, la empresa aplica parches al sistema operativo cada semana con Systems Manager Patch Manager. En su base de datos Amazon RDS for PostgreSQL, AWS aplica parches al motor durante una ventana de mantenimiento dominical que la empresa eligió. En sus funciones Lambda, AWS se encarga del entorno de ejecución mientras la empresa analiza y actualiza las dependencias de su código. En S3, la empresa es responsable de las políticas de bucket y de la configuración de Block Public Access.

Consejo para el examen: El sistema operativo es la señal clave: en EC2 tú le aplicas parches; en RDS y Lambda lo hace AWS. En todos los servicios, tú configuras el acceso y proteges tus datos.

Comprueba lo que sabes

En Amazon RDS, ¿quién aplica parches al motor de base de datos?

AWS, durante la ventana de mantenimiento que selecciona el cliente.

En AWS Lambda, ¿qué responsabilidades de seguridad siguen siendo del cliente?

El código de la función y sus dependencias, el rol de ejecución de IAM y sus permisos, la configuración y los datos que procesa la función.

¿Cuál de EC2, RDS, Lambda y S3 le deja al cliente la mayor responsabilidad, y por qué?

EC2, porque es infraestructura como servicio y el cliente administra el sistema operativo invitado, las aplicaciones y la configuración de red.

¿Quién es responsable de la política de un bucket de S3 que contiene datos de clientes?

El cliente, porque la configuración del acceso y la protección de los datos son siempre responsabilidades del cliente.
