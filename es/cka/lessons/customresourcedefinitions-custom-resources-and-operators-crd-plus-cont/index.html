CustomResourceDefinitions, custom resources y operators (CRD más controlador)

La API de Kubernetes es extensible. Una CustomResourceDefinition (CRD) le enseña al API server un nuevo tipo de recurso, y desde ese momento puedes crear objetos de ese tipo (custom resources) con kubectl, guardarlos en etcd y protegerlos con RBAC, exactamente igual que los objetos integrados.

Una CRD vive en la API apiextensions.k8s.io/v1. Su nombre debe ser <plural>.<group>, por ejemplo backups.example.com. El spec declara el group, los names (plural, singular, kind y shortNames opcionales), el scope (Namespaced o Cluster) y una o más versions. Cada versión indica si está served, exactamente una está marcada como storage: true, y cada una tiene un schema OpenAPI v3 que el API server usa para validar los objetos.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.example.com
spec:
  group: example.com
  scope: Namespaced
  names: {plural: backups, singular: backup, kind: Backup, shortNames: [bk]}
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              schedule: {type: string}

Un custom resource por sí solo no hace nada; son solo datos almacenados. El comportamiento viene de un controlador que vigila esos objetos y actúa sobre ellos. Una CRD más un controlador que codifica conocimiento operativo (cómo desplegar, respaldar, escalar o actualizar una aplicación concreta) se llama operator. Por ejemplo, un operator de base de datos podría vigilar objetos Postgres y crear StatefulSets, Services y Jobs de backup que correspondan a cada uno.

Los operators normalmente se instalan con Helm o aplicando manifiestos, y la instalación tiene partes diferenciadas: las CRDs, un namespace, un ServiceAccount con permisos de RBAC y el Deployment del controlador. Las CRDs deben existir antes de aplicar cualquier custom resource que las use, por eso muchos proyectos las distribuyen como un archivo o paso separado. Verifica el resultado con kubectl get crd, kubectl api-resources --api-group=example.com, kubectl explain backup.spec y kubectl get backups -A.

Ten cuidado con los borrados: borrar una CRD borra todos los custom resources de ese tipo en el clúster. Además, si un controlador agrega finalizers a sus custom resources y el controlador se elimina primero, esos recursos pueden quedarse atascados en el borrado porque ya no queda nada que quite el finalizer.

Términos clave

CustomResourceDefinition
Un objeto que registra un nuevo tipo de recurso en el API server.
Custom resource (recurso personalizado)
Una instancia de un tipo definido por una CRD, guardada en etcd como cualquier objeto.
Operator
Un controlador más CRDs que automatiza la operación de una aplicación específica.
Finalizer
Una clave en un objeto que bloquea su borrado hasta que un controlador realiza la limpieza y la quita.
Ejemplo real

Una tarea dice que instales un operator y crees un custom resource Certificate. Aplicas primero el manifiesto de la CRD del operator, lo confirmas con kubectl get crd | grep cert, instalas el controlador y luego creas el recurso. kubectl describe certificate muestra las actualizaciones de estado del controlador, lo que demuestra que está reconciliando.

Consejo para el examen: Si kubectl apply dice 'no matches for kind', falta la CRD o su group/version no coincide con el apiVersion del objeto. Usa kubectl api-resources para ver exactamente qué kinds y groups conoce el clúster.

Comprueba lo que sabes

¿Cómo debe verse el metadata.name de una CRD?

El nombre en plural seguido del group, como backups.example.com.

¿Qué convierte una CRD en un operator?

Un controlador que vigila los custom resources y reconcilia recursos reales para que coincidan con ellos.

¿Qué les pasa a los custom resources existentes si borras su CRD?

Se borran todos junto con ella.
