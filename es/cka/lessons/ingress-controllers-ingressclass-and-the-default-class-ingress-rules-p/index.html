Ingress controllers, IngressClass y la clase por defecto; reglas de Ingress, tipos de ruta y TLS

Un Ingress es un objeto de API que describe el enrutamiento HTTP y HTTPS desde fuera del clúster hacia los Services, por hostname y ruta. Por sí solo no hace nada. Un Ingress controller, un proxy inverso como un controlador basado en NGINX, HAProxy o Traefik que se ejecuta como Pods, vigila los objetos Ingress y se configura para que coincidan. Kubernetes no incluye ninguno, así que instalar un controlador (normalmente con Helm) es el primer paso. El propio controlador se expone con un Service NodePort o LoadBalancer.

Como un clúster puede ejecutar varios controladores, cada Ingress indica el que quiere mediante spec.ingressClassName, que hace referencia a un objeto IngressClass. El campo spec.controller de la IngressClass identifica la implementación del controlador. Una IngressClass con la anotación ingressclass.kubernetes.io/is-default-class: "true" pasa a ser la predeterminada, y los Ingress creados sin nombre de clase se le asignan. Si no hay clase predeterminada ni nombre de clase, es posible que todos los controladores ignoren el Ingress. La antigua anotación kubernetes.io/ingress.class está obsoleta.

Cada regla tiene un host opcional y una lista de paths, cada una con un path, un pathType y un backend con el nombre y el puerto de un Service. Hay tres tipos de ruta. Exact coincide exactamente con la ruta de la URL y distingue mayúsculas de minúsculas. Prefix coincide por elementos de la ruta separados por /, así que /api coincide con /api y /api/v1 pero no con /apiv1. ImplementationSpecific deja la coincidencia en manos del controlador. Cuando coinciden varias rutas, gana la coincidencia más larga, y Exact le gana a Prefix a igual longitud. Un defaultBackend captura las solicitudes que no coinciden con ninguna regla.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: {name: shop, namespace: shop}
spec:
  ingressClassName: nginx
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service: {name: api, port: {number: 8080}}
      - path: /
        pathType: Prefix
        backend:
          service: {name: frontend, port: {number: 80}}

TLS se configura con una sección tls que lista los hosts y un secretName que apunta a un Secret de tipo kubernetes.io/tls en el mismo namespace que el Ingress, creado con kubectl create secret tls shop-tls --cert=tls.crt --key=tls.key. El controlador entonces termina TLS para esos hosts. Puedes crear Ingress sencillos de forma imperativa, por ejemplo kubectl create ingress shop --class=nginx --rule="shop.example.com/api*=api:8080,tls=shop-tls", donde un * al final significa Prefix.

El comportamiento específico de cada controlador, como la reescritura de URL, se configura con anotaciones cuyos nombres dependen del controlador. La API de Ingress es estable pero sus funciones están congeladas; las nuevas capacidades van a Gateway API. Para el troubleshooting, kubectl describe ingress muestra los backends resueltos y los eventos, la columna ADDRESS muestra si un controlador lo tomó, y los logs del Pod del controlador muestran los errores de configuración.

Términos clave

Ingress controller (controlador de Ingress)
Un proxy que se ejecuta en el clúster y que implementa los objetos Ingress.
IngressClass
Un objeto de alcance de clúster que vincula un Ingress con un controlador específico.
Default IngressClass (IngressClass predeterminada)
La clase con la anotación is-default-class en true, usada cuando un Ingress no define ingressClassName.
pathType
Coincidencia de rutas Exact, Prefix (por elementos) o ImplementationSpecific.
Ejemplo real

Un Ingress creado sin ingressClassName tiene el ADDRESS vacío y no enruta. kubectl get ingressclass muestra una sola clase, nginx, sin la anotación de predeterminada. Definir ingressClassName: nginx en el Ingress o anotar la clase como predeterminada hace que el controlador lo adopte.

Consejo para el examen: La coincidencia Prefix es por segmento de ruta, no por prefijo de cadena: /app coincide con /app/x pero no con /application. Y el Secret de TLS debe estar en el mismo namespace que el Ingress.

Comprueba lo que sabes

¿La ruta /shop con pathType Prefix coincide con /shopping?

No; Prefix coincide con elementos completos de la ruta, así que solo coincide con /shop y /shop/...

¿Qué hace que una IngressClass sea la predeterminada?

La anotación ingressclass.kubernetes.io/is-default-class con el valor "true".
