ConfigMaps y Secrets: creación, consumo como env y como volumen, objetos inmutables y reinicio de cargas de trabajo tras los cambios

Los ConfigMaps y los Secrets separan la configuración de las imágenes de contenedor. Un ConfigMap guarda datos clave-valor no sensibles; un Secret guarda valores sensibles como contraseñas, tokens y claves TLS. Sus datos solo están codificados en base64, lo cual no es cifrado, así que protege los Secrets con RBAC e, idealmente, con cifrado en reposo (encryption at rest) configurado en el API server.

Créalos de forma imperativa a partir de literales, archivos o archivos env. Los Secrets genéricos son el tipo más común; los Secrets tls contienen un certificado y una clave; los Secrets docker-registry contienen credenciales para descargar imágenes.

kubectl create configmap app-cfg --from-literal=MODE=prod --from-file=app.properties
kubectl create secret generic db-cred --from-literal=user=app --from-literal=password='S3cure!'
kubectl create secret tls web-tls --cert=tls.crt --key=tls.key
kubectl get secret db-cred -o jsonpath='{.data.password}' | base64 -d

Los Pods los consumen de dos maneras. Como variables de entorno, puedes referenciar claves individuales con env[].valueFrom.configMapKeyRef o secretKeyRef, o importar todas las claves con envFrom. Como volúmenes, cada clave se convierte en un archivo dentro del directorio de montaje, lo que resulta adecuado para archivos de configuración y certificados; puedes elegir claves específicas con items y definir los permisos de los archivos con defaultMode.

containers:
- name: app
  image: myapp:1.0
  envFrom:
  - configMapRef: {name: app-cfg}
  env:
  - name: DB_PASSWORD
    valueFrom: {secretKeyRef: {name: db-cred, key: password}}
  volumeMounts:
  - {name: cfg, mountPath: /etc/app, readOnly: true}
volumes:
- name: cfg
  configMap: {name: app-cfg}

Las actualizaciones se comportan distinto según el método, y esta es una distinción favorita del examen. Las variables de entorno se leen una sola vez cuando el contenedor arranca, así que cambiar el ConfigMap no afecta a un contenedor en ejecución. Los ConfigMaps y Secrets montados como volumen los refresca el kubelet después de un breve retraso, aunque la aplicación debe volver a leer el archivo para notarlo. Los volúmenes montados con subPath nunca se actualizan. La forma confiable de aplicar un cambio es kubectl rollout restart deployment/<name>.

Definir immutable: true en un ConfigMap o Secret impide cambiar sus datos. Protege contra ediciones accidentales y permite que el kubelet deje de vigilarlo, lo que reduce la carga del API server en clústeres grandes. Para cambiar un objeto inmutable debes borrarlo y volver a crearlo (o crear uno nuevo con otro nombre y actualizar la carga de trabajo para que lo referencie). Si un ConfigMap o Secret referenciado no existe, el Pod se queda en ContainerCreating o muestra CreateContainerConfigError, a menos que la referencia esté marcada como optional: true.

Términos clave

ConfigMap
Un objeto que guarda configuración no confidencial como pares clave-valor.
Secret
Un objeto para datos sensibles; por defecto los valores están codificados en base64, no cifrados.
envFrom
Importa todas las claves de un ConfigMap o Secret como variables de entorno.
Immutable ConfigMap/Secret (inmutable)
Un objeto con immutable: true cuyos datos no se pueden cambiar después de crearlo.
Ejemplo real

Actualizas la clave LOG_LEVEL de un ConfigMap que un Deployment consume mediante envFrom, pero los logs siguen siendo detallados. Ejecutar kubectl exec con env muestra el valor anterior, porque las variables de entorno quedan fijas al iniciar el contenedor. kubectl rollout restart deployment/api incorpora el nuevo valor.

Consejo para el examen: El consumo como variable de entorno nunca se actualiza en vivo; el consumo como volumen sí (excepto con subPath). Si una tarea dice 'haz que los Pods usen el nuevo valor', reinicia la carga de trabajo.

Comprueba lo que sabes

¿El base64 de un Secret es una forma de cifrado?

No, es solo una codificación; cualquiera que pueda leer el Secret puede decodificarlo.

¿Qué error podría mostrar un Pod que referencia en env una clave inexistente de un ConfigMap?

CreateContainerConfigError, a menos que la referencia sea opcional.

¿Cómo cambias los datos de un ConfigMap inmutable?

Bórralo y vuelve a crearlo, o crea un ConfigMap nuevo y apunta la carga de trabajo hacia él.
