Certified Kubernetes Administrator CKA (Kubernetes v1.35 curriculum)

Probar la conectividad con Pods temporales (busybox, nicolaka/netshoot), nslookup, curl y nc

Muchas tareas del CKA terminan con 'verifica que ...', y muchas tareas de troubleshooting empiezan con 'el Pod A no puede llegar a B'. La herramienta más rápida es un Pod desechable dentro del clúster, porque ve la red exactamente como la ven tus cargas de trabajo, incluidos el DNS y las NetworkPolicies.

kubectl run con --rm -it --restart=Never crea un Pod, conecta tu terminal y lo borra cuando sales. Ubícalo en el namespace correcto con -n y dale etiquetas con -l si una NetworkPolicy decide el acceso por etiqueta. También puedes ejecutar un solo comando en lugar de una shell.

kubectl run tmp --rm -it --restart=Never --image=busybox -- sh
kubectl run tmp --rm -it --restart=Never --image=busybox -n frontend -l app=web -- \
  wget -qO- -T 3 api.backend:8080/health
kubectl run dns --rm -it --restart=Never --image=busybox -- nslookup kubernetes.default
kubectl run net --rm -it --restart=Never --image=nicolaka/netshoot -- bash

busybox es diminuta y se descarga rápido. Incluye nslookup, wget, nc y ping, pero no curl, así que usa wget -qO- <url> para HTTP. nicolaka/netshoot es una imagen más grande repleta de herramientas de red: curl, dig, nslookup, nc, tcpdump, ip, ss, traceroute y más. Úsala cuando necesites detalle. Algunos entornos de examen pueden restringir qué imágenes se pueden descargar, así que siéntete cómodo con lo que te dé cada tarea.

Prueba por capas, para que una falla te diga algo. Primero el DNS: nslookup api.backend.svc.cluster.local debería devolver el ClusterIP; si falla, pasa al troubleshooting de DNS. Luego el Service: nc -zv -w 3 api.backend 8080 o curl -m 3 api.backend:8080 prueba el puerto a través de kube-proxy. Después un Pod directamente por su IP, obtenida de kubectl get pods -o wide, lo que evita el Service. Si la IP del Pod funciona pero el Service no, revisa los selectores, el targetPort y las EndpointSlices. Si ninguno funciona, sospecha de la aplicación, de una NetworkPolicy o del CNI.

Usa timeouts explícitos (-T para wget de busybox, -m para curl, -w para nc) para que una conexión bloqueada falle en segundos en lugar de quedarse colgada, lo que ahorra tiempo real en el examen. Un timeout normalmente indica un descarte por política o un problema de enrutamiento, mientras que 'connection refused' significa que un host respondió pero nada escucha en ese puerto.

También puedes probar desde un Pod existente con kubectl exec -it <pod> -- sh, si su imagen tiene herramientas, o adjuntar un contenedor de depuración con kubectl debug -it <pod> --image=busybox --target=<container>. El contenedor de depuración comparte el network namespace del Pod, y --target además le permite ver los procesos de ese contenedor. Acuérdate de limpiar todo lo que hayas creado sin --rm.

Términos clave

kubectl run --rm -it
Crea un Pod temporal interactivo que se borra cuando termina la sesión.
busybox
Una imagen mínima con herramientas básicas como nslookup, wget y nc, pero sin curl.
nicolaka/netshoot
Una imagen de troubleshooting con muchas herramientas de red, incluidas curl, dig y tcpdump.
Connection refused vs timeout (conexión rechazada frente a tiempo agotado)
Refused significa que nada escucha en el puerto; timeout normalmente significa que el tráfico se descarta o no es enrutable.
Ejemplo real

Los Pods del namespace frontend no pueden llegar al Service api en backend. Desde un Pod temporal de busybox etiquetado igual que el frontend, nslookup resuelve el nombre, pero nc -zv -w 3 api.backend 8080 agota el tiempo, y la misma prueba hacia la IP del Pod también. Revisar las NetworkPolicies de backend revela un default deny sin ninguna regla para el namespace frontend.

Consejo para el examen: Prueba siempre desde un Pod con el mismo namespace y las mismas etiquetas que el cliente real, o los resultados de las NetworkPolicies te engañarán. Y busybox tiene wget, no curl.

Comprueba lo que sabes

¿Qué combinación de flags crea un Pod temporal interactivo que se elimina al salir?

kubectl run <name> --rm -it --restart=Never --image=<image> -- <cmd>.

Si la IP de un Pod responde pero su Service no, ¿dónde deberías mirar?

En el selector, el port y el targetPort del Service, y en sus EndpointSlices.
