EndpointSlices, Services sin selectores, externalTrafficPolicy y sessionAffinity

El selector de un Service no es lo que realmente usa kube-proxy. El controlador de EndpointSlice evalúa el selector y escribe las IP y puertos de los Pods coincidentes en objetos EndpointSlice, y son kube-proxy, el DNS y los ingress controllers quienes los consumen. Las EndpointSlices reemplazaron a la antigua API Endpoints, que no podía escalar a Services muy grandes porque un solo objeto contenía todas las direcciones.

Cada EndpointSlice lleva la etiqueta kubernetes.io/service-name=<service> y contiene un número limitado de endpoints (100 por defecto), así que un Service grande tiene varias slices. Cada endpoint registra sus direcciones y condiciones: ready, serving y terminating. Los Pods que fallan su readiness probe siguen listados, pero no como listos, y kube-proxy deja de enviarles tráfico nuevo.

kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl describe endpointslice <name>

Un Service sin selector no recibe EndpointSlices automáticas. Eso es útil para apuntar un Service del clúster a algo fuera del clúster, como una base de datos en una IP fija, mientras los clientes siguen usando un nombre DNS de Service normal. Creas el Service con puertos pero sin selector y luego creas tú mismo una EndpointSlice con la etiqueta service-name, addressType: IPv4, las direcciones de los endpoints y nombres de puerto coincidentes.

apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: legacy-db-1
  labels: {kubernetes.io/service-name: legacy-db}
addressType: IPv4
ports:
- {name: pg, port: 5432, protocol: TCP}
endpoints:
- addresses: ["10.20.0.15"]

externalTrafficPolicy se aplica a los Services NodePort y LoadBalancer y controla el tráfico que llega desde fuera. Con Cluster (el predeterminado), cualquier nodo acepta el tráfico y puede reenviarlo a un Pod de otro nodo; la carga se reparte de forma pareja, pero la IP de origen se reemplaza por la del nodo, así que la aplicación ve una dirección de cliente incorrecta. Con Local, un nodo solo reenvía a Pods que están en él mismo, la IP de origen del cliente se conserva y no hay un salto extra, pero los nodos sin un Pod local descartan el tráfico (los balanceadores de carga en la nube usan un health check node port para evitarlos) y la carga puede quedar desigual. internalTrafficPolicy es el equivalente para el tráfico dentro del clúster.

sessionAffinity: ClientIP hace que kube-proxy envíe todas las conexiones de la misma IP de cliente al mismo Pod de backend, durante un tiempo definido en sessionAffinityConfig.clientIP.timeoutSeconds (10800 segundos, tres horas, por defecto). El valor predeterminado es None, que elige un backend por conexión. La afinidad es solo por IP, así que muchos clientes detrás de un mismo gateway NAT quedan todos pegados a un solo Pod.

Términos clave

EndpointSlice
Un objeto que lista un subconjunto de las direcciones, puertos y condiciones de readiness de los backends de un Service.
Selectorless Service (Service sin selector)
Un Service sin selector cuyas EndpointSlices gestionas manualmente.
externalTrafficPolicy: Local
Solo los Pods locales del nodo reciben el tráfico externo, conservando la IP de origen del cliente.
sessionAffinity: ClientIP
Enruta de forma consistente una IP de cliente dada al mismo Pod de backend.
Ejemplo real

Una aplicación web detrás de un Service NodePort registra a cada visitante con la IP de un nodo, lo que rompe su limitación de tasa. Definir externalTrafficPolicy: Local conserva las IP reales de los clientes. El equipo además ejecuta los Pods como un DaemonSet para que cada nodo tenga un endpoint local y no se descarte tráfico.

Consejo para el examen: Una EndpointSlice vacía significa que el selector no coincide con ningún Pod Ready; revisa las etiquetas y la readiness antes de culpar a kube-proxy. Para externalTrafficPolicy, recuerda: Local conserva la IP de origen, Cluster reparte la carga.

Comprueba lo que sabes

¿Qué etiqueta vincula una EndpointSlice con su Service?

kubernetes.io/service-name con el nombre del Service como valor.

¿Cuál es el trade-off de externalTrafficPolicy Local?

Conserva las IP de origen de los clientes y evita un salto extra, pero los nodos sin Pods locales no pueden atender el tráfico y la carga puede quedar desigual.
