kubeadm init (pod network CIDR, control-plane endpoint), instalación de un plugin CNI, kubeadm join y bootstrap tokens

Una vez preparados los hosts, kubeadm init convierte la primera máquina en un nodo del control plane. Genera una autoridad certificadora y certificados, escribe archivos kubeconfig, crea manifiestos de static Pods para el API server, etcd, el scheduler y el controller-manager, los inicia a través del kubelet e instala CoreDNS y kube-proxy.

Dos flags son los más importantes. --pod-network-cidr le indica al clúster qué rango de direcciones usarán los Pods; debe coincidir con lo que tu plugin de CNI tiene configurado y no debe solaparse con las redes de tus nodos ni de los Services. Por ejemplo, el manifiesto por defecto de Flannel espera 10.244.0.0/16. --control-plane-endpoint establece un nombre DNS o IP estable para el API server, normalmente la dirección de un balanceador de carga. Debes definirlo en el momento del init si alguna vez quieres agregar más nodos al control plane, porque queda incrustado en los certificados y en los archivos kubeconfig.

sudo kubeadm init --pod-network-cidr=10.244.0.0/16 \
  --control-plane-endpoint=k8s-api.lab.local:6443
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

Después del init, kubectl get nodes muestra el nodo como NotReady y los Pods de CoreDNS se quedan en Pending. Eso es lo esperado: todavía no hay red de Pods. Instala un plugin CNI (Container Network Interface) como Calico, Cilium o Flannel, normalmente aplicando su manifiesto o instalando su operator. Cuando los Pods del CNI están en ejecución y escriben su configuración en /etc/cni/net.d/, el nodo pasa a Ready y CoreDNS arranca.

Los worker nodes se unen con kubeadm join, usando el comando que init imprimió al final. Contiene el endpoint, un bootstrap token y un --discovery-token-ca-cert-hash. El token permite que el nuevo kubelet se autentique el tiempo justo para solicitar su propio certificado de cliente; el hash de la CA permite que el nodo que se une verifique que está hablando con el control plane real y no con un impostor.

Los bootstrap tokens expiran, por defecto después de 24 horas. Si necesitas agregar un nodo más adelante, crea un token nuevo y el comando completo con kubeadm token create --print-join-command. kubeadm token list muestra los tokens existentes y su vencimiento. Para unir un nodo adicional al control plane agregas --control-plane y un --certificate-key, que se explican en la lección de alta disponibilidad.

Términos clave

--pod-network-cidr
El rango de IP reservado para las direcciones de los Pods, del cual asigna el plugin CNI.
--control-plane-endpoint
Una dirección compartida y estable para el API server, necesaria para expandir a HA más adelante.
Bootstrap token (token de arranque)
Un token de corta duración que permite a un nodo que se une autenticarse para solicitar su certificado de kubelet.
discovery-token-ca-cert-hash
Un hash de la clave pública de la CA del clúster que el nodo que se une usa para verificar el control plane.
Ejemplo real

Tres días después de montar un clúster de laboratorio agregas un tercer worker, pero el comando de join que guardaste falla con un error de autenticación. Ejecutar kubeadm token create --print-join-command en el control plane te da un comando nuevo con un token válido, y el nodo se une.

Consejo para el examen: Nodos NotReady y CoreDNS en Pending justo después del init casi siempre significan que todavía no hay un plugin CNI instalado, no que el clúster esté roto.

Comprueba lo que sabes

¿Por qué --control-plane-endpoint debe definirse en el init si en el futuro quieres un clúster HA?

Se escribe en los certificados y kubeconfigs; cambiarlo después implica regenerarlos.

¿Cómo obtienes un comando de join que funcione cuando el token original ya expiró?

Ejecuta kubeadm token create --print-join-command en un nodo del control plane.
