Gateway API: GatewayClass, listeners y allowedRoutes del Gateway, parentRefs y matches de HTTPRoute y backendRefs con pesos; instalación de las CRDs y de un controlador

Gateway API es la forma más nueva y orientada a roles de gestionar el tráfico que entra al clúster, diseñada como sucesora de Ingress. Divide la configuración en recursos que pertenecen a distintas personas: el proveedor de infraestructura, el operador del clúster y los desarrolladores de aplicaciones.

Gateway API no viene integrada en Kubernetes; se distribuye como CRDs. Instalas las CRDs, normalmente el manifiesto del canal standard de una versión de Gateway API, y luego una implementación (un controlador) como Envoy Gateway, NGINX Gateway Fabric, Istio, Cilium o Contour, cada una con sus propias instrucciones de instalación. Verifica con kubectl get crd | grep gateway.networking.k8s.io y kubectl get gatewayclass.

Una GatewayClass es de alcance de clúster e indica en controllerName el controlador que la implementa, de forma muy parecida a una IngressClass. Un Gateway solicita un punto de entrada de tráfico usando una clase. Cada uno de sus listeners tiene un name, protocol (HTTP, HTTPS, TLS, TCP), port, un hostname opcional y, para HTTPS, una sección tls que referencia Secrets con certificados. allowedRoutes controla qué rutas pueden adjuntarse: namespaces.from es Same (predeterminado), All o Selector, y kinds puede limitar los tipos de ruta.

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: {name: web-gw, namespace: infra}
spec:
  gatewayClassName: example
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces: {from: All}
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: shop, namespace: shop}
spec:
  parentRefs:
  - {name: web-gw, namespace: infra, sectionName: http}
  hostnames: ["shop.example.com"]
  rules:
  - matches:
    - path: {type: PathPrefix, value: /api}
    backendRefs:
    - {name: api-v1, port: 8080, weight: 90}
    - {name: api-v2, port: 8080, weight: 10}

Un HTTPRoute se adjunta a un Gateway mediante parentRefs (nombre, namespace si es distinto y, opcionalmente, sectionName para elegir un listener). hostnames filtra por el encabezado Host. Cada regla tiene matches, por ruta (Exact, PathPrefix o RegularExpression), encabezados, parámetros de consulta o método; filters opcionales como modificación de encabezados, redirecciones o reescrituras de URL; y backendRefs que apuntan a Services y puertos. Los pesos dividen el tráfico de forma proporcional, lo que simplifica los despliegues canary: 90 y 10 envía aproximadamente el diez por ciento a v2.

Adjuntarse requiere el acuerdo de ambas partes: la ruta referencia el Gateway, y los allowedRoutes del Gateway deben permitir el namespace de la ruta. Un backendRef hacia un Service de otro namespace además necesita un ReferenceGrant en el namespace de destino. Cuando algo no funciona, haz kubectl describe del Gateway y del HTTPRoute y lee las condiciones de estado: Accepted y Programmed en el Gateway, y ResolvedRefs en las rutas, explican la mayoría de las fallas, como NotAllowedByListeners o BackendNotFound.

Términos clave

GatewayClass
Un recurso de alcance de clúster que indica el controlador que implementa los Gateways de esa clase.
Gateway
Una solicitud de un punto de entrada de tráfico con uno o más listeners.
HTTPRoute
Reglas de enrutamiento que se adjuntan a listeners de un Gateway mediante parentRefs y reenvían a backendRefs.
allowedRoutes
Ajuste del listener que controla qué namespaces y tipos de ruta pueden adjuntarse.
ReferenceGrant
Un objeto que permite referencias entre namespaces, como una ruta hacia el Service de otro namespace.
Ejemplo real

Un HTTPRoute en el namespace shop nunca recibe tráfico, y su estado muestra que el padre no lo aceptó con el motivo NotAllowedByListeners. El Gateway del namespace infra usa el allowedRoutes predeterminado, Same. Cambiar el listener a from: All (o a Selector con una etiqueta en shop) permite que la ruta se adjunte.

Consejo para el examen: Si una ruta se ignora, revisa ambos lados de la vinculación: parentRefs (incluidos sectionName y namespace) y los allowedRoutes del listener. Las condiciones de estado te dicen qué lado la rechazó.
