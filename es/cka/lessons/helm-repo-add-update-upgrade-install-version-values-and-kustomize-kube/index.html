Helm (repo add/update, upgrade --install, --version, values) y Kustomize (kubectl apply -k) para instalar componentes del clúster

Muchos componentes del clúster, como ingress controllers, metrics-server, plugins CNI y operators, se distribuyen como charts de Helm o bases de Kustomize. El CKA espera que sepas instalarlos y configurarlos con ambas herramientas.

Helm es un gestor de paquetes para Kubernetes. Un chart es un paquete de manifiestos con plantillas y un archivo values.yaml con los valores por defecto. Instalar un chart crea un release, una instancia con nombre que Helm registra en el namespace de destino. Primero registra un repositorio de charts y actualiza el índice local: helm repo add <name> <repo-url> y helm repo update. helm search repo <keyword> encuentra charts, y helm search repo <chart> --versions lista las versiones de un chart.

El comando individual más útil es helm upgrade --install: instala el release si no existe y lo actualiza si existe, lo que hace que los scripts y las respuestas del examen sean idempotentes. --version fija la versión del chart (es la versión del chart, que puede diferir de la versión de la aplicación). -n elige el namespace y --create-namespace lo crea si no existe. Sobrescribe valores con -f my-values.yaml o --set key=value; las fuentes posteriores prevalecen sobre las anteriores.

helm show values ingress-nginx/ingress-nginx > defaults.yaml
helm upgrade --install ingress ingress-nginx/ingress-nginx \
  -n ingress --create-namespace --version <chart-version> \
  --set controller.replicaCount=2
helm list -A
helm get values ingress -n ingress
helm history ingress -n ingress && helm rollback ingress 1 -n ingress

Kustomize tiene un enfoque distinto: sin plantillas, solo YAML plano más un kustomization.yaml que lista resources y aplica transformaciones, como definir un namespace, agregar un namePrefix, agregar etiquetas, cambiar tags en images, aplicar patches o generar ConfigMaps y Secrets. Viene integrado en kubectl. kubectl kustomize <dir> imprime el resultado renderizado y kubectl apply -k <dir> lo aplica. Los overlays (por ejemplo overlays/prod) referencian una base compartida y parchean solo lo que difiere por entorno.

# kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml
namespace: monitoring
images:
  - name: metrics-app
    newTag: "2.1"

Elige Helm cuando un proveedor distribuye un chart y principalmente necesitas definir valores; elige Kustomize cuando tienes manifiestos planos y necesitas ediciones repetibles. Se pueden combinar, pero para el examen basta con que domines cada uno: inspecciona los valores antes de instalar, fija las versiones y verifica después con helm list o kubectl get.

Términos clave

Chart
Un paquete de Helm con manifiestos de Kubernetes en plantillas y valores por defecto.
Release
Una instancia instalada y con nombre de un chart en un namespace, con su propio historial de revisiones.
helm upgrade --install
Instala un release si no existe o lo actualiza si ya existe.
kustomization.yaml
El archivo de Kustomize que lista recursos y transformaciones; se aplica con kubectl apply -k.
Ejemplo real

Una tarea te pide instalar un chart en la versión de chart 4.x en el namespace ingress con dos réplicas del controlador. Ejecutas helm repo update, confirmas la versión exacta con helm search repo --versions y luego helm upgrade --install con --version, -n, --create-namespace y --set. helm list -n ingress muestra el release desplegado.

Consejo para el examen: Los releases de Helm pertenecen a un namespace: helm list muestra solo el namespace actual, así que usa helm list -A cuando parezca que falta un release. Y --version se refiere a la versión del chart, no a la de la aplicación.

Comprueba lo que sabes

¿Por qué preferir helm upgrade --install en lugar de helm install en la automatización?

Funciona tanto si el release ya existe como si no.

¿Cómo previsualizas lo que producirá un directorio de Kustomize sin aplicarlo?

Ejecuta kubectl kustomize <dir>.
