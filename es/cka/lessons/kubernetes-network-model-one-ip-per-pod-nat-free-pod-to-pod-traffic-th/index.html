El modelo de red de Kubernetes: una IP por Pod, tráfico entre Pods sin NAT, el papel del plugin CNI y los CIDR de Pods y Services

Kubernetes simplifica la red para las aplicaciones estableciendo unas pocas reglas estrictas y dejando la implementación a un plugin. Entender las reglas te ayuda a razonar sobre cualquier problema de conectividad.

El modelo tiene tres requisitos. Cada Pod obtiene su propia dirección IP, compartida por todos los contenedores del Pod. Cada Pod puede comunicarse con cualquier otro Pod en cualquier nodo sin traducción de direcciones de red (NAT), así que la IP de origen que ve el receptor es la IP real del Pod que envía. Y los agentes de un nodo, como el kubelet, pueden llegar a todos los Pods de ese nodo. Dentro de un Pod, los contenedores comparten un network namespace, así que se comunican por localhost y no deben usar el mismo puerto. Un pequeño contenedor pause (sandbox) mantiene abierto ese namespace.

Kubernetes en sí no implementa estas reglas. Lo hace el plugin CNI (Container Network Interface). Cuando el kubelet crea el sandbox de un Pod, el runtime llama al plugin CNI, que crea una interfaz virtual en el network namespace del Pod, asigna una IP del rango del nodo y configura las rutas. Entre nodos, el plugin enruta el tráfico de los Pods de forma nativa (por ejemplo con BGP) o lo encapsula en un overlay como VXLAN. Sin un CNI que funcione, los Pods se quedan atascados en ContainerCreating y los nodos permanecen NotReady.

Dos rangos de direcciones no deben solaparse entre sí ni con la red de tus nodos. El Pod CIDR es el rango del que toman sus IP los Pods, definido con kubeadm init --pod-network-cidr (se convierte en el --cluster-cidr del controller-manager). Con el IPAM de nodos, cada nodo recibe una porción registrada en node.spec.podCIDR, aunque muchos CNIs gestionan su propia asignación. El Service CIDR es el rango de las IP virtuales de los Services, definido por el --service-cluster-ip-range del API server; el valor por defecto de kubeadm es 10.96.0.0/12, por eso el Service kubernetes suele ser 10.96.0.1 y CoreDNS suele ser 10.96.0.10.

kubectl get pods -o wide                     # IP de los Pods y nodos
kubectl get nodes -o jsonpath='{.items[*].spec.podCIDR}'
grep service-cluster-ip-range /etc/kubernetes/manifests/kube-apiserver.yaml
kubectl cluster-info dump | grep -m1 cluster-cidr

Las IP de los Services son distintas de las IP de los Pods: ninguna interfaz las posee y solo existen como reglas de reenvío programadas por kube-proxy (o un reemplazo como Cilium). Las IP de los Pods son direcciones reales y enrutables dentro de la red del clúster. Ten presente esa distinción: hacer ping a la IP de un Service a menudo falla aunque el Service funcione bien, mientras que hacer ping a la IP de un Pod normalmente debería funcionar.

Términos clave

Pod CIDR
El rango de direcciones del que se asignan las IP de los Pods, definido al crear el clúster.
Service CIDR
El rango de direcciones para los ClusterIP de los Services, definido por --service-cluster-ip-range.
Pause container (contenedor pause)
El contenedor sandbox que mantiene el network namespace compartido de un Pod.
Overlay network (red overlay)
Una encapsulación (como VXLAN) que transporta el tráfico de los Pods entre nodos a través de la red de los nodos.
Ejemplo real

Se construyó un clúster nuevo con un Pod CIDR de 192.168.0.0/16 mientras que los propios nodos están en 192.168.1.0/24. Los Pods de distintos nodos no pueden comunicarse y parte del tráfico de los nodos se enruta mal. Reconstruirlo con un Pod CIDR que no se solape, como 10.244.0.0/16, lo resuelve, lo que muestra por qué hay que planificar los rangos primero.

Consejo para el examen: Recuerda qué componente es dueño de cada rango: el Pod CIDR lo usan el CNI y el controller-manager; el Service CIDR, el API server y kube-proxy. No deben solaparse entre sí ni con la subred de los nodos.

Comprueba lo que sabes

¿Necesitan los Pods NAT para comunicarse con Pods de otros nodos?

No, el modelo de red exige comunicación entre Pods sin NAT.

¿Dónde encuentras el Service CIDR en un clúster de kubeadm?

En el flag --service-cluster-ip-range del manifiesto del static Pod de kube-apiserver.
