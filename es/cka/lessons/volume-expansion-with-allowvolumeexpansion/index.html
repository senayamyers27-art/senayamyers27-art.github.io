Expansión de volúmenes con allowVolumeExpansion

Las aplicaciones crecen y sus volúmenes terminan por llenarse. Kubernetes te permite agrandar un PersistentVolumeClaim en su lugar, sin copiar los datos a un volumen nuevo, siempre que el almacenamiento lo admita y el administrador lo haya permitido.

El permiso viene de la StorageClass: allowVolumeExpansion: true. A diferencia de la mayoría de los campos de la StorageClass, este se puede cambiar en una clase existente, por ejemplo con kubectl patch sc fast -p '{"allowVolumeExpansion": true}'. Si es false o no está, el API server rechaza cualquier intento de aumentar el tamaño de un PVC con un error que dice que el claim solo se puede expandir si su StorageClass lo permite. El driver subyacente también debe admitir la expansión; el flag no agrega una capacidad que el almacenamiento no tenga.

Para expandir, edita el claim, no el PV. Aumenta spec.resources.requests.storage en el PVC con kubectl edit pvc data o con un patch. El controlador de redimensionamiento y el driver CSI agrandan entonces el volumen del backend, actualizan la capacidad del PV y, por último, el kubelet del nodo donde está montado hace crecer el sistema de archivos.

kubectl get sc fast -o jsonpath='{.allowVolumeExpansion}'
kubectl patch pvc data -n app -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
kubectl get pvc data -n app -w           # CAPACITY se actualiza al terminar
kubectl describe pvc data -n app          # condiciones y eventos

La expansión ocurre en dos etapas, y puedes verlas en las condiciones del PVC. Primero el controlador redimensiona el volumen en sí (una condición Resizing). Luego hay que hacer crecer el sistema de archivos. Muchos drivers CSI admiten la expansión online, que hace crecer el sistema de archivos mientras el Pod sigue ejecutándose. Con drivers que solo admiten la expansión offline, el PVC muestra una condición FileSystemResizePending y el sistema de archivos se redimensiona la próxima vez que un Pod monte el volumen, así que reinicias el Pod. El status.capacity del PVC solo refleja el nuevo tamaño una vez que termina todo el proceso, mientras que spec muestra lo que pediste.

La reducción no está soportada. Disminuir el tamaño solicitado se rechaza. Si por accidente solicitas un tamaño mucho mayor del que querías, consulta la documentación de tu versión de Kubernetes sobre cómo recuperarse de fallas de expansión en lugar de intentar reducirlo.

Algunos límites para recordar: los PVs creados estáticamente sin StorageClass no se pueden expandir mediante este mecanismo, y un volumen solo puede crecer hasta donde lo permita su backend. Los volúmenes hostPath no aplican ningún límite real de tamaño y no admiten la expansión; su capacidad es solo una etiqueta.

Términos clave

allowVolumeExpansion
Flag de la StorageClass que permite agrandar los PVCs de esa clase.
Online expansion (expansión en línea)
Hacer crecer el sistema de archivos de un volumen mientras el Pod que lo usa sigue ejecutándose.
FileSystemResizePending
Una condición del PVC que indica que el sistema de archivos se redimensionará la próxima vez que un Pod lo monte.
Ejemplo real

Un PVC de base de datos de 10Gi está lleno al 95 por ciento. La clase ya tiene allowVolumeExpansion en true, así que aplicas un patch al PVC para llevarlo a 20Gi. kubectl describe pvc muestra Resizing y luego la columna CAPACITY muestra 20Gi, y df -h dentro del Pod confirma el sistema de archivos más grande sin reiniciar, porque el driver admite la expansión online.

Consejo para el examen: Expande el PVC, nunca el PV, y solo hacia arriba. Si la edición se rechaza, revisa primero allowVolumeExpansion en la StorageClass del claim.

Comprueba lo que sabes

¿Qué objeto editas para hacer crecer un volumen?

El PersistentVolumeClaim, aumentando spec.resources.requests.storage.

¿Puedes reducir el tamaño de un PVC después de expandirlo?

No, la reducción de PVCs no está soportada.
