RBAC: Roles, ClusterRoles, RoleBindings, ClusterRoleBindings, roles agregados e integrados, usuarios mediante CertificateSigningRequests y kubectl auth can-i

El control de acceso basado en roles (RBAC) decide qué puede hacer una identidad autenticada. Los permisos siempre son aditivos: no existen reglas de denegación, así que un usuario solo puede hacer lo que algún rol le otorga. Cada regla enumera API groups, recursos y verbos como get, list, watch, create, update, patch y delete.

Hay cuatro objetos. Un Role otorga permisos dentro de un namespace. Un ClusterRole es de alcance de clúster: puede cubrir recursos a nivel de clúster como nodes y PersistentVolumes, o ser un conjunto reutilizable de permisos de namespace. Un RoleBinding otorga un Role o un ClusterRole a sujetos (users, groups o ServiceAccounts) dentro de un namespace. Un ClusterRoleBinding otorga un ClusterRole en todo el clúster. Vincular un ClusterRole con un RoleBinding es un patrón común: defines 'leer pods' una vez y lo otorgas por namespace.

kubectl create role pod-reader -n dev --verb=get,list,watch --resource=pods
kubectl create rolebinding jane-read -n dev --role=pod-reader --user=jane
kubectl create clusterrolebinding ci-view --clusterrole=view --serviceaccount=ci:deployer
kubectl auth can-i list pods -n dev --as=jane
kubectl auth can-i --list --as=system:serviceaccount:ci:deployer -n ci

Kubernetes incluye ClusterRoles integrados: cluster-admin (todo), admin (casi todo en un namespace, incluido RBAC ahí), edit (leer y escribir la mayoría de los objetos, pero no roles ni bindings) y view (solo lectura, excluyendo Secrets). Varios de estos son ClusterRoles agregados. Un ClusterRole agregado tiene un aggregationRule con selectores de etiquetas, y el controller manager incorpora automáticamente las reglas de cualquier ClusterRole que tenga una etiqueta coincidente, como rbac.authorization.k8s.io/aggregate-to-view: "true". Así es como el instalador de un CRD puede extender el rol view a sus nuevos recursos.

Kubernetes no tiene objetos de usuario. Un usuario normal es simplemente quien presenta un certificado de cliente firmado por la CA del clúster; el common name (CN) del certificado es el nombre de usuario y los campos de organización (O) son los grupos. Para crear uno, genera una clave y una solicitud de firma de certificado con openssl (por ejemplo -subj "/CN=jane/O=dev"), envuélvela en un objeto CertificateSigningRequest con signerName: kubernetes.io/kube-apiserver-client y usages: [client auth], y pon el CSR codificado en base64 en spec.request. Luego ejecuta kubectl certificate approve jane, lee el certificado emitido desde .status.certificate, decodifícalo y agrégalo a un kubeconfig con kubectl config set-credentials y set-context.

Verifica con kubectl auth can-i. Usar --as suplanta otra identidad, y --as-group agrega grupos, así que puedes demostrar que un binding funciona sin cambiar de kubeconfig.

Términos clave

Role / ClusterRole
Conjuntos de reglas de permisos, de namespace o de alcance de clúster respectivamente.
RoleBinding / ClusterRoleBinding
Objetos que otorgan un rol a users, groups o ServiceAccounts, en un namespace o en todo el clúster.
Aggregated ClusterRole (ClusterRole agregado)
Un ClusterRole cuyas reglas se ensamblan automáticamente a partir de otros ClusterRoles que coinciden con un selector de etiquetas.
CertificateSigningRequest
Un objeto de API que le pide a un firmante, como el signer kube-apiserver-client, que emita un certificado.
Ejemplo real

Una desarrolladora llamada Jane necesita ver y borrar Pods solo en el namespace qa. Le emites un certificado mediante un CSR con CN=jane, creas un Role con get, list y delete sobre pods en qa, lo vinculas con un RoleBinding y lo confirmas con kubectl auth can-i delete pods -n qa --as=jane (yes) y -n prod (no).

Consejo para el examen: Un RoleBinding que referencia un ClusterRole igual solo otorga acceso en el namespace del RoleBinding. Recuerda también que, al suplantar, los sujetos ServiceAccount se escriben como system:serviceaccount:<namespace>:<name>.

Comprueba lo que sabes

¿Puede RBAC expresar 'todo excepto Secrets'?

No con una regla de denegación; RBAC es solo aditivo, así que debes otorgar exactamente los recursos que quieres.

¿Qué determina el nombre de usuario y los grupos de un usuario basado en certificado?

El CN del certificado es el nombre de usuario y cada campo O es un grupo.

¿Cómo verificas si el ServiceAccount builder del namespace ci puede crear Deployments ahí?

kubectl auth can-i create deployments -n ci --as=system:serviceaccount:ci:builder.
