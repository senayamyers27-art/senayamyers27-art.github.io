Certified Kubernetes Administrator CKA (Kubernetes v1.35 curriculum)

Interfaces de extensión: CRI (containerd, CRI-O, crictl), CNI (Calico, Cilium, Flannel) y drivers CSI

Kubernetes no ejecuta contenedores, ni conecta redes, ni adjunta discos por sí mismo. Define interfaces estándar y deja que los plugins hagan el trabajo. Conocer las tres interfaces te dice dónde buscar cuando algo por debajo de la API se rompe.

La Container Runtime Interface (CRI) es una API gRPC entre el kubelet y un container runtime. containerd y CRI-O son los runtimes CRI más comunes. Docker Engine ya no está soportado directamente por el kubelet desde que se eliminó dockershim. El kubelet se apunta al socket del runtime, como unix:///run/containerd/containerd.sock para containerd o unix:///var/run/crio/crio.sock para CRI-O.

crictl es la herramienta de depuración de CRI, y funciona incluso cuando el API server está caído porque se comunica con el runtime local. Configura su endpoint en /etc/crictl.yaml (runtime-endpoint:). Comandos clave: crictl ps -a (contenedores, incluidos los terminados), crictl pods, crictl images, crictl logs <container-id>, crictl inspect <id> y crictl rmi --prune. No está pensada para construir imágenes ni para crear cargas de trabajo de larga duración.

La Container Network Interface (CNI) especifica cómo un runtime le pide a un plugin que le dé al network namespace de un Pod una interfaz y una IP. El kubelet y el runtime leen la configuración de red de /etc/cni/net.d/ y los binarios de los plugins de /opt/cni/bin/. Si falta esa configuración, los Pods fallan con errores de red del sandbox y los nodos reportan NotReady. Calico ofrece redes enrutadas (opcionalmente con BGP) u overlays, y soporte completo de NetworkPolicy. Cilium usa eBPF en el kernel para redes, políticas y observabilidad, e incluso puede reemplazar a kube-proxy. Flannel es un overlay sencillo (normalmente VXLAN) fácil de instalar, pero que por sí solo no aplica NetworkPolicies.

La Container Storage Interface (CSI) permite a los proveedores de almacenamiento distribuir drivers fuera del código de Kubernetes. Un driver CSI suele tener un componente controlador (un Deployment o StatefulSet que crea, borra, adjunta y hace snapshots de volúmenes, con sidecars como el external provisioner) y un componente de nodo (un DaemonSet que monta los volúmenes en cada nodo). Puedes listar los drivers instalados con kubectl get csidrivers y ver el lado del nodo con kubectl get csinodes. Una StorageClass indica su driver CSI en el campo provisioner.

La lección práctica: los problemas de CRI aparecen como contenedores que no inician (revisa el servicio del runtime y crictl), los de CNI como Pods atascados en ContainerCreating o que no pueden comunicarse entre sí, y los de CSI como PVCs atascados en Pending o volúmenes que no logran adjuntarse o montarse.

Términos clave

CRI
La interfaz gRPC que usa el kubelet para controlar container runtimes como containerd y CRI-O.
crictl
Un cliente de línea de comandos para runtimes CRI, usado para depurar a nivel de nodo.
CNI
La especificación y los plugins que configuran las interfaces de red y las direcciones IP de los Pods.
CSI
La interfaz estándar para drivers de almacenamiento externos al árbol de Kubernetes que aprovisionan, adjuntan y montan volúmenes.
Ejemplo real

Los Pods nuevos en node02 se quedan en ContainerCreating con un evento que dice que el network plugin no está listo. En node02 encuentras /etc/cni/net.d/ vacío porque el Pod del DaemonSet del CNI de ese nodo está fallando. Corregir la toleration del DaemonSet le permite ejecutarse, escribe la configuración y los Pods arrancan.

Consejo para el examen: Si kubectl no está disponible, crictl es tu forma de ver lo que pasa en el nodo. Recuerda que Flannel por sí solo no aplica NetworkPolicy; una política que parece ignorada puede simplemente no tener un CNI que la haga cumplir.

Comprueba lo que sabes

¿Qué directorios contienen la configuración de CNI y los binarios de los plugins en un nodo?

/etc/cni/net.d para la configuración y /opt/cni/bin para los binarios.

¿Por qué crictl sigue funcionando cuando el API server está caído?

Se comunica directamente con el container runtime local por el socket CRI, no con el API server.
