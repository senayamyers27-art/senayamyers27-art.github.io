Tipos de Service: ClusterIP, NodePort (30000–32767), LoadBalancer (cloud controller o MetalLB), headless y ExternalName

Un Service da un nombre y una dirección estables a un conjunto cambiante de Pods, seleccionados por etiquetas. Su type decide quién puede llegar a él y cómo.

ClusterIP es el predeterminado. El Service obtiene una IP virtual del Service CIDR accesible solo dentro del clúster, más un nombre DNS como web.shop.svc.cluster.local. port es el puerto al que se conectan los clientes; targetPort es el puerto del contenedor (un número o un puerto con nombre) al que se reenvía el tráfico.

NodePort se construye sobre ClusterIP y además abre el mismo puerto en todos los nodos, del rango 30000 a 32767 a menos que se cambie el --service-node-port-range del API server. Los clientes fuera del clúster llegan a la IP de cualquier nodo en ese puerto. Puedes dejar que Kubernetes elija el puerto o definir nodePort explícitamente. LoadBalancer se construye sobre NodePort y pide que se aprovisione un balanceador de carga externo. En la nube, eso lo hace el cloud-controller-manager. En bare metal o en un laboratorio, nada lo hace a menos que instales algo como MetalLB, que asigna direcciones de un pool configurado. Sin eso, el EXTERNAL-IP del Service se queda en <pending>, aunque su NodePort y su ClusterIP siguen funcionando.

kubectl expose deployment web --port=80 --target-port=8080 --name=web          # ClusterIP
kubectl expose deployment web --port=80 --target-port=8080 --type=NodePort --name=web-np
kubectl create service nodeport web2 --tcp=80:8080 --node-port=30080
kubectl get svc -o wide

Un headless Service define clusterIP: None. No obtiene IP virtual y kube-proxy lo ignora; en cambio, el DNS devuelve las IP individuales de los Pods como registros A. Se usa cuando los clientes necesitan llegar a Pods específicos, sobre todo en los StatefulSets, cuyos Pods reciben nombres como db-0.db.ns.svc.cluster.local.

Un Service ExternalName no tiene selector ni hace ningún proxy. Simplemente hace que el DNS del clúster devuelva un registro CNAME que apunta a un hostname externo indicado en spec.externalName, por ejemplo para crear un alias de db.prod.svc.cluster.local hacia el nombre DNS de una base de datos gestionada. Como es solo DNS, los puertos no se remapean y los protocolos que verifican el hostname, como HTTPS, pueden verse afectados.

Cuando creas un Service con kubectl expose, copia el selector del recurso que expones, que es la forma más fácil de acertar con las etiquetas. Sea cual sea el tipo, un Service solo envía tráfico a los Pods que coinciden con su selector y están Ready, así que la primera verificación para un Service que no responde siempre es kubectl get endpointslices -l kubernetes.io/service-name=<svc>.

Términos clave

ClusterIP
El tipo de Service predeterminado, accesible solo dentro del clúster mediante una IP virtual.
NodePort
Un tipo de Service que además abre un puerto del rango 30000–32767 en todos los nodos.
LoadBalancer
Un tipo de Service que solicita un balanceador de carga externo a un cloud controller o a MetalLB.
Headless Service
Un Service con clusterIP None cuyo nombre DNS se resuelve directamente en las IP de los Pods.
ExternalName
Un Service que devuelve un CNAME de DNS hacia un hostname externo, sin proxy.
Ejemplo real

En un laboratorio de kubeadm en bare metal, un Service LoadBalancer se queda con EXTERNAL-IP <pending>. Aun así puedes llegar a él a través de la IP de cualquier nodo y el NodePort asignado. Instalar MetalLB con un pool de direcciones de la subred del laboratorio le da una IP externa.

Consejo para el examen: port es el puerto del Service, targetPort es el puerto del contenedor y nodePort es el puerto del nodo. Confundir port con targetPort es la causa más común de un Service que existe pero rechaza las conexiones.

Comprueba lo que sabes

¿Por qué un Service LoadBalancer muestra EXTERNAL-IP pending en un clúster bare metal?

Nada está aprovisionando balanceadores de carga; necesitas un cloud controller o algo como MetalLB.

¿Qué devuelve el DNS para un headless Service?

Las direcciones IP de sus Pods listos, en lugar de una única IP virtual.
