Certified Kubernetes Administrator CKA (Kubernetes v1.35 curriculum)

Problemas de nodos: NotReady, estado del kubelet y journalctl -u kubelet, configuración y certificados del kubelet, container runtime caído y condiciones del nodo (DiskPressure, MemoryPressure)

El troubleshooting es el dominio más grande del CKA, y un nodo en NotReady es una tarea clásica. El estado del nodo lo reporta su kubelet, así que un nodo NotReady casi siempre significa que el kubelet está detenido, mal configurado, no puede llegar al API server o reporta que su runtime o su red no están listos.

Empieza desde afuera: kubectl get nodes y kubectl describe node node01. La sección Conditions muestra Ready, MemoryPressure, DiskPressure, PIDPressure y, con algunos CNIs, NetworkUnavailable, cada una con un motivo y un mensaje. Si Ready es Unknown y el mensaje dice que el kubelet dejó de publicar el estado del nodo, el kubelet no se está comunicando en absoluto con el API server. Si Ready es False, el kubelet se está ejecutando pero reporta un problema, como que el container runtime está caído o que el CNI no está inicializado.

Luego conéctate por SSH al nodo y revisa el servicio del kubelet. Es una unidad de systemd, así que systemctl status kubelet te dice si se está ejecutando, y journalctl -u kubelet (agrega -f para seguirlo, o --no-pager | tail -50) muestra por qué falla. Si simplemente está detenido o deshabilitado, systemctl enable --now kubelet lo resuelve.

sudo systemctl status kubelet
sudo journalctl -u kubelet --no-pager | tail -50
sudo systemctl status containerd
sudo crictl info | head
cat /var/lib/kubelet/config.yaml
systemctl cat kubelet            # unidad y drop-ins, incluidos los flags de kubeadm
cat /var/lib/kubelet/kubeadm-flags.env

Las fallas de configuración comunes están en unos pocos archivos. /var/lib/kubelet/config.yaml es la KubeletConfiguration (cgroup driver, ruta de static Pods, DNS del clúster, ajustes de certificados). /etc/kubernetes/kubelet.conf es el kubeconfig del kubelet, incluida la dirección del API server. El drop-in de systemd (míralo con systemctl cat kubelet) y /var/lib/kubelet/kubeadm-flags.env agregan flags de línea de comandos como el endpoint del runtime. Una ruta, un puerto o una ubicación de binario equivocados, o un error de tipeo en cualquiera de ellos, aparecen claramente en el journal. Después de corregir, ejecuta systemctl daemon-reload si editaste un archivo de unidad, y luego systemctl restart kubelet.

Los certificados también importan. El certificado de cliente del kubelet, normalmente /var/lib/kubelet/pki/kubelet-client-current.pem, suele rotarse automáticamente. Si venció o la CA no coincide, el journal muestra errores x509 o unauthorized. Revisa el vencimiento con openssl x509 -noout -enddate -in <file>.

Si el kubelet se ejecuta pero el runtime está caído, el journal se queja de que no puede conectarse al socket de containerd; inicia containerd y revisa su propio journal. Por último, las condiciones de presión vienen de los umbrales de desalojo del kubelet. DiskPressure aparece cuando al sistema de archivos del nodo o al de imágenes le queda poco espacio; el kubelet hace recolección de basura de imágenes y puede desalojar Pods, y el nodo recibe un taint disk-pressure para que los Pods nuevos lo eviten. MemoryPressure, de forma similar, desencadena desalojos, empezando por los Pods que superan sus requests. Libera espacio o memoria y la condición desaparece.

Términos clave

NotReady
Estado del nodo cuando la condición Ready es False o Unknown.
journalctl -u kubelet
Muestra los logs del servicio kubelet, la fuente principal de errores a nivel de nodo.
Node conditions (condiciones del nodo)
Indicadores de estado como Ready, MemoryPressure, DiskPressure y PIDPressure que reporta el kubelet.
KubeletConfiguration
El archivo de configuración del kubelet, normalmente /var/lib/kubelet/config.yaml.
Ejemplo real

node01 está NotReady con estado Unknown. En el nodo, systemctl status kubelet muestra que falló; el journal dice que no se puede cargar el archivo de configuración porque la ruta del drop-in apunta a /var/lib/kubelet/confg.yaml. Corregir el error de tipeo, ejecutar daemon-reload y reiniciar el kubelet devuelve node01 a Ready en menos de un minuto.

Consejo para el examen: Ready Unknown significa que el kubelet dejó de reportar; Ready False significa que reporta un problema. En ambos casos, systemctl status kubelet y journalctl -u kubelet en el nodo son tus dos primeros comandos.

Comprueba lo que sabes

¿Qué comando muestra la unidad de systemd del kubelet junto con sus archivos drop-in?

systemctl cat kubelet.

¿Qué hace el kubelet ante una condición DiskPressure?

Hace recolección de basura de imágenes y desaloja Pods si es necesario, y aplica un taint al nodo para mantener alejados los Pods nuevos.
