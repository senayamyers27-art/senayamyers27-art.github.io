Certified Kubernetes Administrator CKA (Kubernetes v1.35 curriculum)

Actualizaciones del clúster con kubeadm: una versión minor a la vez, upgrade plan/apply/node, drain, actualización del kubelet, uncordon y version skew

Kubernetes publica una nueva versión minor (1.x) con regularidad, y kubeadm solo admite actualizar una versión minor a la vez. Para pasar de 1.33 a 1.35, primero actualizas a 1.34. Las versiones patch dentro de una minor se pueden saltar. El examen con frecuencia te da un clúster una minor atrás y te pide actualizar el control plane y un worker.

Las reglas de version skew (desfase de versiones) explican el orden. El kubelet nunca debe ser más nuevo que el API server, y puede quedarse atrás algunas versiones minor. kubectl debe estar dentro de una versión minor respecto al API server. Por eso siempre actualizas primero el control plane y después los nodos.

En el primer nodo del control plane, actualiza el paquete de kubeadm a la versión objetivo exacta, luego revisa el plan y aplícalo. kubeadm upgrade plan verifica que el clúster se pueda actualizar y muestra las versiones disponibles. kubeadm upgrade apply v1.X.Y actualiza los manifiestos de static Pods, CoreDNS y kube-proxy, y renueva los certificados. En los nodos adicionales del control plane ejecutas kubeadm upgrade node en lugar de apply.

# control plane (Debian/Ubuntu, ajusta la versión)
sudo apt-mark unhold kubeadm && sudo apt-get install -y kubeadm='1.X.Y-*' && sudo apt-mark hold kubeadm
sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.X.Y
kubectl drain cp1 --ignore-daemonsets
sudo apt-mark unhold kubelet kubectl && sudo apt-get install -y kubelet='1.X.Y-*' kubectl='1.X.Y-*' && sudo apt-mark hold kubelet kubectl
sudo systemctl daemon-reload && sudo systemctl restart kubelet
kubectl uncordon cp1

Cada worker sigue un patrón similar. Desde una máquina con kubectl, haz drain del nodo para que sus Pods se muevan a otro lado: kubectl drain node01 --ignore-daemonsets (agrega --delete-emptydir-data si hay Pods que usan emptyDir). En el worker, actualiza el paquete de kubeadm y ejecuta sudo kubeadm upgrade node, que actualiza la configuración local del kubelet. Luego actualiza los paquetes de kubelet y kubectl, recarga systemd y reinicia el kubelet. Por último, haz uncordon del nodo para que vuelva a aceptar Pods.

Ten en cuenta que los repositorios de paquetes de Kubernetes se publican por versión minor, así que pasar a una nueva minor puede requerir cambiar la definición del repositorio en cada nodo antes de que aparezcan los nuevos paquetes. Verifica con kubectl get nodes: la columna VERSION muestra la versión del kubelet de cada nodo, que es la forma más fácil de confirmar que un nodo realmente terminó.

Términos clave

kubeadm upgrade plan
Verifica si se puede actualizar y lista las versiones objetivo sin cambiar nada.
kubeadm upgrade apply
Actualiza los componentes del primer nodo del control plane a una versión dada.
kubeadm upgrade node
Actualiza los nodos adicionales del control plane o la configuración del kubelet de un worker.
Version skew policy (política de desfase de versiones)
Reglas sobre cuánto pueden diferir las versiones de los componentes; los kubelets nunca pueden ser más nuevos que el API server.
Ejemplo real

Te piden actualizar el control plane y node01 al siguiente patch de la siguiente minor: actualizas kubeadm en cp1, ejecutas plan y apply, haces drain y actualizas el kubelet en cp1, le haces uncordon y luego repites drain, kubeadm upgrade node, actualización del kubelet y uncordon en node01. kubectl get nodes muestra ambos en la nueva versión.

Consejo para el examen: Actualizar el paquete no basta: olvidar systemctl daemon-reload && systemctl restart kubelet deja al nodo reportando la versión anterior. Recuerda también: upgrade apply solo en el primer nodo del control plane y upgrade node en todos los demás.

Comprueba lo que sabes

¿Puedes actualizar directamente de 1.33 a 1.35 con kubeadm?

No; se actualiza una minor a la vez, de 1.33 a 1.34 y luego de 1.34 a 1.35.

¿Por qué se actualiza el control plane antes que los kubelets de los workers?

La version skew policy prohíbe que un kubelet sea más nuevo que el API server.
