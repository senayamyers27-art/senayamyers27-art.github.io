Problemas del control plane: manifiestos de static Pods, crictl ps/logs cuando el API server está caído, síntomas del scheduler y del controller-manager, y salud de etcd con etcdctl

En un clúster de kubeadm, los componentes del control plane son static Pods definidos en /etc/kubernetes/manifests. Cuando uno se rompe, la causa suele ser una mala edición de su manifiesto: un error de tipeo en un flag, una ruta de certificado equivocada, un puerto incorrecto, una imagen inválida o un error de indentación en el YAML. La habilidad consiste en averiguar qué componente está roto y leer sus logs, incluso cuando kubectl no funciona.

Si el API server está caído, kubectl falla con 'connection refused' en el puerto 6443 o agota el tiempo. No puedes usar kubectl logs, así que ve al nodo del control plane y usa directamente el container runtime. crictl ps -a lista todos los contenedores, incluidos los terminados; un componente que se sigue cayendo muestra un contador de intentos creciente o un estado Exited. crictl logs <container-id> muestra por qué. Si no existe ningún contenedor, el kubelet ni siquiera pudo analizar el manifiesto, así que revisa journalctl -u kubelet en busca de errores sobre el archivo del static Pod. Los logs de los contenedores también están en disco en /var/log/pods/ y /var/log/containers/.

sudo crictl ps -a | grep -E 'apiserver|etcd|scheduler|controller'
sudo crictl logs <container-id> 2>&1 | tail -20
sudo journalctl -u kubelet | grep -i manifest | tail
sudo ls /var/log/pods/ | grep kube-apiserver

Errores típicos del API server: no puede llegar a etcd (URL de --etcd-servers equivocada o flags de certificados de etcd incorrectos), no existe la ruta de un archivo de certificado o de clave, o un flag está mal escrito. Después de corregir el manifiesto, espera: el kubelet detecta el cambio, y el API server puede tardar un minuto en estar listo.

El scheduler y el controller-manager fallan de forma más silenciosa, porque kubectl sigue funcionando. Reconócelos por sus síntomas. Scheduler caído: los Pods nuevos se quedan en Pending sin nodo y sin eventos FailedScheduling. Controller-manager caído: escalar un Deployment no crea Pods, los Deployments nuevos no obtienen ReplicaSet, las EndpointSlices no se actualizan y los nodos caídos no se marcan ni se limpian. Revisa con kubectl get pods -n kube-system y kubectl logs -n kube-system kube-controller-manager-<node>, o con kubectl describe para ver los motivos de las caídas. Las fallas comunes son rutas de kubeconfig equivocadas (/etc/kubernetes/scheduler.conf, controller-manager.conf) o un nombre de comando incorrecto en el manifiesto.

La salud de etcd se puede verificar con etcdctl usando los mismos flags de certificados que para los backups. endpoint health informa si un miembro responde, endpoint status -w table muestra el líder, el tamaño de la base de datos y el índice raft, y member list muestra los miembros. Si el directorio de datos o el hostPath de etcd están mal, etcd puede arrancar vacío o fallar, y el API server pierde sus datos o no puede arrancar.

sudo ETCDCTL_API=3 etcdctl --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint health

Antes de editar cualquier manifiesto, cópialo a una ubicación de respaldo fuera del directorio de manifiestos. Una copia que quede dentro del directorio se iniciaría como un segundo Pod.

Términos clave

crictl ps -a
Lista todos los contenedores de un nodo desde el runtime, incluidos los terminados.
crictl logs
Lee los logs de un contenedor directamente desde el runtime; útil cuando el API server está caído.
etcdctl endpoint health
Verifica si un miembro de etcd está respondiendo.
/var/log/pods
Directorio en disco donde el kubelet guarda los archivos de log de los contenedores por Pod.
Ejemplo real

Después de que un compañero cambió las rutas de certificados del API server, kubectl informa connection refused. crictl ps -a muestra que el contenedor kube-apiserver se cierra repetidamente, y crictl logs dice que un archivo en /etc/kubernetes/pki no existe por un nombre de archivo mal escrito. Corregir la ruta en kube-apiserver.yaml devuelve la API.

Consejo para el examen: Si no hay ningún contenedor en crictl ps -a, el manifiesto no se pudo analizar (revisa el journal del kubelet); si el contenedor se cae, el componente arrancó pero rechazó su configuración (revisa crictl logs).

Comprueba lo que sabes

¿Cómo lees los logs del API server cuando kubectl no puede conectarse?

En el nodo del control plane, encuentra su contenedor con crictl ps -a y ejecuta crictl logs <id>, o lee los archivos en /var/log/pods.

¿Qué síntoma sugiere que el controller-manager está caído?

Los Deployments o ReplicaSets no crean ni reemplazan Pods aunque el API server funcione.
