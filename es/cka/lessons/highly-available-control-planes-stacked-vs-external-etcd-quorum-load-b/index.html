Control planes de alta disponibilidad: etcd stacked vs externo, quorum, balanceador de carga frente a los API servers, --upload-certs y --certificate-key

Un único nodo de control plane es un punto único de falla: si muere, los Pods en ejecución siguen funcionando, pero no se puede cambiar, programar ni reparar nada. Un control plane de alta disponibilidad (HA) ejecuta varios nodos de control plane para que el clúster sobreviva a la pérdida de uno.

kubeadm admite dos topologías. En una topología stacked (apilada), cada nodo del control plane ejecuta su propio miembro de etcd junto al API server, el scheduler y el controller-manager. Necesita menos máquinas y es lo que kubeadm configura por defecto, pero perder un nodo elimina a la vez una instancia del control plane y un miembro de etcd. En una topología de etcd externo, etcd se ejecuta en sus propios hosts dedicados y los nodos del control plane se conectan a él. Separa los dos dominios de falla y te permite dimensionar etcd por separado, a costa de más máquinas y más configuración (le das a kubeadm los endpoints y certificados de etcd en un archivo de configuración).

etcd usa el algoritmo de consenso Raft, que necesita un quorum, es decir, una mayoría de miembros, para aceptar escrituras. El quorum para n miembros es floor(n/2) + 1. Tres miembros toleran una falla; cinco toleran dos. Cuatro miembros siguen tolerando solo una, por eso los clústeres de etcd usan tamaños impares. Si se pierde el quorum, etcd deja de aceptar escrituras y el API server no puede cambiar nada, aunque algunos miembros estén sanos.

Los API servers no tienen estado y están todos activos a la vez, así que los clientes llegan a ellos a través de un balanceador de carga (por ejemplo HAProxy con keepalived, o un balanceador de carga en la nube) que escucha en el puerto 6443 y reenvía a todos los nodos del control plane. La dirección de ese balanceador es lo que pasas como --control-plane-endpoint. El scheduler y el controller-manager son distintos: se ejecutan en todos los nodos del control plane, pero usan leader election (elección de líder), así que solo una instancia de cada uno está activa a la vez y las demás esperan para tomar el relevo.

Unir nodos adicionales al control plane requiere compartir la CA del clúster y las claves de service-account. kubeadm puede hacerlo por ti. kubeadm init --control-plane-endpoint=LB:6443 --upload-certs cifra esos certificados, los guarda en el Secret kubeadm-certs en kube-system e imprime una certificate key. Los demás nodos del control plane se unen con kubeadm join LB:6443 --token ... --discovery-token-ca-cert-hash ... --control-plane --certificate-key <key>.

Los certificados subidos se borran automáticamente después de poco tiempo (dos horas por defecto), así que si agregas un nodo al control plane más adelante, vuelve a subirlos con kubeadm init phase upload-certs --upload-certs, que imprime una nueva certificate key. Sin la clave, la alternativa es copiar manualmente los archivos de certificados al nuevo nodo.

Términos clave

Stacked etcd (etcd apilado)
Topología en la que cada nodo del control plane también ejecuta un miembro de etcd.
External etcd (etcd externo)
Topología en la que etcd se ejecuta en hosts separados del control plane.
Quorum
Una mayoría de miembros de etcd, floor(n/2)+1, necesaria para confirmar escrituras.
--certificate-key
La clave usada para descifrar los certificados del control plane subidos con --upload-certs al unirse como nodo del control plane.
Leader election (elección de líder)
Mecanismo que mantiene activos un solo scheduler y un solo controller-manager entre los nodos del control plane.
Ejemplo real

Un control plane stacked de tres nodos pierde cp2 por una falla de disco. etcd todavía tiene dos de tres miembros, así que el quorum se mantiene, el balanceador deja de enviar tráfico al API server caído de cp2 y el scheduler líder en cp1 sigue ubicando Pods. El equipo reconstruye cp2 generando una nueva certificate key y ejecutando join con --control-plane.

Consejo para el examen: Domina las cuentas del quorum: 3 miembros sobreviven a 1 falla, 5 sobreviven a 2, y agregar un cuarto miembro a tres no mejora la tolerancia a fallas. Recuerda también que el scheduler y el controller-manager son activo/pasivo, mientras que los API servers son activo/activo.

Comprueba lo que sabes

¿Cuántas fallas de miembros puede tolerar un clúster de etcd de cinco miembros?

Dos, porque el quorum es tres.

¿Qué flag de kubeadm init comparte los certificados para que otros nodos del control plane se unan sin copiar archivos?

--upload-certs, que imprime la certificate key que se usa con join --certificate-key.

¿Cuál es el principal trade-off del etcd externo frente al stacked?

Mejor aislamiento de fallas a cambio de más hosts y más complejidad de configuración.
