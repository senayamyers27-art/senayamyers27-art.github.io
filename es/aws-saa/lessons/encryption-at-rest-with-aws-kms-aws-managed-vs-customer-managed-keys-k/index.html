Cifrado en reposo con AWS KMS: claves administradas por AWS vs por el cliente, key policies, envelope encryption y S3 SSE-S3, SSE-KMS y SSE-C

AWS Key Management Service (KMS) crea y controla las claves que se usan para cifrar datos en reposo en todos los servicios de AWS. Las claves de KMS nunca salen del servicio sin cifrar; KMS realiza las operaciones criptográficas dentro de módulos de seguridad de hardware (HSM), y cada uso de una clave queda registrado en CloudTrail. El examen espera que sepas qué tipo de clave elegir y cómo se controla el acceso a las claves.

Hay tres modelos de propiedad. Las AWS owned keys (claves propiedad de AWS) las usan internamente los servicios y nunca las ves. Las AWS managed keys (claves administradas por AWS), con alias como aws/s3 o aws/ebs, las crea un servicio en tu cuenta la primera vez que lo usas; puedes verlas y auditar su uso, pero no puedes cambiar su key policy, y AWS las rota automáticamente. Las customer managed keys (claves administradas por el cliente) las creas tú: controlas la key policy, los grants y la rotación automática, y puedes deshabilitar la clave o programar su eliminación. Elige customer managed keys cuando necesites tu propio control de acceso, uso entre cuentas o la capacidad de cortar el acceso deshabilitando la clave.

Cada clave de KMS tiene una key policy, una política basada en recursos, y es el control de acceso principal. A diferencia de la mayoría de los recursos, las políticas de IAM por sí solas no pueden otorgar acceso a una clave de KMS a menos que la key policy lo permita; la key policy predeterminada lo hace dando acceso al principal root de la cuenta, lo que delega en IAM. Para el uso entre cuentas, la key policy debe permitir a la otra cuenta, y la política de IAM de esa cuenta también debe permitir el uso. Los grants proporcionan permisos temporales y programáticos, a menudo usados por servicios como EBS.

KMS solo puede cifrar directamente cargas pequeñas (hasta 4 KB), así que los servicios usan envelope encryption (cifrado de sobre). El servicio llama a GenerateDataKey y recibe una data key en texto plano y la misma clave cifrada con la clave de KMS. Cifra los datos localmente con la data key en texto plano, descarta esa clave de la memoria y guarda la data key cifrada junto a los datos. Para descifrar, envía la data key cifrada a KMS, recibe el texto plano y descifra localmente. Esto evita enviar datos masivos por la red hacia KMS y lo hace rápido.

Amazon S3 ofrece tres opciones de cifrado del lado del servidor. SSE-S3 usa claves administradas completamente por S3 y es la opción predeterminada para objetos nuevos. SSE-KMS usa una clave de KMS, lo que agrega control mediante key policy, registros de CloudTrail del uso de la clave y la posibilidad de deshabilitarla; con tasas altas de solicitudes, las S3 Bucket Keys reducen el número de llamadas a KMS y su costo. SSE-C usa una clave que el cliente proporciona en cada solicitud por HTTPS; S3 la usa y la descarta, así que debes administrarla y nunca perderla. El cifrado del lado del cliente, donde los datos se cifran antes de subirlos, es la cuarta opción cuando AWS nunca debe ver el texto plano.

Términos clave

Customer managed key (clave administrada por el cliente)
Una clave de KMS que creas y controlas, incluidas su key policy, rotación, deshabilitación y eliminación.
Key policy (política de clave)
La política basada en recursos de una clave de KMS, que es el control principal sobre quién puede usarla y administrarla.
Envelope encryption (cifrado de sobre)
Cifrar los datos con una data key y luego cifrar esa data key con una clave de KMS.
SSE-KMS
Cifrado del lado del servidor de S3 con una clave de KMS, con uso de clave auditable y control mediante key policy.
Ejemplo real

Una empresa de salud debe demostrar quién usó las claves que protegen los archivos de los pacientes y debe poder revocar el acceso al instante. Crea una customer managed key de KMS, otorga el uso solo al rol de la aplicación en la key policy, configura el cifrado predeterminado del bucket como SSE-KMS con una S3 Bucket Key y revisa los eventos de KMS en CloudTrail.

Consejo para el examen: Auditoría del uso de la clave, control de la key policy o capacidad de deshabilitar la clave: SSE-KMS con una customer managed key. El cliente debe proporcionar y conservar la clave por sí mismo: SSE-C. Lo más simple sin gestión de claves: SSE-S3.

Comprueba lo que sabes

¿Por qué no puedes compartir con otra cuenta un snapshot de EBS cifrado con la AWS managed key aws/ebs?

Porque no puedes editar la política de una AWS managed key para dar acceso a otra cuenta. Vuelve a cifrarlo con una customer managed key y comparte esa clave.

¿Qué devuelve GenerateDataKey?

Una data key en texto plano para el cifrado local y una copia de esa data key cifrada con la clave de KMS, para guardarla junto con los datos.
