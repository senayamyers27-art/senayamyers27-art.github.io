Gestión de secretos: rotación en Secrets Manager vs SecureString de Systems Manager Parameter Store

Las aplicaciones necesitan contraseñas de bases de datos, claves de API y tokens. Escribirlos directamente en el código fuente, en Amazon Machine Images (AMIs), en imágenes de contenedores o en archivos de entorno es una falla de seguridad clásica: los secretos terminan en el control de versiones, en los registros y en los respaldos, cualquiera que pueda leer el artefacto puede leer el secreto, y cambiar un secreto obliga a volver a desplegar. La solución es guardar los secretos en un servicio administrado, dar al rol de IAM de cada aplicación permiso para leer solo sus propios secretos y obtenerlos en tiempo de ejecución. AWS te ofrece dos lugares administrados para hacerlo, y el examen te pide elegir entre ellos.

AWS Secrets Manager está hecho para secretos. Cifra cada secreto con una clave de KMS, controla el acceso con IAM y políticas de recursos, registra los accesos en CloudTrail y, lo más importante, rota los secretos automáticamente según un calendario. Para Amazon RDS, Aurora, Redshift y DocumentDB ofrece rotación administrada (managed rotation): cambia la contraseña en la base de datos y en el secreto al mismo tiempo, de modo que las aplicaciones que obtienen el secreto en tiempo de ejecución siguen funcionando. Para otros tipos de secretos, la rotación ejecuta una función Lambda que proporcionas tú o adaptas de las plantillas de AWS. El proceso de rotación usa etiquetas de etapa (staging labels) como AWSCURRENT y AWSPENDING para que el valor nuevo se pruebe antes de pasar a ser el actual. Secrets Manager también puede replicar secretos a otras regiones para recuperación ante desastres, y RDS puede administrar por ti la contraseña del usuario maestro en Secrets Manager. Cobra por secreto al mes y por llamada a la API.

AWS Systems Manager Parameter Store es un almacén jerárquico de datos de configuración, con nombres como /prod/app/db-host. Los parámetros son de tres tipos: String, StringList y SecureString. Un SecureString se cifra con una clave de KMS, ya sea la clave administrada por AWS aws/ssm o una clave administrada por el cliente. Los parámetros estándar no tienen cargo adicional de almacenamiento, y un nivel avanzado (advanced tier) agrega valores más grandes y políticas de parámetros, como notificaciones de vencimiento. Eso hace que Parameter Store sea atractivo para configuración y secretos simples. Sin embargo, Parameter Store no tiene rotación integrada; tendrías que construirla tú mismo con EventBridge y Lambda.

aws ssm get-parameter --name /prod/app/api-key --with-decryption
aws secretsmanager get-secret-value --secret-id prod/app/db

¿Cómo eliges? Si el requisito menciona rotación automática, sobre todo de credenciales de bases de datos, o replicación de secretos entre regiones, elige Secrets Manager. Si se trata de configuración general, feature flags o secretos que casi no cambian, y el costo importa, Parameter Store con SecureString está bien. Ambos se integran con las referencias dinámicas de CloudFormation, las definiciones de tareas de ECS, EKS y Lambda, así que las aplicaciones pueden cargar los valores al iniciar sin código que maneje archivos en texto plano. Parameter Store incluso puede hacer referencia a secretos de Secrets Manager mediante la ruta especial /aws/reference/secretsmanager/, de modo que una sola API puede leer ambos. Elijas el que elijas, el rol de la aplicación necesita permiso para leer el secreto y para usar la clave de KMS que lo cifra. Obtén los secretos en tiempo de ejecución y guárdalos en caché por poco tiempo, por ejemplo con la AWS Parameters and Secrets Lambda Extension o una biblioteca de caché del lado del cliente, en lugar de llamar a la API en cada solicitud, lo que agrega latencia, costo y riesgo de limitación (throttling).

Veamos un ejemplo práctico. Una auditoría de seguridad exige que la contraseña de la base de datos de producción cambie cada 30 días sin tiempo de inactividad, y encontró la contraseña en un archivo .env dentro de la imagen del contenedor. El equipo mueve las credenciales a Secrets Manager, habilita la rotación administrada para la base de datos RDS y concede al rol de tarea de ECS secretsmanager:GetSecretValue sobre ese único secreto. La definición de tarea inyecta el secreto como variable de entorno al iniciar, y la aplicación se reconecta con un valor nuevo cuando falla un inicio de sesión. Las configuraciones no sensibles, como el nombre de host de la base de datos y los feature flags, van a Parameter Store como parámetros String normales bajo /prod/app/.

Errores comunes: guardar secretos en parámetros String normales en lugar de SecureString; olvidar el permiso de KMS, de modo que el rol puede leer el parámetro pero no descifrarlo; guardar un secreto en caché para siempre, de modo que la aplicación falla después de la rotación; incrustar secretos en AMIs o imágenes; y elegir Parameter Store cuando la pregunta exige explícitamente rotación automática. Otra trampa es suponer que las variables de entorno por sí solas son un almacenamiento seguro; son solo un mecanismo de entrega.

La palabra clave del examen es rotación. 'Rotar automáticamente credenciales de bases de datos', 'rotar sin cambios en la aplicación' o 'replicar secretos a otra región' apunta a Secrets Manager. 'Almacenar valores de configuración de forma jerárquica', 'menor costo' o 'secretos que no necesitan rotación' apunta a Parameter Store con SecureString. 'Eliminar credenciales escritas en el código' apunta a cualquiera de los dos servicios más un rol de IAM que lea el valor en tiempo de ejecución.

Términos clave

Secrets Manager
Un servicio administrado que almacena, cifra, audita y rota automáticamente los secretos.
Parameter Store
Una función de Systems Manager para datos de configuración jerárquicos y secretos, sin rotación integrada.
SecureString
Un tipo de parámetro de Parameter Store cuyo valor se cifra con una clave de KMS.
Rotación (rotation)
Reemplazar periódicamente un secreto por un valor nuevo y actualizar todos los lugares que lo usan.
Rotación administrada (managed rotation)
La rotación de Secrets Manager para bases de datos compatibles, que no requiere código Lambda personalizado.
Referencia dinámica (dynamic reference)
Una referencia en una plantilla de CloudFormation que resuelve el valor de un parámetro o secreto en el momento del despliegue.
Ejemplo real

Cada una de las funciones Lambda de una empresa tenía una clave de API de un tercero en variables de entorno en texto plano, visible para cualquiera con acceso de lectura a la configuración de la función. El equipo guarda la clave como un secreto de Secrets Manager con una Lambda de rotación que solicita una clave nueva al proveedor cada trimestre, concede al rol de ejecución de cada función acceso de lectura solo a ese secreto y hace que las funciones obtengan el valor y lo guarden en caché durante unos minutos, de modo que una rotación surte efecto sin volver a desplegar.

Consejo para el examen: La palabra clave es rotación. La rotación automática de credenciales de bases de datos apunta a Secrets Manager; el almacenamiento de bajo costo de configuración y secretos estáticos apunta a Parameter Store con SecureString.

Comprueba lo que sabes

¿Qué servicio rota automáticamente las credenciales de RDS sin código personalizado?

AWS Secrets Manager, mediante la rotación administrada para RDS.

¿Qué cifra un parámetro SecureString?

Una clave de AWS KMS, ya sea la clave administrada por AWS aws/ssm o una clave administrada por el cliente.

Una aplicación puede llamar a ssm:GetParameter pero recibe un error al descifrar un SecureString. ¿Qué falta?

Permiso para usar la clave de KMS (kms:Decrypt) que cifra el parámetro.

¿Por qué las aplicaciones no deben guardar en caché indefinidamente un secreto que se rota?

Después de la rotación el valor anterior deja de funcionar, así que la aplicación debe actualizar el secreto periódicamente o cuando falle la autenticación.
