Desacoplamiento con Amazon SQS (standard vs FIFO, visibility timeout, dead-letter queues) y fan-out con SNS

Los sistemas fuertemente acoplados fallan juntos: si una capa web llama directamente a un procesador de pedidos y el procesador se vuelve lento, la capa web también se atasca. El desacoplamiento pone un búfer entre los componentes para que cada uno pueda escalar y fallar de forma independiente. Amazon Simple Queue Service (SQS) y Amazon Simple Notification Service (SNS) son los dos bloques de construcción clásicos.

SQS es una cola de mensajes totalmente administrada. Los productores envían mensajes; los consumidores los sondean (poll), los procesan y los eliminan. Los mensajes se almacenan de forma redundante y se conservan durante un período de retención configurable (hasta 14 días). Una standard queue (cola estándar) ofrece un rendimiento casi ilimitado con entrega at-least-once (al menos una vez) y orden de mejor esfuerzo, así que los consumidores deben tolerar duplicados y mensajes fuera de orden, lo que implica diseñar un procesamiento idempotente. Una FIFO queue, cuyo nombre debe terminar en .fifo, garantiza el orden first-in-first-out dentro de un message group y el procesamiento exactly-once (exactamente una vez) dentro de un intervalo de deduplicación, con un rendimiento menor que las colas estándar.

Cuando un consumidor recibe un mensaje, SQS lo oculta a los demás consumidores durante el visibility timeout (tiempo de visibilidad). Si el consumidor elimina el mensaje a tiempo, desaparece. Si el consumidor falla o tarda demasiado, el mensaje vuelve a ser visible y otro consumidor lo reintenta. Configura el visibility timeout más largo que tu tiempo normal de procesamiento; si a veces el procesamiento se alarga, el consumidor puede extenderlo con ChangeMessageVisibility. El long polling (sondeo largo), con un tiempo de espera de recepción de hasta 20 segundos, reduce las respuestas vacías y el costo. Una delay queue (cola de retraso) pospone la entrega de los mensajes nuevos.

Algunos mensajes nunca tendrán éxito, quizá porque están mal formados. Una dead-letter queue (DLQ, cola de mensajes fallidos) los atrapa: una redrive policy en la cola de origen indica que, después de que un mensaje se haya recibido cierta cantidad de veces (el maxReceiveCount), se mueva a la DLQ. Eso evita que los mensajes venenosos bloqueen el trabajo y te permite inspeccionarlos y reenviarlos (redrive) más tarde. La DLQ de una FIFO queue también debe ser FIFO.

SNS es un servicio de publicación-suscripción. Los publicadores envían un mensaje a un topic (tema), y SNS envía una copia a cada suscriptor: colas SQS, funciones Lambda, endpoints HTTP, correo electrónico o SMS. El patrón fan-out los combina: publicas una vez en un topic de SNS con varias colas SQS suscritas, y cada sistema posterior obtiene su propia copia duradera para procesarla a su propio ritmo. Las subscription filter policies permiten que cada suscriptor reciba solo los mensajes que le interesan. La access policy de la cola debe permitir que el topic le envíe mensajes.

Términos clave

Visibility timeout (tiempo de visibilidad)
El período durante el cual un mensaje de SQS recibido queda oculto a los demás consumidores mientras se procesa.
Dead-letter queue (cola de mensajes fallidos)
Una cola que recibe los mensajes que fallaron en su procesamiento más veces que el maxReceiveCount.
FIFO queue
Un tipo de cola de SQS que conserva el orden dentro de un message group y evita duplicados.
Fan-out
Publicar un mensaje una sola vez en un topic de SNS para que muchos suscriptores, a menudo colas SQS, reciban cada uno una copia.
Ejemplo real

Cuando se realiza un pedido, la capa web publica un mensaje en un topic de SNS. Tres colas SQS están suscritas: una para pagos, otra para envíos y otra para analítica. Durante una venta relámpago el servicio de envíos se queda atrás, pero sus mensajes esperan seguros en su cola mientras pagos y analítica se mantienen al día, y su Auto Scaling group escala según la profundidad de la cola.

Consejo para el examen: Mensajes procesados dos veces suelen significar que el visibility timeout es más corto que el tiempo de procesamiento. Orden estricto y sin duplicados significa FIFO. Un evento entregado a varios consumidores independientes significa fan-out de SNS hacia SQS.

Comprueba lo que sabes

Un consumidor tarda 90 segundos por mensaje, pero el visibility timeout es de 30 segundos. ¿Qué sucede?

El mensaje vuelve a ser visible antes de eliminarse, así que otro consumidor también lo procesa, generando duplicados. Aumenta el visibility timeout por encima del tiempo de procesamiento.

¿Cómo evitas que un mensaje mal formado se reintente para siempre?

Configura una dead-letter queue con una redrive policy y un maxReceiveCount.
