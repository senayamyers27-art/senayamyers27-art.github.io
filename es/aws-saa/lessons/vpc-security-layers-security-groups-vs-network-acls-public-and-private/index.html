Capas de seguridad de la VPC: security groups vs network ACLs, subredes públicas y privadas, NAT gateways, bastion hosts vs Session Manager

Una nube privada virtual (VPC) es tu propia red aislada en una región de AWS, definida por un bloque CIDR (Classless Inter-Domain Routing) IPv4 como 10.0.0.0/16. La divides en subredes, y cada subred vive en exactamente una zona de disponibilidad (AZ). La seguridad en una VPC se organiza en capas: hacia dónde puede enrutar una subred, qué firewalls están delante de cada recurso y cómo llegan los administradores a las máquinas. El examen espera que diseñes las tres de forma que solo el balanceador de carga quede expuesto a internet y todo lo demás permanezca privado.

Lo que hace pública a una subred es su tabla de rutas, no su nombre. Una subred pública tiene una ruta 0.0.0.0/0 que apunta a un internet gateway, y las instancias que están en ella necesitan una dirección IP pública o una Elastic IP para ser alcanzables. Una subred privada no tiene ruta hacia el internet gateway, así que nada en internet puede iniciar una conexión hacia ella. Las instancias en subredes privadas a menudo siguen necesitando acceso saliente a internet para parches y APIs externas. Un NAT (network address translation) gateway lo proporciona: lo colocas en una subred pública con una Elastic IP, y la tabla de rutas de la subred privada envía 0.0.0.0/0 hacia él. Permite conexiones salientes y sus respuestas, pero bloquea las conexiones entrantes desde internet. Un NAT gateway vive en una sola AZ, así que para alta disponibilidad despliegas uno por AZ y enrutas cada subred privada al gateway de su propia AZ. Las NAT instances son la alternativa antigua autogestionada, y para IPv6 un egress-only internet gateway cumple el mismo papel de solo salida.

Dos capas de firewall protegen los recursos. Los security groups se adjuntan a interfaces de red elásticas (elastic network interfaces) y, por lo tanto, a instancias, balanceadores de carga, bases de datos RDS y funciones Lambda dentro de una VPC. Tienen estado (stateful), lo que significa que el tráfico de retorno se permite automáticamente; admiten solo reglas de permiso; y todas las reglas se evalúan en conjunto. El origen de una regla puede ser otro security group, que es la forma limpia de decir que solo la capa web puede llegar a la capa de base de datos, aunque las instancias vayan y vengan. Las network ACLs (NACLs) se adjuntan a subredes y no tienen estado (stateless), así que debes permitir explícitamente el tráfico de retorno en los puertos efímeros (normalmente 1024-65535). Admiten reglas de permiso y de denegación y se evalúan en orden de número de regla, y gana la primera coincidencia. Usa una denegación en la NACL cuando necesites bloquear un rango de IP específico, porque los security groups no pueden denegar.

Los administradores necesitan una forma de llegar a las instancias privadas. La respuesta clásica es un bastion host: una instancia reforzada en una subred pública que permite SSH (Secure Shell) desde rangos de IP conocidos, y desde la cual saltas a las instancias privadas. Funciona, pero requiere parches, gestión de claves SSH y un puerto de entrada abierto. AWS Systems Manager Session Manager es la respuesta moderna: el SSM Agent de la instancia establece una conexión saliente hacia Systems Manager, y abres una shell desde la consola o con aws ssm start-session --target i-0123abcd, con IAM controlando quién puede conectarse. No hay puertos de entrada ni claves SSH, y las sesiones pueden registrarse en CloudWatch Logs o S3. La instancia necesita un instance profile con los permisos AmazonSSMManagedInstanceCore y una ruta hacia los endpoints de Systems Manager, a través de un NAT gateway o de interface endpoints. EC2 Instance Connect Endpoint es otra opción sin claves para entrar por SSH a instancias privadas.

Veamos un ejemplo práctico. Una aplicación de tres capas coloca su Application Load Balancer (ALB) en subredes públicas de dos AZs, sus servidores web EC2 y su base de datos RDS en subredes privadas, y un NAT gateway en cada AZ. El security group del ALB permite el 443 desde cualquier lugar; el security group web permite el 443 solo desde el security group del ALB; el security group de la base de datos permite el 3306 solo desde el security group web. Los operadores usan Session Manager, así que ninguna instancia tiene abierto el puerto 22. Cuando un escáner desde un rango de IP inunda el sitio, el equipo agrega en las subredes públicas una regla de denegación en la NACL para ese rango, con un número menor que las reglas de permiso para que se evalúe primero.

Errores comunes: llamar pública a una subred solo porque las instancias tienen IPs públicas (lo que importa es la ruta hacia un internet gateway); olvidar que las NACLs no tienen estado, lo que provoca que se descarten las respuestas; intentar escribir una regla de denegación en un security group; poner un solo NAT gateway para todas las AZs, que se convierte en un punto único de falla y agrega cargos por transferencia de datos entre AZs; y colocar el NAT gateway en una subred privada, donde no tiene ruta de salida. Abrir SSH a 0.0.0.0/0 en un bastion es también un hallazgo clásico.

Las preguntas del examen usan palabras clave consistentes. 'Con estado', 'solo permitir' o 'hacer referencia a otra capa' apunta a un security group. 'Sin estado', 'denegar una dirección IP específica' u 'orden de las reglas' apunta a una network ACL. 'Las instancias privadas deben descargar parches pero no deben ser alcanzables desde internet' apunta a un NAT gateway, uno por AZ para resiliencia. 'Acceso por shell sin puertos de entrada abiertos y sin gestión de claves' apunta a Session Manager en lugar de un bastion host.

Términos clave

Security group
Un firewall virtual con estado, solo de permisos, adjunto a interfaces de red.
Network ACL
Un firewall sin estado a nivel de subred, con reglas numeradas de permiso y denegación que se evalúan en orden.
Subred pública (public subnet)
Una subred cuya tabla de rutas envía el tráfico destinado a internet hacia un internet gateway.
NAT gateway
Un servicio administrado en una subred pública que permite a las instancias privadas iniciar conexiones salientes a internet.
Bastion host
Una instancia reforzada en una subred pública que se usa como punto de salto para entrar por SSH a instancias privadas.
Session Manager
Una función de Systems Manager que da acceso por shell a las instancias mediante una conexión saliente del agente, controlada por IAM.
Ejemplo real

Una auditoría de una empresa encuentra el puerto 22 abierto a internet en un bastion host con claves SSH compartidas. El equipo instala el SSM Agent en todas las instancias, adjunta un instance profile con los permisos básicos de Systems Manager, agrega interface endpoints de Systems Manager en las subredes privadas, registra cada sesión en S3 y elimina el bastion. Ahora los ingenieros se conectan con sesiones controladas por IAM, y ningún security group permite SSH entrante.

Consejo para el examen: Con estado y solo de permisos significa security group; sin estado, con reglas de denegación y orden, significa network ACL. Cuando una pregunta pida acceso por shell sin puertos de entrada abiertos y sin gestión de claves, elige Session Manager en lugar de un bastion host.

Comprueba lo que sabes

El HTTPS saliente desde una instancia privada funciona a través de un NAT gateway, pero las respuestas se descartan. El security group está bien. ¿Qué debes revisar?

La network ACL de la subred. Las NACLs no tienen estado, así que necesitan una regla de entrada que permita el tráfico de retorno en los puertos efímeros.

¿Cómo haces que un diseño con NAT sobreviva a la pérdida de una zona de disponibilidad?

Despliega un NAT gateway en cada AZ y enruta cada subred privada al NAT gateway de su propia AZ.

Debes impedir que un rango de IP abusivo llegue a una subred. ¿Security group o NACL?

Una regla de denegación en una network ACL, porque los security groups solo admiten reglas de permiso.

¿Qué debe tener una instancia para administrarse con Session Manager?

El SSM Agent, un instance profile con los permisos básicos de Systems Manager y acceso de red a los endpoints de Systems Manager mediante NAT o interface endpoints.
