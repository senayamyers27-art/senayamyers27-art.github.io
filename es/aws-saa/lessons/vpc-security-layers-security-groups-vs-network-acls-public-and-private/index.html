Capas de seguridad de la VPC: security groups vs network ACLs, subredes públicas y privadas, NAT gateways, bastion hosts vs Session Manager

Una virtual private cloud (VPC) es tu red privada en una Región de AWS, definida por un bloque CIDR IPv4 como 10.0.0.0/16. La divides en subredes (subnets), cada una en una Availability Zone (AZ, zona de disponibilidad). Lo que hace pública a una subred es su route table (tabla de rutas): una subred pública tiene una ruta 0.0.0.0/0 que apunta a un internet gateway, y las instancias allí necesitan una dirección IP pública o Elastic IP para ser alcanzables. Una subred privada no tiene ruta hacia el internet gateway, así que nada en internet puede iniciar una conexión hacia ella.

Las instancias en subredes privadas a menudo aún necesitan acceso saliente a internet para los parches. Un NAT gateway lo proporciona: lo colocas en una subred pública con una Elastic IP, y la route table de la subred privada envía 0.0.0.0/0 hacia él. Permite conexiones salientes y sus respuestas, pero bloquea las conexiones entrantes desde internet. Un NAT gateway vive en una sola AZ, así que para alta disponibilidad despliegas uno por AZ y enrutas cada subred privada al gateway de su propia AZ. Las NAT instances son la alternativa más antigua y autogestionada.

Dos capas de firewall protegen los recursos. Los security groups (grupos de seguridad) se adjuntan a elastic network interfaces (y por lo tanto a instancias, balanceadores de carga y bases de datos RDS). Son stateful (con estado), lo que significa que el tráfico de retorno se permite automáticamente, solo admiten reglas de permiso y todas las reglas se evalúan juntas. El origen de una regla puede ser otro security group, que es la forma limpia de decir que solo la capa web puede llegar a la capa de base de datos. Las network ACLs (NACLs) se adjuntan a subredes, son stateless (sin estado), así que debes permitir explícitamente el tráfico de retorno en los puertos efímeros, admiten reglas de permiso y de denegación, y se evalúan en orden de número de regla, donde gana la primera coincidencia. Usa un deny en la NACL cuando necesites bloquear un rango de IP específico, porque los security groups no pueden denegar.

Los administradores necesitan una forma de llegar a las instancias privadas. La respuesta clásica es un bastion host: una instancia reforzada en una subred pública que permite SSH desde rangos de IP conocidos, desde la cual saltas a las instancias privadas. Funciona, pero requiere parches, gestión de claves y un puerto entrante abierto. AWS Systems Manager Session Manager es la respuesta moderna: el SSM Agent de la instancia establece una conexión saliente hacia Systems Manager, y abres una shell desde la consola o la CLI, con IAM controlando quién puede conectarse. Sin puertos entrantes, sin claves SSH, y las sesiones pueden registrarse en CloudWatch Logs o S3. La instancia necesita un instance profile con los permisos básicos de Systems Manager y una ruta hacia los endpoints de Systems Manager, mediante NAT o interface endpoints.

Términos clave

Security group (grupo de seguridad)
Un firewall virtual stateful que solo permite, adjunto a interfaces de red.
Network ACL (lista de control de acceso de red)
Un firewall stateless a nivel de subred con reglas numeradas de permiso y denegación evaluadas en orden.
NAT gateway
Un servicio administrado en una subred pública que permite a las instancias privadas iniciar conexiones salientes a internet.
Session Manager
Una función de Systems Manager que da acceso de shell a las instancias mediante una conexión saliente del agente, controlada por IAM.
Ejemplo real

Una app de tres capas coloca su ALB en subredes públicas, sus servidores web EC2 y su base de datos RDS en subredes privadas, y un NAT gateway en cada AZ. El security group de la base de datos permite el puerto 3306 solo desde el security group de la capa web, y los operadores usan Session Manager en lugar de un bastion host, así que ninguna instancia tiene abierto el puerto 22.

Consejo para el examen: Stateful y solo de permiso significa security group; stateless con reglas de denegación y orden significa network ACL. Cuando una pregunta pida acceso de shell sin puertos entrantes abiertos y sin gestión de claves, elige Session Manager en lugar de un bastion host.

Comprueba lo que sabes

El HTTPS saliente desde una instancia privada funciona a través de un NAT gateway, pero las respuestas se descartan. El security group está bien. ¿Qué debes revisar?

La network ACL de la subred. Las NACLs son stateless, así que necesitan una regla de entrada que permita el tráfico de retorno en los puertos efímeros (1024-65535).

¿Cómo haces que un diseño de NAT sobreviva a la pérdida de una Availability Zone?

Despliega un NAT gateway en cada AZ y enruta cada subred privada al NAT gateway de su propia AZ.
