Caché: ElastiCache for Redis vs Memcached, DynamoDB Accelerator (DAX), lazy loading vs write-through

Una caché mantiene en memoria rápida los datos que se leen con frecuencia para que las solicitudes repetidas no lleguen a una base de datos más lenta. Eso reduce la latencia, a menudo de milisegundos a microsegundos, y disminuye la carga y el costo de la base de datos. El examen pregunta qué caché encaja y qué estrategia de caché encaja.

Amazon ElastiCache es una caché en memoria administrada. ElastiCache for Redis, y su motor sucesor de código abierto Valkey, que ElastiCache también admite, es rico en funciones: estructuras de datos avanzadas como sorted sets (ideales para tablas de clasificación o leaderboards), hashes y listas; replicación con failover automático en configuraciones Multi-AZ; persistencia con respaldos y restauraciones; mensajería publish-subscribe; y cluster mode para fragmentar (shard) los datos entre nodos. Úsalo para almacenes de sesiones, leaderboards, limitación de tasa y cualquier caché que deba sobrevivir a la falla de un nodo. ElastiCache for Memcached es más simple: una caché multihilo de clave-valor pura que escala horizontalmente agregando nodos, sin replicación, sin persistencia y sin respaldos. Úsalo cuando necesites una caché simple escalada horizontalmente y sea aceptable perder datos si falla un nodo.

DynamoDB Accelerator (DAX) es una caché en memoria diseñada solo para DynamoDB. Es compatible con la API, así que una aplicación cambia del cliente de DynamoDB al cliente de DAX con cambios mínimos de código, y la latencia de lectura baja de milisegundos a microsegundos para las lecturas eventualmente consistentes. DAX es la respuesta cuando una pregunta pide lecturas de microsegundos en DynamoDB con pocos cambios de código. No ayuda a las cargas con muchas escrituras ni a las lecturas fuertemente consistentes, que pasan directamente a DynamoDB.

Dos estrategias de caché aparecen con frecuencia. Lazy loading (carga diferida), también llamada cache-aside, significa que la aplicación revisa primero la caché; ante un fallo (miss) lee de la base de datos y escribe el resultado en la caché. Solo se almacenan en caché los datos solicitados, y un nodo de caché caído no es fatal, pero un miss cuesta tres viajes y los datos pueden quedar obsoletos. Write-through (escritura directa) significa que la aplicación escribe en la caché cada vez que escribe en la base de datos, así que los datos en caché siempre están actualizados, pero cada escritura paga latencia adicional y la caché se llena de datos que quizá nunca se lean. Muchos diseños combinan ambas y agregan un time to live (TTL) a las claves para que los datos obsoletos expiren.

La caché también aparece en otros lugares: API Gateway puede almacenar respuestas en caché, CloudFront almacena contenido en caché en el borde, y las read replicas de RDS pueden descargar lecturas cuando una caché no es apropiada, por ejemplo cuando cada consulta es diferente.

Términos clave

ElastiCache for Redis
Un almacén de datos en memoria administrado con tipos de datos ricos, replicación, persistencia y failover Multi-AZ.
ElastiCache for Memcached
Una caché de clave-valor administrada y multihilo, sin replicación ni persistencia.
DAX
DynamoDB Accelerator, una caché en memoria compatible con la API de DynamoDB con latencia de lectura de microsegundos.
Lazy loading (carga diferida)
Una estrategia de caché que carga los datos en la caché solo después de un cache miss.
Ejemplo real

Una empresa de videojuegos guarda los perfiles de los jugadores en DynamoDB y su leaderboard global en ElastiCache for Redis usando un sorted set, con réplicas Multi-AZ para que el leaderboard sobreviva a la falla de un nodo. Cuando las lecturas de perfiles se disparan durante los torneos, agrega DAX delante de la tabla, cambiando solo la biblioteca cliente.

Consejo para el examen: Leaderboards, pub/sub, persistencia o alta disponibilidad: Redis. La caché de clave-valor multihilo más simple: Memcached. Lecturas de microsegundos para DynamoDB con cambios mínimos de código: DAX. Caché siempre actualizada a costa de latencia de escritura: write-through.

Comprueba lo que sabes

¿Qué estrategia de caché puede servir datos obsoletos y cómo lo limitas?

Lazy loading, porque la caché solo se actualiza ante un miss. Configura un TTL en los elementos en caché para que expiren y se vuelvan a cargar.

¿Ayudaría DAX a una aplicación que hace principalmente lecturas fuertemente consistentes?

No. DAX pasa las lecturas fuertemente consistentes directamente a DynamoDB; acelera las lecturas eventualmente consistentes.
