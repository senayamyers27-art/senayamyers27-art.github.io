Caché: ElastiCache for Redis vs Memcached, DynamoDB Accelerator (DAX), lazy loading vs write-through

Una caché guarda los datos que se leen con frecuencia en memoria rápida para que las solicitudes repetidas no lleguen a una base de datos más lenta. Eso reduce la latencia, a menudo de milisegundos a microsegundos, y disminuye la carga y el costo de la base de datos, porque le llegan menos lecturas y muchas veces puede ser de menor tamaño. La caché funciona mejor para datos que se leen mucho más a menudo de lo que cambian, como catálogos de productos, perfiles de usuario y datos de sesión. El examen hace dos tipos de pregunta: qué servicio de caché encaja y qué estrategia de caché encaja.

Amazon ElastiCache es una caché en memoria administrada. ElastiCache for Redis OSS, y Valkey, el motor de código abierto derivado de Redis que ElastiCache también admite, es rico en funcionalidades: estructuras de datos avanzadas como sorted sets (ideales para tablas de clasificación), hashes y listas; replicación con conmutación por error automática en configuraciones Multi-AZ; persistencia con respaldos y restauraciones; mensajería de publicación-suscripción (pub/sub); y cluster mode para fragmentar los datos entre nodos. Úsalo para almacenes de sesiones, tablas de clasificación, limitación de tasa y cualquier caché que deba sobrevivir a la falla de un nodo. ElastiCache for Memcached es más simple: una caché multihilo de clave-valor pura que escala horizontalmente agregando nodos, sin replicación, sin persistencia y sin respaldos. Úsalo cuando necesitas una caché simple escalada horizontalmente y es aceptable perder los datos en caché si falla un nodo. ElastiCache también ofrece una opción serverless que escala la capacidad automáticamente.

DynamoDB Accelerator (DAX) es una caché en memoria diseñada exclusivamente para Amazon DynamoDB. Es compatible con la API de DynamoDB, así que una aplicación cambia del cliente de DynamoDB al cliente de DAX con cambios mínimos de código, y la latencia de lectura baja de milisegundos de un solo dígito a microsegundos para las lecturas eventualmente consistentes. DAX se ejecuta como un clúster dentro de tu nube privada virtual (VPC). Es la respuesta cuando una pregunta pide lecturas en microsegundos sobre DynamoDB con pocos cambios de código. No ayuda a las cargas con muchas escrituras, y las lecturas fuertemente consistentes pasan directamente a DynamoDB.

Dos estrategias de caché aparecen con frecuencia. Lazy loading, también llamada cache-aside, significa que la aplicación consulta primero la caché; si hay un acierto devuelve el valor, y si hay un fallo lee de la base de datos y escribe el resultado en la caché. Solo se almacenan en caché los datos solicitados y la falla de un nodo de caché no es fatal, pero un fallo cuesta tres viajes y los datos pueden quedar desactualizados. Write-through significa que la aplicación escribe en la caché cada vez que escribe en la base de datos, así que los datos en caché siempre están al día, pero cada escritura paga latencia adicional y la caché se llena de datos que quizá nunca se lean. Muchos diseños combinan ambas y agregan un tiempo de vida (TTL) a las claves para que los datos desactualizados expiren. El patrón lazy loading con TTL se ve así en Python.

v = cache.get(key)
if v is None:
    v = db.query(key)
    cache.set(key, v, ex=300)  # 5-minute TTL
return v

Veamos un ejemplo práctico. Una empresa de videojuegos guarda los perfiles de los jugadores en DynamoDB y mantiene su tabla de clasificación global en ElastiCache for Redis OSS usando un sorted set, donde agregar una puntuación y leer los 100 mejores jugadores son comandos únicos y rápidos. Habilita Multi-AZ con una réplica para que la tabla de clasificación sobreviva a la falla de un nodo. Cuando las lecturas de perfiles se disparan durante los torneos, agrega DAX delante de la tabla de perfiles, cambiando solo la biblioteca cliente. Para los datos de sesión web usa el mismo clúster de Redis, así que la sesión de un usuario no se pierde si se reemplaza un servidor web. Las descripciones de productos se cargan con lazy loading con un TTL de una hora, mientras que los saldos de los jugadores, que siempre deben estar al día, se escriben con write-through.

Errores comunes: elegir Memcached cuando la pregunta necesita alta disponibilidad, respaldos o sorted sets; esperar que DAX acelere las escrituras o las lecturas fuertemente consistentes; agregar una caché para datos en los que cada consulta es única, lo que da una tasa de aciertos pobre (una réplica de lectura puede encajar mejor); y olvidar los TTL, de modo que los datos cargados con lazy loading quedan desactualizados indefinidamente. Otra trampa es suponer que una caché es una base de datos duradera; a menos que se configuren persistencia y replicación, los datos en caché pueden desaparecer. La caché también existe en otros lugares: Amazon API Gateway puede almacenar respuestas en caché, y CloudFront almacena contenido en caché en el edge.

Las preguntas del examen suelen seguir pistas reconocibles. 'Tabla de clasificación', 'sorted sets', 'pub/sub', 'persistencia', 'conmutación por error Multi-AZ' o 'almacén de sesiones que debe sobrevivir a fallas' apuntan a ElastiCache for Redis OSS o Valkey. 'Simple', 'multihilo', 'solo clave-valor' y 'pérdida de datos aceptable' apuntan a Memcached. 'DynamoDB', 'microsegundos' y 'cambios mínimos de código' apuntan a DAX. 'La caché nunca debe estar desactualizada' apunta a write-through; 'almacenar en caché solo lo que se solicita' o 'tolera fallas de la caché' apunta a lazy loading, con un TTL para limitar la desactualización.

Términos clave

ElastiCache for Redis OSS
Un almacén de datos en memoria administrado con tipos de datos ricos, replicación, persistencia y conmutación por error Multi-AZ; Valkey es una opción de motor compatible.
ElastiCache for Memcached
Una caché de clave-valor multihilo administrada, sin replicación ni persistencia.
DAX
DynamoDB Accelerator, una caché en memoria compatible con la API de DynamoDB con latencia de lectura de microsegundos.
Lazy loading
Una estrategia de caché que carga los datos en la caché solo después de un fallo de caché; también se llama cache-aside.
Write-through
Una estrategia de caché que actualiza la caché cada vez que se escribe en la base de datos, manteniendo al día los datos en caché.
Tiempo de vida (TTL)
Un tiempo de expiración de un elemento en caché, después del cual se elimina y se vuelve a cargar en la siguiente solicitud.
Tasa de aciertos de caché (cache hit ratio)
La proporción de solicitudes atendidas desde la caché en lugar de la base de datos de respaldo.
Ejemplo real

Una empresa de videojuegos guarda los perfiles de los jugadores en DynamoDB y su tabla de clasificación global en ElastiCache for Redis OSS usando un sorted set, con una réplica Multi-AZ para que la tabla de clasificación sobreviva a la falla de un nodo. Cuando las lecturas de perfiles se disparan durante los torneos, agrega DAX delante de la tabla, cambiando solo la biblioteca cliente, y la latencia de lectura baja a microsegundos sin tocar la configuración de capacidad de la tabla.

Consejo para el examen: Tablas de clasificación, pub/sub, persistencia o alta disponibilidad: Redis OSS o Valkey. La caché de clave-valor multihilo más simple: Memcached. Lecturas en microsegundos para DynamoDB con cambios mínimos de código: DAX. Caché siempre al día a costa de latencia en las escrituras: write-through.

Comprueba lo que sabes

¿Qué estrategia de caché puede servir datos desactualizados, y cómo lo limitas?

Lazy loading, porque la caché solo se actualiza cuando hay un fallo. Define un TTL en los elementos en caché para que expiren y se vuelvan a cargar.

¿Ayudaría DAX a una aplicación que hace principalmente lecturas fuertemente consistentes?

No. DAX pasa las lecturas fuertemente consistentes directamente a DynamoDB; acelera las lecturas eventualmente consistentes.

Un almacén de sesiones debe sobrevivir a la pérdida de un nodo de caché. ¿Redis OSS o Memcached?

ElastiCache for Redis OSS (o Valkey) con replicación y conmutación por error automática Multi-AZ; Memcached no tiene replicación.

¿Cuál es la principal desventaja de la caché write-through?

Cada escritura paga latencia adicional para actualizar la caché, y la caché se llena de datos que quizá nunca se lean.
