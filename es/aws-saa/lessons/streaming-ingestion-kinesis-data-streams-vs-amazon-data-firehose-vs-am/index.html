Ingesta de streaming: Kinesis Data Streams vs Amazon Data Firehose vs Amazon MSK

Los datos de streaming llegan de forma continua, como clickstreams, logs de aplicaciones, lecturas de sensores IoT o transacciones financieras, y a menudo deben procesarse en segundos. AWS ofrece tres servicios principales de ingesta, y el examen los distingue por cuánto control necesitas y hacia dónde van los datos.

Amazon Kinesis Data Streams es un flujo de datos en tiempo real que lees con tus propios consumidores. Los productores ponen registros con una partition key; los registros con la misma clave van al mismo shard, conservando el orden dentro de la clave. En modo provisioned, cada shard admite una tasa de ingesta fija (1 MB/s o 1,000 registros por segundo) y una tasa de lectura, y agregas shards para escalar; en modo on-demand, Kinesis administra la capacidad por ti. Los registros se conservan 24 horas por defecto, ampliables hasta 365 días, así que varios consumidores pueden leer los mismos datos de forma independiente y reproducirlos (replay). Los consumidores incluyen Lambda, aplicaciones que usan la Kinesis Client Library y Amazon Managed Service for Apache Flink para analítica en tiempo real. El enhanced fan-out da a cada consumidor un rendimiento de lectura dedicado. Elige Data Streams para procesamiento personalizado en tiempo real, múltiples consumidores y replay.

Amazon Data Firehose, antes Kinesis Data Firehose, es la forma más sencilla de cargar datos de streaming en destinos. Es totalmente administrado y escala automáticamente sin shards. Almacena en búfer los datos entrantes por tamaño o tiempo y los entrega a Amazon S3, Redshift, OpenSearch Service, Splunk, endpoints HTTP y varios servicios de socios. Puede transformar registros con Lambda, convertir JSON a Parquet u ORC y comprimir los datos. Por el búfer, la entrega es casi en tiempo real (de segundos a minutos) en lugar de inmediata, y Firehose no almacena los datos para replay. Elígelo cuando el requisito sea cargar datos de streaming en S3 o Redshift con la menor sobrecarga operativa.

Amazon Managed Streaming for Apache Kafka (MSK) ejecuta clústeres de Apache Kafka por ti, y MSK Serverless elimina la gestión de capacidad. Elígelo cuando una empresa ya usa Kafka, quiere conservar las APIs, herramientas y conectores de Kafka, o necesita funciones específicas de Kafka. Ofrece más control de configuración que Kinesis a costa de requerir más conocimiento de Kafka.

Los servicios también se combinan: un patrón común envía eventos a Kinesis Data Streams para los consumidores en tiempo real y conecta Firehose como uno de los consumidores para archivar todo en S3 y analizarlo después con Athena.

Términos clave

Shard
La unidad de capacidad de un Kinesis data stream en modo provisioned, con rendimiento de lectura y escritura fijo.
Partition key (Kinesis)
El valor que determina qué shard recibe un registro, conservando el orden por clave.
Amazon Data Firehose
Un servicio totalmente administrado que almacena en búfer los datos de streaming y los entrega a destinos como S3 y Redshift.
Amazon MSK
Amazon Managed Streaming for Apache Kafka, un servicio de Kafka administrado.
Ejemplo real

Una empresa de viajes compartidos transmite las ubicaciones de los conductores a Kinesis Data Streams. Un consumidor Lambda actualiza un mapa en vivo en menos de un segundo, una aplicación Flink detecta las zonas de alta demanda, y Firehose, leyendo el mismo stream, escribe archivos Parquet comprimidos en S3 cada pocos minutos para que los científicos de datos los consulten con Athena.

Consejo para el examen: Entregar a S3, Redshift u OpenSearch sin código y sin gestión de capacidad: Firehose. Consumidores personalizados en tiempo real, orden por clave o replay: Kinesis Data Streams. Cargas de Kafka existentes o APIs de Kafka: MSK.

Comprueba lo que sabes

¿Puede Amazon Data Firehose reproducir los datos de ayer para un consumidor nuevo?

No. Firehose entrega y no conserva los datos para replay. Kinesis Data Streams conserva los registros para que los consumidores puedan volver a leerlos.

Un productor de Kinesis recibe errores de rendimiento excedido en un stream provisioned. ¿Cuáles son dos soluciones?

Agregar shards (o cambiar al modo on-demand) y usar una partition key bien distribuida para que los registros se repartan entre los shards.
