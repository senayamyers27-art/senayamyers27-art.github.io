Ingesta de streaming: Kinesis Data Streams vs Amazon Data Firehose vs Amazon MSK

Los datos de streaming llegan de forma continua, como clickstreams, logs de aplicaciones, lecturas de sensores de Internet de las cosas (IoT) o transacciones financieras, y a menudo deben procesarse en segundos en lugar de en un lote nocturno. AWS ofrece tres servicios principales de ingesta. El examen los distingue por cuánto control necesitas, si los datos deben poder reproducirse, si ya usas Apache Kafka y hacia dónde van los datos.

Amazon Kinesis Data Streams es un flujo de datos en tiempo real que lees con tus propios consumidores. Los productores ponen registros con una partition key, por ejemplo aws kinesis put-record --stream-name rides --partition-key driver-812 --data <base64>. Los registros con la misma partition key van al mismo shard, lo que preserva el orden dentro de esa clave. En modo provisioned, cada shard admite una tasa de escritura fija (1 MB/s o 1,000 registros por segundo) y una tasa de lectura (2 MB/s compartidos por los consumidores), y agregas shards para escalar; en modo on-demand, Kinesis administra la capacidad por ti. Los registros se conservan 24 horas de forma predeterminada, ampliables hasta 365 días, así que varios consumidores pueden leer los mismos datos de forma independiente y reproducirlos después de corregir un error.

Los consumidores de Data Streams incluyen AWS Lambda, las aplicaciones construidas con la Kinesis Client Library (KCL) y Amazon Managed Service for Apache Flink para analítica en tiempo real, como agregaciones por ventanas y detección de anomalías. Enhanced fan-out da a cada consumidor registrado su propio rendimiento de lectura dedicado por shard, así que agregar consumidores no ralentiza a los demás. Elige Data Streams para procesamiento personalizado en tiempo real, múltiples consumidores independientes, orden por clave y reproducción.

Amazon Data Firehose, antes Kinesis Data Firehose, es la forma más sencilla de cargar datos de streaming en destinos de almacenamiento y analítica. Es totalmente administrado y escala automáticamente sin shards que planificar. Acumula en búfer los datos entrantes por tamaño o por tiempo y los entrega a Amazon S3, Amazon Redshift (preparándolos en S3 y emitiendo un COPY), Amazon OpenSearch Service, Splunk, endpoints HTTP y varios servicios de socios. Puede transformar registros con una función Lambda, convertir JSON a los formatos columnares Apache Parquet u ORC, particionar los datos dinámicamente por un campo y comprimirlos. Debido al búfer, la entrega es casi en tiempo real, normalmente de segundos a minutos, y Firehose no conserva los datos para reproducirlos. Elígelo cuando el requisito sea cargar datos de streaming en S3, Redshift u OpenSearch con la menor carga operativa.

Amazon Managed Streaming for Apache Kafka (MSK) ejecuta clústeres de Apache Kafka por ti, encargándose del aprovisionamiento, los parches y el reemplazo de los brokers, y MSK Serverless elimina por completo la administración de capacidad. Elígelo cuando una empresa ya usa Kafka, quiere conservar las API de Kafka, las bibliotecas cliente, las herramientas y los conectores de Kafka Connect, o necesita funcionalidades específicas de Kafka, como la retención prolongada en los topics o una configuración particular. Ofrece más control que Kinesis, a costa de necesitar conocimientos de Kafka.

Veamos un ejemplo práctico. Una empresa de viajes compartidos envía las ubicaciones de los conductores a Kinesis Data Streams, usando el ID del conductor como partition key para que las actualizaciones de cada conductor se mantengan en orden. Un consumidor Lambda actualiza el mapa en vivo en menos de un segundo, una aplicación Flink detecta zonas donde la demanda supera a la oferta, y un delivery stream de Firehose, que lee del mismo data stream como otro consumidor, escribe cada pocos minutos archivos Parquet comprimidos y particionados por fecha en S3 para que los científicos de datos los consulten con Athena. El equipo de pagos de la empresa, que ya ejecuta Kafka en sus instalaciones con decenas de conectores, se traslada a MSK en lugar de reescribir sus productores.

Errores comunes: elegir Firehose cuando la pregunta necesita procesamiento en menos de un segundo, consumidores personalizados o reproducción; elegir Data Streams cuando la única necesidad es dejar datos en S3 sin código; usar una partition key de baja cardinalidad, de modo que un shard se vuelve caliente y lanza ProvisionedThroughputExceededException; y elegir MSK para una carga nueva y sencilla sin ningún requisito de Kafka, lo que añade conocimientos operativos que el equipo quizá no tenga. Otra trampa es pensar que Firehose almacena datos; solo los mantiene brevemente en búfer antes de entregarlos.

La redacción del examen suele delatar la respuesta. 'Cargar en S3, Redshift, OpenSearch o Splunk', 'casi en tiempo real', 'sin administración', 'convertir a Parquet' apuntan a Amazon Data Firehose. 'Tiempo real', 'procesamiento personalizado', 'múltiples consumidores', 'orden por clave' o 'reproducción' apuntan a Kinesis Data Streams. 'Kafka existente', 'API de Kafka de código abierto' o 'Kafka Connect' apuntan a Amazon MSK. 'Analítica en tiempo real con SQL o Java sobre un stream' apunta a Managed Service for Apache Flink leyendo de Data Streams o MSK.

Términos clave

Shard
La unidad de capacidad de un data stream de Kinesis en modo provisioned, con rendimiento de lectura y escritura fijo.
Partition key (Kinesis)
El valor que determina qué shard recibe un registro, preservando el orden por clave.
Periodo de retención (retention period)
Cuánto tiempo conserva Kinesis Data Streams los registros para leerlos y reproducirlos; 24 horas de forma predeterminada y ampliable.
Enhanced fan-out
Una funcionalidad de Kinesis que da a cada consumidor registrado rendimiento de lectura dedicado por shard.
Amazon Data Firehose
Un servicio totalmente administrado que acumula en búfer los datos de streaming y los entrega a destinos como S3, Redshift y OpenSearch.
Amazon MSK
Amazon Managed Streaming for Apache Kafka, un servicio de Kafka administrado con una opción serverless.
Ejemplo real

Una empresa de viajes compartidos envía las ubicaciones de los conductores a Kinesis Data Streams. Un consumidor Lambda actualiza un mapa en vivo en menos de un segundo, una aplicación Flink detecta zonas de alta demanda, y Firehose, leyendo el mismo stream, escribe cada pocos minutos archivos Parquet comprimidos en S3 para que los científicos de datos los consulten con Athena. El equipo de pagos, que ya usa Kafka, traslada sus productores y conectores existentes a Amazon MSK.

Consejo para el examen: Entregar a S3, Redshift u OpenSearch sin código y sin administrar capacidad: Firehose. Consumidores personalizados en tiempo real, orden por clave o reproducción: Kinesis Data Streams. Cargas de Kafka existentes o API de Kafka: MSK.

Comprueba lo que sabes

¿Puede Amazon Data Firehose reproducir los datos de ayer para un consumidor nuevo?

No. Firehose entrega los datos y no los conserva para reproducirlos. Kinesis Data Streams conserva los registros para que los consumidores puedan volver a leerlos.

Un productor de Kinesis recibe errores de rendimiento excedido en un stream en modo provisioned. ¿Cuáles son dos soluciones?

Agregar shards (o cambiar al modo on-demand) y usar una partition key bien distribuida para que los registros se repartan entre los shards.

Cinco aplicaciones distintas leen el mismo stream y se ralentizan entre sí. ¿Qué funcionalidad ayuda?

Enhanced fan-out, que da a cada consumidor registrado su propio rendimiento de lectura dedicado.

Una empresa ejecuta Kafka en sus instalaciones con muchos conectores de Kafka Connect y quiere un servicio administrado. ¿Cuál usa?

Amazon MSK, que mantiene la compatibilidad con las API, los clientes y los conectores de Kafka.
