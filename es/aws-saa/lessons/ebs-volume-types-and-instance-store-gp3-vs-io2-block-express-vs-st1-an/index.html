Tipos de volúmenes EBS e instance store: gp3 vs io2 Block Express vs st1 y sc1

Amazon Elastic Block Store (EBS) proporciona volúmenes de almacenamiento en bloque conectados por red para EC2, que se comportan como discos duros virtuales. Un volumen vive en una zona de disponibilidad (AZ), se replica dentro de esa AZ para protegerse contra una falla de hardware individual, persiste de forma independiente de la instancia y puede respaldarse con snapshots de un momento dado almacenados en Amazon S3. Normalmente un volumen se adjunta a una sola instancia a la vez; los volúmenes io1 e io2 admiten Multi-Attach a varias instancias basadas en Nitro en la misma AZ, para aplicaciones en clúster que coordinan ellas mismas las escrituras concurrentes. Como un volumen está atado a una AZ, mover los datos a otra AZ implica crear un snapshot y restaurarlo allí.

Los tipos de volumen EBS se dividen en volúmenes de unidad de estado sólido (SSD), que se miden principalmente en operaciones de entrada/salida por segundo (IOPS), y volúmenes de disco duro (HDD), que se miden en rendimiento (MB/s). El SSD de propósito general gp3 es la opción predeterminada para volúmenes de arranque y la mayoría de las cargas de trabajo. Su característica clave es que el rendimiento es independiente del tamaño: todo volumen gp3 obtiene una base de 3,000 IOPS y 125 MB/s, y puedes aprovisionar más IOPS y rendimiento por separado sin comprar más almacenamiento. El gp2, más antiguo, vincula las IOPS al tamaño del volumen (tres IOPS por GiB) y usa créditos de ráfaga en volúmenes pequeños, por eso los equipos solían sobreaprovisionar capacidad gp2 solo para obtener rendimiento, y por eso migrar de gp2 a gp3 normalmente reduce costos o mejora el rendimiento.

Los SSD de IOPS aprovisionadas, io1 e io2, son para bases de datos con mucha E/S que necesitan IOPS sostenidas y consistentes y baja latencia. io2 Block Express es el nivel de EBS de mayor rendimiento: latencia inferior a un milisegundo, IOPS y rendimiento máximos por volumen mucho mayores que gp3, y más durabilidad que los demás tipos de volumen. Los volúmenes io2 nuevos se crean sobre Block Express. Elígelo para bases de datos grandes y de misión crítica como SAP HANA, Oracle o SQL Server cuando los máximos o la consistencia de gp3 no son suficientes. Las IOPS se definen explícitamente al crear el volumen, por ejemplo aws ec2 create-volume --volume-type io2 --size 500 --iops 20000 --availability-zone us-east-1a.

Los volúmenes HDD están optimizados para lecturas y escrituras secuenciales grandes y no pueden ser volúmenes de arranque. El HDD optimizado para rendimiento (st1) sirve para big data, data warehouses, procesamiento de logs y cargas de streaming que leen archivos grandes en orden. El Cold HDD (sc1) es la opción de EBS de menor costo, para datos orientados a rendimiento a los que se accede con poca frecuencia. La E/S aleatoria pequeña rinde mal en volúmenes HDD, así que nunca los elijas para bases de datos transaccionales. El instance store es otra cosa: almacenamiento en bloque temporal en discos conectados físicamente al host. Ofrece un rendimiento de E/S muy alto y no tiene cargo aparte, pero los datos se pierden cuando la instancia se detiene, hiberna o termina, o si falla el disco subyacente; solo sobreviven a un reinicio. Úsalo para cachés, búferes, datos temporales de trabajo o datos que la aplicación replica entre nodos. Solo ciertos tipos de instancia lo incluyen, y no puedes desconectarlo y conectarlo en otro lugar.

Veamos un ejemplo práctico. Una empresa ejecuta una base de datos Oracle grande que necesita IOPS muy altas y sostenidas con latencia consistente inferior a un milisegundo, así que usa volúmenes de datos io2 Block Express. Sus servidores web arrancan desde volúmenes gp3 con las 3,000 IOPS predeterminadas. Un clúster de analítica de logs que escanea terabytes de forma secuencial cada noche usa st1, y un conjunto de extractos históricos que rara vez se leen está en sc1. Una capa de caché se ejecuta en instancias optimizadas para almacenamiento con instance store NVMe, porque la caché puede reconstruirse desde la base de datos si una instancia se detiene. Cuando más tarde el equipo de base de datos necesita más IOPS, cambia en el mismo volumen las IOPS aprovisionadas con Elastic Volumes en lugar de migrar.

Errores comunes: elegir st1 o sc1 para un volumen de arranque o una base de datos de procesamiento de transacciones en línea (OLTP); suponer que el rendimiento de gp3 crece con el tamaño como en gp2; creer que los datos del instance store sobreviven a una detención y un nuevo arranque (solo a un reinicio); esperar que un volumen EBS se adjunte a una instancia en otra AZ; y pagar por io2 cuando gp3 con IOPS adicionales aprovisionadas cumpliría el requisito a menor costo. Otra trampa es olvidar que el cifrado de EBS se configura por volumen, y que los snapshots de volúmenes cifrados también quedan cifrados.

Las preguntas del examen suelen formularse en torno al patrón de acceso y al presupuesto. 'Volumen de arranque', 'propósito general' o 'el SSD más rentable' apuntan a gp3. 'Las IOPS más altas', 'base de datos de misión crítica', 'latencia inferior a un milisegundo' o 'la mayor durabilidad' apuntan a io2 Block Express. 'Secuencial grande', 'big data', 'procesamiento de logs' y 'rendimiento' apuntan a st1; almacenamiento en bloque con 'acceso poco frecuente' más 'el menor costo' apunta a sc1. 'Temporal', 'scratch', 'búfer', 'la mayor E/S' y 'los datos pueden perderse' apuntan a instance store. 'Volumen en bloque compartido para una aplicación en clúster en una AZ' apunta a Multi-Attach de io1 o io2.

Términos clave

gp3
SSD de propósito general con una base de 3,000 IOPS y 125 MB/s, en el que las IOPS y el rendimiento se aprovisionan de forma independiente del tamaño.
gp2
El SSD de propósito general más antiguo, cuyas IOPS escalan con el tamaño del volumen y usan créditos de ráfaga en volúmenes pequeños.
io2 Block Express
El SSD de EBS de mayor rendimiento para bases de datos exigentes, con latencia inferior a un milisegundo y mayor durabilidad.
st1
HDD optimizado para rendimiento, para cargas secuenciales grandes como big data y logs; no sirve como arranque.
sc1
Cold HDD, el volumen EBS de menor costo, para datos secuenciales de acceso poco frecuente; no sirve como arranque.
Instance store
Almacenamiento en bloque temporal conectado físicamente al host; los datos se pierden al detener, hibernar o terminar la instancia o si falla el disco.
Multi-Attach
Una funcionalidad de io1 e io2 que adjunta un volumen a varias instancias Nitro en la misma AZ.
Ejemplo real

Una empresa ejecuta una base de datos Oracle grande que necesita IOPS sostenidas muy altas y elige io2 Block Express. Sus servidores web usan volúmenes de arranque gp3. Un clúster de analítica de logs que lee terabytes de forma secuencial usa st1, y los extractos mensuales archivados que rara vez se escanean están en sc1. Una capa de caché usa instance store NVMe en instancias optimizadas para almacenamiento, porque la caché puede reconstruirse si se pierden los datos.

Consejo para el examen: Volumen predeterminado o de arranque: gp3. Las IOPS sostenidas más altas para bases de datos críticas: io2 Block Express. Mucho rendimiento secuencial a bajo costo: st1; lo más frío y barato: sc1. El espacio temporal más rápido que puede perderse: instance store.

Comprueba lo que sabes

Detienes e inicias una instancia. ¿Qué pasa con los datos de su volumen de instance store?

Se pierden. Los datos del instance store solo sobreviven a reinicios, no a detenciones, hibernación ni terminación.

¿Por qué gp3 suele ser más barato que gp2 para el mismo rendimiento?

gp3 permite aprovisionar IOPS y rendimiento de forma independiente del tamaño, así que ya no necesitas sobreaprovisionar almacenamiento para obtener IOPS.

¿Se puede usar un volumen st1 como volumen de arranque de una instancia Linux?

No. Los volúmenes st1 y sc1 basados en HDD no pueden ser volúmenes de arranque; usa un tipo SSD como gp3.

Una aplicación en clúster en una AZ necesita que varias instancias compartan un mismo volumen en bloque. ¿Qué opción de EBS encaja?

Un volumen io1 o io2 con Multi-Attach habilitado, adjunto a instancias Nitro en la misma AZ, con la aplicación gestionando las escrituras concurrentes.
