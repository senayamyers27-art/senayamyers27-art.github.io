Contenedores en AWS: ECS vs EKS, y los launch types Fargate vs EC2

Los contenedores empaquetan una aplicación con sus dependencias para que se ejecute igual en todas partes. En AWS eliges un orquestador, que programa y administra los contenedores, y un modelo de capacidad, que decide dónde se ejecutan. Las imágenes de contenedores suelen almacenarse en Amazon Elastic Container Registry (ECR), un registro privado que puede escanear las imágenes en busca de vulnerabilidades.

Amazon Elastic Container Service (ECS) es el orquestador propio de AWS. Describes los contenedores en una task definition (imagen, CPU, memoria, puertos, entorno, task role de IAM), y un ECS service mantiene en ejecución una cantidad deseada de tareas, reemplaza las que fallan y las registra en un balanceador de carga. ECS es más fácil de aprender y está profundamente integrado con AWS, lo que lo hace una buena respuesta cuando una pregunta enfatiza la mínima sobrecarga operativa y ningún requisito especial de Kubernetes.

Amazon Elastic Kubernetes Service (EKS) ejecuta por ti el control plane (plano de control) de Kubernetes en varias AZs. Usas herramientas estándar de Kubernetes como kubectl, charts de Helm y manifiestos. Elige EKS cuando una organización ya usa Kubernetes, quiere portabilidad entre nubes u on-premises, o depende del ecosistema de Kubernetes. Los pods obtienen permisos de AWS mediante IAM roles for service accounts o EKS Pod Identity, en lugar de permisos a nivel de todo el nodo.

Ambos orquestadores admiten dos modelos de capacidad. Con el EC2 launch type (en EKS, managed node groups o nodos autoadministrados), los contenedores se ejecutan en instancias EC2 de tu cuenta. Eliges los tipos de instancia, aplicas parches a los hosts y administras la capacidad del clúster, lo que te da control sobre GPUs, instancias especializadas, precios de Reserved Instances o Spot y agentes tipo daemon. Con AWS Fargate no hay instancias que administrar: especificas CPU y memoria por tarea o pod, y AWS lo ejecuta en capacidad aislada, facturando los recursos solicitados mientras se ejecuta. Fargate es la respuesta para la menor sobrecarga operativa; EC2 es la respuesta cuando necesitas control sobre el host o el menor costo para cargas estables y densas. Fargate Spot y las instancias Spot ofrecen capacidad interrumpible con descuento para tareas tolerantes a fallos.

Dos detalles aparecen con frecuencia. En ECS, el task execution role permite que el agente de ECS descargue imágenes y escriba logs, mientras que el task role le da al código de la aplicación sus permisos de AWS. Y los ECS services pueden escalar las tareas con Service Auto Scaling según métricas como la CPU o el número de solicitudes del ALB.

Términos clave

Task definition (definición de tarea)
El plano de ECS que describe los contenedores, recursos, red y roles de IAM de una tarea.
Amazon EKS
Un servicio administrado de Kubernetes que ejecuta el control plane por ti.
AWS Fargate
Un motor de cómputo serverless para contenedores que elimina la necesidad de administrar hosts EC2.
ECS task role
El rol de IAM cuyos permisos usa la aplicación dentro de una tarea de ECS.
Ejemplo real

Una startup quiere ejecutar una API en contenedores sin administrar servidores ni aprender Kubernetes. Sube las imágenes a ECR, define un ECS service en Fargate detrás de un ALB y configura Service Auto Scaling según la CPU. Otro equipo que ya ejecuta Kubernetes on-premises traslada sus cargas de trabajo a EKS para conservar los mismos manifiestos y herramientas.

Consejo para el examen: Conocimientos previos de Kubernetes o portabilidad: EKS. Orquestación nativa de AWS más simple: ECS. Sin servidores que administrar: Fargate. Necesidad de GPUs, control a nivel de host o precios Reserved en los hosts: EC2 launch type.

Comprueba lo que sabes

¿Qué rol de ECS usa el código de la aplicación para leer de DynamoDB?

El task role. El task execution role es para que el agente de ECS descargue imágenes y envíe logs.

¿Cuál es la principal diferencia operativa entre Fargate y el EC2 launch type?

Con Fargate, AWS administra los hosts subyacentes; con EC2, tú aprovisionas, aplicas parches y escalas las instancias de contenedores.
