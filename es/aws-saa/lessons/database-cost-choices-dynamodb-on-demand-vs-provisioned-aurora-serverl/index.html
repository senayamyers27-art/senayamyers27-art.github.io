AWS Certified Solutions Architect – Associate SAA-C03

Decisiones de costo en bases de datos: DynamoDB on-demand vs provisioned, Aurora Serverless v2, Reserved DB Instances y detener bases de datos inactivas

Las bases de datos suelen estar entre las partidas más grandes de una factura de AWS porque se ejecutan todo el tiempo, y porque los equipos las dimensionan para la carga pico y luego las dejan así. La optimización de costos aquí se reduce a tres hábitos: hacer coincidir el modelo de capacidad con el patrón de tráfico, comprometerse donde el uso es estable y dejar de pagar por bases de datos que nadie usa. El examen presenta una descripción del tráfico o un entorno inactivo y pide la opción más rentable que siga cumpliendo el requisito.

En Amazon DynamoDB, la elección es entre modos de capacidad. El modo on-demand cobra por cada solicitud de lectura y escritura, no necesita planificación de capacidad y absorbe picos repentinos, lo que lo hace rentable para aplicaciones nuevas, tráfico impredecible y tablas que están inactivas gran parte del tiempo. El modo provisioned cobra por hora las unidades de capacidad de lectura (RCU) y de escritura (WCU) que configuras, las uses o no; con auto scaling siguiendo una utilización objetivo, suele ser más barato para tráfico estable y predecible, y la reserved capacity reduce aún más el precio con compromisos a largo plazo. Un camino común es empezar en on-demand, aprender el patrón a partir de las métricas de CloudWatch y pasar las tablas estables a provisioned. Otros ahorros en DynamoDB incluyen la clase de tabla Standard-Infrequent Access (Standard-IA) para tablas cuyo costo de almacenamiento domina sobre su costo de rendimiento, y el tiempo de vida (TTL) para eliminar ítems expirados sin consumir capacidad de escritura.

Aurora Serverless v2 escala la capacidad de la base de datos automáticamente en incrementos finos medidos en Aurora capacity units (ACU), entre un mínimo y un máximo que defines, en segundos y sin cortar conexiones. Pagas por la capacidad usada cada segundo. Conviene a cargas variables, con picos o impredecibles, a bases de datos de desarrollo y pruebas, y a aplicaciones multiinquilino. Un mínimo bajo mantiene pequeño el costo en inactividad, y las versiones recientes pueden pausarse automáticamente cuando están inactivas si fijas el mínimo en cero, a costa de un breve retraso al reanudar. Para bases de datos constantemente ocupadas, las instancias Aurora provisioned con precios reservados suelen ser más baratas. Puedes mezclar instancias provisioned y Serverless v2 en un mismo clúster, por ejemplo un writer provisioned con readers serverless que escalan para los picos de informes.

Para el uso estable de Amazon Relational Database Service (RDS) y Aurora, las Reserved DB Instances dan un descuento significativo por un plazo de uno o tres años, igual que las Reserved Instances de EC2. Las reservas con flexibilidad de tamaño se aplican a todos los tamaños dentro de una familia de instancias en muchos motores, así que una reserva sigue ayudando después de cambiar de tamaño dentro de la familia. Ajusta primero el tamaño usando las métricas de CloudWatch y Compute Optimizer, y considera las clases de instancia de base de datos basadas en Graviton para lograr mejor relación precio-rendimiento, lo que en muchos motores es un simple cambio de clase de instancia durante una ventana de mantenimiento.

Por último, las bases de datos inactivas. Puedes detener una instancia RDS o un clúster Aurora hasta siete días seguidos, con aws rds stop-db-instance --db-instance-identifier test-db; mientras está detenida, pagas el almacenamiento y los respaldos pero no las horas de instancia. Después de siete días AWS la vuelve a iniciar automáticamente para que no se pierda el mantenimiento, así que para periodos de inactividad más largos debes automatizar que se detenga de nuevo, o tomar un snapshot final y eliminar la base de datos, restaurándola desde el snapshot cuando se necesite. En entornos de desarrollo y pruebas, programar detenciones fuera del horario laboral con Amazon EventBridge Scheduler y AWS Lambda, o usar Aurora Serverless v2 con un mínimo bajo, evita pagar por las noches y los fines de semana.

Veamos un ejemplo práctico. El writer Aurora de producción de una empresa de software como servicio (SaaS) está ocupado a un nivel estable todo el día, así que compra Reserved DB Instances para él después de confirmar el tamaño con un mes de métricas. Su reader de informes solo trabaja intensamente a fin de mes, así que pasa a ser un reader Aurora Serverless v2 que escala durante unos días y el resto del tiempo se mantiene cerca de su mínimo. Veinte bases de datos de prueba se detienen cada noche y cada fin de semana mediante una función Lambda programada, y una que solo se usa para una auditoría anual se respalda con un snapshot y se elimina. La tabla de DynamoDB de una funcionalidad nueva empieza en modo on-demand y se revisará después de tres meses de datos de tráfico.

Errores comunes: elegir capacidad provisioned de DynamoDB para tráfico totalmente nuevo o con muchos picos, lo que provoca throttling o desperdicia capacidad; comprar Reserved DB Instances antes de ajustar el tamaño; suponer que una instancia RDS detenida permanece detenida indefinidamente; elegir Aurora Serverless v2 para una base de datos ocupada a un nivel constante todo el día, donde provisioned más reservas es más barato; y olvidar que el almacenamiento y los respaldos se siguen facturando mientras la instancia está detenida. Otra trampa es pensar que las réplicas de lectura reducen costos; agregan instancias y costo, y sirven para rendimiento y disponibilidad.

Las preguntas del examen suelen formularse en torno al patrón de tráfico. 'Impredecible', 'con picos', 'aplicación nueva' o 'inactiva la mayor parte del tiempo' apuntan a DynamoDB on-demand o Aurora Serverless v2. 'Estable', 'predecible' o 'funciona 24/7 durante años' apuntan a capacidad provisioned con reservas, o a Reserved DB Instances. 'Solo se necesita en horario laboral' apunta a detener e iniciar de forma programada. 'Se necesita una semana por trimestre' o 'inactiva durante meses' apunta a tomar un snapshot y eliminarla, porque una base de datos detenida se reinicia después de siete días.

Términos clave

Modo on-demand (DynamoDB)
Un modo de capacidad que factura por cada solicitud de lectura y escritura sin planificación de capacidad.
Modo provisioned (DynamoDB)
Un modo de capacidad que factura por hora las RCU y WCU configuradas, opcionalmente con auto scaling.
Aurora capacity unit (ACU)
La unidad de capacidad de Aurora Serverless v2, que combina memoria con la CPU y la red correspondientes.
Aurora Serverless v2
Una configuración de Aurora que escala la capacidad automáticamente en incrementos finos de ACU entre límites definidos.
Reserved DB Instance
Un compromiso de uno o tres años de RDS o Aurora que reduce el precio por hora de la instancia.
Reserved capacity de DynamoDB
Un compromiso con capacidad provisioned de DynamoDB a cambio de una tarifa con descuento.
Instancia de base de datos detenida
Una instancia RDS por la que no se facturan horas de instancia, que se reinicia automáticamente después de siete días.
Ejemplo real

El writer Aurora de producción de una empresa SaaS está ocupado todo el día, así que compra Reserved DB Instances para él. Su réplica de informes solo trabaja intensamente a fin de mes, así que pasa a ser un reader Aurora Serverless v2. Veinte bases de datos de prueba se detienen cada noche y cada fin de semana mediante una función Lambda programada, y la tabla de DynamoDB de una funcionalidad nueva empieza en modo on-demand hasta que se conozca su patrón de tráfico.

Consejo para el examen: Impredecible o con picos: DynamoDB on-demand o Aurora Serverless v2. Estable y predecible: capacidad provisioned con reservas. Una base de datos RDS detenida se reinicia después de siete días, así que para periodos largos de inactividad toma un snapshot y elimínala.

Comprueba lo que sabes

Una base de datos de pruebas se necesita solo una semana por trimestre. ¿Cuál es el enfoque más barato?

Tomar un snapshot y eliminar la instancia, y luego restaurarla desde el snapshot cuando se necesite; una instancia detenida se reiniciaría después de siete días.

¿Cuándo es más barata la capacidad provisioned de DynamoDB que on-demand?

Cuando el tráfico es estable y predecible, de modo que la capacidad provisioned con auto scaling se mantiene bien utilizada.

¿Qué sigues pagando mientras una instancia RDS está detenida?

El almacenamiento y los respaldos; las horas de instancia no se facturan mientras está detenida.

Un clúster Aurora tiene un writer estable, pero un reader que solo está ocupado a fin de mes. ¿Qué configuración ahorra dinero?

Mantener un writer provisioned y reservado, y convertir el reader en una instancia Aurora Serverless v2 que escala con la demanda.
