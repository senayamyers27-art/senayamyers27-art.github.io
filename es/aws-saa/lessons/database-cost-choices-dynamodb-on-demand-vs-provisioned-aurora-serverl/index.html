Decisiones de costo en bases de datos: DynamoDB on-demand vs provisioned, Aurora Serverless v2, Reserved DB Instances y detener bases de datos inactivas

Las bases de datos suelen estar entre las partidas más grandes de una factura de AWS porque se ejecutan todo el tiempo. Aquí la optimización de costos significa adecuar el modelo de capacidad al patrón de tráfico, comprometerse donde el uso es estable y no pagar por bases de datos que nadie usa.

En DynamoDB, la elección es entre modos de capacidad. El modo on-demand cobra por cada solicitud de lectura y escritura, no necesita planificación y maneja picos repentinos, lo que lo hace rentable para aplicaciones nuevas, tráfico impredecible y tablas que están inactivas gran parte del tiempo. El modo provisioned cobra por hora las unidades de capacidad de lectura y escritura que configuras, las uses o no; con auto scaling siguiendo una utilización objetivo, suele ser más barato para tráfico estable y predecible, y la reserved capacity reduce aún más el precio para compromisos a largo plazo. Un camino común es empezar en on-demand, aprender el patrón y pasar las tablas estables a provisioned. Otros ahorros en DynamoDB incluyen la table class Standard-Infrequent Access para tablas cuyo costo de almacenamiento domina sobre su costo de rendimiento, y TTL para eliminar gratis los elementos vencidos.

Aurora Serverless v2 escala automáticamente la capacidad de la base de datos en incrementos finos medidos en Aurora capacity units (ACUs), entre un mínimo y un máximo que configuras, en segundos. Pagas por la capacidad usada cada segundo. Se adapta a cargas variables, con picos o impredecibles, a bases de datos de desarrollo y pruebas, y a aplicaciones multiinquilino. Para bases de datos constantemente ocupadas, las instancias Aurora provisioned con precios reservados suelen ser más baratas. Puedes mezclar instancias provisioned y Serverless v2 en un mismo clúster, por ejemplo un escritor provisioned y lectores serverless.

Para un uso estable de RDS y Aurora, las Reserved DB Instances dan un descuento significativo por un plazo de uno o tres años, igual que las RIs de EC2. Las reservas con flexibilidad de tamaño (size-flexible) se aplican a los distintos tamaños dentro de una familia de instancias para muchos motores. Ajusta el tamaño primero, y considera las clases de instancia de base de datos basadas en Graviton para una mejor relación precio-rendimiento.

Por último, las bases de datos inactivas. Puedes detener una instancia RDS o un clúster Aurora hasta siete días seguidos; mientras está detenida, pagas el almacenamiento y los respaldos, pero no las horas de instancia. Después de siete días AWS la vuelve a iniciar automáticamente, así que para períodos de inactividad más largos automatizas volver a detenerla, o tomas un snapshot y eliminas la base de datos, restaurándola cuando se necesite. Para entornos de desarrollo y pruebas, programar detenciones fuera del horario laboral con EventBridge y Lambda, o usar Aurora Serverless v2 con un mínimo bajo, evita pagar las noches y los fines de semana.

Términos clave

Aurora capacity unit (ACU)
La unidad de capacidad de Aurora Serverless v2, que combina memoria con la CPU y la red correspondientes.
Reserved DB Instance
Un compromiso de uno o tres años en RDS o Aurora que reduce el precio por hora de la instancia.
DynamoDB reserved capacity (capacidad reservada)
Un compromiso con capacidad provisioned de DynamoDB a cambio de una tarifa con descuento.
Stopped DB instance (instancia de base de datos detenida)
Una instancia RDS que no se factura por horas de instancia y que se reinicia automáticamente después de siete días.
Ejemplo real

El escritor de Aurora de producción de una empresa SaaS está ocupado todo el día, así que compra Reserved DB Instances para él. Su réplica de reportes solo trabaja intensamente a fin de mes, así que se convierte en un lector de Aurora Serverless v2. Veinte bases de datos de prueba se detienen cada noche y cada fin de semana mediante una función Lambda programada, y la tabla de DynamoDB de una nueva función empieza en modo on-demand.

Consejo para el examen: Impredecible o con picos: DynamoDB on-demand o Aurora Serverless v2. Estable y predecible: capacidad provisioned con reservas. Una base de datos RDS detenida se reinicia a los siete días, así que para largos períodos de inactividad toma un snapshot y elimínala.

Comprueba lo que sabes

Una base de datos de prueba solo se necesita una semana por trimestre. ¿Cuál es el enfoque más barato?

Tomar un snapshot y eliminar la instancia, y luego restaurar desde el snapshot cuando se necesite; una instancia detenida se reiniciaría a los siete días.

¿Cuándo es la capacidad provisioned de DynamoDB más barata que on-demand?

Cuando el tráfico es estable y predecible, de modo que la capacidad provisioned con auto scaling se mantiene bien utilizada.
