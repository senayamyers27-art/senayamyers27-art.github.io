Seguridad multicuenta: AWS Organizations, service control policies, IAM Identity Center y roles entre cuentas

Los grandes clientes de AWS rara vez ejecutan todo en una sola cuenta. Las cuentas separadas ofrecen límites firmes de seguridad, facturación y cuotas: un error o una brecha en una cuenta de desarrollo no puede afectar a producción. AWS Organizations es el servicio que agrupa las cuentas. Una management account (cuenta de administración) crea o invita cuentas miembro, las organiza en organizational units (OUs, unidades organizativas) como Security, Production y Sandbox, y paga una única factura consolidada.

Las service control policies (SCPs) son políticas de Organizations adjuntas a la raíz, a una OU o a una cuenta. Definen los permisos máximos disponibles para los usuarios y roles de IAM en las cuentas miembro afectadas, incluido el usuario root de la cuenta. Las SCPs nunca otorgan permisos; una identidad aún necesita una política de IAM que permita la acción. Son barreras de protección (guardrails): por ejemplo, denegar salir de la organización, denegar la desactivación de CloudTrail o denegar cualquier acción fuera de las Regiones aprobadas mediante la condición aws:RequestedRegion. Las SCPs no afectan a la management account, que es una de las razones por las que AWS recomienda no ejecutar cargas de trabajo allí. Tampoco restringen los service-linked roles.

AWS IAM Identity Center (el sucesor de AWS Single Sign-On) es la forma recomendada para que las personas inicien sesión en muchas cuentas. Conectas una fuente de identidad, como el directorio integrado, Active Directory o un proveedor de identidad externo como Okta o Microsoft Entra ID, y defines permission sets (conjuntos de permisos). Un permission set es una plantilla de políticas; cuando asignas un permission set a un usuario o grupo en una cuenta, Identity Center crea un rol correspondiente en esa cuenta. Los usuarios inician sesión una vez en el portal de acceso y eligen la cuenta y el rol, recibiendo credenciales temporales.

Para cargas de trabajo y automatización, el acceso entre cuentas usa roles de IAM. En la cuenta de destino creas un rol cuya trust policy indica como principal la cuenta de origen o un rol específico de ella. En la cuenta de origen, una identidad necesita permiso para sts:AssumeRole sobre el ARN de ese rol. Ambos lados deben estar de acuerdo. Cuando un tercero, como un proveedor de monitoreo, asume un rol en tu cuenta, agregas una condición de external ID a la trust policy para evitar el problema del confused deputy (suplente confundido), en el que se engaña al proveedor para que use su acceso en nombre de otra persona.

Otras herramientas multicuenta que puedes encontrar: AWS Control Tower configura una landing zone con OUs, registros y guardrails recomendados; AWS Resource Access Manager (RAM) comparte recursos como subredes o Transit Gateways entre cuentas; y el delegated administrator (administrador delegado) permite que una cuenta miembro gestione un servicio como GuardDuty o Security Hub para toda la organización.

Términos clave

Organizational unit (OU, unidad organizativa)
Un contenedor de cuentas dentro de AWS Organizations al que se pueden adjuntar políticas como las SCPs.
Service control policy (SCP)
Una política de Organizations que fija los permisos máximos de las identidades en las cuentas miembro; nunca otorga acceso.
Permission set (conjunto de permisos)
Una plantilla de políticas de IAM Identity Center que se convierte en un rol en cada cuenta a la que se asigna.
External ID
Un valor secreto exigido en la trust policy de un rol entre cuentas para protegerse del problema del confused deputy.
Ejemplo real

Una empresa quiere garantizar que nadie en sus cuentas de cargas de trabajo pueda crear recursos fuera de dos Regiones aprobadas. Adjunta a la OU Workloads una SCP que deniega todas las acciones cuando aws:RequestedRegion no es una de las dos, con excepciones para los servicios globales. Ni siquiera un administrador de una cuenta miembro puede eludirla.

Consejo para el examen: Las SCPs filtran, no otorgan, y no se aplican a la management account. Si la pregunta busca un inicio de sesión centralizado para personas en muchas cuentas, elige IAM Identity Center; si busca que una aplicación de la cuenta A actúe en la cuenta B, elige un rol entre cuentas.

Comprueba lo que sabes

Una SCP permite solo acciones de EC2 y S3. Un usuario de una cuenta miembro tiene AdministratorAccess. ¿Puede crear una tabla de DynamoDB?

No. La SCP fija los permisos máximos disponibles, así que las acciones fuera de EC2 y S3 se bloquean sin importar la política de IAM.

¿Qué dos cosas se requieren para que un rol de la cuenta A asuma un rol de la cuenta B?

El rol de la cuenta B debe confiar en la cuenta A (o en ese rol) en su trust policy, y la identidad de la cuenta A debe tener permitido sts:AssumeRole sobre el ARN del rol.
