Capas web Multi-AZ: Elastic Load Balancing (ALB vs NLB), Auto Scaling groups y health checks de ELB

Cada región de AWS contiene varias zonas de disponibilidad (AZs): uno o más centros de datos con energía, refrigeración y red independientes, conectados entre sí por enlaces de baja latencia. Una capa web resiliente se ejecuta en al menos dos AZs, de modo que la pérdida de un centro de datos, o de una AZ completa, no derribe la aplicación. Tres servicios lo hacen posible: Elastic Load Balancing (ELB) reparte el tráfico entre destinos sanos, Amazon EC2 Auto Scaling mantiene en ejecución la cantidad correcta de instancias sanas, y los health checks unen a ambos. Esta combinación aparece en una gran parte de las preguntas de resiliencia del SAA-C03.

Un Application Load Balancer (ALB) trabaja en la capa 7, el nivel de HTTP y HTTPS. Puede enrutar por nombre de host, ruta, encabezados HTTP, cadenas de consulta e IP de origen, así que un solo ALB puede enviar /api/* a un target group y /images/* a otro. Los destinos pueden ser instancias EC2, direcciones IP (incluidos contenedores) o funciones Lambda. Termina TLS, admite WebSockets y HTTP/2, puede autenticar usuarios mediante Cognito o un proveedor OpenID Connect y se integra con AWS WAF. Un Network Load Balancer (NLB) trabaja en la capa 4 con TCP, UDP y TLS. Maneja un rendimiento muy alto con una latencia muy baja, puede conservar la IP de origen del cliente y proporciona una dirección IP estática por AZ, a la que puedes asociar Elastic IPs. Elige el NLB para protocolos que no son HTTP, IPs estáticas para listas de permitidos en firewalls, rendimiento extremo o para exponer un servicio mediante PrivateLink. Un Gateway Load Balancer es un tercer tipo, que se usa para insertar appliances virtuales de terceros, como firewalls, en la ruta del tráfico.

Un Auto Scaling group (ASG) lanza instancias a partir de una plantilla de lanzamiento (launch template) en las subredes que elijas, y mantiene la cantidad entre un mínimo y un máximo alrededor de una capacidad deseada. Equilibra las instancias entre AZs y, si una AZ falla, lanza reemplazos en las restantes. Las políticas de escalado cambian la capacidad deseada: target tracking mantiene una métrica cerca de un valor (por ejemplo, el CPU promedio al 50 por ciento o la cantidad de solicitudes por destino), step scaling reacciona a umbrales de alarmas, el escalado programado (scheduled scaling) atiende picos conocidos y el escalado predictivo (predictive scaling) pronostica patrones diarios. Asociar el ASG a un target group del balanceador de carga registra automáticamente las instancias nuevas y anula el registro de las terminadas.

Los health checks deciden qué pasa con una instancia defectuosa. El balanceador de carga ejecuta su propio health check, por ejemplo un HTTP GET a /health que espera una respuesta 200, y deja de enviar tráfico a los destinos que fallan. El ASG, por defecto, usa solo las verificaciones de estado de EC2 (EC2 status checks), que detectan fallas de hardware y del sistema operativo, pero no un proceso de servidor web caído. Habilitar el tipo de health check ELB en el ASG hace que también reemplace las instancias que el balanceador de carga marca como no sanas. Esa configuración es una respuesta frecuente en el examen. Un período de gracia del health check (health check grace period) da tiempo a las instancias nuevas para arrancar antes de que cuenten las verificaciones, y el drenaje de conexiones (deregistration delay) permite que terminen las solicitudes en curso antes de retirar una instancia.

aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name web-asg \
  --health-check-type ELB --health-check-grace-period 300

Veamos un ejemplo práctico. Una tienda en línea ejecuta un ALB delante de un ASG que abarca tres AZs, con un mínimo de tres instancias y una política de target tracking sobre la cantidad de solicitudes por destino. Un despliegue defectuoso hace que el servidor web de una instancia devuelva errores mientras el sistema operativo sigue sano. El health check del ALB falla y el tráfico pasa a las otras dos instancias; como el ASG usa el tipo de health check ELB, termina la instancia averiada y lanza una nueva a partir de la launch template. Los datos de sesión viven en Amazon ElastiCache, así que los clientes que estaban en la instancia fallida siguen con la sesión iniciada, y las imágenes subidas se guardan en S3 en lugar de en discos locales.

Errores comunes: ejecutar todas las instancias en una sola AZ; dejar el ASG con los health checks de EC2, de modo que las aplicaciones averiadas siguen ejecutándose; elegir un ALB cuando los clientes necesitan direcciones IP fijas o UDP; elegir un NLB cuando el requisito es enrutamiento por ruta; fijar una capacidad mínima tan baja que la falla de una AZ deja muy pocas instancias para la carga; y guardar sesiones o archivos en las instancias, lo que falla cuando el ASG reduce su tamaño. Las sesiones persistentes (sticky sessions) existen en el ALB, pero hacen que el escalado y la conmutación por error sean menos uniformes, así que son un parche y no un objetivo de diseño.

La redacción del examen es predecible. 'Basado en ruta', 'basado en host' o 'enrutar a microservicios por URL' apunta a ALB. 'IP estática', 'UDP', 'TCP', 'millones de solicitudes por segundo' o 'latencia ultrabaja' apunta a NLB. 'Appliances de firewall de terceros' apunta a Gateway Load Balancer. 'El ASG no reemplaza las instancias que el balanceador de carga reporta como no sanas' apunta al tipo de health check ELB, y 'sobrevivir a la pérdida de una AZ' apunta a instancias repartidas en varias AZs con suficiente capacidad mínima.

Términos clave

Zona de disponibilidad (Availability Zone)
Uno o más centros de datos aislados dentro de una región, con energía y red independientes.
Application Load Balancer
Un balanceador de carga de capa 7 que enruta solicitudes HTTP y HTTPS según el contenido, como la ruta y el host.
Network Load Balancer
Un balanceador de carga de capa 4 para TCP, UDP y TLS, con IPs estáticas por AZ y un rendimiento muy alto.
Auto Scaling group
Un conjunto de instancias EC2 lanzadas desde una plantilla que EC2 Auto Scaling mantiene en una cantidad deseada y sana.
Política de target tracking (target tracking policy)
Una política de escalado que ajusta la capacidad para mantener una métrica elegida cerca de un valor objetivo.
Tipo de health check ELB (ELB health check type)
Una configuración del Auto Scaling group que reemplaza las instancias que el balanceador de carga reporta como no sanas.
Ejemplo real

Una empresa de videojuegos necesita un servicio de lobby que usa un protocolo UDP personalizado, y las redes de sus socios deben incluir sus direcciones en listas de permitidos. Despliega un Network Load Balancer con una Elastic IP en cada una de dos AZs delante de un Auto Scaling group, y un Application Load Balancer separado para su tienda web HTTPS que enruta /store/* y /account/* a target groups distintos. Cada ASG usa target tracking y health checks de ELB.

Consejo para el examen: El enrutamiento basado en ruta o en host significa ALB. IP estática, UDP o millones de solicitudes por segundo con latencia ultrabaja significa NLB. Si un ASG no reemplaza las instancias que el balanceador de carga dice que no están sanas, cambia el ASG al tipo de health check ELB.

Comprueba lo que sabes

Un servidor de juegos usa UDP y los clientes deben incluir direcciones IP fijas en listas de permitidos. ¿Qué balanceador de carga encaja?

Un Network Load Balancer, que admite UDP y ofrece una dirección IP estática por AZ (opcionalmente Elastic IPs).

¿Por qué los servidores web detrás de un ASG no deben guardar las sesiones de usuario en la memoria local?

Las instancias pueden terminarse o agregarse en cualquier momento; guardar las sesiones en ElastiCache o DynamoDB permite que cualquier instancia atienda a cualquier usuario.

Por defecto, ¿qué health checks usa un Auto Scaling group?

Solo las verificaciones de estado de EC2, que no detectan fallas de la aplicación a menos que se habilite el tipo de health check ELB.

¿Qué política de escalado mantiene el CPU promedio cerca del 50 por ciento con la menor configuración?

Una política de escalado target tracking con un objetivo de utilización de CPU del 50 por ciento.
