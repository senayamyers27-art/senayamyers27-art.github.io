Protección del borde: AWS WAF, Shield Standard vs Shield Advanced y CloudFront con origin access control

El borde (edge) es donde tu aplicación se encuentra con internet, y es el mejor lugar para detener el tráfico malicioso antes de que llegue a tus servidores. AWS ofrece allí tres servicios que trabajan juntos: AWS WAF para el filtrado en la capa de aplicación, AWS Shield para la protección contra ataques de denegación de servicio distribuido (DDoS) y Amazon CloudFront, la red de entrega de contenido (CDN) que sirve y filtra el tráfico en una red global de ubicaciones de borde (edge locations). Entender qué capa cubre cada uno te permite responder rápido la mayoría de las preguntas de seguridad en el borde.

AWS WAF es un firewall de aplicaciones web. Creas una lista de control de acceso web (web ACL) y la asocias con una distribución de CloudFront, un Application Load Balancer, una REST API de API Gateway, una API GraphQL de AppSync, un Cognito user pool u otros servicios compatibles. Inspecciona solicitudes HTTP(S) en la capa 7 y aplica reglas en orden de prioridad: grupos de reglas administrados por AWS para amenazas comunes como la inyección SQL, el cross-site scripting (XSS) y entradas maliciosas conocidas, reglas de conjuntos de IP para bloquear o permitir rangos de direcciones, reglas de coincidencia geográfica, coincidencias de expresiones regulares y de encabezados, y reglas basadas en tasa (rate-based rules) que bloquean a un origen que envía demasiadas solicitudes en una ventana de tiempo. Las reglas pueden bloquear, permitir, contar (para probar sin riesgo) o presentar un CAPTCHA o un desafío. WAF no puede adjuntarse a un Network Load Balancer ni directamente a una instancia EC2.

AWS Shield Standard es automático y está incluido para todos los clientes de AWS sin cargo adicional. Protege contra los ataques más comunes de las capas de red y transporte (capas 3 y 4), como las inundaciones SYN (SYN floods) y la reflexión UDP. Shield Advanced es una suscripción de pago para una mayor protección de recursos específicos: distribuciones de CloudFront, zonas alojadas de Route 53, aceleradores de Global Accelerator, Elastic Load Balancers y direcciones Elastic IP. Agrega detección y mitigación ajustadas a tu tráfico, mitigación de DDoS en la capa de aplicación mediante WAF, visibilidad de los ataques casi en tiempo real, acceso al AWS Shield Response Team (SRT) durante los ataques, AWS WAF sin costo adicional para los recursos protegidos y protección de costos que acredita los cargos de escalado causados por un ataque DDoS.

CloudFront en sí es una defensa sólida, porque el tráfico de ataque se reparte entre muchas ubicaciones de borde y solo los fallos de caché (cache misses) llegan a tu origen. Para asegurarte de que los usuarios no puedan saltarse CloudFront y llegar directamente a un origen S3, usa origin access control (OAC). Habilitas OAC en la distribución, mantienes el bucket privado con Block Public Access activado y agregas una bucket policy que permite s3:GetObject solo cuando el principal es cloudfront.amazonaws.com y aws:SourceArn es igual al ARN de tu distribución. OAC reemplaza a la antigua origin access identity (OAI) y admite objetos cifrados con SSE-KMS. Para orígenes personalizados como un ALB, los patrones comunes son hacer que CloudFront agregue un encabezado personalizado secreto que el ALB exige, y permitir solo la lista de prefijos administrada de CloudFront en el security group del ALB.

Veamos un ejemplo práctico. Un sitio de comercio minorista ve bots que atacan sin parar su página de inicio de sesión y un scraper que copia las páginas de productos. El equipo adjunta a su distribución de CloudFront un web ACL de WAF con el conjunto de reglas principal administrado por AWS, una regla basada en tasa limitada a la ruta /login y una regla geográfica que bloquea los países donde la empresa no opera. Primero ejecuta las reglas nuevas en modo de conteo durante un día para detectar falsos positivos y luego las cambia a bloqueo. Como se acerca una gran venta, la empresa también se suscribe a Shield Advanced, para que el Shield Response Team pueda ayudar durante un ataque y se acrediten los costos de escalado que este cause. Las imágenes de los productos están en un bucket de S3 privado que solo la distribución puede leer mediante OAC.

Errores comunes: esperar que WAF detenga una inundación volumétrica de capa 3 (ese es el trabajo de Shield) o que Shield detenga una inyección SQL (ese es el trabajo de WAF); intentar poner WAF en un Network Load Balancer; dejar público un origen S3 para que los usuarios puedan saltarse CloudFront y sus reglas de WAF; y usar la OAI heredada cuando una pregunta destaca el soporte de SSE-KMS. Otra trampa es pensar que Shield Standard debe habilitarse; siempre está activo.

Las preguntas del examen usan señales claras. 'Inyección SQL', 'cross-site scripting', 'bloquear solicitudes de ciertos países' o 'limitar las solicitudes por IP' apunta a AWS WAF. 'Gran ataque DDoS', 'soporte experto durante un ataque' o 'protegerse de costos de escalado inesperados por un ataque' apunta a Shield Advanced. 'Protección contra DDoS comunes sin costo adicional' es Shield Standard. 'Los usuarios no deben acceder directamente al contenido de S3, solo a través de CloudFront' apunta a origin access control con un bucket privado.

Términos clave

AWS WAF
Un firewall de aplicaciones web de capa 7 que filtra solicitudes HTTP(S) usando reglas en un web ACL.
Web ACL
El recurso de AWS WAF que contiene las reglas y se asocia con CloudFront, ALB, API Gateway y otros recursos compatibles.
Regla basada en tasa (rate-based rule)
Una regla de WAF que bloquea las IPs de origen que superan un número de solicitudes dentro de una ventana de tiempo.
Shield Standard
Protección automática y sin costo adicional para todos los clientes de AWS contra ataques DDoS comunes de capas 3 y 4.
Shield Advanced
Un nivel de pago de protección contra DDoS con soporte del SRT, detección avanzada y protección de costos por DDoS.
Origin access control (OAC)
Una función de CloudFront que firma las solicitudes a un origen S3 para que el bucket pueda permanecer privado y aceptar solo a esa distribución.
Ejemplo real

El bucket de S3 de un sitio de noticias era público para que CloudFront pudiera leerlo, y unos investigadores notaron que podían descargar imágenes no publicadas directamente desde la URL del bucket. El equipo habilita origin access control en la distribución, activa Block Public Access y reemplaza la bucket policy por una que permite lecturas solo desde el principal de servicio de CloudFront para el ARN de esa distribución. Ahora las solicitudes directas al bucket devuelven acceso denegado y el sitio sigue funcionando.

Consejo para el examen: Inyección SQL, cross-site scripting, limitación de tasa o bloqueo geográfico apunta a AWS WAF. Un DDoS grande con soporte experto y protección de costos apunta a Shield Advanced. Mantener privado un origen S3 detrás de CloudFront apunta a origin access control.

Comprueba lo que sabes

¿Puedes adjuntar AWS WAF a un Network Load Balancer?

No. WAF funciona en la capa 7 y se adjunta a CloudFront, ALB, REST APIs de API Gateway, AppSync, Cognito user pools y servicios similares, no a NLBs.

¿Qué nivel de Shield está habilitado por defecto sin costo adicional?

Shield Standard, que protege a todos los clientes contra ataques DDoS comunes de capas 3 y 4.

¿Qué verifica una bucket policy para OAC para permitir lecturas de CloudFront?

Que el principal sea el servicio de CloudFront y que aws:SourceArn coincida con el ARN de la distribución específica.

¿Cómo puedes probar reglas nuevas de WAF sin bloquear a usuarios reales?

Configura las reglas en modo de conteo, revisa las solicitudes coincidentes en los registros o métricas y luego cámbialas a bloqueo.
