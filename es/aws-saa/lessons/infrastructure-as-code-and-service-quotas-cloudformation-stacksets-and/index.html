Infraestructura como código y cuotas de servicio: CloudFormation, StackSets y planificación de límites y throttling

La resiliencia no se trata solo de hardware redundante. Si una región falla y tu entorno de recuperación debe construirse a mano y de memoria, la recuperación será lenta y propensa a errores, y el entorno reconstruido no coincidirá del todo con producción. La infraestructura como código (IaC) describe tu entorno en archivos de texto que pueden versionarse, revisarse y desplegarse repetidamente, lo que hace que las reconstrucciones sean rápidas y consistentes y deja a la vista cualquier desviación (drift) respecto del diseño aprobado. La misma idea se aplica a la capacidad: un diseño que funciona en pruebas puede fallar en producción si alcanza una cuota de servicio o un límite de tasa de la API.

AWS CloudFormation es el servicio de IaC nativo de AWS. Una plantilla (template), escrita en JSON o YAML, declara recursos como VPCs, instancias y bases de datos, con parámetros para las entradas, mapeos (mappings) para las búsquedas, condiciones para los recursos opcionales y salidas (outputs) para compartir valores. CloudFormation los crea como una pila (stack), resolviendo el orden de las dependencias, y si la creación falla, revierte los cambios (rollback) por defecto. Para actualizar una pila, envías una plantilla modificada; un conjunto de cambios (change set) muestra de antemano qué se agregará, modificará o reemplazará antes de ejecutarlo, lo que es importante porque algunos cambios de propiedades reemplazan un recurso, como una base de datos. La detección de desviaciones (drift detection) muestra los recursos que se modificaron fuera de CloudFormation. Una DeletionPolicy con Retain o Snapshot protege datos como las bases de datos cuando se elimina una pila, y la protección contra la terminación de la pila (stack termination protection) evita la eliminación accidental. AWS Cloud Development Kit (CDK) y AWS Serverless Application Model (SAM) te permiten escribir en lenguajes de programación o en una sintaxis abreviada para serverless que generan plantillas de CloudFormation.

CloudFormation StackSets despliega una plantilla en muchas cuentas y regiones en una sola operación. Con permisos administrados por el servicio (service-managed permissions) en AWS Organizations, StackSets puede desplegar automáticamente en todas las cuentas de una OU, incluidas las que se agreguen después. Esta es la forma estándar de implementar configuraciones base, como roles de IAM, reglas de Config o registros, en todas las cuentas, o de preparar infraestructura idéntica en una región de DR. Las opciones de despliegue controlan cuántas cuentas se actualizan a la vez y cuántas fallas se toleran antes de que la operación se detenga.

Cada servicio de AWS tiene cuotas de servicio (service quotas), antes llamadas límites, como la cantidad de VPCs por región, las vCPUs de instancias On-Demand en ejecución por región o las solicitudes por segundo a una API. Algunas son ajustables mediante la consola o la API de Service Quotas, y otras son fijas. Las cuotas suelen ser por cuenta y por región, así que para la resiliencia la idea clave es la planificación: si haces failover a otra región, las cuotas de esa región deben ser lo bastante altas para tu carga de producción completa, así que solicita los aumentos con anticipación, porque las aprobaciones pueden tardar. Las alarmas de CloudWatch sobre el uso de las cuotas y las verificaciones de límites de servicio de AWS Trusted Advisor te ayudan a detectar cuándo te acercas a un límite. Las APIs también aplican limitación (throttling): cuando superas una tasa de solicitudes, el servicio devuelve un error de throttling, como un HTTP 429 o una ThrottlingException. Los clientes bien construidos reintentan con espera exponencial (exponential backoff) y variación aleatoria (jitter), algo que los SDKs de AWS hacen automáticamente. Los diseños que disparan muchas llamadas en paralelo deben usar colas para suavizar las ráfagas, caché para evitar llamadas repetidas y APIs por lotes donde existan.

Veamos un ejemplo práctico. Antes de una prueba de DR, una arquitecta descubre que la cuota de vCPUs de instancias On-Demand en la región de recuperación está muy por debajo de lo que usa producción, y que la cuota de Elastic IPs también es demasiado baja. Solicita los aumentos mediante Service Quotas y agrega alarmas de CloudWatch al 80 por ciento de cada cuota. Luego usa un StackSet para desplegar la configuración base de red e IAM en la región de recuperación en todas las cuentas de cargas de trabajo, de modo que el failover solo requiera desplegar las pilas de la aplicación a partir de las mismas plantillas que se usan en producción.

Errores comunes: hacer cambios manuales en la consola sobre recursos administrados por una pila, lo que provoca drift y fallas en las actualizaciones; actualizar una pila sin revisar un change set y reemplazar sin querer una base de datos; olvidar la DeletionPolicy en los almacenes de datos; suponer que las cuotas de la región de DR coinciden con las de la principal; reintentar las llamadas limitadas de inmediato en un bucle cerrado, lo que empeora el throttling; y desplegar plantillas cuenta por cuenta cuando StackSets lo haría de forma centralizada.

Las pistas del examen son directas. 'Desplegar los mismos recursos en muchas cuentas o regiones' apunta a StackSets. 'Previsualizar los cambios antes de actualizar' apunta a un change set. 'Recursos modificados fuera de la plantilla' apunta a la detección de drift. 'Conservar la base de datos cuando se elimina la pila' apunta a DeletionPolicy. 'La región de failover no puede lanzar suficientes instancias' apunta a solicitar aumentos de cuota con anticipación, y 'ThrottlingException durante las ráfagas' apunta a espera exponencial con jitter, colas o caché.

Términos clave

Infraestructura como código (infrastructure as code, IaC)
Definir la infraestructura en archivos de texto versionados que las herramientas despliegan de forma repetible.
Pila de CloudFormation (CloudFormation stack)
Un conjunto de recursos de AWS que se crean y administran juntos a partir de una plantilla.
Conjunto de cambios (change set)
Una vista previa de los cambios que CloudFormation hará al actualizar una pila.
StackSets
Una función de CloudFormation que despliega una plantilla en varias cuentas y regiones.
Cuota de servicio (service quota)
Un límite por cuenta y por región sobre los recursos o las tasas de solicitudes, algunos de los cuales pueden aumentarse.
Espera exponencial (exponential backoff)
Una estrategia de reintentos que espera cada vez más tiempo entre intentos, normalmente con variación aleatoria (jitter).
Ejemplo real

El trabajo nocturno de una empresa inicia miles de funciones Lambda en paralelo, cada una de las cuales llama a una API de DynamoDB y a un servicio de terceros, y falla con errores de throttling. El equipo coloca los elementos de trabajo en una cola de SQS, configura la concurrencia reservada en la función consumidora, usa APIs de escritura por lotes y confía en la espera exponencial con jitter del SDK. Ahora el trabajo termina de forma confiable, y una alarma de CloudWatch avisa si la cuenta se acerca a su cuota de concurrencia de Lambda.

Consejo para el examen: Desplegar los mismos recursos en muchas cuentas o regiones: StackSets. Previsualizar los cambios antes de actualizar: change set. Los planes de DR deben incluir aumentos de cuota en la región de recuperación. Los errores de throttling se manejan con reintentos usando espera exponencial.

Comprueba lo que sabes

¿Qué hace CloudFormation por defecto si un recurso falla durante la creación de una pila?

Revierte los cambios (rollback) y elimina los recursos que creó para esa pila.

Una aplicación recibe errores ThrottlingException durante las ráfagas. ¿Cuáles son dos buenas soluciones?

Reintentar con espera exponencial y jitter, y suavizar o reducir las llamadas con una cola, caché o procesamiento por lotes (o solicitar un aumento de cuota si es ajustable).

¿Cómo proteges una base de datos RDS para que no se elimine cuando se elimina su pila de CloudFormation?

Configura una DeletionPolicy con Retain o Snapshot en el recurso de la base de datos.

¿Por qué la planificación de DR debe incluir las cuotas de servicio en la región de recuperación?

Las cuotas son por región, así que la región de recuperación podría no permitir suficientes recursos para la carga de producción completa a menos que se soliciten aumentos con anticipación.
