Infraestructura como código y cuotas de servicio: CloudFormation, StackSets y planificación de límites y throttling

La resiliencia no se trata solo de hardware redundante. Si una Región falla y tu entorno de recuperación tiene que construirse a mano y de memoria, la recuperación será lenta y propensa a errores. La infraestructura como código (IaC) describe tu entorno en archivos de texto que se pueden versionar, revisar y desplegar repetidamente, lo que hace que las reconstrucciones sean rápidas y consistentes.

AWS CloudFormation es el servicio de IaC nativo de AWS. Un template (plantilla), escrito en JSON o YAML, declara recursos como VPC, instancias y bases de datos, con parameters para las entradas, mappings para las búsquedas, conditions y outputs. CloudFormation los crea como un stack (pila), en orden de dependencias, y si la creación falla hace rollback por defecto. Para actualizar un stack envías una plantilla modificada; un change set muestra por adelantado qué se agregará, modificará o reemplazará antes de ejecutarlo. La drift detection (detección de desviaciones) muestra los recursos que se cambiaron fuera de CloudFormation. Una DeletionPolicy de Retain o Snapshot protege datos como las bases de datos cuando se elimina un stack. AWS Cloud Development Kit (CDK) y AWS SAM te permiten escribir en lenguajes de programación o en una notación abreviada serverless que generan plantillas de CloudFormation.

CloudFormation StackSets despliega una plantilla en muchas cuentas y Regiones en una sola operación. Con service-managed permissions en AWS Organizations, StackSets puede desplegar automáticamente en todas las cuentas de una OU, incluidas las que se agreguen después. Esta es la forma estándar de distribuir líneas base como roles de IAM, Config rules o registro de logs a todas las cuentas, o de preparar infraestructura idéntica en una Región de DR.

Cada servicio de AWS tiene service quotas (cuotas de servicio), antes llamadas límites, como el número de VPC por Región, las vCPUs On-Demand en ejecución por Región o las solicitudes por segundo a una API. Algunas son ajustables desde la consola de Service Quotas y otras son fijas. Para la resiliencia, la idea clave es planificar: si haces failover a otra Región, las cuotas de esa Región deben ser lo bastante altas para toda tu carga de producción, así que solicita los aumentos por adelantado. Las alarmas de CloudWatch sobre el uso de cuotas y las verificaciones de límites de servicio de Trusted Advisor te ayudan a detectar límites que se acercan.

Las APIs también aplican throttling (limitación): cuando superas una tasa de solicitudes, el servicio devuelve un error de throttling, como HTTP 429 o una ThrottlingException. Los clientes bien construidos reintentan con exponential backoff (espera exponencial) y jitter, lo que los SDKs de AWS hacen automáticamente. Los diseños que disparan muchas llamadas deben usar colas para suavizar las ráfagas, caché para reducir llamadas repetidas y APIs por lotes donde existan.

Términos clave

CloudFormation stack
Un conjunto de recursos de AWS creados y administrados juntos a partir de una plantilla.
Change set (conjunto de cambios)
Una vista previa de los cambios que hará CloudFormation al actualizar un stack.
StackSets
Una función de CloudFormation que despliega una plantilla en varias cuentas y Regiones.
Exponential backoff (espera exponencial)
Una estrategia de reintentos que espera cada vez más entre intentos, normalmente con jitter aleatorio.
Ejemplo real

Antes de una prueba de DR, una arquitecta descubre que la cuota de vCPUs para instancias On-Demand de la Región de recuperación está muy por debajo de lo que usa producción. Solicita un aumento mediante Service Quotas y usa un StackSet para desplegar la línea base de red e IAM en la Región de recuperación de cada cuenta de cargas de trabajo, de modo que el failover solo requiera desplegar los stacks de la aplicación.

Consejo para el examen: Desplegar los mismos recursos en muchas cuentas o Regiones: StackSets. Ver los cambios antes de actualizar: change set. Los planes de DR deben incluir aumentos de cuota en la Región de recuperación. Los errores de throttling se manejan con reintentos con exponential backoff.

Comprueba lo que sabes

¿Qué hace CloudFormation por defecto si un recurso falla durante la creación del stack?

Hace rollback, eliminando los recursos que creó para ese stack.

Una aplicación recibe errores ThrottlingException durante las ráfagas. ¿Cuáles son dos buenas soluciones?

Reintentar con exponential backoff y jitter, y suavizar o reducir las llamadas con una cola, caché o lotes (o solicitar un aumento de cuota si es ajustable).
