Resiliencia de bases de datos relacionales: RDS Multi-AZ, read replicas, Aurora Replicas y Aurora Global Database

Amazon RDS ejecuta bases de datos relacionales administradas: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server y Db2, además de Amazon Aurora. AWS se encarga del aprovisionamiento, los parches, los respaldos automáticos y la conmutación por error (failover). El examen evalúa qué función resuelve la disponibilidad, cuál resuelve el escalado de lecturas y cuál resuelve la recuperación ante desastres regional, porque es fácil confundirlas.

RDS Multi-AZ es para alta disponibilidad. En el despliegue clásico de instancia Multi-AZ, RDS mantiene un standby (réplica en espera) en otra AZ con replicación síncrona. El standby no atiende lecturas. Si el primario falla, o durante algunos mantenimientos, RDS hace failover automáticamente apuntando el nombre DNS del endpoint de la base de datos al standby, normalmente en uno o dos minutos, así que las aplicaciones se reconectan al mismo endpoint. El despliegue más reciente Multi-AZ DB cluster tiene dos standbys legibles y un failover más rápido, para MySQL y PostgreSQL.

Las read replicas (réplicas de lectura) son para escalar las lecturas. RDS copia los cambios de forma asíncrona a una o más réplicas, cada una con su propio endpoint, así que diriges allí los reportes y las consultas de lectura intensiva. Como la replicación es asíncrona, las réplicas pueden tener un ligero retraso (lag). Las réplicas pueden estar en la misma AZ, en otra AZ o en otra Región; una réplica entre Regiones también sirve como copia de recuperación ante desastres que puedes promover manualmente a una base de datos independiente. La promoción no es automática y rompe la replicación.

Amazon Aurora, compatible con MySQL y PostgreSQL, tiene una arquitectura diferente. El cluster volume guarda seis copias de tus datos en tres AZs, y hasta 15 Aurora Replicas comparten ese almacenamiento, así que el retraso de las réplicas suele ser muy bajo. Las réplicas atienden lecturas a través del reader endpoint, que balancea la carga entre ellas, y también son destinos de failover: si el escritor falla, Aurora promueve automáticamente una réplica, según los niveles de prioridad que configures. Así, en Aurora, las réplicas dan tanto escalado de lecturas como alta disponibilidad.

Aurora Global Database extiende un clúster entre Regiones: una Región primaria gestiona las escrituras, y hasta varias Regiones secundarias reciben replicación a nivel de almacenamiento con un retraso típico de menos de un segundo. Los clústeres secundarios atienden lecturas locales de baja latencia y se pueden promover durante una interrupción regional, lo que da un recovery point objective de segundos y un recovery time objective de alrededor de un minuto. Eso la convierte en la respuesta preferida para una base de datos relacional que debe sobrevivir a una falla regional con una pérdida mínima de datos.

Términos clave

Multi-AZ deployment (despliegue Multi-AZ)
Una configuración de RDS con un standby replicado de forma síncrona en otra AZ y failover automático.
Read replica (réplica de lectura)
Una copia de una base de datos replicada de forma asíncrona que se usa para descargar lecturas; puede promoverse manualmente.
Aurora Replica
Una instancia lectora que comparte el cluster volume de Aurora, atiende lecturas y es un destino de failover automático.
Aurora Global Database
Una configuración de Aurora que replica un clúster a Regiones secundarias con un retraso típico de menos de un segundo.
Ejemplo real

Un tablero de reportes ralentiza la base de datos de pedidos a fin de mes. El equipo agrega dos read replicas y apunta la herramienta de reportes hacia ellas, lo que resuelve el rendimiento. Por separado, habilita Multi-AZ en el primario para que una falla de hardware provoque un failover automático en lugar de una interrupción. Más adelante, cuando una nueva norma exige recuperarse de una falla de Región en minutos, migra a Aurora Global Database.

Consejo para el examen: Multi-AZ equivale a disponibilidad, no a rendimiento; el standby clásico no puede atender lecturas. Read replicas equivalen a rendimiento de lectura, con replicación asíncrona. DR relacional entre Regiones con RPO de segundos equivale a Aurora Global Database.

Comprueba lo que sabes

¿Puedes enviar consultas de lectura al standby en un despliegue clásico de instancia RDS Multi-AZ?

No. El standby existe solo para el failover. Usa read replicas (o un Multi-AZ DB cluster con standbys legibles) para las lecturas.

¿Qué le sucede a un clúster de Aurora cuando falla su instancia escritora?

Aurora promueve automáticamente una Aurora Replica como nuevo escritor, y el cluster endpoint apunta a ella.
