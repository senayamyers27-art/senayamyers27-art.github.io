AWS Certified Solutions Architect – Associate SAA-C03

Resiliencia de bases de datos relacionales: RDS Multi-AZ, read replicas, Aurora Replicas y Aurora Global Database

Amazon Relational Database Service (RDS) ejecuta bases de datos relacionales administradas: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server y Db2, además de Amazon Aurora. AWS se encarga del aprovisionamiento, los parches, los respaldos automáticos con restauración a un punto en el tiempo y la conmutación por error (failover). El examen evalúa qué función resuelve la disponibilidad, cuál resuelve el escalado de lecturas y cuál resuelve la recuperación ante desastres regional, porque es fácil confundirlas. Ten presentes tres preguntas: qué pasa cuando falla la instancia principal, a dónde va el tráfico de lectura y qué pasa cuando falla una región completa.

RDS Multi-AZ es para alta disponibilidad. En el despliegue clásico de instancia de base de datos Multi-AZ, RDS mantiene una réplica en espera (standby) en otra AZ con replicación síncrona, de modo que cada escritura confirmada está en ambas. El standby no atiende lecturas. Si la instancia principal falla, si su AZ sufre una interrupción o durante ciertos mantenimientos, RDS hace el failover automáticamente apuntando el nombre DNS del endpoint de la base de datos al standby, normalmente en uno o dos minutos, así que las aplicaciones se reconectan al mismo endpoint sin cambiar la configuración. El despliegue más reciente de clúster de base de datos Multi-AZ (Multi-AZ DB cluster), para MySQL y PostgreSQL, tiene dos standbys legibles en AZs distintas y suele tener un failover más rápido.

Las réplicas de lectura (read replicas) son para escalar las lecturas. RDS copia los cambios de forma asíncrona a una o más réplicas, cada una con su propio endpoint, así que diriges allí los informes y las consultas con muchas lecturas, y tu aplicación debe saber qué endpoint usar. Como la replicación es asíncrona, las réplicas pueden tener un ligero retraso, por lo que las consultas de lectura después de escritura (read-after-write) deben ir a la instancia principal. Las réplicas pueden estar en la misma AZ, en otra AZ o en otra región; una réplica entre regiones también sirve como copia de recuperación ante desastres que puedes promover manualmente a una base de datos independiente. La promoción no es automática y rompe la replicación. Una réplica puede ser a su vez Multi-AZ.

Amazon Aurora, compatible con MySQL y PostgreSQL, tiene una arquitectura diferente. El volumen del clúster guarda seis copias de tus datos en tres AZs y se repara solo, y hasta 15 Aurora Replicas comparten ese almacenamiento, así que el retraso de las réplicas suele ser muy bajo. El endpoint del clúster (cluster endpoint) siempre apunta a la instancia de escritura; el endpoint de lectura (reader endpoint) balancea las conexiones entre las réplicas. Las réplicas también son destinos de failover: si la instancia de escritura falla, Aurora promueve automáticamente una réplica según los niveles de prioridad que configures. Así que en Aurora las réplicas dan tanto escalado de lecturas como alta disponibilidad. Aurora Serverless agrega escalado automático de capacidad para cargas variables, y Aurora Auto Scaling puede agregar o quitar réplicas según la carga.

Aurora Global Database extiende un clúster entre regiones: una región principal atiende las escrituras, y las regiones secundarias reciben replicación a nivel de almacenamiento con un retraso típico de menos de un segundo. Los clústeres secundarios atienden lecturas locales de baja latencia y pueden promoverse durante una interrupción regional, con un objetivo de punto de recuperación (RPO) de segundos y un objetivo de tiempo de recuperación (RTO) de alrededor de un minuto. Un cambio administrado (managed switchover) mueve la región principal sin pérdida de datos en eventos planificados. Eso la convierte en la respuesta habitual para una base de datos relacional que debe sobrevivir a una falla regional con una pérdida mínima de datos.

Veamos un ejemplo práctico. Un panel de informes vuelve lenta la base de datos de pedidos a fin de mes. El equipo agrega dos read replicas y apunta la herramienta de informes a sus endpoints, lo que resuelve el rendimiento sin tocar la instancia principal. Por separado, habilita Multi-AZ en la instancia principal para que una falla de hardware provoque un failover automático en lugar de una interrupción. Más adelante, una nueva regla de negocio exige recuperarse de una falla de región en minutos y casi sin pérdida de datos, y el equipo migra a Aurora con un secundario de Global Database en otra región, usando el reader endpoint para los informes.

Errores comunes: enviar lecturas al standby del Multi-AZ clásico, lo cual es imposible; elegir Multi-AZ para mejorar el rendimiento de lectura; esperar que las read replicas hagan failover automático en RDS (la promoción es manual); olvidar el retraso de las réplicas cuando una aplicación debe leer sus propias escrituras; y elegir read replicas entre regiones cuando el requisito es un RPO de segundos y un RTO de alrededor de un minuto, que Aurora Global Database cumple de forma más directa.

Las palabras clave del examen son confiables. 'Alta disponibilidad', 'failover automático' o 'sobrevivir a la falla de una AZ' apunta a Multi-AZ. 'Muchas lecturas', 'las consultas de informes vuelven lenta la base de datos' o 'descargar las lecturas' apunta a read replicas. 'Escalado de lecturas y failover automático rápido con hasta 15 réplicas' apunta a Aurora Replicas. 'Recuperación ante desastres entre regiones con un RPO de segundos' o 'lecturas globales de baja latencia para una base de datos relacional' apunta a Aurora Global Database.

Términos clave

Despliegue Multi-AZ (Multi-AZ deployment)
Una configuración de RDS con un standby replicado de forma síncrona en otra AZ y failover automático.
Réplica de lectura (read replica)
Una copia de una base de datos replicada de forma asíncrona que se usa para descargar lecturas; puede promoverse manualmente.
Retraso de réplica (replica lag)
La demora entre una escritura en la instancia principal y su aparición en una réplica asíncrona.
Aurora Replica
Una instancia de lectura que comparte el volumen del clúster de Aurora, atiende lecturas y es un destino de failover automático.
Endpoint de lectura (reader endpoint)
Un endpoint de Aurora que balancea las conexiones de lectura entre las réplicas del clúster.
Aurora Global Database
Una configuración de Aurora que replica un clúster a regiones secundarias con un retraso típico de menos de un segundo.
Ejemplo real

Una empresa de educación en línea ejecuta PostgreSQL en una sola instancia de RDS. Una interrupción de AZ deja el sitio caído durante horas, y el tráfico de la semana de exámenes vuelve lentas las consultas. El equipo habilita Multi-AZ para el failover automático, agrega read replicas para las consultas con muchas lecturas del catálogo de cursos y enruta esas consultas a través de una cadena de conexión de lectura separada en la aplicación. La siguiente interrupción de AZ provoca un failover de alrededor de un minuto en lugar de una caída.

Consejo para el examen: Multi-AZ es igual a disponibilidad, no a rendimiento; el standby clásico no puede atender lecturas. Read replicas es igual a rendimiento de lectura, con replicación asíncrona. Recuperación ante desastres relacional entre regiones con un RPO de segundos es igual a Aurora Global Database.

Comprueba lo que sabes

¿Puedes enviar consultas de lectura al standby en un despliegue clásico de instancia RDS Multi-AZ?

No. El standby existe solo para el failover. Usa read replicas (o un Multi-AZ DB cluster con standbys legibles) para las lecturas.

¿Qué le pasa a un clúster de Aurora cuando falla su instancia de escritura?

Aurora promueve automáticamente una Aurora Replica como nueva instancia de escritura, y el cluster endpoint apunta a ella.

¿Una read replica de RDS se promueve automáticamente cuando falla la instancia principal?

No. La promoción es una acción manual que convierte la réplica en una base de datos independiente y termina la replicación.

¿Por qué un usuario podría no ver una actualización justo después de guardarla cuando las lecturas van a una réplica?

La replicación hacia las read replicas es asíncrona, así que puede existir un breve retraso; las consultas de lectura después de escritura deben ir a la instancia principal.
