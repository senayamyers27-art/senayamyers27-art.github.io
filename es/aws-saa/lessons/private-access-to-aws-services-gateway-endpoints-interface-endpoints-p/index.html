Acceso privado a servicios de AWS: gateway endpoints, interface endpoints (PrivateLink) y endpoint policies

A la mayoría de los servicios de AWS, como S3, DynamoDB, SQS y Secrets Manager, se llega a través de endpoints de servicio públicos. Una instancia privada puede alcanzarlos mediante un NAT gateway, pero entonces el tráfico sale del espacio de direcciones privado de tu VPC, necesita una ruta hacia internet y pagas cargos de procesamiento de datos del NAT. Los VPC endpoints permiten que los recursos de tu VPC lleguen a los servicios de AWS de forma privada, sin internet gateway, sin dispositivo NAT y sin direcciones IP públicas, y el tráfico permanece en la red de AWS. Muchas preguntas de seguridad y de costos del examen dependen de elegir el tipo correcto de endpoint. Los gateway endpoints existen para exactamente dos servicios: Amazon S3 y Amazon DynamoDB. Creas el endpoint y seleccionas las tablas de rutas; AWS agrega una ruta cuyo destino es la lista de prefijos (prefix list) del servicio (una lista administrada de los rangos de IP del servicio, que aparece como pl-xxxxxxxx) y cuyo destino de salto es el endpoint. Las aplicaciones siguen usando el nombre de host normal del servicio, y la tabla de rutas hace el resto. Los gateway endpoints no tienen cargo por hora ni por datos. Solo funcionan para tráfico que se origina dentro de la VPC; no pueden usarse desde las instalaciones locales (on-premises) a través de VPN o Direct Connect, ni desde una VPC emparejada (peered).

Los interface endpoints funcionan con AWS PrivateLink. Cada uno coloca una interfaz de red elástica con una dirección IP privada en las subredes que elijas, una por AZ para resiliencia, y un security group controla quién puede llegar a ella. Con el DNS privado habilitado, el nombre de host normal del servicio, como secretsmanager.eu-west-1.amazonaws.com, se resuelve a esas IPs privadas dentro de la VPC, así que las aplicaciones no requieren cambios de código. Hay interface endpoints para la mayoría de los servicios de AWS, incluido S3, y para servicios propios o de socios publicados como endpoint services detrás de un Network Load Balancer. Se cobran por hora y por AZ, más un cargo por gigabyte procesado. Como son direcciones IP reales, se puede llegar a ellos desde redes on-premises a través de VPN o Direct Connect y desde VPCs emparejadas o conectadas mediante Transit Gateway.

Las endpoint policies son políticas basadas en recursos que se aplican al propio endpoint y limitan lo que se puede hacer a través de él. Por ejemplo, la endpoint policy de un gateway endpoint de S3 puede permitir el acceso solo a los buckets propios de la empresa, lo que ayuda a impedir que se copien datos a un bucket personal. El otro lado del control está en el recurso: una bucket policy puede usar la condición aws:SourceVpce para denegar cualquier solicitud que no haya llegado a través de un endpoint específico, o aws:SourceVpc para una VPC específica. Juntas, las endpoint policies y las políticas de recursos forman un perímetro de datos: identidades de confianza que acceden a recursos de confianza desde redes esperadas.

PrivateLink también resuelve un problema de redes: exponer un servicio a muchas VPCs consumidoras, incluso en otras cuentas, sin emparejar redes completas y sin preocuparse por rangos CIDR superpuestos. El proveedor coloca el servicio detrás de un Network Load Balancer y crea un endpoint service; cada consumidor crea un interface endpoint en su propia VPC y solo ve ese endpoint, no la red del proveedor. El tráfico fluye en un solo sentido, del consumidor al proveedor, lo que mantiene reducida la exposición.

Veamos un ejemplo práctico. Una flota de análisis en subredes privadas lee terabytes al día desde S3 a través de un NAT gateway, y los cargos de procesamiento del NAT son altos. El arquitecto agrega un gateway endpoint de S3 a las tablas de rutas privadas, con una endpoint policy que permite solo los buckets de datos de la empresa. Ahora el tráfico permanece en la red de AWS, los cargos del NAT por ese tráfico desaparecen y una bucket policy deniega las solicitudes que no llegan a través del endpoint. La misma flota también llama a Secrets Manager y SQS, así que el arquitecto agrega interface endpoints para esos dos servicios en cada AZ con el DNS privado habilitado, y elimina el NAT gateway cuando nada más necesita internet.

Errores comunes: esperar que un gateway endpoint funcione desde on-premises o desde una VPC emparejada; olvidar asociar el gateway endpoint con todas las tablas de rutas privadas; crear un interface endpoint en una sola AZ; dejar el security group del endpoint cerrado a la aplicación en el puerto 443; y suponer que una endpoint policy otorga acceso por sí sola, cuando IAM y las políticas de recursos también deben permitir la llamada.

Las preguntas del examen suelen depender de dónde viene el tráfico y a qué servicio va dirigido. 'S3 o DynamoDB desde dentro de la VPC al menor costo' apunta a un gateway endpoint. 'Cualquier otro servicio de forma privada', 'acceso desde on-premises' o 'compartir un servicio con muchas VPCs o cuentas con CIDRs superpuestos' apunta a un interface endpoint y PrivateLink. 'Asegurar que al bucket solo se pueda llegar desde nuestra VPC' apunta a una bucket policy con aws:SourceVpce o aws:SourceVpc.

Términos clave

VPC endpoint
Una conexión privada desde una VPC hacia un servicio compatible de AWS o de un socio sin usar internet.
Gateway endpoint
Un destino en la tabla de rutas que da acceso privado y gratuito a S3 o DynamoDB desde dentro de una VPC.
Interface endpoint
Una interfaz de red de PrivateLink con IPs privadas en tus subredes que sirve de entrada a un servicio de AWS o de un socio.
AWS PrivateLink
La tecnología que expone un servicio mediante interface endpoints en las VPCs consumidoras sin emparejamiento.
Endpoint policy
Una política de recurso en un VPC endpoint que restringe qué acciones y recursos se pueden alcanzar a través de él.
aws:SourceVpce
Una clave de condición que coincide con el ID del VPC endpoint por el que llegó una solicitud.
Ejemplo real

Una empresa de software vende un servicio de monitoreo a 300 clientes, muchos de los cuales usan el mismo rango 10.0.0.0/16. En lugar de VPC peering, que falla con CIDRs superpuestos, coloca el servicio detrás de un Network Load Balancer y lo publica como un endpoint service de PrivateLink. Cada cliente crea un interface endpoint en su propia VPC después de que la empresa acepta la solicitud de conexión, y el tráfico llega al servicio de forma privada sin que ninguna de las partes exponga su red.

Consejo para el examen: S3 o DynamoDB, desde dentro de la VPC, al menor costo: gateway endpoint. Cualquier otro servicio, o acceso desde on-premises, o compartir un servicio con otras VPCs: interface endpoint (PrivateLink).

Comprueba lo que sabes

Servidores on-premises conectados por Direct Connect necesitan acceso privado a S3. ¿Pueden usar un gateway endpoint?

No. Los gateway endpoints solo atienden tráfico que se origina en la VPC. Usa un interface endpoint de S3, que tiene IPs privadas alcanzables a través de Direct Connect.

¿Cómo te aseguras de que a un bucket solo se pueda llegar a través de un VPC endpoint específico?

Agrega una bucket policy que deniegue las solicitudes cuando aws:SourceVpce no sea igual al ID de ese endpoint.

¿Qué dos servicios admiten gateway endpoints?

Amazon S3 y Amazon DynamoDB; todos los demás servicios usan interface endpoints.

Una aplicación en una subred privada llama a Secrets Manager y falla después de eliminar el NAT gateway. ¿Qué lo soluciona sin acceso a internet?

Crear un interface endpoint de Secrets Manager en las subredes de la aplicación con el DNS privado habilitado y un security group que permita HTTPS desde la aplicación.
