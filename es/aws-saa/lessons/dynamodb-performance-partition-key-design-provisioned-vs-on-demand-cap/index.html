Rendimiento de DynamoDB: diseño de la partition key, capacidad provisioned vs on-demand, auto scaling e índices secundarios

DynamoDB ofrece un rendimiento constante a cualquier escala, pero solo si la tabla está diseñada para la forma en que se va a acceder a ella. A diferencia de las bases de datos relacionales, diseñas las tablas de DynamoDB en torno a las consultas, no en torno a entidades normalizadas.

Cada elemento tiene una clave primaria. Una clave primaria simple es solo una partition key (clave de partición); una clave primaria compuesta agrega una sort key (clave de ordenamiento). DynamoDB aplica un hash a la partition key para decidir qué partición física almacena el elemento, y cada partición tiene un límite de rendimiento. Si muchas solicitudes van al mismo valor de partition key, se forma una hot partition (partición caliente), y las solicitudes sufren throttling aunque la tabla en su conjunto tenga capacidad de sobra. Las buenas partition keys tienen alta cardinalidad y reparten las solicitudes de forma uniforme, como un ID de usuario o un ID de pedido. Las malas tienen pocos valores o concentran el tráfico, como un campo de estado o la fecha de hoy. Cuando un valor es inevitablemente caliente, el write sharding agrega un sufijo aleatorio o calculado para repartirlo. La adaptive capacity ayuda a absorber algo de desequilibrio, pero no corrige un mal diseño.

La capacidad viene en dos modos. La provisioned capacity (capacidad aprovisionada) define read capacity units (RCUs) y write capacity units (WCUs). Una RCU es una lectura fuertemente consistente por segundo, o dos lecturas eventualmente consistentes, de un elemento de hasta 4 KB; una WCU es una escritura por segundo de un elemento de hasta 1 KB. Las operaciones transaccionales usan el doble de unidades. El modo provisioned se adapta al tráfico predecible, puede usar auto scaling, que ajusta la capacidad entre un mínimo y un máximo para seguir una utilización objetivo, y puede usar reserved capacity para ahorrar aún más. El modo on-demand (bajo demanda) cobra por solicitud sin planificación de capacidad y se adapta al instante al tráfico que crece rápido, lo que encaja con cargas nuevas, impredecibles o con picos. Puedes cambiar de modo, con algunos límites sobre la frecuencia.

Los índices secundarios permiten consultas sobre atributos distintos de la clave primaria. Un global secondary index (GSI) tiene su propia partition key y una sort key opcional, se puede crear o eliminar en cualquier momento, tiene su propia capacidad y solo admite lecturas eventualmente consistentes. Un local secondary index (LSI) comparte la partition key de la tabla pero usa una sort key diferente, debe crearse junto con la tabla y admite lecturas fuertemente consistentes. Los índices proyectan atributos de la tabla; proyectar menos atributos ahorra almacenamiento y capacidad de escritura.

Por último, prefiere Query, que lee los elementos con un valor de partition key, en lugar de Scan, que lee toda la tabla y consume capacidad por cada elemento que examina. Si una carga de trabajo necesita muchos scans, probablemente necesita un nuevo índice o un almacén de datos diferente.

Términos clave

Partition key (clave de partición)
El atributo clave al que DynamoDB aplica un hash para distribuir los elementos entre particiones.
Hot partition (partición caliente)
Una partición que recibe una proporción desmedida del tráfico, lo que provoca throttling.
Global secondary index (índice secundario global)
Un índice con una partition key diferente que se puede agregar en cualquier momento y admite lecturas eventualmente consistentes.
On-demand capacity (capacidad bajo demanda)
Un modo de facturación de DynamoDB que cobra por solicitud sin planificación de capacidad.
Ejemplo real

Una app de votación usa el nombre del candidato como partition key, y en la noche de la elección las particiones de los dos candidatos principales sufren throttling. El equipo cambia las escrituras para usar claves como candidateA#7, con un sufijo aleatorio del 1 al 10, y luego suma los fragmentos al leer. También cambia la tabla al modo on-demand porque el tráfico es impredecible.

Consejo para el examen: Throttling mientras la capacidad total no se usa apunta a una hot partition y a un mal diseño de claves. Tráfico desconocido o con picos apunta a on-demand; tráfico estable y predecible apunta a provisioned con auto scaling. ¿Necesitas un nuevo patrón de consulta después del lanzamiento? Agrega un GSI, porque los LSI deben crearse junto con la tabla.

Comprueba lo que sabes

¿Cuántas RCUs se necesitan para 10 lecturas fuertemente consistentes por segundo de elementos de 6 KB?

20. Cada lectura de 6 KB se redondea a 8 KB, que son dos unidades de 4 KB, así que 10 x 2 = 20 RCUs.

Necesitas consultar una tabla existente por dirección de correo electrónico, que no forma parte de la clave. ¿Qué agregas?

Un global secondary index con el correo electrónico como su partition key, ya que los LSI solo se pueden crear junto con la tabla.
