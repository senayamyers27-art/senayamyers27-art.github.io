Compilar y subir imágenes con `az acr build` (quick tasks) y ACR Tasks activadas por commits, actualizaciones de la imagen base o programaciones

No necesitas tener Docker instalado localmente para producir una imagen para Azure. ACR Tasks es un conjunto de funciones de compilación dentro de Azure Container Registry que ejecuta compilaciones en cómputo administrado por Azure y sube el resultado directamente a tu registro. Esto es importante en equipos de desarrollo restringidos, en shells en la nube y en pipelines de CI donde prefieres no ejecutar un daemon de Docker.

La forma más simple es una quick task (tarea rápida). az acr build --registry myregistry --image orders-api:{{.Run.ID}} . sube el directorio actual (el contexto de compilación, filtrado por .dockerignore) a ACR, compila ahí el Dockerfile, transmite el registro de compilación de vuelta a tu terminal y sube la imagen si la compilación tiene éxito. {{.Run.ID}} es un marcador de posición que ACR reemplaza con el ID único de la ejecución, lo que te da una etiqueta única para cada compilación. Puedes agregar --file para apuntar a otro Dockerfile y --platform para apuntar a otro sistema operativo o arquitectura.

Las quick tasks son puntuales y manuales. Cuando quieres que las compilaciones ocurran automáticamente, creas una tarea con az acr task create. Una tarea guarda la definición de compilación (contexto, Dockerfile, nombre de la imagen) y uno o más desencadenadores (triggers). Su contexto suele ser un repositorio Git, por ejemplo la URL de un repositorio de GitHub con una rama, más un token de acceso personal para que ACR pueda leer el repositorio y registrar un webhook.

Vale la pena memorizar los tres tipos de trigger. Un trigger de actualización de código fuente (trigger de commit) ejecuta la tarea cuando se sube un commit, o se abre un pull request, en la rama configurada. Un trigger de actualización de la imagen base ejecuta la tarea cuando la imagen base de la que depende la línea FROM de tu Dockerfile se actualiza en ACR o en un registro público, de modo que la imagen de tu app recoge automáticamente los parches del sistema operativo y del runtime. Un trigger de temporizador ejecuta la tarea según una programación definida con una expresión cron mediante --schedule, útil para recompilaciones nocturnas o trabajos de mantenimiento.

az acr task create --registry myregistry --name build-orders \
  --image orders-api:{{.Run.ID}} \
  --context <git-repo-url>#main \
  --file Dockerfile --git-access-token $PAT

az acr task run --registry myregistry --name build-orders
az acr task list-runs --registry myregistry --output table

Los triggers de actualización de la imagen base están habilitados de forma predeterminada al crear una tarea, y son la función que más probablemente aparezca en un escenario sobre mantener las imágenes con parches sin esfuerzo de los desarrolladores. Para flujos más complejos, una tarea de varios pasos definida en un archivo YAML (que se ejecuta con az acr run) puede compilar, probar y subir varias imágenes en secuencia, y también es la forma de ejecutar comandos de mantenimiento como el comando purge que se ve en la siguiente lección.

Términos clave

Quick task (tarea rápida)
Una compilación puntual en la nube iniciada con az acr build que sube el contexto, compila en ACR y sube la imagen.
ACR task (tarea de ACR)
Una definición de compilación guardada en un registro que se ejecuta automáticamente con triggers como commits, actualizaciones de la imagen base o una programación.
Base image update trigger (trigger de actualización de la imagen base)
Un trigger de ACR Tasks que recompila la imagen de tu app cuando se actualiza la imagen de su línea FROM.
Run ID (ID de ejecución)
El identificador único de cada ejecución de ACR Tasks, disponible como el marcador {{.Run.ID}} para etiquetas únicas.
Ejemplo real

Un equipo de seguridad quiere que cada imagen de app se recompile cada vez que la imagen base de Python recibe un parche de seguridad, sin que los desarrolladores lo noten. El equipo de plataforma crea una tarea de ACR por app con un trigger de commit en main y el trigger predeterminado de actualización de la imagen base. Cuando se publica una imagen base con parches, ACR recompila cada imagen de app dependiente y sube una nueva etiqueta única, y el pipeline de despliegue la toma.

Consejo para el examen: Relaciona el trigger con la redacción: código subido significa trigger de commit; parches del sistema operativo o del runtime en la imagen padre significan trigger de actualización de la imagen base; y cada noche o cada semana significa trigger de temporizador con una programación cron.

Comprueba lo que sabes

¿Qué hace az acr build que no hacen docker build más docker push?

Sube el contexto de compilación y ejecuta la compilación en cómputo administrado por Azure, y luego sube la imagen a ACR, así que no se necesita un motor Docker local.

¿Qué trigger de ACR Tasks mantiene una imagen de app con parches cuando cambia su imagen padre?

El trigger de actualización de la imagen base, que recompila la imagen cuando se actualiza la imagen de su línea FROM.
