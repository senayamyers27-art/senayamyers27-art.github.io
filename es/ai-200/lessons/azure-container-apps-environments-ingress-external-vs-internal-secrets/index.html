Azure Container Apps: entornos, ingress (externo vs interno), secretos e identidad administrada

Azure Container Apps es una plataforma de contenedores sin servidor (serverless) construida sobre Kubernetes y componentes de código abierto como KEDA (Kubernetes Event-driven Autoscaling), Envoy y Dapr, sin exponer la API de Kubernetes. Despliegas imágenes de contenedor y describes el escalado y la red; Azure ejecuta el clúster. Encaja con APIs, procesadores en segundo plano y microservicios que necesitan escalar, incluso hasta cero.

Cada container app vive en un entorno de Container Apps (Container Apps environment), un límite seguro alrededor de un grupo de apps. Las apps del mismo entorno comparten una red virtual y escriben registros en el mismo área de trabajo de Log Analytics, y pueden llamarse entre sí por nombre. Creas uno con az containerapp env create, opcionalmente en tu propia VNet. Coloca en un mismo entorno las apps que se comunican o comparten ciclo de vida; separa entornos cuando necesites aislamiento, por ejemplo entre producción y pruebas.

El ingress controla cómo llega el tráfico HTTP o TCP a tu app. Con el ingress deshabilitado, la app no recibe tráfico entrante, lo cual sirve para workers de colas. Con ingress externo, la app obtiene un nombre de dominio completo (FQDN) público accesible desde internet (o desde la VNet, en un entorno configurado con un balanceador de carga interno). Con ingress interno, la app solo es accesible desde dentro del entorno, por ejemplo desde otras container apps, que es la configuración habitual para servicios de back end. También defines el puerto de destino en el que escucha tu contenedor, el transporte (HTTP/1, HTTP/2 o TCP) y si se permite HTTP no seguro.

az containerapp create -n orders -g rg --environment prod-env \
  --image myregistry.azurecr.io/orders-api:20260914.3 \
  --ingress internal --target-port 8000 \
  --secrets db-pass=$DB_PASS \
  --env-vars DB_PASSWORD=secretref:db-pass \
  --user-assigned <identity-resource-id>

Los secretos se definen a nivel de app y están disponibles para todas las revisiones. Luego los referencias desde variables de entorno con secretref: (como arriba) o los montas como archivos en un volumen. Cambiar el valor de un secreto no crea una nueva revisión ni reinicia las existentes; debes reiniciar o crear una nueva revisión para que las réplicas en ejecución lo tomen. En lugar de guardar el valor directamente, un secreto puede ser una referencia de Key Vault, en la que Container Apps lo lee de Key Vault usando una identidad administrada.

Container Apps admite identidades administradas tanto asignadas por el sistema como asignadas por el usuario. La misma identidad puede descargar imágenes de ACR (AcrPull), leer secretos de Key Vault y llamar a servicios de datos como Cosmos DB o Service Bus mediante DefaultAzureCredential en tu código Python, de modo que la app no tiene ninguna cadena de conexión. Recuerda que el ingress entrante y la identidad saliente son asuntos separados: el ingress decide quién puede llegar a la app; la identidad decide a qué puede llegar la app.

Términos clave

Container Apps environment (entorno de Container Apps)
Un límite que agrupa container apps que comparten una red virtual y un área de trabajo de Log Analytics.
External ingress (ingress externo)
Ingress que expone la app fuera del entorno, normalmente con un punto de conexión público.
Internal ingress (ingress interno)
Ingress que hace que la app solo sea accesible desde dentro de su entorno.
secretref
El prefijo que se usa en una variable de entorno de una container app para tomar su valor de un secreto a nivel de app.
Ejemplo real

Una tienda ejecuta un front end web público y una API de pedidos privada. Ambas son container apps en un mismo entorno: el front end tiene ingress externo en el puerto 8000 y la API de pedidos tiene ingress interno, así que solo el front end puede llamarla por nombre. Cada app tiene una identidad asignada por el usuario con AcrPull y Key Vault Secrets User, y las contraseñas de base de datos son referencias de Key Vault expuestas mediante variables de entorno con secretref.

Consejo para el examen: Los servicios de back end a los que solo deben llamar otras apps del entorno usan ingress interno; los workers que solo procesan colas no necesitan ingress. Recuerda también que actualizar un secreto no reinicia las réplicas por sí solo.

Comprueba lo que sabes

¿Qué comparten las apps del mismo entorno de Container Apps?

Un límite de red virtual y un área de trabajo de Log Analytics, y pueden comunicarse directamente entre sí.

¿Cómo lee un contenedor un secreto a nivel de app como variable de entorno?

Estableciendo el valor de la variable en secretref:<nombre-del-secreto>, que inyecta el secreto en tiempo de ejecución.
