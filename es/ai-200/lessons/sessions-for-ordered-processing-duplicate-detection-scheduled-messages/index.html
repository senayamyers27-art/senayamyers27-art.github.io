Sesiones para el procesamiento ordenado, detección de duplicados, mensajes programados y filtros de suscripción (SQL y correlación)

Los niveles Standard y Premium de Service Bus agregan características que resuelven problemas comunes de mensajería: orden estricto, duplicados accidentales, entrega diferida y enrutamiento. Cada una corresponde claramente a un escenario, así que apréndelas como pares de problema y solución.

Las sesiones ofrecen procesamiento ordenado de mensajes relacionados. Habilitas las sesiones (requires session) al crear una cola o suscripción, y a partir de ahí cada mensaje debe llevar un session_id, como un ID de pedido o de cliente. Service Bus garantiza la entrega FIFO (primero en entrar, primero en salir) dentro de una sesión, y un receptor bloquea una sesión completa, así que solo un receptor procesa una sesión determinada a la vez mientras otros receptores atienden otras sesiones en paralelo. Las sesiones también ofrecen estado de sesión, un pequeño valor almacenado por sesión para llevar el control del progreso.

from azure.servicebus import NEXT_AVAILABLE_SESSION
sender.send_messages(ServiceBusMessage(body, session_id="order-1001"))
with client.get_queue_receiver("order-steps", session_id=NEXT_AVAILABLE_SESSION) as r:
    print(r.session.session_id)
    for msg in r.receive_messages(max_wait_time=5):
        r.complete_message(msg)

La detección de duplicados resuelve el caso en que un emisor reintenta después de un error de red y el agente recibe el mismo mensaje dos veces. Cuando se habilita en una cola o tema al crearlo, Service Bus recuerda cada message_id durante una ventana configurable de historial de detección de duplicados y descarta en silencio cualquier mensaje posterior con el mismo ID dentro de esa ventana. Solo funciona si el emisor define un ID de mensaje significativo derivado de los datos de negocio, como el número de pedido, en lugar de un valor aleatorio.

Los mensajes programados se envían ahora, pero solo se vuelven visibles en el momento elegido. Define scheduled_enqueue_time_utc en el mensaje o llama a sender.schedule_messages(msg, when), que devuelve números de secuencia que puedes pasar a cancel_scheduled_messages si cambian los planes. Úsalos para recordatorios, reintentos diferidos o flujos de trabajo basados en tiempo. (La hora de puesta en cola programada también está disponible en Basic).

Los filtros de suscripción deciden qué mensajes del tema recibe cada suscripción. Cada suscripción nueva empieza con una regla predeterminada que acepta todos los mensajes. Un filtro SQL usa una condición similar a SQL sobre las propiedades del mensaje, por ejemplo region = 'EU' AND amount > 100; es flexible, pero su evaluación cuesta más. Un filtro de correlación coincide con valores exactos de propiedades del sistema (como subject, correlation ID, message ID o content type) y de propiedades de usuario; es más simple y eficiente, así que prefiérelo cuando solo necesites coincidencias por igualdad. Las reglas también pueden incluir una acción SQL que modifica las propiedades del mensaje cuando entra en la suscripción. Un filtro booleano true o false acepta todo o nada.

az servicebus topic subscription rule create -g rg --namespace-name shop-sb \
  --topic-name orders --subscription-name eu-large --name EuLarge \
  --filter-sql-expression "region = 'EU' AND amount > 100"

Recuerda eliminar la regla predeterminada cuando agregues tu propio filtro; de lo contrario, la suscripción seguirá recibiendo todos los mensajes.

Términos clave

Session (sesión)
Un grupo de mensajes que comparten un ID de sesión y que Service Bus entrega en orden a un receptor a la vez.
Duplicate detection (detección de duplicados)
Una configuración de cola o tema que descarta los mensajes cuyo ID de mensaje ya se vio dentro de una ventana de historial.
Scheduled message (mensaje programado)
Un mensaje que se acepta de inmediato, pero que queda disponible para los receptores solo a una hora UTC especificada.
SQL filter (filtro SQL)
Una regla de suscripción que usa una expresión similar a SQL sobre las propiedades del mensaje.
Correlation filter (filtro de correlación)
Una regla de suscripción que coincide con valores exactos de propiedades del sistema o de usuario, más económica que un filtro SQL.
Ejemplo real

Los eventos de un mismo pedido a veces se procesaban fuera de orden: el envío antes del pago. El equipo habilitó sesiones en la cola order-steps y usó el ID de pedido como ID de sesión, lo que obligó a procesar en orden cada pedido. También habilitaron la detección de duplicados basada en un ID de evento, porque el sistema de origen reintentaba los envíos, y usaron un filtro de correlación sobre subject para enrutar los reembolsos a una suscripción separada.

Consejo para el examen: FIFO por cliente o por pedido significa sesiones; los envíos reintentados que crean duplicados significan detección de duplicados con IDs de mensaje de negocio; para enrutar por valores exactos de propiedades, prefiere los filtros de correlación sobre los filtros SQL.

Comprueba lo que sabes

¿Qué debe definir un emisor para que funcione la detección de duplicados?

Un message_id coherente derivado de los datos de negocio, para que un envío reintentado lleve el mismo ID y se descarte.

¿Por qué una suscripción con un filtro SQL nuevo podría seguir recibiendo todos los mensajes?

La regla predeterminada que acepta todos los mensajes sigue presente; hay que eliminarla.
