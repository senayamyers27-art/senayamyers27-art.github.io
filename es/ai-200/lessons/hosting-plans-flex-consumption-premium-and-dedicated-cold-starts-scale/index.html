Planes de hospedaje: Flex Consumption, Premium y Dedicated; arranques en frío, límites de escalado e integración con VNet

El plan de hospedaje decide cómo escala tu function app, cómo se factura, qué redes puede usar y cuánto tiempo pueden ejecutarse las funciones. El mismo código se ejecuta en cualquier plan, pero la elección determina el comportamiento en producción.

Flex Consumption es el plan serverless recomendado actualmente para apps nuevas, y se ejecuta en Linux. Escala dinámicamente según los eventos, incluso hasta cero, y factura el tiempo de ejecución y la memoria de las instancias mientras se ejecutan, más las instancias siempre listas (always-ready) que configures. Las instancias siempre listas mantienen activo un número elegido de instancias para funciones o grupos concretos, lo que reduce los arranques en frío. Escala por función (las funciones HTTP, las de blob y Durable Functions escalan como grupos; los demás triggers escalan de forma individual), te permite elegir el tamaño de memoria de la instancia y admite integración con redes virtuales, algo de lo que carecía el hospedaje de consumo anterior. El plan Consumption anterior todavía existe, pero se considera heredado para las apps nuevas de Linux.

Un arranque en frío (cold start) es el retraso que ocurre cuando llega una solicitud o un evento y no hay ninguna instancia en ejecución: la plataforma debe asignar una instancia, iniciar el runtime, cargar tu código de Python e importar las dependencias. Los planes que escalan a cero ahorran dinero, pero pagan esta latencia después de periodos de inactividad. Las mitigaciones son las instancias siempre listas o precalentadas, un conjunto de dependencias más ligero con importaciones diferidas y los planes que nunca escalan a cero.

El plan Premium (Elastic Premium) se ejecuta en instancias precalentadas y siempre listas, así que no hay arranque en frío para el número mínimo de instancias, y aun así escala horizontalmente de forma elástica según los eventos. Admite integración con VNet, private endpoints, tiempos de ejecución más largos e instancias más potentes, y factura por segundo de núcleo y memoria de las instancias asignadas, incluidas las mínimas siempre listas, así que nunca cuesta cero. Elígelo cuando necesites cero arranques en frío más escalado controlado por eventos, o características que el plan Flex no tiene.

El plan Dedicated ejecuta las funciones en un App Service plan que ya pagas. El escalado es manual o mediante reglas de escalado automático de App Service, en lugar de estar controlado por eventos, y debes habilitar Always On para que el host permanezca cargado y los triggers de temporizador o de cola sigan activándose. Elígelo cuando tengas capacidad sobrante en un App Service plan existente, necesites costos fijos predecibles o necesites funciones de larga duración con control total. App Service Environment es la variante aislada.

Los límites de escalado y los tiempos de espera varían según el plan. Cada plan limita el número máximo de instancias a las que puede escalar una app, y puedes definir un máximo más bajo por app para proteger recursos posteriores, como una base de datos. Los tiempos de espera de ejecución también varían: en el plan Consumption heredado, las funciones están limitadas a un tiempo máximo de ejecución corto medido en minutos, mientras que Flex Consumption, Premium y Dedicated admiten ejecuciones mucho más largas o sin límite. La configuración functionTimeout de host.json controla esto dentro del rango permitido por el plan. Las funciones activadas por HTTP están limitadas además por el tiempo de espera de inactividad del equilibrador de carga, así que el trabajo largo debe delegarse a una cola.

La integración con VNet permite que las funciones lleguen a recursos privados, como una base de datos detrás de un private endpoint. Está disponible en Flex Consumption, Premium y Dedicated. El acceso privado de entrada usa private endpoints en la function app.

Términos clave

Flex Consumption
Un plan serverless de Functions en Linux con escalado a cero controlado por eventos, escalado por función, instancias siempre listas e integración con VNet.
Premium plan (plan Premium)
Un plan elástico de Functions con instancias precalentadas, sin arranque en frío para las instancias mínimas y compatible con VNet.
Dedicated plan (plan dedicado)
Ejecutar funciones en un App Service plan con escalado manual o automático y costo fijo.
Cold start (arranque en frío)
La latencia de inicio cuando se invoca una función y no hay ninguna instancia activa disponible.
Always On
Una configuración de App Service que mantiene cargada una function app del plan Dedicated para que los triggers sigan activándose.
Ejemplo real

Una API interna creada con Functions debe llamar a un servidor PostgreSQL al que solo se llega mediante un private endpoint, responder sin retrasos por arranque en frío durante el horario laboral y costar poco por la noche. El equipo elige Flex Consumption con integración con VNet y un pequeño número de instancias siempre listas para las funciones HTTP. Una app separada con trabajo por lotes nocturno se ejecuta en un App Service plan existente con Always On.

Consejo para el examen: Cero arranques en frío más escalado elástico apunta a Premium (o a Flex con instancias siempre listas); si ya pagas un App Service plan, apunta a Dedicated con Always On; el acceso a redes privadas necesita un plan con integración con VNet.

Comprueba lo que sabes

¿Por qué debe habilitarse Always On en una function app del plan Dedicated con triggers de temporizador?

Sin él, el host puede descargarse cuando está inactivo, así que los temporizadores y los triggers que no son HTTP pueden dejar de activarse.

Menciona dos formas de reducir los arranques en frío de una function app de Python.

Usar instancias siempre listas (Flex) o instancias precalentadas (Premium), y reducir o importar de forma diferida las dependencias pesadas.
