Escalado de Container Apps: reglas HTTP, reglas de eventos de KEDA (por ejemplo, longitud de una cola de Service Bus), réplicas mínimas/máximas y escalado a cero

Container Apps escala horizontalmente: agrega o quita réplicas (copias en ejecución de una revisión) según las reglas de escalado que definas. El escalado lo impulsa KEDA (Kubernetes Event-driven Autoscaling), que puede vigilar la carga HTTP, las conexiones TCP, la CPU o la memoria, y decenas de orígenes de eventos como colas y flujos. Cada revisión tiene su propia configuración de escalado, porque esa configuración forma parte de la plantilla de la revisión.

Dos números acotan todo: el mínimo de réplicas y el máximo de réplicas. Con un mínimo de 0, la app puede escalar a cero cuando no hay tráfico ni eventos pendientes, y no pagas nada por réplicas en ejecución mientras está inactiva (en el perfil de consumo). El costo es un arranque en frío (cold start): la primera solicitud o mensaje después de la inactividad espera a que se inicie una réplica. Con un mínimo de 1 o más, la app siempre está caliente. El máximo limita el costo y protege a los sistemas posteriores, como una base de datos, de verse saturados.

Una regla de escalado HTTP agrega réplicas según las solicitudes HTTP simultáneas por réplica. Si configuras 50 solicitudes simultáneas y hay 400 solicitudes en curso, KEDA apunta a unas ocho réplicas, dentro de tu mínimo y tu máximo. Si no defines ninguna regla en una app con ingress, se aplica una regla HTTP predeterminada. Las reglas TCP funcionan de forma parecida con las conexiones simultáneas.

Las reglas controladas por eventos (personalizadas) usan un scaler de KEDA. Para una cola de Service Bus, el scaler azure-servicebus lee el número de mensajes de la cola y escala para que cada réplica maneje aproximadamente el número objetivo de mensajes. La regla necesita metadatos (espacio de nombres, nombre de la cola, número objetivo de mensajes) y autenticación, ya sea un secreto con una cadena de conexión o, preferiblemente, una identidad administrada con permiso para leer las métricas de la cola.

az containerapp update -n order-worker -g rg \
  --min-replicas 0 --max-replicas 20 \
  --scale-rule-name sb-queue --scale-rule-type azure-servicebus \
  --scale-rule-metadata queueName=orders namespace=shop-sb messageCount=20 \
  --scale-rule-auth connection=sb-connection-secret

Las reglas de CPU y memoria escalan según el uso de recursos, pero no pueden escalar a cero, porque debe haber una réplica en ejecución para informar la CPU. Si el escalado a cero es importante, usa reglas HTTP o de eventos. Cuando hay varias reglas, la app escala para satisfacer la que necesite más réplicas. La reducción (scale-in) ocurre después de un período de enfriamiento, para que las bajadas breves no provoquen oscilaciones.

Diseña tu worker pensando en el escalado: los mensajes deben procesarse de forma idempotente, ya que una réplica podría eliminarse a mitad del trabajo y otra tomará el mensaje cuando expire su bloqueo. En un laboratorio, envía una ráfaga de mensajes a la cola y observa cómo sube az containerapp replica list, y luego cómo vuelve a cero cuando la cola se vacía.

Términos clave

Replica (réplica)
Una instancia en ejecución de una revisión de una container app; el escalado cambia el número de réplicas.
KEDA
Kubernetes Event-driven Autoscaling, el motor de código abierto detrás de las reglas de escalado de Container Apps.
Scale to zero (escalado a cero)
Ejecutar cero réplicas cuando no hay actividad; es posible con un mínimo de 0 y reglas HTTP o controladas por eventos.
Scaler
Un componente de KEDA que lee una métrica de un origen de eventos, como el número de mensajes de Service Bus, para impulsar el escalado.
Ejemplo real

Un worker de pedidos no tiene ingress y procesa una cola de Service Bus. Está configurado con mínimo 0, máximo 20 y una regla azure-servicebus con un objetivo de 20 mensajes por réplica. Durante la noche no ejecuta réplicas y casi no cuesta nada; durante una venta relámpago, 400 mensajes en cola lo llevan a 20 réplicas, y vuelve a cero cuando la cola se vacía.

Consejo para el examen: Si un escenario exige escalar a cero, descarta las reglas de escalado por CPU y memoria; usa una regla HTTP para tráfico web o una regla de eventos de KEDA como azure-servicebus para workers de colas, con el mínimo de réplicas en 0.

Comprueba lo que sabes

¿Por qué una regla de escalado por CPU no puede escalar una app a cero?

El uso de CPU tiene que medirse desde una réplica en ejecución, así que con cero réplicas no hay ninguna métrica que active el escalado horizontal.

¿Qué significa el metadato messageCount en una regla de escalado azure-servicebus?

El número objetivo de mensajes en cola por réplica; KEDA agrega réplicas a medida que la longitud de la cola supera esa proporción.
