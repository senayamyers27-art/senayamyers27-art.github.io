Rotación de secretos y eventos de Key Vault (SecretNearExpiry) mediante Event Grid

Los secretos de larga duración son riesgosos: cuanto más tiempo sigue siendo válida una contraseña o una clave, más oportunidades tiene de filtrarse y usarse de forma indebida. La rotación reemplaza un secreto por un valor nuevo de forma programada y retira el anterior. Si se hace a mano, a menudo se olvida; si se automatiza, se vuelve rutina. Key Vault proporciona los componentes básicos: fechas de expiración, versiones y eventos.

Empieza por definir una fecha de expiración en cada secreto, que registra cuándo debe reemplazarse. Key Vault publica eventos sobre sus objetos en Event Grid mediante un tema del sistema del almacén. Los eventos de secretos importantes son Microsoft.KeyVault.SecretNewVersionCreated (se agregó una versión nueva), Microsoft.KeyVault.SecretNearExpiry (la versión actual expirará pronto; Key Vault lo genera 30 días antes de la fecha de expiración) y Microsoft.KeyVault.SecretExpired. Las claves y los certificados tienen eventos equivalentes, como CertificateNearExpiry.

El patrón de rotación estándar: crea una suscripción de Event Grid en el tema del sistema del almacén, filtrada por SecretNearExpiry, con una Azure Function como controlador. Cuando llega el evento, la función lee el nombre del secreto del asunto y los datos del evento, genera o solicita una credencial nueva al servicio que la posee (por ejemplo, regenerar una clave de una cuenta de almacenamiento o restablecer la contraseña de un usuario de base de datos), escribe el valor nuevo en Key Vault como una versión nueva con una nueva fecha de expiración y deja que los consumidores lo tomen. Después, el ciclo se repite automáticamente.

@app.event_grid_trigger(arg_name="event")
def rotate(event: func.EventGridEvent):
    if event.event_type != "Microsoft.KeyVault.SecretNearExpiry":
        return
    name = event.get_json()["ObjectName"]
    new_value = regenerate_credential(name)          # llama al servicio propietario
    secrets.set_secret(name, new_value,
                       expires_on=datetime.now(timezone.utc) + timedelta(days=60))

La identidad administrada de la función necesita Key Vault Secrets Officer (para escribir versiones nuevas) más el permiso que exija el servicio propietario para restablecer la credencial. Los consumidores solo necesitan Key Vault Secrets User.

Para los servicios con dos claves (cuentas de almacenamiento, claves de Cosmos DB, claves de acceso compartido de Service Bus), el enfoque de doble credencial evita el tiempo de inactividad: las apps usan la clave 1 mientras regeneras la clave 2, guardas la clave 2 en Key Vault, dejas que las apps cambien y luego regeneras la clave 1 en el siguiente ciclo. En ningún momento se invalida la clave en uso. Para sistemas con una sola credencial, crea la credencial nueva antes de revocar la anterior cuando el servicio lo permita.

La rotación solo sirve si las apps cargan el valor nuevo. Haz referencia a los secretos sin versión (para usar la más reciente), guárdalos en caché por un tiempo limitado y vuelve a cargarlos cuando falle la autenticación, o apóyate en características de la plataforma: las referencias de Key Vault en App Service se actualizan periódicamente, y App Configuration puede actualizarse con una clave centinela. Las claves de Key Vault también tienen una directiva integrada de rotación automática, y los certificados pueden renovarse automáticamente, pero los secretos dependen de este patrón controlado por eventos. Mejor aún, cuando un servicio admita identidades administradas, elimina el secreto por completo.

Términos clave

Secret rotation (rotación de secretos)
Reemplazar periódicamente un secreto por un valor nuevo y retirar el anterior para limitar la exposición.
SecretNearExpiry
Un evento de Key Vault publicado mediante Event Grid 30 días antes de la fecha de expiración de un secreto.
SecretNewVersionCreated
Un evento de Key Vault que se genera cuando se crea una versión nueva de un secreto.
Dual-credential rotation (rotación de doble credencial)
Alternar entre dos claves válidas para que una pueda regenerarse mientras las apps usan la otra.
Ejemplo real

La clave de una cuenta de almacenamiento que usa una app heredada debe rotarse cada 60 días. El equipo define una expiración de 60 días en el secreto de Key Vault y suscribe una función a SecretNearExpiry. Treinta días antes de la expiración, la función regenera la clave de almacenamiento que la app no está usando, la guarda como una versión nueva del secreto con una nueva expiración, y la app, que lee la versión más reciente cada hora, cambia sin tiempo de inactividad.

Consejo para el examen: SecretNearExpiry se activa 30 días antes de la expiración y llega a los controladores mediante Event Grid; el proceso de rotación necesita Secrets Officer, los lectores necesitan Secrets User y los consumidores deben hacer referencia al secreto sin versión para obtener los valores nuevos.

Comprueba lo que sabes

¿Qué servicio entrega las notificaciones de expiración próxima de Key Vault a tu función de rotación?

Azure Event Grid, mediante un tema del sistema del almacén y una suscripción a eventos filtrada por SecretNearExpiry.

¿Por qué usar dos claves al rotar las claves de una cuenta de almacenamiento?

Las apps siguen usando una clave válida mientras se regenera la otra, así que la rotación nunca invalida la clave en uso.
