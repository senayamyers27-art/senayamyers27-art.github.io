Roles de RBAC de Azure del plano de datos: Key Vault Secrets User, Service Bus Data Sender/Receiver, AcrPull y los roles de datos integrados de Cosmos DB

Azure separa dos tipos de operaciones. El plano de control (plano de administración) administra los propios recursos: crear un Key Vault, cambiar el nivel de Service Bus, eliminar una cuenta de Cosmos DB. Pasa por Azure Resource Manager. El plano de datos trabaja con los datos que hay dentro: leer un secreto, enviar un mensaje, descargar una imagen, consultar elementos. Roles como Owner y Contributor son roles del plano de control; te permiten administrar el recurso pero, en los servicios que usan acceso a datos con RBAC, por sí solos no te permiten leer los datos. Las apps necesitan roles del plano de datos, asignados a su identidad administrada con el mínimo privilegio.

En Key Vault con el modelo de permisos de Azure RBAC, Key Vault Secrets User puede leer el contenido de los secretos, que es lo que necesita una aplicación. Key Vault Secrets Officer también puede crear, actualizar y eliminar secretos, adecuado para un proceso de rotación o un administrador. Key Vault Reader ve los metadatos pero no los valores de los secretos. Existen pares similares para las claves (Key Vault Crypto User, Crypto Officer) y los certificados (Key Vault Certificates Officer), y Key Vault Administrator cubre todo el plano de datos.

En Service Bus, Azure Service Bus Data Sender permite enviar a colas y temas, Azure Service Bus Data Receiver permite recibir de colas y suscripciones, y Azure Service Bus Data Owner permite acceso completo a los datos, incluida la administración de entidades. Asigna en el ámbito útil más reducido: una sola cola o un solo tema en lugar de todo el namespace. Un productor solo necesita Sender; un worker solo necesita Receiver.

En Azure Container Registry, AcrPull permite que una identidad descargue imágenes y AcrPush le permite subirlas y descargarlas. Las plataformas de proceso reciben AcrPull; las canalizaciones de compilación reciben AcrPush. Storage tiene roles equivalentes, como Storage Blob Data Reader y Contributor, y Event Hubs tiene Data Sender y Receiver.

Cosmos DB for NoSQL es diferente y se evalúa con frecuencia. Su acceso al plano de datos usa el control de acceso basado en roles nativo de Cosmos DB, con dos roles de datos integrados: Cosmos DB Built-in Data Reader (leer elementos y consultar, leer metadatos) y Cosmos DB Built-in Data Contributor (crear, leer, actualizar y eliminar elementos). No se asignan en la página habitual Access control (IAM) del portal, sino mediante asignaciones de roles SQL de Cosmos DB, por ejemplo con la CLI. El ámbito puede ser la cuenta, una base de datos o un contenedor.

PRINCIPAL=$(az identity show -g rg -n app-id --query principalId -o tsv)
az cosmosdb sql role assignment create -g rg --account-name shop-cosmos \
  --role-definition-name "Cosmos DB Built-in Data Contributor" \
  --principal-id $PRINCIPAL --scope "/"

az role assignment create --assignee $PRINCIPAL \
  --role "Azure Service Bus Data Receiver" --scope $QUEUE_ID

Una vez que las apps usan roles de Microsoft Entra, puedes deshabilitar la autenticación local (basada en claves) en servicios como Cosmos DB, Service Bus y Storage, para que las claves filtradas dejen de funcionar. Las asignaciones de roles pueden tardar varios minutos en aplicarse, así que un 403 Forbidden justo después de la asignación puede resolverse solo; un 403 persistente suele significar el rol, el ámbito o la identidad equivocados.

Términos clave

Data plane (plano de datos)
Operaciones sobre los datos dentro de un servicio, como leer secretos o enviar mensajes, a diferencia de administrar el recurso.
Key Vault Secrets User
Un rol integrado que puede leer el contenido de los secretos en un Key Vault con RBAC habilitado.
Azure Service Bus Data Sender
Un rol integrado que permite a una identidad enviar mensajes a las colas y temas de su ámbito.
Cosmos DB Built-in Data Contributor
Un rol de datos nativo de Cosmos DB que permite leer y escribir elementos, asignado mediante asignaciones de roles SQL de Cosmos DB.
Ejemplo real

Un desarrollador le dio a la identidad de una function app el rol Contributor sobre una cuenta de Cosmos DB, pero todas las consultas fallaban con 403 Forbidden. Contributor es un rol del plano de control. Después de ejecutar az cosmosdb sql role assignment create con Cosmos DB Built-in Data Contributor en el ámbito de la cuenta, las consultas funcionaron, y luego el equipo deshabilitó la autenticación basada en claves en la cuenta.

Consejo para el examen: Contributor u Owner no conceden acceso a los datos; elige el rol de datos que corresponde a la acción (Secrets User para leer secretos, Data Sender o Receiver para Service Bus, AcrPull para imágenes) y recuerda que los roles de datos de Cosmos DB se asignan con az cosmosdb sql role assignment.

Comprueba lo que sabes

Una app solo debe leer secretos de un Key Vault en modo RBAC. ¿Qué rol?

Key Vault Secrets User, que puede leer el contenido de los secretos pero no modificarlos.

¿Por qué una identidad con Contributor sobre una cuenta de Cosmos DB podría seguir recibiendo 403 en las consultas?

Contributor es un rol del plano de control; el acceso a los datos necesita un rol de datos de Cosmos DB, como Built-in Data Reader o Contributor.
