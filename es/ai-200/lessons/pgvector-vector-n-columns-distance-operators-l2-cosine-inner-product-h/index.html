pgvector: columnas vector(n), operadores de distancia (<-> L2, <=> coseno, <#> producto interno), índices HNSW vs IVFFlat y su ajuste (m, ef_search, lists, probes)

Con la extensión creada, almacenas los embeddings en una columna de tipo vector(n), donde n es el número de dimensiones que devuelve tu modelo de embeddings. Insertar un vector con otra longitud falla, lo que te protege de mezclar modelos. Una tabla típica guarda juntos el texto del fragmento, sus metadatos y su embedding, para que una sola consulta SQL pueda filtrar y ordenar por relevancia.

CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  doc_id int, lang text, body text,
  embedding vector(1536));

SELECT id, body, embedding <=> $1 AS distance
FROM chunks WHERE lang = 'en'
ORDER BY embedding <=> $1
LIMIT 5;

pgvector define tres operadores de distancia principales. <-> es la distancia L2 (euclidiana). <=> es la distancia coseno, que es 1 menos la similitud coseno, así que un valor menor significa más similitud. <#> es el producto interno negativo; se niega porque los recorridos de índice de PostgreSQL solo funcionan en orden ascendente, así que ordenar de forma ascendente por <#> devuelve primero los productos internos más grandes. En todos los casos usas ORDER BY con el operador en orden ascendente y LIMIT para obtener el top-k. Para embeddings normalizados (longitud 1), el coseno y el producto interno dan el mismo orden, y el producto interno es un poco más barato.

Sin un índice, la consulta hace un recorrido exacto de cada fila, lo cual es perfectamente preciso pero se vuelve lento a medida que crece la tabla. pgvector ofrece dos tipos de índices de vecinos más cercanos aproximados (ANN), y cada índice se crea para una clase de operador que debe coincidir con el operador de tu consulta: vector_l2_ops para <->, vector_cosine_ops para <=> y vector_ip_ops para <#>. Si el operador no coincide, el planificador ignora el índice.

HNSW (Hierarchical Navigable Small World) construye un grafo de varias capas. Tiene un mejor equilibrio entre velocidad y recall (exhaustividad), se puede crear en una tabla vacía y sigue siendo preciso a medida que se agregan filas, pero se construye más lento y usa más memoria. Sus parámetros de construcción son m, el máximo de conexiones por nodo, y ef_construction, el tamaño de la lista de candidatos durante la construcción; los valores más grandes mejoran el recall y cuestan tiempo de construcción y memoria. En el momento de la consulta, hnsw.ef_search define el tamaño de la lista de candidatos: súbelo para mejorar el recall y bájalo para ganar velocidad.

IVFFlat (archivo invertido con listas planas) agrupa los vectores en lists y busca solo en las listas más cercanas. Se construye más rápido y usa menos memoria, pero debe crearse después de que la tabla tenga datos representativos, porque los clústeres se calculan al construirlo. La recomendación de pgvector es aproximadamente filas divididas entre 1000 listas hasta un millón de filas, y la raíz cuadrada del número de filas a partir de ahí. En el momento de la consulta, ivfflat.probes define cuántas listas se buscan; más probes significan mejor recall y consultas más lentas.

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;
-- o
CREATE INDEX ON chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
SET ivfflat.probes = 10;

Usa EXPLAIN ANALYZE para confirmar que se usa el índice. Recuerda que un filtro WHERE restrictivo aplicado después de un recorrido de índice aproximado puede devolver menos de k filas; subir ef_search o probes ayuda.

Términos clave

vector(n)
El tipo de columna de pgvector que guarda un embedding de exactamente n dimensiones.
<=> operator (operador <=>)
El operador de distancia coseno de pgvector; los valores más pequeños indican vectores más similares.
HNSW
Un índice ANN basado en grafos con buen recall y velocidad, que se ajusta con m, ef_construction y hnsw.ef_search.
IVFFlat
Un índice ANN basado en clústeres que se construye después de cargar los datos; se ajusta con lists al construirlo y con ivfflat.probes al consultar.
Operator class (clase de operador)
La configuración del índice, como vector_cosine_ops, que debe coincidir con el operador de distancia usado en las consultas.
Ejemplo real

Una consulta de búsqueda era lenta incluso después de crear un índice. EXPLAIN mostró un recorrido secuencial: el índice usaba vector_l2_ops, pero la consulta ordenaba por <=>. Al volver a crear el índice HNSW con vector_cosine_ops, el planificador empezó a usarlo. El recall en las consultas filtradas era algo bajo, así que subieron hnsw.ef_search para esa sesión.

Consejo para el examen: Haz coincidir el operador con la clase de operador (<-> con vector_l2_ops, <=> con vector_cosine_ops, <#> con vector_ip_ops). Construye IVFFlat después de cargar los datos; HNSW funciona en tablas vacías. ef_search y probes intercambian velocidad por recall.

Comprueba lo que sabes

¿Por qué el operador de producto interno <#> es negativo?

Los recorridos de índice de PostgreSQL ordenan de forma ascendente, así que negar el producto interno hace que los vectores más similares queden primero.

¿Qué parámetro subes para mejorar el recall de un índice IVFFlat al consultar?

ivfflat.probes, que busca en más listas a costa de velocidad.
