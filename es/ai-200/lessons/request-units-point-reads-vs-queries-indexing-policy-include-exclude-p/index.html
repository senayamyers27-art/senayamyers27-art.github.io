Request Units: lecturas puntuales vs consultas, rutas include/exclude de la directiva de indexación, niveles de coherencia y su costo en RU

Cosmos DB mide cada operación en Request Units (RU, unidades de solicitud), una moneda única que combina CPU, memoria y E/S. Aprovisionas el rendimiento como RU por segundo (manual o con escalado automático) o pagas por RU consumida en el modo serverless. Si superas tus RU/s aprovisionadas, las solicitudes se limitan con HTTP 429 y una indicación de cuándo reintentar (retry-after). Cada respuesta informa su costo en el encabezado x-ms-request-charge, que el SDK de Python expone a través de los últimos encabezados de respuesta, así que puedes medir en lugar de adivinar.

La referencia es una lectura puntual: leer un elemento de 1 KB por id y clave de partición cuesta alrededor de 1 RU. Las escrituras cuestan más que las lecturas porque el elemento debe almacenarse e indexarse, y los elementos más grandes cuestan más. Las consultas varían mucho: el costo crece con el número de elementos examinados, el tamaño del resultado, la complejidad de los filtros y funciones, y si la consulta abarca varias particiones. Una consulta que devuelve un solo elemento puede costar fácilmente varias veces lo que cuesta una lectura puntual de ese mismo elemento, así que el diseño más barato lee por id y clave de partición siempre que sea posible.

La directiva de indexación (indexing policy) afecta mucho el costo de escritura. De forma predeterminada, Cosmos DB indexa cada propiedad de cada elemento (la ruta incluida /*), lo que hace rápido cualquier filtro pero obliga a cada escritura a pagar por actualizar muchas entradas del índice. Si nunca filtras por un campo grande, como el cuerpo de un documento o un arreglo de embeddings, exclúyelo. También puedes invertir el enfoque: excluir /* e incluir solo las rutas que consultas.

{
  "indexingMode": "consistent",
  "includedPaths": [ { "path": "/customerId/?" }, { "path": "/status/?" } ],
  "excludedPaths": [ { "path": "/*" } ],
  "compositeIndexes": [[ { "path": "/status" }, { "path": "/orderDate", "order": "descending" } ]]
}

Una ruta que termina en /? indexa un valor escalar, y /* indexa todo lo que hay por debajo de ese punto. Los índices compuestos permiten un ORDER BY eficiente sobre varias propiedades. Establecer indexingMode en none deshabilita la indexación por completo, lo que sirve para una carga de trabajo puramente clave-valor que solo hace lecturas puntuales.

Los niveles de coherencia, del más fuerte al más débil, son Strong, Bounded Staleness, Session, Consistent Prefix y Eventual. Session es el predeterminado: un cliente siempre lee sus propias escrituras, lo cual encaja con la mayoría de las apps. Strong y Bounded Staleness hacen que las lecturas cuesten aproximadamente el doble de RU que los niveles más débiles, porque las lecturas se atienden con un quórum de réplicas, y Strong además agrega latencia de escritura entre regiones. Las lecturas en Session, Consistent Prefix y Eventual cuestan más o menos lo mismo. Estableces un nivel predeterminado en la cuenta, y un cliente puede solicitar un nivel más débil (nunca uno más fuerte) por cliente o por solicitud.

Cuando una pregunta te pide cómo reducir el consumo de RU, busca estas palancas: cambiar consultas por lecturas puntuales, agregar la clave de partición a los filtros, excluir del índice las rutas que no se consultan y relajar la coherencia desde Strong o Bounded Staleness si el escenario lo permite.

Términos clave

Request Unit (RU, unidad de solicitud)
La unidad de costo normalizada para las operaciones de Cosmos DB; una lectura puntual de 1 KB cuesta alrededor de 1 RU.
Indexing policy (directiva de indexación)
Configuración del contenedor que elige qué rutas se indexan, el modo de indexación y los índices compuestos o vectoriales.
Session consistency (coherencia de sesión)
El nivel predeterminado, que garantiza que un cliente lea sus propias escrituras dentro de su sesión.
HTTP 429
El estado que se devuelve cuando las solicitudes superan el rendimiento aprovisionado; los clientes deben reintentar después del retraso indicado.
Ejemplo real

Un almacén de documentos tenía cargos de RU altos en cada escritura. Al revisar x-ms-request-charge se vio que las inserciones grandes costaban mucho más de lo esperado, porque la directiva predeterminada indexaba un campo de texto grande y cada elemento de un embedding de 1536 números. Excluir esas rutas redujo mucho el costo de escritura, y cambiar las lecturas de una consulta por id a read_item bajó los cargos de lectura a alrededor de 1 RU cada una.

Consejo para el examen: Las lecturas en Strong y Bounded Staleness cuestan aproximadamente el doble; excluir rutas no usadas reduce las RU de escritura; una lectura puntual supera a cualquier consulta. Los clientes pueden relajar la coherencia por solicitud, pero no pueden hacerla más fuerte que el valor predeterminado de la cuenta.

Comprueba lo que sabes

¿Cómo puedes reducir el costo en RU de las escrituras de elementos con un campo de texto grande por el que nunca se filtra?

Excluyendo esa ruta en la directiva de indexación para que las escrituras no mantengan entradas de índice para ella.

¿Qué niveles de coherencia duplican aproximadamente el costo en RU de las lecturas?

Strong y Bounded Staleness, porque las lecturas requieren un quórum de réplicas.
