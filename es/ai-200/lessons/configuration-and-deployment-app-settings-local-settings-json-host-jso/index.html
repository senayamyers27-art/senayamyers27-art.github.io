Configuración e implementación: configuración de la app, local.settings.json, host.json, conexiones basadas en identidad y `func azure functionapp publish`

Una function app lee su configuración de varios lugares, y saber qué hace cada archivo evita muchos problemas del tipo "funciona en local, falla en Azure".

La configuración de la app (app settings) son las variables de entorno de la function app en Azure. Contienen detalles de conexión, interruptores de características y configuraciones obligatorias del runtime, como FUNCTIONS_WORKER_RUNTIME=python y AzureWebJobsStorage. Tu código las lee con os.environ, y los enlaces las referencian por nombre mediante el argumento connection. Las administras en la página Environment variables del portal o con az functionapp config appsettings set. Los valores pueden ser referencias de Key Vault para que los secretos vivan en Key Vault.

local.settings.json cumple la misma función en tu máquina. Core Tools carga su sección Values como variables de entorno cuando ejecutas func start. Es solo para desarrollo local: no se implementa de forma predeterminada y debe incluirse en .gitignore porque a menudo contiene secretos. Con Azurite, el emulador de almacenamiento local, puedes definir AzureWebJobsStorage como UseDevelopmentStorage=true.

{
  "IsEncrypted": false,
  "Values": {
    "FUNCTIONS_WORKER_RUNTIME": "python",
    "AzureWebJobsStorage": "UseDevelopmentStorage=true",
    "ServiceBusConn__fullyQualifiedNamespace": "shop-sb.servicebus.windows.net"
  }
}

host.json configura el runtime de Functions para todas las funciones de la app, y se implementa junto con tu código. Contiene los niveles de registro y el muestreo de Application Insights, la configuración de las extensiones (por ejemplo, la simultaneidad de Service Bus o si los mensajes se completan automáticamente), el functionTimeout, la configuración de reintentos y la versión del paquete de extensiones (extension bundle) que proporciona los enlaces que no son HTTP. Un cambio en host.json afecta a todas las funciones; la configuración de la app puede reemplazar valores de host.json cuando necesitas diferencias por entorno.

Las conexiones basadas en identidad reemplazan las cadenas de conexión por una identidad administrada. En lugar de una configuración llamada ServiceBusConn que contiene un secreto, creas configuraciones que comparten el prefijo, como ServiceBusConn__fullyQualifiedNamespace para Service Bus, DocsStorage__blobServiceUri o DocsStorage__accountName para Storage y CosmosConn__accountEndpoint para Cosmos DB. El runtime usa de forma predeterminada la identidad asignada por el sistema de la app; para una identidad asignada por el usuario, agrega __credential con el valor managedidentity y __clientId. Luego asigna a la identidad los roles de datos adecuados, como Azure Service Bus Data Receiver o Storage Blob Data Owner para la cuenta de almacenamiento del host. En local, las mismas configuraciones usan tu inicio de sesión de desarrollador mediante la cadena de credenciales de Azure.

La implementación con Core Tools es func azure functionapp publish <APP_NAME>. Empaqueta el proyecto, lo sube y (en Python) inicia una compilación remota que instala requirements.txt para Linux. Agrega --publish-local-settings -i si quieres enviar los valores locales a la configuración de la app en Azure, con cuidado de no sobrescribir valores de producción. En CI/CD usarías GitHub Actions o Azure Pipelines con la misma implementación basada en zip. Después de publicar, func azure functionapp list-functions <APP_NAME> confirma qué funciones se indexaron.

Términos clave

App settings (configuración de la app)
Variables de entorno de una function app en Azure, que el código lee y los enlaces referencian.
local.settings.json
Un archivo solo local cuya sección Values carga Core Tools como variables de entorno; no se implementa de forma predeterminada.
host.json
Un archivo de configuración del runtime para toda la app (registro, extensiones, tiempos de espera y muestreo) que se implementa con el código.
Identity-based connection (conexión basada en identidad)
Una conexión de enlace definida por configuraciones como Prefijo__fullyQualifiedNamespace que se autentica con una identidad administrada.
Ejemplo real

Una función funcionaba en local, pero en Azure fallaba con un error de configuración faltante. El desarrollador había agregado ServiceBusConn__fullyQualifiedNamespace solo en local.settings.json, que no se publica. Agregó la configuración de la app en Azure, asignó a la identidad de la function app el rol Azure Service Bus Data Receiver sobre la cola, volvió a implementar con func azure functionapp publish y el trigger empezó a procesar.

Consejo para el examen: local.settings.json es solo local y no se implementa; host.json es la configuración del runtime para toda la app y sí se implementa; las conexiones basadas en identidad usan configuraciones con doble guion bajo, como __fullyQualifiedNamespace, más un rol de RBAC.

Comprueba lo que sabes

¿Dónde configuras la simultaneidad o el completado automático de Service Bus para todas las funciones de una app?

En host.json, en la configuración de la extensión de Service Bus.

¿Qué configuración de la app permite que un trigger de Service Bus se conecte con una identidad administrada en lugar de una cadena de conexión?

Una configuración llamada <connection>__fullyQualifiedNamespace con el nombre de host del namespace, más un rol de datos sobre el namespace o la entidad.
