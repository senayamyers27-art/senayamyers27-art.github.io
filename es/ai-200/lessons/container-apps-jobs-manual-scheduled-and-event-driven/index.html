Container Apps jobs: manuales, programados y controlados por eventos

Una container app está diseñada para ejecutarse de forma continua (o escalar a cero y despertar cuando se necesita) y atender solicitudes o procesar un flujo. Sin embargo, parte del trabajo debe ejecutarse hasta terminar y detenerse: un informe nocturno, una migración de base de datos, un lote de embeddings que procesa documentos nuevos. Los Container Apps jobs están hechos para eso. Un job ejecuta contenedores que se inician, hacen una tarea finita y terminan; cada ejecución se llama execution.

Los jobs viven en el mismo entorno de Container Apps que tus apps, comparten su red y su registro, y admiten las mismas descargas de imágenes, secretos e identidades administradas. La diferencia principal es el tipo de desencadenador (trigger type), y hay tres.

Un job manual solo se ejecuta cuando tú lo inicias, con az containerapp job start o la API REST. Úsalo para tareas bajo demanda, como ejecutar una migración durante un lanzamiento, o cuando un pipeline u otro servicio decide exactamente cuándo debe hacerse el trabajo.

Un job programado se ejecuta según una expresión cron, por ejemplo 0 2 * * * para las 2:00 todos los días. Las expresiones cron de Container Apps usan el formato estándar de cinco campos y se evalúan en UTC (tiempo universal coordinado), así que ten en cuenta las zonas horarias. Úsalo para limpiezas nocturnas, reindexaciones periódicas o informes.

Un job controlado por eventos usa reglas de escalado de KEDA, igual que el escalado de una container app, pero en lugar de agregar réplicas de larga duración inicia nuevas ejecuciones cuando hay eventos en espera. Por ejemplo, con una regla azure-servicebus, en cada intervalo de sondeo el job revisa la cola e inicia ejecuciones para procesar los mensajes. Cada ejecución suele procesar uno o unos pocos mensajes y termina. Esto sirve para elementos de trabajo pesados e independientes, como renderizar un video o generar embeddings de un documento grande.

az containerapp job create -n nightly-embed -g rg --environment prod-env \
  --trigger-type Schedule --cron-expression "0 2 * * *" \
  --replica-timeout 1800 --replica-retry-limit 2 \
  --parallelism 1 --replica-completion-count 1 \
  --image myregistry.azurecr.io/embedder:20260920.1
az containerapp job execution list -n nightly-embed -g rg -o table

Algunas configuraciones controlan cada ejecución: el tiempo de espera de réplica (replica timeout, el tiempo máximo de ejecución en segundos), el límite de reintentos para una réplica fallida, el paralelismo (cuántas réplicas se ejecutan a la vez) y el número de réplicas completadas (cuántas deben tener éxito para que la ejecución cuente como exitosa). El contenedor de un job indica éxito o fallo con su código de salida: 0 significa éxito; cualquier otro valor significa fallo y puede provocar un reintento. Los registros van al área de trabajo de Log Analytics del entorno, y el historial de ejecuciones muestra el estado de cada ejecución.

Elige un job en lugar de una container app cuando el trabajo tiene un final claro; elige una app cuando escucha de forma continua.

Términos clave

Container Apps job
Un recurso de Container Apps que ejecuta contenedores hasta que terminan, en lugar de hacerlo de forma continua.
Execution (ejecución)
Una sola ejecución de un job, que contiene una o más réplicas que deben terminar correctamente.
Trigger type (tipo de desencadenador)
Cómo se inicia un job: Manual, Schedule (cron) o Event (reglas de escalado de KEDA).
Replica timeout (tiempo de espera de réplica)
El número máximo de segundos que puede ejecutarse una réplica de un job antes de detenerse y considerarse fallida.
Ejemplo real

Una aplicación RAG debe generar embeddings de los documentos recién subidos. Las subidas colocan un mensaje en una cola de Service Bus, y un Container Apps job controlado por eventos con una regla azure-servicebus inicia una ejecución para los mensajes pendientes. Cada ejecución genera los embeddings de un documento, escribe los vectores en Cosmos DB y termina con código 0, mientras que un job programado aparte vuelve a revisar todo el índice cada noche a las 02:00 UTC.

Consejo para el examen: El trabajo que se ejecuta hasta terminar apunta a Container Apps jobs: elige Manual para bajo demanda, Schedule para horarios basados en cron (UTC) y Event para trabajo impulsado por colas que maneja KEDA.

Comprueba lo que sabes

¿Qué distingue a un Container Apps job de una container app?

Un job ejecuta contenedores que terminan y salen, registrados como ejecuciones, mientras que una app se ejecuta de forma continua o escala bajo demanda para atender tráfico.

¿Cómo informa un fallo una ejecución de un job?

El contenedor termina con un código de salida distinto de cero, lo que marca la réplica como fallida y puede provocar reintentos hasta el límite de reintentos.
