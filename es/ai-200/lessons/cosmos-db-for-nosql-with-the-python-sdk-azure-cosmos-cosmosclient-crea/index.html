Cosmos DB for NoSQL con el SDK de Python (azure-cosmos): CosmosClient, crear/upsert/leer/eliminar elementos y consultas parametrizadas

Azure Cosmos DB for NoSQL es una base de datos distribuida globalmente que almacena documentos JSON llamados elementos (items). Los elementos viven en contenedores, los contenedores viven en bases de datos y las bases de datos viven en una cuenta. Cada elemento tiene un id y un valor para la clave de partición del contenedor; juntos identifican el elemento de forma única. El SDK de Python es el paquete azure-cosmos.

Todo empieza con CosmosClient. Crea uno por aplicación y reutilízalo, porque mantiene conexiones y almacena metadatos en caché; crear un cliente por solicitud es un error de rendimiento común. Autentícate con Microsoft Entra ID pasando una credencial como DefaultAzureCredential(), que funciona con una identidad administrada en Azure y con tu inicio de sesión de desarrollador en local. Las claves de cuenta también funcionan, pero son secretos que tendrías que proteger.

from azure.cosmos import CosmosClient
from azure.identity import DefaultAzureCredential

client = CosmosClient(ACCOUNT_ENDPOINT, credential=DefaultAzureCredential())
container = client.get_database_client("shop").get_container_client("orders")

order = {"id": "o-1001", "customerId": "c-42", "total": 59.90, "status": "new"}
container.create_item(order)          # falla con 409 Conflict si id+pk ya existe
order["status"] = "paid"
container.upsert_item(order)          # inserta o reemplaza
item = container.read_item(item="o-1001", partition_key="c-42")
container.delete_item(item="o-1001", partition_key="c-42")

Conoce la diferencia entre los métodos de escritura. create_item inserta y lanza un error de conflicto (HTTP 409) si ya existe un elemento con el mismo id en esa partición. replace_item sobrescribe un elemento existente y falla con no encontrado (404) si no existe. upsert_item hace cualquiera de las dos cosas, lo cual es práctico para el procesamiento idempotente. patch_item cambia campos específicos sin enviar el documento completo. read_item necesita tanto el id como el valor de la clave de partición, y es la operación más barata de Cosmos DB: una lectura puntual (point read).

Las consultas usan un lenguaje similar a SQL sobre JSON. Pasa siempre la entrada del usuario como parámetros en lugar de construir cadenas; los parámetros evitan la inyección y permiten que el servicio reutilice los planes de consulta. Cada parámetro tiene un nombre que empieza con @ y un valor.

items = container.query_items(
    query="SELECT c.id, c.total FROM c WHERE c.customerId = @cust AND c.total > @min",
    parameters=[{"name": "@cust", "value": "c-42"}, {"name": "@min", "value": 20}],
    partition_key="c-42")
for row in items:
    print(row["id"], row["total"])

Proporcionar partition_key mantiene la consulta en una sola partición. Sin él, pasas enable_cross_partition_query=True y la consulta se distribuye a todas las particiones, lo que cuesta más Request Units. Los errores aparecen como CosmosHttpResponseError con un código de estado, como 404, 409, o 429 cuando superas el rendimiento aprovisionado; el SDK reintenta automáticamente los 429 un número limitado de veces. El cliente asíncrono en azure.cosmos.aio ofrece las mismas operaciones para apps con asyncio.

Términos clave

CosmosClient
El punto de entrada de azure-cosmos que se conecta a una cuenta; crea uno y reutilízalo durante toda la vida de la app.
Upsert
Una operación que inserta un elemento si no existe o lo reemplaza si ya existe.
Point read (lectura puntual)
Leer un elemento por id y clave de partición con read_item; es la operación más barata de Cosmos DB.
Parameterized query (consulta parametrizada)
Una consulta cuyos valores se pasan por separado como parámetros @nombre en lugar de concatenar cadenas.
Ejemplo real

Un servicio de pedidos llama a create_item para cada pedido entrante y, de vez en cuando, recibe el mismo mensaje dos veces desde su cola, lo que provoca 409 Conflict. El equipo cambia a upsert_item, haciendo que el procesamiento sea idempotente, y reemplaza una consulta construida con cadenas por una parametrizada que incluye la clave de partición del cliente, lo que reduce el costo en RU y elimina un riesgo de inyección.

Consejo para el examen: read_item siempre necesita el id del elemento y la clave de partición; create_item falla con duplicados mientras que upsert_item no, y las consultas entre particiones necesitan enable_cross_partition_query=True.

Comprueba lo que sabes

¿Qué método deberías usar para escrituras idempotentes en las que un mensaje podría procesarse dos veces?

upsert_item, porque inserta o reemplaza sin fallar cuando el elemento ya existe.

¿Por qué usar parámetros en query_items en lugar de f-strings?

Los parámetros evitan la inyección en las consultas y permiten que el servicio trate los valores de forma segura y coherente.
