Azure Managed Redis: patrón cache-aside, TTL e invalidación, directivas de expulsión

Redis es un almacén de datos en memoria que responde en mucho menos de un milisegundo, lo que lo convierte en la caché estándar frente a bases de datos más lentas y llamadas costosas a modelos de IA. Azure Managed Redis es la oferta actual de Redis administrado de Microsoft, basada en el software Redis Enterprise, con niveles optimizados para memoria, equilibrio o proceso, clustering, alta disponibilidad y módulos opcionales como search y JSON. Desde Python te conectas con el paquete redis (redis-py) mediante TLS, autenticándote con una clave de acceso o, preferiblemente, con Microsoft Entra ID.

El patrón de caché más común es cache-aside (carga diferida). La aplicación, no la caché, es la que manda. En una lectura, la app revisa primero la caché. Si hay acierto, devuelve el valor almacenado. Si hay un fallo, lee de la base de datos, escribe el resultado en la caché con una expiración y lo devuelve. La caché solo contiene datos que alguien pidió.

import json, redis
r = redis.Redis(host=HOST, port=10000, ssl=True, password=KEY)

def get_product(pid):
    key = f"product:{pid}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    product = db_read_product(pid)
    r.set(key, json.dumps(product), ex=300)   # TTL de 300 segundos
    return product

def update_product(pid, data):
    db_write_product(pid, data)
    r.delete(f"product:{pid}")                 # invalidar

El TTL (time to live, tiempo de vida) es cuánto vive una clave antes de que Redis la elimine. Se define con ex= en SET o con EXPIRE; se consulta con TTL. Un TTL limita qué tan desactualizados pueden estar los datos en caché y libera memoria automáticamente. Los TTL cortos significan datos más frescos y más carga en la base de datos; los TTL largos, lo contrario. Agregar una pequeña variación aleatoria (jitter) a los TTL evita que muchas claves expiren a la vez y saturen la base de datos.

El TTL por sí solo permite lecturas desactualizadas hasta la expiración. La invalidación elimina o actualiza la entrada de caché cuando cambia el origen. Con cache-aside, el enfoque habitual es: escribir en la base de datos y luego eliminar la clave de la caché, para que la siguiente lectura cargue datos frescos. Eliminar es más seguro que escribir el valor nuevo en la caché, porque evita condiciones de carrera en las que un valor antiguo sobrescribe uno más nuevo. Para eventos de otros sistemas, un change feed o un mensaje puede controlar la invalidación.

Cuando la memoria está llena, la directiva de expulsión (eviction policy) decide qué pasa. noeviction rechaza las escrituras nuevas con un error. allkeys-lru expulsa las claves usadas menos recientemente entre todas las claves, un buen valor predeterminado para una caché pura. volatile-lru expulsa las claves usadas menos recientemente solo entre las que tienen TTL, lo que protege a las claves sin expiración. Hay variantes LFU (usadas con menos frecuencia), allkeys-random y volatile-random, y volatile-ttl, que expulsa primero las claves más cercanas a expirar. Si tu caché contiene solo datos desechables, conviene una directiva allkeys; si la misma instancia guarda datos que no deben desaparecer, usa una directiva volatile y asigna TTL solo a las entradas de caché.

Supervisa la tasa de aciertos de la caché, el uso de memoria y las expulsiones. Una tasa de aciertos baja sugiere que los TTL son demasiado cortos o que las claves son demasiado específicas; las expulsiones frecuentes sugieren que la caché es demasiado pequeña.

Términos clave

Cache-aside
Un patrón en el que la app revisa la caché, carga desde la base de datos cuando hay un fallo y llena la caché por sí misma.
TTL (tiempo de vida)
Time to live: el número de segundos que existe una clave antes de que Redis la expire automáticamente.
Invalidation (invalidación)
Eliminar o actualizar una entrada de caché cuando cambian los datos subyacentes.
Eviction policy (directiva de expulsión)
La regla que sigue Redis para liberar memoria cuando está llena, como allkeys-lru o volatile-lru.
Ejemplo real

Una API de páginas de productos tardaba 120 ms por solicitud leyendo PostgreSQL. Con cache-aside y un TTL de 5 minutos en Azure Managed Redis, las lecturas repetidas respondían en unos pocos milisegundos. Cuando un administrador cambiaba un precio, los clientes veían el precio anterior durante minutos, así que ahora la ruta de actualización elimina la clave del producto justo después de escribir en la base de datos, y la siguiente lectura la vuelve a cargar.

Consejo para el examen: Conoce los nombres de las directivas: allkeys-* expulsa de entre todas las claves, volatile-* solo de las claves con TTL y noeviction devuelve errores en las escrituras cuando la memoria está llena.

Comprueba lo que sabes

En cache-aside, ¿quién carga los datos en la caché cuando hay un fallo?

La aplicación: lee la base de datos y luego escribe el valor en la caché con un TTL.

¿Por qué eliminar la clave de caché después de actualizar la base de datos en lugar de escribir el valor nuevo?

Eliminarla evita condiciones de carrera en las que un escritor más lento vuelve a poner datos desactualizados en la caché; la siguiente lectura carga el valor actual.
