Fundamentos de AKS para desarrolladores: manifiestos Deployment y Service, `kubectl apply`, requests y limits, ConfigMaps y Secrets, y asociar ACR

Azure Kubernetes Service (AKS) es un clúster de Kubernetes administrado: Azure ejecuta el plano de control y tus cargas de trabajo se ejecutan en grupos de nodos (node pools) de máquinas virtuales. En comparación con Container Apps, obtienes la API completa de Kubernetes y más control, y también asumes más responsabilidad. Como desarrollador, sobre todo escribes manifiestos YAML que describen el estado deseado y dejas que Kubernetes lo haga realidad.

Un Deployment describe un conjunto de pods idénticos (un pod es uno o más contenedores que se programan juntos). Declara la imagen, el número de réplicas y un selector de etiquetas; Kubernetes mantiene esa cantidad de pods en ejecución y realiza actualizaciones graduales (rolling updates) cuando cambias la imagen. Un Service les da a esos pods una IP virtual y un nombre DNS estables, y equilibra la carga entre ellos haciendo coincidir etiquetas. El tipo ClusterIP (el predeterminado) solo es accesible dentro del clúster; el tipo LoadBalancer obtiene un balanceador de carga de Azure con una IP externa.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
spec:
  replicas: 3
  selector:
    matchLabels: { app: orders }
  template:
    metadata:
      labels: { app: orders }
    spec:
      containers:
      - name: orders
        image: myregistry.azurecr.io/orders-api:20260920.1
        ports: [{ containerPort: 8000 }]
        envFrom: [{ configMapRef: { name: orders-config } }]
        resources:
          requests: { cpu: 250m, memory: 256Mi }
          limits: { cpu: 500m, memory: 512Mi }
---
apiVersion: v1
kind: Service
metadata:
  name: orders
spec:
  type: ClusterIP
  selector: { app: orders }
  ports: [{ port: 80, targetPort: 8000 }]

kubectl apply -f orders.yaml envía el manifiesto al servidor de API, creando o actualizando objetos de forma declarativa. Continúa con kubectl rollout status deployment/orders, kubectl get pods y kubectl describe pod <name> para ver eventos como errores de descarga de imagen. Primero obtén las credenciales con az aks get-credentials.

Los requests (solicitudes de recursos) son lo que el programador (scheduler) reserva para un contenedor al elegir un nodo; los limits (límites) son el máximo que puede usar. Un contenedor que supera su límite de memoria se termina (OOMKilled); uno que supera su límite de CPU se limita (throttling). Configurar requests demasiado altos desperdicia nodos; no configurar ninguno hace que la programación sea impredecible y el escalado automático impreciso.

Los ConfigMaps guardan configuración no sensible como pares clave-valor; los Secrets guardan valores sensibles. Ambos pueden inyectarse como variables de entorno o montarse como archivos. Los Secrets de Kubernetes solo están codificados en base64, y esa codificación no los cifra, así que restringe el acceso con Kubernetes RBAC y considera el proveedor de Azure Key Vault para el Secrets Store CSI Driver para obtener los secretos de Key Vault en su lugar.

Para que los nodos descarguen de tu registro privado sin contraseñas, ejecuta az aks update -n mycluster -g rg --attach-acr myregistry (o --attach-acr al crearlo). Esto otorga el rol AcrPull a la identidad administrada kubelet del clúster, así que no se necesitan imagePullSecrets.

Términos clave

Deployment
Un objeto de Kubernetes que mantiene en ejecución un número especificado de pods idénticos y administra las actualizaciones graduales.
Service
Un objeto de Kubernetes que le da a un conjunto de pods, seleccionados por etiquetas, una IP estable, un nombre DNS y equilibrio de carga.
Requests and limits (solicitudes y límites)
Configuración de CPU y memoria por contenedor: los requests se reservan para la programación y los limits ponen un tope al uso.
ConfigMap
Un objeto de Kubernetes que almacena datos de configuración no secretos para los pods.
Kubernetes Secret (secreto de Kubernetes)
Un objeto para datos sensibles que está codificado en base64, sin que esa codificación lo cifre, y cuyo acceso debe controlarse.
Ejemplo real

Los pods de un servicio nuevo se quedan en ImagePullBackOff. kubectl describe pod muestra un error de no autorizado del registro. El desarrollador ejecuta az aks update --attach-acr, que otorga AcrPull a la identidad kubelet; después del siguiente reintento, los pods se inician. Más tarde, los pods se reinician con OOMKilled, así que el equipo aumenta el límite de memoria después de revisar el uso real.

Consejo para el examen: Los requests determinan la programación y los limits imponen topes (la memoria por encima del límite provoca OOMKilled, la CPU se limita); el acceso a ACR para AKS es az aks update --attach-acr, no una contraseña de administrador en un imagePullSecret.

Comprueba lo que sabes

¿Cuál es la diferencia entre un Deployment y un Service?

Un Deployment ejecuta y actualiza los pods; un Service les da a esos pods un punto de conexión de red estable y les distribuye la carga por etiqueta.

¿Un Secret de Kubernetes está cifrado por estar codificado en base64?

No. Base64 es solo una codificación; la protección viene de RBAC, del cifrado en reposo o de usar Key Vault mediante el CSI driver.
