Identidades administradas: asignadas por el sistema vs asignadas por el usuario; DefaultAzureCredential en azure-identity

Las aplicaciones necesitan credenciales para llamar a los servicios de Azure, y cada secreto almacenado es algo que puede filtrarse, expirar u olvidarse en un repositorio. Una identidad administrada (managed identity) resuelve esto: Azure crea una identidad en Microsoft Entra ID para tu recurso y gestiona sus credenciales por ti. Tu código le pide un token al punto de conexión local de la plataforma y lo usa para llamar a cualquier servicio que admita la autenticación de Microsoft Entra, como Key Vault, Storage, Service Bus, Cosmos DB, Azure SQL y PostgreSQL.

Una identidad asignada por el sistema (system-assigned) se habilita en un solo recurso, como una web app, una function app o una container app, y comparte su ciclo de vida. Se crea con el recurso, se elimina cuando se elimina el recurso y no se puede compartir. Es la opción más simple cuando un recurso necesita sus propios permisos.

Una identidad asignada por el usuario (user-assigned) es un recurso independiente de Azure que creas y luego asocias a uno o más recursos. Existe hasta que la eliminas. Elígela cuando varios recursos deban compartir los mismos permisos (por ejemplo, diez container apps que necesitan AcrPull), cuando quieras asignar roles antes de que exista el recurso de proceso (para evitar el problema del huevo y la gallina en la primera implementación) o cuando los recursos se vuelvan a crear con frecuencia y no quieras rehacer las asignaciones de roles. Un recurso puede tener ambos tipos y varias identidades asignadas por el usuario.

Recuerda que una identidad por sí sola no concede nada. Debes asignarle roles, como Key Vault Secrets User o Azure Service Bus Data Sender, en el ámbito correcto.

En Python, el paquete azure-identity proporciona DefaultAzureCredential, una credencial que prueba una cadena de métodos en orden hasta que uno funciona. Revisa las variables de entorno en busca de una entidad de servicio (service principal), luego la identidad de carga de trabajo (workload identity, para Kubernetes), luego la identidad administrada y después las herramientas de desarrollo, como los inicios de sesión de Azure CLI, Azure PowerShell y Azure Developer CLI. Por eso, el mismo código usa tu cuenta de az login en tu laptop y la identidad administrada en Azure, sin cambios en el código.

from azure.identity import DefaultAzureCredential, ManagedIdentityCredential
from azure.keyvault.secrets import SecretClient

credential = DefaultAzureCredential()
# para una identidad asignada por el usuario: define AZURE_CLIENT_ID en la configuración de la app, o
# credential = ManagedIdentityCredential(client_id="<client-id>")
secrets = SecretClient(vault_url=VAULT_URL, credential=credential)
db_password = secrets.get_secret("db-password").value

Cuando un recurso tiene una identidad asignada por el usuario, la credencial debe saber qué identidad usar. Define la variable de entorno AZURE_CLIENT_ID con el client ID de la identidad, pasa managed_identity_client_id a DefaultAzureCredential o usa directamente ManagedIdentityCredential(client_id=...). Olvidar esto es una razón común de errores de autenticación cuando una app tiene más de una identidad. En producción, algunos equipos usan una credencial específica, como ManagedIdentityCredential, para evitar alternativas inesperadas y que los errores sean más claros. Crea la credencial y los clientes del SDK una sola vez y reutilízalos, ya que almacenan los tokens en caché.

Términos clave

System-assigned identity (identidad asignada por el sistema)
Una identidad administrada ligada al ciclo de vida de un recurso y que se elimina con él.
User-assigned identity (identidad asignada por el usuario)
Un recurso de identidad administrada independiente que se puede asociar a muchos recursos y que sobrevive a ellos.
DefaultAzureCredential
Una credencial de azure-identity que prueba en orden el entorno, la workload identity, la identidad administrada y los inicios de sesión de desarrollador.
AZURE_CLIENT_ID
La variable de entorno que le indica a azure-identity qué identidad administrada asignada por el usuario usar.
Ejemplo real

Un equipo ejecuta doce container apps que leen del mismo Key Vault y descargan del mismo registro. En lugar de habilitar doce identidades asignadas por el sistema y hacer veinticuatro asignaciones de roles, crean una identidad asignada por el usuario, le asignan AcrPull y Key Vault Secrets User, la asocian a cada app y definen AZURE_CLIENT_ID. Su código de Python usa DefaultAzureCredential sin cambios en las laptops y en Azure.

Consejo para el examen: Compartida entre recursos o creada antes que el recurso significa asignada por el usuario; ciclo de vida ligado a un solo recurso significa asignada por el sistema. Con una identidad asignada por el usuario, define AZURE_CLIENT_ID para que DefaultAzureCredential elija la correcta.

Comprueba lo que sabes

¿Qué le pasa a una identidad asignada por el sistema cuando se elimina su web app?

También se elimina, porque comparte el ciclo de vida del recurso; sus asignaciones de roles dejan de funcionar y quedan como entradas huérfanas hasta que las quites.

¿Por qué el mismo código con DefaultAzureCredential funciona en local y en Azure?

Prueba varias fuentes de credenciales en orden; en local encuentra tu inicio de sesión de desarrollador y en Azure encuentra la identidad administrada.
