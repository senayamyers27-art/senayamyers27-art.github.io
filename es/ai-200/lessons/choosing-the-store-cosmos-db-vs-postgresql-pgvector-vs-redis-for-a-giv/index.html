Elegir el almacén: Cosmos DB vs PostgreSQL + pgvector vs Redis para una carga de trabajo de IA determinada

Al examen le gustan las preguntas de escenario que describen una carga de trabajo de IA y preguntan qué servicio de datos encaja. Los tres servicios de este dominio pueden almacenar vectores y responder consultas de similitud, así que la decisión depende de todo lo demás: la forma de los datos, la escala, la latencia, la durabilidad, las habilidades y sistemas existentes, y cómo se relacionan los vectores con el resto de la aplicación.

Elige Azure Cosmos DB for NoSQL cuando la aplicación ya tiene forma de documentos y necesita escala elástica y global. Fortalezas: elementos JSON con esquemas flexibles, particionamiento automático para volúmenes muy grandes de datos y rendimiento, lecturas puntuales de milisegundos de un solo dígito, escrituras y replicación en varias regiones, un change feed para canalizaciones controladas por eventos y búsqueda vectorial sobre los mismos elementos que los datos operativos (con índices flat, quantizedFlat o diskANN). Casos típicos: historial de chat y memoria de agentes por usuario, bases de conocimiento SaaS multiinquilino, catálogos de productos con embeddings y apps que necesitan distribución global. Los costos se miden en RU, así que diseña con cuidado las claves de partición y la indexación.

Elige Azure Database for PostgreSQL flexible server con pgvector cuando los datos son relacionales o el equipo ya trabaja con PostgreSQL. Fortalezas: joins de SQL, transacciones y restricciones entre vectores y tablas de negocio, filtrado completo con cláusulas WHERE comunes, el enorme ecosistema de PostgreSQL (ORM, migraciones, herramientas) y los conocidos índices HNSW e IVFFlat. Casos típicos: agregar búsqueda semántica a una base de datos de línea de negocio existente, RAG sobre datos que deben combinarse con pedidos, clientes o permisos, y equipos que prefieren SQL. Escala bien verticalmente y admite réplicas de lectura, pero no se particiona automáticamente entre regiones como lo hace Cosmos DB.

Elige Azure Managed Redis cuando la velocidad es lo más importante y los datos son una caché o de corta duración. Fortalezas: en memoria, latencia inferior a un milisegundo, TTL y expulsión, y búsqueda vectorial mediante el módulo search. Casos típicos: caché semántica de respuestas del modelo, estado de sesión y contexto de la conversación actual, limitación de velocidad (rate limiting) y subconjuntos "calientes" de embeddings que necesitan la búsqueda más rápida. Debilidades: la memoria es cara por gigabyte en comparación con los almacenes en disco y, aunque existen opciones de persistencia, Redis no suele ser el sistema de registro.

Muchas soluciones reales los combinan: Cosmos DB o PostgreSQL como almacén vectorial duradero y fuente de verdad, con Redis delante como caché semántica y capa cache-aside. Esa suele ser la mejor respuesta cuando un escenario menciona tanto conocimiento duradero como reducir llamadas repetidas al modelo.

Una forma rápida de decidir en una pregunta: encuentra el requisito dominante. La distribución global, la escala masiva, la flexibilidad de esquema o el change feed apuntan a Cosmos DB. Un PostgreSQL existente, joins de SQL con tablas relacionales o transacciones apuntan a PostgreSQL con pgvector. La latencia más baja, el almacenamiento en caché, la expiración basada en TTL o reducir llamadas repetidas al LLM apuntan a Redis. Fíjate también en las pistas de costo: Redis guarda todo en memoria y Cosmos DB cobra por RU, así que un archivo enorme de embeddings que rara vez se consulta no es una carga de trabajo para Redis.

Términos clave

System of record (sistema de registro)
El almacén autoritativo y duradero de los datos, a diferencia de una caché que se puede reconstruir.
Operational data (datos operativos)
Los datos activos de la aplicación, como pedidos o perfiles, junto a los cuales se pueden almacenar los vectores.
Global distribution (distribución global)
Replicar una base de datos en varias regiones para lecturas y escrituras locales, una característica central de Cosmos DB.
In-memory store (almacén en memoria)
Un almacén de datos como Redis que guarda los datos en RAM para lograr una latencia muy baja a un costo mayor por gigabyte.
Ejemplo real

Un minorista ya tiene su catálogo, sus pedidos y sus tablas de clientes en PostgreSQL y quiere búsqueda semántica de productos filtrada por existencias y región del cliente. PostgreSQL con pgvector encaja porque una sola consulta SQL puede combinar los embeddings con el inventario. Para reducir los costos del modelo de su asistente de compras, agrega Azure Managed Redis como caché semántica delante del modelo en lugar de mover el catálogo.

Consejo para el examen: Elige según el requisito dominante: escala global o change feed significa Cosmos DB; joins relacionales o un PostgreSQL existente significa pgvector; latencia mínima o caché de respuestas significa Redis; las combinaciones son comunes y a menudo correctas.

Comprueba lo que sabes

Una app debe combinar los resultados de la búsqueda vectorial con pedidos y aplicar claves externas. ¿Qué almacén encaja mejor?

Azure Database for PostgreSQL con pgvector, porque admite joins de SQL, transacciones y restricciones junto con los vectores.

¿Por qué Redis no suele ser el almacén principal para un archivo grande de embeddings?

Guarda los datos en memoria, lo cual es costoso por gigabyte, y normalmente se usa como caché y no como sistema de registro.
