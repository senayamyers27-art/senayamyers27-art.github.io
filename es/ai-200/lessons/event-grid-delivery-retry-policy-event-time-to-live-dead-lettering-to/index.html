Entrega de Event Grid: directiva de reintentos, tiempo de vida del evento, envío a mensajes fallidos en Blob Storage, validación de webhooks y esquema CloudEvents

Event Grid entrega cada evento a cada suscripción que coincide al menos una vez. Si el controlador no confirma el éxito, Event Grid reintenta. Entender cómo funciona la entrega te ayuda a crear controladores que no pierdan eventos ni fallen ante los reintentos.

Un controlador confirma el éxito devolviendo un código de estado HTTP de éxito (como 200 OK o 202 Accepted). Los errores y los tiempos de espera agotados activan la directiva de reintentos: Event Grid espera y reintenta según un calendario de retroceso exponencial con algo de aleatoriedad, en intervalos cada vez más largos. Algunos errores que reintentar no puede solucionar, como ciertas respuestas 400 Bad Request o 413 Request Entity Too Large, no se reintentan. Como un evento puede llegar más de una vez, los controladores deben ser idempotentes, por ejemplo haciendo seguimiento del id del evento.

La directiva de reintentos de cada suscripción tiene dos límites: el máximo de intentos de entrega y el tiempo de vida del evento en minutos. De forma predeterminada, Event Grid intenta hasta 30 veces y sigue intentando durante un máximo de 1,440 minutos (24 horas), lo que ocurra primero. Puedes reducir cualquiera de los dos, por ejemplo cuando los eventos pierden su valor después de unos minutos.

Cuando se alcanzan los límites, el evento se descarta a menos que hayas configurado el envío a mensajes fallidos (dead-lettering). Este envía los eventos no entregados a un contenedor de Blob Storage que especifiques, como archivos JSON, para que puedas inspeccionarlos y volver a reproducirlos. Event Grid necesita permiso para escribir en ese contenedor, normalmente mediante una identidad administrada en el tema.

az eventgrid event-subscription create --name orders-hook \
  --source-resource-id $TOPIC_ID --endpoint $WEBHOOK_URL \
  --max-delivery-attempts 10 --event-ttl 120 \
  --deadletter-endpoint $STORAGE_ID/blobServices/default/containers/eg-deadletter

Antes de entregar a un webhook, Event Grid valida que eres el propietario del punto de conexión, para que nadie pueda dirigir eventos al servicio de otra persona. Con el esquema de Event Grid, envía un Microsoft.EventGrid.SubscriptionValidationEvent cuyos datos contienen un validationCode. Tu punto de conexión demuestra la propiedad de forma sincrónica, devolviendo el código en el cuerpo de la respuesta como validationResponse, o de forma manual, enviando una solicitud GET a la validationUrl incluida en el evento dentro de un tiempo limitado. Con el esquema CloudEvents, la validación usa en su lugar el protocolo de enlace de protección contra abusos de webhooks de CloudEvents: una solicitud HTTP OPTIONS con un encabezado WebHook-Request-Origin, que se responde con un encabezado WebHook-Allowed-Origin. Azure Functions, Logic Apps y otros controladores de Azure completan la validación por ti.

Event Grid admite dos esquemas de eventos. El esquema de Event Grid usa campos como id, topic, subject, eventType, eventTime, data y dataVersion. CloudEvents v1.0 es una especificación abierta y neutral respecto al proveedor de la CNCF (Cloud Native Computing Foundation), con campos como id, source, type, subject, time, specversion y data. Elige CloudEvents para la interoperabilidad entre nubes y herramientas. Defines el esquema de entrada en un tema personalizado y el esquema de entrega en una suscripción.

Términos clave

Retry policy (directiva de reintentos)
Límites por suscripción de intentos de entrega y de tiempo de vida del evento que rigen los reintentos de Event Grid.
Event time-to-live (tiempo de vida del evento)
El número de minutos que Event Grid sigue reintentando un evento antes de rendirse; 1,440 de forma predeterminada.
Dead-letter destination (destino de mensajes fallidos)
Un contenedor de Blob Storage donde Event Grid escribe los eventos que no pudo entregar.
Validation handshake (protocolo de validación)
El proceso mediante el cual un webhook demuestra que es propietario del punto de conexión antes de que Event Grid le entregue eventos.
CloudEvents
Una especificación abierta para describir los datos de eventos en un formato común entre servicios y nubes.
Ejemplo real

El webhook de un socio estuvo caído durante dos días. Los eventos de más de 24 horas se perdieron porque la suscripción no tenía un destino de mensajes fallidos. El equipo configuró el envío a mensajes fallidos a un contenedor de almacenamiento, redujo el máximo de intentos de entrega para detectar fallas más rápido y escribió una pequeña herramienta de reproducción que lee los blobs JSON fallidos y los vuelve a publicar cuando el socio se recupera.

Consejo para el examen: Valores predeterminados que debes recordar: 30 intentos de entrega y 1,440 minutos de TTL; los eventos no entregados se descartan a menos que se configure el envío a mensajes fallidos en Blob Storage. Un webhook personalizado debe devolver el validationCode como validationResponse (o llamar a validationUrl).

Comprueba lo que sabes

¿Qué le pasa a un evento que agota sus reintentos cuando no hay un destino de mensajes fallidos?

Se descarta; configura el envío a mensajes fallidos en un contenedor de Blob Storage para conservar los eventos no entregados.

¿Cómo completa un webhook personalizado la validación del esquema de Event Grid de forma sincrónica?

Responde al SubscriptionValidationEvent devolviendo el validationCode como validationResponse en el cuerpo.
