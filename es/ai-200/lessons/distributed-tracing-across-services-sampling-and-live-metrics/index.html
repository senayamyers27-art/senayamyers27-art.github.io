Seguimiento distribuido entre servicios, muestreo y métricas en vivo

Las apps modernas son cadenas de servicios: un front-end llama a una API, que lee de Cosmos DB, envía un mensaje de Service Bus y llama al punto de conexión de un modelo, y un worker toma el mensaje más tarde. Cuando un usuario informa de una solicitud lenta o fallida, necesitas seguir esa solicitud a través de cada salto. El seguimiento distribuido (distributed tracing) lo logra dando a todo el trabajo de una operación un ID de traza compartido y vinculando cada pieza con su padre.

El mecanismo es la propagación del contexto. OpenTelemetry usa el estándar W3C Trace Context: cuando tu app instrumentada hace una llamada HTTP saliente, agrega un encabezado traceparent que contiene el ID de traza y el ID del span actual. El servicio receptor, también instrumentado, lee el encabezado y crea sus propios spans como hijos dentro de la misma traza. Los SDK de mensajería, incluidos Service Bus y Event Hubs, llevan el mismo contexto en las propiedades del mensaje, para que el procesamiento de un consumidor quede vinculado con el productor. Si un servicio de la cadena no está instrumentado, o elimina los encabezados, la traza se rompe en piezas separadas.

En Application Insights, el ID de traza aparece como operation_Id en cada elemento (requests, dependencies, exceptions, traces), y operation_ParentId vincula un elemento con su span padre. La vista de detalles de transacción de extremo a extremo del portal dibuja todo el árbol como una línea de tiempo, para que veas qué salto consumió el tiempo o lanzó el error. El mapa de aplicación (application map) agrega muchas trazas en un diagrama de componentes y sus llamadas, con las tasas de error y las duraciones en cada conexión. Cada servicio debe definir un nombre de rol en la nube distinto (por ejemplo, mediante la variable de entorno OTEL_SERVICE_NAME o los atributos del recurso) para que aparezca como su propio nodo en el mapa.

Las apps con mucho tráfico pueden producir más telemetría de la que quieres pagar o analizar. El muestreo (sampling) conserva un subconjunto representativo. Con la Azure Monitor OpenTelemetry Distro, configuras una proporción de muestreo (por ejemplo, configure_azure_monitor(sampling_ratio=0.1) para conservar alrededor del 10 por ciento), y las versiones más recientes también ofrecen un muestreador con límite de frecuencia que limita las trazas por segundo. Las decisiones de muestreo se toman por traza, no por elemento, así que una traza conservada mantiene todos sus spans relacionados en todos los servicios, y nunca se muestra una solicitud a la que le falte la mitad de sus dependencias. Application Insights registra la tasa de muestreo en la columna itemCount, y los gráficos del portal la usan para estimar los totales reales; en tus propias consultas KQL, usa sum(itemCount) en lugar de count() cuando necesites recuentos precisos sobre datos muestreados.

Live Metrics muestra un flujo casi en tiempo real de la tasa de solicitudes, la tasa de errores, las llamadas a dependencias, las excepciones, la CPU y la memoria de cada instancia en ejecución, con una latencia de alrededor de un segundo. No se basa en datos almacenados y no se ve afectado por el muestreo, así que es ideal mientras implementas una revisión nueva o durante un incidente, cuando esperar minutos a la ingesta es demasiado lento. Con la distro lo habilitas mediante una opción de configuración, y se puede proteger con la autenticación de Microsoft Entra.

En la práctica: instrumenta todos los servicios, propaga el contexto a través de HTTP y la mensajería, muestrea con criterio, observa Live Metrics durante los despliegues y usa la vista de extremo a extremo y el mapa de aplicación para las investigaciones.

Términos clave

Trace context (contexto de traza)
El estándar de W3C para propagar los IDs de traza y de span entre servicios, que viaja en el encabezado traceparent.
operation_Id
El campo de Application Insights que contiene el ID de traza compartido por toda la telemetría de una operación.
Sampling (muestreo)
Conservar solo una parte de la telemetría, decidido por traza, para reducir costos sin dejar de ser representativo.
Live Metrics (métricas en vivo)
Una vista casi en tiempo real de las métricas de solicitudes, errores y recursos que no se ve afectada por el muestreo.
Application map (mapa de aplicación)
Una vista de Application Insights que muestra los componentes y sus dependencias con datos de rendimiento y errores.
Ejemplo real

Los usuarios informan que el proceso de pago a veces tarda ocho segundos. En la vista de transacción de extremo a extremo de un operation_Id lento, la solicitud del front-end contiene una llamada a la API cuya dependencia hija con el punto de conexión del modelo tarda siete segundos, mientras que las llamadas a Cosmos DB tardan milisegundos. El equipo agrega un tiempo de espera y una alternativa en caché, observa Live Metrics mientras se despliega la revisión nueva y ve que la latencia baja de inmediato.

Consejo para el examen: El ID de traza compartido aparece como operation_Id; el muestreo es por traza y se registra en itemCount, así que cuenta con sum(itemCount); Live Metrics es en tiempo real y no se ve afectado por el muestreo.

Comprueba lo que sabes

¿Cómo sabe un servicio posterior que pertenece a la misma traza que quien lo llamó?

Quien llama propaga el encabezado traceparent (o las propiedades del mensaje) con el ID de traza y el ID del span padre.

¿Por qué usar sum(itemCount) en lugar de count() en KQL sobre telemetría muestreada?

Cada elemento almacenado representa itemCount elementos originales, así que sumarlo estima el total real.
