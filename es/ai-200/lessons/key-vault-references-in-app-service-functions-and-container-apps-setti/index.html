Referencias de Key Vault en la configuración de App Service, Functions y Container Apps

Muchas apps leen la configuración de variables de entorno, y quizá no quieras cambiar el código para llamar al SDK de Key Vault. Las referencias de Key Vault permiten que la plataforma obtenga un secreto de Key Vault y se lo presente a tu app como una configuración o secreto común. El valor nunca aparece en la configuración de la app, en el control de código fuente ni en las plantillas de implementación; solo aparece un puntero.

En App Service y Azure Functions, defines el valor de una configuración de la app con una sintaxis de referencia especial en lugar del secreto en sí. Hay dos formas: una que nombra el almacén y el secreto, y otra que da el URI completo del secreto. Ambas van envueltas en @Microsoft.KeyVault(...).

DB_PASSWORD = @Microsoft.KeyVault(VaultName=shop-kv;SecretName=db-password)
DB_PASSWORD = @Microsoft.KeyVault(VaultName=shop-kv;SecretName=db-password;SecretVersion=<version-id>)
DB_PASSWORD = @Microsoft.KeyVault(SecretUri=<vault-uri>/secrets/db-password/)

Tu código de Python sigue llamando a os.environ["DB_PASSWORD"] y recibe el secreto resuelto. Para que esto funcione, la app necesita una identidad administrada con acceso de lectura al secreto (Key Vault Secrets User en modo RBAC, o un permiso Get en una directiva de acceso), y el almacén debe ser accesible desde la red de la app. De forma predeterminada, la plataforma usa la identidad asignada por el sistema; para usar una identidad asignada por el usuario, define la propiedad keyVaultReferenceIdentity del sitio con el ID de recurso de esa identidad. El portal muestra un estado junto a cada referencia, que es el primer lugar donde mirar si una configuración muestra el texto de referencia sin procesar o un error: las causas comunes son un rol faltante, la identidad equivocada, un firewall que bloquea el acceso o un error de escritura en el nombre.

Sin versión, la referencia se resuelve con la versión más reciente, y la plataforma la actualiza periódicamente (en aproximadamente un día) o cuando cambia la configuración o se reinicia la app, así que un secreto rotado se toma sin editar la configuración. Con versión, la referencia queda fijada y nunca cambia hasta que la actualices. Functions también puede usar referencias para configuraciones de conexión como AzureWebJobsStorage, aunque las conexiones basadas en identidad suelen ser mejores que almacenar esa cadena de conexión.

Container Apps usa un modelo ligeramente distinto. Los secretos se definen a nivel de la app, y un secreto puede ser una referencia de Key Vault: indicas el URI del secreto de Key Vault y la identidad administrada que se usará (el ID de recurso de una identidad asignada por el usuario, o system). Luego, las variables de entorno apuntan a ese secreto con secretref:, como con cualquier otro secreto. Container Apps obtiene el valor de Key Vault y, cuando haces referencia a un secreto sin versión, se usa la versión más reciente; las réplicas en ejecución toman los cambios después de un reinicio o de una revisión nueva.

az containerapp secret set -n orders -g rg \
  --secrets "db-pass=keyvaultref:<key-vault-secret-uri>,identityref:<identity-resource-id>"
az containerapp update -n orders -g rg --set-env-vars DB_PASSWORD=secretref:db-pass

La idea principal para el examen: el código sigue igual, el secreto vive solo en Key Vault y una identidad administrada con un rol de lectura del plano de datos une ambos.

Términos clave

Key Vault reference (referencia de Key Vault)
Un valor de configuración o secreto de la app que apunta a un secreto de Key Vault, que la plataforma resuelve en tiempo de ejecución.
@Microsoft.KeyVault(...)
La sintaxis de referencia que se usa en la configuración de las apps de App Service y Functions, con VaultName/SecretName o SecretUri.
keyVaultReferenceIdentity
La propiedad del sitio de App Service que selecciona una identidad asignada por el usuario para resolver las referencias de Key Vault.
keyvaultref
La sintaxis de secretos de Container Apps que obtiene el valor de un secreto a partir del URI de un secreto de Key Vault con una identidad.
Ejemplo real

Una app de App Service mostraba el texto literal @Microsoft.KeyVault(VaultName=shop-kv;SecretName=db-password) como contraseña de la base de datos y no lograba conectarse. El estado de la referencia en el portal indicaba acceso denegado. La app usaba una identidad asignada por el usuario, pero keyVaultReferenceIdentity no estaba definida, así que la plataforma intentaba con la asignada por el sistema. Definir la propiedad y asignar Key Vault Secrets User lo resolvió.

Consejo para el examen: Si una app recibe el texto @Microsoft.KeyVault sin procesar, la referencia no se resolvió: revisa la identidad, su rol Secrets User, keyVaultReferenceIdentity para identidades asignadas por el usuario y la red del almacén. Omite la versión para seguir las rotaciones.

Comprueba lo que sabes

¿Qué necesita una app de App Service para que se resuelva una referencia de Key Vault?

Una identidad administrada con acceso de lectura al secreto (como Key Vault Secrets User) y acceso de red al almacén.

¿Cómo usa una variable de entorno de Container Apps un secreto respaldado por Key Vault?

Define un secreto de la app con keyvaultref y un identityref, y luego asigna a la variable el valor secretref:<nombre-del-secreto>.
