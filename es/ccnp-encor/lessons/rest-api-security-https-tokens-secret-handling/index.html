Seguridad de las API REST: HTTPS, tokens, manejo de secretos

Los controladores como Catalyst Center y SD-WAN Manager, y los dispositivos que ejecutan RESTCONF, exponen API REST que pueden leer y cambiar toda la red. Quien tenga credenciales de API válidas tiene, en la práctica, acceso de administrador. ENCOR espera que entiendas cómo se protegen estas API y cómo manejar las credenciales de forma segura en la automatización.

La seguridad del transporte va primero. Las API deben ser alcanzables solo por HTTPS, que usa TLS (Transport Layer Security) para cifrar las solicitudes y las respuestas y para demostrar la identidad del servidor con un certificado. HTTP simple expondría las credenciales y los tokens a cualquiera en la ruta. Los clientes deben validar el certificado del servidor contra una autoridad certificadora de confianza. Deshabilitar la verificación, por ejemplo con verify=False en requests de Python, es común en laboratorios con certificados autofirmados, pero en producción permite ataques de intermediario (man-in-the-middle). La mejor solución es instalar en el controlador o dispositivo un certificado de la autoridad certificadora de tu empresa, o apuntar el cliente al paquete de CA correcto.

Los métodos de autenticación varían. La autenticación HTTP Basic envía un usuario y una contraseña codificados en base64 en el encabezado Authorization en cada solicitud; base64 es una codificación, no un cifrado, así que solo es aceptable sobre HTTPS. La mayoría de los controladores usan en su lugar autenticación basada en tokens: el cliente envía las credenciales una vez a un endpoint de autenticación y recibe un token, que luego incluye en las solicitudes posteriores. Catalyst Center, por ejemplo, devuelve un token desde su endpoint de autenticación que pasas en el encabezado X-Auth-Token. Los tokens expiran después de un tiempo definido, lo que limita el daño si uno se filtra. Otros esquemas incluyen las API keys (secretos de larga duración que identifican una aplicación), los bearer tokens de OAuth 2.0 (Authorization: Bearer <token>) con scopes, y las cookies de sesión con tokens contra la falsificación de solicitudes entre sitios (CSRF), que usa SD-WAN Manager.

La autorización debe seguir el principio de mínimo privilegio. Crea cuentas de servicio para la automatización con solo los roles que necesitan, como solo lectura para los scripts de monitoreo, en lugar de reutilizar una cuenta personal de administrador. Los controladores admiten el control de acceso basado en roles para esto. Registra y revisa la actividad de las API, y aplica limitación de tasa y restricciones de direcciones de origen donde sea posible.

El manejo de secretos es donde ocurren la mayoría de las fallas en el mundo real. Nunca escribas contraseñas, tokens o claves directamente en los scripts, y nunca los subas al control de versiones; un secreto subido a un repositorio debe considerarse comprometido y rotarse aunque se borre después. En su lugar, lee los secretos de variables de entorno, de un archivo de configuración protegido excluido del repositorio o, lo mejor, de un gestor de secretos o vault que proporcione control de acceso, auditoría y rotación. Enmascara los secretos en los logs y en los mensajes de error. Rota las credenciales periódicamente y de inmediato cuando alguien se va o se sospecha una filtración. Guarda los tokens solo en memoria durante la duración del trabajo, y solicita uno nuevo cuando expiren.

Por último, valida las entradas y maneja los errores: una respuesta 401 significa que la autenticación falló o que el token expiró, y un 403 significa que la identidad está autenticada pero no tiene permiso, lo cual es una señal para revisar los roles en lugar de reintentar.

Términos clave

HTTPS
HTTP protegido por TLS, que cifra el tráfico y autentica al servidor con un certificado.
Token authentication (autenticación por token)
Intercambiar las credenciales una sola vez por un token con tiempo limitado que se envía con las solicitudes posteriores.
Bearer token
Un token presentado en el encabezado Authorization; quien lo tenga puede usarlo.
Least privilege (mínimo privilegio)
Otorgar a una cuenta solo los permisos que su tarea requiere.
Secrets manager (gestor de secretos)
Un sistema que almacena las credenciales de forma segura con control de acceso, auditoría y rotación.
Ejemplo real

El script de un desarrollador para Catalyst Center contiene una contraseña de administrador en texto claro y se sube a un repositorio Git compartido. El equipo rota la contraseña, crea una cuenta de servicio de solo lectura para el script, guarda sus credenciales en el vault de la empresa y cambia el script para que las obtenga en tiempo de ejecución y solicite un token nuevo en cada ejecución.

Consejo para el examen: La autenticación Basic solo está codificada, no cifrada, así que necesita HTTPS. 401 significa que debes autenticarte de nuevo; 403 significa que te falta permiso. Un secreto filtrado debe rotarse, no solo borrarse del archivo.

Comprueba lo que sabes

¿Por qué verify=False es peligroso en los scripts de producción?

Deshabilita la validación de certificados, lo que permite que un intermediario suplante al servidor de la API y capture credenciales o tokens.

¿Por qué las API basadas en tokens mejoran respecto a enviar las credenciales en cada solicitud?

Las credenciales se envían una sola vez; el token tiene tiempo limitado y puede tener un alcance restringido, lo que reduce la exposición si se filtra.

Menciona dos lugares seguros para guardar los secretos de API de un script.

Variables de entorno o, preferiblemente, un gestor de secretos o vault; no en el script ni en el repositorio.
