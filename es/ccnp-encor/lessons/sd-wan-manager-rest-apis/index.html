APIs REST de SD-WAN Manager

Cisco Catalyst SD-WAN Manager (antes vManage) expone una API REST que cubre casi todo lo que hay en su GUI: inventario de dispositivos, estadísticas de monitoreo, alarmas y eventos, plantillas y grupos de configuración, políticas y actualizaciones de software. Es el único punto de entrada programable a todo el fabric SD-WAN, porque los WAN Edges se administran a través del Manager y no de forma individual.

Las rutas de la API empiezan con /dataservice/ en la dirección HTTPS del Manager. La autenticación se basa en sesiones, no en un simple encabezado con token. Primero, envías un POST a /j_security_check con los campos codificados como formulario j_username y j_password. Si tiene éxito, el Manager devuelve una cookie de sesión llamada JSESSIONID, que el cliente debe enviar en las solicitudes posteriores. Un objeto Session de requests maneja esto automáticamente. Segundo, para cualquier solicitud que cambie algo (POST, PUT, DELETE), necesitas un token contra falsificación de solicitudes entre sitios (CSRF o XSRF): envía un GET a /dataservice/client/token e incluye el valor devuelto en un encabezado X-XSRF-TOKEN. Algunas versiones más recientes también admiten otros métodos basados en token, pero el patrón de cookie de sesión más token XSRF es el que debes conocer.

import os, requests
s = requests.Session()
BASE = os.environ["MANAGER_URL"]  # Dirección HTTPS de SD-WAN Manager
user, password = os.environ["MANAGER_USER"], os.environ["MANAGER_PASS"]
s.post(BASE + "/j_security_check",
       data={"j_username": user, "j_password": password}, verify="ca.pem")
xsrf = s.get(BASE + "/dataservice/client/token", verify="ca.pem").text
s.headers.update({"X-XSRF-TOKEN": xsrf, "Content-Type": "application/json"})
devices = s.get(BASE + "/dataservice/device", verify="ca.pem").json()
for d in devices["data"]:
    print(d["host-name"], d["system-ip"], d["reachability"])

Algunas cosas para notar. Un inicio de sesión fallido a menudo igual devuelve HTTP 200, pero con una página HTML de login en lugar de una cookie, así que revisa el contenido de la respuesta, no solo el código de estado. La mayoría de las respuestas de monitoreo envuelven los resultados en una clave data, y los nombres de los campos usan guiones, como host-name y system-ip. Cuando termines, cierra la sesión (con un endpoint como /logout) para liberarla, ya que el Manager limita las sesiones concurrentes.

La API está agrupada en áreas. Los endpoints de monitoreo entregan el estado del dispositivo, estadísticas de interfaces, el health de sesiones BFD y túneles, las conexiones de control y el estado de OMP para un dispositivo identificado por su system IP. Los endpoints de alarmas y eventos reportan problemas. Los endpoints de configuración administran plantillas, grupos de configuración y políticas, y los endpoints de acciones de dispositivo disparan operaciones como actualizaciones de software o reinicios, que son asíncronas y devuelven un ID cuyo estado debes revisar. Las consultas en tiempo real se envían al dispositivo a través del Manager y deben usarse con moderación porque cargan al dispositivo. El Manager incluye documentación de la API integrada (a menudo accesible desde su menú de ayuda) que lista los endpoints de tu versión, y es la referencia autorizada, ya que las rutas cambian entre versiones.

Los usos típicos de automatización incluyen llevar el inventario a una CMDB, exportar el rendimiento de los túneles a un sistema de reportes, auditar que cada edge tenga la versión de software aprobada e integrar las alarmas con el sistema de tickets. Sigue las mismas prácticas de seguridad que con cualquier API: cuentas dedicadas de mínimo privilegio, secretos fuera del código, validación de certificados y cierre de sesión.

Términos clave

/dataservice
La ruta base de los endpoints de la API REST de SD-WAN Manager.
j_security_check
El endpoint de inicio de sesión que acepta usuario y contraseña codificados como formulario y devuelve una cookie JSESSIONID.
JSESSIONID
La cookie de sesión que autentica las llamadas posteriores a la API de SD-WAN Manager.
X-XSRF-TOKEN
Encabezado que lleva el token CSRF obtenido de /dataservice/client/token, requerido para POST, PUT y DELETE.
Ejemplo real

Un equipo de operaciones quiere un reporte nocturno de los WAN Edges que no son alcanzables o que tienen una versión de software antigua. Un script inicia sesión mediante j_security_check, lee /dataservice/device, filtra la lista data por alcanzabilidad y versión, escribe un CSV y cierra la sesión, sin que nadie abra la GUI.

Consejo para el examen: SD-WAN Manager usa una cookie de sesión (JSESSIONID desde j_security_check) más un X-XSRF-TOKEN para los cambios; Catalyst Center usa X-Auth-Token. No los confundas.

Comprueba lo que sabes

¿Qué dos credenciales necesita un script para enviar un POST a SD-WAN Manager?

La cookie de sesión JSESSIONID obtenida al iniciar sesión mediante j_security_check y el token XSRF en el encabezado X-XSRF-TOKEN.

¿Por qué revisar el contenido de la respuesta de inicio de sesión y no solo su código de estado?

Un inicio de sesión fallido puede devolver HTTP 200 con una página HTML de login en lugar de una sesión válida.
