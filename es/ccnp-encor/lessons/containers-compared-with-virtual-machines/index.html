Contenedores en comparación con máquinas virtuales

Los contenedores son otra forma de aislar aplicaciones y se han convertido en la manera estándar de empaquetar el software moderno, incluidas muchas herramientas de red y algunas aplicaciones de Cisco. ENCOR te pide entender en qué se diferencian los contenedores de las máquinas virtuales y cuándo conviene cada uno.

Una máquina virtual virtualiza el hardware. El hipervisor presenta CPU, memoria y dispositivos virtuales, y cada VM ejecuta su propio sistema operativo invitado completo con su propio kernel. Eso da un aislamiento fuerte y te permite ejecutar distintos sistemas operativos lado a lado, por ejemplo Windows y Linux en el mismo host. El costo es el tamaño y el tiempo de arranque: cada VM lleva un sistema operativo completo, típicamente de gigabytes, y arranca como una computadora real.

Un contenedor, en cambio, virtualiza el sistema operativo. Todos los contenedores de un host comparten el kernel del host. El motor de contenedores, como Docker o containerd, usa funciones del kernel (namespaces para darle a cada contenedor su propia vista de los procesos, las interfaces de red y el sistema de archivos, y control groups para limitar la CPU y la memoria) para aislar los procesos. Una imagen de contenedor contiene solo la aplicación y las bibliotecas que necesita, no un kernel, así que las imágenes son pequeñas, a menudo de megabytes, y los contenedores arrancan en aproximadamente el tiempo que tarda en iniciarse un proceso. Puedes ejecutar muchos más contenedores que VM en el mismo hardware.

Las contrapartidas se derivan directamente de esto. Como los contenedores comparten el kernel del host, deben ser compatibles con él: los contenedores Linux necesitan un kernel Linux. El aislamiento es más débil que el de una VM, ya que una vulnerabilidad del kernel puede afectar a todos los contenedores del host, así que importan prácticas de seguridad como ejecutar sin privilegios de root, usar imágenes mínimas y escanear las imágenes. Las VM son mejores para ejecutar distintos sistemas operativos, aplicaciones heredadas y cargas de trabajo que necesitan un aislamiento fuerte. Los contenedores son mejores para microservicios, el escalado rápido, entornos consistentes desde la laptop del desarrollador hasta producción y los pipelines de despliegue automatizados. En la práctica a menudo se combinan: los contenedores se ejecutan dentro de VM.

Cuando muchos contenedores se ejecutan en muchos hosts, un orquestador los programa, reinicia los que fallan, los escala y los conecta. Kubernetes es el más común. Las redes de contenedores usan interfaces virtuales y bridges en cada host, y los orquestadores agregan redes overlay para que los contenedores en distintos hosts puedan comunicarse.

Los dispositivos de red Cisco también alojan contenedores. Muchos switches y routers Catalyst IOS XE admiten application hosting, que te permite ejecutar un contenedor Docker en el dispositivo, por ejemplo un agente de monitoreo o una herramienta de resolución de problemas, aislado de los procesos de IOS XE. Guest Shell es un entorno de contenedor Linux integrado en IOS XE que te permite ejecutar scripts de Python en el dispositivo.

Términos clave

Container (contenedor)
Un entorno de procesos aislado que comparte el kernel del sistema operativo del host y empaqueta una aplicación con sus dependencias.
Container image (imagen de contenedor)
Un paquete portable y por capas de una aplicación y sus bibliotecas que se usa para iniciar contenedores.
Namespaces y cgroups
Funciones del kernel de Linux que aíslan la vista del sistema de un contenedor y limitan su uso de recursos.
Kubernetes
Una plataforma de orquestación de contenedores que programa, escala y repara contenedores en un clúster de hosts.
Ejemplo real

Un equipo de red empaqueta su script de respaldo de configuraciones con Python y sus bibliotecas en una pequeña imagen de contenedor. Se ejecuta de forma idéntica en una laptop, en un servidor Linux y en un clúster de Kubernetes, y arranca en aproximadamente un segundo cada noche, mientras que el enfoque anterior necesitaba una VM dedicada que tardaba minutos en arrancar y en recibir parches.

Consejo para el examen: La distinción central es el kernel: cada VM tiene el kernel de su propio sistema operativo invitado; los contenedores comparten el kernel del host. Por eso los contenedores son más ligeros y rápidos, pero están menos aislados y deben coincidir con la familia del sistema operativo del host.

Comprueba lo que sabes

¿Por qué los contenedores arrancan más rápido que las máquinas virtuales?

No arrancan un sistema operativo; son procesos aislados que comparten el kernel del host que ya está en ejecución.

¿Cuándo elegirías una VM en lugar de un contenedor?

Cuando necesitas un sistema operativo distinto al del host, un aislamiento fuerte, o estás ejecutando una aplicación heredada no diseñada para contenedores.
