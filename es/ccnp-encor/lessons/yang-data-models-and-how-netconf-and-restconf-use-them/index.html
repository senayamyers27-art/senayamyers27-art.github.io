Modelos de datos YANG y cómo los usan NETCONF y RESTCONF

YANG (Yet Another Next Generation, RFC 7950) es un lenguaje de modelado de datos. Un modelo YANG no contiene la configuración en sí; define la estructura, los nombres, los tipos de datos y las restricciones de los datos de configuración y operacionales, como un esquema. Como todas las herramientas coinciden en el modelo, un script puede establecer la descripción de una interfaz mediante NETCONF o RESTCONF y saber exactamente qué campo está cambiando y qué valores son válidos, sin analizar texto de la CLI.

Los modelos YANG se construyen con unos cuantos tipos de nodos. Un container agrupa nodos relacionados y no tiene valor propio, como una carpeta. Un leaf contiene un solo valor de un tipo definido, como una cadena, un entero, un booleano o una enumeración. Un leaf-list contiene múltiples valores de un mismo tipo, como una lista de servidores DNS. Un list contiene múltiples entradas de un conjunto de nodos, cada una identificada por un leaf clave (key), como una lista de interfaces con el nombre como clave. Los modelos también definen tipos (typedef), grupos reutilizables de nodos (grouping y uses), restricciones como rangos y patrones, y si los datos son de configuración (config true) o de estado (config false, datos operacionales).

container interfaces {
  list interface {
    key "name";
    leaf name { type string; }
    leaf description { type string; }
    leaf enabled { type boolean; default true; }
  }
}

Hay varias familias de modelos. Los modelos IETF se basan en estándares y son neutrales respecto al fabricante, como ietf-interfaces e ietf-ip. Los modelos OpenConfig los escribe un grupo de operadores de red para que sean neutrales respecto al fabricante y estén enfocados en la operación. Los modelos nativos (del fabricante), como Cisco-IOS-XE-native de Cisco, cubren todas las funciones que admite la plataforma, incluidas las que los modelos estándar no cubren. Los modelos estándar hacen que los scripts sean portables; los modelos nativos dan cobertura completa. Los dispositivos anuncian los modelos que admiten, y puedes explorarlos con herramientas como pyang, que imprime un modelo como árbol, o YANG Suite de Cisco.

NETCONF y RESTCONF son los transportes que llevan los datos definidos por YANG. NETCONF los codifica en XML dentro de RPC sobre SSH, con namespaces XML que identifican el modelo; las capabilities intercambiadas en el mensaje hello listan los modelos admitidos. Un get-config de NETCONF con un filtro subtree selecciona parte de un modelo. RESTCONF los codifica en JSON o XML sobre HTTPS, y la ruta de la URL sigue el árbol del modelo: /restconf/data/ más el nombre del módulo, dos puntos, el nodo de nivel superior y luego los nodos hijos, con las claves de las listas indicadas después de un signo igual. Por ejemplo, /restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1/description direcciona el leaf description de una interfaz. En JSON, la clave de nivel superior se califica con el nombre del módulo, como en "ietf-interfaces:interfaces".

La idea clave para ENCOR es la separación de responsabilidades: YANG es el modelo (cómo se ven los datos), XML o JSON es la codificación (cómo se escriben) y NETCONF o RESTCONF es el protocolo (cómo se transportan y qué operaciones están permitidas).

Términos clave

YANG
Un lenguaje de modelado de datos que define la estructura y los tipos de los datos de configuración y de estado de la red.
Container
Un nodo YANG que agrupa otros nodos y no contiene valor propio.
Leaf
Un nodo YANG que contiene un solo valor con tipo.
List
Un nodo YANG con múltiples entradas, cada una identificada por un leaf clave.
Native model (modelo nativo)
Un modelo YANG específico del fabricante que cubre todas las funciones de la plataforma, como Cisco-IOS-XE-native.
Ejemplo real

Una ingeniera quiere deshabilitar una interfaz mediante RESTCONF. Al mirar el árbol de ietf-interfaces en pyang, ve que interfaces es un container, interface es un list con name como clave y enabled es un leaf booleano. Envía un PATCH a /restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet2 con el cuerpo JSON que establece enabled en false.

Consejo para el examen: Recuerda las capas: YANG es el modelo, XML o JSON es la codificación, NETCONF o RESTCONF es el transporte. Un list necesita una clave; un container no.

Comprueba lo que sabes

¿Cuál es la diferencia entre un leaf y un leaf-list?

Un leaf contiene un valor; un leaf-list contiene múltiples valores del mismo tipo.

¿Cómo se identifica una entrada específica de un list en una URL de RESTCONF?

Agregando un signo igual y el valor de la clave al nombre del list, por ejemplo interface=GigabitEthernet1.

¿Por qué podrías usar un modelo nativo en lugar de un modelo IETF?

Los modelos nativos cubren todas las funciones de la plataforma, incluidas las que los modelos neutrales respecto al fabricante no definen.
