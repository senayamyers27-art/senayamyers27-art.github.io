Workload Identity Federation para GKE y para cargas de trabajo fuera de Google Cloud

Las cargas de trabajo también necesitan identidades, y el objetivo es darle a cada una sus propias credenciales de Google de corta duración sin claves. Google Cloud ofrece dos funciones relacionadas, ambas llamadas Workload Identity Federation, una para los pods de GKE y otra para las cargas de trabajo que se ejecutan en otros lugares.

Sin una configuración especial, los pods de un nodo de GKE usan la cuenta de servicio del nodo a través del servidor de metadatos, así que todos los pods del nodo comparten los mismos permisos. Workload Identity Federation for GKE soluciona esto. Cuando está habilitada en el clúster (siempre está activa en Autopilot) y en el grupo de nodos, GKE ejecuta un servidor de metadatos que da a cada pod credenciales para su cuenta de servicio de Kubernetes. Luego otorgas roles de IAM directamente a esa cuenta de servicio de Kubernetes usando un identificador de principal basado en el workload identity pool del proyecto (PROJECT_ID.svc.id.goog), o vinculas la cuenta de servicio de Kubernetes con una cuenta de servicio de Google otorgándole el rol Workload Identity User y anotando la cuenta de servicio de Kubernetes. De cualquier forma, cada app obtiene solo el acceso otorgado a su propia identidad.

Workload Identity Federation para cargas de trabajo externas permite que las aplicaciones fuera de Google Cloud se autentiquen sin claves. Algunos ejemplos son los pipelines de CI/CD en GitHub Actions o GitLab, las cargas de trabajo en AWS o Azure, y los sistemas locales con un proveedor de identidad OIDC o SAML. Creas un workload identity pool y un proveedor que confía en el proveedor de identidad externo, asignas atributos (como el nombre del repositorio) y agregas condiciones de atributos para restringir qué identidades externas se aceptan. La carga de trabajo externa intercambia su propio token con el Security Token Service de Google por un token federado de corta duración, y luego lo usa directamente en los recursos donde el principal federado tiene roles, o suplanta una cuenta de servicio.

Ambos enfoques eliminan las claves de larga duración, así que no hay nada que se pueda filtrar o rotar, y el acceso queda vinculado a identidades verificables, como un repositorio específico o un namespace de Kubernetes. El examen normalmente presenta un escenario con un pipeline de CI o con pods y pregunta por la forma más segura de dar acceso; la respuesta es la función de Workload Identity Federation correspondiente, no una clave guardada como secreto.

Términos clave

Workload Identity Federation for GKE
Una función de GKE que da a cada cuenta de servicio de Kubernetes su propia identidad de IAM y credenciales de corta duración.
Workload identity pool
Un contenedor de identidades externas en las que confía Google Cloud.
Workload identity pool provider
La configuración que confía en un proveedor de identidad externo específico, como el emisor OIDC de GitHub.
Security Token Service
El servicio de Google que intercambia tokens externos por tokens federados de corta duración.
Ejemplo real

El flujo de trabajo de GitHub Actions de una empresa despliega en Cloud Run. Un workload identity pool provider confía en los tokens OIDC de GitHub solo para el repositorio example-org/shop, y esa identidad puede suplantar a deploy-sa. No existe ninguna clave en ningún lugar, y un fork del repositorio no puede obtener credenciales.

Consejo para el examen: Pods que necesitan su propia identidad de Google: Workload Identity Federation for GKE. CI/CD u otras nubes sin claves: Workload Identity Federation con un pool y un proveedor. Las claves guardadas en secretos son la respuesta incorrecta.

Comprueba lo que sabes

¿Por qué es un problema usar la cuenta de servicio del nodo para todos los pods?

Todos los pods del nodo comparten los mismos permisos, lo que rompe el mínimo privilegio.

¿Qué restringe qué repositorios de GitHub pueden usar un workload identity pool provider?

Las asignaciones de atributos y las condiciones de atributos del proveedor, como una condición sobre el claim del repositorio.
