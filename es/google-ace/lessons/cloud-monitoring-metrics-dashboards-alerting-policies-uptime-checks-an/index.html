Cloud Monitoring: métricas, paneles, políticas de alertas, verificaciones de tiempo de actividad y el Ops Agent

Cloud Monitoring recopila métricas, que son mediciones numéricas a lo largo del tiempo, de servicios de Google Cloud, aplicaciones y agentes. Muchas métricas vienen integradas: utilización de CPU, bytes de red y operaciones de disco de Compute Engine; cantidad de solicitudes y latencias de Cloud Run; conexiones de Cloud SQL; códigos de respuesta del balanceador de carga. Un metrics scope permite que un proyecto vea las métricas de varios proyectos, para que puedas supervisar un entorno completo desde un solo lugar.

Algunas métricas importantes de las VMs vienen del interior del sistema operativo invitado y no se recopilan de forma predeterminada, en particular la utilización de memoria y el espacio en disco usado. Para obtenerlas, instala el Ops Agent en la VM. Recopila métricas del sistema y de aplicaciones y también envía logs a Cloud Logging, reemplazando a los antiguos agentes separados de Monitoring y Logging. Puedes instalarlo en VMs individuales o en flotas con una política de agentes (agent policy).

Los paneles (dashboards) visualizan las métricas. Google ofrece paneles predefinidos para muchos servicios, y puedes crear paneles personalizados con gráficos, filtros y agrupaciones. Metrics Explorer te permite consultar cualquier métrica rápidamente, por ejemplo la CPU promedio agrupada por instancia.

Las políticas de alertas (alerting policies) notifican a las personas cuando algo requiere atención. Una política tiene una o más condiciones, como un umbral de métrica (CPU por encima del 80% durante 5 minutos), la ausencia de una métrica (sin datos) o una coincidencia en los logs, y uno o más canales de notificación, como correo electrónico, SMS, la app móvil, Slack, PagerDuty, webhooks o Pub/Sub. Cuando se cumple la condición, se abre un incidente y se envían las notificaciones; la documentación de la política les indica a quienes responden qué hacer.

Las verificaciones de tiempo de actividad (uptime checks) prueban la disponibilidad desde el exterior. Envían solicitudes HTTP, HTTPS o TCP a una URL pública, una IP o un recurso desde varias ubicaciones del mundo a un intervalo fijo, y pueden verificar el contenido de la respuesta. Combinadas con una política de alertas, te avisan cuando los usuarios no pueden llegar a tu sitio. Para endpoints privados, las uptime checks pueden apuntar a recursos internos mediante una configuración compatible.

El monitoreo de servicios (service monitoring) se basa en todo esto con objetivos de nivel de servicio (SLOs), como que el 99.9% de las solicitudes tarde menos de 300 ms, y alertas de tasa de consumo (burn-rate) que avisan cuando estás gastando tu presupuesto de errores demasiado rápido.

Términos clave

Ops Agent
El agente de Google que recopila métricas del sistema operativo invitado, como el uso de memoria y disco, y logs de las VMs.
Alerting policy (política de alertas)
Condiciones más canales de notificación que abren incidentes cuando se cumple una condición de métrica o de log.
Uptime check (verificación de tiempo de actividad)
Una prueba de una URL, IP o recurso desde varias ubicaciones globales para verificar la disponibilidad.
Metrics scope
El conjunto de proyectos cuyas métricas puede ver juntas un proyecto de alcance.
Ejemplo real

Un equipo de operaciones instala el Ops Agent en todas las VMs mediante una política de agentes, agrega un panel que muestra la CPU, la memoria y el disco por servicio, crea una alerta cuando el uso de disco supera el 85% y agrega una uptime check sobre la página de inicio de www.example.com que alerta al ingeniero de guardia si fallan dos regiones.

Consejo para el examen: Las métricas de memoria y de espacio en disco necesitan el Ops Agent. 'Notificar cuando una métrica cruza un umbral' es una política de alertas. '¿Mi sitio web es accesible desde todo el mundo?' es una uptime check.

Comprueba lo que sabes

¿Por qué no ves la utilización de memoria de una VM nueva de forma predeterminada?

La memoria se mide dentro del sistema operativo invitado, así que requiere el Ops Agent.

¿Cuáles son las dos partes principales de una política de alertas?

Las condiciones que definen cuándo alertar y los canales de notificación que definen a quién se le avisa.
