Cuentas de servicio: crearlas, otorgarles roles, adjuntarlas a recursos y las cuentas de servicio predeterminadas

Una cuenta de servicio (service account) es una identidad para una carga de trabajo, no para una persona. Las aplicaciones que se ejecutan en VMs, GKE, Cloud Run o Cloud Run functions usan cuentas de servicio para llamar a las APIs de Google. Una cuenta de servicio tiene una dirección de correo como app-sa@my-proj.iam.gserviceaccount.com. Es a la vez un principal (se le pueden otorgar roles) y un recurso (a las personas se les pueden otorgar roles sobre ella, como el permiso para usarla).

Crea una con gcloud iam service-accounts create app-sa --display-name="App", y luego otórgale roles sobre los recursos que necesita, por ejemplo gcloud storage buckets add-iam-policy-binding gs://uploads --member=serviceAccount:app-sa@my-proj.iam.gserviceaccount.com --role=roles/storage.objectCreator. Crea una cuenta de servicio distinta para cada aplicación o componente, para que cada una tenga solo sus propios permisos y los registros de auditoría muestren qué carga de trabajo hizo qué.

Adjuntar una cuenta de servicio a un recurso es la forma en que la carga de trabajo obtiene credenciales. Para una VM, usa gcloud compute instances create ... --service-account=app-sa@... --scopes=cloud-platform; el código de la VM obtiene entonces tokens de acceso de corta duración del servidor de metadatos automáticamente, sin claves que administrar. Los servicios y funciones de Cloud Run reciben --service-account al desplegarse. Los access scopes son un mecanismo heredado de las VMs que limita a qué APIs pueden llegar las credenciales de la VM; la recomendación de Google es establecer el scope cloud-platform y controlar el acceso con roles de IAM.

Para adjuntar una cuenta de servicio necesitas el rol Service Account User (roles/iam.serviceAccountUser) sobre esa cuenta de servicio, porque ejecutar código como ella te permite usar sus permisos. Esto impide que alguien que solo tiene permiso para crear VMs tome prestada una cuenta de servicio poderosa. Service Account Admin te permite crear y administrar cuentas de servicio, que es un poder distinto.

Algunos servicios crean cuentas de servicio predeterminadas, como la cuenta de servicio predeterminada de Compute Engine, PROJECT_NUMBER-compute@developer.gserviceaccount.com. Según la configuración de tu organización, puede recibir automáticamente el rol Editor, y las VMs la usan a menos que elijas otra. La mejor práctica es crear en su lugar cuentas de servicio dedicadas y con mínimo privilegio, y muchas organizaciones usan una política de la organización para evitar la asignación automática de Editor. No las confundas con los agentes de servicio (service agents), que Google usa para ejecutar servicios en tu nombre.

Términos clave

Service account (cuenta de servicio)
Una identidad para aplicaciones y cargas de trabajo, identificada por una dirección de correo.
Service Account User
Un rol que permite adjuntar una cuenta de servicio o actuar como ella.
Metadata server (servidor de metadatos)
Un endpoint en cada VM que proporciona tokens de corta duración para la cuenta de servicio adjunta.
Compute Engine default service account
Una cuenta de servicio creada automáticamente que las VMs usan a menos que se especifique otra.
Ejemplo real

Un equipo despliega un servicio de facturas en Cloud Run con su propia cuenta de servicio, invoice-sa, que solo tiene Secret Manager Secret Accessor sobre un secreto y Cloud SQL Client en el proyecto. Cuando los logs muestran una lectura inesperada, saben exactamente qué servicio la hizo.

Consejo para el examen: Las cargas de trabajo deben usar cuentas de servicio dedicadas y adjuntas, no claves ni la cuenta predeterminada con Editor. Los errores de permiso al adjuntar una cuenta de servicio significan que el usuario no tiene Service Account User sobre ella.

Comprueba lo que sabes

¿Por qué adjuntar una cuenta de servicio a una VM requiere Service Account User?

Porque el código de la VM puede usar entonces los permisos de la cuenta de servicio, lo cual es una forma de actuar como ella.

¿Cómo obtiene el código de una VM las credenciales de su cuenta de servicio adjunta?

Del servidor de metadatos, que emite tokens de acceso de corta duración automáticamente.
