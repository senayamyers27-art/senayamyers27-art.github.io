Identity-Aware Proxy y OS Login para un acceso administrativo seguro

Identity-Aware Proxy (IAP) implementa un modelo de acceso de confianza cero (zero trust): en lugar de confiar en cualquiera que esté en la red correcta, verifica quién es el usuario (y, opcionalmente, su dispositivo y su contexto) en cada solicitud, y solo entonces deja pasar la solicitud hacia la aplicación o la VM. Elimina la necesidad de VPNs y bastion hosts en muchos patrones de acceso.

Para las aplicaciones web, IAP se coloca delante del servicio de backend de un Application Load Balancer externo, de App Engine o de Cloud Run. Los usuarios inician sesión con su identidad de Google, e IAP permite la solicitud solo si tienen el rol IAP-secured Web App User sobre la app. La app aún tiene que aceptar tráfico solo del balanceador de carga, normalmente con reglas de firewall, para que los usuarios no puedan evadir IAP. Con Access Context Manager puedes agregar condiciones basadas en el contexto, como exigir un dispositivo administrado por la empresa o cierto rango de IPs.

Para el acceso administrativo a las VMs, el reenvío TCP de IAP tuneliza conexiones SSH, RDP u otras conexiones TCP hacia VMs que no tienen dirección IP externa. Los usuarios necesitan el rol IAP-secured Tunnel User, y las reglas de firewall deben permitir el rango de IAP 35.235.240.0/20 hacia el puerto. Comandos como gcloud compute ssh vm-1 --tunnel-through-iap o gcloud compute start-iap-tunnel vm-1 3389 --local-host-port=localhost:3389 establecen el túnel.

OS Login complementa a IAP controlando quién puede iniciar sesión en las VMs Linux una vez conectado. Vincula las cuentas de usuario de Linux con identidades de Google y otorga el acceso mediante IAM: Compute OS Login para los usuarios normales, Compute OS Admin Login para los usuarios que necesitan sudo. OS Login puede exigir la verificación en dos pasos y, como usa IAM, el acceso se elimina en cuanto se revoca un rol o se deshabilita una cuenta. Eso es mucho más fácil de gobernar que las claves SSH dispersas en los metadatos del proyecto. Para los usuarios de fuera de la organización, también se necesita el rol Compute OS Login External User a nivel de organización.

Juntos dan un modelo limpio: sin IPs públicas en las VMs, IAP decide quién puede llegar a la VM, OS Login decide quién puede iniciar sesión y con qué privilegios, y los registros de auditoría lo registran todo.

Términos clave

Identity-Aware Proxy
Un servicio que autoriza cada solicitud según la identidad y el contexto del usuario antes de que llegue a una app o VM.
IAP-secured Web App User
El rol que permite a un usuario pasar a través de IAP hacia una app web protegida.
IAP-secured Tunnel User
El rol que permite el reenvío TCP a través de IAP hacia las VMs.
Compute OS Admin Login
El rol de OS Login que otorga inicio de sesión con privilegios de sudo.
Ejemplo real

Una empresa retira su VPN para una app interna de RR. HH. colocándola detrás de un Application Load Balancer externo con IAP habilitado, otorgando IAP-secured Web App User al grupo hr-staff y exigiendo dispositivos administrados por la empresa mediante un nivel de acceso. Los administradores llegan a las VMs de la app mediante túneles de IAP con OS Login.

Consejo para el examen: Acceso basado en identidad a una app web interna sin VPN: IAP. SSH sin IPs externas: reenvío TCP de IAP. Acceso SSH controlado por IAM: OS Login.

Comprueba lo que sabes

¿Qué rol permite a un usuario ejecutar sudo en una VM usando OS Login?

Compute OS Admin Login.

¿Qué impide que los usuarios evadan IAP para llegar directamente al backend?

Reglas de firewall que permiten tráfico solo desde los rangos del balanceador de carga y de IAP, y la ausencia de IPs públicas en los backends.
