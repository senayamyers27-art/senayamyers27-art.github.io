Cloud Logging: Logs Explorer, métricas basadas en logs, log buckets y sinks

Cloud Logging recopila entradas de log de los servicios de Google Cloud, los registros de auditoría, las VMs que ejecutan el Ops Agent, los contenedores de GKE, Cloud Run y tus aplicaciones (cualquier cosa escrita en la salida estándar en plataformas serverless, o mediante las bibliotecas cliente). Cada entrada tiene una marca de tiempo, una severidad, un recurso (como una VM o una revisión de Cloud Run), un nombre de log y un payload que es texto o JSON estructurado.

Logs Explorer es donde haces las búsquedas. Escribes consultas en el lenguaje de consultas de Logging, por ejemplo resource.type="gce_instance" severity>=ERROR o textPayload:"payment declined", y acotas por rango de tiempo. Desde la CLI, gcloud logging read 'severity>=ERROR' --limit=20 devuelve entradas. Log Analytics te permite consultar logs con SQL cuando un log bucket se actualiza para ello.

Las métricas basadas en logs (log-based metrics) convierten las entradas de log en métricas de Cloud Monitoring. Una métrica de contador cuenta las entradas que coinciden con un filtro, como cuántas veces aparece 'payment declined'; una métrica de distribución extrae valores numéricos, como latencias, de las entradas. Puedes graficarlas y crear políticas de alertas sobre ellas.

El enrutamiento y el almacenamiento se controlan con el Log Router. Cada proyecto tiene sinks que deciden a dónde va cada entrada de log. De forma predeterminada, el bucket _Required almacena los registros Admin Activity, System Event y algunos otros de auditoría durante 400 días y no se puede modificar, y el bucket _Default almacena la mayoría de los demás logs durante 30 días de forma predeterminada, lo cual puedes cambiar. Puedes crear tus propios log buckets con retención personalizada, incluso en otras regiones, y los filtros de exclusión descartan los logs ruidosos que no quieres pagar por almacenar.

Los sinks definidos por el usuario envían copias de los logs que coinciden a otros destinos: un bucket de Cloud Storage para un archivado económico a largo plazo, un dataset de BigQuery para análisis con SQL, un tema de Pub/Sub para transmitir a herramientas de terceros como un SIEM, un log bucket en otro proyecto, o un proyecto de Google Cloud. Cuando creas un sink, Logging le da una writer identity (una cuenta de servicio) a la que debes otorgar permiso sobre el destino, por ejemplo BigQuery Data Editor sobre el dataset. Los sinks agregados (aggregated sinks), creados en una organización o carpeta con --include-children, enrutan los logs de todos los proyectos que están debajo, que es la forma estándar de centralizar los logs de seguridad.

Términos clave

Logs Explorer
La herramienta de la consola para consultar y ver entradas de log.
Log-based metric (métrica basada en logs)
Una métrica de Cloud Monitoring derivada de las entradas de log que coinciden con un filtro.
Sink
Una regla del Log Router que envía las entradas de log coincidentes a un destino como BigQuery o Pub/Sub.
Aggregated sink (sink agregado)
Un sink en una organización o carpeta que enruta los logs de todos los proyectos hijos.
Ejemplo real

Una empresa crea un sink agregado en su organización que envía todos los registros de auditoría a un dataset de BigQuery en un proyecto de seguridad, y otro que los transmite a Pub/Sub para su SIEM. Los desarrolladores agregan una métrica de contador basada en logs para 'payment declined' y crean una alerta cuando se dispara.

Consejo para el examen: Contar o graficar algo que aparece en los logs: métrica basada en logs. Enviar los logs a otro lugar: sink (y otorgar acceso a su writer identity). Todos los proyectos de la organización: sink agregado con include-children.

Comprueba lo que sabes

¿Cuánto tiempo se conservan los logs en el bucket _Default de forma predeterminada?

30 días, lo cual puedes cambiar.

¿Qué debes hacer después de crear un sink hacia BigQuery?

Otorgar a la writer identity del sink permiso para escribir en el dataset.
