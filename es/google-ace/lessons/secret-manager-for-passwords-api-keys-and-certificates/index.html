Secret Manager para contraseñas, claves de API y certificados

Las aplicaciones necesitan secretos: contraseñas de bases de datos, claves de API de terceros, claves privadas de TLS y tokens. Ponerlos en el código fuente, en imágenes de contenedor, en variables de entorno en texto plano dentro de archivos de despliegue o en buckets de configuración es riesgoso, porque cualquiera que pueda leer esos lugares puede leer el secreto, y es difícil rotarlos. Secret Manager es el servicio administrado de Google Cloud para almacenar secretos de forma segura.

Un secreto en Secret Manager es un contenedor con nombre, y los valores reales se guardan como versiones. Cuando rotas una contraseña, agregas una versión nueva y, una vez que todo la usa, deshabilitas o destruyes la anterior. Las aplicaciones pueden solicitar un número de versión específico o latest. Crea un secreto con gcloud secrets create db-password --replication-policy=automatic y agrega un valor con gcloud secrets versions add db-password --data-file=pw.txt. La replicación puede ser automática (Google elige las ubicaciones) o administrada por el usuario (tú eliges las regiones, por residencia de datos), y los secretos se cifran de forma predeterminada, con CMEK opcional.

El acceso se controla con IAM. El rol clave es Secret Manager Secret Accessor (roles/secretmanager.secretAccessor), que permite leer los valores de los secretos; otórgalo a la cuenta de servicio específica de la carga de trabajo, sobre el secreto específico, no sobre todo el proyecto. Secret Manager Admin administra los secretos, pero solo debes otorgarlo a los administradores. Cada acceso se registra en Cloud Audit Logs (registros Data Access, cuando están habilitados), así que puedes ver qué identidad leyó un secreto.

Las integraciones hacen que los secretos sean fáciles de usar. Cloud Run y Cloud Run functions pueden montar un secreto como archivo o exponerlo como variable de entorno al desplegar, por ejemplo gcloud run deploy api --set-secrets=DB_PASSWORD=db-password:latest. GKE puede leer secretos mediante el complemento de Secret Manager o el Secrets Store CSI driver, y cualquier aplicación puede llamar a la API de Secret Manager con las bibliotecas cliente. Los calendarios de rotación pueden enviar notificaciones de Pub/Sub para activar tu propio código de rotación, y los secretos pueden tener fechas de vencimiento.

Secret Manager es para los secretos de las aplicaciones. Es distinto de Cloud KMS, que administra claves de cifrado que se usan para cifrar datos, pero nunca te entrega el material de clave en bruto de una clave de software o de HSM.

Términos clave

Secret (secreto)
Un contenedor con nombre en Secret Manager que guarda versiones de un valor sensible.
Secret version (versión del secreto)
Un valor inmutable de un secreto; para rotar se agregan versiones nuevas.
Secret Manager Secret Accessor
El rol de IAM que permite leer el valor de un secreto.
Replication policy (política de replicación)
Si los datos de un secreto se replican automáticamente o solo en las regiones que elijas.
Ejemplo real

Un equipo de pagos guarda la clave de API de su procesador en Secret Manager, otorga Secret Accessor sobre ese único secreto a la cuenta de servicio del servicio de checkout y despliega en Cloud Run con --set-secrets. Cuando el procesador rota la clave, el equipo agrega una versión nueva, y el siguiente despliegue toma latest.

Consejo para el examen: Las contraseñas y las claves de API van en Secret Manager, con Secret Accessor otorgado a la cuenta de servicio de la carga de trabajo. Cloud KMS es para claves de cifrado, no para almacenar contraseñas de apps.

Comprueba lo que sabes

¿Cómo rotas un secreto en Secret Manager?

Agrega una versión nueva, haz que las aplicaciones la usen y luego deshabilita o destruye la versión anterior.

¿Qué rol debe tener la cuenta de servicio de un servicio de Cloud Run para leer un secreto?

Secret Manager Secret Accessor sobre ese secreto específico.
