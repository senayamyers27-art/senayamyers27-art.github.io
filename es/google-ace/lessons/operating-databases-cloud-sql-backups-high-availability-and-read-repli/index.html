Operar bases de datos: copias de seguridad, alta disponibilidad y réplicas de lectura de Cloud SQL, y dry runs de BigQuery

Cloud SQL se encarga de gran parte de las operaciones de la base de datos por ti, pero tú eliges las funciones de protección. Las copias de seguridad automáticas se ejecutan a diario en una ventana de respaldo que eliges y se conservan durante una cantidad configurable de días; también puedes tomar copias de seguridad bajo demanda antes de cambios riesgosos. La recuperación a un momento dado (point-in-time recovery) usa los logs de transacciones (binary logs para MySQL, write-ahead logs para PostgreSQL) para que puedas restaurar a un momento específico, por ejemplo justo antes de un DELETE equivocado. Las restauraciones se hacen en una instancia nueva o existente; no son una conmutación por error instantánea.

La alta disponibilidad (HA), también llamada configuración regional, ejecuta una instancia principal en una zona y una de reserva (standby) en otra zona de la misma región, con replicación síncrona del almacenamiento. Si la principal o su zona fallan, Cloud SQL conmuta automáticamente a la instancia de reserva, y los clientes siguen usando la misma dirección IP después de una breve interrupción. La instancia de reserva no atiende lecturas. La HA protege contra fallas de zona, no contra un error como borrar una tabla, lo cual cubren las copias de seguridad y la recuperación a un momento dado.

Las réplicas de lectura (read replicas) son copias de la principal que reciben replicación asíncrona y atienden consultas de solo lectura. Úsalas para descargar los informes o el tráfico con muchas lecturas. Las réplicas entre regiones también sirven para la recuperación ante desastres: puedes promover una réplica a principal independiente si se pierde una región, aunque la promoción es una acción manual y en un solo sentido. Las réplicas requieren que la principal tenga habilitadas las copias de seguridad y el registro binario (para MySQL).

Otras operaciones incluyen conectarse de forma segura con Cloud SQL Auth Proxy o con los conectores (que usan IAM y cifran el tráfico sin administrar certificados SSL ni poner IPs en listas de permitidas), usar IP privada en tu VPC, escalar el tipo de máquina (lo que requiere un reinicio) y programar ventanas de mantenimiento.

En BigQuery, la principal preocupación operativa es el costo. Con los precios bajo demanda pagas por bytes procesados, así que antes de ejecutar una consulta grande haz un dry run: bq query --use_legacy_sql=false --dry_run 'SELECT ...', o mira el validador de consultas en la consola, que informa cuántos bytes procesará la consulta. Selecciona solo las columnas necesarias, filtra por columnas particionadas y usa clustering; agregar LIMIT no reduce los bytes escaneados en una tabla normal. También puedes establecer un límite máximo de bytes facturados en una consulta o limitar el uso con cuotas personalizadas.

Términos clave

Point-in-time recovery (recuperación a un momento dado)
Restaurar una base de datos a un momento específico usando copias de seguridad más los logs de transacciones.
Cloud SQL high availability (alta disponibilidad de Cloud SQL)
Una instancia principal y una de reserva en distintas zonas de una región con conmutación por error automática.
Read replica (réplica de lectura)
Una copia actualizada de forma asíncrona que atiende tráfico de solo lectura y se puede promover manualmente.
Dry run
Una validación de consulta de BigQuery que informa los bytes que se procesarán sin ejecutarla ni cobrar.
Ejemplo real

Un equipo de comercio electrónico ejecuta Cloud SQL for PostgreSQL con HA para las fallas de zona, recuperación a un momento dado para los errores y una réplica de lectura para su herramienta de informes. Los analistas estiman cada nuevo informe de BigQuery con un dry run y agregan un filtro de partición cuando una consulta habría escaneado 3 TB.

Consejo para el examen: Conmutación automática ante fallas de zona: HA. Descargar lecturas: réplica de lectura. Deshacer un cambio equivocado: recuperación a un momento dado. Estimar el costo de BigQuery: dry run. LIMIT no reduce los bytes escaneados.

Comprueba lo que sabes

¿Puede la instancia de reserva de HA de Cloud SQL atender consultas de lectura?

No. Solo toma el control durante una conmutación por error; usa réplicas de lectura para las lecturas.

¿Qué te dice un dry run de BigQuery?

Si la consulta es válida y cuántos bytes procesaría, sin ejecutarla.
