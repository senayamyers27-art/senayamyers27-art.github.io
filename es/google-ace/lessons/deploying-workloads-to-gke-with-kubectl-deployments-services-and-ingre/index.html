Desplegar cargas de trabajo en GKE con kubectl: Deployments, Services e Ingress

Antes de usar kubectl en un clúster de GKE, obtén las credenciales: gcloud container clusters get-credentials my-cluster --region=us-central1. Esto escribe una entrada en tu kubeconfig para que kubectl se comunique con el servidor de API de ese clúster usando tu identidad de Google. El acceso dentro del clúster se controla con roles de IAM como Kubernetes Engine Developer y, opcionalmente, con RBAC de Kubernetes.

Un Deployment es la forma estándar de ejecutar una app sin estado. Declara la imagen del contenedor, la cantidad de réplicas y las solicitudes de recursos, y Kubernetes mantiene esa cantidad de pods en ejecución mediante un ReplicaSet. Puedes crear uno rápidamente con kubectl create deployment web --image=us-docker.pkg.dev/my-proj/repo/web:1.0, pero en la práctica escribes YAML y ejecutas kubectl apply -f web.yaml. Las imágenes normalmente vienen de Artifact Registry, y los nodos (o los pods, con Workload Identity Federation) necesitan permiso para descargarlas.

Los pods obtienen nuevas direcciones IP cada vez que se vuelven a crear, así que los expones con un Service, que da una IP virtual y un nombre DNS estables y balancea la carga entre los pods que coinciden. El tipo ClusterIP (el predeterminado) solo es accesible dentro del clúster. El tipo NodePort abre un puerto en cada nodo. El tipo LoadBalancer hace que GKE cree un Network Load Balancer de paso (passthrough) de Google Cloud con una IP externa (o una interna, con una anotación). La forma rápida es kubectl expose deployment web --type=LoadBalancer --port=80 --target-port=8080, donde port es el que usan los clientes y target-port es en el que escucha el contenedor.

Para apps HTTP(S), un Ingress (o la más reciente Gateway API) enruta el tráfico por host y ruta hacia distintos Services. En GKE, un Ingress crea un Application Load Balancer externo, compatible con certificados administrados por Google y Cloud CDN. Esta es la respuesta cuando necesitas una sola IP para varios servicios con enrutamiento basado en URL.

Otros objetos de cargas de trabajo también aparecen en el examen: StatefulSets para apps que necesitan identidades estables y volúmenes persistentes, DaemonSets para ejecutar un pod en cada nodo (como un agente de logs), Jobs y CronJobs para tareas por lotes, y ConfigMaps y Secrets para la configuración. kubectl get pods, kubectl describe pod NAME y kubectl logs NAME son tus primeros comandos para solucionar problemas.

Términos clave

Deployment
Un objeto de Kubernetes que mantiene en ejecución una cantidad fija de réplicas idénticas de pods y gestiona las actualizaciones progresivas.
Service
Una IP y un nombre DNS estables que balancean el tráfico hacia un conjunto de pods.
LoadBalancer Service
Un tipo de Service que aprovisiona un balanceador de carga de red de Google Cloud con una IP externa o interna.
Ingress
Un objeto de Kubernetes que enruta el tráfico HTTP(S) por host y ruta; en GKE crea un Application Load Balancer.
Ejemplo real

Un equipo despliega los Deployments frontend y api, cada uno con un Service ClusterIP. Un Ingress enruta shop.example.com/ hacia frontend y shop.example.com/api hacia api a través de un solo Application Load Balancer externo con un certificado administrado por Google.

Consejo para el examen: Solo interno: ClusterIP. Una IP externa para un servicio: LoadBalancer. Enrutamiento por URL hacia varios servicios: Ingress. No olvides get-credentials antes de que kubectl funcione.

Comprueba lo que sabes

¿Qué hace gcloud container clusters get-credentials?

Agrega el endpoint y la configuración de autenticación del clúster a tu kubeconfig para que kubectl pueda usarlo.

En kubectl expose, ¿cuál es la diferencia entre --port y --target-port?

--port es el puerto en el que escucha el Service; --target-port es el puerto del contenedor al que se envía el tráfico.
