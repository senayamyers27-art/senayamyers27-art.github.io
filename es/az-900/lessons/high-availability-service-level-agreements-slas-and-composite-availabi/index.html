Alta disponibilidad, acuerdos de nivel de servicio (SLA) y disponibilidad compuesta

La disponibilidad es la proporción del tiempo en que un servicio está activo y se puede usar. Alta disponibilidad significa diseñar un sistema para que siga disponible incluso cuando falla alguna de sus partes, normalmente eliminando los puntos únicos de falla: ejecutar más de una instancia para que otra pueda tomar el control, almacenar más de una copia de los datos y distribuir esas copias en hardware o ubicaciones separadas. En Azure construyes alta disponibilidad con funciones como varias máquinas virtuales detrás de un balanceador de carga, zonas de disponibilidad y almacenamiento redundante. La alta disponibilidad está relacionada con la recuperación ante desastres, pero no es lo mismo: la alta disponibilidad mantiene un servicio funcionando ante fallas cotidianas, mientras que la recuperación ante desastres lo restaura después de un evento grande, como la pérdida de una región.

Microsoft describe su compromiso para cada servicio de Azure en un acuerdo de nivel de servicio (SLA). Un SLA es un acuerdo formal que indica el tiempo de actividad o la conectividad que Microsoft se compromete a ofrecer para un servicio, normalmente como un porcentaje sobre un mes de facturación, como 99.9% o 99.99%. También indica qué ocurre si Microsoft no cumple ese objetivo, normalmente un crédito de servicio, que es un descuento porcentual en la factura de ese servicio que debes reclamar. Los SLA se aplican a servicios pagados y con disponibilidad general; los servicios gratuitos y las funciones en versión preliminar (preview) normalmente no tienen un SLA respaldado financieramente. Un SLA es una promesa de compensación, no una garantía de que no puedan ocurrir interrupciones.

Las diferencias pequeñas en el porcentaje importan mucho. En un mes de 30 días hay 43,200 minutos. Para calcular el tiempo de inactividad permitido, multiplica los minutos del mes por la fracción no disponible. 99% permite 432 minutos, unas 7.2 horas. 99.9% permite 43.2 minutos. 99.95% permite 21.6 minutos. 99.99% permite unos 4.3 minutos. 99.999% permite bastante menos de un minuto. Cada nueve adicional divide entre diez el tiempo de inactividad permitido.

El SLA que obtiene un servicio puede depender de cómo lo implementes. Una sola máquina virtual tiene un SLA más bajo que dos o más VM en un availability set, que a su vez es más bajo que el de VM distribuidas entre zonas de disponibilidad, porque cada diseño redundante sobrevive a una falla mayor: un solo host, un rack o un datacenter completo. Algunos servicios también ofrecen SLA más altos en niveles premium. Consulta el documento de SLA vigente para ver las cifras exactas en lugar de memorizarlas, porque cambian.

Una aplicación normalmente depende de varios servicios, como una aplicación web, una base de datos y una cuenta de almacenamiento. Si la aplicación necesita que todos funcionen, su disponibilidad total, llamada SLA compuesto, se obtiene multiplicando los SLA individuales expresados como decimales. Dos servicios de 99.95% y 99.99% dan 0.9995 x 0.9999 = 0.9994, aproximadamente 99.94%, que es más bajo que cualquiera de los dos por separado. Agregar dependencias en cadena siempre reduce la disponibilidad. Agregar redundancia la aumenta: si dos copias independientes tienen cada una 99.9%, la probabilidad de que ambas estén caídas al mismo tiempo es 0.001 x 0.001, así que el par ofrece aproximadamente 99.9999%.

Considera un ejemplo práctico. Un equipo ejecuta un front end web en App Service con un SLA de 99.95%, respaldado por una base de datos con un SLA de 99.99%. Su SLA compuesto es de aproximadamente 99.94%, lo que permite unos 26 minutos de inactividad en un mes de 30 días. El negocio pide no más de unos 5 minutos. El equipo no puede lograrlo ajustando un solo servicio, así que implementa toda la aplicación en una segunda región con un enrutamiento de tráfico que conmuta por error automáticamente. Como cualquiera de las dos regiones puede atender a los usuarios, la disponibilidad combinada sube muy por encima de la cifra de una sola región.

Errores comunes: sumar los SLA en lugar de multiplicarlos; esperar que el compuesto sea al menos tan bueno como el eslabón más débil (siempre es más bajo cuando todas las partes son necesarias); pensar que un porcentaje más alto significa más tiempo de inactividad; suponer que las funciones en preview tienen el mismo SLA que las publicadas; y creer que Microsoft hace automáticamente que tu aplicación sea de alta disponibilidad. La plataforma proporciona los componentes y publica el SLA, pero tú eliges si implementas una instancia o varias.

Las preguntas del examen suelen pedirte comparar números o elegir un diseño. 'Qué SLA permite el menor tiempo de inactividad' es el que tiene más nueves. 'Qué recibes si Microsoft no cumple un SLA' es un crédito de servicio. '¿Una función en preview tiene SLA?' en general es no. 'Cómo calculas el SLA de una aplicación que usa dos servicios' es multiplicando, lo que da un valor más bajo. 'Cómo aumentas el SLA de una carga de trabajo en VM' es agregar instancias en un availability set o en zonas de disponibilidad.

Términos clave

Disponibilidad (availability)
El porcentaje del tiempo en que un servicio está en ejecución y se puede usar.
Alta disponibilidad (high availability)
Un diseño que mantiene un servicio funcionando cuando fallan componentes individuales, normalmente mediante redundancia.
Acuerdo de nivel de servicio (SLA)
El compromiso formal de Microsoft con el tiempo de actividad o la conectividad de un servicio, con créditos si no se cumple el objetivo.
Crédito de servicio (service credit)
Un descuento en la factura del servicio afectado que puedes reclamar cuando no se cumple un SLA.
SLA compuesto (composite SLA)
La disponibilidad total de una aplicación que depende de varios servicios, que se obtiene multiplicando sus SLA.
Punto único de falla (single point of failure)
Cualquier componente cuya falla detiene todo el sistema porque no existe una copia redundante.
Redundancia (redundancy)
Ejecutar copias adicionales de un componente para que una pueda tomar el control si otra falla.
Ejemplo real

La aplicación de reclamaciones de una aseguradora usa App Service con 99.95% y una base de datos con 99.99%, lo que da un compuesto de aproximadamente 99.94%. Después de que un incidente regional provoca una interrupción larga, el arquitecto implementa una segunda copia en otra región con conmutación por error automática. El director financiero pregunta si pueden reclamar algo por la interrupción; la respuesta es que pueden solicitar un crédito de servicio si no se cumplió el SLA, pero el crédito es pequeño comparado con el negocio perdido, por eso invirtieron en redundancia.

Consejo para el examen: Los SLA compuestos se obtienen multiplicando y siempre son más bajos que el SLA individual más bajo de la cadena. Más nueves significa menos tiempo de inactividad permitido. No cumplir un SLA otorga un crédito de servicio, no una garantía.

Comprueba lo que sabes

¿Aproximadamente cuánto tiempo de inactividad permite un SLA de 99.9% en un mes de 30 días?

Unos 43 minutos, porque 43,200 minutos x 0.001 = 43.2 minutos.

Una aplicación necesita una aplicación web (99.95%) y una base de datos (99.99%). ¿El compuesto es mayor o menor que 99.95%?

Menor, aproximadamente 99.94%, porque los SLA se multiplican y ambos servicios deben estar activos.

¿Qué proporciona normalmente Microsoft si no cumple un SLA?

Un crédito de servicio, un descuento porcentual en la factura del servicio afectado.

¿Cómo puedes aumentar el SLA de una carga de trabajo que se ejecuta en una sola VM?

Ejecutar dos o más VM en un availability set o, mejor aún, en zonas de disponibilidad, para que una sola falla no detenga el servicio.
