Plataforma como servicio (PaaS) y serverless: qué administra el proveedor y casos de uso típicos

La plataforma como servicio (PaaS) es un punto intermedio entre la infraestructura como servicio (IaaS) y el software como servicio (SaaS). El proveedor administra la infraestructura física y también el sistema operativo, el middleware, el runtime y las herramientas de desarrollo. Tú aportas el código de tu aplicación y tus datos, y configuras cómo se ejecuta el servicio. No inicias sesión en servidores ni les instalas actualizaciones. El objetivo de PaaS es permitir que los desarrolladores dediquen su tiempo a la aplicación y no a las máquinas que están debajo.

Algunos ejemplos de PaaS en Azure son Azure App Service para alojar aplicaciones web e interfaces de programación de aplicaciones (API), Azure SQL Database para bases de datos relacionales administradas y Azure Cosmos DB para datos NoSQL distribuidos globalmente. Con Azure SQL Database, por ejemplo, Microsoft se encarga de las actualizaciones del motor de base de datos, los parches del sistema operativo, la alta disponibilidad y las copias de seguridad automatizadas; tú diseñas las tablas, escribes las consultas, eliges un nivel de rendimiento y controlas quién puede conectarse. Implementar una aplicación web en App Service se ve así:

az appservice plan create --resource-group rg-web --name plan-web --sku S1 --is-linux
az webapp create --resource-group rg-web --plan plan-web --name contoso-orders-web --runtime "NODE:20-lts"
az webapp deploy --resource-group rg-web --name contoso-orders-web --src-path app.zip

Según el modelo de responsabilidad compartida, PaaS sube la línea en la pila. Microsoft es responsable del sistema operativo y el runtime, lo que elimina el trabajo de aplicar parches y reduce la superficie de ataque que tienes que mantener. La responsabilidad por las aplicaciones, los controles de red y la infraestructura de identidad suele ser compartida, porque Microsoft proporciona los controles y tú los configuras, por ejemplo las reglas de firewall de un servidor SQL o las restricciones de acceso de una aplicación web. Como siempre, sigues siendo responsable de tus datos, dispositivos y cuentas. Los casos de uso típicos de PaaS son crear e implementar aplicaciones rápidamente, en especial cuando los desarrolladores quieren concentrarse en el código. Los servicios PaaS suelen incluir escalado integrado, balanceo de carga, opciones de alta disponibilidad e implementación directa desde el control de código fuente. La contrapartida es menos control: no puedes elegir cada configuración del sistema operativo ni instalar software arbitrario en las máquinas subyacentes.

La computación serverless (sin servidor) a menudo se agrupa con PaaS. Con serverless no administras servidores en absoluto, la plataforma escala automáticamente, incluso hasta cero cuando no ocurre nada, y en los planes de tipo consumo pagas solo cuando tu código se ejecuta. Azure Functions ejecuta pequeños fragmentos de código en respuesta a eventos, como una solicitud HTTP, un mensaje en una cola, un nuevo archivo en el almacenamiento o un temporizador. Azure Logic Apps crea flujos de trabajo que conectan servicios con poco o ningún código, usando un diseñador visual y conectores listos para usar. Los servidores siguen existiendo, pero el proveedor los administra por completo, y la aplicación se diseña en torno a eventos en lugar de procesos siempre en ejecución. La distinción que hace el examen es que un PaaS como App Service ejecuta tu aplicación de forma continua en la capacidad que elegiste, mientras que serverless ejecuta código solo cuando se dispara y factura por ejecución.

Considera un ejemplo práctico. Un equipo pequeño está construyendo un sistema de reservas en línea. El sitio para clientes funciona todo el día y necesita dominios personalizados, ranuras de implementación (deployment slots) para pruebas y un rendimiento estable, así que lo alojan en App Service. Las reservas se almacenan en Azure SQL Database, lo que les evita administrar un servidor de base de datos. Cada vez que se guarda una reserva, se envía un mensaje a una cola, y una Azure Function lo toma y envía el correo de confirmación. La función se ejecuta solo cuando llega una reserva, así que por la noche casi no cuesta nada. Una Logic App publica un resumen diario en el canal de chat del equipo sin nada de código.

Errores comunes: creer que PaaS significa que el cliente no tiene responsabilidades de seguridad (sigues configurando el acceso, protegiendo los datos y administrando las identidades); pensar que 'serverless' significa que literalmente no hay servidores; elegir Functions para una aplicación web de larga ejecución que debe estar siempre encendida; y olvidar que PaaS limita el control, así que una aplicación que necesita un componente de sistema operativo personalizado podría tener que quedarse en IaaS. Otra trampa es tratar Logic Apps y Functions como lo mismo: Logic Apps es una herramienta de flujos de trabajo centrada en el diseñador, y Functions está centrada en el código.

Las preguntas del examen usan palabras clave claras. 'Los desarrolladores quieren concentrarse en el código', 'no hace falta administrar el sistema operativo', 'base de datos administrada' o 'alojar una aplicación web sin administrar servidores' apunta a PaaS, a menudo App Service o Azure SQL Database. 'Ejecutar código en respuesta a un evento', 'pagar solo cuando el código se ejecuta' o 'escalar automáticamente a cero' apunta a serverless, normalmente Azure Functions. 'Automatizar un flujo de trabajo entre servicios con poco o ningún código' apunta a Logic Apps. Si el escenario necesita control total del sistema operativo, no es PaaS.

Términos clave

Plataforma como servicio (PaaS)
Un tipo de servicio en el que el proveedor administra la infraestructura, el sistema operativo y el runtime, y tú administras tu aplicación y tus datos.
Azure App Service
Un servicio PaaS para alojar aplicaciones web, API REST y back ends móviles sin administrar servidores.
Azure SQL Database
Un servicio de base de datos relacional totalmente administrado en el que Microsoft se encarga de los parches, las copias de seguridad y la alta disponibilidad.
Computación serverless (serverless computing)
Un modelo en el que el proveedor administra por completo los servidores, escala automáticamente y factura solo por la ejecución.
Azure Functions
Cómputo serverless basado en eventos que ejecuta código en respuesta a desencadenadores como solicitudes HTTP, mensajes de cola o temporizadores.
Azure Logic Apps
Un servicio de poco código para crear flujos de trabajo automatizados que conectan aplicaciones y servicios.
Desencadenador (trigger)
El evento que hace que se ejecute una función o un flujo de trabajo serverless.
Ejemplo real

Los desarrolladores de una startup de noticias quieren publicar funciones a diario sin preocuparse por los servidores. Alojan el sitio en App Service con implementación desde su control de código fuente, almacenan los artículos en Azure Cosmos DB y usan una Azure Function que se dispara con cada nueva imagen subida para crear miniaturas. Microsoft aplica los parches a los sistemas operativos y runtimes subyacentes, mientras el equipo administra el código, la configuración de acceso y los datos.

Consejo para el examen: Si los desarrolladores quieren concentrarse en el código y no administrar el sistema operativo, elige PaaS. Si el código debe ejecutarse solo cuando ocurre un evento y facturarse por ejecución, piensa en serverless, normalmente Azure Functions; los flujos de trabajo de poco código apuntan a Logic Apps.

Comprueba lo que sabes

En PaaS, ¿quién aplica los parches al sistema operativo que ejecuta tu aplicación web?

Microsoft, porque en PaaS el proveedor administra el sistema operativo y el runtime.

¿Qué servicio de Azure ejecuta pequeños fragmentos de código en respuesta a eventos y factura por ejecución?

Azure Functions, un servicio de cómputo serverless.

Menciona algo de lo que el cliente sigue siendo responsable en PaaS.

El código de su aplicación, sus datos y la administración de las cuentas y el acceso; configurar los controles de red y de identidad es compartido.

¿Por qué un equipo podría elegir App Service en lugar de Azure Functions para un sitio web público?

El sitio web se ejecuta de forma continua y necesita funciones de alojamiento web como dominios personalizados y ranuras de implementación, lo que se adapta mejor a App Service que a funciones disparadas por eventos.
