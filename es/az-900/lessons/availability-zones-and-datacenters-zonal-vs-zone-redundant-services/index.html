Zonas de disponibilidad y datacenters: servicios zonales frente a redundantes entre zonas

La base física de Azure es el datacenter: un edificio lleno de servidores, almacenamiento y equipos de red con su propia energía, refrigeración y seguridad física. Nunca eliges un datacenter individual al implementar un recurso. En cambio, Azure agrupa los datacenters en zonas de disponibilidad, y las zonas en regiones. Entender esa jerarquía, datacenter dentro de zona dentro de región, es la clave para responder las preguntas de resiliencia del examen Microsoft Azure Fundamentals (AZ-900). Una zona de disponibilidad es una ubicación físicamente separada dentro de una región de Azure, formada por uno o más datacenters con energía, refrigeración y red independientes. Las zonas están lo bastante separadas como para que una falla local, como un incendio, una inundación o un corte de energía en un edificio, no afecte a las demás, pero lo bastante cerca como para estar conectadas por una red privada de alta velocidad y baja latencia, de modo que los datos puedan replicarse rápidamente entre ellas. Las regiones que admiten zonas de disponibilidad tienen un mínimo de tres zonas. No todas las regiones admiten zonas, y no todos los servicios las admiten, así que verifícalo antes de diseñar en torno a ellas.

Las zonas de disponibilidad son la forma principal de proteger una aplicación contra la falla de un datacenter dentro de una región. Si ejecutas copias de tu aplicación en cada una de tres zonas detrás de un balanceador de carga redundante entre zonas, la pérdida de una zona deja a las otras dos atendiendo a los usuarios. Usar zonas puede aumentar el costo, por ejemplo porque ejecutas más instancias y podrías pagar la transferencia de datos entre zonas, pero mejora la resiliencia y normalmente obtiene un acuerdo de nivel de servicio (SLA) más alto que un diseño de una sola zona.

Los servicios de Azure que admiten zonas de disponibilidad se dividen en dos categorías. Los servicios zonales están fijados a una zona específica que tú eliges, por ejemplo una máquina virtual, un disco administrado o una dirección IP pública implementados en la zona 1. La plataforma no los mueve si esa zona falla, así que para que un diseño zonal sea resiliente implementas tú mismo varios recursos en zonas diferentes. Los servicios redundantes entre zonas son replicados o distribuidos entre zonas automáticamente por la plataforma, como el almacenamiento con redundancia de zona (ZRS), una base de datos SQL redundante entre zonas o un balanceador de carga redundante entre zonas; si una zona falla, el servicio sigue funcionando sin que hagas nada. Esta es la diferencia en comandos:

# Zonal: you pick the zone, one VM per command
az vm create --resource-group rg-app --name web1 --image Ubuntu2204 --zone 1
az vm create --resource-group rg-app --name web2 --image Ubuntu2204 --zone 2
# Zone-redundant: the platform spreads the copies
az storage account create --resource-group rg-app --name contosozrs01 --sku Standard_ZRS

También existen servicios no regionales o siempre disponibles, que son resilientes tanto a interrupciones de zona como de región porque se ejecutan globalmente, como Microsoft Entra ID, Azure DNS y Azure Front Door. Para el examen, recuerda las capas de protección: los availability sets protegen contra fallas de hardware a nivel de rack dentro de un datacenter, las zonas de disponibilidad protegen contra la pérdida de un datacenter dentro de una región, y los pares de regiones o los diseños multirregión protegen contra la pérdida de una región completa.

Considera un ejemplo práctico. Una pasarela de pagos se ejecuta en una región con zonas habilitadas. El equipo implementa las VM web como un scale set distribuido entre las zonas 1, 2 y 3, usa un balanceador de carga redundante entre zonas, almacena los archivos en almacenamiento ZRS y usa una Azure SQL Database redundante entre zonas. Durante una falla de refrigeración, la zona 2 queda fuera de línea. El balanceador de carga deja de enviar tráfico a las VM de la zona 2, el almacenamiento y la base de datos siguen sirviendo desde las zonas restantes, y los clientes no notan nada. Como cada capa era consciente de las zonas, ningún datacenter fue un punto único de falla.

Errores comunes: pensar que una sola VM colocada en la zona 2 está protegida contra la falla de una zona (es zonal, así que cae junto con su zona); suponer que todas las regiones tienen zonas; creer que las zonas protegen contra un desastre de toda la región; y confundir el almacenamiento con redundancia local (LRS), que mantiene copias en un solo datacenter, con ZRS, que las distribuye entre zonas. También es fácil olvidar que la redundancia entre zonas debe existir en todas las capas: un nivel web redundante entre zonas sigue fallando si la única base de datos detrás de él es zonal.

Las preguntas del examen dan pistas claras, y ayuda leer los verbos con cuidado: 'tú eliges la zona' o 'fijado a una zona' significa zonal; 'replicado automáticamente entre zonas' significa redundante entre zonas; 'proteger contra la falla de un datacenter' significa zonas de disponibilidad; 'proteger contra una interrupción regional' significa una segunda región. Si una pregunta enumera opciones de almacenamiento, LRS se queda en un datacenter, ZRS abarca las zonas y GRS llega a la región emparejada.

Términos clave

Datacenter
Una instalación física de servidores, almacenamiento y redes con su propia energía, refrigeración y seguridad.
Zona de disponibilidad (availability zone)
Una ubicación físicamente separada dentro de una región, con energía, refrigeración y red independientes.
Servicio zonal (zonal service)
Un recurso fijado a una sola zona que tú eliges, como una VM en la zona 1.
Servicio redundante entre zonas (zone-redundant service)
Un servicio que la plataforma replica entre zonas automáticamente, como el almacenamiento ZRS.
Almacenamiento con redundancia de zona (ZRS)
Una opción de redundancia de almacenamiento que mantiene copias de los datos en tres zonas de la región.
Servicio no regional (non-regional service)
Un servicio global, como Microsoft Entra ID, que no está ligado a una sola región.
Ejemplo real

Una empresa de venta de boletos descubre que su VM de base de datos en la zona 1 quedó fuera de línea durante una interrupción de zona y tiró el sitio, aunque sus servidores web en las zonas 1, 2 y 3 estaban bien. La revisión explica que la VM de base de datos era zonal y no tenía copia en otro lugar. El equipo pasa a una Azure SQL Database redundante entre zonas y a almacenamiento ZRS para que la plataforma mantenga los datos disponibles en las tres zonas.

Consejo para el examen: Una VM colocada en la 'zona 2' es zonal; el almacenamiento ZRS es redundante entre zonas. Las regiones con zonas habilitadas tienen al menos tres zonas. Las zonas protegen contra fallas de datacenter, no contra fallas de toda la región.

Comprueba lo que sabes

¿Cuál es el número mínimo de zonas de disponibilidad en una región con zonas habilitadas?

Tres, para que la pérdida de una zona todavía deje al menos dos.

¿Una VM implementada en una zona específica es zonal o redundante entre zonas?

Zonal, porque está fijada a la zona que elegiste y no se moverá si esa zona falla.

¿Contra qué protege una zona de disponibilidad que un diseño de un solo datacenter no cubre?

Contra la falla de un datacenter completo, como un corte de energía o de refrigeración en un edificio.

Una empresa necesita protección contra un desastre regional. ¿Son suficientes las zonas de disponibilidad?

No, todas las zonas están dentro de una región; protegerse contra un desastre regional requiere una segunda región, por ejemplo la región emparejada.
