Cisco CCNA 200-301 v2.0

Solución de problemas de conectividad de clientes cableados e inalámbricos (verificar la configuración IP en Windows, macOS y Linux)

Muchos tickets de red empiezan con un solo usuario que no puede conectarse. Antes de revisar switches o routers, verifica lo que cree el propio cliente: su dirección IP, máscara, gateway predeterminado y servidores DNS (Domain Name System), y si realmente está conectado en las Capas 1 y 2. El CCNA espera que conozcas los comandos de verificación de los tres sistemas operativos de escritorio más comunes y que interpretes su salida rápidamente, porque una sola línea, como una dirección 169.254 o un gateway ausente, a menudo te dice dónde está la falla real.

En Windows, ipconfig muestra las direcciones IPv4 e IPv6, la máscara y el gateway predeterminado de cada adaptador. ipconfig /all agrega la dirección MAC (control de acceso al medio), etiquetada como Physical Address, si DHCP (Dynamic Host Configuration Protocol) está habilitado, el servidor DHCP, los tiempos de concesión y los servidores DNS. ipconfig /release e ipconfig /renew liberan y solicitan una concesión DHCP, e ipconfig /flushdns borra la caché DNS local. netsh wlan show interfaces informa el SSID (identificador de conjunto de servicios) conectado, el BSSID, el canal y la calidad de la señal Wi-Fi, y route print muestra la tabla de enrutamiento.

En macOS, ifconfig muestra las interfaces y las direcciones; en las laptops, en0 suele ser el Wi-Fi. ipconfig getifaddr en0 imprime solo la dirección, y networksetup -getinfo Wi-Fi muestra dirección, máscara y router. netstat -rn muestra la tabla de enrutamiento, donde la ruta predeterminada revela el gateway, y scutil --dns lista los resolvedores. En Linux la herramienta moderna es ip: ip addr (o ip a) lista las direcciones, ip route muestra el gateway predeterminado en la línea que empieza con default via, e ip link muestra el estado del enlace. Los sistemas más antiguos todavía tienen ifconfig y route -n. La configuración DNS está en /etc/resolv.conf, o se puede revisar con resolvectl status en los sistemas que usan systemd-resolved. Los tres admiten ping, nslookup y un rastreo de ruta (tracert en Windows, traceroute en macOS y Linux).

Usa un enfoque estructurado de abajo hacia arriba. Primero revisa las Capas 1 y 2: ¿el cable está conectado y con luz de enlace, o la laptop está asociada al SSID correcto con una señal razonable? Luego revisa la configuración IP: una dirección 169.254 apunta a una falla de DHCP; una dirección que parece correcta pero con máscara o gateway equivocados apunta a un error de configuración estática. Después prueba la alcanzabilidad por pasos: haz ping al loopback, a la propia dirección del host, al gateway, a una IP remota y luego a un nombre. Si una IP funciona pero un nombre falla, el problema es DNS. Si el gateway responde pero las direcciones remotas no, busca más allá del cliente, en el enrutamiento o los firewalls.

Lo inalámbrico agrega sus propios puntos de falla. El cliente puede estar en el SSID equivocado o en una red de invitados, puede tener guardada una contraseña incorrecta, puede fallar la autenticación 802.1X, puede estar demasiado lejos del AP (punto de acceso) o en un canal congestionado o con interferencia. Un cliente asociado pero con una dirección APIPA (direccionamiento IP privado automático) normalmente tiene una conexión inalámbrica que funciona, pero la WLAN está asignada a una VLAN donde DHCP no es alcanzable. Compara siempre con un cliente que funcione en el mismo lugar: si los demás se conectan bien, concéntrate en el cliente; si todos fallan, concéntrate en la red.

Veamos un ejemplo práctico. Un usuario con una laptop Linux no puede navegar. ip a muestra 10.20.30.44/24 en wlan0 e ip route muestra default via 10.20.30.1. ping 10.20.30.1 y un ping a una IP externa conocida funcionan, pero ping intranet.example.com falla con un error de resolución de nombres. /etc/resolv.conf lista un servidor DNS que se retiró el mes pasado, resto de una configuración estática. Volver a configurar la conexión con el DNS entregado por DHCP y confirmar con nslookup intranet.example.com resuelve el problema. Las Capas 1 a 3 nunca fueron el problema.

Errores comunes: confundir comandos entre sistemas operativos, como escribir ipconfig /all en Linux; renovar DHCP una y otra vez cuando el puerto del switch está en la VLAN equivocada; saltarse el ping al gateway e ir directo a internet; culpar al Wi-Fi cuando el cliente tiene una IP estática de otro sitio; y olvidar que una caché DNS desactualizada puede hacer que un sitio falle mientras otros funcionan. Registra lo que revisaste, porque el siguiente ingeniero no debería repetir cada paso.

Las preguntas del examen suelen mostrar una salida y preguntar qué está mal o qué plataforma la produjo. 'ipconfig' es Windows, 'ifconfig' con en0 sugiere macOS, e 'ip addr' o 'ip route' es Linux. 'El ping por IP funciona pero por nombre falla' apunta a DNS. '169.254' apunta a DHCP. 'Puede hacer ping a dispositivos locales pero no al gateway' apunta a la configuración del gateway o a la VLAN. 'Asociado al SSID pero sin IP válida' apunta a la asignación de la WLAN a la VLAN o a DHCP.

Términos clave

ipconfig /all
Comando de Windows que muestra todos los detalles del adaptador, incluidos la MAC, el servidor DHCP, la concesión y los servidores DNS.
ip addr / ip route
Comandos de Linux que muestran las direcciones de las interfaces y la tabla de enrutamiento, incluido el gateway predeterminado.
ifconfig
Comando de interfaz heredado que todavía se usa en macOS y en Linux antiguos para mostrar direcciones y el estado de las interfaces.
nslookup
Un comando disponible en las tres plataformas que consulta DNS para comprobar si un nombre se resuelve.
RSSI
Indicador de intensidad de la señal recibida, una medida de qué tan fuerte llega la señal inalámbrica al cliente.
/etc/resolv.conf
El archivo de Linux que lista los servidores DNS que usa el resolvedor del sistema.
Ejemplo real

Un usuario de Windows en el nuevo SSID de invitados no puede llegar a nada. ipconfig /all muestra 169.254.12.80 sin gateway, mientras que netsh wlan show interfaces muestra una señal fuerte y el SSID correcto. Los demás invitados también fallan. El controlador inalámbrico asigna la WLAN de invitados a la VLAN 99, que nunca se agregó a la troncal del AP; al agregarla, DHCP pasa y los clientes obtienen direcciones correctas.

Consejo para el examen: Aprende a qué sistema operativo pertenece cada comando: ipconfig en Windows, ifconfig en macOS, ip addr en Linux. Las preguntas suelen mostrar una salida y preguntar de qué plataforma es o qué configuración está mal.

Comprueba lo que sabes

¿Qué comando de Windows muestra los servidores DNS y el servidor DHCP que usa un cliente?

ipconfig /all, que muestra todos los detalles del adaptador, incluidos el servidor DHCP, los tiempos de concesión y los servidores DNS.

Un usuario puede hacer ping a un servidor remoto por IP pero no por nombre. ¿Qué configuración investigas?

DNS: los servidores DNS configurados en el cliente y si pueden resolver el nombre.

En un host Linux moderno, ¿cómo muestras el gateway predeterminado?

Ejecuta ip route y busca la línea que empieza con 'default via'.

Varios usuarios inalámbricos de la misma zona obtienen direcciones 169.254. ¿Es más probable que la falla esté en los clientes o en la red?

En la red, porque muchos clientes fallan a la vez; revisa la asignación de la WLAN a la VLAN, las troncales y la alcanzabilidad de DHCP.
