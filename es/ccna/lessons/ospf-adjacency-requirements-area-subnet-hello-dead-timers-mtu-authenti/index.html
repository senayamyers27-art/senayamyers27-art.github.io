Requisitos de adyacencia de OSPF: área, subred, temporizadores hello/dead, MTU, autenticación, router ID único

Dos routers OSPF en el mismo enlace no siempre se convierten en vecinos. OSPF revisa varios parámetros en los paquetes hello, y algunos más después, y si no coinciden la relación se estanca. Conocer cada requisito, y el estado en el que cada desajuste deja al vecino, te permite diagnosticar rápidamente los problemas de adyacencia.

Lo siguiente debe coincidir en los paquetes hello; de lo contrario, los routers se ignoran entre sí y nunca pasan de Down o Init. El ID de área: ambas interfaces deben estar en la misma área, por ejemplo el área 0. La subred y la máscara: en enlaces Ethernet broadcast y punto a punto, ambas interfaces deben estar en la misma subred con la misma máscara. Los intervalos hello y dead: si un router usa 10 y 40 segundos y el otro 5 y 20, no se convertirán en vecinos. La autenticación: si un lado usa autenticación OSPF y el otro no, o las claves difieren, los hellos se rechazan. El flag de área stub también debe coincidir, aunque las áreas stub están fuera del alcance del CCNA de área única.

Los router ID deben ser únicos. Si dos routers tienen el mismo RID, no formarán una adyacencia, e IOS registra un mensaje de router-id duplicado. Esto suele ocurrir cuando se copia una configuración entre routers incluyendo la línea router-id.

La MTU (maximum transmission unit, unidad máxima de transmisión) se revisa después, durante el intercambio de la base de datos. Si las MTU de las interfaces difieren, los routers se ven entre sí y llegan a ExStart o Exchange, pero los paquetes de descripción de la base de datos se rechazan y se quedan atascados ahí. La solución es hacer que los valores de MTU coincidan; el comando ip ospf mtu-ignore existe, pero oculta el problema real.

Otras condiciones también impiden la adyacencia. Una interfaz pasiva no envía hellos, así que no se forma ningún vecino en ella. Una interfaz que no tiene OSPF habilitado mediante una sentencia network o un comando ip ospf tampoco envía nada. Una ACL que bloquea OSPF (protocolo IP 89) o los multicasts 224.0.0.5 y 224.0.0.6 rompe los hellos. En segmentos broadcast, si ambos routers tienen prioridad 0, ninguno puede ser DR, así que no se forma ninguna adyacencia completa. Un desajuste de tipo de red (un lado broadcast y el otro punto a punto) puede llegar a Full, pero las rutas no se instalarán correctamente, porque los dos lados describen el enlace de forma distinta.

R1# show ip ospf interface g0/0
  Internet Address 10.0.12.1/24, Area 0
  Process ID 1, Router ID 1.1.1.1, Network Type BROADCAST, Cost: 1
  Timer intervals configured, Hello 10, Dead 40, Wait 40, Retransmit 5

Resuelve los problemas comparando show ip ospf interface en ambos extremos: ahí están el área, la dirección y la máscara, el tipo de red y los temporizadores. show ip ospf neighbor muestra el estado alcanzado. debug ip ospf adj y debug ip ospf hello (usados con cuidado) revelan mensajes como parámetros hello que no coinciden o errores de autenticación.

Términos clave

Hello/dead interval (intervalo hello/dead)
Cada cuánto se envían los hellos y cuánto esperar antes de declarar caído a un vecino; 10 y 40 segundos de forma predeterminada en enlaces broadcast y punto a punto.
MTU mismatch (desajuste de MTU)
Unidades máximas de transmisión distintas en los dos extremos, lo que deja a los vecinos OSPF atascados en ExStart o Exchange.
OSPF authentication (autenticación OSPF)
Verificación de los paquetes OSPF con una clave compartida; ambos lados deben usar el mismo tipo y la misma clave.
Duplicate router ID (router ID duplicado)
Dos routers que usan el mismo RID, lo que impide la adyacencia y provoca errores en el log.
Ejemplo real

R1 y R2 se conectan por un enlace Ethernet, pero show ip ospf neighbor en R1 está vacío. show ip ospf interface g0/0 en cada router revela que R1 tiene 10.0.12.1/24 mientras que R2 tiene 10.0.12.2/25. Ambos están en el mismo rango, pero las máscaras difieren, así que los hellos se rechazan. Corregir la máscara de R2 a /24 lleva al vecino a FULL en segundos.

Consejo para el examen: Los vecinos atascados en EXSTART o EXCHANGE apuntan a un desajuste de MTU. La ausencia total de vecinos apunta a desajustes a nivel de hello: área, subred/máscara, temporizadores, autenticación o una interfaz pasiva.

Comprueba lo que sabes

¿Qué parámetros de OSPF deben coincidir en los paquetes hello para que dos routers se conviertan en vecinos?

El ID de área, la subred y la máscara, los intervalos hello y dead, la autenticación y el flag stub; además, los router ID deben ser únicos.

Dos vecinos están atascados en EXSTART. ¿Cuál es la causa más probable?

Un desajuste de MTU entre las dos interfaces.

¿El ID del proceso OSPF debe coincidir entre vecinos?

No. El ID de proceso tiene significado solo local; solo deben coincidir parámetros como el área, la subred, los temporizadores y la autenticación.
