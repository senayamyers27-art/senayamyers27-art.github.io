Requisitos de adyacencia de OSPF: área, subred, temporizadores hello/dead, MTU, autenticación, router ID único

Dos routers OSPF (Open Shortest Path First) en el mismo enlace no siempre se convierten en vecinos. OSPF revisa varios parámetros dentro de los paquetes hello, y algunos más durante el intercambio de bases de datos que sigue, y si no coinciden, la relación se estanca. Conocer cada requisito, y el estado de vecino en el que cada discrepancia deja a los routers, te permite diagnosticar problemas de adyacencia en segundos en lugar de adivinar, y es uno de los temas favoritos del examen.

Lo siguiente debe coincidir en los paquetes hello, o los routers se ignoran mutuamente y nunca pasan de Down o Init. El ID de área: ambas interfaces deben estar en la misma área, como el área 0. La subred y la máscara: en enlaces Ethernet broadcast y punto a punto, ambas interfaces deben estar en la misma subred con la misma máscara. Los intervalos hello y dead: si un router usa 10 y 40 segundos (los valores predeterminados en enlaces broadcast y punto a punto) y el otro usa 5 y 20, no se convertirán en vecinos. La autenticación: si un lado usa autenticación OSPF y el otro no, o las claves difieren, los hello se rechazan. El indicador de área stub también debe coincidir, aunque las áreas stub están fuera del alcance del CCNA de área única.

Los router ID (RID) deben ser únicos. El RID es un valor de 32 bits escrito como una dirección IPv4, que se toma del comando router-id, o si no, de la dirección loopback más alta, o si no, de la dirección más alta de una interfaz física activa. Si dos routers tienen el mismo RID, no forman una adyacencia, e IOS registra un mensaje de router-id duplicado. Esto suele ocurrir cuando se copia una configuración entre routers incluida la línea router-id. Después de cambiar un RID, debes ejecutar clear ip ospf process para que surta efecto.

La MTU (maximum transmission unit) no está en el hello, así que se revisa después, durante el intercambio de bases de datos. Si las MTU de las interfaces difieren, los routers se ven entre sí y llegan a ExStart o Exchange, pero los paquetes de descripción de base de datos se rechazan y quedan atascados allí. La solución es igualar los valores de MTU con el comando de interfaz ip mtu o mtu; existe ip ospf mtu-ignore, pero oculta el problema real.

Otras condiciones también impiden la adyacencia. Una interfaz pasiva (passive-interface g0/1) no envía hello, así que no se forma ningún vecino en ella, aunque su subred se sigue anunciando. Una interfaz que no está habilitada para OSPF con una sentencia network o un comando ip ospf 1 area 0 no envía nada. Una ACL (access control list) que bloquea OSPF, que es el protocolo IP 89, o las direcciones multicast 224.0.0.5 y 224.0.0.6, rompe los hello. En segmentos broadcast, si ambos routers tienen prioridad 0, ninguno puede ser DR (designated router), así que no se forma ninguna adyacencia completa. Una discrepancia de tipo de red, un lado broadcast y el otro punto a punto, puede llegar a Full, pero es posible que las rutas no se instalen correctamente porque los dos lados describen el enlace de forma diferente. Los ID de proceso, en cambio, tienen significado local y no necesitan coincidir.

R1# show ip ospf interface g0/0
  Internet Address 10.0.12.1/24, Area 0
  Process ID 1, Router ID 1.1.1.1, Network Type BROADCAST, Cost: 1
  Timer intervals configured, Hello 10, Dead 40, Wait 40, Retransmit 5

Veamos un ejemplo resuelto. R1 y R2 se conectan en 10.0.12.0/24, pero show ip ospf neighbor en R1 está vacío. Ejecutas show ip ospf interface g0/0 en ambos. R1 muestra Area 0, /24, Hello 10, Dead 40. R2 muestra Area 0, /24, Hello 5, Dead 20, porque alguien configuró ip ospf hello-interval 5 durante unas pruebas. Corregir R2 con no ip ospf hello-interval restaura los valores predeterminados, y en segundos el vecino pasa por Init, 2-Way, ExStart, Exchange y Loading hasta Full. Si en cambio el vecino hubiera quedado atascado en ExStart, habrías comparado los valores de MTU en show interfaces. debug ip ospf adj y debug ip ospf hello, usados con cuidado en un laboratorio, muestran mensajes como 'mismatched hello parameters' o errores de autenticación que confirman la causa.

Errores comunes: pensar que el ID de proceso OSPF debe coincidir (no es así); suponer que una interfaz pasiva impide que se anuncie la subred (solo detiene los hello); olvidar que la MTU no forma parte del hello; configurar el mismo router-id en dos routers; y culpar a una prioridad distinta, que nunca bloquea la adyacencia salvo que ambos lados tengan 0. Las preguntas del examen suelen mostrar dos salidas lado a lado. Las pistas se asocian claramente: 'ningún vecino' apunta a área, subred o máscara, temporizadores, autenticación, una interfaz pasiva o un RID duplicado; 'atascado en EXSTART o EXCHANGE' apunta a la MTU; 'solo Init' apunta a hello en un solo sentido, a menudo por una ACL; y 'los ID de proceso difieren' es un distractor, porque son locales.

Términos clave

Paquete hello (hello packet)
Un mensaje OSPF enviado a 224.0.0.5 que descubre vecinos y lleva parámetros que deben coincidir.
Intervalos hello y dead (hello and dead intervals)
Cada cuánto se envían los hello y cuánto esperar antes de declarar caído a un vecino; 10 y 40 segundos de forma predeterminada en Ethernet.
Router ID (RID)
Un identificador único de 32 bits para cada router OSPF, escrito como una dirección IPv4.
Discrepancia de MTU (MTU mismatch)
Tamaños máximos de paquete distintos en los dos extremos, lo que deja a los vecinos atascados en ExStart o Exchange.
Interfaz pasiva (passive interface)
Una interfaz OSPF que anuncia su subred pero no envía hello, así que no se forman vecinos en ella.
ID de proceso (process ID)
El número con significado local en router ospf; no necesita coincidir entre vecinos.
ID de área (area ID)
El área OSPF a la que pertenece una interfaz; ambos extremos de un enlace deben usar la misma área.
Ejemplo real

Después de reemplazar el router de una sucursal, este nunca forma una adyacencia OSPF con la sede central. El ingeniero compara show ip ospf interface en ambos extremos: el área, la máscara y los temporizadores coinciden, pero el log del router nuevo muestra un mensaje de router-id duplicado. El técnico había pegado la configuración del router viejo en el nuevo, incluido router-id 2.2.2.2, mientras el router viejo seguía conectado para pruebas. Cambiar el RID y ejecutar clear ip ospf process lleva al vecino a Full.

Consejo para el examen: Los vecinos atascados en EXSTART o EXCHANGE apuntan a una discrepancia de MTU. La ausencia total de vecinos apunta a discrepancias a nivel de hello: área, subred y máscara, temporizadores, autenticación, una interfaz pasiva o un router ID duplicado. Los ID de proceso nunca necesitan coincidir.

Comprueba lo que sabes

¿Qué estado de vecino sugiere una discrepancia de MTU?

ExStart o Exchange, porque la MTU se revisa en los paquetes de descripción de base de datos después de que la etapa de hello tiene éxito.

¿Dos vecinos OSPF necesitan el mismo ID de proceso?

No, el ID de proceso tiene significado local; lo que debe coincidir es el área, la subred, los temporizadores, la autenticación y que los router ID sean únicos.

R1 usa hello 10 y dead 40, y R2 usa hello 5 y dead 20. ¿Qué ocurre?

Nunca se convierten en vecinos, porque los intervalos hello y dead deben coincidir en el paquete hello.

¿Qué efecto tiene una interfaz pasiva sobre OSPF en ese enlace?

Detiene los hello, así que no se forma adyacencia, pero la subred de la interfaz se sigue anunciando a los demás vecinos.
