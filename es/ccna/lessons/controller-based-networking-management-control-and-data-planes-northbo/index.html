Redes basadas en controlador: planos de administración, control y datos; API northbound y southbound

Para entender las redes basadas en controlador, primero necesitas la idea de los planos: las funciones lógicas que realiza un dispositivo de red. Separar estas funciones, y trasladar algunas a un controlador central, es la idea central de las redes definidas por software (SDN).

El plano de datos, también llamado plano de reenvío, mueve el tráfico de los usuarios: recibe tramas y paquetes, busca a dónde van, aplica funciones como ACL y NAT, y los reenvía por una interfaz. Funciona a alta velocidad, a menudo en hardware especializado. El plano de control construye la información que usa el plano de datos. Los protocolos de enrutamiento como OSPF, spanning tree, ARP y la construcción de las tablas MAC y de enrutamiento son funciones del plano de control. El plano de administración es la forma en que los administradores y los sistemas gestionan el dispositivo: SSH, SNMP, syslog, la configuración de NTP y las API. Una prueba sencilla: si reenvía el tráfico de los usuarios, es plano de datos; si decide cómo debe reenviarse el tráfico, es plano de control; si permite que personas o herramientas configuren y supervisen el dispositivo, es plano de administración.

En una red tradicional, cada dispositivo tiene su propio plano de control y su propio plano de administración. Cada router ejecuta OSPF, cada switch ejecuta spanning tree, y cada uno se configura por separado. En un diseño basado en controlador, un controlador central asume la administración y algunas o todas las funciones del plano de control. El controlador tiene una vista de toda la red, calcula las políticas o los caminos y programa los dispositivos, que siguen haciendo el reenvío del plano de datos. En la práctica, la mayoría de los controladores empresariales, como Cisco Catalyst Center, centralizan la administración y las políticas mientras los dispositivos siguen ejecutando protocolos de enrutamiento distribuidos, mientras que los diseños SDN puros, como los primeros despliegues de OpenFlow, trasladaban al controlador las propias decisiones de reenvío.

El controlador se comunica en dos direcciones, descritas imaginando el controlador dibujado en el medio. Las interfaces southbound (SBI) conectan el controlador hacia abajo con los dispositivos de red, para enviar configuración y recopilar su estado. Algunos ejemplos son NETCONF, RESTCONF, OpenFlow, gRPC, y también los tradicionales SSH, CLI y SNMP. Las interfaces northbound (NBI) conectan el controlador hacia arriba con aplicaciones, scripts, sistemas de orquestación y sistemas de TI, que las usan para solicitar cambios y leer datos. Las API northbound suelen ser API REST: basadas en HTTP, usan verbos como GET, POST, PUT y DELETE, e intercambian datos normalmente codificados en JSON.

La fabric de campus de Cisco, SD-Access, ilustra el modelo. Separa un underlay, la red física de switches y enrutamiento IP que proporciona la alcanzabilidad, de un overlay, túneles virtuales (VXLAN) construidos encima que transportan el tráfico de los usuarios y aplican la segmentación. Catalyst Center la automatiza y administra, mientras que las políticas se aplican con grupos basados en la identidad.

Los beneficios de las redes basadas en controlador incluyen una configuración centralizada y consistente; visibilidad y assurance de toda la red; un despliegue más rápido; políticas expresadas como intención; y API que permiten a otros sistemas automatizar la red. La contrapartida es la dependencia del controlador, que a su vez debe ser de alta disponibilidad y estar protegido.

Términos clave

Data plane (plano de datos)
Las funciones que reenvían el tráfico de los usuarios a través de un dispositivo.
Control plane (plano de control)
Las funciones que deciden cómo se reenvía el tráfico, como los protocolos de enrutamiento, STP y ARP.
Management plane (plano de administración)
Las funciones que se usan para configurar y supervisar un dispositivo, como SSH, SNMP y las API.
Southbound API
Interfaz entre un controlador y los dispositivos de red, como NETCONF, RESTCONF u OpenFlow.
Northbound API
Interfaz entre un controlador y las aplicaciones o scripts, normalmente una API REST que usa JSON.
Ejemplo real

El sistema de tickets de un equipo de seguridad detecta una laptop infectada y llama a la API REST northbound del controlador del campus con una solicitud POST para poner en cuarentena ese equipo. Luego el controlador usa sus conexiones southbound hacia los switches de acceso para aplicar la política de cuarentena. Ni el analista de seguridad ni el ingeniero de redes inician sesión en ningún switch.

Consejo para el examen: Northbound es del controlador hacia las aplicaciones (normalmente REST y JSON); southbound es del controlador hacia los dispositivos (NETCONF, RESTCONF, OpenFlow, SSH, SNMP). OSPF y STP son plano de control; reenviar una trama es plano de datos; SSH es plano de administración.

Comprueba lo que sabes

¿Construir la tabla de enrutamiento de OSPF es una función del plano de control, de datos o de administración?

Del plano de control.

Un script de Python obtiene una lista de dispositivos de un controlador por HTTPS con JSON. ¿Qué interfaz está usando?

Una API northbound (normalmente REST).

Menciona dos protocolos southbound que podría usar un controlador.

Dos cualesquiera de NETCONF, RESTCONF, OpenFlow, gRPC, SSH/CLI o SNMP.
