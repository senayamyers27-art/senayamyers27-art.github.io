Cisco CCNA 200-301 v2.0

Funciones de DHCP y DNS en la red; solución de problemas de resolución de nombres y de clientes DHCP

Dos servicios hacen que toda red sea utilizable sin que nadie lo note. DHCP (Dynamic Host Configuration Protocol) entrega automáticamente a los hosts su dirección IP, su máscara, su gateway predeterminado y las direcciones de los servidores DNS. DNS (Domain Name System) traduce los nombres que las personas recuerdan, como www.example.com, a las direcciones IP que necesitan las computadoras. Cuando cualquiera de los dos falla, los usuarios reportan que la red está caída, aunque el enrutamiento y la conmutación estén bien. Conocer la función de cada servicio te permite distinguir rápidamente esas fallas.

DHCP funciona mediante el intercambio DORA: Discover, Offer, Request, Acknowledgment, usando los puertos UDP (User Datagram Protocol) 67 para el servidor y 68 para el cliente. Como Discover es un broadcast, y los routers no reenvían broadcasts, se necesita un agente de retransmisión (relay agent) cuando el servidor está en otra subred. Lo configuras con ip helper-address 10.1.1.20 en la interfaz del router que da hacia los clientes, y el router reenvía la solicitud como unicast al servidor. La concesión (lease) es temporal, y los clientes intentan renovarla a la mitad del tiempo de concesión. Además de la dirección, las opciones de DHCP entregan el gateway, los servidores DNS y el nombre de dominio y, para dispositivos como teléfonos IP y AP (access points), las direcciones del controlador o del servidor TFTP (Trivial File Transfer Protocol). Un router IOS puede ser servidor DHCP con ip dhcp pool, network, default-router y dns-server, más ip dhcp excluded-address para los dispositivos estáticos.

DNS es una base de datos distribuida y jerárquica. Un cliente consulta a su resolver DNS configurado, que responde desde la caché o consulta la jerarquía: los servidores raíz, luego los servidores del dominio de nivel superior, como .com, y luego el servidor autoritativo del dominio. Los tipos de registro comunes son A (nombre a dirección IPv4), AAAA (nombre a dirección IPv6), CNAME (un alias de otro nombre), MX (servidor de correo de un dominio), NS (servidores de nombres de una zona) y PTR (dirección a nombre, para búsquedas inversas). Las consultas DNS normalmente usan el puerto UDP 53, con el puerto TCP 53 para respuestas grandes y transferencias de zona. Las respuestas se guardan en caché durante su TTL (time to live), por eso un registro modificado puede tardar en verse en todas partes.

En un router Cisco, ip name-server 10.1.1.53 define el servidor DNS que usa el router, e ip domain-lookup (activado de forma predeterminada) habilita las búsquedas. Una molestia conocida es que los comandos mal escritos en la CLI se tratan como nombres de host y el router intenta resolverlos; no ip domain-lookup evita eso en los laboratorios. ip host SERVER1 10.1.1.10 crea una asignación local estática.

Para diagnosticar un cliente DHCP, revisa primero su configuración IP. Una dirección APIPA (Automatic Private IP Addressing) 169.254.x.x, o ninguna dirección, significa que DHCP falló. Luego revisa el camino: enlace activo, VLAN de acceso correcta, relay configurado con la dirección de servidor correcta en la interfaz correcta, un pool o ámbito (scope) para esa subred en el servidor, direcciones libres en el pool, y que DHCP snooping no esté descartando ofertas legítimas porque un enlace ascendente no es confiable. ipconfig /release e ipconfig /renew en Windows, o dhclient en algunos sistemas Linux, reintentan el proceso; show ip dhcp binding, show ip dhcp pool y show ip dhcp conflict en un servidor IOS muestran las concesiones, el agotamiento y las direcciones duplicadas.

Para diagnosticar DNS, separa la alcanzabilidad de la resolución de nombres. Si ping 10.1.1.10 funciona pero ping server1.example.com falla, el problema es DNS. Revisa qué servidor DNS usa el cliente con ipconfig /all, resolvectl status o /etc/resolv.conf, y luego prueba directamente con nslookup server1.example.com o dig server1.example.com. Las causas posibles son una dirección de servidor DNS incorrecta entregada por DHCP, un servidor DNS inalcanzable o bloqueado por una ACL en UDP 53, un registro faltante o incorrecto, o una caché desactualizada que se limpia con ipconfig /flushdns.

Veamos un ejemplo resuelto. Después de crear una nueva VLAN 30 para el equipo de finanzas, todas las PC muestran una dirección 169.254. La interfaz VLAN del switch de núcleo tiene una dirección IP y el servidor DHCP tiene un ámbito para 10.30.0.0/24, pero show running-config interface vlan 30 no tiene ip helper-address. Agregar ip helper-address 10.1.1.20 permite que los Discover lleguen al servidor, y las PC obtienen concesiones. Al día siguiente, un usuario puede llegar al servidor ERP (enterprise resource planning) por IP pero no por nombre. ipconfig /all muestra un servidor DNS 10.30.0.53, que no existe; la opción DNS del ámbito se escribió mal. Corregirla a 10.1.1.53 y renovar la concesión arregla la resolución de nombres.

Errores comunes: poner ip helper-address en la interfaz que da hacia el servidor en lugar de la que da hacia los clientes; tratar una falla de nombres como una falla de enrutamiento; olvidar excluir las direcciones estáticas de un pool, lo que causa conflictos; y suponer que DNS usa solo TCP. Pistas del examen: 'dirección 169.254' significa falla de DHCP; 'funciona por IP, falla por nombre' significa DNS; 'los clientes de una subred remota no obtienen dirección' significa un relay faltante (ip helper-address); 'pool agotado' significa que no hay concesiones libres; 'el nombre se asigna a IPv6' significa AAAA; 'búsqueda inversa' significa PTR.

Términos clave

DORA
Discover, Offer, Request, Acknowledgment: el intercambio de cuatro mensajes de DHCP.
ip helper-address
Configura una interfaz de router como relay DHCP, que reenvía los broadcasts de los clientes a un servidor en otra subred.
Concesión (lease)
El tiempo durante el cual un cliente DHCP puede usar la dirección asignada antes de renovarla.
APIPA
Automatic Private IP Addressing, una dirección 169.254.x.x autoasignada que indica una falla de DHCP.
Registros A y AAAA (A and AAAA records)
Registros DNS que asignan un nombre a una dirección IPv4 o IPv6, respectivamente.
Registro PTR (PTR record)
Un registro DNS que asigna una dirección de vuelta a un nombre para búsquedas inversas.
nslookup
Una herramienta de línea de comandos que consulta directamente a los servidores DNS para probar la resolución de nombres.
Ejemplo real

Los escáneres portátiles de un almacén dejan de conectarse por nombre al servidor de inventario después de una migración de DNS. Todavía pueden hacer ping a la dirección IP del servidor. El ingeniero descubre que el ámbito DHCP sigue entregando la dirección del servidor DNS anterior, que ya se apagó. Actualizar la opción DNS del ámbito y hacer que los escáneres renueven sus concesiones restablece la resolución de nombres sin ningún cambio de enrutamiento.

Consejo para el examen: Si la IP funciona pero los nombres fallan, la respuesta es DNS. Si el cliente tiene una dirección 169.254, la respuesta es DHCP, y en una subred remota el primer sospechoso es un ip helper-address faltante en la interfaz que da hacia los clientes.

Comprueba lo que sabes

¿Cuáles son los cuatro mensajes de DHCP, en orden?

Discover, Offer, Request y Acknowledgment.

¿Por qué se necesita ip helper-address cuando el servidor DHCP está en otra subred?

DHCP Discover es un broadcast, que los routers no reenvían; el helper lo retransmite como unicast al servidor.

Un usuario puede hacer ping a 10.2.2.2 pero no a app.corp.local. ¿Qué servicio está fallando?

DNS, porque la conectividad IP funciona y solo falla la resolución de nombres.

¿Qué tipo de registro DNS asigna un nombre a una dirección IPv6?

AAAA.
