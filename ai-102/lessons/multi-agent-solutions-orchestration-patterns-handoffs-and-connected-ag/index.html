Multi-agent solutions: orchestration patterns, handoffs and connected agents

▶ Watch the overview video

Last reviewed September 25, 2026

A single agent with many tools and long instructions becomes hard to steer: it picks the wrong tool, forgets rules and is difficult to test. Multi-agent solutions split the work among specialized agents, each with focused instructions and a small set of tools, and coordinate them. This mirrors how teams of people divide work.

Several orchestration patterns are common. Sequential: agents work in a fixed order, each passing its output to the next, such as research, then draft, then review. Concurrent: several agents work on the same input in parallel and their results are combined, such as analyzing a contract for legal, financial and compliance risks at once. Handoff: one agent handles the conversation until it decides another is better suited and transfers control, like a front-desk agent routing to billing or technical support. Group chat: agents take turns in a shared conversation, with a manager or selector deciding who speaks next, useful for brainstorming or maker-checker loops where a writer and a reviewer iterate. Magentic (or planner-led) orchestration: a manager agent plans, assigns tasks to specialists and tracks progress for open-ended problems.

In Azure AI Foundry Agent Service, connected agents let a main agent call other agents as tools. You create specialist agents, then add them to the main agent as connected agents with a name and a description of when to use them. The main agent decides when to delegate, sends the sub-task and uses the specialist's answer, without you writing routing code. Connected agents suit a main orchestrator with a handful of specialists. For more complex or deterministic multi-step processes, workflows in Foundry or frameworks such as Semantic Kernel and the Microsoft Agent Framework provide explicit orchestration.

Design carefully. Give each agent a clear, non-overlapping responsibility and describe it precisely, because routing depends on those descriptions. Keep the number of agents small; every handoff adds latency, tokens and chances for error. Decide what context each agent receives so private data is not passed around unnecessarily. Use deterministic code for steps that must always happen in the same order and reserve model-driven routing for genuinely open decisions. Trace the whole conversation so you can see which agent did what.

Test each agent alone first, then the combined system, including cases where the router should decline or ask a clarifying question.

Key terms

Orchestration
Coordinating multiple agents so their work combines to complete a task.
Handoff
A pattern where one agent transfers control of a conversation to a more suitable agent.
Connected agents
An Agent Service feature that lets a main agent call specialist agents as tools.
Maker-checker
A pattern where one agent produces work and another reviews it, iterating until accepted.
Real-world example

An insurance portal has a main triage agent with three connected agents: policy questions (file search), claims status (OpenAPI to the claims system) and billing (function calling). The triage agent delegates each request based on the connected agents' descriptions and composes the final reply.

Exam tip: A main agent delegating to specialists maps to connected agents or handoff. Agents reviewing each other's work is group chat or maker-checker. Fixed step order is sequential orchestration.

Check yourself

What is the benefit of splitting a large agent into specialists?

Each has focused instructions and fewer tools, so it chooses tools more reliably and is easier to test and maintain.

How does a main agent decide which connected agent to call?

From the names and descriptions you give each connected agent, so they must clearly state when each should be used.
