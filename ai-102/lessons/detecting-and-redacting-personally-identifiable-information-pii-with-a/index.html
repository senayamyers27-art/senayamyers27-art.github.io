Detecting and redacting personally identifiable information (PII) with Azure AI Language

▶ Watch the overview video

Last reviewed September 25, 2026

Organizations handle text full of personal data: chat transcripts, emails, support tickets, medical notes. Storing, sharing or sending that text to other systems creates privacy and compliance risk. Azure AI Language's PII detection finds personally identifiable information in text and can return a redacted copy, helping you meet regulations such as GDPR and internal data handling policies.

You call it with the PiiEntityRecognition kind in REST or recognize_pii_entities in the SDK. The response includes each detected entity with its text, category (such as Person, PhoneNumber, Email, Address, CreditCardNumber, a national identification number or bank account number), subcategory, position (offset and length) and confidence score. It also returns redactedText: the original text with each PII entity replaced by asterisks by default. Other redaction policies can replace entities with their category name or a fixed character, which keeps the text readable for analysis while removing the values.

result = client.recognize_pii_entities(["Call Ana Silva on 555-0100 about card 4111 1111 1111 1111."])
for doc in result:
    print(doc.redacted_text)
    for e in doc.entities:
        print(e.category, e.confidence_score)

You can narrow detection with a categories filter, for example only phone numbers and emails, so the service does not redact names you need to keep. The domain parameter set to phi detects protected health information for healthcare text. There is also a conversational PII feature for chat and call transcripts, and document PII for whole files.

Design the pipeline carefully. Redact as early as possible, before text is logged, stored for analytics or sent to other services such as a language model. Remember detection is statistical: it can miss unusual formats or flag false positives, so combine it with other controls (access restrictions, retention policies) and test it on your real data, adjusting any confidence threshold you apply. Where text must never leave your environment, run the PII container on premises.

PII detection is different from Content Safety: PII is about personal data, while Content Safety is about harmful content such as hate or violence. It is also different from general NER, which categorizes entities but does not produce redacted text or focus on sensitive data types.

Key terms

PII
Personally identifiable information: data that can identify a person, such as names, phone numbers or ID numbers.
Redaction
Masking or replacing sensitive values in text so they are not exposed.
redactedText
The PII detection output field containing the input text with detected entities masked.
PHI
Protected health information, detected by setting the PII domain to phi.
Real-world example

A telecom company feeds call-center transcripts to an analytics warehouse and a summarization model. It first runs conversational PII detection, stores only the redacted transcripts with categories in place of values, and keeps the original audio in a restricted store with a 30-day retention policy.

Exam tip: Mask personal data in text: PII detection with redactedText. Restrict which types are masked with the categories filter. Healthcare data: domain phi.

Check yourself

What does the PII detection response include besides the entity list?

A redactedText field with the input text where each detected entity is masked.

How can you keep person names but redact phone numbers?

Pass a categories filter that includes only phone number (and any other types you want) so other categories are not redacted.
