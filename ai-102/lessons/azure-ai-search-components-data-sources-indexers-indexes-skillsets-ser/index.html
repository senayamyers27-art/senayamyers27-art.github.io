Azure AI Search components: data sources, indexers, indexes, skillsets, service tiers, replicas and partitions

▶ Watch the overview video

Last reviewed September 25, 2026

Azure AI Search (formerly Azure Cognitive Search) is a managed search service. It stores your content in indexes and answers keyword, vector and hybrid queries quickly, and it can enrich content with AI as it is imported. It is the backbone of knowledge mining (making large volumes of documents searchable and analyzable) and of retrieval for RAG apps.

Several components work together. An index is the searchable store, like a database table of JSON documents with a schema of fields. A data source is a connection to where your content lives, such as Azure Blob Storage, Azure Data Lake Storage Gen2, Azure SQL Database, Azure Cosmos DB or Azure Table Storage. An indexer is a crawler that reads from a data source, cracks documents open to extract text and metadata, maps source fields to index fields (field mappings) and writes documents into the index; it can run on a schedule and uses change detection to process only new or modified items. A skillset is an optional set of AI enrichment steps that an indexer runs during indexing, such as OCR, language detection or entity extraction. A knowledge store optionally saves the enriched output to Azure Storage for other uses.

You can also skip indexers and push data: your code sends JSON documents to the index with the push API or SDK, which suits data sources that indexers do not support or near real-time updates.

The service tier sets capacity and features. The Free tier is shared, small and meant for learning, with no SLA and no scaling. Basic suits small production workloads. The Standard tiers (S1, S2, S3) increase storage and index limits, and Storage Optimized tiers (L1, L2) hold very large indexes at lower cost per gigabyte with higher query latency. You cannot change the tier of an existing service; you create a new one and rebuild the indexes, so choose carefully.

Within a tier you scale with replicas and partitions. Replicas are copies of the whole index that serve queries in parallel; add them for more query throughput and for high availability. Microsoft's SLA for read (query) availability needs at least two replicas, and read-write availability needs three. Partitions split the index storage and indexing work across more machines; add them when the index grows or indexing is slow. Billing is per search unit, which is replicas multiplied by partitions, per hour, whether or not you query.

Security options include API keys (admin keys for full control, query keys for read-only search), Microsoft Entra ID with roles such as Search Index Data Reader, IP firewall rules and private endpoints.

Key terms

Index
The searchable collection of documents and its schema of fields in Azure AI Search.
Indexer
A crawler that reads a data source, cracks documents, maps fields, runs skillsets and loads the index.
Replica
A copy of the index that serves queries, added for throughput and availability.
Partition
A unit of storage and indexing capacity, added for larger indexes and faster indexing.
Real-world example

A legal firm indexes 2 million contracts from Blob Storage with an indexer on an hourly schedule. Queries slow at month end, so the team adds a third replica, which also meets the read-write SLA; later, as the archive grows, it adds a partition for storage.

Exam tip: Slow queries or availability: add replicas. Bigger index or slow indexing: add partitions. Pull from Azure data on a schedule: indexer. The tier cannot be changed after creation.

Check yourself

How many replicas are needed for the query availability SLA?

At least two replicas for read availability; three for read-write availability.

When would you use the push API instead of an indexer?

When the data source is not supported by indexers or you need to push changes into the index immediately from your own code.
