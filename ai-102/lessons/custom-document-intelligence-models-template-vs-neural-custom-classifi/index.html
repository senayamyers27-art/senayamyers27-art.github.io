Custom Document Intelligence models: template vs neural, custom classifiers and composed models

▶ Watch the overview video

Last reviewed September 25, 2026

Prebuilt models cover common documents, but most organizations also have their own forms: an internal claim form, a supplier's purchase order, a lab report. Document Intelligence lets you train custom models on a small number of your own labeled examples to extract exactly the fields you need.

The process runs in Document Intelligence Studio. Put sample documents in a Blob Storage container, create a custom extraction project connected to it, and label the fields: draw regions or select words for each field (such as PatientName or TotalAmount), and label tables and signatures if needed. You need only a few samples to start; Microsoft's guidance is at least five examples of each form type, with more for variable documents. Training produces a model with a model ID that you call like a prebuilt model.

There are two types of custom extraction model. Custom template models (formerly custom form) suit documents with a consistent, fixed layout, where fields are always in the same place, like a standard government form. They train quickly and are accurate for that layout but struggle when the layout varies. Custom neural models use deep learning to understand document content and structure, so they handle structured, semi-structured and some unstructured documents whose layout varies, such as invoices or purchase orders from many suppliers. Neural models are the recommended starting point in most cases; use template when layouts are truly fixed or neural does not support your language or field type.

A custom classification model identifies the type of each document, or of each page range in a combined file, before extraction. You train it with examples of each document class, such as W-2, pay stub and bank statement. It is useful when documents arrive mixed together, for example a mortgage application PDF that contains several document types; the classifier splits and labels them so each goes to the right extraction model.

A composed model groups several custom extraction models under one model ID. When you analyze a document with the composed model, the service determines which of the component models fits best and uses it, returning which one was used (in the current API version the routing uses a custom classifier). Your application calls a single model ID for many form types instead of choosing the model itself, and you can update component models without changing the app.

Evaluate custom models with test documents not used in training, check field-level accuracy and confidence, and add more varied labeled samples where fields are weak. Keep training data representative of real documents, including poor scans if you receive them.

Key terms

Custom template model
A custom extraction model for documents with a consistent, fixed layout.
Custom neural model
A deep learning custom extraction model that handles documents with varying layouts.
Custom classifier
A model that identifies document types, and splits combined files, before extraction.
Composed model
Several custom models grouped under one model ID that routes each document to the best match.
Real-world example

A logistics company receives bills of lading from 200 carriers in different layouts. It labels 60 samples across carriers and trains a custom neural model. Its own standard delivery receipt, which never changes, gets a custom template model, and both are placed in a composed model so the intake app calls one model ID.

Exam tip: Fixed layout: template. Varying layouts from many sources: neural. Mixed document types in one stream: custom classifier. One model ID for several custom models: composed model.

Check yourself

Why might a template model fail on invoices from many vendors?

Template models expect fields in consistent positions; varied layouts need a neural model.

What does a composed model do when it receives a document?

It determines which component custom model best fits the document and extracts fields with that model, returning which model was used.
