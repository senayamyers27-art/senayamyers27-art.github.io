Deploying agents and integrating them into applications

▶ Watch the overview video

Last reviewed September 25, 2026

An agent that works in the playground still needs to reach users. Deployment means making the agent available to applications with proper identity, networking, versioning and operations, and integration means connecting it to the channels and systems where users already work.

With Azure AI Foundry Agent Service, the agent itself is hosted by the service. Your application, such as a web app, API or function, calls the service through the Foundry project endpoint using the SDK or REST API, authenticating with Microsoft Entra ID, ideally through a managed identity with an appropriate role on the project. The app is responsible for mapping users to threads, sending their messages, starting runs, handling requires_action for local functions and rendering responses, including citations and generated files. Stream responses so users see progress. Store thread IDs with the user's session so conversations can resume.

Agents built with a framework such as Semantic Kernel or the Microsoft Agent Framework run inside your own code, so you deploy them like any other application: container images on Azure Container Apps or Azure Kubernetes Service, Azure App Service or Azure Functions. You manage scaling, state storage and secrets yourself, which gives more control.

Integration channels vary. A web chat front end is common. Agents can be published to Microsoft Teams and Microsoft 365 Copilot through Microsoft 365 Agents SDK or Copilot Studio, and exposed to other systems through APIs. Agents can also be triggered by events, such as a new email, a queue message or a scheduled job, rather than by a person chatting.

Treat agent configuration as code. Keep instructions, tool definitions and model choices in source control, deploy them through a pipeline to separate development, test and production projects, and run your evaluation test set as a quality gate before promotion. Pin model versions and test upgrades before switching.

For enterprise environments, use private networking (the standard setup can bring your own virtual network and resources), keep data in your own storage when required, apply content filters, and set up monitoring and alerts from day one.

Key terms

Project endpoint
The Foundry project URL that apps use with the SDK to call Agent Service.
Thread mapping
Storing each user's thread ID so their conversation can continue across requests.
Quality gate
An automated evaluation that must pass before a change is promoted to the next environment.
Standard setup
An Agent Service configuration that uses your own storage, search and networking resources for agent data.
Real-world example

A company deploys its IT support agent in a dev project, runs 100 test tickets through an evaluation pipeline, then promotes the same instructions and tools to production. A web app with a managed identity calls the production project, and the agent is also published to Teams so employees can chat where they work.

Exam tip: Apps call hosted agents through the project endpoint with Entra ID, ideally a managed identity. Framework-based agents are deployed like any app (Container Apps, App Service, Functions).

Check yourself

What must an application track to continue a user's conversation with a hosted agent?

The user's thread ID, so new messages are added to the same thread.

How should changes to an agent's instructions reach production safely?

Through source control and a pipeline that runs an evaluation test set as a quality gate before promotion.
