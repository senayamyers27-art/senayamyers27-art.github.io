Designing a search index: key field, field attributes (searchable, filterable, sortable, facetable, retrievable), analyzers and suggesters

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

An index schema defines the fields of each search document and how each field can be used. Good design decides what users can search, filter, sort and see, and affects storage size and relevance. Some attributes cannot be changed on an existing field without rebuilding the index, so design with the queries in mind.

Every index needs exactly one key field of type Edm.String that uniquely identifies each document; indexers often map it from a storage path or database primary key (base64-encoding values that contain characters not allowed in keys). Other field types include Edm.Int32, Edm.Int64, Edm.Double, Edm.Boolean, Edm.DateTimeOffset, Edm.GeographyPoint, collections such as Collection(Edm.String) for lists of tags, complex types for nested objects, and Collection(Edm.Single) for vectors.

Attributes control behavior. Searchable means the field's text is analyzed and included in full-text search. Filterable allows the field in $filter expressions, such as category eq 'Budget'. Sortable allows $orderby. Facetable allows facet counts, such as the number of hotels per city for a navigation sidebar. Retrievable means the field can be returned in results; turn it off for fields used only for search or filtering, such as vectors or internal scores. Each extra attribute adds storage, so enable only what you need.

Analyzers process searchable text at indexing and query time: they break text into tokens, lowercase them and may remove stop words or reduce words to their root. The default is the standard Lucene analyzer. Language analyzers, such as en.microsoft or fr.lucene, understand a language's word forms, so a search for 'running' matches 'ran'. Specialized analyzers such as keyword (treat the whole value as one token) suit codes and IDs, and you can build custom analyzers. The analyzer is set per field.

A suggester enables autocomplete (completing the word being typed) and suggestions (returning matching documents as the user types). You define one suggester per index, listing the fields it uses as source fields, typically names and titles. It must be defined when those fields are created.

Other schema features include scoring profiles, which boost relevance by field weights or freshness and distance functions; synonym maps attached to fields so 'USA' also matches 'United States'; semantic configurations for semantic ranking; vector search profiles; and CORS options for browser clients.

Key terms

Key field
The single Edm.String field that uniquely identifies each document in an index.
Facetable
A field attribute that enables counts of documents per value for faceted navigation.
Analyzer
A component that tokenizes and normalizes text for full-text search, such as a language analyzer.
Suggester
An index definition that enables autocomplete and search-as-you-type suggestions on chosen fields.
Real-world example

A hotel search site marks name and description searchable with the en.microsoft analyzer, city and rating filterable and facetable, price sortable, and adds a suggester on name. The description vector field is not retrievable, saving bandwidth in every response.

Exam tip: Map the query feature to the attribute: $filter needs filterable, $orderby needs sortable, facets need facetable, full-text needs searchable, returned in results needs retrievable. Autocomplete needs a suggester.

Check yourself

A query with $orderby=price desc fails. What is the likely cause?

The price field is not marked sortable.

Why use a language analyzer instead of the standard analyzer?

It understands the language's word forms, so different inflections such as 'run' and 'running' match, improving recall.
