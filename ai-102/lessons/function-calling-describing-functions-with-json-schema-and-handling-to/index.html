Function calling: describing functions with JSON schema and handling tool calls in code

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

Function calling (also called tool calling) is the mechanism that lets a language model use your code. The model never runs anything itself. You describe the functions it may use; when it decides one would help, it returns a structured request naming the function and its arguments, your code runs the function, and you send the result back so the model can continue. This works both in plain chat completions and inside Agent Service.

Each function is described with a name, a description and parameters written as JSON schema: an object with properties, their types, descriptions, allowed values (enum) and which are required. The model reads these descriptions to decide when to call the function and how to fill the arguments, so clear descriptions are essential.

{"type": "function", "function": {
  "name": "get_order_status",
  "description": "Look up the shipping status of a customer order by its order number.",
  "parameters": {"type": "object",
    "properties": {"order_id": {"type": "string", "description": "Order number, for example ORD-1234"}},
    "required": ["order_id"]}}}

In chat completions you pass the list in the tools parameter. If the model wants a function, the response has finish_reason tool_calls and the assistant message contains tool_calls, each with an ID, the function name and arguments as a JSON string. Your code parses the arguments, runs the function, then appends the assistant message and a tool role message with the matching tool_call_id and the result, and calls the model again. The model may request several calls at once (parallel tool calls) or chain calls across rounds. tool_choice can let the model decide (auto), force a specific function, or disable tools.

In Agent Service the same idea appears as a run in requires_action status. The run's required action lists tool calls; you run them and submit tool outputs with their IDs, and the run resumes. The SDKs can also call Python functions automatically if you register them.

Treat arguments as untrusted input. The model can produce wrong or malicious values, especially if the user tries to manipulate it, so validate types and ranges, check that the user is allowed to do what is asked, and require confirmation for actions such as payments or deletions. Structured outputs (strict schema mode) can guarantee arguments match the schema, but they cannot guarantee the values are sensible.

Key terms

Function calling
A model feature that returns a structured request to call a described function with arguments, which the app executes.
JSON schema
A standard for describing the structure, types and required fields of JSON data, used for function parameters.
tool_call_id
The identifier linking a tool result message to the model's specific tool call request.
tool_choice
A parameter that lets the model choose tools automatically, forces a specific one or disables them.
Real-world example

A user asks a store bot 'Where is my order ORD-5521?'. The model returns a tool call to get_order_status with order_id ORD-5521. The app checks the order belongs to the signed-in user, calls the order API, returns 'shipped, arriving Thursday' as the tool message, and the model writes a friendly reply.

Exam tip: The model only proposes calls; your code executes them and must send results back with the matching tool call ID. Descriptions drive which function the model chooses.

Check yourself

What does finish_reason tool_calls mean?

The model wants the app to run one or more functions; the arguments are in the assistant message's tool_calls.

Why should you validate function arguments from the model?

They are generated text and can be wrong or manipulated, so they must be checked like any untrusted input before acting.
