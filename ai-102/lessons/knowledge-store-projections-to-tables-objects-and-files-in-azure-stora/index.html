Knowledge store: projections to tables, objects and files in Azure Storage

▶ Watch the overview video

Last reviewed September 25, 2026

AI enrichment produces valuable data: entities, key phrases, sentiment, OCR text, image tags. A search index is built for queries, not for analytics, data science or other applications. A knowledge store saves the enriched output of a skillset into Azure Storage so other tools can use it, independent of the index.

You define a knowledge store in the skillset with a connection to a storage account (a connection string or managed identity) and one or more projections. Projections describe what data to save and in what shape. There are three kinds. Table projections write rows to Azure Table Storage, ideal for analysis in Power BI or other tools that expect tabular data; you can project related tables, such as a Documents table and a KeyPhrases table with a key linking each phrase to its document. Object projections write JSON documents to Blob Storage, preserving hierarchical structure, useful for data science pipelines or loading into other databases. File projections write binary files, usually the normalized images extracted during document cracking, to Blob Storage.

Projections take their data from the enrichment tree. Because the tree can be complex, you often use the Shaper skill to build a custom shape first, a single object with exactly the fields you want, and project that. Alternatively, inline shaping defines the shape inside the projection itself. Each projection names its source path, such as /document/projectionShape, and a table name or container.

Projection groups control relationships. Projections inside the same group share a generated key, so rows in related tables can be joined back together (for example a document row and its entity rows). Projections in different groups are independent copies with no link, which is useful when different consumers want different shapes of the same data.

"knowledgeStore": { "storageConnectionString": "<connection>",
  "projections": [ { "tables": [
      { "tableName": "Docs", "source": "/document/projectionShape" },
      { "tableName": "KeyPhrases", "source": "/document/projectionShape/keyPhrases/*" } ],
    "objects": [ { "storageContainer": "enriched", "source": "/document/projectionShape" } ],
    "files": [] } ] }

The knowledge store is written when the indexer runs, whether or not you also populate an index. Storage Browser in the portal or Storage Explorer lets you inspect the tables and blobs.

Key terms

Knowledge store
Azure Storage output of a skillset's enriched data, saved for uses beyond search.
Table projection
A projection that writes enriched data as rows in Azure Table Storage.
Object projection
A projection that writes enriched data as JSON documents in Blob Storage.
Shaper skill
A utility skill that builds a custom data shape from the enrichment tree for projection.
Real-world example

A market research firm enriches 100,000 survey responses with sentiment and key phrases. A Shaper skill builds a response shape, table projections in one group write Responses and KeyPhrases tables linked by key, and analysts build a Power BI report of top complaint phrases by region, while the same indexer also fills the search index.

Exam tip: Analytics in Power BI: table projections. Hierarchical JSON for other systems: object projections. Extracted images: file projections. Related tables that must join: same projection group.

Check yourself

Which projection type would you use to save normalized images extracted from PDFs?

File projections, which write binary files such as images to Blob Storage.

Why put table projections in the same projection group?

So they share generated keys and related rows can be joined back together.
