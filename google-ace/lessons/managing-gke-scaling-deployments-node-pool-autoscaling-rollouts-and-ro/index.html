Managing GKE: scaling Deployments, node pool autoscaling, rollouts and rollbacks, and cluster upgrades

▶ Watch the overview video

Last reviewed September 25, 2026

Running GKE means managing two layers of capacity: pods and nodes. Keep them straight, because exam distractors mix them up.

At the pod layer, you scale a Deployment manually with kubectl scale deployment/web --replicas=8, or automatically with a Horizontal Pod Autoscaler (HPA), for example kubectl autoscale deployment web --cpu-percent=60 --min=2 --max=20. The HPA changes the number of pod replicas based on CPU, memory or custom metrics. The Vertical Pod Autoscaler recommends or sets pod CPU and memory requests instead of the replica count.

At the node layer in a Standard cluster, the cluster autoscaler adds nodes when pods are Pending because no node has room for them, and removes underused nodes. You enable it per node pool: gcloud container clusters update prod --enable-autoscaling --node-pool=default-pool --min-nodes=1 --max-nodes=10 --region=us-central1. You can also resize a pool manually with gcloud container clusters resize. Node auto-provisioning can create new node pools automatically. In Autopilot, Google handles all node scaling for you.

Updating an app is a rollout. Change the image with kubectl set image deployment/web web=REPO/web:2.0 or by applying new YAML, and Kubernetes creates a new ReplicaSet and shifts pods gradually according to the Deployment's maxSurge and maxUnavailable. Watch it with kubectl rollout status deployment/web, list past versions with kubectl rollout history, and if the new version misbehaves, kubectl rollout undo deployment/web returns to the previous revision.

Clusters themselves need upgrades. Google upgrades the control plane automatically, and nodes are upgraded automatically when node auto-upgrade is on, which is the default and required in Autopilot. Release channels (Rapid, Regular, Stable) decide how quickly new versions arrive; maintenance windows and exclusions control when upgrades may happen. Surge upgrades replace nodes a few at a time, and PodDisruptionBudgets tell Kubernetes how many replicas of an app must stay available while nodes are drained. Node auto-repair recreates nodes that fail health checks.

To see what's happening, use kubectl get pods, kubectl describe for events such as scheduling failures, and the GKE pages in the console, which show workloads, logs and metrics from Cloud Logging and Cloud Monitoring.

Key terms

Horizontal Pod Autoscaler
Kubernetes object that changes a workload's number of pod replicas based on metrics.
Cluster autoscaler
GKE feature that adds or removes nodes in a node pool based on pending pods and utilization.
kubectl rollout undo
Reverts a Deployment to its previous revision.
Release channel
A GKE setting that controls how quickly a cluster receives new Kubernetes versions.
Real-world example

During a sale, a retailer's HPA scales the checkout Deployment from 4 to 30 pods. Several go Pending, so the cluster autoscaler adds nodes to the pool within minutes. After a buggy release later that day, the on-call engineer runs kubectl rollout undo deployment/checkout and error rates return to normal.

Exam tip: More pods: kubectl scale or HPA. More nodes: cluster autoscaler or resize the node pool. Bad release: kubectl rollout undo. Don't autoscale GKE's underlying instance groups directly.

Check yourself

Pods are stuck in Pending because nodes are full. Which feature adds nodes automatically?

The cluster autoscaler, enabled on the node pool (or Autopilot, which does it for you).

Which command shows a Deployment's previous revisions?

kubectl rollout history deployment/NAME.
