Compute Engine instances: machine families, custom machine types, images and Spot VMs

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

Creating a VM means choosing a zone, a machine type, a boot disk image and networking. From the CLI a basic example is gcloud compute instances create web-1 --zone=us-central1-a --machine-type=e2-medium --image-family=debian-12 --image-project=debian-cloud.

Machine types are grouped into families. General-purpose families (such as E2, N2, N2D, N4 and C3 in current generations) balance CPU and memory; E2 is cost-optimized and includes shared-core types such as e2-micro and e2-small. Compute-optimized families (such as C2 and H3) are for CPU-heavy work like high-performance computing. Memory-optimized families (M series) serve very large in-memory databases. Accelerator-optimized families (A and G series) attach GPUs for machine learning. Within a family, predefined types come in shapes like standard, highmem and highcpu. Exact family names change as new generations launch, so focus on the categories.

If no predefined type fits, create a custom machine type in families that support it (such as E2, N2 and N1) by choosing vCPUs and memory, for example --custom-cpu=6 --custom-memory=20GB. You pay for what you choose, which avoids wasting money on the next larger size. Memory per vCPU must stay within the family's ratio unless you enable extended memory.

Images supply the boot disk. Public images from Google and vendors cover Debian, Ubuntu, Rocky Linux, Windows Server and others; Container-Optimized OS is designed to run containers. Image families always point to the latest image in a series, which is why commands often use --image-family. You can also build custom images from your own disks.

Spot VMs are spare capacity at a steep discount. Google can stop (preempt) them at any time when it needs the capacity, giving about 30 seconds of notice, and there's no availability guarantee. They're ideal for fault-tolerant batch jobs, rendering, CI runners and stateless workers in managed instance groups, and a poor fit for databases or anything that can't be interrupted. Preemptible VMs are the older version, limited to 24 hours of runtime. For steady workloads, committed use discounts and sustained use discounts reduce the cost of regular VMs instead.

Key terms

Machine family
A group of machine types optimized for a workload class, such as general-purpose or memory-optimized.
Custom machine type
A VM shape where you choose the number of vCPUs and amount of memory.
Image family
A name that always resolves to the newest image in a series, such as debian-12.
Spot VM
A discounted VM that Google can preempt at any time when it needs the capacity.
Real-world example

An animation studio renders frames overnight on 200 Spot VMs in a managed instance group. When some are preempted, the group recreates them and the job queue hands the unfinished frames to other workers, cutting the rendering bill substantially compared with regular VMs.

Exam tip: 'Can be interrupted' plus 'lowest cost' means Spot VMs. 'Needs an unusual CPU-to-memory ratio' means a custom machine type. Spot VMs are not a fit for databases.

Check yourself

What happens to a Spot VM when Google needs the capacity back?

It's preempted (stopped or deleted, depending on its setting) after a short notice period.

Why use --image-family instead of a specific image name?

The family always resolves to the latest non-deprecated image, so you get current patches.
