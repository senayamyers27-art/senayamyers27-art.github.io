Encryption: Google default encryption, Cloud KMS customer-managed keys and customer-supplied keys

▶ Watch the overview video

Last reviewed September 25, 2026

All data stored in Google Cloud is encrypted at rest by default, with no action on your part. Google uses envelope encryption: data is encrypted with data encryption keys, which are themselves encrypted with key encryption keys held in Google's internal key management systems. Data in transit between Google data centers and to Google services is also encrypted. For many workloads, this default encryption with Google-owned and Google-managed keys is enough.

Some organizations must control the keys themselves, for compliance or to be able to cut off access to data. Customer-managed encryption keys (CMEK) let you create key rings and keys in Cloud Key Management Service (Cloud KMS) and tell services such as Cloud Storage, Compute Engine disks, BigQuery, Cloud SQL and GKE to use them. Google still performs the encryption, but you control the key's lifecycle: rotation schedule, enabling and disabling versions, destroying versions, and IAM on the key. If you disable the key, the service can't decrypt the data. Each service uses a service agent that needs the Cloud KMS CryptoKey Encrypter/Decrypter role on the key.

Cloud KMS keys can be protected in software, in hardware security modules (Cloud HSM, validated to FIPS 140-2 Level 3), or kept outside Google in a supported external key manager (Cloud External Key Manager). Key usage is recorded in Cloud Audit Logs. Destroying a key version is scheduled after a waiting period, to protect against mistakes; once destroyed, data encrypted with it can't be recovered.

Customer-supplied encryption keys (CSEK) are supported by a few services, notably Cloud Storage and Compute Engine disks. You generate the key yourself and supply it with each request; Google uses it in memory and doesn't store it. If you lose the key, Google can't recover your data. CSEK gives maximum control but adds operational burden, which is why CMEK is the usual answer.

Finally, client-side encryption means you encrypt data before sending it to Google Cloud, so Google only ever sees ciphertext. This is your responsibility entirely and is independent of the server-side options.

Key terms

Default encryption
Automatic encryption at rest of all data with Google-managed keys.
CMEK
Customer-managed encryption keys in Cloud KMS that you control and Google services use.
CSEK
Customer-supplied encryption keys that you provide with each request and Google doesn't store.
Key ring
A grouping of Cloud KMS keys in one location.
Real-world example

A healthcare company must be able to make patient data unreadable on demand. It creates a key in Cloud KMS, sets it as the default CMEK on its records bucket and grants the Cloud Storage service agent Encrypter/Decrypter on the key. Security can disable the key to block all decryption instantly.

Exam tip: 'Control rotation and be able to disable the key, but Google does the encryption' is CMEK. 'Google must never store the key' is CSEK. Nothing required means default encryption.

Check yourself

What permission does a service need to use a CMEK key?

Its service agent needs the Cloud KMS CryptoKey Encrypter/Decrypter role on the key.

What happens if you lose a customer-supplied key?

The data encrypted with it can't be recovered, because Google doesn't store the key.
