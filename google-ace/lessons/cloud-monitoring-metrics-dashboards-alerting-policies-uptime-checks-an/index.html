Cloud Monitoring: metrics, dashboards, alerting policies, uptime checks and the Ops Agent

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

Cloud Monitoring collects metrics, which are numeric measurements over time, from Google Cloud services, applications and agents. Many metrics are built in: Compute Engine CPU utilization, network bytes and disk operations; Cloud Run request counts and latencies; Cloud SQL connections; load balancer response codes. A metrics scope lets one project view metrics from several projects, so you can monitor a whole environment from one place.

Some important VM metrics come from inside the guest OS and aren't collected by default, notably memory utilization and disk space used. To get them, install the Ops Agent on the VM. It collects system and application metrics and also sends logs to Cloud Logging, replacing the older separate Monitoring and Logging agents. You can install it on individual VMs or on fleets with an agent policy.

Dashboards visualize metrics. Google provides predefined dashboards for many services, and you can build custom ones with charts, filters and grouping. Metrics Explorer lets you query any metric quickly, for example average CPU grouped by instance.

Alerting policies notify people when something needs attention. A policy has one or more conditions, such as a metric threshold (CPU above 80% for 5 minutes), metric absence (no data), or a log match, and one or more notification channels such as email, SMS, the mobile app, Slack, PagerDuty, webhooks or Pub/Sub. When the condition is met, an incident opens and notifications go out; documentation in the policy tells responders what to do.

Uptime checks test availability from outside. They send HTTP, HTTPS or TCP requests to a public URL, IP or resource from several locations around the world at a set interval, and can check the response content. Combined with an alerting policy, they tell you when users can't reach your site. For private endpoints, uptime checks can target internal resources through a supported configuration.

Service monitoring builds on these with service-level objectives (SLOs), such as 99.9% of requests under 300 ms, and burn-rate alerts that warn when you're using up your error budget too fast.

Key terms

Ops Agent
Google's agent that collects guest OS metrics, such as memory and disk usage, and logs from VMs.
Alerting policy
Conditions plus notification channels that open incidents when a metric or log condition is met.
Uptime check
A probe of a URL, IP or resource from multiple global locations to test availability.
Metrics scope
The set of projects whose metrics a scoping project can view together.
Real-world example

An operations team installs the Ops Agent on all VMs through an agent policy, adds a dashboard showing CPU, memory and disk per service, creates an alert when disk usage exceeds 85%, and adds an uptime check on the www.example.com home page that pages the on-call engineer if two regions fail.

Exam tip: Memory and disk-space metrics need the Ops Agent. 'Notify when a metric crosses a threshold' is an alerting policy. 'Is my website reachable from around the world' is an uptime check.

Check yourself

Why don't you see memory utilization for a new VM by default?

Memory is measured inside the guest OS, so it requires the Ops Agent.

What are the two main parts of an alerting policy?

Conditions that define when to alert, and notification channels that define who is told.
