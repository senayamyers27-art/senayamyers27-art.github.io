Cloud Logging: Logs Explorer, log-based metrics, log buckets and sinks

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

Cloud Logging collects log entries from Google Cloud services, audit logs, VMs running the Ops Agent, GKE containers, Cloud Run and your applications (anything written to standard output on serverless platforms, or through client libraries). Each entry has a timestamp, severity, a resource (such as a VM or Cloud Run revision), a log name, and a payload that is either text or structured JSON.

Logs Explorer is where you search. You write queries in the Logging query language, for example resource.type="gce_instance" severity>=ERROR or textPayload:"payment declined", and narrow by time range. From the CLI, gcloud logging read 'severity>=ERROR' --limit=20 returns entries. Log Analytics lets you query logs with SQL when a log bucket is upgraded for it.

Log-based metrics turn log entries into Cloud Monitoring metrics. A counter metric counts entries matching a filter, such as how many times 'payment declined' appears; a distribution metric extracts numeric values, such as latencies, from entries. You can chart them and create alerting policies on them.

Routing and storage are controlled by the Log Router. Every project has sinks that decide where each log entry goes. By default, the _Required bucket stores Admin Activity, System Event and some other audit logs for 400 days and can't be changed, and the _Default bucket stores most other logs for 30 days by default, which you can change. You can create your own log buckets with custom retention, including in other regions, and exclusion filters drop noisy logs you don't want to pay to store.

User-defined sinks send copies of matching logs to other destinations: a Cloud Storage bucket for cheap long-term archiving, a BigQuery dataset for SQL analysis, a Pub/Sub topic for streaming to third-party tools such as a SIEM, a log bucket in another project, or a Google Cloud project. When you create a sink, Logging gives it a writer identity (a service account) that you must grant permission on the destination, for example BigQuery Data Editor on the dataset. Aggregated sinks, created on an organization or folder with --include-children, route logs from all projects beneath it, which is the standard way to centralize security logs.

Key terms

Logs Explorer
The console tool for querying and viewing log entries.
Log-based metric
A Cloud Monitoring metric derived from log entries that match a filter.
Sink
A Log Router rule that sends matching log entries to a destination such as BigQuery or Pub/Sub.
Aggregated sink
A sink on an organization or folder that routes logs from all child projects.
Real-world example

A company creates an aggregated sink on its organization that sends all audit logs to a BigQuery dataset in a security project, and another that streams them to Pub/Sub for its SIEM. Developers add a counter log-based metric for 'payment declined' and alert when it spikes.

Exam tip: Count or chart something that appears in logs: log-based metric. Send logs somewhere else: sink (and grant its writer identity access). All projects in the organization: aggregated sink with include-children.

Check yourself

How long are logs kept in the _Default bucket by default?

30 days, which you can change.

What must you do after creating a sink to BigQuery?

Grant the sink's writer identity permission to write to the dataset.
