Service accounts: creating them, granting roles, attaching them to resources, and default service accounts

▶ Watch the overview video

Last reviewed September 25, 2026

A service account is an identity for a workload, not a person. Applications running on VMs, GKE, Cloud Run or Cloud Run functions use service accounts to call Google APIs. A service account has an email address like app-sa@my-proj.iam.gserviceaccount.com. It is both a principal (it can be granted roles) and a resource (people can be granted roles on it, such as permission to use it).

Create one with gcloud iam service-accounts create app-sa --display-name="App", then grant it roles on the resources it needs, for example gcloud storage buckets add-iam-policy-binding gs://uploads --member=serviceAccount:app-sa@my-proj.iam.gserviceaccount.com --role=roles/storage.objectCreator. Create a separate service account for each application or component so each has only its own permissions and audit logs show which workload did what.

Attaching a service account to a resource is how the workload gets credentials. For a VM, use gcloud compute instances create ... --service-account=app-sa@... --scopes=cloud-platform; code on the VM then gets short-lived access tokens from the metadata server automatically, with no keys to manage. Cloud Run services and functions take --service-account at deployment. Access scopes are a legacy VM mechanism that limits which APIs the VM's credentials can reach; Google's recommendation is to set the cloud-platform scope and control access with IAM roles.

To attach a service account, you need the Service Account User role (roles/iam.serviceAccountUser) on that service account, because running code as it lets you use its permissions. This prevents someone with only permission to create VMs from borrowing a powerful service account. Service Account Admin lets you create and manage service accounts, which is a separate power.

Some services create default service accounts, such as the Compute Engine default service account, PROJECT_NUMBER-compute@developer.gserviceaccount.com. Depending on your organization's settings, it may be granted the Editor role automatically, and VMs use it unless you pick another. Best practice is to create dedicated, least-privilege service accounts instead, and many organizations use an organization policy to stop the automatic Editor grant. Don't confuse these with service agents, which Google uses to run services on your behalf.

Key terms

Service account
An identity for applications and workloads, identified by an email address.
Service Account User
A role that allows attaching or acting as a service account.
Metadata server
An endpoint on each VM that provides short-lived tokens for the attached service account.
Compute Engine default service account
An automatically created service account that VMs use unless another is specified.
Real-world example

A team deploys an invoice service to Cloud Run with its own service account, invoice-sa, which has only Secret Manager Secret Accessor on one secret and Cloud SQL Client on the project. When the logs show an unexpected read, they know exactly which service made it.

Exam tip: Workloads should use attached, dedicated service accounts, not keys and not the default Editor account. Permission errors when attaching a service account mean the user lacks Service Account User on it.

Check yourself

Why does attaching a service account to a VM require Service Account User?

Because the VM's code can then use the service account's permissions, which is a form of acting as it.

How does code on a VM get credentials for its attached service account?

From the metadata server, which issues short-lived access tokens automatically.
