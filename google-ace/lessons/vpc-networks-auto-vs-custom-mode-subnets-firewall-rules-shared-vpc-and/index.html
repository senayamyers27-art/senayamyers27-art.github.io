VPC networks: auto vs custom mode, subnets, firewall rules, Shared VPC and VPC Network Peering

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

A Virtual Private Cloud (VPC) network in Google Cloud is global: one VPC can have subnets in many regions, and VMs in different regions of the same VPC can talk over internal IPs without extra setup. Subnets are regional and each has a primary IPv4 range, plus optional secondary ranges used for things like GKE pod and service IPs.

When you create a VPC you choose a subnet mode. In auto mode, Google creates one subnet in every region automatically from the 10.128.0.0/9 block, and adds new regions as they launch. The default network that new projects often have is an auto mode VPC with permissive firewall rules. In custom mode, you create only the subnets you want with the ranges you choose. Custom mode is recommended for production because it avoids overlapping with on-premises or other networks you might connect later. You can convert an auto mode network to custom, but not back.

VPC firewall rules are stateful and apply to VM instances. Each rule has a direction (ingress or egress), an action (allow or deny), a priority from 0 to 65535 where lower numbers win, protocols and ports, a source or destination range, and targets: all instances, instances with a network tag, or instances running as a service account. Every VPC has implied rules that deny all ingress and allow all egress. For example: gcloud compute firewall-rules create allow-web --network=prod --direction=INGRESS --action=ALLOW --rules=tcp:80,tcp:443 --source-ranges=0.0.0.0/0 --target-tags=web. Hierarchical firewall policies at the organization or folder level and network firewall policies add central control.

Shared VPC lets a host project own a VPC network while service projects create resources in its subnets. A central network team manages subnets, routes and firewalls in the host project, and app teams get Compute Network User on specific subnets. This is the answer for centralized network control across many projects in one organization.

VPC Network Peering connects two VPC networks, in the same or different projects or organizations, so they exchange internal routes privately. Each side remains administered separately, subnet ranges must not overlap, and peering isn't transitive: if A peers with B and B with C, A can't reach C through B.

Key terms

Custom mode VPC
A VPC where you create subnets and choose their ranges yourself.
Firewall rule priority
A number from 0 to 65535 where the lowest-numbered matching rule takes effect.
Shared VPC
A model where service projects use subnets from a centrally managed host project's VPC.
VPC Network Peering
A private, non-transitive connection between two VPC networks that exchanges subnet routes.
Real-world example

A company builds a custom mode VPC in a Shared VPC host project with subnets in us-east1 and europe-west1 that don't overlap its data center ranges. Five app teams attach their service projects, and a firewall rule allows tcp:443 only to VMs with the tag web.

Exam tip: Central team manages the network for many projects: Shared VPC. Connecting two separately managed VPCs: peering. Peering isn't transitive and ranges can't overlap. Lower priority numbers win.

Check yourself

Is a VPC network regional or global in Google Cloud?

Global. Its subnets are regional.

Which implied firewall rules does every VPC have?

Deny all ingress and allow all egress, at the lowest priority.
