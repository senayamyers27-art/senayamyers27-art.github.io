Identity-Aware Proxy and OS Login for secure administrative access

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

Identity-Aware Proxy (IAP) implements a zero-trust access model: instead of trusting anyone on the right network, it checks who the user is (and optionally their device and context) on every request, and only then lets the request through to the application or VM. It removes the need for VPNs and bastion hosts for many access patterns.

For web applications, IAP sits in front of an external Application Load Balancer's backend service, App Engine, or Cloud Run. Users sign in with their Google identity, and IAP allows the request only if they have the IAP-secured Web App User role on the app. The app still has to accept traffic only from the load balancer, typically with firewall rules, so users can't bypass IAP. With Access Context Manager you can add context-aware conditions, such as requiring a company-managed device or a certain IP range.

For administrative access to VMs, IAP TCP forwarding tunnels SSH, RDP or other TCP connections to VMs that have no external IP address. Users need the IAP-secured Tunnel User role, and firewall rules must allow the IAP range 35.235.240.0/20 to the port. Commands like gcloud compute ssh vm-1 --tunnel-through-iap or gcloud compute start-iap-tunnel vm-1 3389 --local-host-port=localhost:3389 set up the tunnel.

OS Login complements IAP by controlling who can log in to Linux VMs once connected. It links Linux user accounts to Google identities and grants access through IAM: Compute OS Login for normal users, Compute OS Admin Login for users who need sudo. OS Login can enforce two-step verification, and because it uses IAM, access is removed as soon as a role is revoked or an account is disabled. That's much easier to govern than SSH keys scattered in project metadata. For users outside the organization, the Compute OS Login External User role is also needed at the organization level.

Together they give a clean model: no public IPs on VMs, IAP decides who can reach the VM, OS Login decides who can log in and with what privileges, and audit logs record it all.

Key terms

Identity-Aware Proxy
A service that authorizes each request based on user identity and context before it reaches an app or VM.
IAP-secured Web App User
The role that allows a user through IAP to a protected web app.
IAP-secured Tunnel User
The role that allows TCP forwarding through IAP to VMs.
Compute OS Admin Login
The OS Login role that grants login with sudo privileges.
Real-world example

A company retires its VPN for an internal HR app by putting it behind an external Application Load Balancer with IAP enabled, granting IAP-secured Web App User to the hr-staff group, and requiring company-managed devices through an access level. Admins reach the app's VMs through IAP tunnels with OS Login.

Exam tip: Identity-based access to an internal web app without VPN: IAP. SSH without external IPs: IAP TCP forwarding. SSH access controlled by IAM: OS Login.

Check yourself

Which role lets a user run sudo on a VM using OS Login?

Compute OS Admin Login.

What stops users from bypassing IAP to reach the backend directly?

Firewall rules that allow traffic only from the load balancer and IAP ranges, and no public IPs on the backends.
