Cloud Audit Logs: Admin Activity, Data Access, System Event and Policy Denied logs

▶ Watch the overview video

Last reviewed September 25, 2026

Cloud Audit Logs answer the question 'who did what, where and when' for Google Cloud resources. They're written to Cloud Logging and each entry records the principal (user or service account), the method called (such as v1.compute.instances.delete), the resource, the time, the caller's IP address and whether the request succeeded. They're essential for security investigations, compliance and troubleshooting.

There are four types. Admin Activity audit logs record API calls that modify configuration or metadata: creating or deleting a VM, changing an IAM policy, updating a bucket's settings. They're always enabled, can't be turned off, and are free. System Event audit logs record actions taken by Google systems rather than users, such as live migration of a VM or a managed instance group's autohealing; they are also always on and free.

Data Access audit logs record API calls that read configuration or metadata (ADMIN_READ) and calls that read or write user-provided data (DATA_READ and DATA_WRITE), such as reading an object in Cloud Storage or querying a table. They can be very large, so they're disabled by default for most services, and you pay for the log volume beyond free allotments. BigQuery is the notable exception, where Data Access logs are enabled by default. You enable them per service, for a project, folder or organization, in the console under IAM and admin > Audit logs, or in the IAM policy's auditConfigs section. You can exempt specific principals.

Policy Denied audit logs are written when Google Cloud denies access because of a security policy, such as a VPC Service Controls perimeter. They're generated by default, and you can exclude them if needed.

To view audit logs you need the right role: Logs Viewer (roles/logging.viewer) can see Admin Activity and System Event logs, while Data Access logs are considered sensitive and require Private Logs Viewer (roles/logging.privateLogViewer). In Logs Explorer, filter on logName containing cloudaudit.googleapis.com, or use protoPayload.methodName and protoPayload.authenticationInfo.principalEmail.

Key terms

Admin Activity audit logs
Always-on logs of API calls that change resource configuration or metadata.
Data Access audit logs
Logs of reads of configuration and reads or writes of user data, off by default for most services.
System Event audit logs
Logs of actions taken by Google systems, such as live migration.
Private Logs Viewer
The role needed to view Data Access audit logs.
Real-world example

After a production VM disappears, an engineer filters Admin Activity logs for methodName containing instances.delete and finds the principal and time within a minute. To meet a new regulation, the company then enables DATA_READ audit logs for Cloud Storage on its patient-records project only, keeping log costs under control.

Exam tip: Who changed or deleted something: Admin Activity (always on). Who read data: Data Access, which must be enabled first (except BigQuery). Viewing Data Access logs needs Private Logs Viewer.

Check yourself

Can you disable Admin Activity audit logs?

No. They're always written and can't be turned off.

Why are Data Access logs disabled by default for most services?

They can be very high volume and add cost, so you enable them where needed.
