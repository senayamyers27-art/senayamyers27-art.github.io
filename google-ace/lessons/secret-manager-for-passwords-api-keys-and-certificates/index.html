Google Cloud Associate Cloud Engineer Associate Cloud Engineer · Domain 4: Configuring access and security

Secret Manager for passwords, API keys and certificates

▶ Watch the overview video

Last reviewed September 25, 2026

Applications need secrets: database passwords, third-party API keys, TLS private keys and tokens. Putting them in source code, container images, plain environment variables in deployment files or configuration buckets is risky, because anyone who can read those places can read the secret, and it's hard to rotate them. Secret Manager is Google Cloud's managed service for storing secrets securely.

A secret in Secret Manager is a named container, and the actual values are stored as versions. When you rotate a password you add a new version and, once everything uses it, disable or destroy the old one. Applications can request a specific version number or latest. Create a secret with gcloud secrets create db-password --replication-policy=automatic and add a value with gcloud secrets versions add db-password --data-file=pw.txt. Replication can be automatic (Google chooses locations) or user-managed (you choose regions, for data residency), and secrets are encrypted by default, with optional CMEK.

Access is controlled by IAM. The key role is Secret Manager Secret Accessor (roles/secretmanager.secretAccessor), which allows reading secret values; grant it to the specific service account of the workload, on the specific secret, not the whole project. Secret Manager Admin manages secrets but you should grant it only to administrators. Every access is recorded in Cloud Audit Logs (Data Access logs, when enabled), so you can see which identity read a secret.

Integrations make secrets easy to use. Cloud Run and Cloud Run functions can mount a secret as a file or expose it as an environment variable at deployment, for example gcloud run deploy api --set-secrets=DB_PASSWORD=db-password:latest. GKE can read secrets through the Secret Manager add-on or the Secrets Store CSI driver, and any application can call the Secret Manager API with client libraries. Rotation schedules can send Pub/Sub notifications to trigger your own rotation code, and secrets can have expiration times.

Secret Manager is for application secrets. It's different from Cloud KMS, which manages encryption keys used to encrypt data but never gives you the raw key material of a software or HSM key.

Key terms

Secret
A named container in Secret Manager that holds versions of a sensitive value.
Secret version
An immutable value of a secret; new versions are added to rotate.
Secret Manager Secret Accessor
The IAM role that allows reading a secret's value.
Replication policy
Whether a secret's data is replicated automatically or only to regions you choose.
Real-world example

A payments team stores its processor API key in Secret Manager, grants Secret Accessor on that one secret to the checkout service's service account, and deploys to Cloud Run with --set-secrets. When the processor rotates the key, the team adds a new version, and the next deployment picks up latest.

Exam tip: Passwords and API keys belong in Secret Manager with Secret Accessor granted to the workload's service account. Cloud KMS is for encryption keys, not for storing app passwords.

Check yourself

How do you rotate a secret in Secret Manager?

Add a new version, move applications to it, then disable or destroy the old version.

Which role should a Cloud Run service's service account have to read a secret?

Secret Manager Secret Accessor on that specific secret.
