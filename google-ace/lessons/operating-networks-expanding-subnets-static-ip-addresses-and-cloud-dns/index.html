Operating networks: expanding subnets, static IP addresses and Cloud DNS

▶ Watch the overview video

Last reviewed September 25, 2026

Networks change as workloads grow, and the exam expects you to know which changes can be made in place.

Subnet ranges can be expanded but not shrunk. If 10.10.0.0/24 is running out of addresses, gcloud compute networks subnets expand-ip-range app-subnet --region=us-central1 --prefix-length=22 grows it to 10.10.0.0/22 without affecting existing VMs, as long as the larger range doesn't overlap other subnets or peered networks. Each subnet reserves four addresses in its primary range (network, gateway, second-to-last and broadcast), so a /24 gives 252 usable addresses. You can also add secondary ranges, used for alias IPs such as GKE pods, and add new subnets in any region.

IP addresses come in two lifetimes. Ephemeral external IPs are assigned when a VM starts and can change after it stops. Static external IPs are reserved to your project until you release them. Reserve one with gcloud compute addresses create web-ip --region=us-central1 (regional, for VMs and regional load balancers) or --global (for global load balancers), or promote the ephemeral IP a VM already has so it never changes. Internal IPs can also be reserved as static so a server keeps the same private address. Reserved static external IPs that aren't attached to anything are billed, so release ones you don't use.

Cloud DNS is a managed, authoritative DNS service. A public zone serves records for a domain on the internet, such as example.com; after creating it you update your registrar to use the name servers Cloud DNS assigns. A private zone answers only for queries from the VPC networks you authorize, which is handy for internal names like db.corp.internal. You manage records such as A, AAAA, CNAME, MX and TXT in the console or with gcloud dns record-sets create. DNS forwarding zones and server policies connect Cloud DNS with on-premises DNS in hybrid networks, and DNSSEC can be enabled for public zones.

VMs also get automatic internal DNS names of the form VM_NAME.ZONE.c.PROJECT_ID.internal, so other VMs in the same network can reach them by name without managing records.

Key terms

expand-ip-range
The gcloud subcommand that enlarges a subnet's primary range in place.
Static external IP
A reserved public address that stays with your project until released.
Private DNS zone
A Cloud DNS zone visible only to authorized VPC networks.
Internal DNS
Automatic names that let VMs in a network reach each other by name.
Real-world example

A SaaS company's app subnet fills up, so they expand it from /24 to /22 during business hours with no downtime. They promote the ephemeral IP of their SFTP server to static so customers' allowlists keep working, and create a private Cloud DNS zone so services find the database at db.prod.internal.

Exam tip: Subnets grow, never shrink. A changing public IP is fixed by reserving or promoting a static address. Internal-only names: private DNS zone.

Check yourself

How many usable addresses does a /24 subnet provide in Google Cloud?

252, because four addresses in each primary range are reserved.

Do reserved static external IPs cost money when unused?

Yes. Unattached reserved addresses are billed, so release them.
