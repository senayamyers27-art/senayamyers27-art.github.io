Organization Policy Service: constraints such as resource locations and disabling service account key creation

▶ Watch the overview video

Last reviewed September 25, 2026

The Organization Policy Service gives administrators central guardrails. Where IAM decides who can act, an organization policy decides what configurations are allowed at all. Even a project Owner can't create a resource that an organization policy forbids. This makes organization policies the right answer whenever a requirement says something must never happen, 'even by administrators' or 'even by project owners'.

A policy is built from a constraint. Google provides many predefined constraints, and you can write custom constraints for some resource types. List constraints allow or deny a list of values; boolean constraints are simply on or off. Well-known examples include the resource locations constraint (gcp.resourceLocations), which restricts the regions where location-based resources can be created; iam.disableServiceAccountKeyCreation, which blocks new service account keys; compute.vmExternalIpAccess, which restricts which VMs may have external IPs; iam.allowedPolicyMemberDomains, which limits IAM grants to identities from your own domains (domain restricted sharing); and storage.publicAccessPrevention, which stops buckets from being made public.

You set policies on the organization, a folder or a project in the console (IAM and admin > Organization policies) or with gcloud org-policies set-policy policy.yaml. You need the Organization Policy Administrator role, which is granted at the organization level. Policies are inherited, and for list constraints a child can inherit the parent's policy, merge its own values with it, or replace it. Policies generally aren't retroactive: an existing VM with an external IP keeps it, but new ones are blocked.

Organization policies are often combined with IAM. For example, you might grant developers Compute Admin on their projects but use the external IP constraint so that none of their VMs can be exposed directly, and then give them IAP for SSH access. Because policies are evaluated when a resource is created or updated, they're easy to test: try to create a forbidden resource and read the error, which names the constraint.

Key terms

Constraint
A definition of a restriction on a Google Cloud service's behavior, such as allowed locations.
Organization Policy Administrator
The role that lets someone set organization policies; it is granted at the organization level.
Resource locations constraint
gcp.resourceLocations, which limits where location-based resources can be created.
Domain restricted sharing
A constraint that allows IAM grants only to identities from listed Cloud Identity or Workspace customers.
Real-world example

A bank must keep customer data in the EU. The cloud team sets the resource locations constraint on the EU-Customers folder to EU locations only. When an engineer with Owner on a project tries to create a bucket in us-central1, the request fails with an error naming the constraint.

Exam tip: Read the requirement: 'nobody, including owners' points to an organization policy; 'only this group may' points to IAM. Service account key creation, external IPs and allowed regions are classic organization policy questions.

Check yourself

Why doesn't a custom IAM role solve 'no one may create service account keys'?

Other roles, such as Owner, still include the permission. An organization policy applies to everyone regardless of role.

Does setting the external IP constraint remove IPs from existing VMs?

No. Constraints are checked when resources are created or changed; existing configurations generally aren't changed.
