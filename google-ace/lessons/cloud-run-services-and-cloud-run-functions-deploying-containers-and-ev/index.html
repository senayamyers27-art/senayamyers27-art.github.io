Cloud Run services and Cloud Run functions: deploying containers and event-driven code with Eventarc and Pub/Sub

▶ Watch the overview video

Last reviewed September 25, 2026

Cloud Run runs containers without servers or clusters. A container for a Cloud Run service must listen for HTTP requests on the port given in the PORT environment variable (8080 by default) and should be stateless, because instances can be started and stopped at any time. You deploy with gcloud run deploy web --image=us-docker.pkg.dev/my-proj/repo/web:1.0 --region=us-central1, or from source code with --source ., which builds the image with Cloud Build.

Each deployment creates an immutable revision. Cloud Run scales the number of container instances with traffic, from zero up to a maximum you can set, and each instance can handle multiple requests at once (concurrency). Every service gets an HTTPS URL. Access is controlled by IAM: allowing unauthenticated invocations grants the Cloud Run Invoker role to allUsers, which suits a public website; otherwise callers must present an identity token for a principal that has roles/run.invoker. Ingress settings can further restrict traffic to internal sources or a load balancer.

Cloud Run jobs are for work that runs to completion, such as a nightly data export, and can run many tasks in parallel. They're often triggered by Cloud Scheduler.

Cloud Run functions let you deploy just a function written in a supported language such as Node.js, Python, Go or Java. You deploy with gcloud functions deploy (or through the Cloud Run pages), and Google builds and runs it on Cloud Run. Functions are triggered either by HTTP requests or by events.

Events are delivered by Eventarc, which routes events from Google sources to Cloud Run services and functions. Sources include Cloud Storage (for example, an object being finalized after upload), Pub/Sub messages, and Cloud Audit Logs entries for many services. Pub/Sub is Google's messaging service: publishers send messages to a topic, and subscriptions deliver them to subscribers by pull or push, decoupling producers from consumers. A push subscription can send messages directly to a Cloud Run URL.

The trigger's service account needs permission to invoke the target, and a Cloud Run service needs its own service account (not the default one, ideally) with only the roles it requires, such as access to a bucket or a secret.

Key terms

Revision
An immutable snapshot of a Cloud Run service's image and configuration created on each deployment.
Concurrency
The maximum number of requests one Cloud Run instance handles at the same time.
Eventarc
A service that routes events from Google Cloud sources to Cloud Run services and functions.
Pub/Sub
A managed messaging service where publishers send messages to topics and subscribers receive them through subscriptions.
Real-world example

A photo app stores uploads in a bucket. An Eventarc trigger on the object finalized event invokes a Cloud Run function that creates a thumbnail and publishes a message to a Pub/Sub topic, which a separate Cloud Run service consumes to update the search index.

Exam tip: 'Run code when a file lands in a bucket' is an event-driven function via Eventarc. 'Only specific services may call it' means require authentication and grant Cloud Run Invoker to those identities.

Check yourself

What does allowing unauthenticated invocations actually do?

It grants the Cloud Run Invoker role to allUsers, making the service publicly callable.

What's the difference between a Cloud Run service and a Cloud Run job?

A service responds to requests and scales with traffic; a job runs tasks to completion and then stops.
