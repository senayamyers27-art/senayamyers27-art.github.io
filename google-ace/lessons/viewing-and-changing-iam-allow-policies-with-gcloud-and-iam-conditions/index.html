Viewing and changing IAM allow policies with gcloud, and IAM Conditions

▶ Watch the overview video

Last reviewed September 25, 2026

An allow policy is a JSON or YAML document attached to a resource. It contains a list of bindings, each with a role and a list of members, plus an etag and a version. Knowing its shape helps you read command output and exam scenarios.

To view a policy: gcloud projects get-iam-policy my-proj (or --format=json). Similar get-iam-policy commands exist for folders, organizations, buckets (gcloud storage buckets get-iam-policy gs://b), service accounts, and many other resources. The simplest way to change one binding is add-iam-policy-binding or remove-iam-policy-binding, which read, modify and write the policy for you.

For bulk changes you can download the policy, edit it, and upload it with gcloud projects set-iam-policy my-proj policy.json. Be careful: set-iam-policy replaces the entire policy with the file's contents, so if the file is stale or missing bindings you can remove access, even your own. The etag protects against concurrent edits: if someone changed the policy after you downloaded it, the upload is rejected and you must fetch it again.

IAM Conditions let a binding apply only when an expression in Common Expression Language (CEL) is true. Common uses are time-limited access, such as request.time < timestamp("2026-12-31T00:00:00Z"), and resource-based limits, such as allowing access only to resources whose name starts with a prefix or that carry a certain tag. Add one with --condition='expression=...,title=...' on add-iam-policy-binding. Conditions require policy version 3, and not every service or role supports every attribute, so check before relying on them. Basic roles can't be used with conditions.

Remember what an allow policy can't do: it can't remove access granted higher in the hierarchy. For that, Google Cloud offers IAM deny policies, which explicitly block specific permissions for specific principals and are evaluated before allow policies. Principal access boundary policies are another way to limit which resources principals can access.

Key terms

Binding
One role and the list of members that hold it in an allow policy.
etag
A version marker that prevents overwriting a policy someone else changed.
set-iam-policy
A command that replaces a resource's entire allow policy with a file's contents.
IAM Condition
A CEL expression that makes a role binding apply only in certain cases, such as before a date.
Real-world example

An auditor needs read access for two weeks. The admin runs add-iam-policy-binding with the Viewer role on the audit project and a condition that expires on the last day of the audit, so the access disappears automatically without anyone remembering to remove it.

Exam tip: For one change, use add- or remove-iam-policy-binding. set-iam-policy overwrites everything. Temporary access is an IAM Condition on request.time.

Check yourself

What happens if you run set-iam-policy with a file missing some bindings?

Those bindings are removed, because the whole policy is replaced.

Which IAM feature grants a role only until a certain date?

An IAM Condition using request.time in the binding.
