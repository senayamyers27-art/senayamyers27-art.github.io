Deploying workloads to GKE with kubectl: Deployments, Services and Ingress

▶ Watch the overview video

Last reviewed September 25, 2026

Before using kubectl on a GKE cluster, fetch credentials: gcloud container clusters get-credentials my-cluster --region=us-central1. This writes an entry to your kubeconfig so that kubectl talks to that cluster's API server using your Google identity. Access inside the cluster is controlled by IAM roles such as Kubernetes Engine Developer, and optionally Kubernetes RBAC.

A Deployment is the standard way to run a stateless app. It declares the container image, number of replicas and resource requests, and Kubernetes keeps that many pods running through a ReplicaSet. You can create one quickly with kubectl create deployment web --image=us-docker.pkg.dev/my-proj/repo/web:1.0, but in practice you write YAML and run kubectl apply -f web.yaml. Images typically come from Artifact Registry, and the nodes (or pods, with Workload Identity Federation) need permission to pull them.

Pods get new IP addresses whenever they're recreated, so you expose them with a Service, which gives a stable virtual IP and DNS name and load-balances across matching pods. Type ClusterIP (the default) is reachable only inside the cluster. Type NodePort opens a port on every node. Type LoadBalancer makes GKE create a Google Cloud passthrough Network Load Balancer with an external IP (or an internal one with an annotation). The quick way is kubectl expose deployment web --type=LoadBalancer --port=80 --target-port=8080, where port is what clients use and target-port is what the container listens on.

For HTTP(S) apps, an Ingress (or the newer Gateway API) routes traffic by host and path to different Services. On GKE, an Ingress creates an external Application Load Balancer, with support for Google-managed certificates and Cloud CDN. This is the answer when you need one IP for several services with URL-based routing.

Other workload objects appear on the exam too: StatefulSets for apps that need stable identities and persistent volumes, DaemonSets to run one pod on every node (such as a log agent), Jobs and CronJobs for batch tasks, and ConfigMaps and Secrets for configuration. kubectl get pods, kubectl describe pod NAME and kubectl logs NAME are your first troubleshooting commands.

Key terms

Deployment
A Kubernetes object that keeps a set number of identical pod replicas running and handles rolling updates.
Service
A stable IP and DNS name that load-balances traffic to a set of pods.
LoadBalancer Service
A Service type that provisions a Google Cloud network load balancer with an external or internal IP.
Ingress
A Kubernetes object that routes HTTP(S) traffic by host and path; on GKE it creates an Application Load Balancer.
Real-world example

A team deploys frontend and api Deployments, each with a ClusterIP Service. An Ingress routes shop.example.com/ to frontend and shop.example.com/api to api through one external Application Load Balancer with a Google-managed certificate.

Exam tip: Internal only: ClusterIP. One external IP for one service: LoadBalancer. URL-based routing to several services: Ingress. Don't forget get-credentials before kubectl works.

Check yourself

What does gcloud container clusters get-credentials do?

It adds the cluster's endpoint and auth settings to your kubeconfig so kubectl can use it.

In kubectl expose, what is the difference between --port and --target-port?

--port is the port the Service listens on; --target-port is the container port traffic is sent to.
