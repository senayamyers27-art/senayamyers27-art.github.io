Managing Compute Engine VMs: start, stop, resize, SSH with OS Login and IAP TCP forwarding

▶ Watch the overview video

Last reviewed September 25, 2026

Day-to-day VM management is mostly a handful of gcloud commands. gcloud compute instances list shows VMs with their zones, status and IPs. gcloud compute instances stop web-1 --zone=us-central1-a and start stop and start a VM; a stopped VM doesn't incur charges for vCPUs and memory, but you still pay for its disks and any reserved static IPs. suspend saves memory state to disk and resume brings it back. reset is a hard restart, like pulling the power cord.

To change a VM's machine type, you must stop it first: gcloud compute instances set-machine-type web-1 --machine-type=e2-standard-4, then start it again. Disks can be enlarged while the VM runs (gcloud compute disks resize), after which you grow the file system inside the OS. You can also add labels, metadata such as startup scripts, and network tags without recreating the VM. Moving a VM to another zone or region generally means creating a new VM from a snapshot or machine image.

For SSH, gcloud compute ssh web-1 handles keys for you. There are two ways keys get authorized. With metadata-based SSH keys, public keys are stored in project or instance metadata, and anyone whose key is there can log in until someone removes it. With OS Login, Linux accounts are tied to Google identities: access is controlled by IAM roles such as Compute OS Login (regular user) or Compute OS Admin Login (sudo), it can require two-step verification, and removing a person's role or disabling their account removes their access. Enable it with the metadata key enable-oslogin=TRUE on the project or instance. OS Login is recommended for organizations.

Many VMs shouldn't have external IP addresses. To reach them without a bastion host or VPN, use Identity-Aware Proxy (IAP) TCP forwarding: gcloud compute ssh web-1 --tunnel-through-iap. IAP wraps the SSH connection in HTTPS and checks the user's IAM permission (IAP-secured Tunnel User) before forwarding traffic. Your firewall must allow ingress on tcp:22 (or 3389 for RDP) from IAP's range, 35.235.240.0/20. The same technique works for RDP to Windows VMs.

When SSH itself is broken, the serial console lets you interact with the VM's boot process and login prompt, if enabled. Serial port output (gcloud compute instances get-serial-port-output) shows boot logs and is safe to read without enabling interactive access.

Key terms

OS Login
A feature that ties Linux accounts on VMs to Google identities and controls SSH access with IAM roles.
IAP TCP forwarding
Tunneling SSH, RDP or other TCP traffic through Identity-Aware Proxy to VMs without external IPs.
35.235.240.0/20
The source range IAP TCP forwarding uses, which firewall rules must allow.
Serial console
Interactive access to a VM's serial port for troubleshooting when normal login fails.
Real-world example

A security team removes all external IPs from their VMs, enables OS Login at the project level and grants the ops group Compute OS Admin Login and IAP-secured Tunnel User. Admins now connect with gcloud compute ssh --tunnel-through-iap, and when someone leaves the company their access ends as soon as their account is disabled.

Exam tip: No external IP and no bastion: IAP TCP forwarding with a firewall rule for 35.235.240.0/20. Access tied to IAM and removed automatically: OS Login. Changing the machine type requires stopping the VM.

Check yourself

What must you do before changing a VM's machine type?

Stop the VM, change the type, then start it again.

Which IAM role lets a user connect through IAP TCP forwarding?

IAP-secured Tunnel User, together with a firewall rule allowing 35.235.240.0/20.
