Operating databases: Cloud SQL backups, high availability and read replicas, and BigQuery dry runs

▶ Watch the overview video

Last reviewed September 25, 2026

Cloud SQL handles much of database operations for you, but you choose the protection features. Automated backups run daily in a backup window you choose and are kept for a configurable number of days; you can also take on-demand backups before risky changes. Point-in-time recovery uses transaction logs (binary logs for MySQL, write-ahead logs for PostgreSQL) so you can restore to a specific moment, for example just before a bad DELETE. Restores go to a new or existing instance; they aren't instant failover.

High availability (HA), also called the regional configuration, runs a primary instance in one zone and a standby in another zone of the same region, with synchronous replication of the storage. If the primary or its zone fails, Cloud SQL fails over automatically to the standby, and clients keep using the same IP address after a short interruption. The standby doesn't serve reads. HA protects against zone failures, not against a mistake like dropping a table, which backups and point-in-time recovery cover.

Read replicas are copies of the primary that receive asynchronous replication and serve read-only queries. Use them to offload reporting or read-heavy traffic. Cross-region replicas also support disaster recovery: you can promote a replica to a standalone primary if a region is lost, though promotion is a manual, one-way action. Replicas need the primary to have backups and binary logging (for MySQL) enabled.

Other operations include connecting securely with the Cloud SQL Auth Proxy or connectors (which use IAM and encrypt traffic without managing SSL certificates or allowlisting IPs), using private IP in your VPC, scaling up the machine type (which requires a restart), and scheduling maintenance windows.

In BigQuery, the main operational concern is cost. With on-demand pricing you pay by bytes processed, so before running a large query run a dry run: bq query --use_legacy_sql=false --dry_run 'SELECT ...', or look at the query validator in the console, which reports how many bytes the query will process. Select only needed columns, filter on partitioned columns and use clustering; adding LIMIT doesn't reduce bytes scanned for a normal table. You can also set a maximum bytes billed limit on a query or cap usage with custom quotas.

Key terms

Point-in-time recovery
Restoring a database to a specific moment using backups plus transaction logs.
Cloud SQL high availability
A primary and a standby in different zones of a region with automatic failover.
Read replica
An asynchronously updated copy that serves read-only traffic and can be promoted manually.
Dry run
A BigQuery query validation that reports bytes to be processed without running or charging.
Real-world example

An e-commerce team runs Cloud SQL for PostgreSQL with HA for zone failures, point-in-time recovery for mistakes, and a read replica for its reporting tool. Analysts estimate every new BigQuery report with a dry run and add a partition filter when one query would have scanned 3 TB.

Exam tip: Automatic zone failover: HA. Offload reads: read replica. Undo a bad change: point-in-time recovery. Estimate BigQuery cost: dry run. LIMIT doesn't reduce bytes scanned.

Check yourself

Can a Cloud SQL HA standby serve read queries?

No. It only takes over on failover; use read replicas for reads.

What does a BigQuery dry run tell you?

Whether the query is valid and how many bytes it would process, without running it.
