Instance templates and managed instance groups: autoscaling, autohealing and rolling updates

▶ Watch the overview video

Last reviewed September 25, 2026 · Leer en español

An instance template is a saved VM definition: machine type, boot image, disks, network, metadata such as a startup script, labels and service account. Templates are immutable; to change anything you create a new template. You create one with gcloud compute instance-templates create web-v2 --machine-type=e2-medium --image-family=debian-12 --image-project=debian-cloud --tags=web --metadata-from-file=startup-script=start.sh.

A managed instance group (MIG) uses a template to create and maintain a set of identical VMs. A zonal MIG keeps its VMs in one zone; a regional MIG spreads them across zones in a region, which protects against a zone failure and is recommended for production. Unmanaged instance groups, by contrast, are just collections of existing, possibly different VMs that you manage yourself; they can sit behind a load balancer but don't autoscale or autoheal.

Autoscaling adds and removes VMs based on a signal: average CPU utilization, load balancer serving capacity, a Cloud Monitoring metric, or a schedule. You set minimum and maximum instance counts and a target, for example 60% CPU. A cool-down (initialization) period tells the autoscaler to ignore data from new VMs while they boot. For example: gcloud compute instance-groups managed set-autoscaling web-mig --region=us-central1 --min-num-replicas=2 --max-num-replicas=10 --target-cpu-utilization=0.6.

Autohealing uses an application health check, such as an HTTP request to /healthz. If a VM fails the check repeatedly, the MIG recreates it from the template. Set an initial delay long enough for the app to start, or the group may recreate VMs before they're ready. This is different from load balancer health checks, which only stop sending traffic to unhealthy backends.

To change the software or machine type, create a new template and start an update. A rolling update replaces VMs gradually, controlled by maxSurge (how many extra VMs may be created) and maxUnavailable (how many may be offline). You can also run a canary by setting a second template for a target size such as 10% of the group, and roll back by updating to the previous template. Because VMs in a MIG can be recreated at any time, keep them stateless and store data in databases or Cloud Storage; stateful MIGs exist for special cases.

Key terms

Instance template
An immutable definition of VM properties used to create VMs in a managed instance group.
Managed instance group
A group of identical VMs created from a template that supports autoscaling, autohealing and rolling updates.
Autohealing
Recreating VMs that fail an application health check.
Rolling update
Gradually replacing a group's VMs with ones from a new template, governed by maxSurge and maxUnavailable.
Real-world example

An online shop runs a regional MIG of 3 to 20 web servers that autoscales at 65% CPU. To patch the OS, the team builds a new image, creates template web-v8 and starts a rolling update with maxSurge 3 and maxUnavailable 0, so capacity never drops during the change.

Exam tip: You can't edit a template: new template, then rolling update. Autohealing needs a health check. Unmanaged groups don't autoscale.

Check yourself

What is the difference between a zonal and a regional MIG?

A zonal MIG keeps VMs in one zone; a regional MIG spreads them across zones in a region for higher availability.

Why set an initial delay on autohealing?

So the MIG doesn't recreate VMs that are still booting and haven't passed the health check yet.
