Explain it simpler

Every device on a network needs an address and a few settings, like where the exit to the internet is and which server looks up website names. DHCP hands those out automatically, so nobody has to type them in by hand. The device asks, a server offers an address, the device accepts, and the server confirms. The address is lent for a set time, not given forever, so it can be reused later. Picture a hotel front desk handing out room keys: you check in, get a room for a few nights, and the room goes to someone else after you leave. If the desk is closed or out of rooms, new guests wait in the lobby. A 169.254 address is that lobby: the device asked and got no answer.

It is 8:05 a.m. on the first day of a new training lab at Riverbend Community College. Twenty students open their laptops, and every one of them shows a 169.254 address and no internet. Down the hall, the library and the offices work fine. The instructor, Mr. Okafor, is standing in your doorway asking whether he should cancel the class. The DHCP server is up, it has a scope for the lab's new subnet, and nothing on it has changed since yesterday. Something between the lab and that server is missing. What is it, and how quickly can you find it?

Dynamic Host Configuration Protocol (DHCP) automatically gives hosts their Internet Protocol (IP) configuration: an address, subnet mask, default gateway, Domain Name System (DNS) servers and more. Without it, every device would need manual configuration, which is slow, error-prone and invites duplicate addresses. DHCP servers listen on User Datagram Protocol (UDP) port 67 and clients use UDP 68. DHCP problems are among the most common network faults, and the symptom is distinctive: a host that cannot get a lease falls back to an Automatic Private IP Addressing (APIPA) address in the 169.254.x.x range and cannot reach anything beyond its own segment.
